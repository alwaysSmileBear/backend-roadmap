    1부 데이터 시스템의 기초

    1장 신뢰성, 확장성, 유지보수성

    좋은 데이터 시스템의 세 가지 조건, 그리고 "부하"와 "성능"을 어떻게 정의하는가

    신뢰성 (Reliability)

    잘못돼도(결함, fault) 올바르게 동작하는 것. 결함(fault)은 구성 요소 하나가 어긋난 것, 장애(failure)는 시스템 전체가 서비스를 못 하는 것. 결함을 0으로 만들 수는 없으니 결함이 장애가 되지 않게(fault-tolerant) 설계해요.

    • 하드웨어 결함: 디스크 MTTF 10~50년 → 디스크 1만 개면 매일 하나 죽음. 중복(RAID, 다중 머신)으로.
    • 소프트웨어 결함: 특정 입력에 모든 인스턴스가 동시에 죽음(윤초 버그), 연쇄 장애. 하드웨어보다 상관관계가 높아 위험. 가정을 명시하고, 격리하고, 모니터링.
    • 인적 오류: 장애의 가장 큰 원인(설정 실수). 잘 설계된 추상화, 샌드박스, 쉬운 롤백, 상세한 모니터링.

    Netflix Chaos Monkey처럼 일부러 결함을 일으켜 내결함성을 검증하는 게 좋은 관행이에요.

    확장성 (Scalability)

    "부하가 늘어나도 대응할 수 있는가". 먼저 부하 매개변수를 정의해야 해요. 초당 요청 수, 읽기/쓰기 비율, 동시 사용자, 캐시 적중률. 트위터 예: 트윗 쓰기 4.6k/s, 타임라인 읽기 300k/s. 읽기가 압도적이라 쓸 때 팔로워의 타임라인 캐시에 미리 넣는(fan-out on write) 방식을 택했어요. 단, 팔로워 3천만 명인 유명인은 쓸 때 3천만 번 → 하이브리드(유명인은 읽을 때 합침).

    성능 기술하기

    배치는 처리량, 온라인은 응답 시간. 응답 시간은 분포예요. 평균은 쓸모없고 백분위(p50, p95, p99, p999)를 써요. p99가 중요한 이유: 가장 느린 요청을 겪는 사용자가 가장 많은 데이터를 가진 가치 높은 고객인 경우가 많아요(Amazon은 p999 기준). 그리고 꼬리 지연 증폭(tail latency amplification): 요청 하나가 백엔드 호출 10개를 병렬로 하면, 하나만 느려도 전체가 느려요. 백엔드 p99 = 1%라도, 10개 중 하나가 걸릴 확률은 약 10%.

    측정은 클라이언트 쪽에서. 서버에서 재면 큐에서 기다린 시간(head-of-line blocking)이 빠져요. 부하 테스트도 응답을 기다리지 말고 독립적으로 요청을 보내야 해요.

    확장 접근법

    수직 확장(scale up): 더 좋은 머신. 단순하지만 비용이 비선형으로 커지고 한계. 수평 확장(scale out): 머신 추가. 무상태 서비스는 쉽고, 상태(DB)는 어려워서 2부 전체가 이 얘기예요. 만능 아키텍처는 없고, 부하 매개변수에 맞춰야 해요. 조기에 분산하지 마세요.

    유지보수성

    • 운용성: 운영팀이 시스템을 쉽게 건강하게 유지. 모니터링, 자동화, 문서, 예측 가능한 동작.
    • 단순성: 우발적 복잡도 제거. 좋은 추상화.
    • 발전성: 요구사항 변경에 쉽게 적응. 4장 부호화와 연결.
    백엔드에서는 SLO를 "p99 응답 시간 300ms 이하, 가용성 99.9%"처럼 백분위로 정의하세요. 대시보드에 평균만 있으면 꼬리 문제가 안 보여요. 그리고 마이크로서비스에서 요청 하나가 서비스 5개를 거치면 꼬리 지연 증폭이 바로 생겨요. 헤지 요청(hedged request: 느리면 복제본에 한 번 더 보내기), 타임아웃, 병렬 호출 수 제한이 대응이에요.
    시니어 심화 본문은 꼬리 지연 증폭을 다뤘는데, 같은 곱셈이 가용성에도 그대로 적용돼요. 목표를 세울 때 가장 자주 틀리는 계산이에요.

    주문 API가 동기로 부르는 서비스가 다섯 개이고 각자 가용성이 99.9%라면, 주문 API가 정상일 확률은 0.999를 다섯 번 곱한 약 99.5%예요. 다섯 서비스가 각자 목표를 지켜도 주문 API는 한 달에 3.6시간 가까이 실패할 수 있어요. 의존성을 하나 추가할 때마다 내 목표를 깎는 셈이에요. 그래서 핵심 경로(주문, 결제)에서 동기로 부르는 의존성 수를 줄이고, 추천이나 리뷰 같은 부가 기능은 죽어도 핵심이 응답하도록 떼어 내요(실패하면 빈 결과로). 용량도 같은 방식으로 생각해요. 가용 영역 세 곳에 나눠 두었다면 한 곳이 통째로 빠져도 나머지 두 곳만으로 최대 부하를 받을 수 있어야 해요.

    핵심 정리
    • 결함 ≠ 장애. 결함을 견디게 설계. 인적 오류가 최대 원인
    • 부하 매개변수를 먼저 정의. 성능은 백분위로. 꼬리 지연 증폭
    • 수평 확장은 무상태는 쉽고 상태는 어려움 → 2부
    셀프 체크
    1. 백엔드 p99가 100ms인 서비스 5개를 병렬 호출하는 API의 p99는 왜 100ms가 아닌가요?
    2. 평균 응답 시간 50ms인데 사용자 불만이 많아요. 무엇을 봐야 하나요?
    답 보기

    1. 5개 중 하나라도 p99 이상으로 느리면 전체가 느려요. 각각 1% 확률이면 "모두 빠를" 확률은 0.99⁵ ≈ 95%, 즉 약 5%의 요청이 100ms를 넘어요. API의 p95가 백엔드의 p99 수준이 돼요. 병렬 호출이 많을수록 꼬리가 증폭돼요.

    2. p95, p99, p999. 평균 50ms여도 p99가 5초면 1%의 요청(활동 많은 사용자일수록 더 자주 겪음)이 5초예요. 그리고 서버 측이 아니라 클라이언트 측 측정값, 큐 대기 포함.

    2장 데이터 모델과 질의 언어

    관계형, 문서, 그래프 — 어떤 모델이 어떤 데이터에 맞는가

    관계형 vs 문서

    관계형(SQL)은 데이터를 테이블(관계)과 행으로, 문서(MongoDB 등)는 JSON 같은 자기 완결 문서로. NoSQL이 다시 나온 이유: 큰 데이터셋·높은 쓰기 처리량, 특정 질의에 최적화, 관계형의 제약 불만, 동적 스키마.

    • 객체-관계 불일치(impedance mismatch): 객체와 테이블 사이 변환. ORM이 줄이지만 못 없앰. 이력서 같은 일대다 트리 구조는 문서 하나가 자연스러움(지역성: 한 번에 읽음).
    • 다대일, 다대다: "지역 ID → 지역명"처럼 공유되는 데이터는 정규화(ID로 참조)가 맞고, 조인이 필요해요. 문서 DB는 조인이 약해서 애플리케이션에서 여러 번 조회하거나 비정규화(중복)해야 해요. 데이터가 연결될수록 관계형이 유리.

    스키마 유연성

    문서 DB는 "스키마리스"가 아니라 쓰기 스키마(schema-on-read): 읽을 때 구조를 해석. 관계형은 읽기 스키마(schema-on-write): 쓸 때 검증. 전자는 구조가 다양한 데이터(이기종 항목, 외부 시스템이 정한 구조)에, 후자는 모든 레코드가 같은 구조라고 기대할 때 유리. 스키마 변경: 관계형은 ALTER(MySQL은 과거에 느렸지만 8.0 INSTANT), 문서는 코드에서 옛 형식을 처리.

    지역성

    문서 전체를 자주 함께 읽으면 한 번의 디스크 접근으로 끝나는 지역성 이점. 반대로 일부만 읽어도 전체를 로드하고, 갱신 시 전체를 다시 써야 해요. 문서는 작게 유지. 관계형도 지역성을 흉내 내요(Oracle multi-table index cluster, Bigtable column family).

    수렴

    관계형 DB는 JSON 컬럼을, 문서 DB는 조인($lookup)과 트랜잭션을 추가했어요. 하이브리드가 추세.

    그래프 모델

    다대다 관계가 핵심일 때(소셜, 지식 그래프, 도로망). 정점과 간선. 속성 그래프(Neo4j, Cypher)와 트리플 저장소(SPARQL). SQL로도 재귀 CTE(WITH RECURSIVE)로 그래프 탐색이 되지만 Cypher가 훨씬 간결(4줄 vs 29줄). 다양한 관계가 섞여 있고 깊이를 모르는 탐색에 그래프 DB.

    질의 언어

    선언형(SQL, Cypher): "무엇을"만 말하고 옵티마이저가 "어떻게"를 결정 → 병렬화·최적화 가능. 명령형(IMS, 초기 MapReduce): 순서를 직접. 선언형이 거의 항상 이겨요. CSS 셀렉터가 선언형, DOM 순회 코드가 명령형인 것과 같아요.

    백엔드에서는 "MongoDB가 빠르다/쉽다"로 선택하면 나중에 조인과 트랜잭션 때문에 고생해요. 기준은 데이터의 모양: 자기 완결 문서가 대부분이고 관계가 적으면 문서 DB, 엔티티 간 관계가 많으면 관계형. 대부분의 비즈니스 데이터(주문·사용자·상품·결제)는 관계가 많아요. MySQL + JSON 컬럼으로 "부가 속성만 유연하게"가 현실적 타협인 경우가 많아요.
    시니어 심화 본문은 데이터 모양으로 DB를 고르라고 했는데, 실무에서 더 큰 비용은 저장소를 하나 더 들이는 것 자체예요. 기술 선택이 아니라 운영 부담을 지는 결정이에요.

    MongoDB든 Elasticsearch든 새 저장소를 들이면, 그 저장소의 백업과 복원 절차, 모니터링, 버전 업그레이드, 용량 계획, 그리고 장애가 났을 때 다룰 줄 아는 사람이 필요해요. 더 큰 문제는 데이터가 두 곳에 있게 되는 순간 둘 사이의 일관성(이중 쓰기, 11장)이 생긴다는 거예요. 그래서 기존 DB로 80%가 해결된다면 그쪽이 보통 이겨요. MySQL의 JSON 컬럼, PostgreSQL의 JSONB와 GIN 인덱스, 전문 검색 기능으로 "부가 속성만 유연하게", "간단한 검색은 DB에서"를 먼저 시도해 보고, 그것으로 정말 안 될 때 새 저장소를 들이세요.

    핵심 정리
    • 일대다 트리 = 문서 유리, 다대다·조인 많음 = 관계형 유리
    • schema-on-read vs schema-on-write
    • 선언형 질의가 옵티마이저와 병렬화를 가능하게 함
    셀프 체크
    1. 문서 DB에서 "지역명"을 문서마다 문자열로 넣는 것과 ID로 참조하는 것의 트레이드오프는?
    답 보기

    문자열 중복: 읽기는 한 번에 끝나지만, 지역명이 바뀌면 모든 문서를 갱신해야 하고 표기가 흩어져요(갱신 이상, DB 챕터 0장). ID 참조: 일관성은 좋지만 읽을 때 조인(문서 DB는 애플리케이션 조인)이 필요해요. 바뀌지 않는 값이면 중복이 괜찮고, 바뀌거나 공유되는 값은 참조.

    3장 저장소와 검색

    DB는 데이터를 어떻게 디스크에 쓰고 찾는가 — 로그 구조 vs 페이지 지향

    가장 단순한 DB

    파일 끝에 append(쓰기 O(1), 매우 빠름), 읽기는 전체 스캔(O(n)). 쓰기를 빠르게 유지하면서 읽기를 빠르게 하려면 인덱스가 필요하고, 인덱스는 쓰기를 느리게 해요. 모든 저장소 엔진은 이 트레이드오프 위에 있어요.

    해시 인덱스 (Bitcask)

    메모리 해시맵: 키 → 파일 오프셋. 쓰기는 append + 해시 갱신, 읽기는 해시 → 한 번 seek. 파일이 커지면 세그먼트로 나누고 컴팩션(최신 값만 남기기)·병합. 삭제는 tombstone. 장점: 쓰기 순차, 동시성·복구 단순. 한계: 모든 키가 메모리에, 범위 질의 불가.

    SSTable과 LSM 트리

    세그먼트를 키 순으로 정렬해 저장(Sorted String Table). 병합은 병합 정렬처럼 간단, 희소 인덱스(몇 KB마다 키 하나)로 메모리 절약, 범위 질의 가능. 쓰기가 들어오면:

    1. memtable(메모리, 균형 트리나 스킵 리스트)에 추가. 크래시 대비 WAL에도 append.
    2. memtable이 크면(수 MB) SSTable 파일로 flush(순차 쓰기).
    3. 읽기: memtable → 최신 SSTable → 오래된 SSTable 순. 없는 키는 전부 확인 → Bloom filter로 "없음"을 빨리 판단.
    4. 백그라운드 컴팩션: SSTable 병합, 덮어쓴 값·삭제 정리. 크기 계층(size-tiered)과 레벨(leveled) 전략.

    LevelDB, RocksDB, Cassandra, HBase, Lucene(역색인 세그먼트)이 이 구조. 쓰기 증폭(한 번 쓴 데이터가 컴팩션으로 여러 번 다시 써짐)이 있지만 순차 I/O라 B-Tree보다 쓰기 처리량이 높아요.

    B-Tree

    DB 챕터 8장. 고정 크기 페이지(4~16KB), 제자리 갱신, 높이 3~4. 크래시 복구는 WAL(redo log). 동시성은 래치. 읽기는 LSM보다 빠르고 예측 가능(키는 한 곳에만), 트랜잭션 격리 구현이 쉬움(범위 락). 쓰기는 페이지 전체를 다시 쓰고 랜덤 I/O.

    B-Tree vs LSM

    B-TreeLSM
    쓰기랜덤 I/O, WAL + 페이지순차 I/O, 처리량 높음, 압축 잘 됨
    읽기안정적 O(log n)여러 SSTable 확인, Bloom filter 의존
    지연예측 가능컴팩션이 가끔 높은 꼬리 지연 유발
    공간페이지 단편화컴팩션으로 공간 효율 좋음
    대표MySQL, PostgreSQL, OracleRocksDB, Cassandra, ScyllaDB, Kafka Streams

    기타 인덱스 구조

    • 클러스터드 vs 비클러스터드: DB 챕터 8.8. 커버링 인덱스.
    • 다중 컬럼: 결합 인덱스(순서 중요), 다차원(R-tree, 공간).
    • 전문 검색: 역색인 + 오타 허용(편집 거리, Lucene은 FST).
    • 인메모리 DB: Redis, VoltDB. 빠른 이유는 디스크 안 읽어서가 아니라(OS 캐시로 디스크 DB도 메모리에서 읽음) 디스크용 인코딩 오버헤드가 없어서. 그리고 우선순위 큐, 집합 같은 디스크에 구현하기 어려운 구조를 제공.

    OLTP vs OLAP, 컬럼 지향 저장

    OLTP(사용자 요청, 소량 행, 키 조회)와 OLAP(분석, 대량 행 집계, 소수 컬럼)는 접근 패턴이 달라 저장소도 달라요. 데이터 웨어하우스는 OLTP DB에서 ETL로 복사(별 모양 스키마: 사실 테이블 + 차원 테이블).

    컬럼 지향: 행 단위가 아니라 컬럼 단위로 파일 저장. "100억 행 중 3개 컬럼만 집계"가 그 3개 파일만 읽음. 같은 컬럼은 값이 비슷해 압축이 매우 잘 됨(비트맵 인코딩, run-length). CPU 캐시·SIMD에 유리(벡터화). 쓰기는 LSM 방식으로. Parquet, ClickHouse, BigQuery, Redshift. 구체화 뷰 / 데이터 큐브는 집계를 미리 계산.

    백엔드에서는 운영 DB(MySQL)에 분석 쿼리(월별 매출 집계, 풀스캔)를 돌리면 버퍼풀을 쓸어버리고 서비스가 느려져요. 분석은 복제본 → 웨어하우스(BigQuery, Redshift)나 ClickHouse로. 쓰기가 압도적인 데이터(이벤트 로그, 시계열, 메시지)는 LSM 기반(Cassandra, ScyllaDB, RocksDB 임베디드)을 고려하고, 읽기·트랜잭션 중심은 B-Tree. Elasticsearch가 "쓰기 직후 검색 안 됨"인 건 세그먼트가 refresh 주기(1초)로 생성되기 때문이고, LSM과 같은 구조예요.
    핵심 정리
    • 로그 구조(append + 컴팩션) vs 페이지 지향(제자리 갱신)
    • LSM = memtable + SSTable + Bloom filter + 컴팩션, 쓰기에 강함
    • B-Tree = 읽기 안정, 트랜잭션 친화
    • OLAP = 컬럼 지향 + 압축 + 벡터화
    셀프 체크
    1. LSM에서 "없는 키"를 조회하면 왜 느리고, 어떻게 해결하나요?
    2. 컬럼 지향 저장이 분석 쿼리에 빠른 두 가지 이유는?
    답 보기

    1. memtable부터 가장 오래된 SSTable까지 전부 확인해야 "없음"을 알 수 있어요. SSTable마다 디스크 접근. Bloom filter를 SSTable마다 두면 "확실히 없음"인 파일을 디스크 안 읽고 건너뛰어요.

    2. (1) 필요한 컬럼 파일만 읽어 I/O가 컬럼 수에 비례(행 지향은 모든 컬럼을 읽음). (2) 같은 컬럼은 값이 유사해 압축률이 높고, 연속 메모리라 CPU 캐시와 SIMD 벡터화에 유리.

    4장 부호화와 발전

    데이터 형식이 바뀌어도 시스템이 계속 돌아가게 — 호환성과 데이터플로

    왜 중요한가

    롤링 업그레이드(서버를 하나씩 교체)와 클라이언트의 느린 업데이트 때문에 구버전 코드와 신버전 코드, 구형식 데이터와 신형식 데이터가 동시에 존재해요. 그래서 두 방향 호환이 필요해요.

    • 하위 호환(backward): 새 코드가 옛 데이터를 읽음. 쉬움(옛 형식을 알고 있음).
    • 상위 호환(forward): 옛 코드가 새 데이터를 읽음. 어려움(모르는 필드를 무시해야).

    부호화 형식

    • 언어 내장(Java Serializable, pickle): 다른 언어에서 못 읽고, 보안 취약(역직렬화 공격), 버전 관리 어려움. 쓰지 마세요.
    • JSON, XML, CSV: 사람이 읽음, 널리 지원. 숫자 정밀도 문제(JS는 2⁵³ 초과 정수 깨짐 → 큰 ID는 문자열로), 바이너리 미지원(base64), 스키마 선택적. 공개 API의 표준.
    • Thrift, Protocol Buffers: 스키마(IDL) 필수, 필드에 태그 번호. 바이너리라 작고 빠름. 호환 규칙: 태그 번호는 절대 바꾸지 않고, 새 필드는 optional/기본값, 삭제는 태그 재사용 금지. gRPC가 protobuf.
    • Avro: 태그 없이 writer 스키마와 reader 스키마를 둘 다 알고 변환. 스키마 레지스트리로 버전 관리. 동적 생성 스키마(DB 덤프)에 유리. Kafka 생태계 표준.

    스키마의 가치: 문서 역할, 호환성을 도구로 검사, 코드 생성(정적 타입). 바이너리 JSON(MessagePack, BSON)은 크기만 약간 줄 뿐 스키마 이점이 없어요.

    데이터플로 세 가지

    1. DB를 통해: 쓰는 프로세스가 부호화, 읽는 프로세스가 복호화. "미래의 자신에게 메시지". 옛 코드가 새 필드가 있는 행을 읽고 다시 쓸 때 모르는 필드를 보존해야 해요(ORM이 조용히 지우는 경우 있음). 스키마 마이그레이션: 컬럼 추가는 기본값 NULL로 옛 행을 안 고쳐도 됨.
    2. 서비스 호출(REST, RPC): 서버를 먼저 업데이트하고 클라이언트를 나중에 → 요청은 하위 호환, 응답은 상위 호환 필요. RPC의 문제: 네트워크 호출은 로컬 호출과 근본적으로 다름(실패·타임아웃·재시도·멱등성·지연). REST는 그걸 숨기지 않고, gRPC는 비동기·스트림을 명시. 공개 API는 REST(JSON), 내부는 gRPC/Thrift가 흔해요. 버전 관리: URL/헤더(REST), 필드 호환 규칙(protobuf).
    3. 메시지 전달(비동기): 브로커(Kafka, RabbitMQ)가 중간에. 장점: 수신자가 죽어도 버퍼링, 송신자는 응답 안 기다림, 1:N 가능, 송수신 분리. 메시지 포맷도 호환성 필요. 11장에서 자세히. 액터 모델(Akka, Erlang)은 메시지 전달을 프로그래밍 모델로.
    백엔드에서는 API 응답 JSON에 필드를 추가하는 건 안전(클라이언트가 모르는 필드 무시), 삭제·이름 변경·타입 변경은 호환성 파괴예요. 요청 필수 필드 추가도 파괴. "필드는 추가만, 삭제는 deprecate 후 충분히 지나서". Jackson은 기본으로 모르는 필드에 실패하니 FAIL_ON_UNKNOWN_PROPERTIES=false. Kafka 메시지 스키마는 Schema Registry + Avro/Protobuf로 호환성 검사를 CI에 넣으세요. 그리고 Java 직렬화(ObjectInputStream)는 세션 저장·캐시에 쓰지 마세요(보안, 버전).
    시니어 심화 본문은 "필드는 추가만"이라는 규칙을 다뤘는데, 롤링 배포를 하면 롤백도 호환성 시나리오가 된다는 점을 놓치기 쉬워요.

    새 버전이 이벤트에 새 형식으로 쓰기 시작했는데 문제가 생겨 옛 버전으로 롤백했다고 해 봐요. 옛 버전은 이미 저장된 새 형식의 데이터를 읽지 못해서, 롤백한 순간부터 에러가 나요. 앞으로도 뒤로도 못 가는 상태예요. 그래서 형식을 바꾸는 배포는 두 단계로 나눠요. 먼저 "새 형식도 읽을 수 있는" 버전을 배포하고, 그 버전이 안정된 것을 확인한 뒤에 "새 형식으로 쓰기"를 켜요. 그러면 두 번째 단계를 되돌려도 첫 번째 버전이 새 형식을 읽을 수 있어요. enum에 값을 추가하는 것도 같아요. 옛 소비자가 모르는 값을 만나면 역직렬화에서 실패하니, 모르는 값을 기본값으로 받도록 소비자를 먼저 고친 뒤에 값을 추가해요.

    핵심 정리
    • 신구 코드·데이터 공존 → 하위 + 상위 호환 모두 필요
    • JSON(공개), Protobuf/Avro(내부·메시지). 언어 내장 직렬화 금지
    • 데이터플로: DB(모르는 필드 보존), RPC(네트워크는 다름), 메시지(분리)
    셀프 체크
    1. Protobuf에서 필드를 삭제한 뒤 그 태그 번호를 새 필드에 재사용하면 무슨 일이?
    2. 롤링 배포 중 옛 서버가 새 클라이언트의 요청을 받아요. 어떤 호환성이 필요한가요?
    답 보기

    1. 옛 데이터(또는 옛 코드가 보낸 메시지)에 그 태그로 저장된 옛 필드 값이 새 코드에서 새 필드로 해석돼요. 타입이 같으면 엉뚱한 값, 다르면 파싱 오류. 태그는 영구 예약(reserved).

    2. 옛 서버가 새 요청을 읽어야 하니 요청의 상위 호환(새 필드 무시), 그리고 새 클라이언트가 옛 응답을 읽어야 하니 응답의 하위 호환(없는 필드에 기본값). 보통은 서버를 먼저 올려 반대 방향만 신경 쓰지만, 롤링 중엔 둘 다.

    2부 분산 데이터

    5장 복제

    같은 데이터를 여러 머신에 — 리더 기반, 다중 리더, 리더 없는 복제와 그 문제들

    왜 복제하나

    지리적 근접(지연 감소), 장애 시 가용성, 읽기 확장. 어려운 부분은 변경을 다루는 것. 데이터가 안 바뀌면 복사만 하면 돼요.

    리더 기반 복제 (single-leader)

    쓰기는 리더만, 팔로워는 리더의 복제 로그를 적용. 읽기는 아무 곳. MySQL, PostgreSQL, MongoDB, Kafka. DB 챕터 16장.

    • 동기 vs 비동기: 동기는 팔로워 확인 후 커밋(유실 없음, 팔로워 죽으면 쓰기 멈춤). 비동기는 안 기다림(리더 죽으면 유실). 실무는 반동기(하나만 동기) 또는 전부 비동기.
    • 새 팔로워 추가: 리더 스냅샷 + 그 시점 이후 로그 적용.
    • 팔로워 장애: 로그 위치부터 따라잡기.
    • 리더 장애 → 장애 조치(failover): 타임아웃으로 감지 → 새 리더 선출(가장 최신 팔로워) → 클라이언트와 팔로워를 새 리더로. 문제들: 비동기면 새 리더에 없는 쓰기가 유실(GitHub 사고: MySQL 자동증가 ID가 Redis와 어긋남), 스플릿 브레인(리더 둘), 타임아웃을 얼마로(짧으면 불필요한 조치, 길면 복구 지연). 그래서 수동 장애 조치를 선호하는 팀도 많아요.
    • 복제 로그 구현: 구문 기반(비결정적 함수 문제), WAL 전송(저장소 포맷 종속, 버전 다르면 불가), 논리적(행) 로그(독립적, CDC 가능), 트리거 기반.

    복제 지연 문제

    비동기 팔로워는 뒤처져요. 최종적 일관성: 언젠가는 같아짐. "언젠가"가 몇 초~몇 분이면 사용자가 겪는 문제:

    • 자신의 쓰기 읽기(read-your-writes): 글 쓰고 새로고침했는데 없음. 해결: 자기가 수정한 데이터는 리더에서 읽기, 쓴 뒤 1분간 리더, 클라이언트가 마지막 쓰기 타임스탬프를 보내 그 이후 팔로워만 사용.
    • 단조 읽기(monotonic reads): 첫 번째는 최신 팔로워, 두 번째는 뒤처진 팔로워에서 읽어 시간이 거꾸로. 해결: 같은 사용자는 같은 복제본(해시).
    • 일관된 순서로 읽기(consistent prefix reads): 질문보다 답이 먼저 보임(파티션마다 지연 다름). 해결: 인과 관계 있는 쓰기는 같은 파티션.

    이 보장들을 애플리케이션이 직접 구현하면 복잡해요. 트랜잭션(7장)이 DB가 이걸 대신해 주는 방법인데, 분산 환경에서 많은 시스템이 포기했어요.

    다중 리더 복제

    여러 데이터센터에 각각 리더. 각 DC 안은 single-leader, DC 간은 비동기. 장점: 지연 짧음, DC 장애 독립, 네트워크 문제 견딤. 단점: 같은 데이터를 두 리더가 동시에 수정 → 쓰기 충돌. 오프라인 앱(캘린더 동기화), 협업 편집(Google Docs)도 다중 리더.

    충돌 해결: 피하기(같은 레코드는 같은 리더), 최종 쓰기 승리(LWW)(타임스탬프 큰 것, 데이터 유실), 복제본 ID 우선, 값 병합(문자열 연결), 애플리케이션 콜백, CRDT(자동 병합 가능한 자료구조). 토폴로지: 원형, 별, 전체 연결(인과 순서 문제 → 버전 벡터).

    리더 없는 복제 (leaderless)

    Dynamo, Cassandra, Riak. 클라이언트가 여러 복제본에 동시에 쓰고 읽어요. n개 중 w개 쓰기 성공, r개 읽기 응답, w + r > n이면 최신 값을 포함한 노드를 최소 하나 읽음(쿼럼). 보통 n=3, w=r=2. 죽었던 노드는 읽기 복구(읽을 때 옛 값 발견하면 갱신)와 안티 엔트로피(백그라운드 비교)로 따라잡아요.

    쿼럼의 한계: 느슨한 쿼럼(sloppy quorum, 다른 노드에 임시 저장 → 힌트 핸드오프)이면 보장 깨짐, 동시 쓰기 충돌, 쓰기 일부만 성공, 타이밍. 그래서 "쿼럼 = 선형성"이 아니에요. 동시성 감지는 버전 번호·버전 벡터로, 병합은 애플리케이션이(장바구니 합집합, 삭제는 tombstone).

    백엔드에서는 MySQL 복제본 읽기를 도입하면 read-your-writes 위반이 즉시 나타나요. "쓴 직후 조회 API"가 어디로 가는지 설계에 포함하세요. Aurora는 복제 지연이 ms 단위라 덜 겪지만 0이 아니에요. Cassandra/DynamoDB를 쓸 때 일관성 수준(ONE/QUORUM/ALL, DynamoDB의 strongly consistent read)이 바로 이 r/w 설정이에요. 그리고 장애 조치는 RDS Multi-AZ가 자동으로 하지만 그 수십 초 동안 쓰기가 실패하니 재시도와 커넥션 풀 재연결(failover 시 DNS 캐시!)이 준비돼야 해요.
    시니어 심화 본문은 쓰기 직후 조회가 어디로 가는지 설계하라고 했는데, read-your-writes를 구현하는 방법은 여러 가지이고 각자 다른 비용을 내요.

    가장 단순한 것은 자기 데이터 조회(내 주문, 내 프로필)는 항상 리더에서 읽는 거예요. 리더 부하가 늘지만 구현이 쉬워요. 다음은 쓰기를 한 사용자의 요청만 일정 시간(예: 10초) 리더로 보내는 거예요. 세션이나 쿠키에 "최근 쓰기 시각"을 표시해 두면 돼요. 가장 정교한 것은 쓰기가 돌려준 위치(MySQL의 GTID, PostgreSQL의 LSN)를 받아 두고, 복제본이 그 위치까지 따라왔는지 확인한 뒤에 복제본에서 읽는 거예요. 리더 부하는 가장 적지만 구현이 복잡해요. 서비스 전체에 하나를 고르기보다, 화면마다 "방금 쓴 것이 바로 보여야 하는가"를 묻고 필요한 곳에만 적용하세요.

    핵심 정리
    • single-leader: 단순, 장애 조치가 어려움(유실, 스플릿 브레인)
    • 복제 지연 → read-your-writes, 단조 읽기, 일관된 순서. 앱이 대응
    • multi-leader: 지리 분산, 쓰기 충돌 해결 필요(LWW는 유실)
    • leaderless: 쿼럼 w+r>n, 하지만 선형성 보장은 아님
    셀프 체크
    1. 자동 장애 조치에서 "스플릿 브레인"이 무엇이고 왜 위험한가요?
    2. n=3, w=1, r=3은 어떤 성격의 설정인가요?
    답 보기

    1. 네트워크 단절로 옛 리더가 살아 있는데 새 리더가 선출돼 리더가 둘이 되는 상황. 둘 다 쓰기를 받으면 데이터가 갈라지고 병합이 불가능해요. 펜싱(옛 리더 강제 종료, STONITH)이나 8장의 펜싱 토큰으로 막아요.

    2. 쓰기는 한 노드만 성공하면 되니 빠르고 가용성 높음, 읽기는 셋 다 응답해야 하니 느리고 하나만 죽어도 읽기 불가. 쓰기 위주, 읽기 드문 워크로드(로그 수집)에 맞아요. w+r=4>3이라 최신 값은 읽어요.

    6장 파티셔닝

    데이터를 여러 노드에 나누기 — 키 범위, 해시, 핫스팟, 보조 색인, 리밸런싱

    목적

    한 노드에 안 들어가는 데이터와 부하를 나눠요(샤딩). 보통 복제와 함께(파티션마다 리더 + 팔로워). 목표: 부하를 고르게. 한 파티션에 몰리면 핫스팟(skew).

    키-값 파티셔닝

    • 키 범위: 백과사전처럼 A~C는 1번, D~F는 2번. 범위 질의가 효율적(연속된 키가 같은 파티션). 하지만 타임스탬프 키면 오늘 쓰기가 전부 한 파티션 → 핫스팟. 해결: 키 앞에 다른 것(센서 ID)을 붙임.
    • 해시: hash(key)로 파티션 결정. 고르게 분산, 범위 질의 불가(인접 키가 흩어짐). Cassandra는 복합 PK의 첫 컬럼만 해시, 나머지는 정렬 → (user_id, timestamp)면 사용자별 시간 범위 질의 가능.
    • 핫 키: 유명인의 게시물에 수백만 반응. 해시로도 못 나눔. 애플리케이션이 키에 랜덤 숫자를 붙여 100개로 쪼개고 읽을 때 합침(쓰기 분산, 읽기 비용 증가).

    보조 색인 파티셔닝

    "색상이 빨강인 차"처럼 PK가 아닌 조건으로 찾으려면 보조 색인이 필요한데, 분산하면 두 방식:

    • 문서 기준(local index): 각 파티션이 자기 데이터의 색인만. 쓰기는 한 파티션, 읽기는 모든 파티션에 질의 후 합침(scatter/gather). 꼬리 지연 증폭. MongoDB, Elasticsearch, Cassandra.
    • 용어 기준(global index): 색인 자체를 용어로 파티셔닝(빨강은 1번 파티션). 읽기는 한 파티션, 쓰기는 여러 파티션의 색인 갱신(분산 트랜잭션 필요 → 보통 비동기). DynamoDB GSI.

    리밸런싱

    노드 추가·제거 시 파티션 이동. 요건: 이동 후 부하 균등, 이동 중에도 서비스, 이동량 최소. hash % N은 최악(N 바뀌면 대부분 이동, DSA 챕터 4장).

    • 고정 파티션 수: 노드보다 훨씬 많은 파티션(1000개)을 미리 만들고 노드에 배분. 노드 추가 시 파티션 몇 개를 통째로 옮김. Riak, Elasticsearch(샤드 수 고정!), Kafka. 처음에 수를 잘 정해야 함.
    • 동적 파티셔닝: 파티션이 크면 둘로 분할, 작으면 병합(B-Tree처럼). HBase, MongoDB. 초기엔 파티션이 1개라 한 노드에 몰림 → 사전 분할.
    • 노드 비례: 노드당 고정 파티션 수. Cassandra vnode.

    자동 리밸런싱은 편하지만 위험해요(과부하 노드를 느리다고 오판 → 리밸런싱 → 더 과부하 → 연쇄). 사람이 확인하는 반자동이 안전.

    요청 라우팅

    클라이언트가 어느 노드에 물어볼지: (1) 아무 노드나 → 전달, (2) 라우팅 계층(프록시), (3) 클라이언트가 파티션 맵을 앎. 파티션 배치 정보는 ZooKeeper 같은 코디네이션 서비스(9장)나 가십 프로토콜로 공유.

    백엔드에서는 Kafka 토픽의 파티션 수는 나중에 늘리면 키 → 파티션 매핑이 바뀌어 순서 보장이 깨져요. 처음에 넉넉히. Elasticsearch 인덱스의 primary shard 수도 변경 불가(reindex 필요). DB 샤딩에서 샤드 키는 "대부분의 쿼리가 샤드 키를 조건으로 갖는가"로 정하고(보통 user_id, tenant_id), 샤드 키 없는 조회는 scatter/gather라 느리고 꼬리 지연이 커요. 샤딩은 조인·트랜잭션·유니크 제약을 전부 애플리케이션으로 옮기는 거라 최후의 수단이에요.
    핵심 정리
    • 키 범위 = 범위 질의 OK·핫스팟 위험, 해시 = 균등·범위 불가
    • 보조 색인: local(쓰기 쉬움, 읽기 scatter) vs global(읽기 쉬움, 쓰기 분산)
    • 리밸런싱: 고정 파티션 수 또는 동적. % N 금지
    셀프 체크
    1. 타임스탬프를 파티션 키로 쓰면 생기는 문제와 해결책은?
    2. user_id로 샤딩된 주문 DB에서 "특정 상품의 주문 목록"을 조회하면?
    답 보기

    1. 키 범위 파티셔닝이면 현재 시각의 쓰기가 전부 마지막 파티션에 몰려 핫스팟. 해결: 키 앞에 다른 식별자(센서 ID, 사용자 ID)를 붙여 (device, timestamp)로 분산하되 device별 시간 범위 질의는 유지. 또는 해시 파티셔닝 + 파티션 안에서 시간 정렬.

    2. 샤드 키(user_id)가 조건에 없으니 모든 샤드에 질의하고 합쳐야 해요(scatter/gather). 느리고 샤드 하나만 느려도 전체가 느려요. 자주 필요하면 product_id 기준 global 보조 색인(별도 테이블/검색 엔진에 비동기 복제)을 두거나, 그 조회는 분석 DB로.

    7장 트랜잭션

    ACID의 진짜 의미, 약한 격리 수준의 함정들, 직렬성을 구현하는 세 가지 방법

    ACID 다시 보기

    • 원자성: "전부 아니면 전무". 중단 가능성(abortability)이 더 정확한 이름. 실패 시 안전하게 재시도 가능.
    • 일관성: 애플리케이션의 불변식. DB가 아니라 애플리케이션의 속성. ACID에서 C는 끼워 넣은 것.
    • 격리성: 동시 트랜잭션이 서로 안 보임. 이론적으로 직렬성(하나씩 실행한 것과 같은 결과)이지만 비싸서 대부분 약한 격리.
    • 지속성: 커밋되면 안 사라짐. 하지만 완벽한 지속성은 없어요(디스크·백업·복제 모두 실패 가능). 위험 감소 기법들의 조합.

    단일 객체 연산(한 행 갱신)은 거의 모든 DB가 원자적. 문제는 다중 객체(여러 행·테이블·파티션). 재시도 시 주의: 커밋됐는데 응답 유실이면 중복 실행 → 멱등성 필요(부록).

    약한 격리 수준

    수준막는 것못 막는 것구현
    Read Committeddirty read, dirty writeread skew, lost update, write skew, phantom쓰기는 행 락, 읽기는 커밋된 옛 값 보관
    Snapshot Isolation (RR)+ read skew(비반복 읽기)lost update(DB마다), write skew, phantomMVCC: 트랜잭션 시작 시점 스냅샷. 읽기는 쓰기 안 막고, 쓰기는 읽기 안 막음
    Serializable전부-아래 세 가지

    갱신 손실 (Lost Update)

    읽기 → 수정 → 쓰기 사이클 두 개가 겹쳐 하나가 사라짐(카운터 증가, 위키 편집). 해결: 원자적 쓰기(UPDATE SET v = v + 1), 명시적 잠금(FOR UPDATE), 자동 감지(PostgreSQL RR, Oracle은 감지해 중단; MySQL InnoDB RR은 감지 안 함), compare-and-set(UPDATE ... WHERE v = old), 충돌 해결(복제 환경).

    쓰기 스큐 (Write Skew)와 팬텀

    의사 당직 예: 최소 1명 유지 규칙. Alice와 Bob이 동시에 "당직 2명 이상?"을 확인(각자 스냅샷에서 2명) → 둘 다 빠짐 → 0명. 서로 다른 객체를 갱신해서 lost update가 아니고, 스냅샷 격리로 못 막아요. 패턴: SELECT로 조건 확인 → 그 결과에 따라 INSERT/UPDATE/DELETE → 사이에 조건이 바뀜. 회의실 예약, 사용자명 중복, 잔고 두 번 인출 전부 이거예요. 조건이 "없음"을 확인하는 경우면 잠글 행이 없어서(팬텀) FOR UPDATE도 못 써요.

    해결: 직렬성, 또는 충돌 구체화(회의실×시간 슬롯 테이블을 미리 만들어 그 행을 잠금), 유니크 제약(사용자명).

    직렬성 구현

    1. 실제 순차 실행: 단일 스레드로 하나씩. 메모리에 다 들어가고 트랜잭션이 짧으면(스토어드 프로시저로 왕복 제거) 가능. VoltDB, Redis(단일 스레드 명령). 파티션 간 트랜잭션은 느림.
    2. 2단계 잠금(2PL): 읽기는 공유 락, 쓰기는 배타 락, 트랜잭션 끝까지 유지. 읽기가 쓰기를 막고 쓰기가 읽기를 막음(스냅샷 격리와 반대). 팬텀은 술어 락(조건에 맞는 모든 행) 또는 근사인 색인 범위 락(InnoDB 넥스트 키 락). 처리량 낮고 꼬리 지연 큼, 데드락 잦음. MySQL SERIALIZABLE이 이것.
    3. 직렬성 스냅샷 격리(SSI): 낙관적. 스냅샷 격리로 실행하다 커밋 시 "내가 읽은 것을 다른 트랜잭션이 바꿨는가"를 검사해 충돌이면 중단. 읽기가 쓰기를 안 막아 처리량 좋음, 경합 심하면 중단 많음. PostgreSQL SERIALIZABLE, FoundationDB, CockroachDB.
    백엔드에서는 "확인 후 실행" 로직(재고 확인, 중복 체크, 잔고 확인, 예약 가능 확인)은 전부 write skew 후보예요. 격리 수준을 올려도 MySQL RR은 못 막아요. 대책 우선순위: (1) DB 제약(UNIQUE, CHECK)으로 불변식을 DB에, (2) 원자적 UPDATE with 조건, (3) FOR UPDATE로 확인 대상 행 잠금, (4) 충돌 구체화(슬롯 테이블), (5) 분산 락(Redis). JPA @Version은 lost update만 막고 write skew는 못 막아요.
    시니어 심화 본문은 확인 후 실행 로직의 대책을 나열했는데, 격리 수준으로 해결하려 할 때 함정은 같은 이름의 격리 수준이 DB마다 다르게 동작한다는 거예요.

    MySQL의 REPEATABLE READ는 갱신 손실을 자동으로 막지 않고, PostgreSQL의 REPEATABLE READ는 같은 행을 동시에 고치면 한쪽을 에러로 중단시켜요(PostgreSQL 챕터 5장). Oracle의 SERIALIZABLE은 실제로는 스냅샷 격리라 쓰기 왜곡을 막지 못해요. 그래서 "SERIALIZABLE로 올리면 안전하다"는 DB에 따라 맞기도 틀리기도 해요. DB를 바꾸거나 여러 DB를 쓴다면 갱신 손실, 쓰기 왜곡, 팬텀을 각각 재현하는 작은 테스트를 만들어 직접 확인하세요. 그리고 직렬성을 보장하는 DB는 충돌을 에러로 알려 주니 트랜잭션 전체를 처음부터 다시 실행하는 재시도가 필수예요. 이전 시도에서 읽어 둔 값을 재사용하면 재시도의 의미가 없어요.

    핵심 정리
    • C는 앱 책임. 다중 객체·재시도·멱등성이 어려운 부분
    • RC → SI(스냅샷) → Serializable. SI도 lost update(MySQL)·write skew·phantom 못 막음
    • write skew = 확인 후 실행. 제약·원자적 갱신·잠금·구체화로
    • 직렬성: 순차 실행, 2PL(비관), SSI(낙관)
    셀프 체크

    2. 2PL과 SSI의 차이를 "누가 누구를 막는가"로 설명하세요.
    답 보기

    1. 두 트랜잭션이 각자 스냅샷에서 "없음"을 확인 → 둘 다 INSERT → 중복. 잠글 행이 없어 FOR UPDATE 불가(팬텀). 해결: username에 UNIQUE 제약을 두고 두 번째 INSERT가 실패하게. 가장 단순하고 확실해요. 애플리케이션 확인은 UX용일 뿐 보장이 아니에요.

    2. 2PL(비관적): 읽기 락이 쓰기를 막고 쓰기 락이 읽기를 막아요. 충돌 가능성만 있어도 기다려요. SSI(낙관적): 아무도 안 막고 진행하다 커밋 시 "내가 읽은 데이터가 바뀌었나"를 검사해 충돌한 트랜잭션만 중단. 경합이 적으면 SSI가 훨씬 빠르고, 심하면 중단·재시도 비용이 커요.

    8장 분산 시스템의 골칫거리

    네트워크, 시계, 프로세스 중단 — 분산에서 "확실한 것"은 없다

    부분 실패

    단일 머신은 전부 동작하거나 전부 죽어요(결정적). 분산 시스템은 일부가 예측 불가능하게 실패하고, 심지어 실패했는지조차 알 수 없어요. 슈퍼컴퓨터는 체크포인트 후 전체 재시작, 클라우드는 부분 실패를 견디며 계속 동작해야 해요. "의심스러운 상황에서도 동작하는 소프트웨어"가 목표.

    신뢰할 수 없는 네트워크

    비동기 패킷 네트워크: 패킷은 유실·지연·순서 바뀜·중복될 수 있고, 응답이 없으면 요청이 유실됐는지, 상대가 죽었는지, 응답이 유실됐는지 구분 불가. 네트워크 결함은 흔해요(데이터센터에서 월 12건, 상어가 해저 케이블 물기, 잘못된 스위치 설정, 한 방향만 끊김).

    • 결함 감지: 포트 닫힘(RST), 프로세스 죽음(OS가 알림), 스위치 링크 다운은 빨리 알 수 있지만, 그 외는 타임아웃뿐.
    • 타임아웃 길이: 짧으면 느린 노드를 죽었다고 오판(작업 중복, 연쇄 장애), 길면 복구 지연. 네트워크 지연은 큐잉(스위치 버퍼, OS 큐, 가상화 CPU 스틸, TCP 재전송) 때문에 무한히 변동. 그래서 고정값 대신 측정된 분포로 동적 조정(Phi Accrual Failure Detector, TCP RTO).
    • 동기(전화망, 회선 예약, 지연 보장) vs 비동기(인터넷, 패킷 교환, 활용도 최대화). 인터넷은 후자를 택했고 지연 보장이 없어요.

    신뢰할 수 없는 시계

    • 일 기준 시계(time-of-day): 벽시계. NTP로 동기화되지만 뒤로 갈 수 있음(점프). 경과 시간 측정에 부적합.
    • 단조 시계(monotonic): 항상 증가, 절대값 무의미. 경과 시간·타임아웃에 사용(System.nanoTime()).
    • 시계는 드리프트(수정 진동자, 하루 수십 ms~초), NTP 서버 오류, 윤초, 가상 머신 일시 정지로 어긋나요. Google은 수백 ms 어긋난 시계를 흔하다고 가정.
    • 타임스탬프로 순서 정하기(LWW)는 위험: 시계가 느린 노드의 쓰기가 "과거"로 분류돼 조용히 사라져요. 인과 관계는 논리 시계(Lamport, 버전 벡터)로.
    • 신뢰 구간: Google Spanner TrueTime은 시각을 [earliest, latest] 구간으로 주고, 겹치지 않을 때만 순서를 확정(커밋 대기). GPS+원자시계 필요.

    프로세스 중단

    리더가 "나는 리더야, 임대(lease)가 10초 남았어"라고 확인한 직후 GC로 15초 멈추면? 깨어났을 땐 다른 노드가 리더인데 자기가 리더인 줄 알고 쓰기해요. 중단 원인: stop-the-world GC, VM 일시 정지/마이그레이션, 노트북 덮개, 컨텍스트 스위치, 디스크 I/O 대기(페이지 폴트, 스왑), 시그널. 어느 시점에든 임의 시간 동안 멈출 수 있고, 스레드는 그걸 몰라요. 실시간 OS가 아니면 보장 불가.

    지식, 진실, 거짓말

    • 진실은 다수결: 노드 자신의 판단("난 살아 있어")은 믿을 수 없고, 쿼럼(과반수)이 결정. 다수가 죽었다고 하면 죽은 것.
    • 펜싱 토큰: 락/임대를 줄 때마다 증가하는 토큰을 함께 주고, 저장소가 더 작은 토큰의 쓰기를 거부. GC로 멈췄던 옛 리더(토큰 33)가 쓰려 해도 새 리더(34)가 이미 썼으면 거절. 클라이언트가 스스로 멈추는 걸 믿지 말고 서버가 검사.
    • 비잔틴 결함: 노드가 거짓말함(해킹, 하드웨어 오류). 블록체인·항공·우주 영역. 보통의 데이터센터는 비잔틴 내성 불필요, 하지만 체크섬·입력 검증 같은 약한 방어는 필요.
    • 시스템 모델: 타이밍(동기/부분 동기/비동기) × 노드 결함(crash-stop/crash-recovery/비잔틴). 알고리즘의 정확성은 모델 가정 위에서만 성립. 안전성(나쁜 일이 안 일어남, 항상 지켜야)과 활동성(좋은 일이 결국 일어남, 조건부 허용).
    백엔드에서는 Redis 분산 락(SET NX PX)이 "GC 중단 + 락 만료 + 다른 클라이언트 획득 + 옛 클라이언트 깨어나 쓰기"로 깨지는 게 이 장의 예 그대로예요. Redlock 논쟁의 핵심. 중요한 자원은 DB의 조건부 갱신(펜싱 토큰 = version)으로 최종 방어하세요. 타임아웃은 "서비스별 p99 × 여유"로 정하고, 재시도는 지수 백오프 + 지터. 그리고 로그 타임스탬프로 "A가 B보다 먼저"를 판단하지 마세요. 서버마다 시계가 달라요. 분산 트레이싱이 인과 관계를 ID로 추적하는 이유예요.
    핵심 정리
    • 부분 실패 + 응답 없음의 원인 구분 불가 → 타임아웃뿐, 동적 조정
    • 벽시계는 점프, 단조 시계로 경과 측정. LWW는 유실
    • 프로세스는 언제든 임의로 멈춤(GC) → 임대는 믿을 수 없음
    • 진실은 쿼럼, 펜싱 토큰으로 옛 리더 거부
    셀프 체크
    1. Redis 락으로 보호한 임계 구역이 GC 때문에 깨지는 시나리오와 펜싱 토큰 해결책을 설명하세요.
    2. 타임아웃을 요청마다 고정 5초로 두면 생기는 두 가지 문제는?
    답 보기

    1. 클라이언트 A가 락(TTL 10초) 획득 → 15초 GC 멈춤 → 락 만료 → B가 락 획득 후 쓰기 → A 깨어나 자기가 락 가진 줄 알고 쓰기 → B의 쓰기 덮어씀. 펜싱: 락 서비스가 획득마다 증가하는 토큰(A=33, B=34)을 주고, 저장소가 토큰을 기록해 33 < 34면 A의 쓰기를 거부. DB라면 UPDATE ... WHERE fencing_token < 33 식의 조건부 갱신.

    2. (1) 평소 100ms인 서비스가 5초까지 느려져도 감지 못 해 스레드가 5초씩 묶임(풀 고갈). (2) 평소 3초인 서비스는 약간만 느려져도 타임아웃돼 불필요한 재시도·장애 판정, 부하 증가로 연쇄. 서비스별 지연 분포에 맞춰야 해요.

    9장 일관성과 합의

    선형성, 순서화, 전체 순서 브로드캐스트, 2PC, 그리고 합의 알고리즘

    선형성 (Linearizability)

    "복제본이 하나뿐인 것처럼" 보이는 것. 쓰기가 완료되면 이후 모든 읽기는 그 값(또는 더 새 값)을 봄. 최신성 보장. 직렬성(트랜잭션 격리, 7장)과 다른 개념. 필요한 곳: 잠금·리더 선출(둘이 리더면 안 됨), 유니크 제약(사용자명), 채널 간 타이밍 의존(이미지 업로드 후 큐로 리사이즈 요청 → 워커가 옛 복제본에서 못 찾음).

    구현: single-leader(동기 복제 + 리더에서 읽기)면 가능, 합의 알고리즘은 보장, multi-leader·leaderless는 불가(쿼럼도 엄밀히는 아님). 비용: 네트워크 단절 시 선형성을 지키려면 일부가 멈춰야(CAP의 C vs A). 그리고 지연이 커요. 멀티코어 CPU도 선형적이지 않아요(캐시, 메모리 배리어). 성능 때문에 포기.

    CAP

    "일관성(선형성), 가용성, 분단 내성 중 둘"은 오해를 낳는 표현. 분단은 선택이 아니라 일어나는 것. 정확히는 "분단 시 선형성 또는 가용성 중 하나". 그리고 네트워크 지연, 죽은 노드, 다른 일관성 모델을 다루지 않아 실용성이 낮아요. 역사적 의미.

    순서화 보장

    • 인과성: 원인이 결과보다 먼저. 질문이 답보다 먼저. 부분 순서(동시 사건은 순서 없음). 선형성보다 약하지만 네트워크 지연에 민감하지 않고 분단에도 가용. 대부분의 "선형성이 필요해 보이는" 상황은 사실 인과적 일관성으로 충분.
    • 램포트 타임스탬프: (카운터, 노드 ID). 메시지 받으면 카운터를 max로. 인과 관계와 일치하는 전체 순서. 하지만 "지금 이 결정이 최종인가"(사용자명 유일성)는 못 답함 — 다른 노드가 더 작은 타임스탬프로 같은 요청을 했는지 모름.
    • 전체 순서 브로드캐스트: 모든 노드에 같은 순서로 메시지 전달, 유실 없음. = 복제 로그 = 상태 머신 복제. 이걸로 선형적 저장소(CAS), 락, 펜싱 토큰(로그 위치), 유니크 제약을 구현. 전체 순서 브로드캐스트 ≡ 합의.

    분산 트랜잭션: 2단계 커밋 (2PC)

    여러 노드에 걸친 원자적 커밋. 코디네이터가 (1) 준비 요청 → 각 참여자가 "예"(커밋 가능 보장, 디스크에 기록) (2) 전부 예면 커밋 요청, 아니면 중단. 참여자는 "예"라고 한 뒤엔 코디네이터 결정을 무한정 기다려야 함(의심 상태, 락 유지). 코디네이터가 죽으면 전체가 멈춤(블로킹). 3PC는 비블로킹이지만 완벽한 결함 감지 가정.

    실무: XA 트랜잭션(JTA)은 느리고(fsync 여러 번, 네트워크 왕복), 코디네이터가 단일 장애점이고, 의심 상태에서 락이 서비스 전체를 막아요. Kafka의 exactly-once는 내부 2PC 변형. 이기종 시스템 간 2PC는 피하고, 멱등성 + 재시도, Outbox, Saga로(부록).

    합의 (Consensus)

    여러 노드가 하나의 값에 동의. 속성: 균일한 동의(둘로 안 갈림), 무결성(한 번만), 유효성(제안된 값), 종료(죽지 않은 노드는 결국 결정 — 2PC가 못 하는 것, 과반수 필요). FLP 불가능성: 비동기 모델에서는 결정적 합의 불가, 하지만 타임아웃·랜덤으로 현실에선 가능.

    알고리즘: Paxos, Raft, Zab(ZooKeeper), VSR. 공통 구조: 에포크 번호(단조 증가, 임기)와 쿼럼. 에포크마다 리더 하나. 리더는 쿼럼의 동의를 받아 제안. 더 높은 에포크의 리더가 나타나면 옛 리더는 무효. 두 번의 투표(리더 선출, 제안 수락)의 쿼럼이 겹쳐야 함.

    • Raft 흐름: 팔로워가 하트비트 못 받으면 후보 → 임기 올리고 투표 요청 → 과반수면 리더 → 클라이언트 쓰기를 로그에 추가 → 팔로워에 복제 → 과반수가 저장하면 커밋 → 적용.
    • 한계: 동기 복제라 느림, 과반수 필요(5대면 2대 장애까지), 멤버 변경 어려움, 타임아웃 의존(네트워크 불안정하면 리더가 계속 바뀜).

    ZooKeeper / etcd

    합의를 직접 구현하지 말고 "메모리에 다 들어가는 소량의 데이터"를 전체 순서 브로드캐스트로 복제하는 코디네이션 서비스를 쓰세요. 제공: 선형적 원자 연산(CAS → 락), 전체 순서(zxid = 펜싱 토큰), 결함 감지(세션·임시 노드), 변경 알림(watch). 용도: 리더 선출, 파티션 할당(Kafka, HBase), 서비스 디스커버리(변동이 잦아 약한 일관성으로 충분한 경우도), 멤버십. 쿠버네티스가 etcd 위에 있어요.

    백엔드에서는 마이크로서비스 간 "주문 생성 + 재고 차감 + 결제"를 XA로 묶으려는 시도는 거의 항상 실패해요(느림, 블로킹, 의심 상태). 대신 각 서비스의 로컬 트랜잭션 + 이벤트(Outbox) + 보상(Saga). Kafka 컨트롤러, 쿠버네티스, 스프링 클라우드의 리더 선출은 전부 ZooKeeper/etcd/Raft 위예요. 직접 합의 알고리즘을 짜지 말고, 그것들이 "과반수가 살아 있어야 동작한다"는 전제를 운영에 반영하세요(3 또는 5대, 짝수 금지).
    핵심 정리
    • 선형성 = 단일 복사본처럼. 비싸고 분단 시 가용성 포기. 인과적 일관성으로 충분한 경우 많음
    • 전체 순서 브로드캐스트 = 복제 로그 = 합의
    • 2PC = 원자적 커밋, 코디네이터 장애 시 블로킹. 이기종 XA 지양
    • 합의 = 에포크 + 쿼럼. Raft. ZooKeeper/etcd로 아웃소싱
    셀프 체크
    1. 2PC와 Raft 같은 합의 알고리즘의 결정적 차이는?
    2. etcd 클러스터를 4대로 구성하면 몇 대 장애까지 견디나요? 3대와 비교하면?
    답 보기

    1. 2PC는 모든 참여자가 "예"여야 하고 코디네이터가 죽으면 참여자가 무한정 기다려요(종료 속성 없음). 합의는 과반수만 있으면 진행하고, 리더가 죽으면 새 리더를 뽑아 계속해요(종료 보장). 2PC는 원자성, 합의는 가용성까지.

    2. 과반수 = 3대 필요. 4대면 1대 장애까지(2대 죽으면 2 < 3). 3대도 과반수 2라 1대 장애까지. 즉 4대는 3대와 내결함성이 같은데 비용만 늘고, 분단 시 2:2로 갈리면 양쪽 다 과반수 미달로 멈춰요. 홀수(3, 5)로.

    3부 파생 데이터

    10장 일괄 처리

    Unix 파이프에서 MapReduce, 데이터플로 엔진까지

    시스템의 세 종류

    온라인(서비스): 요청 → 응답, 지연 중요. 일괄 처리(배치): 대량 입력 → 출력, 처리량 중요, 몇 분~며칠. 스트림: 이벤트 발생 직후 처리, 둘의 중간(11장). 파생 데이터: 원본(기록 시스템)에서 변환해 만든 데이터(캐시, 색인, 집계, 추천 모델). 잃어도 원본에서 재생성 가능. 이 구분이 3부의 축.

    Unix 철학

    cat log | awk '{print $7}' | sort | uniq -c | sort -rn | head. 각 도구는 한 가지를 잘하고, 균일한 인터페이스(파일 = 바이트 스트림)로 연결. 불변 입력, 출력은 다른 곳이라 실패해도 재실행 안전. 메모리보다 큰 데이터도 처리(sort는 외부 정렬). 한계: 단일 머신.

    MapReduce

    Unix 파이프를 수천 대로. 분산 파일 시스템(HDFS) 위에서:

    1. Map: 입력 레코드마다 (키, 값) 쌍 추출. 상태 없음, 병렬.
    2. 셔플: 키로 정렬·파티셔닝해 같은 키를 같은 리듀서로.
    3. Reduce: 같은 키의 값들을 순회해 출력.

    조인: 정렬 병합 조인(양쪽을 키로 매핑해 리듀서에서 만남), 브로드캐스트 해시 조인(작은 쪽을 모든 매퍼 메모리에), 파티션 해시 조인. 그룹화와 핫키(skew) 처리(랜덤 분산 후 재집계). 출력은 새 파일(불변, 재실행 가능, 실패 시 폐기). HDFS가 느린 이유: 중간 결과를 전부 디스크에 쓰고(구체화), 다음 작업은 이전 전체가 끝나야 시작.

    데이터플로 엔진 (Spark, Flink, Tez)

    작업 전체를 연산자 DAG로 보고 중간 결과를 디스크에 안 쓰고 메모리/네트워크로 다음 연산자에 바로 전달. 불필요한 정렬 생략, 연산자 재사용, 실패 시 재계산(Spark RDD 계보). 결정적 연산자여야 재계산이 안전(시계, 난수 주의). 그래프 처리(Pregel, 반복), 고수준 API(DataFrame, SQL)는 옵티마이저가 조인 방식 선택.

    파생 데이터로서의 배치 출력

    검색 색인 구축(Lucene 세그먼트 → 교체), 추천·분류 모델, 키-값 저장소 벌크 로드(Voldemort: 파일로 만들어 통째로 교체). 출력을 DB에 한 건씩 쓰지 말 것(느림, 부분 실패 시 불일치). 파일로 만들고 원자적으로 교체. 입력이 불변이고 출력이 새 파일이면 버그 있는 코드도 롤백 가능(인적 오류 내성, 1장).

    백엔드에서는 "매일 밤 정산 배치"를 운영 DB에서 수십만 건 UPDATE로 돌리면 복제 지연과 락 경합이 나요. 배치는 복제본/웨어하우스에서 읽고, 결과를 파일/별도 테이블로 만들어 원자적 교체(rename, 파티션 swap). Spark/BigQuery로 집계하고 결과만 서비스 DB에 벌크 로드. 그리고 배치 작업은 멱등해야 해요(같은 날짜로 두 번 돌려도 같은 결과). 중간에 죽으면 재실행하는 게 유일한 복구 수단이니까요.
    핵심 정리
    • 파생 데이터 = 원본에서 재생성 가능. 불변 입력 + 새 출력 = 재실행 안전
    • MapReduce = map/셔플/reduce, 조인·그룹화를 셔플로. 디스크 구체화가 느림
    • 데이터플로 엔진 = DAG, 메모리 전달, 재계산
    • 배치 출력은 파일로 만들어 통째로 교체
    셀프 체크
    1. 배치 작업이 멱등해야 하는 이유와 멱등하게 만드는 방법은?
    답 보기

    중간에 실패하면 재실행이 복구 수단인데, 멱등하지 않으면(예: 누적 +=) 두 번 반영돼요. 방법: 입력은 불변 스냅샷(날짜 파티션), 출력은 "해당 날짜 결과를 통째로 덮어쓰기"(DELETE WHERE date=? 후 INSERT, 또는 파티션 교체), 외부 효과(메일 발송)는 "이미 보냈음" 기록으로 중복 방지.

    11장 스트림 처리

    메시지 브로커, 로그 기반 브로커, CDC, 이벤트 소싱, 시간과 윈도우, 정확히 한 번

    이벤트 스트림

    배치는 입력을 "끝이 있는" 파일로 보지만, 실제 데이터는 계속 들어와요. 이벤트(불변, 시각 포함)를 생산자가 발행하고 소비자가 구독. 토픽으로 묶음. 전달: 직접(UDP 멀티캐스트, 웹훅 — 소비자 오프라인이면 유실), 또는 메시지 브로커.

    두 종류의 브로커

    AMQP/JMS 스타일 (RabbitMQ, ActiveMQ, SQS)로그 기반 (Kafka, Kinesis, Pulsar)
    모델메시지를 소비자에 할당, ACK 받으면 삭제디스크 로그에 append, 소비자는 오프셋으로 순차 읽기, 보존 기간 후 삭제
    순서로드밸런싱(여러 소비자에 분배) 시 순서 깨짐, 재전달도 순서 바꿈파티션 안에서 순서 보장. 파티션당 소비자 1개
    재처리불가(삭제됨)오프셋 되돌려 재생 가능. 배치처럼
    처리량메시지 단위 추적, 중간순차 디스크 I/O, 매우 높음
    적합작업 큐(처리 비용 큼, 순서 무관, 완료 추적)이벤트 스트림(처리량, 순서, 재생, 다중 소비자)

    로그 기반에서 소비자가 느리면? 오프셋이 뒤처질 뿐 생산자나 다른 소비자에 영향 없음(브로커가 버퍼). 보존 기간을 넘기면 유실 → 지연 모니터링(consumer lag) 필수. 소비자 그룹의 오프셋만 저장하면 되니 소비 상태 관리가 단순.

    DB와 스트림

    • 이중 쓰기 문제: 앱이 DB와 검색 색인에 각각 쓰면 하나만 성공하거나(불일치) 순서가 엇갈려요(경쟁 조건). 2PC는 비싸고.
    • CDC (Change Data Capture): DB의 변경 로그(MySQL binlog, PostgreSQL WAL)를 읽어 스트림으로. DB가 리더, 색인·캐시·웨어하우스가 팔로워. Debezium, Maxwell. 순서 보장, 누락 없음. 초기 스냅샷 + 로그 컴팩션(키별 최신만 보존)으로 전체 재구축 가능.
    • 이벤트 소싱: 애플리케이션 레벨에서 "상태 변경"이 아니라 "일어난 일"(이벤트)을 불변 로그로 저장하고 현재 상태는 이벤트를 재생해 파생. "장바구니에 X 추가 → X 제거"가 "장바구니 비어 있음"보다 많은 정보. 감사, 디버깅, 새 뷰 추가가 쉬움. 명령(요청, 검증 필요) vs 이벤트(사실, 되돌릴 수 없음) 구분. 스냅샷으로 재생 비용 절감.
    • 불변성의 힘: 상태 = 이벤트의 적분, 이벤트 = 상태의 미분. 같은 로그에서 여러 읽기 뷰(CQRS: 쓰기 모델과 읽기 모델 분리). 한계: 삭제 요구(GDPR) — 로그를 진짜 지워야 함, 로그 크기.

    스트림 처리

    스트림을 읽어 (1) 저장소에 쓰기(색인, 캐시), (2) 알림·대시보드, (3) 다른 스트림 생성. 용도: 복잡 이벤트 처리(패턴 매칭), 스트림 분석(윈도우 집계), 구체화 뷰 유지, 검색(저장된 질의에 이벤트 매칭).

    • 시간: 이벤트 시각(발생) vs 처리 시각(도착). 처리 지연·재시작·오프라인 기기로 어긋남. 이벤트 시각으로 윈도우를 정해야 하지만 "이 윈도우의 이벤트가 다 왔는가"는 알 수 없음 → 뒤늦은 이벤트(straggler): 버리거나 수정값 발행. 기기 시계 오류는 서버 수신 시각과의 차이로 보정.
    • 윈도우: 텀블링(고정, 안 겹침), 홉핑(고정, 겹침), 슬라이딩(모든 구간), 세션(활동 간격 기준).
    • 스트림 조인: 스트림-스트림(두 이벤트 시간 창 안에서 매칭, 상태 유지), 스트림-테이블(이벤트에 DB 정보 보강 — CDC로 테이블 복제본을 로컬에), 테이블-테이블(구체화 뷰 유지). 시간 의존성: 조인 시점에 따라 결과가 달라짐(환율 변경) → 버전 ID로.
    • 내결함성: 마이크로배치(Spark Streaming, 1초 단위 작은 배치), 체크포인트(Flink, 주기적 상태 저장 후 재시작 시 오프셋 복원). 출력이 외부에 나간 뒤 실패하면 중복 → 멱등성(Kafka 오프셋을 함께 저장해 중복 감지) 또는 원자적 커밋(Kafka 트랜잭션). "정확히 한 번" = 실제로는 "효과적으로 한 번"(at-least-once + 멱등).
    백엔드에서는 "DB 저장 후 Kafka 발행"을 코드에서 순서대로 하면 이중 쓰기 문제예요. 둘 사이에 죽으면 이벤트 유실. 해결은 Outbox 패턴(부록): 같은 트랜잭션에 outbox 테이블에 이벤트를 쓰고, CDC(Debezium)나 폴링 릴레이가 Kafka로. 소비자는 at-least-once를 가정하고 멱등하게(이벤트 ID로 처리 여부 기록). 그리고 Kafka 파티션 키를 잘못 잡으면(랜덤) 같은 주문의 이벤트 순서가 깨져요. 순서가 중요한 단위(주문 ID, 사용자 ID)를 키로.
    시니어 심화 본문은 소비자를 멱등하게 만들라고 했는데, Kafka 소비자를 운영하면 가장 자주 만나는 장애는 처리가 느려져서 그룹에서 쫓겨나기를 반복하는 상황이에요.

    컨슈머는 한 번에 여러 메시지를 가져와 처리하고 다시 가져가요. 가져가는 간격이 max.poll.interval.ms를 넘으면, Kafka는 그 컨슈머가 멈춘 것으로 보고 그룹에서 내보낸 뒤 파티션을 다른 컨슈머에게 넘겨요. 그런데 처리가 느려진 이유가 하위 시스템(외부 API, DB) 때문이라면 새로 파티션을 받은 컨슈머도 똑같이 느려서 또 쫓겨나요. 그 사이 커밋하지 못한 메시지는 계속 다시 처리돼요. 일은 열심히 하는데 진척이 없는 상태예요. 한 번에 가져오는 건수(max.poll.records)를 줄여 묶음 하나의 처리 시간이 한도를 넘지 않게 하고, 메시지 하나의 처리 시간에도 상한(외부 호출 타임아웃)을 두세요(Kafka 챕터 3장).

    핵심 정리
    • AMQP = 작업 큐(삭제), 로그 기반 = 이벤트 스트림(오프셋, 재생, 순서)
    • 이중 쓰기 → CDC(DB가 리더) 또는 이벤트 소싱(로그가 원본)
    • 이벤트 시각 vs 처리 시각, 윈도우, 뒤늦은 이벤트
    • 정확히 한 번 = at-least-once + 멱등/원자적 커밋
    셀프 체크
    1. "DB에 저장하고 Kafka에 발행"이 왜 안전하지 않고, 어떻게 고치나요?
    2. Kafka 소비자가 메시지를 두 번 받을 수 있는 상황과 대응은?
    답 보기

    1. DB 커밋 후 Kafka 발행 전에 프로세스가 죽으면 이벤트 유실, 반대 순서면 DB 롤백됐는데 이벤트는 나감. 두 시스템을 원자적으로 못 묶어요. Outbox: 비즈니스 데이터와 outbox 행을 같은 DB 트랜잭션에 쓰고, 별도 프로세스(CDC/폴러)가 outbox를 읽어 발행 후 표시. 발행이 중복될 수 있으니 소비자는 멱등하게.

    2. 처리 후 오프셋 커밋 전에 소비자가 죽거나 리밸런싱되면 다음 소비자가 같은 오프셋부터 다시 읽어요. 대응: 이벤트 ID(또는 파티션+오프셋)를 처리 결과와 함께 저장해 "이미 처리함"이면 건너뛰기, 또는 처리 자체를 멱등하게(upsert, 조건부 갱신).

    12장 데이터 시스템의 미래

    데이터 통합, DB 언번들링, 정확성과 신뢰, 윤리 — DDIA의 결론

    데이터 통합

    단일 도구로 모든 접근 패턴을 만족할 수 없어요(OLTP, 검색, 분석, 캐시). 여러 저장소를 쓰되, 변경 순서를 하나의 로그(CDC, 이벤트 로그)로 정하고 모든 파생 시스템이 그 순서로 따라가게 하면 이중 쓰기 문제 없이 일관성이 유지돼요. 파생 데이터 vs 분산 트랜잭션: 비동기지만 느슨하게 결합되고 내결함성이 좋아요.

    배치와 스트림을 통합: 람다 아키텍처(배치로 정확한 결과 + 스트림으로 근사 결과 → 병합, 코드 이중 유지)에서 하나의 시스템이 둘 다(Flink, Kafka Streams, 이벤트 시간 처리 + 로그 재생)로.

    DB 언번들링

    DB는 사실 색인 유지, 구체화 뷰, 복제 로그, 트리거를 한 곳에 묶은 것. 이걸 풀어서(unbundle) Kafka(로그) + 스트림 처리기(파생 유지) + 각 전문 저장소로 조합하는 추세. "Unix 철학을 데이터 시스템에". 애플리케이션 코드가 파생 함수. 읽기 요청도 스트림 처리의 일부로 볼 수 있어요(구독 기반 UI, 오프라인 우선).

    정확성

    • 종단 간 논리(end-to-end argument): TCP가 중복을 제거해도 애플리케이션 재시도로 중복이 생겨요. 멱등성·중복 제거는 애플리케이션 끝에서 끝까지(요청 ID) 해야 해요. 저수준 보장만으로 부족.
    • 제약 조건 강제: 유니크 제약은 합의가 필요하지만, 로그 기반(같은 키를 같은 파티션으로 → 단일 소비자가 순서대로 판정)으로 선형적 시스템 없이도 가능. 다중 파티션은 요청을 로그에 먼저 쓰고 파티션별로 처리.
    • 적시성 vs 무결성: 적시성(최신)은 어겨도 결국 맞춰지지만, 무결성(유실·중복·불일치 없음)은 어기면 영구 손상. 대부분 적시성보다 무결성이 중요하고, 비동기 스트림도 무결성은 보장할 수 있어요(불변 로그, 멱등, 결정적 파생).
    • 믿지 말고 검증: 디스크·네트워크·소프트웨어 모두 조용히 데이터를 깨뜨릴 수 있음. 체크섬, 감사(audit), 종단 간 무결성 확인, 복구 훈련(백업 복원 테스트).

    옳은 일 하기

    데이터는 사람에 관한 것. 예측 분석의 편향과 차별, 감시, 동의와 선택의 자유, 데이터 최소화. "미래의 나에게 부끄럽지 않을 시스템"을 만들 책임.

    백엔드에서는 요청 ID(Idempotency-Key)를 클라이언트부터 DB까지 관통시키는 게 종단 간 논리의 실천이에요. 중간의 어떤 계층도 "재시도 안전"을 대신 보장하지 않아요. 백업은 복원해 본 적이 없으면 백업이 아니에요. 분기마다 복원 훈련을 하세요. 그리고 개인정보는 "수집하지 않는 것"이 최고의 보안이에요.
    핵심 정리
    • 하나의 변경 로그 + 파생 시스템들 = 느슨한 결합 + 일관성
    • 종단 간 멱등성은 앱 책임. 무결성 > 적시성
    • 검증하고 감사하고 복원 훈련
    셀프 체크
    1. TCP가 재전송·중복 제거를 하는데 왜 애플리케이션에 멱등성 키가 또 필요한가요?
    답 보기

    TCP의 보장은 하나의 연결 안에서만이에요. 응답이 유실되거나 타임아웃돼 애플리케이션이 새 연결로 재시도하면 TCP는 그게 같은 요청인지 몰라요. 로드밸런서, 프록시, 클라이언트 라이브러리의 자동 재시도도 마찬가지. 중복 제거는 요청의 의미를 아는 양 끝(클라이언트가 키 부여, 서버가 키로 판정)에서만 가능해요.

    부록 — 실무 설계 패턴 (대규모 시스템 설계 기초)

    A. 캐시 전략과 캐시 문제

    cache-aside, write-through, 무효화, stampede, 관통, 핫키

    읽기·쓰기 패턴

    패턴흐름특징
    Cache-aside (lazy)읽기: 캐시 → 없으면 DB → 캐시 저장. 쓰기: DB 갱신 → 캐시 삭제표준. 캐시 장애 시 DB로 동작. 첫 읽기는 미스
    Read-through캐시 라이브러리가 미스 시 DB 로드를 대신cache-aside를 추상화(Caffeine loader, Spring @Cacheable)
    Write-through쓰기 시 캐시와 DB 동시 갱신일관성 좋음, 쓰기 지연 증가, 안 읽을 데이터도 캐시
    Write-behind캐시에 먼저 쓰고 비동기로 DB쓰기 빠름, 캐시 장애 시 유실. 카운터·로그에

    쓰기 시 캐시를 갱신하지 말고 삭제하는 이유: 두 쓰기가 교차하면(A 쓰기 → B 쓰기 → B 캐시 갱신 → A 캐시 갱신) 옛 값이 남아요. 삭제하면 다음 읽기가 DB에서 최신을 가져와요. 그래도 "DB 갱신 전 읽기가 옛 값을 캐시에 넣는" 틈은 남으니 TTL은 항상 안전망으로.

    캐시 문제들

    • Stampede(thundering herd): 핫 키 만료 순간 수천 요청이 DB로. 해결: 락/single-flight(한 요청만 DB, 나머지 대기), 만료 전 백그라운드 갱신, TTL 지터(동시 만료 방지), 논리 만료(물리적으로 안 지우고 만료 표시 후 갱신).
    • 관통(penetration): 없는 키 반복 요청 → 매번 DB. 해결: null도 짧게 캐시, Bloom filter(DSA 챕터 4장).
    • 핫 키: 한 키에 트래픽 집중 → Redis 단일 노드 한계. 해결: 로컬 캐시(Caffeine) 앞단에, 키 복제(key:1~key:N 랜덤 읽기).
    • 큰 키: 수 MB 값 하나가 네트워크·메모리 점유. 쪼개거나 필드 단위(Hash).
    • 일관성: 캐시는 본질적으로 최종적 일관성. 강한 일관성 필요한 데이터(잔고)는 캐시하지 말거나 DB에서.

    다층 캐시

    브라우저/CDN(HTTP 캐시, 네트워크 챕터 부록 B) → 게이트웨이 → 로컬 캐시(프로세스 메모리, 나노초, 노드 간 불일치) → 분산 캐시(Redis, 마이크로초) → DB. 각 층의 TTL과 무효화 경로를 설계.

    백엔드에서는 Spring @Cacheable/@CacheEvict가 cache-aside예요. @CachePut(갱신)보다 @CacheEvict(삭제)를. 캐시 키에 사용자·테넌트·버전을 포함하지 않으면 데이터가 섞여요. Redis 키에는 반드시 TTL, 네임스페이스(svc:entity:id), 그리고 캐시 히트율·미스율·DB 쿼리 수를 메트릭으로. "캐시를 넣었더니 더 느려졌다"는 직렬화 비용(큰 객체)이나 네트워크 왕복이 DB 조회보다 비싼 경우예요.
    시니어 심화 본문은 cache-aside + 쓰기 시 삭제를 권했는데, 이 조합에도 구조적인 경쟁 조건이 하나 있어요. 드물지만 트래픽이 많으면 반드시 일어나요.

    순서는 이래요. (1) 읽기 요청이 캐시 미스를 보고 DB에서 상품 가격 10,000원을 읽어요. (2) 그 사이 쓰기 요청이 DB를 12,000원으로 바꾸고 캐시를 지워요. (3) 읽기 요청이 뒤늦게 아까 읽은 10,000원을 캐시에 넣어요. 이제 TTL이 끝날 때까지 캐시에는 옛 가격이 남아요. 읽기가 느려지는 순간(GC, DB 지연)일수록 잘 일어나요. 그래서 짧은 TTL이 기본 안전망이에요. 더 엄격하게 하려면 값에 버전을 넣어 더 낮은 버전으로 덮어쓰지 못하게 하거나, DB 변경 로그(CDC)를 순서대로 따라가며 캐시를 지워요. 그리고 캐시를 다시 채울 때 복제본에서 읽으면, 복제 지연만큼의 옛 값이 캐시에 고정된다는 점도 기억하세요.

    핵심 정리
    • cache-aside + 쓰기 시 삭제 + TTL 안전망
    • stampede(single-flight, 지터), 관통(null 캐시, Bloom), 핫 키(로컬 캐시, 복제)
    셀프 체크
    1. 쓰기 시 캐시를 삭제해도 남는 불일치 틈은 무엇이고 어떻게 줄이나요?
    답 보기

    읽기 A가 캐시 미스로 DB에서 옛 값을 읽음 → 쓰기 B가 DB 갱신 후 캐시 삭제 → A가 옛 값을 캐시에 저장. 옛 값이 TTL 동안 남아요. 확률은 낮지만(읽기의 DB 조회와 캐시 저장 사이 틈이 짧음) 0은 아니에요. 완화: 짧은 TTL, 쓰기 후 잠시 뒤 한 번 더 삭제(delayed double delete), 또는 CDC로 DB 변경을 캐시 무효화 이벤트로 흘려 순서 보장.

    B. 멱등성, 재시도, Outbox, Saga

    실패를 전제로 한 쓰기 설계 — 분산 트랜잭션 없이 일관성 유지하기

    멱등성 키

    1. 클라이언트가 작업마다 고유 키(UUID) 생성, 헤더 Idempotency-Key로 전송. 재시도 시 같은 키.
    2. 서버는 키를 UNIQUE 제약이 있는 테이블에 "처리 중"으로 INSERT(동시 요청은 하나만 성공, 7장 write skew 방어).
    3. 처리 후 결과(상태 코드, 본문)를 키와 함께 저장.
    4. 같은 키 재요청 → 저장된 결과 반환. "처리 중"이면 409/425로 잠시 후 재시도 요청.
    5. 키는 TTL(24시간) 후 삭제. 키 + 요청 본문 해시를 비교해 다른 요청에 같은 키 쓰는 오용 감지.

    외부 시스템(PG)에도 같은 주문 번호를 멱등 키로 넘겨 양쪽에서 중복 차단. 타임아웃 시 무작정 재시도 전에 상태 조회 API로 실제 결과 확인.

    재시도 정책

    • 재시도할 것: 네트워크 오류, 타임아웃, 503/429, 일시적 DB 에러(데드락, 락 타임아웃). 하지 말 것: 400/404/422(같은 결과), 비멱등 요청(키 없이).
    • 지수 백오프 + 지터: 1s, 2s, 4s... + 랜덤. 모든 클라이언트가 동시에 재시도하는 폭풍 방지. 최대 횟수·총 시간 제한.
    • 재시도 예산: 재시도가 전체 요청의 10%를 넘으면 중단(장애 시 부하 증폭 방지).
    • 계층 간 재시도 중첩 주의: 클라이언트 3회 × 게이트웨이 3회 × 서비스 3회 = 27배.

    Outbox 패턴

    BEGIN;
  INSERT INTO orders (...) VALUES (...);
  INSERT INTO outbox (id, aggregate_id, type, payload, created_at)
    VALUES (uuid, order_id, 'OrderCreated', {...}, now());
COMMIT;
-- 별도 릴레이: outbox를 폴링(또는 CDC)해 Kafka 발행 → 발행 완료 표시/삭제

    비즈니스 데이터와 이벤트가 같은 트랜잭션이라 "저장됐는데 이벤트 없음"이 불가능. 릴레이는 at-least-once(발행 후 표시 전에 죽으면 재발행) → 소비자 멱등. Debezium Outbox Event Router가 표준 구현.

    Saga

    여러 서비스에 걸친 비즈니스 트랜잭션을 로컬 트랜잭션의 연쇄로. 실패하면 이미 완료된 단계를 보상 트랜잭션(결제 취소, 재고 복구)으로 되돌려요. 원자성 대신 "결국 일관"(최종적 일관성).

    • 코레오그래피: 각 서비스가 이벤트를 듣고 다음을 수행, 중앙 없음. 단순하지만 흐름이 분산돼 추적 어려움, 순환 의존 위험.
    • 오케스트레이션: 오케스트레이터가 각 단계를 명령하고 상태를 관리. 흐름이 한 곳에, 보상 로직 명확. 오케스트레이터 자체의 내구성 필요(상태를 DB에, Temporal/Camunda).

    주의: 보상은 "취소"이지 "롤백"이 아니에요. 중간 상태가 다른 트랜잭션에 보여요(격리 없음). "주문 확정 → 결제 실패 → 주문 취소" 사이에 사용자가 배송 중으로 볼 수 있어요. 시맨틱 락(상태 PENDING), 보상 가능한 순서 배치(가장 실패하기 쉬운 단계를 먼저, 되돌릴 수 없는 단계를 마지막).

    백엔드에서는 결제·주문·포인트처럼 돈이 걸린 API는 멱등성 키 없이 공개하지 마세요. Outbox는 "이벤트 발행 코드"를 서비스 로직에서 제거해 주는 효과도 있어요. Saga를 도입하기 전에 "정말 여러 서비스에 쪼개야 하나?"를 먼저. 한 DB 안이면 그냥 트랜잭션이 훨씬 단순하고 정확해요. 분산은 필요할 때만.
    시니어 심화 본문은 멱등성 키를 UNIQUE 테이블로 구현한다고 했는데, 실제로 구현해 보면 "처리 중"이라는 상태를 다루는 것이 가장 어려워요.

    같은 키의 요청이 거의 동시에 두 번 오면, 첫 요청이 아직 처리 중일 때 두 번째가 도착해요. 두 번째에게 무엇을 돌려줘야 할까요? 저장된 결과는 아직 없어요. 그래서 처리를 시작하기 전에 키를 먼저 선점해요. 유니크 제약이 있는 테이블에 "처리 중" 상태로 키를 넣고, 넣기에 실패한(이미 있는) 요청은 처리 중이면 409로, 완료됐으면 저장된 결과로 응답해요. 그리고 같은 키인데 요청 본문이 다르면 클라이언트 버그이니 거부하도록 본문의 해시도 같이 저장해요. 남는 문제는 외부 결제 호출이 낀 경우예요. 처리 도중 서버가 죽으면 키는 "처리 중"으로 남는데, 결제가 됐는지는 모르는 상태예요. 이런 키는 결제사의 조회 API로 실제 결과를 확인해 정리하는 절차가 필요해요.

    핵심 정리
    • 멱등성 키 = UNIQUE 테이블 + 결과 저장 + 재요청 시 반환
    • 재시도 = 지수 백오프 + 지터 + 예산, 멱등한 요청만
    • Outbox = 같은 트랜잭션에 이벤트 저장 → 릴레이. Saga = 로컬 트랜잭션 + 보상, 격리 없음

    답 보기

    (1) 격리가 없어요. 보상 전까지 중간 상태가 다른 트랜잭션·사용자에게 보여요(dirty read와 유사). (2) 보상은 새로운 쓰기라서 실패할 수 있고, "되돌릴 수 없는" 효과(이메일 발송, 외부 배송 요청)는 보상이 아니라 별도 조치(취소 메일)가 돼요. 그래서 되돌리기 어려운 단계를 마지막에 두고, 보상 자체도 멱등·재시도 가능해야 해요.

    C. 회복탄력성과 관측성

    서킷 브레이커, 벌크헤드, 백프레셔, 레이트 리밋, 그리고 로그·메트릭·트레이스

    연쇄 장애의 구조

    의존 서비스 하나가 느려짐 → 호출 스레드가 오래 묶임 → 스레드풀 고갈 → 무관한 요청까지 실패 → 상위 서비스도 같은 과정 → 전체 다운. 느린 실패가 빠른 실패보다 훨씬 위험해요. 대응 원칙: 빨리 실패하고, 격리하고, 부하를 줄여라.

    패턴

    패턴동작구현
    타임아웃모든 외부 호출에. connect·read 분리. 서비스별 p99 기반HTTP 클라이언트, DB 풀, Redis 클라이언트 설정

    Fallback / 우아한 성능 저하추천 실패 시 인기 상품, 재고 조회 실패 시 "확인 중"비즈니스 결정 필요: 무엇을 포기할 수 있나

    관측성 세 기둥

    • 로그: 개별 사건. 구조화(JSON), 요청 ID·트레이스 ID 포함, 레벨 관리. 중앙 수집(ELK, Loki). "무슨 일이 있었나".
    • 메트릭: 수치의 시계열 집계. 카운터, 게이지, 히스토그램(백분위!). RED(Rate, Errors, Duration — 서비스), USE(Utilization, Saturation, Errors — 자원). 알람의 근거. Prometheus.
    • 트레이스: 요청 하나가 서비스들을 거치는 경로와 구간별 시간. 스팬 트리. "어디서 느렸나". OpenTelemetry, Jaeger, Tempo. 트레이스 ID를 로그에 넣어 셋을 연결.

    알람 설계: 증상(사용자 영향: 에러율, p99)에 알람, 원인(CPU, 메모리)은 대시보드. 알람 피로를 피하려면 "행동이 필요한 것"만. SLO 기반 에러 예산 소진율(burn rate) 알람이 좋은 기준.

    장애 대응 문화

    런북, 온콜 로테이션, 비난 없는 포스트모템(원인은 사람이 아니라 시스템), 카오스 엔지니어링(의도적 결함 주입으로 검증), 복구 훈련. 1장의 "인적 오류가 최대 원인"에 대한 답이에요.

    백엔드에서는 신규 서비스 체크리스트: 모든 외부 호출에 타임아웃 → 핵심 의존성에 서킷 브레이커 + fallback → 의존성별 풀 분리 → 유한 큐 + 429 → 구조화 로그에 트레이스 ID → RED 메트릭 + p99 → SLO와 알람. Spring Boot면 Resilience4j + Micrometer + OpenTelemetry로 대부분 설정만으로 돼요. 그리고 "헬스체크 엔드포인트가 DB까지 확인"은 네트워크 챕터 5장의 전체 장애 유발 패턴이에요. liveness(자기 자신)와 readiness(트래픽 받을 준비)를 구분하세요.
    시니어 심화 본문은 연쇄 장애를 막는 패턴들을 다뤘는데, 그 패턴들을 다 넣고도 무너지는 경우가 있어요. 원인이 사라졌는데도 회복하지 못하는 상태예요. 준안정 장애라고 불러요.

    예를 들어 DB가 30초 동안 느려졌다고 해 봐요. 그동안 클라이언트들은 타임아웃 후 재시도하고, 캐시는 만료돼서 비고, 큐에는 처리 못 한 작업이 쌓여요. DB가 정상으로 돌아와도 재시도 폭주, 빈 캐시로 인한 DB 직접 조회, 밀린 큐의 처리가 겹쳐 평소의 몇 배 부하가 들어와요. 그 부하 때문에 DB는 다시 느려지고, 그래서 재시도가 또 늘어요. 서버를 늘려도 잘 안 풀려요. 이 상태에서 빠져나오려면 들어오는 부하를 강제로 깎아야 해요. 그래서 평소에 수동으로 걸 수 있는 부하 차단 스위치(일부 요청을 즉시 거절)를 만들어 두고, 재시도에는 예산(전체 요청 중 재시도 비율의 상한)을 두고, 차단할 때는 결제와 로그인처럼 중요한 요청을 마지막까지 살려 두는 우선순위를 정해요.

    • 로그(사건)·메트릭(집계, 백분위)·트레이스(경로), ID로 연결
    • 증상에 알람, 비난 없는 포스트모템

    1. 서킷 브레이커와 재시도를 함께 쓸 때 순서와 주의점은?
    2. "CPU 80% 알람"이 나쁜 알람인 이유는?
    답 보기

    1. 재시도 → 서킷 브레이커 → 실제 호출 순서로 감싸요(재시도가 바깥). 그러면 브레이커가 Open일 때 재시도도 즉시 실패해 부하를 안 줘요. 반대로 브레이커가 안쪽에서 재시도마다 실패를 세면 재시도 몇 번에 바로 Open돼요. 그리고 재시도 자체가 장애 서비스에 부하를 더하니 횟수와 예산을 제한하고, 멱등 요청에만.

    2. 원인 지표이지 증상이 아니에요. CPU 80%여도 응답이 정상이면 행동할 게 없고, 20%여도 에러율이 50%일 수 있어요. 사용자 영향(에러율, p99 지연, SLO 소진율)에 알람을 걸고 CPU는 원인 분석용 대시보드에.

    • 7장 두 세션으로 write skew(당직 의사 예제 또는 잔고 이중 인출) 재현. REPEATABLE READ에서 안 막히는 것 확인 후 FOR UPDATE / UNIQUE / SERIALIZABLE로 각각 해결
    • 8장 Redis SET NX PX 락을 걸고 클라이언트를 kill -STOP으로 멈춰 TTL 만료 후 다른 클라이언트가 락을 얻는 것, 그리고 깨어난 첫 클라이언트가 쓰는 것을 재현. version 컬럼 조건부 갱신(펜싱)으로 방어
    • 9장 etcd 3노드 클러스터를 띄우고 1대, 2대를 차례로 죽이며 쓰기 가능 여부 확인. Raft 로그와 임기(term) 변화 관찰
    • 11장 Kafka + Debezium으로 MySQL 테이블 변경을 토픽으로 받아보기. 소비자를 처리 중 죽여 중복 수신을 재현하고 멱등 처리 구현
    • 부록 간단한 주문 API에 멱등성 키를 구현하고 같은 키로 동시 요청 100개를 보내 하나만 처리되는지 확인. Resilience4j로 서킷 브레이커를 달고 의존 서비스를 죽여 Open → Half-open → Closed 전이 로그 보기
    • 설계 "URL 단축기", "알림 시스템", "채팅"을 각각 1시간 안에 설계서로 작성: 요구사항 → 부하 추정 → API → 데이터 모델 → 확장 → 장애 시나리오
