    검색 엔진

    기준 자료: Introduction to Information Retrieval + Elasticsearch 공식 문서 · 2~3주

    "상품명에 이 단어가 들어간 것"을 DB의 LIKE로 찾다가 느려지면 검색 엔진을 들이게 돼요. 이 챕터는 검색 엔진이 왜 그 질문에 빠른지, 결과의 순서를 어떻게 정하는지, 그리고 그 구조 때문에 무엇을 못 하는지를 다뤄요.

    예시는 Elasticsearch를 쓰지만 바탕인 Lucene의 원리는 OpenSearch, Solr에도 같아요. 시간이 없으면 1장(역색인과 분석기)과 5장(매핑과 쿼리)을 먼저 읽으세요. "검색이 안 돼요"의 대부분이 이 둘에서 풀려요.

    Elasticsearch 공식 문서 심화매핑, 텍스트 분석, 확장성 부분
    1부 원리

    1장 역색인과 분석기

    문서에서 단어를 찾지 않고, 단어에서 문서를 찾는다

    LIKE가 느린 이유

    WHERE title LIKE '%노트북%'은 인덱스를 쓸 수 없어요. B-Tree는 값의 앞부분부터 정렬돼 있어서, 중간에 들어 있는 문자열은 모든 행을 읽어 봐야 알아요.

    역색인

    책 뒤의 찾아보기와 같아요. 단어마다 그 단어가 나오는 문서의 목록을 미리 만들어 둬요.

    문서 1: "가벼운 게이밍 노트북"
      문서 2: "사무용 노트북 가방"
      문서 3: "게이밍 마우스"

      가방    → [2]
      가벼운  → [1]
      게이밍  → [1, 3]
      노트북  → [1, 2]
      마우스  → [3]
      사무용  → [2]

    "게이밍 노트북"을 찾으면 두 단어의 목록을 가져와 교집합을 구해요. 문서가 몇 개든 그 단어가 나온 문서 수에만 비례해요. 목록에는 문서 번호 외에 단어의 출현 횟수와 위치도 저장해요. 위치가 있어야 "두 단어가 붙어 있는" 구문 검색을 할 수 있어요.

    분석기: 텍스트를 단어로

    역색인의 품질은 텍스트를 어떻게 단어(토큰)로 쪼개느냐에 달려 있어요. 분석기는 세 단계예요.

    1. 문자 필터: 원문을 다듬는다(HTML 태그 제거 등).
    2. 토크나이저: 토큰으로 자른다(공백, 문장 부호, 형태소 기준).
    3. 토큰 필터: 토큰을 변환한다(소문자화, 불용어 제거, 어간 추출, 동의어 추가).

    가장 중요한 규칙

    색인할 때와 검색할 때 같은 방식으로 분석해야 해요. 색인에서 "Notebook"을 "notebook"으로 바꿔 저장했다면, 검색어 "NOTEBOOK"도 "notebook"으로 바꿔야 맞아요. 검색은 문자열 비교가 아니라 토큰의 일치예요.

    한국어

    한국어는 공백으로 자르면 "노트북을", "노트북이", "노트북"이 전부 다른 토큰이 돼요. 조사와 어미를 떼어 내는 형태소 분석기(Elasticsearch의 nori 등)가 필요해요. 복합어를 어떻게 쪼갤지("삼성전자" → "삼성" + "전자")와 사용자 사전도 검색 품질을 좌우해요.

    백엔드에서는 "분명히 있는 단어인데 검색이 안 된다"면 추측하지 말고 분석 결과를 직접 보세요. Elasticsearch의 _analyze API에 텍스트와 분석기를 넣으면 어떤 토큰이 나오는지 보여줘요. 색인된 토큰과 검색어의 토큰을 나란히 놓으면 왜 안 맞는지 바로 보여요. 신조어나 상품명이 잘못 쪼개지면 사용자 사전에 추가해요.
    시니어 심화
    • 부분 일치 요구("노트"로 "노트북" 찾기)는 역색인의 기본 동작이 아니에요. 앞부분 일치는 사전이 정렬돼 있어 가능하지만, 중간 일치는 토큰을 글자 조각(n-gram)으로 잘라 색인해야 하고 색인 크기가 몇 배로 커져요. 자동 완성은 앞에서부터의 조각(edge n-gram)이나 전용 자료구조를 써요.
    • 분석기를 바꾸면 전체를 다시 색인해야 해요. 이미 저장된 토큰은 옛 방식으로 만들어졌기 때문이에요. 사전에 단어 하나를 추가하는 것도 마찬가지예요. 무중단 재색인 절차를 미리 만들어 둬요(6장).
    • 동의어는 검색 시점에 적용하는 편이 유연해요. 색인 시점에 넣으면 동의어 목록을 바꿀 때마다 재색인이 필요해요.
    핵심 정리
    • 역색인 = 단어 → 문서 목록. 조회 비용이 전체 문서 수와 무관
    • 분석기 = 문자 필터 → 토크나이저 → 토큰 필터
    • 색인과 검색에 같은 분석. 한국어는 형태소 분석기 필수
    셀프 체크
    1. 상품명 "Apple MacBook Pro"를 색인했는데 "macbook"으로 검색하면 나오고 "mac"으로는 나오지 않습니다. 이유는 무엇인가요?
    답 보기

    역색인에는 분석기가 만든 토큰이 저장돼요. 표준 분석기는 이 상품명을 apple, macbook, pro 세 토큰으로 만들어요. 검색은 검색어의 토큰과 저장된 토큰이 정확히 같은지를 봐요. macbook은 저장된 토큰과 일치하지만 mac이라는 토큰은 어디에도 없어요. mac이 macbook의 일부라는 사실은 역색인이 알지 못해요. 앞부분 일치를 지원하려면 토큰의 앞에서부터 잘라 낸 조각들을 함께 색인하거나 접두사 검색 쿼리를 써야 해요.

    2장 랭킹 — TF-IDF와 BM25

    맞는 문서가 아니라 가장 맞는 문서를 먼저

    검색과 DB 조회의 차이

    DB 조회의 결과는 조건에 맞거나 안 맞거나예요. 검색의 결과는 얼마나 관련 있는가의 순서예요. 맞는 문서가 만 개여도 사용자는 첫 페이지만 봐요.

    점수의 직관

    • 단어 빈도(TF): 문서 안에 검색어가 많이 나올수록 관련 있다.
    • 역문서 빈도(IDF): 전체 문서 중 드문 단어일수록 중요하다. "노트북"보다 "썬더볼트"가 문서를 더 잘 구분해요. 모든 문서에 나오는 단어는 정보가 없어요.
    • 길이 정규화: 긴 문서는 단어가 많이 나오기 쉬우니 보정한다.

    BM25

    현재 기본으로 쓰이는 점수 함수예요. TF-IDF의 두 문제를 고쳤어요.

    • 빈도의 포화: 단어가 1번에서 2번으로 늘 때의 효과가 20번에서 21번으로 늘 때보다 커요. 일정 수준을 넘으면 더 나와도 점수가 거의 안 올라요. 단어를 반복해 넣는 문서가 유리해지지 않아요.
    • 조절 가능한 길이 보정: 문서 길이의 영향을 매개변수로 조절해요.

    필드마다 다른 가중치

    제목에 나온 단어와 본문에 나온 단어는 무게가 달라요. 필드별로 가중치(부스트)를 줘요.

    텍스트 점수만으로는 부족하다

    실제 서비스의 순위는 텍스트 관련도에 업무 신호를 섞어요. 판매량, 최신성, 평점, 재고 여부. 관련도 점수를 이런 값으로 조정하는 함수를 쓰거나, 1차로 검색한 상위 결과를 별도 모델로 다시 정렬해요.

    품질을 재는 방법

    • 정밀도: 보여준 것 중 관련 있는 것의 비율.
    • 재현율: 관련 있는 것 중 찾아낸 것의 비율.

    둘은 서로 당겨요. 동의어를 넓히면 재현율이 오르고 정밀도가 떨어져요.

    백엔드에서는 "왜 이 문서가 위에 나오지?"는 explain 옵션으로 답할 수 있어요. 점수가 어떤 항들의 합으로 나왔는지 문서별로 보여줘요. 순위 조정 요청이 올 때마다 가중치를 감으로 바꾸면 다른 검색어의 결과가 망가져요. 대표 검색어와 기대 결과의 목록을 만들어 두고, 설정을 바꿀 때마다 전체를 다시 돌려 비교하세요.
    시니어 심화
    • 점수는 샤드마다 따로 계산돼요. IDF에 쓰이는 문서 빈도가 샤드별 통계라서, 문서가 적거나 샤드 간 분포가 고르지 않으면 같은 문서가 어느 샤드에 있느냐에 따라 점수가 달라져요. 작은 인덱스에서 결과 순서가 이상하면 이것을 의심하고, 샤드를 하나로 줄이거나 전역 통계를 쓰는 검색 방식을 써요.
    • 필터와 질의를 구분하세요. 점수에 영향을 주지 않는 조건(카테고리, 가격대, 판매 중 여부)은 필터로 넣어요. 점수 계산을 건너뛰고 결과가 캐시돼요.
    • 온라인 지표로 검증해요. 사람이 매긴 관련도 평가는 비싸고 금방 낡아요. 클릭률, 검색 후 이탈, 결과 없음 비율, 재검색 비율을 보고, 순위 변경은 실험으로 비교해요.
    핵심 정리
    • 검색 결과는 관련도 순서. TF(많이 나옴) × IDF(드문 단어) × 길이 보정
    • BM25: 빈도 효과가 포화. 기본 점수 함수
    • 텍스트 점수 + 업무 신호. 변경은 기준 검색어 묶음으로 검증
    셀프 체크
    1. IDF가 낮은 단어(거의 모든 문서에 나오는 단어)가 점수에 적게 기여하도록 설계된 이유를 설명하세요.
    답 보기

    검색의 목적은 관련 있는 문서를 다른 문서와 구분하는 거예요. 거의 모든 문서에 나오는 단어는 그 단어가 있다는 사실만으로는 어떤 문서가 더 관련 있는지 알려주지 못해요. 쇼핑몰에서 "상품"이라는 단어가 그런 예예요. 반대로 소수의 문서에만 나오는 단어는 그 단어를 가진 문서가 검색 의도와 맞을 가능성을 크게 높여요. 그래서 드문 단어의 일치에 높은 점수를, 흔한 단어의 일치에 낮은 점수를 줘서 구분력이 있는 단어가 순위를 정하게 해요.

    2부 구현

    3장 세그먼트와 준실시간 검색

    색인 직후에 검색이 안 되는 이유

    세그먼트는 불변

    Lucene의 인덱스는 여러 개의 세그먼트로 이뤄져요. 세그먼트 하나는 그 자체로 완결된 작은 역색인이고, 한번 쓰면 바꾸지 않아요.

    • 불변이라 락 없이 여러 스레드가 읽을 수 있어요.
    • OS 파일 캐시에 올라가면 그대로 유효해요.
    • 압축된 형태로 저장할 수 있어요.

    쓰기 흐름

    1. 새 문서는 메모리 버퍼에 쌓이고, 동시에 트랜스로그(복구용 로그)에 기록된다.
    2. 리프레시: 버퍼의 내용을 새 세그먼트로 만들어 검색 가능하게 한다. 기본 1초마다.
    3. 플러시: 세그먼트를 디스크에 확실히 내려쓰고 트랜스로그를 비운다.

    그래서 색인한 문서는 다음 리프레시까지 검색되지 않아요. "준실시간"이라고 부르는 이유예요. 단, ID로 문서를 직접 가져오는 조회는 바로 돼요.

    수정과 삭제

    세그먼트를 못 고치니 삭제는 "삭제됨" 표시만 해요. 수정은 옛 문서를 삭제 표시하고 새 문서를 추가하는 거예요. 필드 하나만 바꿔도 문서 전체가 다시 색인돼요.

    병합

    리프레시마다 세그먼트가 생기면 수가 너무 많아져요. 검색은 모든 세그먼트를 봐야 하니 느려져요. 백그라운드에서 작은 세그먼트들을 큰 세그먼트로 병합하고, 이때 삭제 표시된 문서가 실제로 사라져요.

    이 구조는 LSM 트리와 닮았어요. 쓰기는 덧붙이기만 하고, 정리는 백그라운드 병합이 해요.

    백엔드에서는 저장 직후 목록에 바로 보여야 하는 화면에 검색 엔진을 쓰면 "방금 쓴 글이 안 보여요"가 나와요. 색인 요청에 리프레시를 기다리는 옵션(refresh=wait_for)을 쓸 수 있지만 응답이 그만큼 늦어져요. 매 요청마다 강제 리프레시를 하면 작은 세그먼트가 폭증해 전체가 느려져요. 방금 쓴 데이터는 원본 DB에서 읽게 하는 것이 보통 더 나아요.
    시니어 심화
    • 대량 색인 때는 리프레시 간격을 늘리세요. 처음 적재하거나 전체 재색인을 할 때 간격을 길게 하거나 끄고, 복제본 수를 0으로 뒀다가 끝난 뒤 되돌리면 색인 속도가 크게 올라요. 문서는 하나씩 보내지 말고 묶음(bulk)으로 보내요.
    • 갱신이 잦은 필드는 문서 전체의 재색인을 부르고 삭제 표시된 문서를 쌓아요. 조회수나 재고처럼 초 단위로 바뀌는 값을 검색 문서에 넣으면 색인 부하와 병합 부하가 커져요. 모아서 주기적으로 반영하거나 검색 문서에서 빼고 조회 시점에 합쳐요.
    • 내구성과 속도: 트랜스로그를 요청마다 디스크에 동기화하는 것이 기본이에요. 비동기로 바꾸면 색인이 빨라지지만 장애 시 최근 몇 초의 쓰기를 잃어요. 원본 DB에서 다시 만들 수 있다면 감수할 만한 선택이에요.
    핵심 정리
    • 세그먼트 = 불변의 작은 역색인. 리프레시(기본 1초)로 검색 가능해짐
    • 수정 = 삭제 표시 + 재추가. 병합이 세그먼트를 합치고 삭제를 반영
    • 쓰기 직후 읽기는 원본 DB에서
    셀프 체크
    1. Elasticsearch에 문서를 색인하고 바로 검색했더니 결과에 없습니다. 원인을 설명하세요.
    답 보기

    색인된 문서는 먼저 메모리 버퍼에 들어가고, 리프레시가 일어나 그 버퍼가 새 세그먼트로 만들어져야 검색 대상이 돼요. 리프레시는 기본적으로 1초마다 일어나므로 그 사이에 실행한 검색에는 방금 색인한 문서가 포함되지 않아요. 문서가 유실된 것은 아니고 트랜스로그에 기록돼 있으며, ID로 직접 조회하면 바로 나와요. 검색 엔진이 실시간이 아니라 준실시간인 이유예요. 쓰기 직후의 일관성이 필요한 화면은 리프레시를 기다리는 옵션을 쓰거나 원본 저장소에서 읽어야 해요.

    4장 분산 구조 — 샤드와 검색 실행

    검색 한 번이 모든 샤드에 부채꼴로 퍼진다

    인덱스, 샤드, 복제본

    • 인덱스: 문서의 논리적 모음.
    • 프라이머리 샤드: 인덱스를 나눈 조각. 샤드 하나가 Lucene 인덱스 하나예요.
    • 레플리카 샤드: 프라이머리의 사본. 장애 대비와 검색 처리량을 위해 둬요. 프라이머리와 다른 노드에 놓여요.

    문서 라우팅

    문서가 어느 샤드로 갈지는 라우팅 값(기본은 문서 ID)의 해시를 프라이머리 샤드 수로 나눈 나머지로 정해요. 그래서 프라이머리 샤드 수는 인덱스를 만든 뒤에 자유롭게 바꿀 수 없어요. 바꾸면 기존 문서의 위치가 전부 틀려져요. 재색인이 필요해요.

    쓰기

    쓰기는 프라이머리 샤드에서 먼저 실행되고, 그 뒤 레플리카들에 전달돼요.

    검색은 두 단계

    1. 질의 단계: 조정 노드가 요청을 모든 샤드(샤드마다 프라이머리나 레플리카 중 하나)로 보내요. 각 샤드는 자기 안에서 상위 N개의 문서 ID와 점수만 돌려줘요.
    2. 가져오기 단계: 조정 노드가 결과를 합쳐 전체 상위 N개를 정하고, 그 문서들의 본문을 해당 샤드에서 가져와요.

    깊은 페이징이 비싼 이유

    10,000번째부터 10개를 원하면 각 샤드가 상위 10,010개씩 돌려줘야 해요. 샤드가 5개면 조정 노드가 50,050개를 받아 정렬하고 10개만 써요. 그래서 기본적으로 깊이에 상한이 있어요. 깊이 내려가야 하면 마지막 결과의 정렬 값을 넘겨받아 이어 가는 방식(search_after)을 써요.

    샤드 수

    • 너무 적으면 샤드 하나가 지나치게 커져 복구와 이동이 느려요.
    • 너무 많으면 샤드마다 드는 고정 비용(메모리, 파일, 클러스터 상태)이 쌓이고 검색이 퍼지는 폭이 커져요. 작은 샤드를 지나치게 많이 만드는 것이 더 흔한 실수예요.
    백엔드에서는 테넌트나 사용자 단위로만 검색한다면 그 ID를 라우팅 값으로 지정하세요. 같은 테넌트의 문서가 한 샤드에 모이고, 검색할 때도 그 샤드 하나만 조회하면 돼서 부채꼴로 퍼지지 않아요. 대신 큰 테넌트가 샤드 하나를 불균형하게 키울 수 있어요. 로그처럼 시간순으로 쌓이는 데이터는 기간별로 인덱스를 나누고, 오래된 인덱스를 통째로 지워요.
    시니어 심화
    • 꼬리 지연이 증폭돼요. 검색은 모든 샤드의 응답을 기다리므로 가장 느린 샤드가 전체 응답 시간이 돼요. 샤드가 많을수록 그중 하나가 느릴 확률이 높아져요. 느린 노드 하나(GC, 디스크, 병합 중)가 모든 검색을 느리게 해요. 부분 결과 허용과 타임아웃 설정을 정해 둬요.
    • 집계는 메모리를 써요. 고유 값이 많은 필드로 집계하면 각 샤드가 많은 버킷을 만들고 조정 노드가 합쳐요. 무거운 집계 하나가 노드를 메모리 부족으로 넘어뜨릴 수 있어요. 차단기 설정과 집계 크기 상한이 방어예요. 샤드별 상위 N개만 합치는 집계는 결과가 근사치라는 점도 알고 써야 해요.
    • 역할 분리: 큰 클러스터에서는 클러스터 상태를 관리하는 노드, 데이터를 가진 노드, 요청을 조정하는 노드를 나눠요. 관리 노드는 과반수 합의가 되도록 홀수(보통 3대)로 둬요.
    핵심 정리
    • 문서 위치 = 해시 % 프라이머리 샤드 수. 샤드 수 변경은 재색인
    • 검색 = 모든 샤드에 질의 → 합쳐서 상위 문서만 가져오기
    • 깊은 페이징은 샤드 수에 비례해 비쌈. search_after 사용
    셀프 체크
    1. 프라이머리 샤드 수를 인덱스 생성 후에 자유롭게 바꿀 수 없는 이유는 무엇인가요?
    답 보기

    문서가 저장될 샤드는 라우팅 값의 해시를 프라이머리 샤드 수로 나눈 나머지로 정해져요. 문서를 가져올 때도 같은 계산으로 어느 샤드에 있는지 찾아요. 샤드 수가 바뀌면 같은 문서에 대한 계산 결과가 달라져서, 이미 저장된 문서들을 엉뚱한 샤드에서 찾게 돼요. 그래서 샤드 수를 바꾸려면 새 샤드 수로 인덱스를 새로 만들고 모든 문서를 다시 색인해 새 위치로 옮겨야 해요. 배수 단위의 분할처럼 제한된 형태의 변경만 재색인 없이 지원돼요.

    5장 매핑과 쿼리 설계

    text와 keyword의 차이가 대부분을 정한다

    매핑

    필드의 타입과 색인 방식을 정하는 스키마예요. 가장 중요한 구분은 문자열의 두 타입이에요.

    textkeyword
    색인분석기로 쪼개 토큰으로값 전체를 토큰 하나로
    검색전문 검색(단어 일치, 관련도)정확히 일치, 접두사
    정렬·집계기본적으로 불가가능
    예제목, 본문, 설명상태, 카테고리 코드, ID, 이메일, 태그

    한 필드를 두 방식으로 함께 색인할 수 있어요(다중 필드). 제목을 text로 검색하면서 keyword로 정렬하는 식이에요.

    동적 매핑의 함정

    매핑 없이 문서를 넣으면 처음 본 값으로 타입을 추측해요. 추측이 틀려도 이미 정해진 필드의 타입은 바꿀 수 없어요. 재색인해야 해요. 또 임의의 키를 가진 JSON을 그대로 넣으면 필드 수가 끝없이 늘어 클러스터 상태가 비대해져요. 운영 인덱스는 매핑을 명시하고 동적 매핑을 제한해요.

    질의 문맥과 필터 문맥

    • 질의 문맥: "얼마나 잘 맞는가". 점수를 계산해요.
    • 필터 문맥: "맞는가 아닌가". 점수를 계산하지 않고 결과가 캐시돼요.

    기본 쿼리

    • match: 검색어를 분석해서 토큰으로 찾는다. text 필드용.
    • term: 검색어를 분석하지 않고 그대로 찾는다. keyword 필드용.
    • bool: 여러 조건을 조합한다. must(점수에 반영), filter(점수 없이 걸러냄), should(맞으면 가점), must_not(제외).

    문서 모델링: 비정규화

    검색 엔진에는 조인이 사실상 없어요. 검색에 필요한 정보를 한 문서에 펼쳐 넣어요. 상품 문서에 브랜드 이름, 카테고리 이름을 함께 넣는 식이에요. 대가는 브랜드 이름이 바뀌면 그 브랜드의 모든 상품 문서를 다시 색인해야 한다는 거예요.

    객체의 배열은 기본적으로 필드별로 납작하게 색인돼 원소 사이의 짝이 사라져요. 옵션 목록에서 "색상이 빨강이고 사이즈가 L인 옵션"을 찾으려면 원소를 별도 문서처럼 다루는 nested 타입이 필요해요.

    백엔드에서는 term 쿼리를 text 필드에 쓰면 거의 항상 결과가 없어요. 색인된 것은 소문자로 바뀐 토큰인데 검색어는 분석 없이 원문 그대로 비교하기 때문이에요. 반대로 상태 코드 같은 값을 text로 색인하면 정렬과 집계가 안 돼요. 필드를 추가할 때마다 "이 필드로 전문 검색을 하나, 정확히 일치를 찾나, 정렬·집계를 하나"를 묻고 타입을 정하세요.
    시니어 심화
    • 앞에 와일드카드가 붙은 검색과 정규식은 사전 전체를 훑어요. 사용자 입력으로 이런 쿼리를 만들 수 있게 열어 두면 요청 하나가 클러스터를 멈춰요. 필요하면 전용 필드 타입이나 n-gram 색인으로 풀고, 비싼 쿼리 유형은 설정으로 막아요.
    • 검색 엔진을 원본 저장소로 쓰지 마세요. 트랜잭션이 없고, 매핑을 바꾸려면 재색인이 필요하고, 분산 환경에서 쓰기 유실 가능성이 관계형 DB보다 커요. 언제든 원본에서 인덱스를 다시 만들 수 있어야 해요.
    • _source와 저장 비용: 원문 전체가 기본으로 저장돼요. 큰 필드를 검색에만 쓰고 반환하지 않는다면 응답에서 제외하고, 정렬·집계에 안 쓰는 필드는 그 용도의 자료구조를 꺼서 디스크를 줄여요.
    핵심 정리
    • text = 분석해서 전문 검색, keyword = 그대로 일치·정렬·집계
    • 매핑은 명시. 정해진 타입은 못 바꿈
    • 점수가 필요 없는 조건은 filter. 문서는 비정규화
    셀프 체크
    1. status 필드에 "ACTIVE"를 넣고 term 쿼리로 "ACTIVE"를 찾았는데 결과가 없습니다. 가능한 원인을 설명하세요.
    답 보기

    status 필드가 text 타입으로 매핑됐을 가능성이 커요. 매핑을 명시하지 않으면 문자열은 text로 추측돼요. text 필드는 색인할 때 분석기를 거치므로 "ACTIVE"가 소문자 토큰 "active"로 저장돼요. term 쿼리는 검색어를 분석하지 않고 그대로 "ACTIVE"와 일치하는 토큰을 찾으니 맞는 것이 없어요. 해결은 이 필드를 keyword 타입으로 매핑하는 거예요. 값 전체가 변환 없이 토큰 하나로 저장돼 정확한 일치, 정렬, 집계가 모두 돼요. 타입을 바꾸려면 재색인이 필요해요.

    6장 운영 — 동기화, 재색인, 용량

    원본 DB와 검색 인덱스를 맞춰 두는 일

    데이터 동기화

    원본은 DB에 있고 검색 인덱스는 그 사본이에요. 둘을 맞추는 방법이 설계의 중심이에요.

    방식방법문제
    이중 쓰기애플리케이션이 DB와 검색 엔진에 각각 쓴다한쪽만 성공하면 어긋남. 동시 요청의 순서가 뒤바뀌면 옛 값이 남음
    주기적 배치변경된 행을 주기적으로 읽어 색인한다지연이 큼. 삭제를 놓치기 쉬움
    변경 데이터 캡처(CDC)DB의 변경 로그를 읽어 순서대로 색인한다구성 요소가 늘어남. 가장 견고함

    이중 쓰기는 가장 쉽지만 반드시 어긋나요. 어긋난 것을 찾아 고치는 주기적 대조를 함께 두거나, 변경 로그 기반으로 가요.

    순서와 멱등성

    같은 문서의 갱신이 순서가 바뀌어 도착하면 옛 값이 최신 값을 덮어써요. 원본의 버전 번호나 갱신 시각을 외부 버전으로 함께 보내, 더 낮은 버전의 쓰기를 거부하게 해요. 색인 요청은 문서 ID를 지정해 여러 번 보내도 결과가 같게 해요.

    무중단 재색인

    매핑이나 분석기를 바꾸려면 새 인덱스를 만들어 전부 다시 넣어야 해요.

    1. 애플리케이션은 인덱스 이름이 아니라 별칭으로 접근한다.
    2. 새 설정으로 새 인덱스를 만든다.
    3. 원본에서 새 인덱스로 전체를 색인한다. 그동안 들어오는 변경도 새 인덱스에 반영되게 한다.
    4. 건수와 표본을 검증한다.
    5. 별칭을 새 인덱스로 원자적으로 바꾼다.
    6. 문제가 없으면 옛 인덱스를 지운다. 문제가 있으면 별칭만 되돌린다.

    용량과 안정성

    • 메모리의 절반은 OS에: Lucene은 파일 캐시에 크게 의존해요. JVM 힙을 메모리 전부로 잡으면 오히려 느려져요.
    • 디스크 수위: 디스크 사용률이 일정 수준을 넘으면 그 노드에 샤드를 배치하지 않고, 더 넘으면 인덱스가 읽기 전용이 돼요. 병합과 재색인은 일시적으로 디스크를 더 쓰니 여유를 둬요.
    • 수명 주기 관리: 시간순 데이터는 최근 것을 빠른 노드에, 오래된 것을 싼 노드에 두다가 기간이 지나면 삭제해요.

    클러스터 상태

    녹색(모든 샤드 배치됨), 노랑(프라이머리는 전부 있으나 일부 레플리카 미배치), 빨강(일부 프라이머리 없음, 그 데이터는 검색 불가). 미배치 샤드가 있을 때는 배치 설명 API가 이유를 알려줘요.

    백엔드에서는 검색 엔진 장애가 서비스 전체 장애가 되지 않게 하세요. 검색 호출에 타임아웃과 서킷 브레이커를 걸고, 색인 실패가 원본 DB의 쓰기 트랜잭션을 롤백시키지 않게 분리해요. 그리고 "인덱스를 처음부터 다시 만드는 데 얼마나 걸리는가"를 실제로 재 두세요. 매핑 변경, 분석기 변경, 데이터 불일치 복구가 전부 이 절차를 쓰기 때문에, 이것이 느리면 검색 개선 전체가 느려져요.
    핵심 정리
    • 이중 쓰기는 어긋남. CDC 또는 주기적 대조. 외부 버전으로 순서 보장
    • 별칭 + 새 인덱스 + 원자적 전환으로 무중단 재색인
    • 힙은 메모리의 절반 이하, 디스크 여유 확보, 검색 장애를 격리
    셀프 체크
    1. 애플리케이션이 DB에 저장한 뒤 검색 엔진에 색인하는 이중 쓰기 방식에서 두 저장소가 어긋나는 경우를 두 가지 말해보세요.
    답 보기

    첫째, 부분 실패예요. DB 저장은 성공했는데 검색 엔진 색인이 네트워크 오류나 타임아웃으로 실패하면 DB에만 데이터가 있어요. 색인 실패로 DB를 롤백하려 해도 이미 커밋된 뒤일 수 있고, 반대 순서로 해도 같은 문제가 반대로 생겨요. 둘째, 순서 뒤바뀜이에요. 같은 문서를 두 요청이 거의 동시에 수정하면, DB에는 A 다음 B 순서로 반영됐는데 검색 엔진에는 B 다음 A 순서로 도착할 수 있어요. 그러면 DB의 최종 값은 B인데 검색 인덱스에는 A가 남아요. 변경 로그를 순서대로 따라가는 방식이나 버전 번호로 낮은 버전의 쓰기를 거부하는 방식으로 막아요.

    실습

    실습 과제

    단일 노드 Elasticsearch나 OpenSearch를 컨테이너로 띄워서 해 보세요.

    • 1장 문서 몇 개로 역색인을 직접 구현(단어 → 문서 ID 목록, 교집합 검색). _analyze로 표준 분석기와 한국어 형태소 분석기의 토큰 비교
    • 2장 같은 검색어의 결과를 explain으로 열어 점수의 구성 확인. 제목 필드에 가중치를 주고 순위 변화 관찰
    • 3장 색인 직후 검색과 ID 조회의 결과 비교. 리프레시 간격을 바꿔 가며 대량 색인 속도 측정
    • 4장 샤드 5개 인덱스에서 깊은 페이지를 요청해 응답 시간 측정. search_after로 바꿔 비교
    • 5장 같은 문자열 필드를 text와 keyword로 각각 매핑하고 match와 term 쿼리의 결과 비교. 객체 배열의 교차 매칭 문제를 재현하고 nested로 해결
    • 6장 별칭을 사용해 매핑을 바꾼 새 인덱스로 무중단 전환. 이중 쓰기 중 색인을 일부러 실패시켜 불일치를 만들고 대조 스크립트로 찾기
