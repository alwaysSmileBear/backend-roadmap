    검색 엔진

    기준 자료: Introduction to Information Retrieval + Elasticsearch 공식 문서 · 2~3주

    "상품명에 이 단어가 들어간 것"을 DB의 LIKE로 찾다가 느려지면 검색 엔진을 들이게 돼요. 이 챕터는 검색 엔진이 왜 그 질문에 빠른지, 결과의 순서를 어떻게 정하는지, 그리고 그 구조 때문에 무엇을 못 하는지를 봐요.

    예시는 쇼핑몰의 상품 검색이에요. 상품 300만 개를 Elasticsearch로 검색하는 상황을 따라가요. 바탕인 Lucene의 원리는 OpenSearch, Solr에도 같아요. 시간이 없으면 1장(역색인과 분석기)과 5장(매핑과 쿼리)을 먼저 읽으세요. "검색이 안 돼요"의 대부분이 이 둘에서 풀려요.

    Introduction to Information Retrieval 기준 자료nlp.stanford.edu/IR-book · 무료. 1, 2, 6장
    Elasticsearch 공식 문서 심화매핑, 텍스트 분석, 확장성 부분
    1부 원리

    1장 역색인과 분석기

    문서에서 단어를 찾지 않고, 단어에서 문서를 찾는다

    문제: LIKE 검색이 3초 걸린다

    상품 검색을 WHERE name LIKE '%노트북%'으로 만들었어요. 상품이 1만 개일 때는 괜찮았는데 300만 개가 되자 검색 한 번에 3초가 걸려요. name에 인덱스도 걸려 있는데요.

    B-Tree 인덱스는 값의 앞부분부터 정렬돼 있어요. "노트북으로 시작하는 것"은 빨리 찾지만, "중간 어딘가에 노트북이 들어 있는 것"은 정렬 순서와 상관이 없어서 모든 행을 읽어 봐야 알아요. 게다가 "노트북"으로 검색하면 "노트북을"이나 "notebook"은 못 찾고, 결과의 순서도 정할 수 없어요.

    역색인: 단어마다 문서 목록을 만든다

    책 뒤의 찾아보기를 생각해 보세요. 본문을 처음부터 읽지 않고, 단어를 찾으면 그 단어가 나오는 쪽 번호가 적혀 있어요. 검색 엔진도 같아요. 미리 단어마다 그 단어가 나오는 문서의 목록을 만들어 둬요. 이것을 역색인이라고 해요.

    "게이밍 노트북"을 검색하면 "게이밍"의 목록 [1, 3]과 "노트북"의 목록 [1, 2]를 가져와 겹치는 것(1번)을 찾아요. 상품이 300만 개여도 비용은 그 단어가 나오는 문서 수에만 비례해요. 목록에는 문서 번호뿐 아니라 단어가 몇 번, 몇 번째 자리에 나왔는지도 저장해요. 자리 정보가 있어야 "두 단어가 붙어 있는" 구문 검색을 할 수 있어요.

    분석기: 텍스트를 단어로 쪼갠다

    역색인의 품질은 텍스트를 어떻게 단어(토큰)로 쪼개느냐에 달려 있어요. 이 일을 하는 것이 분석기이고, 세 단계예요. 먼저 문자 필터가 원문을 다듬어요(HTML 태그 제거 등). 다음으로 토크나이저가 토큰으로 잘라요(공백, 문장 부호, 형태소 기준). 마지막으로 토큰 필터가 토큰을 바꿔요(소문자로, 불용어 제거, 어간 추출, 동의어 추가).

    가장 중요한 규칙은 색인할 때와 검색할 때 같은 방식으로 분석한다는 거예요. 색인할 때 "Notebook"을 "notebook"으로 바꿔 저장했다면, 검색어 "NOTEBOOK"도 "notebook"으로 바꿔야 맞아요. 검색은 문자열 비교가 아니라 토큰끼리의 일치예요.

    한국어는 공백으로 자를 수 없다

    한국어를 공백으로 자르면 "노트북을", "노트북이", "노트북"이 전부 다른 토큰이 돼요. "노트북"으로 검색하면 "가벼운 노트북을 찾는다면"이라는 설명의 상품은 안 나와요. 조사와 어미를 떼어 내는 형태소 분석기(Elasticsearch의 nori 등)가 필요해요. 그리고 "삼성전자"를 "삼성"과 "전자"로 쪼갤지, 새로 나온 상품명이나 브랜드명을 어떻게 다룰지는 사용자 사전으로 정해요. 검색 품질의 상당 부분이 여기서 갈려요.

    백엔드에서는 "분명히 있는 단어인데 검색이 안 된다"는 문의가 오면 추측하지 말고 분석 결과를 직접 보세요. Elasticsearch의 _analyze API에 텍스트와 분석기를 넣으면 어떤 토큰이 나오는지 보여줘요. 상품명이 색인될 때의 토큰과 검색어의 토큰을 나란히 놓으면 왜 안 맞는지 바로 보여요. 신조어나 상품명이 엉뚱하게 쪼개지면 사용자 사전에 추가해요.
    시니어 심화 "노트"로 "노트북"을 찾고 싶다는 요구가 자주 와요. 그런데 이것은 역색인의 기본 동작이 아니에요. 그리고 이 요구를 해결하려고 분석기를 바꾸는 순간 전체 재색인이 따라와요.

    상황

    상품 검색에서 "노트"를 치면 노트북이 안 나온다는 문의가 들어왔어요. 개발자가 분석기 설정에 n-gram을 추가했는데, 새로 등록한 상품만 그렇게 검색되고 기존 상품 200만 개는 여전히 안 나왔어요. 사용자 사전에 신상품 브랜드명을 추가했을 때도 같은 일이 있었어요.

    깨지는 과정

    1. 역색인은 문서를 분석기로 토큰으로 자른 뒤 "토큰마다 그것이 들어 있는 문서 목록"을 저장해요. 검색은 토큰이 정확히 같은지를 봐요. "노트"라는 토큰은 "노트북" 토큰과 다른 것이라서 안 나와요.
    2. 앞부분 일치("노트"로 시작하는 토큰)는 토큰 사전이 정렬돼 있어서 비교적 싸게 지원돼요(접두사 쿼리). 하지만 중간 일치("트북"으로 "노트북")는 토큰을 글자 조각(n-gram)으로 잘라 전부 색인해야 하고, 색인 크기가 몇 배로 커져요.
    3. 분석기를 바꿔도 이미 저장된 토큰은 옛 방식으로 만들어진 그대로예요. 기존 문서를 다시 색인하기 전까지는 새 분석기의 효과가 없어요.
    4. 사용자 사전에 단어를 추가하는 것도 분석기를 바꾸는 것과 같아요. 색인할 때 적용되는 설정이라면 재색인이 필요해요.

    해결책

    • 용도별로 필드를 나눠요. 같은 상품명을 일반 분석기 필드, 자동 완성용 앞부분 조각(edge n-gram) 필드, 필요하면 중간 일치용 n-gram 필드로 각각 색인하고(멀티 필드), 검색할 때 상황에 맞는 필드를 써요. 하나의 필드로 모든 요구를 풀려고 하지 않아요.
    • 자주 바뀌는 것은 검색할 때 적용해요. 동의어("노트북 = 랩탑")처럼 자주 바뀌는 규칙은 검색 시점 분석기에 넣으면, 목록을 바꿔도 재색인 없이 바로 반영돼요. 색인 시점에 넣으면 바꿀 때마다 재색인이 필요해요.
    • 재색인을 언제든 할 수 있게 만들어 둬요. 새 매핑으로 새 인덱스를 만들고, 원본에서 다시 색인하고, 별칭(alias)을 새 인덱스로 한 번에 바꾸는 절차를 자동화해 두면 분석기 변경이 두렵지 않아요(6장).
    • 분석 결과를 직접 확인해요. Elasticsearch의 _analyze API로 "삼성 갤럭시북3 프로"가 어떤 토큰으로 잘리는지 보고, 분석기를 바꾸기 전후를 비교해요.

    운영에서 알아채는 법

    • "결과 없음" 검색어 상위 목록을 매일 봐요. 분석기나 사전이 놓치는 단어가 바로 보여요.
    • 분석기 설정을 바꾼 PR에는 "재색인이 필요한가"를 체크 항목으로 넣어요.
    핵심 정리
    • 역색인 = 단어 → 문서 목록. 비용이 전체 문서 수와 무관
    • 분석기 = 문자 필터 → 토크나이저 → 토큰 필터. 색인과 검색에 같은 분석
    • 한국어는 형태소 분석기 + 사용자 사전
    셀프 체크
    1. 상품명 "Apple MacBook Pro"를 색인했는데 "macbook"으로 검색하면 나오고 "mac"으로는 나오지 않습니다. 이유는 무엇인가요?
    답 보기

    역색인에는 분석기가 만든 토큰이 저장돼요. 표준 분석기는 이 상품명을 apple, macbook, pro 세 토큰으로 만들어요. 검색은 검색어의 토큰과 저장된 토큰이 정확히 같은지를 봐요. macbook은 저장된 토큰과 일치하지만 mac이라는 토큰은 어디에도 없어요. mac이 macbook의 앞부분이라는 사실을 역색인은 모르기 때문이에요. 앞부분 일치를 지원하려면 토큰의 앞에서부터 잘라 낸 조각들을 함께 색인하거나 접두사 쿼리를 써야 해요.

    2장 랭킹 — TF-IDF와 BM25

    맞는 문서가 아니라 가장 맞는 문서를 먼저

    문제: "썬더볼트 노트북"을 검색했는데 가방이 먼저 나온다

    "썬더볼트 노트북"을 검색했더니 썬더볼트 단자가 있는 노트북보다 "노트북 가방 · 노트북 파우치 · 노트북 거치대"라는 상품이 먼저 나왔어요. 둘 다 검색어와 맞는 상품이긴 해요. 순서는 무엇으로 정해질까요?

    검색은 순서의 문제다

    DB 조회의 결과는 조건에 맞거나 안 맞거나예요. 검색의 결과는 얼마나 관련 있는가의 순서예요. 맞는 상품이 2만 개여도 사용자는 첫 화면의 20개만 봐요. 그래서 검색 엔진은 문서마다 점수를 매기고 점수 순으로 보여줘요.

    점수의 세 가지 직관

    첫째, 문서 안에 검색어가 많이 나올수록 관련 있어요(단어 빈도, TF). 둘째, 전체 문서 중 드문 단어일수록 중요해요(역문서 빈도, IDF). 셋째, 긴 문서는 단어가 많이 나오기 쉬우니 길이를 보정해요.

    둘째가 이 문제의 핵심이에요. 쇼핑몰에서 "노트북"은 수십만 개의 상품(노트북, 가방, 파우치, 거치대, 키보드)에 나와요. 어떤 상품에 "노트북"이 있다는 사실은 그 상품을 다른 상품과 거의 구분해 주지 못해요. 반면 "썬더볼트"는 수백 개의 상품에만 나와요. 이 단어가 있는 상품은 검색 의도와 맞을 가능성이 훨씬 커요. 그래서 드문 단어의 일치에 높은 점수를, 흔한 단어의 일치에 낮은 점수를 줘요.

    그런데 위의 가방 상품은 "노트북"을 세 번이나 반복했어요. 단순한 빈도 계산에서는 흔한 단어라도 많이 나오면 점수가 쌓여서, 드문 단어 한 번을 이길 수 있어요.

    BM25: 반복은 일정 수준에서 멈춘다

    지금 기본으로 쓰이는 점수 함수인 BM25는 이 문제를 고쳤어요. 단어가 1번에서 2번으로 늘 때의 효과는 크지만, 3번, 5번, 20번으로 늘수록 점수는 거의 오르지 않아요(포화). 상품명에 같은 단어를 반복해 넣는 것이 유리해지지 않아요. 문서 길이의 영향도 매개변수로 조절해요.

    텍스트 점수만으로는 부족하다

    그래도 BM25는 텍스트만 봐요. 실제 쇼핑몰의 순위에는 업무 신호가 섞여요. 판매량, 리뷰 평점, 최신성, 재고 여부예요. 필드별 가중치(상품명의 일치를 설명보다 더 크게)를 주고, 텍스트 점수를 판매량 같은 값으로 조정하는 함수를 써요. 더 나아가 1차로 검색한 상위 결과 수백 개를 별도의 모델로 다시 정렬하기도 해요.

    백엔드에서는 "왜 이 상품이 위에 나오지?"는 explain 옵션으로 답할 수 있어요. 점수가 어떤 항들의 합으로 나왔는지 문서마다 보여줘요. 순위 조정 요청이 올 때마다 가중치를 감으로 바꾸면 다른 검색어의 결과가 조용히 망가져요. 대표 검색어 100개와 각각 위에 나와야 할 상품의 목록을 만들어 두고, 설정을 바꿀 때마다 전체를 다시 돌려 비교하세요.
    시니어 심화 작은 인덱스에서 결과 순서가 이상하게 흔들리거나, 분명히 더 관련 있는 상품이 아래에 있는 경우가 있어요. 원인은 대개 점수의 계산 방식에 있어요.

    상황

    신규 오픈한 카테고리 전용 인덱스(상품 3,000개, 샤드 5개)에서 같은 검색어를 두 번 했는데 순서가 달랐어요. 그리고 "판매 중" 조건을 검색 쿼리에 넣은 뒤로 판매 중인 상품 사이의 순서가 이상해졌다는 문의도 있었어요.

    깨지는 과정

    1. 점수는 샤드마다 따로 계산돼요. BM25의 IDF(이 단어가 얼마나 드문가)에 쓰는 "이 단어가 몇 개 문서에 나오는가"를 각 샤드가 자기 문서만 보고 세요(4장).
    2. 문서가 3,000개를 5개 샤드에 나누면 샤드마다 600개뿐이에요. 어떤 단어가 한 샤드에는 3번, 다른 샤드에는 30번 나오면, 같은 문서라도 어느 샤드에 있느냐에 따라 점수가 크게 달라져요.
    3. 복제본마다 삭제 표시된 문서 수가 조금씩 달라서, 같은 검색이 어느 복제본으로 가느냐에 따라 점수도 조금씩 달라져요. 순서가 흔들려요.
    4. 필터를 쿼리로 넣으면 점수가 섞여요. "판매 중"을 점수에 영향을 주는 쿼리(must)로 넣자, "판매 중"이라는 단어 자체의 점수가 더해졌어요. 모든 문서에 같은 값이라 의미 없는 점수가 섞여서 순위가 이상해졌어요.

    해결책

    • 문서가 적은 인덱스는 샤드를 하나로 둬요. 수만 개 이하의 문서라면 샤드 하나로 충분하고, 점수가 한 곳에서 계산돼요. 꼭 여러 샤드여야 하면 전역 통계를 먼저 모으는 검색 방식(dfs_query_then_fetch)을 써요. 요청이 한 번 더 오가는 대가가 있어요.
    • 같은 사용자는 같은 복제본으로 보내요. 검색 요청에 preference로 세션 ID를 넘기면, 같은 사용자의 검색은 같은 복제본으로 가서 페이지를 넘기는 동안 순서가 흔들리지 않아요.
    • 점수에 영향을 주면 안 되는 조건은 필터로 넣어요. 카테고리, 가격대, 판매 중 여부는 bool 쿼리의 filter에 넣어요. 필터는 점수를 계산하지 않고 결과가 캐시돼서 빠르기도 해요(5장).
    • 업무 신호는 명시적으로 섞어요. 판매량, 평점, 신상품 여부를 순위에 반영하고 싶다면 function_score로 가중치를 명시해요. 텍스트 점수에 우연히 섞이게 두지 않아요.

    품질은 사용자 행동으로 확인해요

    사람이 매긴 관련도 평가는 비싸고 금방 낡아요. 검색 후 클릭률, 결과 없음 비율, 바로 다시 검색하는 비율(원하는 결과가 없었다는 신호), 검색 후 구매 전환을 지표로 남기고, 순위 변경은 A/B 실험으로 비교해요. 랭킹 설정을 바꾼 뒤 "느낌상 좋아졌다"로 배포하지 않아요.

    핵심 정리
    • 검색 결과는 관련도 순서. TF(많이 나옴) × IDF(드문 단어) × 길이 보정
    • BM25: 반복의 효과가 포화. 지금의 기본 점수 함수
    • 텍스트 점수 + 업무 신호. 변경은 대표 검색어 묶음과 사용자 행동으로 검증
    셀프 체크
    1. IDF가 낮은 단어(거의 모든 문서에 나오는 단어)가 점수에 적게 기여하도록 만든 이유를 설명하세요.
    답 보기

    검색의 목적은 관련 있는 문서를 다른 문서와 구분하는 거예요. 거의 모든 문서에 나오는 단어는 그 단어가 있다는 사실만으로는 어떤 문서가 더 관련 있는지 알려주지 못해요. 쇼핑몰에서 "상품"이나 "노트북" 같은 단어가 그래요. 반대로 소수의 문서에만 나오는 단어는 그 단어를 가진 문서가 검색 의도와 맞을 가능성을 크게 높여요. 그래서 드문 단어의 일치에 높은 점수를, 흔한 단어의 일치에 낮은 점수를 줘서 구분력이 있는 단어가 순위를 정하게 해요.

    2부 구현

    3장 세그먼트와 준실시간 검색

    방금 등록한 상품이 검색되지 않는 이유

    문제: 상품을 등록했는데 검색에 없다

    판매자가 새 상품을 등록하고 곧바로 검색해 봤더니 나오지 않았어요. 1~2초 뒤에 다시 검색하니 나왔어요. 그리고 상품 상세 페이지에서는 바로 보였어요. 색인 요청은 분명히 성공했는데, 왜 검색에만 늦게 나타날까요?

    세그먼트: 한번 쓰면 바꾸지 않는 작은 색인

    Lucene의 색인은 여러 개의 세그먼트로 이뤄져 있어요. 세그먼트 하나는 그 자체로 완결된 작은 역색인이고, 한번 쓰면 절대 바꾸지 않아요. 바꾸지 않으니 여러 스레드가 락 없이 동시에 읽을 수 있고, 운영체제의 파일 캐시에 올라가면 계속 유효하고, 압축해서 저장할 수 있어요.

    쓰기의 흐름

    새 상품을 색인하면 먼저 메모리 버퍼에 쌓이고, 동시에 장애 복구용 기록(트랜스로그)에 남아요. 메모리 버퍼에 있는 동안은 아직 역색인이 아니라서 검색되지 않아요. 리프레시가 일어나면 버퍼의 내용이 새 세그먼트로 만들어지고 그때부터 검색돼요. 리프레시는 기본적으로 1초마다 일어나요. 위 문제의 "1~2초"가 이것이에요. 이렇게 쓰기와 검색 사이에 짧은 지연이 있어서 준실시간 검색이라고 불러요. 반면 문서 ID로 직접 가져오는 조회는 트랜스로그와 버퍼를 함께 보기 때문에 바로 돼요. 상품 상세 페이지에서는 바로 보였던 이유예요.

    주기적으로는 플러시가 세그먼트를 디스크에 확실히 내려쓰고, 더 이상 필요 없어진 트랜스로그를 비워요.

    수정과 삭제는 표시만 한다

    세그먼트를 고칠 수 없으니, 상품 삭제는 "이 문서는 삭제됨"이라고 표시만 해요. 상품 수정은 옛 문서에 삭제 표시를 하고 새 문서를 추가하는 거예요. 가격 하나만 바꿔도 상품 문서 전체가 다시 색인돼요.

    병합

    리프레시마다 작은 세그먼트가 하나씩 생기니 그대로 두면 세그먼트가 수천 개가 돼요. 검색은 모든 세그먼트를 봐야 해서 느려져요. 그래서 백그라운드에서 작은 세그먼트들을 큰 세그먼트로 병합하고, 이때 삭제 표시된 문서가 실제로 사라져요. 덧붙이기만 하고 정리는 나중에 병합으로 하는 이 구조는 LSM 트리(분산 시스템 챕터 3장)와 같은 생각이에요.

    백엔드에서는 저장 직후 목록에 바로 보여야 하는 화면에 검색 엔진을 쓰면 "방금 등록한 상품이 안 보여요"가 나와요. 색인 요청에 리프레시를 기다리는 옵션(refresh=wait_for)을 쓸 수 있지만 응답이 그만큼 늦어져요. 요청마다 강제로 리프레시하면 아주 작은 세그먼트가 폭증해 전체가 느려져요. 판매자의 "내 상품 목록"처럼 방금 쓴 데이터를 봐야 하는 화면은 원본 DB에서 읽는 편이 보통 나아요.
    시니어 심화 수정이 "삭제 표시 + 새 문서"라는 사실은 자주 바뀌는 필드를 검색 문서에 넣을 때 문제가 돼요. 그리고 대량 색인과 평소 색인은 정반대의 설정이 필요해요.

    상황

    상품 검색 문서에 재고 수량과 조회수를 함께 넣어 "품절 제외"와 "인기순"을 검색 엔진에서 처리했어요. 세일 날 주문이 몰리자 검색 클러스터의 CPU와 디스크 I/O가 치솟았고, 검색 응답이 몇 배로 느려졌어요. 검색 트래픽은 평소와 비슷했어요.

    깨지는 과정

    1. 검색 엔진의 세그먼트는 한 번 쓰면 고치지 않아요. 문서를 수정하면 옛 문서에 삭제 표시를 하고 새 문서를 통째로 다시 색인해요.
    2. 주문이 하나 들어올 때마다 재고가 바뀌고, 그 상품의 문서 전체(상품명, 설명 분석 포함)가 다시 색인돼요. 상품 페이지가 열릴 때마다 조회수가 바뀌니 또 다시 색인돼요.
    3. 인기 상품일수록 더 자주 바뀌어서, 삭제 표시된 옛 문서가 빠르게 쌓여요. 세그먼트 병합이 이것을 치우느라 디스크를 계속 써요.
    4. 색인 부하와 병합 부하가 검색과 같은 노드의 CPU와 디스크를 나눠 쓰면서 검색이 느려져요.

    해결책

    • 초 단위로 바뀌는 값은 검색 문서에서 빼요. 재고는 검색 결과를 받은 뒤 원본(DB나 캐시)에서 따로 가져와 합치고, 품절 여부처럼 검색 조건에 꼭 필요한 값은 "품절됨/판매 중"처럼 덜 자주 바뀌는 형태로만 넣어요.
    • 필요하면 모아서 반영해요. 조회수처럼 순위에 필요한 값은 몇 분마다 모아서 한 번에 반영해요. 1분 늦은 인기순은 사용자가 알아채지 못해요.
    • 대량 색인 때는 쓰기를 최대한 빠르게 하는 설정을 써요. 처음 적재하거나 전체를 다시 색인할 때는 리프레시 간격을 길게 하거나 끄고(refresh_interval: -1), 복제본 수를 0으로 뒀다가 끝난 뒤 되돌리고, 문서는 하나씩이 아니라 묶음(bulk)으로 보내요. 끝나면 평소 설정으로 꼭 되돌려요.
    • 트랜스로그 설정은 원본이 있을 때만 느슨하게 해요. 트랜스로그를 요청마다 디스크에 동기화하는 것이 기본인데, 비동기로 바꾸면 색인이 빨라지는 대신 장애 때 최근 몇 초의 쓰기를 잃어요. 원본 DB에서 언제든 다시 만들 수 있는 검색 인덱스라면 감수할 만한 선택이에요.

    운영에서 알아채는 법

    • 인덱스의 초당 색인 문서 수를 검색 트래픽과 함께 봐요. 상품 수에 비해 색인 수가 훨씬 많다면 자주 바뀌는 필드가 들어 있어요.
    • 인덱스의 삭제 표시 문서 비율(docs.deleted ÷ docs.count)과 병합 시간을 지표로 남겨요.
    핵심 정리
    • 세그먼트 = 바꾸지 않는 작은 역색인. 리프레시(기본 1초) 뒤에 검색 가능
    • ID 조회는 바로 됨. 수정 = 삭제 표시 + 재추가, 병합이 정리
    • 쓰기 직후 읽어야 하는 화면은 원본 DB에서
    셀프 체크
    1. Elasticsearch에 문서를 색인하고 바로 검색했더니 결과에 없습니다. 원인을 설명하세요.
    답 보기

    색인된 문서는 먼저 메모리 버퍼에 들어가고, 리프레시가 일어나 그 버퍼가 새 세그먼트로 만들어져야 검색 대상이 돼요. 리프레시는 기본적으로 1초마다 일어나므로 그 사이에 한 검색에는 방금 색인한 문서가 포함되지 않아요. 문서가 사라진 것은 아니고 트랜스로그에 기록돼 있으며, ID로 직접 조회하면 바로 나와요. 쓰기 직후의 일관성이 필요한 화면은 리프레시를 기다리는 옵션을 쓰거나 원본 저장소에서 읽어야 해요.

    4장 분산 구조 — 샤드와 검색 실행

    검색 한 번이 모든 샤드로 퍼진다

    문제: 500페이지째는 응답이 몇 초 걸린다

    상품 검색 결과는 한 페이지에 20개씩 보여줘요. 1페이지는 50ms면 나오는데, 크롤러가 500페이지째(10,000번째 결과)를 요청하면 몇 초가 걸리고 검색 클러스터의 메모리가 출렁여요. 같은 20개를 가져오는데 왜 이렇게 다를까요?

    인덱스는 샤드로 나뉜다

    상품 300만 개를 서버 한 대에 다 두기 어려우니, 인덱스를 여러 조각으로 나눠요. 이 조각이 프라이머리 샤드이고, 샤드 하나가 Lucene 색인 하나예요. 각 프라이머리에는 사본인 레플리카 샤드를 두어 장애에 대비하고 검색 처리량을 늘려요. 레플리카는 프라이머리와 다른 서버에 놓여요.

    상품 하나가 어느 샤드에 들어갈지는 라우팅 값(기본은 문서 ID)의 해시를 프라이머리 샤드 수로 나눈 나머지로 정해요. 그래서 프라이머리 샤드 수는 인덱스를 만든 뒤 자유롭게 바꿀 수 없어요. 바꾸면 이미 저장된 상품들의 위치 계산이 전부 틀려지니까요. 바꾸려면 재색인해야 해요(6장).

    검색은 두 단계로 실행된다

    검색 요청을 받은 노드(조정 노드)는 요청을 모든 샤드로 보내요. 어떤 상품이 어느 샤드에 있을지 모르니까요. 1단계(질의)에서 각 샤드는 자기 안에서 상위 20개를 골라 문서 ID와 점수만 돌려줘요. 조정 노드는 이것을 합쳐 전체 상위 20개를 정해요. 2단계(가져오기)에서 그 20개의 본문을 해당 샤드에서 가져와요.

    깊은 페이지가 비싼 이유

    이제 문제의 답이 나와요. 10,000번째부터 20개를 원하면, 각 샤드는 자기 안의 상위 10,020개를 골라 돌려줘야 해요. 그중 어느 것이 전체 10,001~10,020번째가 될지 샤드 혼자서는 모르니까요. 샤드가 5개면 조정 노드는 50,100개를 받아 정렬하고 20개만 써요. 페이지가 깊어질수록 이 비용이 커져서, Elasticsearch는 기본으로 10,000번째까지만 허용해요. 깊이 내려가야 한다면 마지막 결과의 정렬 값을 넘겨받아 "그 다음부터" 가져오는 방식(search_after)을 써요. API 챕터 3장의 커서 페이징과 같은 생각이에요.

    샤드 수 정하기

    샤드가 너무 적으면 샤드 하나가 지나치게 커져서 장애 때 복구하고 다른 서버로 옮기는 데 오래 걸려요. 너무 많으면 샤드마다 드는 고정 비용(메모리, 파일, 클러스터 상태)이 쌓이고, 검색 한 번이 퍼져 나가는 대상이 늘어나요. 실무에서는 작은 샤드를 지나치게 많이 만드는 실수가 더 흔해요.

    백엔드에서는 입점 업체가 자기 상품만 검색하는 판매자 관리 화면이라면, 판매자 ID를 라우팅 값으로 지정하세요. 같은 판매자의 상품이 한 샤드에 모이고, 검색할 때도 그 샤드 하나만 보면 돼서 모든 샤드로 퍼지지 않아요. 대신 상품이 아주 많은 대형 판매자 하나가 샤드 하나를 불균형하게 키울 수 있어요. 검색 로그처럼 시간순으로 쌓이는 데이터는 기간별로 인덱스를 나누고, 오래된 인덱스를 통째로 지워요.
    시니어 심화 검색은 모든 샤드의 응답을 기다리므로 가장 느린 샤드가 전체 응답 시간이 돼요. 그리고 집계는 검색보다 훨씬 많은 메모리를 써요.

    상황

    상품 검색 클러스터는 데이터 노드 12대, 인덱스 샤드 24개예요. 평소 p99가 80ms인데, 하루 몇 번씩 모든 검색이 1초 넘게 걸렸어요. 확인해 보니 노드 하나가 GC로 멈춰 있었어요. 또 한 번은 운영자가 "전체 상품의 판매자별 개수" 집계를 돌리자 노드 두 대가 메모리 부족으로 떨어졌어요.

    깨지는 과정

    1. 검색 요청은 조정 노드가 모든 샤드에 보내고, 모든 응답을 모아 합쳐서 돌려줘요(scatter-gather).
    2. 샤드 24개 중 하나가 GC로 1초 멈춰 있으면, 그 샤드의 응답을 기다리느라 모든 검색이 1초가 돼요. 샤드가 많을수록 그중 하나가 느릴 확률이 높아져요(성능 분석 챕터 2장의 팬아웃).
    3. 병합으로 디스크가 바쁜 노드, 인기 인덱스의 샤드가 몰린 노드도 같은 효과를 내요.
    4. 판매자별 집계는 판매자 수만큼 버킷을 만들어요. 판매자가 수십만이면 각 샤드가 수십만 개의 버킷을 만들어 조정 노드로 보내고, 조정 노드가 그것을 합치느라 메모리를 다 써요.

    해결책

    • 느린 샤드에 대한 정책을 미리 정해요. 검색 요청에 타임아웃을 두고, 일부 샤드가 늦으면 그 샤드를 빼고 부분 결과를 돌려줄지(allow_partial_search_results) 정해요. 상품 검색이라면 일부 결과가 빠지는 것이 1초 지연보다 나은 경우가 많아요.
    • 복제본으로 꼬리를 줄여요. 적응형 복제본 선택(adaptive replica selection)은 응답이 빠른 복제본으로 요청을 보내서, 느린 노드 하나의 영향을 줄여요. 최근 버전은 기본으로 켜져 있어요.
    • 샤드 수를 적정하게 둬요. 샤드가 너무 많으면 팬아웃이 커지고, 샤드마다 고정 비용이 생겨요. 샤드 하나에 수십 GB 정도가 흔한 기준이에요.
    • 집계에 상한을 둬요. 버킷 수 상한(search.max_buckets)과 메모리 차단기(circuit breaker) 설정으로 무거운 집계가 노드를 넘어뜨리기 전에 거부하게 해요. 운영용 분석 집계는 서비스 클러스터가 아니라 별도 클러스터나 DB에서 해요.
    • 집계 결과가 근사치일 수 있다는 것을 알아 둬요. "상위 10개 브랜드" 같은 집계는 각 샤드의 상위 N개만 합치는 방식이라 순위와 개수가 정확하지 않을 수 있어요. 정산이나 리포트처럼 정확해야 하는 수치에는 검색 엔진의 집계를 쓰지 않아요.
    • 노드 역할을 나눠요. 큰 클러스터에서는 클러스터 상태를 관리하는 노드, 데이터를 가진 노드, 요청을 조정하는 노드를 나누고, 관리 노드는 과반수 판단이 되도록 3대를 둬요. 관리 노드가 무거운 검색에 휘말려 멈추면 클러스터 전체가 불안정해져요.

    운영에서 알아채는 법

    • 노드별 검색 지연과 GC 시간을 겹쳐 봐요. 전체 p99가 튀는 순간 특정 노드의 GC가 튄다면 그 노드가 꼬리를 만들고 있어요.
    • 차단기가 요청을 거부한 횟수를 지표로 남기고, 어떤 쿼리가 걸렸는지 로그로 확인해요.
    핵심 정리
    • 문서 위치 = 해시 % 프라이머리 샤드 수. 샤드 수를 바꾸려면 재색인
    • 검색 = 모든 샤드에서 상위 N개 ID 모으기 → 최종 N개 본문 가져오기
    • 깊은 페이지는 샤드 수에 비례해 비쌈. search_after로
    셀프 체크
    1. 프라이머리 샤드 수를 인덱스를 만든 뒤에 자유롭게 바꿀 수 없는 이유는 무엇인가요?
    답 보기

    문서가 저장될 샤드는 라우팅 값의 해시를 프라이머리 샤드 수로 나눈 나머지로 정해져요. 문서를 가져올 때도 같은 계산으로 어느 샤드에 있는지 찾아요. 샤드 수가 바뀌면 같은 문서에 대한 계산 결과가 달라져서, 이미 저장된 문서들을 엉뚱한 샤드에서 찾게 돼요. 그래서 샤드 수를 바꾸려면 새 샤드 수로 인덱스를 새로 만들고 모든 문서를 다시 색인해서 새 위치로 옮겨야 해요. 정확히 배수로 나누는 것처럼 제한된 형태의 변경만 재색인 없이 지원돼요.

    5장 매핑과 쿼리 설계

    text와 keyword의 차이가 대부분을 정한다

    문제: 상태가 ACTIVE인 상품이 하나도 안 나온다

    판매 중인 상품만 검색하려고 {"term": {"status": "ACTIVE"}} 조건을 넣었더니 결과가 0건이에요. 문서를 직접 열어 보면 "status": "ACTIVE"가 분명히 들어 있어요. 그리고 같은 인덱스에서 브랜드 이름으로 정렬하려 하니 에러가 나요.

    매핑: 필드를 어떻게 색인할지 정한다

    매핑은 필드마다 타입과 색인 방식을 정하는 스키마예요. 가장 중요한 구분은 문자열의 두 타입이에요.

    text는 분석기를 거쳐 토큰으로 쪼개 색인해요. "Apple MacBook Pro"는 apple, macbook, pro 세 토큰이 돼요. 전문 검색(단어 일치, 관련도 점수)에 써요. 기본적으로 정렬과 집계는 안 돼요. keyword는 값 전체를 바꾸지 않고 토큰 하나로 색인해요. 정확히 같은 값 찾기, 정렬, 집계에 써요. 상태, 카테고리 코드, 브랜드, ID, 태그가 여기예요. 한 필드를 두 방식으로 함께 색인할 수도 있어요(다중 필드). 상품명을 text로 검색하면서 keyword로 정렬하는 식이에요.

    이제 문제의 답이 나와요. 매핑을 정하지 않고 문서를 넣으면 Elasticsearch는 문자열을 text(와 보조 keyword)로 추측해요. status가 text로 색인되면서 분석기가 "ACTIVE"를 소문자 토큰 "active"로 저장했어요. 그런데 term 쿼리는 검색어를 분석하지 않고 그대로 "ACTIVE"와 같은 토큰을 찾아요. 맞는 것이 없으니 0건이에요.

    매핑은 처음에 정한다

    추측이 틀려도 이미 정해진 필드의 타입은 바꿀 수 없어요. 재색인해야 해요. 그리고 판매자가 자유롭게 넣는 상품 속성(JSON)을 그대로 넣으면 키마다 필드가 생겨서 필드 수가 끝없이 늘고, 클러스터 상태가 비대해져요. 운영 인덱스는 매핑을 명시하고 자동 추측을 제한해요.

    점수를 매길 것과 걸러낼 것

    쿼리에는 두 문맥이 있어요. 질의 문맥은 "얼마나 잘 맞는가"를 보고 점수를 계산해요. 필터 문맥은 "맞는가 아닌가"만 보고 점수를 계산하지 않으며, 결과가 캐시돼요. bool 쿼리로 조합하는데, 상품명 검색어는 must(점수에 반영)에, 판매 중 여부·카테고리·가격대는 filter에 넣어요. 쿼리 종류도 구분해요. match는 검색어를 분석해서 찾으니 text 필드에, term은 분석 없이 그대로 찾으니 keyword 필드에 써요.

    문서는 펼쳐서 넣는다

    검색 엔진에는 조인이 사실상 없어요. 검색에 필요한 정보를 상품 문서 하나에 펼쳐 넣어요. 브랜드 이름, 카테고리 이름, 판매자 등급을 상품 문서에 함께 넣는 식이에요. 대가는 브랜드 이름이 바뀌면 그 브랜드의 모든 상품을 다시 색인해야 한다는 거예요. 그리고 옵션 목록 같은 객체 배열은 기본적으로 필드별로 납작하게 색인돼서 원소 사이의 짝이 사라져요. "빨강-S, 파랑-L" 옵션이 있는 상품이 "빨강이면서 L인 옵션" 검색에 걸려요. 원소를 각각 따로 다루려면 nested 타입이 필요해요.

    백엔드에서는 term 쿼리를 text 필드에 쓰면 거의 항상 결과가 없어요. 반대로 상태 코드 같은 값을 text로 두면 정렬과 집계가 안 돼요. 필드를 추가할 때마다 세 가지를 물으세요. 이 필드로 단어 검색을 하는가(text), 정확히 같은 값을 찾거나 정렬·집계를 하는가(keyword), 둘 다인가(다중 필드).
    시니어 심화 검색창의 입력을 그대로 쿼리로 만들 때 가장 위험한 것은 비싼 쿼리를 사용자가 고를 수 있게 되는 것이에요. 그리고 검색 엔진을 원본 저장소로 쓰면 돌이킬 수 없는 일이 생겨요.

    상황

    상품 검색 API가 검색어를 query_string 쿼리에 그대로 넣었어요. 고급 검색 문법(AND, OR, 와일드카드)을 지원하려는 의도였어요. 어느 날 누군가 *북* 같은 검색어를 반복해서 보내자 검색 클러스터의 CPU가 100%가 됐고, 모든 검색이 타임아웃 났어요.

    깨지는 과정

    1. 역색인은 토큰 사전이 정렬돼 있어서 "북으로 시작하는 토큰"은 빠르게 찾아요.
    2. 앞에 와일드카드가 붙은 *북은 "북으로 끝나는 토큰"이라 정렬이 도움이 안 돼요. 토큰 사전 전체를 훑어야 해요. 수백만 개의 토큰을 요청 하나가 훑어요.
    3. 정규식 쿼리, 퍼지 쿼리, 아주 긴 OR 조건도 비슷하게 비싸요.
    4. query_string은 사용자 입력의 문법을 해석해서 이런 쿼리를 만들어요. 우연이든 고의든, 검색창 하나로 클러스터를 멈출 수 있어요. 문법 오류가 있는 입력은 에러를 내기도 해요.

    해결책

    • 사용자 입력에는 안전한 쿼리를 써요. 일반 검색창은 match나 multi_match처럼 입력을 문법으로 해석하지 않는 쿼리로 만들어요. 고급 문법이 꼭 필요하면 simple_query_string으로 허용할 연산자를 제한해요.
    • 비싼 쿼리를 설정으로 막아요. Elasticsearch는 search.allow_expensive_queries: false로 앞 와일드카드, 정규식 같은 비싼 쿼리를 클러스터 전체에서 거부할 수 있어요.
    • 필요한 기능은 색인 구조로 풀어요. 중간 일치가 정말 필요하면 n-gram 필드나 와일드카드 전용 필드 타입으로 색인해서, 쿼리 시점에 사전을 훑지 않게 해요(1장 시니어).
    • 입력 길이와 요청 빈도를 제한해요. 검색어 길이 상한과 사용자별 검색 빈도 제한을 둬요.

    검색 엔진을 원본으로 쓰지 않기

    검색 엔진은 트랜잭션이 없고, 매핑을 바꾸려면 재색인이 필요하고, 분산 환경에서 확인된 쓰기를 잃을 가능성이 관계형 DB보다 커요. 상품의 원본은 DB에 두고, 검색 인덱스는 언제든 원본에서 다시 만들 수 있는 사본으로 다뤄요(6장). 저장 비용도 신경 써요. 원문 전체(_source)가 기본으로 저장되니, 검색에만 쓰고 응답에는 안 쓰는 큰 필드는 저장에서 빼고, 정렬이나 집계에 안 쓰는 필드는 그 용도의 자료구조(doc values)를 꺼서 디스크를 줄여요.

    운영에서 알아채는 법

    • 검색 슬로우 로그(index.search.slowlog)를 켜서 느린 쿼리의 원문을 남겨요. 와일드카드나 정규식이 보이면 입력 처리 경로를 확인해요.
    • 사용자별 검색 요청 수와 검색 CPU 시간을 보면, 소수의 사용자가 비싼 쿼리를 반복하는 패턴이 보여요.
    핵심 정리
    • text = 분석해서 단어 검색, keyword = 그대로 일치·정렬·집계
    • 매핑은 처음에 명시. 정해진 타입은 못 바꿈(재색인)
    • 점수가 필요 없는 조건은 filter. 문서는 펼쳐 넣고, 객체 배열의 짝은 nested
    셀프 체크
    1. status 필드에 "ACTIVE"를 넣고 term 쿼리로 "ACTIVE"를 찾았는데 결과가 없습니다. 가능한 원인을 설명하세요.
    답 보기

    status 필드가 text 타입으로 매핑됐을 가능성이 커요. 매핑을 명시하지 않으면 문자열은 text로 추측돼요. text 필드는 색인할 때 분석기를 거치므로 "ACTIVE"가 소문자 토큰 "active"로 저장돼요. term 쿼리는 검색어를 분석하지 않고 그대로 "ACTIVE"와 같은 토큰을 찾으니 맞는 것이 없어요. 해결은 이 필드를 keyword로 매핑하는 거예요. 값 전체가 바뀌지 않고 토큰 하나로 저장돼 정확한 일치, 정렬, 집계가 모두 돼요. 타입을 바꾸려면 재색인이 필요해요.

    6장 운영 — 동기화, 재색인, 용량

    원본 DB와 검색 인덱스를 맞춰 두는 일

    문제: 품절 상품이 검색에 계속 나온다

    상품이 품절되면 애플리케이션이 DB의 상태를 바꾸고, 이어서 검색 엔진에 색인 요청을 보내요. 그런데 고객센터에 "검색에서는 판매 중인데 들어가면 품절"이라는 문의가 꾸준히 들어와요. 확인해 보니 DB에서는 품절인데 검색 인덱스에는 판매 중으로 남아 있는 상품이 수백 개였어요.

    두 곳에 쓰면 반드시 어긋난다

    원본은 DB에 있고 검색 인덱스는 그 사본이에요. 둘을 맞추는 방법이 검색 운영의 중심이에요. 위의 방식처럼 애플리케이션이 DB와 검색 엔진에 각각 쓰는 것을 이중 쓰기라고 하는데, 두 가지 이유로 반드시 어긋나요.

    첫째, 한쪽만 성공할 수 있어요. DB 커밋은 됐는데 검색 엔진 요청이 타임아웃 나면 DB에만 반영돼요. 둘째, 순서가 뒤바뀔 수 있어요. 품절 처리와 재입고 처리가 거의 동시에 일어나면, DB에는 "품절 → 재입고" 순서로 반영됐는데 검색 엔진에는 "재입고 → 품절" 순서로 도착해서 마지막 상태가 반대가 될 수 있어요.

    변경 로그를 따라간다

    더 견고한 방법은 DB의 변경 로그를 순서대로 읽어 색인하는 거예요(변경 데이터 캡처, CDC). DB가 커밋한 순서 그대로 따라가니 순서가 뒤바뀌지 않고, 색인이 잠깐 실패해도 그 위치부터 다시 읽으면 돼요. 구성 요소가 늘어나는 대신 가장 믿을 만해요. 이중 쓰기를 유지해야 한다면 둘을 주기적으로 대조해 어긋난 것을 찾아 고치는 작업을 함께 둬요.

    어느 방식이든 순서 문제를 막는 장치가 있어요. 원본의 버전 번호나 갱신 시각을 외부 버전으로 함께 보내면, 검색 엔진이 지금보다 낮은 버전의 쓰기를 거부해요. 늦게 도착한 옛 변경이 새 상태를 덮어쓰지 못해요.

    무중단 재색인: 별칭으로 바꿔 낀다

    분석기나 매핑을 바꾸려면 새 인덱스를 만들어 전부 다시 넣어야 해요(1장, 5장). 서비스를 멈추지 않고 하는 방법이 별칭이에요.

    애플리케이션은 인덱스 이름이 아니라 별칭(products)으로 검색해요. 새 설정으로 새 인덱스(products_v2)를 만들고, 원본에서 전부 색인하면서 그동안 들어오는 변경도 새 인덱스에 반영되게 해요. 문서 수와 표본 검색 결과를 옛 인덱스와 비교해 검증한 뒤, 별칭을 새 인덱스로 한 번에 바꿔요. 문제가 생기면 별칭만 되돌리면 돼요. 며칠 지켜보고 옛 인덱스를 지워요.

    용량과 안정성

    Lucene은 운영체제의 파일 캐시에 크게 기대요. 그래서 JVM 힙을 메모리 전부로 잡으면 오히려 느려져요. 힙은 메모리의 절반 이하로 두고 나머지를 운영체제에 남겨요. 디스크 사용률이 일정 수준을 넘으면 그 노드에 샤드를 더 배치하지 않고, 더 넘으면 인덱스가 읽기 전용이 돼요. 병합과 재색인은 잠깐 디스크를 더 쓰니 여유를 넉넉히 둬요. 클러스터 상태가 녹색이면 모든 샤드가 배치된 것, 노랑이면 일부 레플리카만 없는 것, 빨강이면 일부 프라이머리가 없어서 그 데이터는 검색되지 않는 거예요.

    백엔드에서는 검색 엔진의 장애가 서비스 전체 장애가 되지 않게 하세요. 검색 호출에 타임아웃과 서킷 브레이커를 걸고, 색인 실패가 DB 쓰기 트랜잭션을 롤백시키지 않게 떼어 놓아요. 그리고 "인덱스를 처음부터 다시 만드는 데 얼마나 걸리는가"를 실제로 재 두세요. 매핑 변경, 분석기 변경, 불일치 복구가 전부 이 절차를 쓰기 때문에, 이것이 느리면 검색 개선 전체가 느려져요.
    핵심 정리
    • 이중 쓰기는 부분 실패와 순서 뒤바뀜으로 반드시 어긋남. CDC 또는 주기적 대조, 외부 버전으로 순서 보장
    • 별칭 + 새 인덱스 + 검증 + 한 번에 전환으로 무중단 재색인
    • 힙은 메모리 절반 이하, 디스크 여유, 검색 장애를 서비스에서 격리
    셀프 체크
    1. 애플리케이션이 DB에 저장한 뒤 검색 엔진에 색인하는 이중 쓰기 방식에서 두 저장소가 어긋나는 경우를 두 가지 말해보세요.
    답 보기

    첫째, 부분 실패예요. DB 저장은 성공했는데 검색 엔진 색인이 네트워크 오류나 타임아웃으로 실패하면 DB에만 반영돼요. 색인 실패로 DB를 되돌리려 해도 이미 커밋된 뒤일 수 있어요. 둘째, 순서 뒤바뀜이에요. 같은 상품을 두 요청이 거의 동시에 고치면, DB에는 A 다음 B 순서로 반영됐는데 검색 엔진에는 B 다음 A 순서로 도착할 수 있어요. 그러면 DB의 마지막 값은 B인데 검색 인덱스에는 A가 남아요. 변경 로그를 순서대로 따라가는 방식이나 버전 번호로 낮은 버전의 쓰기를 거부하는 방식으로 막아요.

    실습

    실습 과제

    단일 노드 Elasticsearch나 OpenSearch를 컨테이너로 띄워서 해 보세요.

    • 1장 상품명 몇 개로 역색인을 직접 구현(단어 → 상품 ID 목록, 교집합 검색). _analyze로 표준 분석기와 한국어 형태소 분석기의 토큰 비교
    • 2장 같은 검색어의 결과를 explain으로 열어 점수의 구성 확인. 상품명 필드에 가중치를 주고 순위 변화 관찰
    • 3장 색인 직후 검색과 ID 조회의 결과 비교. 리프레시 간격을 바꿔 가며 대량 색인 속도 측정
    • 4장 샤드 5개 인덱스에서 깊은 페이지를 요청해 응답 시간 측정. search_after로 바꿔 비교
    • 5장 같은 문자열 필드를 text와 keyword로 매핑해 match와 term의 결과 비교. 옵션 배열의 교차 매칭을 재현하고 nested로 해결
    • 6장 별칭으로 분석기를 바꾼 새 인덱스에 무중단 전환. 이중 쓰기 중 색인을 일부러 실패시켜 불일치를 만들고 대조 스크립트로 찾기
