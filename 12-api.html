    API 설계

    기준 교재: API Design Patterns(JJ Geewax) + Google API 설계 가이드(AIP) · 2~3주

    API는 한번 공개하면 고치기 어려운 약속이에요. 내부 구현은 언제든 바꿀 수 있지만 API는 그것을 쓰는 클라이언트가 전부 따라와야 바뀌어요. 이 챕터는 나중에 바꾸지 않아도 되는 API를 처음에 어떻게 설계하는지를 다뤄요.

    HTTP 자체(메서드, 캐시, 상태 코드의 의미)는 네트워크 챕터에서 다뤘어요. 시간이 없으면 2장(에러 모델), 3장(페이징), 4장(호환성)을 먼저 읽으세요.

    1장 리소스 모델링

    동사가 아니라 명사부터 정한다

    좋은 API의 성질

    • 예측 가능: 한 부분을 배우면 나머지를 짐작할 수 있다. 일관성이 가장 중요해요.
    • 단순: 흔한 일은 쉽게, 드문 일은 가능하게.
    • 표현력: 클라이언트가 하려는 일을 우회 없이 표현할 수 있다.

    리소스 지향 설계

    먼저 무엇이 있는지(리소스)를 정하고, 그 위에 적은 수의 표준 동작을 올려요.

    동작HTTP예
    목록GET 컬렉션GET /orders
    조회GET 항목GET /orders/42
    생성POST 컬렉션POST /orders
    부분 수정PATCH 항목PATCH /orders/42
    전체 교체PUT 항목PUT /orders/42
    삭제DELETE 항목DELETE /orders/42

    계층과 관계

    /users/7/orders처럼 중첩하는 것은 자식이 부모 없이는 존재할 수 없을 때만 써요. 깊은 중첩은 URL을 길게 하고 리소스를 옮기기 어렵게 해요. 독립적으로 존재하는 리소스는 최상위에 두고 필터로 찾아요(/orders?userId=7).

    표준 동작에 안 맞는 것

    "주문 취소", "비밀번호 재설정"처럼 단순한 필드 수정이 아닌 동작은 두 가지 방법이 있어요.

    • 사용자 정의 동작: POST /orders/42:cancel 또는 POST /orders/42/cancel.
    • 동작을 리소스로: POST /orders/42/cancellations. 취소 사유, 시각 같은 기록이 필요하면 이쪽이 자연스러워요.

    PATCH로 status를 바꾸게 하는 것은 피해요. 상태 전이의 규칙과 부수 효과가 "필드 수정" 뒤에 숨어요.

    백엔드에서는 이름 규칙을 처음에 정하고 문서로 남기세요. 컬렉션은 복수형, 필드는 한 가지 표기법(camelCase 또는 snake_case), 시각은 타임존이 포함된 ISO 8601, 금액은 통화와 함께 정수 최소 단위나 문자열로요. 엔드포인트마다 다르면 클라이언트는 매번 문서를 찾아봐야 해요. DB 테이블 구조를 그대로 리소스로 노출하지 마세요. 스키마를 바꿀 때마다 API가 깨져요.
    시니어 심화
    • 식별자 설계: 리소스 ID는 한번 발급하면 바꿀 수 없어요. 내부 자동 증가 값을 그대로 쓰면 건수가 노출되고 나중에 저장소를 나눌 때 충돌해요. 불투명한 문자열로 내보내고, 타입을 알 수 있는 접두사(ord_)를 붙이면 로그와 지원 업무에서 읽기 쉬워요.
    • 기본값은 약속이에요. 정렬 순서, 페이지 크기, 생략한 필드의 값은 문서에 없어도 클라이언트가 의존하게 돼요. 기본값을 바꾸는 것은 호환성을 깨는 변경이에요.
    • 응답 최상위는 객체로 감싸요. 배열을 그대로 반환하면 나중에 페이징 정보나 메타데이터를 추가할 자리가 없어요.
    핵심 정리
    • 일관성이 가장 중요. 리소스(명사) + 적은 수의 표준 동작
    • 중첩은 소유 관계일 때만. 나머지는 최상위 + 필터
    • 상태 전이는 사용자 정의 동작이나 별도 리소스로
    셀프 체크
    1. 주문 취소를 PATCH /orders/42 {"status":"CANCELLED"} 로 설계할 때의 문제점은 무엇인가요?
    답 보기

    취소는 단순한 필드 변경이 아니라 규칙과 부수 효과가 있는 업무 동작이에요. 이미 배송된 주문은 취소할 수 없고, 취소하면 환불과 재고 복구가 따라와요. PATCH로 열어 두면 클라이언트가 어떤 상태값이든 넣을 수 있는 것처럼 보이고, 서버는 허용되는 전이를 일일이 막아야 해요. 취소 사유 같은 추가 입력을 받을 자리도 애매해요. 별도의 취소 동작으로 만들면 의도가 드러나고, 입력과 권한, 검증을 그 동작에 맞게 정의할 수 있어요.

    2장 요청·응답과 에러 모델

    실패했을 때 클라이언트가 무엇을 해야 하는지 알려준다

    상태 코드는 대분류

    코드의미클라이언트가 할 일
    400요청 형식이나 값이 잘못됨요청을 고친다. 재시도 무의미
    401인증 안 됨로그인 또는 토큰 갱신
    403인증은 됐으나 권한 없음재시도 무의미
    404리소스 없음재시도 무의미
    409현재 상태와 충돌최신 상태를 읽고 다시 판단
    422형식은 맞지만 업무 규칙 위반입력을 고친다
    429요청 한도 초과기다렸다 재시도
    500서버 오류멱등한 요청이면 재시도
    503일시적으로 처리 불가기다렸다 재시도

    4xx는 클라이언트가 고쳐야 하는 것, 5xx는 서버 쪽 문제예요. 이 구분이 재시도 여부를 정하므로 섞으면 안 돼요. 입력 오류에 500을 내면 클라이언트가 의미 없는 재시도를 반복해요.

    에러 본문

    상태 코드만으로는 부족해요. 일관된 구조의 본문을 줘요.

    {
        "error": {
          "code": "INSUFFICIENT_STOCK",
          "message": "재고가 부족합니다.",
          "details": [{ "field": "items[0].quantity", "reason": "요청 5, 재고 2" }],
          "requestId": "req_8f3a"
        }
      }
    • code: 프로그램이 분기하는 기준. 한번 정하면 바꾸지 않아요.
    • message: 사람이 읽는 설명. 바뀔 수 있으니 클라이언트가 문자열 비교를 하면 안 돼요.
    • details: 어느 필드가 왜 틀렸는지. 검증 오류는 전부 한 번에 알려줘요.
    • requestId: 문의가 왔을 때 로그를 찾는 열쇠.

    항상 200에 에러를 담지 않는다

    본문에 "success": false를 넣고 상태 코드는 200으로 주면, 프록시, 모니터링, 클라이언트 라이브러리의 재시도 로직이 전부 성공으로 봐요.

    백엔드에서는 에러 응답에 내부 정보를 싣지 마세요. 스택 트레이스, SQL, 내부 호스트 이름, 프레임워크 기본 에러 페이지가 그대로 나가는 경우가 많아요. 전역 예외 처리기에서 정해진 구조로 바꾸고, 자세한 내용은 요청 ID와 함께 서버 로그에만 남겨요. 그리고 요청 ID는 성공 응답에도 헤더로 넣어 주세요.
    시니어 심화
    • 에러 코드는 API의 일부예요. 클라이언트가 코드로 분기하므로 코드를 없애거나 의미를 바꾸면 호환성이 깨져요. 코드 목록을 문서화하고, 클라이언트는 모르는 코드를 만나면 상태 코드의 대분류로 처리하게 안내해요.
    • 재시도 가능 여부를 명시하면 클라이언트 구현이 단순해져요. 429와 503에는 Retry-After를 줘요. 없으면 클라이언트들이 제각각의 간격으로, 대개 너무 빨리 재시도해요.
    • 부분 성공이 가능한 일괄 요청은 설계가 어려워요. 전체를 원자적으로 처리해 하나라도 실패하면 전부 실패시키거나, 항목별 결과를 본문에 담아요. 후자를 택하면 최상위 상태 코드가 무엇을 뜻하는지 정해야 해요.
    핵심 정리
    • 4xx = 클라이언트가 고칠 것, 5xx = 서버 문제. 재시도 판단의 기준
    • 에러 본문: 기계용 code + 사람용 message + 필드별 details + 요청 ID
    • 에러를 200으로 감싸지 않음. 내부 정보 노출 금지
    셀프 체크
    1. 입력 검증 실패에 500을 반환하면 어떤 문제가 생기나요?
    답 보기

    500은 서버 쪽 문제라는 뜻이라, 클라이언트와 중간 계층은 같은 요청을 다시 보내면 성공할 수 있다고 봐요. 재시도 로직이 있는 클라이언트는 고쳐지지 않을 요청을 반복해서 보내 부하만 늘려요. 서버 쪽에서는 에러율 지표와 알람이 실제 장애가 아닌 사용자 입력 오류로 울려서, 진짜 서버 오류를 구분하기 어려워져요. 입력 오류는 4xx로 내보내 "요청을 고쳐야 한다"를 알려야 해요.

    3장 페이징, 필터, 정렬

    목록은 언젠가 반드시 커진다

    처음부터 페이징을 넣는다

    목록 API를 페이징 없이 공개하면, 데이터가 늘어난 뒤에 페이징을 추가하는 것은 호환성을 깨는 변경이에요. 지금 항목이 10개여도 처음부터 넣어요.

    오프셋 방식

    GET /orders?offset=40&limit=20
    • 단순하고 "N페이지로 이동"이 돼요.
    • 뒤로 갈수록 느려요. DB가 앞의 행을 전부 읽고 버려요.
    • 조회 중에 데이터가 추가·삭제되면 항목이 중복되거나 빠져요.

    커서 방식

    GET /orders?limit=20
      → { "items": [...], "nextPageToken": "eyJjcmVhdGVkQXQiOi..." }

      GET /orders?limit=20&pageToken=eyJjcmVhdGVkQXQiOi...
    • 토큰은 "마지막으로 본 항목의 위치"를 담아요. 서버는 그 뒤부터 읽어요.
    • 깊이에 상관없이 빠르고, 중간에 데이터가 바뀌어도 건너뛰거나 겹치지 않아요.
    • 임의 페이지로 이동은 안 돼요.

    토큰은 클라이언트에게 불투명한 문자열로 줘요. 내부 구조를 알게 하면 클라이언트가 직접 만들어 쓰고, 서버는 구현을 바꿀 수 없게 돼요.

    규칙

    • 페이지 크기에 상한을 둬요. 클라이언트가 100만을 요청해도 서버가 정한 최대치까지만 줘요.
    • 마지막 페이지는 다음 토큰이 없는 것으로 알려요. 항목 수가 요청보다 적다고 마지막인 것은 아니에요.
    • 정렬 기준에는 유일한 키를 마지막에 넣어요. 같은 시각의 항목이 여러 개면 순서가 불안정해요.

    필터와 정렬

    단순한 경우는 필드별 쿼리 파라미터(?status=PAID&userId=7)로 충분해요. 허용하는 필터와 정렬 필드는 명시적으로 제한해요. 아무 필드로나 필터·정렬할 수 있게 열면 인덱스 없는 쿼리가 들어와요.

    백엔드에서는 전체 건수(totalCount)를 응답에 넣기로 하면, 페이지마다 조건에 맞는 전체를 세는 쿼리가 따로 나가요. 큰 테이블에서는 목록 조회보다 이 쿼리가 더 비싸요. 꼭 필요한 화면인지 확인하고, 필요하면 별도 엔드포인트나 근사치로 분리하세요.
    시니어 심화
    • 토큰에 조건을 묶어요. 토큰을 받은 뒤 필터나 정렬을 바꿔서 요청하면 결과가 뒤죽박죽이 돼요. 토큰 안에 필터와 정렬 조건(또는 그 해시)을 넣고, 다르면 거부해요. 변조를 막으려면 서명하거나 암호화해요.
    • 토큰의 수명을 정하세요. 며칠 전 토큰으로 이어서 요청했을 때의 동작(만료 에러인지, 그 위치부터 계속인지)을 문서화해요.
    • 일관된 스냅샷이 필요한 내보내기(전체 다운로드)는 페이징 API로 풀지 말고 별도의 비동기 내보내기 작업으로 만들어요. 페이징은 조회 중 변경을 막아 주지 않아요.
    핵심 정리
    • 목록 API는 처음부터 페이징. 나중에 추가하면 호환성 파괴
    • 커서 방식: 깊이와 무관하게 빠르고 중간 변경에 안정적. 토큰은 불투명
    • 페이지 크기 상한, 유일 키로 정렬 고정, 필터·정렬 필드 제한
    셀프 체크
    1. 오프셋 페이징으로 최신순 목록을 넘기는 도중 새 항목이 맨 앞에 추가되면 어떤 일이 생기나요?
    답 보기

    1페이지(0~19번)를 본 뒤 새 항목 하나가 맨 앞에 추가되면 기존 항목들이 한 칸씩 뒤로 밀려요. 2페이지를 offset=20으로 요청하면 방금 1페이지의 마지막에서 본 항목이 20번 자리에 와 있어서 다시 나와요. 반대로 항목이 삭제되면 한 칸씩 당겨져서 하나를 건너뛰어요. 커서 방식은 "마지막으로 본 항목 다음부터"를 조건으로 읽기 때문에 앞쪽에 무엇이 추가되든 영향을 받지 않아요.

    4장 버저닝과 호환성

    무엇이 깨는 변경인지 아는 것이 먼저

    호환되는 변경과 깨는 변경

    안전한 변경깨는 변경
    응답에 필드 추가응답 필드 삭제, 이름 변경, 타입 변경
    선택적 요청 파라미터 추가필수 요청 파라미터 추가
    새 엔드포인트 추가엔드포인트 삭제, URL 변경
    -검증을 더 엄격하게 변경
    -기본값, 기본 정렬, 에러 코드 변경
    -enum에 값 추가(클라이언트가 전체를 나열해 처리한다면)

    안전한 변경이 안전하려면 클라이언트가 모르는 필드를 무시해야 해요. 이 규칙을 문서에 명시하세요.

    버전을 표현하는 방법

    • URL 경로: /v1/orders. 눈에 잘 보이고 라우팅하기 쉬워요. 가장 흔해요.
    • 헤더: 요청 헤더로 버전 지정. URL이 안 바뀌지만 눈에 안 띄고 테스트가 번거로워요.
    • 날짜 기반: 계정이나 요청마다 날짜 버전을 고정하고, 서버가 그 날짜의 동작으로 응답을 변환해요. 깨는 변경을 작은 단위로 내보낼 수 있지만 서버 구현이 복잡해요.

    버전을 올리지 않는 것이 목표

    새 버전은 옛 버전과 함께 오랫동안 유지해야 해요. 그래서 좋은 버저닝 전략의 핵심은 버전을 올릴 일을 줄이는 것이에요. 가능한 한 추가만으로 진화시켜요.

    없애는 절차

    1. 대체 수단을 먼저 제공한다.
    2. 폐기 예정임을 문서와 응답 헤더(Deprecation, Sunset)로 알린다.
    3. 누가 아직 쓰는지 측정한다. 클라이언트별 호출량을 봐요.
    4. 남은 사용자에게 직접 연락한다.
    5. 기한이 지나고 사용량이 충분히 줄면 제거한다.
    백엔드에서는 내부 서비스 간 API도 같아요. 호출하는 팀이 배포하기 전에는 옛 형식을 유지해야 하므로, 필드 이름을 바꾸려면 "새 필드 추가 → 호출자가 새 필드로 이전 → 옛 필드 제거"를 세 번의 배포로 나눠요. 요청 DTO에 모르는 필드가 오면 실패하게 설정해 두면, 상대가 필드를 추가하는 것만으로 우리가 깨져요.
    시니어 심화
    • 계약을 자동으로 검사하세요. API 명세(OpenAPI, proto)를 저장소에 두고, 변경할 때 이전 버전과 비교해 깨는 변경을 CI에서 막아요. 사람의 리뷰는 타입 변경이나 필수 여부 변경을 놓쳐요.
    • 안정성 등급을 둬요. 실험 단계 기능을 안정 버전과 같은 약속으로 내보내면 영원히 유지해야 해요. 미리보기로 표시한 것은 바뀔 수 있음을 명시해요.
    • 버전의 단위를 정하세요. API 전체를 한 번에 올리면 클라이언트는 필요 없는 변경까지 한꺼번에 이전해야 해요. 리소스별로 버전을 달리하면 이전은 쉬워지지만 조합이 늘어요.
    핵심 정리
    • 추가는 안전, 삭제·변경·엄격화·기본값 변경은 깨는 변경
    • 클라이언트는 모르는 필드를 무시해야 함
    • 버전을 올릴 일을 줄이는 것이 목표. 제거는 사용량을 재고 나서
    셀프 체크
    1. 요청 검증을 더 엄격하게 바꾸는 것이 왜 호환성을 깨는 변경인가요?
    답 보기

    어제까지 성공하던 요청이 오늘부터 실패하기 때문이에요. 예를 들어 이름 필드에 길이 제한을 새로 넣거나 지금까지 무시하던 잘못된 형식을 거부하기 시작하면, 그런 값을 보내고 있던 기존 클라이언트는 코드를 바꾸지 않았는데도 에러를 받아요. API의 계약은 문서에 적힌 것만이 아니라 실제로 받아들이던 입력 전체예요. 검증을 강화해야 하면 먼저 위반하는 요청을 기록만 하면서 누가 영향을 받는지 파악하고, 알린 뒤에 거부로 바꿔요.

    2부 심화

    5장 멱등성, 동시성 제어, 장기 실행 작업

    네트워크가 끊겨도 안전한 API

    요청 중복 제거

    클라이언트가 응답을 못 받았을 때, 요청이 처리됐는지 안 됐는지 알 수 없어요. 재시도하면 두 번 실행될 수 있어요. 생성과 결제 같은 요청은 본래 멱등하지 않아요.

    해결: 클라이언트가 요청마다 고유한 키를 만들어 보내요(Idempotency-Key 헤더). 서버는 키별로 결과를 저장해 두고, 같은 키가 다시 오면 다시 실행하지 않고 저장된 응답을 돌려줘요.

    • 같은 키인데 본문이 다르면 에러로 거부해요.
    • 처음 요청이 아직 처리 중일 때 같은 키가 오면 충돌(409)로 응답해요.
    • 키의 보존 기간을 정하고 문서화해요.

    동시 수정 충돌

    두 클라이언트가 같은 리소스를 읽고 각자 수정해서 보내면 나중 것이 앞의 것을 덮어써요(갱신 손실).

    리소스에 버전을 나타내는 값(ETag)을 주고, 수정 요청에 "내가 읽은 버전"을 함께 보내게 해요.

    GET /orders/42          → ETag: "v7"
      PATCH /orders/42
      If-Match: "v7"          → 현재도 v7이면 수정, 아니면 412

    412를 받은 클라이언트는 최신 상태를 다시 읽고 판단해요. 서버 쪽 구현은 DB의 버전 컬럼을 조건으로 한 갱신이에요.

    부분 수정의 의미

    PATCH에서 "필드를 안 보냄"과 "필드를 null로 보냄"을 구분해야 해요. 앞은 "건드리지 않음", 뒤는 "지움"이에요. 이 구분이 없으면 클라이언트가 모르는 필드를 실수로 지워요. 수정할 필드 목록을 명시하는 방식(필드 마스크)도 있어요.

    장기 실행 작업

    수 초 이상 걸리는 작업(대량 내보내기, 영상 변환)을 요청-응답 한 번에 처리하면 타임아웃과 연결 끊김에 취약해요.

    1. 요청을 받으면 작업 리소스를 만들고 즉시 202 Accepted와 작업의 위치를 반환한다.
    2. 클라이언트는 작업 리소스를 조회해 상태(대기, 진행 중, 완료, 실패)와 진행률을 확인한다.
    3. 완료되면 결과 또는 결과의 위치가 작업 리소스에 담긴다.

    폴링 대신 완료 시 서버가 알려 주는 방식(웹훅)을 더할 수 있어요. 그래도 조회 API는 있어야 해요. 알림은 유실될 수 있어요.

    백엔드에서는 멱등성 키 구현의 핵심은 "키 선점"과 "업무 처리"의 관계예요. 키를 유니크 제약으로 먼저 삽입해 선점하고, 업무 처리와 결과 저장을 같은 트랜잭션으로 묶어요. 외부 호출이 끼면 한 트랜잭션으로 묶을 수 없으니, 처리 중 상태로 남은 키를 정리하는 절차가 필요해요. 웹훅을 보낼 때는 수신 측이 위조를 구분할 수 있게 서명하고, 실패하면 간격을 늘려 가며 재시도하세요.
    핵심 정리
    • 멱등성 키: 같은 키의 재요청은 저장된 결과를 반환
    • 동시 수정: ETag + If-Match, 불일치 시 412
    • 오래 걸리는 작업은 202 + 작업 리소스 조회
    셀프 체크
    1. 클라이언트가 결제 요청을 보냈는데 타임아웃이 났습니다. 멱등성 키가 있을 때와 없을 때 클라이언트가 할 수 있는 일은 어떻게 다른가요?
    답 보기

    타임아웃은 요청이 처리됐는지 알려주지 않아요. 멱등성 키가 없으면 재시도는 이중 결제의 위험이 있고, 재시도하지 않으면 결제가 안 됐을 위험이 있어요. 클라이언트는 별도의 조회 수단으로 결과를 확인하는 수밖에 없는데, 방금 만든 결제의 ID를 받지 못했으니 조회도 어려워요. 멱등성 키가 있으면 같은 키로 그냥 다시 보내면 돼요. 처음 요청이 처리됐다면 서버가 그 결과를 돌려주고, 안 됐다면 이번에 처리돼요. 어느 쪽이든 결제는 한 번만 일어나요.

    6장 REST, gRPC, GraphQL, 이벤트

    스타일마다 잘하는 일이 다르다

    비교

    REST (JSON/HTTP)gRPCGraphQL
    모델리소스 + 표준 동작원격 함수 호출클라이언트가 필요한 모양을 질의
    계약OpenAPI(선택)proto(필수), 코드 생성스키마(필수), 타입 시스템
    전송HTTP/1.1 이상, 텍스트HTTP/2, 바이너리, 스트리밍보통 HTTP POST 하나
    캐시HTTP 캐시를 그대로 활용직접 구현직접 구현(URL이 하나라 HTTP 캐시가 어려움)
    강점범용, 도구가 풍부, 디버깅 쉬움성능, 엄격한 타입, 양방향 스트림화면마다 다른 데이터 요구에 유연
    약점필요 이상·이하로 가져오기 쉬움브라우저에서 직접 쓰기 어려움서버 쪽 성능 통제가 어려움

    gRPC가 맞는 곳

    내부 서비스 간 통신이에요. 양쪽 모두 통제할 수 있고, 호출이 잦아 직렬화 비용과 연결 효율이 중요하고, 계약에서 코드를 생성해 타입을 맞추고 싶을 때. 호출에 기한(deadline)을 실어 전파하는 기능이 기본으로 있어요.

    GraphQL이 맞는 곳

    여러 종류의 클라이언트(웹, 모바일)가 같은 데이터를 서로 다른 모양으로 필요로 할 때예요. 클라이언트가 필요한 필드만 한 번의 요청으로 가져와요. 대가는 서버에 있어요.

    • N+1: 필드마다 따로 조회하는 구조라, 목록의 각 항목에서 하위 필드를 조회하면 쿼리가 폭증해요. 요청 안에서 같은 종류의 조회를 모아 한 번에 실행하는 장치(데이터 로더)가 필수예요.
    • 비용 통제: 클라이언트가 깊고 넓은 질의를 보낼 수 있어요. 질의의 깊이와 복잡도에 상한을 둬야 해요.
    • 권한 검사를 필드 수준에서 해야 해요.

    이벤트 기반(비동기) API

    요청-응답이 아니라 "일어난 일"을 발행하고 관심 있는 쪽이 구독해요. 호출하는 쪽이 받는 쪽을 몰라도 되고, 받는 쪽이 죽어 있어도 발행은 성공해요. 대신 결과를 바로 알 수 없고, 흐름을 따라가기 어려우며, 순서와 중복을 받는 쪽이 다뤄야 해요.

    고르는 기준

    • 외부에 공개하는 API: REST가 기본. 받는 쪽의 기술을 가정하지 않아요.
    • 내부 서비스 간 동기 호출: gRPC 또는 REST.
    • 화면 조합이 다양한 프론트엔드용: GraphQL 또는 화면 전용 백엔드(BFF).
    • 결과를 기다릴 필요가 없는 통지: 이벤트.
    백엔드에서는 한 시스템에서 여러 스타일을 섞는 것이 정상이에요. 외부에는 REST, 내부 호출은 gRPC, 서비스 간 상태 전파는 이벤트. 문제는 스타일 선택보다 "동기 호출이어야 하는 것을 이벤트로" 또는 그 반대로 고르는 거예요. 호출자가 결과에 따라 다음 행동을 정해야 하면 동기 호출이에요. 결과와 무관하게 자기 일을 끝낼 수 있으면 이벤트예요.
    핵심 정리
    • REST = 범용·캐시·디버깅, gRPC = 내부 통신의 성능과 타입, GraphQL = 클라이언트별 유연한 조회
    • GraphQL은 N+1과 질의 비용 통제가 서버의 숙제
    • 결과에 따라 다음 행동이 달라지면 동기, 아니면 이벤트
    셀프 체크
    1. GraphQL에서 N+1 문제가 REST보다 쉽게 생기는 이유를 설명하세요.
    답 보기

    GraphQL 서버는 질의의 각 필드를 그 필드 전용 함수가 따로 해결하는 구조예요. 주문 목록과 각 주문의 고객을 요청하면, 주문 목록을 한 번 조회한 뒤 주문마다 고객 필드의 함수가 따로 호출돼 고객을 조회해요. 주문이 100개면 고객 조회가 100번이에요. REST에서는 엔드포인트 하나가 무엇을 반환할지 서버 개발자가 정하므로 조인이나 일괄 조회를 미리 넣을 수 있지만, GraphQL에서는 어떤 필드 조합이 올지 미리 알 수 없어요. 그래서 한 요청 안에서 같은 종류의 조회를 모아 한 번의 일괄 조회로 바꿔 주는 장치가 필요해요.

    3부 운영

    7장 문서, 한도, 관측

    쓰는 사람의 경험까지가 API다

    명세가 원본

    API 명세(OpenAPI, proto)를 코드와 같은 저장소에 두고 변경을 같이 리뷰해요. 명세에서 문서, 클라이언트 코드, 서버의 요청 검증, 테스트용 가짜 서버를 만들 수 있어요. 문서를 따로 손으로 쓰면 반드시 실제와 어긋나요.

    명세를 먼저 쓰고 구현하는 순서(설계 우선)의 장점은, 쓰는 쪽이 구현 전에 검토할 수 있고 프론트엔드와 백엔드가 병렬로 일할 수 있다는 거예요.

    좋은 문서의 요소

    • 복사해서 바로 실행되는 예제 요청과 응답.
    • 인증 방법, 에러 코드 목록, 페이징 규칙, 한도.
    • 필드마다 필수 여부, 형식, 제약, 기본값.
    • 변경 이력.

    요청 한도

    한도는 서버를 보호하고 사용자 간 공정성을 지켜요.

    • 한도를 넘으면 429와 Retry-After.
    • 남은 한도를 응답 헤더로 알려주면 클라이언트가 스스로 조절할 수 있어요.
    • 기준을 정해요: 사용자별, API 키별, IP별. 엔드포인트의 비용에 따라 다르게.

    입력의 상한

    본문 크기, 배열 길이, 문자열 길이, 페이지 크기, 중첩 깊이. 상한이 없는 입력은 언젠가 서버를 죽이는 요청이 돼요. 일괄 처리 API에는 한 번에 받을 항목 수의 상한을 문서화해요.

    관측

    • 모든 요청에 요청 ID를 부여하고 응답 헤더로 돌려줘요.
    • 엔드포인트별·클라이언트별로 호출량, 에러율, 지연을 봐요.
    • 누가 무엇을 쓰는지를 알아야 폐기와 변경을 계획할 수 있어요. 클라이언트 식별자(API 키, User-Agent, 버전)를 기록해요.
    백엔드에서는 헬스 체크나 내부 관리용 엔드포인트가 공개 API와 같은 경로와 포트로 나가지 않게 하세요. 그리고 응답을 압축하고 필요한 필드만 고를 수 있게 하는 것이 모바일 클라이언트에게는 큰 차이를 만들어요. 로그에 요청 본문을 남길 때는 비밀번호, 토큰, 개인정보 필드를 가려요.
    시니어 심화
    • 한도는 비용 기준이 더 공정해요. 요청 수로만 세면 가벼운 조회 1000번과 무거운 검색 1000번이 같게 취급돼요. 요청마다 비용 점수를 매겨 점수로 한도를 걸어요.
    • 클라이언트 라이브러리를 제공하면 재시도, 백오프, 페이징, 인증 갱신을 올바르게 구현할 기회를 서버 쪽이 가져요. 라이브러리가 없으면 클라이언트마다 재시도를 제각각 구현하고 대개 지터 없이 구현해요.
    • 사용 패턴에서 설계 결함이 보여요. 한 클라이언트가 같은 엔드포인트를 연달아 수십 번 부른다면 일괄 조회 API가 빠진 거예요. 자주 함께 불리는 엔드포인트는 합칠 후보예요.
    핵심 정리
    • 명세를 저장소에 두고 문서·검증·클라이언트를 거기서 생성
    • 429 + Retry-After, 모든 입력에 상한
    • 요청 ID와 클라이언트 식별로 누가 무엇을 쓰는지 파악

    답 보기

    코드를 바꿀 때 문서를 같이 고치는 것을 잊거나 미루게 되고, 시간이 지나면 문서와 실제 동작이 어긋나요. 쓰는 사람은 문서를 믿을 수 없게 되어 직접 호출해 보거나 질문하게 돼요. 대안은 기계가 읽을 수 있는 명세를 코드와 같은 저장소에 두고 그것을 원본으로 삼는 거예요. 명세에서 문서를 생성하고, 서버가 명세대로 응답하는지 테스트로 검증하고, 명세 변경이 깨는 변경인지 자동으로 검사하면 문서와 구현이 구조적으로 어긋나지 않아요.

    실습

    실습 과제

    작은 주문 API 하나를 만들면서 전부 적용해 보세요.

    • 1장 주문·주문 항목·결제 리소스를 설계하고 OpenAPI 명세를 먼저 작성. 취소를 사용자 정의 동작으로 추가
    • 2장 전역 예외 처리기로 에러 응답 구조 통일. 검증 오류를 필드별로 한 번에 반환
    • 3장 같은 목록을 오프셋과 커서로 각각 구현하고, 조회 중 삽입이 일어날 때의 결과와 깊은 페이지의 속도 비교
    • 4장 명세의 이전 버전과 현재 버전을 비교해 깨는 변경을 찾는 검사를 CI에 추가
    • 5장 생성 API에 멱등성 키를 구현하고 같은 요청을 동시에 10번 보내 한 건만 생기는지 확인. ETag와 If-Match로 갱신 손실 방지
    • 5장 내보내기를 202 + 작업 리소스로 구현하고 진행률 조회 추가
    • 7장 사용자별 요청 한도를 걸고 429와 Retry-After, 남은 한도 헤더 반환
