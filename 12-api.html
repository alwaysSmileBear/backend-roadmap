    API 설계

    기준 교재: API Design Patterns(JJ Geewax) + Google API 설계 가이드(AIP) · 2~3주

    API는 한번 공개하면 고치기 어려운 약속이에요. 내부 구현은 언제든 바꿀 수 있지만, API는 그것을 쓰는 모든 클라이언트가 따라와야 바뀌어요. 이 챕터는 나중에 바꾸지 않아도 되는 API를 처음에 어떻게 설계하는지를 봐요.

    예시는 쇼핑몰의 주문 API예요. 우리 모바일 앱과 웹이 쓰고, 입점 업체와 제휴사도 이 API로 주문을 조회해요. 모바일 앱은 사용자가 업데이트하기 전까지 옛 버전이 계속 돌기 때문에, 한번 나간 API를 고치기가 특히 어려워요. HTTP 자체(메서드, 캐시, 상태 코드의 의미)는 네트워크 챕터에서 다뤘어요. 시간이 없으면 2장(에러), 3장(페이징), 4장(호환성)을 먼저 읽으세요.

    1장 리소스 모델링

    동사가 아니라 명사부터 정한다

    문제: 엔드포인트마다 규칙이 다르다

    주문 API를 몇 년 동안 기능이 생길 때마다 만들었더니 이렇게 됐어요. /getOrderList, /order/detail?id=, /updateOrderStatus, /orders/cancelOrder. 제휴사 개발자는 기능 하나를 쓸 때마다 문서를 처음부터 찾아봐야 하고, 우리 팀 신규 입사자도 다음 엔드포인트 이름을 짐작할 수 없어요.

    좋은 API는 짐작할 수 있다

    좋은 API의 첫째 성질은 예측 가능성이에요. 한 부분을 배우면 나머지를 짐작할 수 있어야 해요. 그러려면 무엇이 있는지(리소스)를 먼저 정하고, 그 위에 적은 수의 표준 동작을 똑같이 올려요.

    동작HTTP주문 API
    목록GET 컬렉션GET /orders
    조회GET 항목GET /orders/1042
    생성POST 컬렉션POST /orders
    부분 수정PATCH 항목PATCH /orders/1042
    삭제DELETE 항목DELETE /orders/1042

    이 규칙을 알면 배송지 리소스가 생겼을 때 GET /addresses/7을 문서 없이 짐작할 수 있어요.

    계층은 소유 관계일 때만

    주문 항목은 주문 없이 존재할 수 없으니 /orders/1042/items처럼 주문 아래에 둬요. 반면 주문을 회원 아래(/members/7/orders)에만 두면, 관리자가 전체 주문을 날짜로 찾거나 제휴사가 자기 상품의 주문을 찾을 길이 없어요. 독립적으로 존재하는 리소스는 최상위에 두고 필터로 찾아요(/orders?memberId=7).

    표준 동작에 맞지 않는 것

    "주문 취소"는 어떻게 할까요? PATCH /orders/1042에 {"status": "CANCELLED"}를 보내게 하고 싶어지는데, 그러면 문제가 생겨요. 취소는 필드 하나를 바꾸는 일이 아니라 규칙(배송 전에만 가능)과 부수 효과(환불, 재고 복구)가 따르는 업무 동작이에요. PATCH로 열면 클라이언트가 아무 상태값이나 넣을 수 있는 것처럼 보이고, 취소 사유 같은 입력을 받을 자리도 애매해요.

    이런 동작은 별도의 동작으로 만들어요. POST /orders/1042:cancel처럼 리소스 뒤에 동작 이름을 붙이거나, 취소 자체를 리소스로 보고 POST /orders/1042/cancellations로 만들어요. 취소 사유와 시각, 처리자 같은 기록이 필요하면 뒤쪽이 자연스러워요.

    백엔드에서는 이름 규칙을 처음에 정해서 문서로 남기세요. 컬렉션은 복수형, 필드 표기법은 하나로(camelCase 또는 snake_case), 시각은 타임존이 포함된 ISO 8601, 금액은 통화와 함께 정수 최소 단위나 문자열로요. 그리고 DB 테이블을 그대로 리소스로 내보내지 마세요. JPA 엔티티를 응답으로 바로 내보내면 테이블에 컬럼을 하나 추가하거나 이름을 바꿀 때마다 API가 깨져요. 응답은 별도의 DTO로 만들어요.
    시니어 심화 리소스 설계에서 가장 되돌리기 어려운 것이 식별자예요. 한번 발급한 번호는 제휴사 시스템에, 고객의 문자 메시지에, 고객센터 기록에 남아서 바꿀 수 없어요.

    상황

    주문 API는 DB의 자동 증가 값을 주문 번호로 그대로 내보냈어요. 몇 년 뒤 세 가지 문제가 한꺼번에 왔어요. 경쟁사가 주문 번호 증가량으로 우리 일 매출을 추정한 자료가 돌았고, 보안 점검에서 번호를 바꿔 가며 남의 주문을 조회하는 시도가 발견됐고, 주문 DB를 둘로 나누려 하니 번호가 겹칠 문제가 생겼어요.

    깨지는 과정

    1. 정보가 새요. 오늘 아침 번호와 저녁 번호의 차이가 하루 주문 수예요. 누구나 주문 두 번으로 계산할 수 있어요.
    2. 추측하기 쉬워요. 번호가 연속이니 하나씩 바꿔 가며 조회해 볼 수 있어요. 권한 검사가 있으면 막히지만, 한 곳이라도 빠지면 바로 뚫려요(보안 챕터 5장 시니어).
    3. 저장소에 묶여요. 번호가 DB 하나의 자동 증가 값이라서, DB를 나누거나 다른 저장소로 옮기면 번호가 겹쳐요. 이미 외부에 나간 번호라 바꿀 수도 없어요.

    해결책

    • 외부 식별자와 내부 키를 분리해요. DB 안에서는 자동 증가 값을 PK로 써도 좋아요(조인과 인덱스에 유리해요). 외부에는 별도의 불투명한 문자열을 내보내요. 무작위 값이나 시각 순서가 있는 UUIDv7, ULID 같은 형식을 써요.
    • 타입 접두사를 붙여요. ord_8fK2…, cus_3Lp9…처럼 앞에 타입을 붙이면 로그, 고객 문의, 디버깅에서 무엇의 ID인지 바로 보여요. 주문 ID 자리에 회원 ID를 잘못 넣은 버그도 서버가 접두사로 즉시 거부할 수 있어요.
    • 사람이 읽는 번호는 따로 둬요. 고객센터에서 불러 줘야 하는 주문 번호(20251121-0042)가 필요하면, 식별자와 별개의 표시용 필드로 둬요.
    • 응답의 최상위는 객체로 감싸요. 목록 API가 배열을 그대로 반환하면([...]), 나중에 페이징 정보나 경고 메시지를 추가할 자리가 없어요. 처음부터 {"data": [...], "next_cursor": ...}로 감싸요. 이것도 한 번 내보내면 바꾸기 어려운 결정이에요.

    대가: 외부 ID와 내부 키를 매핑하는 컬럼과 인덱스가 하나 더 필요해요. 공개 API를 처음 설계할 때 넣으면 작은 비용이지만, 나중에 바꾸려면 모든 클라이언트를 옮겨야 하는 큰 비용이에요.

    설계 리뷰에서 확인하는 법

    • 새 API의 응답에 DB의 자동 증가 값이 그대로 나가는지 확인해요.
    • "이 식별자를 5년 뒤에도 그대로 유지할 수 있나?"를 물어요. 저장소, 샤딩, 서비스 분리 계획과 함께 생각해요.
    핵심 정리
    • 일관성이 가장 중요. 리소스(명사) + 적은 수의 표준 동작
    • 계층은 소유 관계일 때만. 독립적인 리소스는 최상위 + 필터
    • 규칙과 부수 효과가 있는 업무 동작은 별도 동작이나 별도 리소스로
    셀프 체크
    1. 주문 취소를 PATCH /orders/1042 {"status":"CANCELLED"} 로 설계할 때의 문제점은 무엇인가요?
    답 보기

    취소는 필드 하나를 바꾸는 일이 아니라 규칙과 부수 효과가 있는 업무 동작이에요. 이미 배송된 주문은 취소할 수 없고, 취소하면 환불과 재고 복구가 따라와요. PATCH로 열어 두면 클라이언트가 어떤 상태값이든 넣을 수 있는 것처럼 보이고, 서버는 허용되는 상태 변화를 하나하나 막아야 해요. 취소 사유 같은 추가 입력을 받을 자리도 애매해요. 별도의 취소 동작으로 만들면 의도가 드러나고, 입력과 권한, 검증을 그 동작에 맞게 정할 수 있어요.

    2장 요청·응답과 에러 모델

    실패했을 때 클라이언트가 무엇을 해야 하는지 알려준다

    문제: 앱이 같은 실패를 계속 재시도한다

    주문 생성 API에서 재고가 부족하면 500 에러를 내고 있었어요. 모바일 앱의 HTTP 라이브러리는 500을 받으면 서버 문제로 보고 자동으로 세 번 재시도해요. 재고가 없는 상품을 주문한 사용자 한 명이 요청 네 번을 만들고, 행사 때는 이 재시도가 서버 부하의 상당 부분을 차지했어요. 게다가 에러율 알람이 계속 울려서 진짜 서버 장애와 구분되지 않았어요.

    상태 코드는 "다음에 무엇을 할지"를 알려준다

    상태 코드의 가장 중요한 구분은 4xx는 클라이언트가 요청을 고쳐야 하는 것, 5xx는 서버 쪽 문제라는 거예요. 이 구분이 재시도 여부를 정해요. 같은 요청을 다시 보내도 결과가 같을 실패에 5xx를 주면, 클라이언트와 중간 계층이 의미 없는 재시도를 반복해요.

    코드의미예
    400요청 형식이나 값이 잘못됨수량이 음수
    401 / 403인증 안 됨 / 권한 없음토큰 만료 / 남의 주문
    404리소스 없음없는 주문 번호
    409현재 상태와 충돌이미 배송된 주문의 취소
    422형식은 맞지만 업무 규칙 위반재고 부족, 쿠폰 조건 미달
    429요청 한도 초과초당 호출 수 초과
    500 / 503서버 오류 / 일시적으로 처리 불가예외, 배포 중

    본문으로 자세히 알려준다

    상태 코드만으로는 부족해요. 422만 받은 앱은 재고가 부족한 건지 쿠폰이 안 맞는 건지 알 수 없어요. 모든 에러를 같은 구조의 본문으로 줘요.

    {
        "error": {
          "code": "INSUFFICIENT_STOCK",
          "message": "재고가 부족합니다.",
          "details": [{ "field": "items[0].quantity", "reason": "요청 5개, 재고 2개" }],
          "requestId": "req_8f3a"
        }
      }

    code는 프로그램이 분기하는 기준이라 한번 정하면 바꾸지 않아요. 앱은 이 값을 보고 "재고 부족" 화면을 띄워요. message는 사람이 읽는 설명이라 문구가 바뀔 수 있으니, 클라이언트가 이 문자열을 비교하면 안 된다고 문서에 적어요. details는 어느 필드가 왜 틀렸는지 알려줘요. 입력 오류는 전부 한 번에 알려줘야 사용자가 하나 고치고 다시 보내는 일을 반복하지 않아요. requestId는 고객 문의가 왔을 때 서버 로그를 찾는 열쇠예요.

    그리고 에러를 200 응답에 "success": false로 감싸지 마세요. 프록시, 모니터링, 클라이언트 라이브러리의 재시도 로직이 전부 성공으로 봐요.

    백엔드에서는 에러 응답에 내부 정보를 싣지 마세요. 스택 트레이스, SQL, 내부 서버 이름, 프레임워크의 기본 에러 페이지가 그대로 나가는 경우가 많아요. 전역 예외 처리기(@RestControllerAdvice)에서 정해진 구조로 바꾸고, 자세한 내용은 요청 ID와 함께 서버 로그에만 남겨요. 요청 ID는 성공 응답에도 헤더로 넣어 주세요.
    시니어 심화 에러 코드는 API 계약의 일부예요. 필드 이름만큼 바꾸기 어렵고, 재시도 안내가 없으면 클라이언트가 장애를 키워요.

    상황 1: 코드 이름을 바꿨더니 앱이 깨짐

    앱은 에러 응답의 INSUFFICIENT_STOCK을 보고 "재고가 부족해요" 화면을 띄워요. 서버 팀이 이름을 정리하면서 OUT_OF_STOCK으로 바꿨어요. 업데이트하지 않은 옛 앱은 모르는 코드를 받아 "알 수 없는 오류" 화면을 띄웠고, 재고 부족 상품을 주문하려던 고객들의 문의가 쏟아졌어요.

    • 에러 코드 목록을 문서로 관리해요. 새 코드 추가는 허용하되, 기존 코드는 지우거나 의미를 바꾸지 않아요. 바꾸는 것은 필드를 지우는 것과 같은 호환성 파괴예요.
    • 모르는 코드의 처리 규칙을 정해 알려요. "모르는 코드를 받으면 상태 코드의 대분류(4xx는 사용자 입력 문제, 5xx는 서버 문제)로 처리하라"고 클라이언트 가이드에 적어요. 그래야 새 코드를 추가해도 옛 앱이 깨지지 않아요.
    • 표준 형식을 써요. RFC 9457(Problem Details)의 type, title, status, detail 구조를 쓰면 클라이언트 라이브러리와 도구가 바로 이해해요.

    상황 2: 재시도 안내가 없어서 서버가 다시 넘어짐

    결제 API가 과부하로 30초 동안 503을 돌려줬어요. 앱은 실패하면 즉시 재시도하도록 만들어져 있었어요. 30초 뒤 서버가 회복하려는 순간, 그동안 쌓인 재시도가 동시에 몰려 서버가 다시 넘어졌어요.

    1. 클라이언트는 언제 다시 시도해야 하는지 몰라서 제각각, 대개 너무 빨리 재시도해요.
    2. 모든 클라이언트가 같은 장애를 같은 순간에 겪었으니 재시도도 같은 순간에 몰려요.
    3. 회복 중인 서버는 평소보다 많은 요청을 받아 다시 넘어져요.
    • 429와 503에는 Retry-After를 붙여요. "몇 초 뒤에 다시"를 서버가 알려줘요. 서버가 상황에 따라 값을 조절하면 회복 속도에 맞춰 재시도를 나눌 수 있어요.
    • 재시도 가능 여부를 명시해요. 에러 응답에 "다시 시도하면 성공할 수 있는가"를 담으면(예: retryable: true) 클라이언트 구현이 단순해져요. 400 같은 입력 오류는 몇 번을 해도 같아요.
    • 클라이언트에는 지수 백오프와 지터를 요구해요. 가이드에 적고, 가능하면 공식 클라이언트 라이브러리로 제공해요(7장 시니어).

    운영에서 알아채는 법

    • 에러 코드별, 앱 버전별 응답 수를 지표로 남겨요. 배포 후 특정 앱 버전에서 "알 수 없는 오류" 화면 이벤트가 튄다면 계약이 깨진 거예요.
    • 장애 회복 시점에 요청 수가 평소보다 크게 튀는지 봐요. 튄다면 재시도가 몰리고 있어요.
    핵심 정리
    • 4xx = 클라이언트가 고칠 것, 5xx = 서버 문제. 재시도 판단의 기준
    • 에러 본문: 기계용 code + 사람용 message + 필드별 details + 요청 ID
    • 에러를 200으로 감싸지 않음. 에러 코드도 계약이라 바꾸지 않음
    셀프 체크
    1. 입력 검증 실패에 500을 반환하면 어떤 문제가 생기나요?
    답 보기

    500은 서버 쪽 문제라는 뜻이라, 클라이언트와 중간 계층은 같은 요청을 다시 보내면 성공할 수 있다고 봐요. 재시도 로직이 있는 클라이언트는 고쳐지지 않을 요청을 반복해서 보내 부하만 늘려요. 서버 쪽에서는 에러율 지표와 알람이 실제 장애가 아닌 사용자 입력 오류로 울려서 진짜 서버 오류를 구분하기 어려워져요. 입력 오류는 4xx로 내보내 "요청을 고쳐야 한다"를 알려야 해요.

    3장 페이징, 필터, 정렬

    목록은 언젠가 반드시 커진다

    문제: 주문 목록을 넘기다 같은 주문이 두 번 보인다

    판매자 앱의 주문 목록은 최신순으로 20개씩 보여주고, "다음"을 누르면 ?offset=20&limit=20을 요청해요. 그런데 판매자들이 "목록을 넘기다 보면 같은 주문이 또 나오고, 가끔은 주문 하나가 빠진다"고 해요. 주문이 많은 판매자일수록 자주 그래요. 그리고 100페이지쯤 넘기면 응답이 몇 초씩 걸려요.

    오프셋 방식이 흔들리는 이유

    오프셋은 "앞에서부터 몇 개를 건너뛰라"는 뜻이에요. 판매자가 1페이지를 보는 동안 새 주문이 하나 들어오면, 기존 주문들이 전부 한 칸씩 뒤로 밀려요.

    2페이지를 offset=20으로 요청하면, 방금 1페이지 마지막에서 본 주문이 21번째 자리로 밀려나 있어서 다시 나와요. 반대로 주문이 취소되어 목록에서 빠지면 한 칸씩 당겨져서 하나를 건너뛰어요. 그리고 DB는 OFFSET 2000을 처리하려면 앞의 2,000개를 실제로 읽고 버려야 해서, 뒤로 갈수록 느려져요(데이터베이스 챕터 9장).

    커서 방식: 어디까지 봤는지를 기억한다

    GET /orders?limit=20
      → { "items": [...], "nextPageToken": "eyJjcmVhdGVkQXQiOi..." }

      GET /orders?limit=20&pageToken=eyJjcmVhdGVkQXQiOi...

    응답에 "마지막으로 본 항목의 위치"를 담은 토큰을 주고, 다음 요청은 그 토큰을 보내요. 서버는 "그 주문보다 오래된 것 20개"를 조회해요. 앞에 새 주문이 몇 개 들어오든 상관없으니 겹치거나 빠지지 않고, DB는 인덱스에서 그 위치를 바로 찾으니 몇 페이지째든 빨라요. 대신 "57페이지로 바로 이동"은 안 돼요.

    토큰은 클라이언트에게 내용을 알 수 없는 문자열로 줘요. 안의 구조(createdAt과 id)를 알려주면 클라이언트가 직접 만들어 쓰고, 서버는 나중에 구현을 바꿀 수 없게 돼요.

    지켜야 할 규칙

    페이지 크기에 상한을 둬요. 클라이언트가 limit=100000을 보내도 서버가 정한 최대치까지만 줘요. 마지막 페이지는 다음 토큰이 없는 것으로 알려요. 항목 수가 요청보다 적다고 마지막인 것은 아니에요. 정렬 기준의 마지막에는 유일한 값(ID)을 넣어요. 같은 시각에 들어온 주문이 여러 개면 순서가 매번 달라질 수 있어요. 그리고 필터와 정렬에 쓸 수 있는 필드를 명시적으로 제한해요. 아무 필드로나 정렬할 수 있게 열면 인덱스 없는 쿼리가 들어와요.

    무엇보다 목록 API는 처음부터 페이징을 넣어야 해요. 지금은 항목이 10개뿐이어도요. 페이징 없이 공개한 뒤에 추가하면, 전체를 한 번에 받는다고 가정한 옛 클라이언트가 깨져요.

    백엔드에서는 전체 건수(totalCount)를 응답에 넣기로 하면, 페이지마다 조건에 맞는 전체를 세는 쿼리가 따로 나가요. 주문이 수백만 건인 판매자에게는 목록 조회보다 이 쿼리가 더 비싸요. 꼭 필요한 화면인지 확인하고, 필요하면 별도 API나 "1,000+" 같은 근사치로 분리하세요.
    시니어 심화 커서 페이징은 편하지만, 토큰이 무엇에 대한 위치인지를 함께 지키지 않으면 이상한 결과가 나와요. 그리고 페이징으로 풀면 안 되는 요구도 있어요.

    상황 1: 필터를 바꿨더니 결과가 뒤죽박죽

    판매자 앱에서 "결제 완료" 필터로 주문 목록을 3페이지까지 넘긴 뒤 필터를 "배송 중"으로 바꿨어요. 앱이 기존 커서 토큰을 그대로 붙여 요청했고, 결과는 엉뚱한 중간 지점부터 시작했어요. 판매자는 배송 중 주문 일부가 없다고 문의했어요.

    1. 커서 토큰은 "결제 완료 주문을 최신순으로 정렬했을 때 이 위치 다음"이라는 뜻이에요.
    2. 그 위치를 "배송 중" 필터에 적용하면 의미가 없는 위치에서 시작해요. 앞쪽의 배송 중 주문은 건너뛰어요.
    3. 서버는 토큰의 위치만 보고 필터가 바뀐 것을 몰라요.
    • 토큰 안에 만들 때의 필터와 정렬 조건을 넣어요. 조건 전체나 그 해시를 넣고, 다른 조건으로 요청이 오면 400으로 거부해요. 클라이언트는 조건이 바뀌면 처음부터 다시 요청하게 돼요.
    • 토큰을 서명하거나 암호화해요. 클라이언트가 토큰 안의 위치를 고쳐서 보내면 예상치 못한 쿼리가 실행될 수 있어요. 서버가 서명을 확인해서 조작된 토큰을 거부해요.
    • 토큰의 수명을 문서에 적어요. 사흘 전 토큰으로 이어서 요청했을 때 만료 에러를 줄지, 그 위치부터 계속할지 정해요. 정하지 않으면 클라이언트는 지금의 동작에 의존하게 돼요.

    상황 2: 엑셀 내려받기를 페이징으로 만듦

    "주문 전체 엑셀 내려받기"를 앱이 주문 목록 API를 끝까지 넘기며 모아서 만들었어요. 주문 2만 건을 받는 데 3분이 걸렸고, 그 사이 상태가 바뀐 주문이 섞였어요. 같은 주문이 "결제 완료"와 "배송 중"으로 두 번 들어간 파일도 나왔어요.

    • 페이징은 넘기는 동안의 변경을 막아 주지 않아요. 각 페이지는 요청한 순간의 데이터라서, 페이지 사이에 바뀐 데이터가 섞여요.
    • 한 시점의 일관된 전체가 필요하면 내보내기 작업으로 만들어요. "내보내기 요청"을 받으면 작업을 만들어 202로 응답하고, 서버가 한 트랜잭션(또는 한 스냅샷)에서 파일을 만든 뒤, 클라이언트는 작업 상태를 조회해 완료되면 내려받아요(5장의 장기 실행 작업).

    운영에서 알아채는 법

    • 토큰 조건 불일치로 거부한 건수를 지표로 남겨요. 많다면 클라이언트가 필터 변경 때 토큰을 초기화하지 않는 버그가 있어요.
    • 한 클라이언트가 같은 목록 API를 끝까지 연속으로 넘기는 패턴이 반복되면, 내보내기 기능이 필요하다는 신호예요.
    핵심 정리
    • 목록 API는 처음부터 페이징. 나중에 추가하면 호환성 파괴
    • 오프셋은 중간 변경에 흔들리고 깊을수록 느림. 커서는 둘 다 해결, 토큰은 불투명하게
    • 페이지 크기 상한, 유일한 키로 정렬 고정, 필터·정렬 필드 제한
    셀프 체크
    1. 오프셋 페이징으로 최신순 목록을 넘기는 도중 새 항목이 맨 앞에 추가되면 어떤 일이 생기나요?
    답 보기

    1페이지(0~19번)를 본 뒤 새 항목 하나가 맨 앞에 추가되면 기존 항목들이 한 칸씩 뒤로 밀려요. 2페이지를 offset=20으로 요청하면 방금 1페이지 마지막에서 본 항목이 20번 자리로 와 있어서 다시 나와요. 반대로 항목이 삭제되면 한 칸씩 당겨져서 하나를 건너뛰어요. 커서 방식은 "마지막으로 본 항목 다음부터"를 조건으로 읽기 때문에 앞쪽에 무엇이 추가되든 영향을 받지 않아요.

    4장 버저닝과 호환성

    필드 이름 하나 바꿨을 뿐인데 옛 앱이 멈췄다

    문제: 이름을 고쳤더니 앱이 죽었다

    주문 응답의 deliveryAddr라는 필드 이름이 마음에 안 들어서 shippingAddress로 바꿨어요. 웹은 같이 배포해서 문제가 없었는데, 다음 날 아침 옛 버전 앱을 쓰는 사용자들의 주문 상세 화면이 전부 비어 있었어요. 앱은 사용자가 업데이트하기 전까지 몇 달이고 옛 버전이 돌아요.

    무엇이 깨는 변경인가

    호환성을 지키려면 먼저 무엇이 안전하고 무엇이 깨는지 알아야 해요.

    안전한 변경깨는 변경
    응답에 필드 추가응답 필드 삭제, 이름 변경, 타입 변경
    선택적 요청 파라미터 추가필수 요청 파라미터 추가
    새 엔드포인트 추가엔드포인트 삭제, 주소 변경
    새 에러 코드 추가(대분류는 유지)기존 에러 코드 변경, 검증을 더 엄격하게
    -기본값, 기본 정렬 순서 변경

    "추가는 안전하다"가 성립하려면 조건이 하나 있어요. 클라이언트가 모르는 필드를 무시해야 해요. 이 규칙을 문서에 명시하고, 우리 클라이언트들도 그렇게 만들어요.

    이름 변경은 "삭제 + 추가"예요. 옛 이름을 읽는 클라이언트에게는 필드가 사라진 거예요. 검증을 더 엄격하게 하는 것도 깨는 변경이에요. 어제까지 성공하던 요청이 오늘 실패하니까요.

    버전을 올리지 않고 바꾸는 방법

    필드 이름을 정말 바꾸고 싶다면 한 번에 하지 않아요. 먼저 새 이름의 필드를 추가해서 두 필드에 같은 값을 넣어요. 우리 웹과 앱을 새 필드를 쓰도록 바꾸고, 옛 필드를 누가 아직 쓰는지 측정해요. 옛 필드를 폐기 예정으로 문서와 응답 헤더(Deprecation, Sunset)로 알리고, 남은 사용자에게 직접 연락해요. 사용량이 충분히 줄고 약속한 기한이 지나면 그때 옛 필드를 제거해요.

    버전을 올려야 할 때

    추가만으로 해결할 수 없는 큰 변경이면 버전을 올려요. 주소에 버전을 넣는 방식(/v2/orders)이 눈에 잘 띄고 라우팅하기 쉬워서 가장 흔해요. 헤더로 버전을 고르는 방식은 주소가 안 바뀌지만 눈에 안 띄어요. 어느 쪽이든 새 버전은 옛 버전과 함께 오랫동안 유지해야 해요. 그래서 좋은 버전 전략의 핵심은 버전을 잘 올리는 것이 아니라 올릴 일을 줄이는 것이에요.

    백엔드에서는 서비스끼리 부르는 내부 API도 마찬가지예요. 호출하는 팀이 배포하기 전에는 옛 형식을 유지해야 해요. 그리고 우리가 클라이언트일 때를 조심하세요. Jackson이 모르는 필드를 만나면 실패하도록 설정되어 있으면(FAIL_ON_UNKNOWN_PROPERTIES), 상대가 필드를 추가하는 것만으로 우리가 깨져요. 받는 쪽은 관대하게, 보내는 쪽은 엄격하게예요.
    시니어 심화 사람이 리뷰로 호환성을 지키는 데는 한계가 있어요. 그래서 계약을 기계로 검사하고, 기능마다 얼마나 안정적인 약속인지를 명시해요.

    상황

    상품 API의 price 필드 타입을 integer에서 number로 바꾼 PR이 리뷰를 통과했어요. 소수점 가격을 지원하려는 의도였어요. 배포 다음 날, 가격을 정수로 파싱하던 제휴사 두 곳의 연동이 멈췄어요. 같은 달, 선택 필드였던 memo를 필수로 바꾼 PR도 아무도 눈치채지 못한 채 배포됐어요.

    왜 리뷰로는 놓치나

    1. 타입 변경, 선택에서 필수로의 변경, enum 값 제거는 코드 diff에서 한두 글자예요. 리뷰어는 로직에 집중하느라 계약의 변화를 놓쳐요.
    2. 무엇이 "깨는 변경"인지 판단하려면 모든 클라이언트를 알아야 하는데, 리뷰어는 모든 클라이언트를 알지 못해요.
    3. 문서에 적지 않은 동작(기본 정렬 순서, 기본 페이지 크기, 응답 필드의 순서)도 클라이언트는 지금 동작에 의존해요.

    해결책

    • 명세를 코드와 같은 저장소에 두고 CI에서 비교해요. OpenAPI 명세라면 oasdiff 같은 도구로, protobuf라면 buf breaking으로 이전 버전 명세와 비교해서 깨는 변경이면 빌드를 실패시켜요. 정말 깨야 한다면 명시적으로 허용하는 절차(라벨, 승인)를 거치게 해요.
    • 명세가 실제 동작과 같은지도 검사해요. 코드에서 명세를 생성하거나, 명세로 계약 테스트를 돌려서 문서와 실제가 어긋나지 않게 해요.
    • 기능마다 안정성 등급을 붙여요. "미리보기", "베타", "정식"처럼 등급을 문서와 응답 헤더에 표시해요. 실험 중인 기능을 정식과 같은 약속으로 내보내면 영원히 유지해야 해요. 미리보기는 바뀔 수 있다고 처음부터 명시하면, 써 보면서 설계를 고칠 여지가 생겨요.
    • 기본값도 약속으로 다뤄요. 정렬 순서와 페이지 크기를 문서에 적고, 바꿀 때는 깨는 변경과 같은 절차를 밟아요.
    • 폐기에는 일정을 붙여요. 없앨 필드나 엔드포인트에는 Deprecation과 Sunset 헤더로 날짜를 알리고, 그 기간 동안 누가 아직 쓰는지 사용량을 봐요.

    운영에서 알아채는 법

    • 폐기 예정 필드와 엔드포인트의 클라이언트별 사용량을 지표로 남겨요. 일정이 다가와도 쓰는 클라이언트가 있으면 직접 연락해요.
    • 배포 후 특정 클라이언트(API 키)의 에러율만 튀면 계약 변경을 의심해요.
    핵심 정리
    • 추가는 안전, 삭제·이름 변경·타입 변경·검증 강화·기본값 변경은 깨는 변경
    • 클라이언트는 모르는 필드를 무시. 이름 변경은 추가 → 이전 → 측정 → 공지 → 제거
    • 버전을 올릴 일을 줄이는 것이 목표. 명세 비교로 깨는 변경을 자동 검출
    셀프 체크
    1. 요청 검증을 더 엄격하게 바꾸는 것이 왜 호환성을 깨는 변경인가요?
    답 보기

    어제까지 성공하던 요청이 오늘부터 실패하기 때문이에요. 예를 들어 배송 메모에 길이 제한을 새로 넣으면, 긴 메모를 보내던 기존 클라이언트는 코드를 바꾸지 않았는데도 에러를 받아요. API의 계약은 문서에 적힌 것만이 아니라 실제로 받아들이던 입력 전체예요. 검증을 강화해야 한다면 먼저 위반하는 요청을 기록만 하면서 누가 영향을 받는지 파악하고, 알린 뒤에 거부로 바꿔요.

    5장 멱등성, 동시성 제어, 장기 실행 작업

    네트워크가 끊겨도 안전한 API

    문제: 주문 버튼을 한 번 눌렀는데 결제가 두 번

    지하철에서 주문 버튼을 눌렀는데 화면이 멈췄다가 "네트워크 오류"가 떴어요. 사용자는 다시 눌렀고, 다음 날 카드 결제가 두 건 찍혀 있었어요. 첫 요청은 사실 서버에 도착해서 주문과 결제까지 끝났는데, 응답이 돌아오는 길에 연결이 끊겼던 거예요.

    응답이 없으면 처리 여부를 알 수 없다

    클라이언트 입장에서 "응답을 못 받았다"는 두 가지 중 하나예요. 요청이 서버에 도착하지 않았거나, 도착해서 처리됐는데 응답만 사라졌거나. 둘을 구분할 방법이 없어요. 다시 보내지 않으면 주문이 안 됐을 수 있고, 다시 보내면 두 번 될 수 있어요. 조회는 여러 번 해도 결과가 같지만(멱등), 주문 생성은 아니에요.

    멱등성 키

    해결은 클라이언트가 주문 시도마다 고유한 키를 만들어 Idempotency-Key 헤더로 보내는 거예요. 같은 시도를 재전송할 때는 같은 키를 보내요. 서버는 키별로 처리 결과를 저장해 두고, 이미 본 키가 다시 오면 다시 처리하지 않고 저장된 응답을 그대로 돌려줘요. 클라이언트는 응답을 못 받으면 마음 놓고 같은 키로 재시도하면 돼요. 처음 요청이 처리됐다면 그 결과를, 안 됐다면 이번 처리 결과를 받아요. 어느 쪽이든 주문은 하나예요.

    세부 규칙이 몇 가지 있어요. 같은 키인데 요청 본문이 다르면(클라이언트 버그) 거부해요. 처음 요청이 아직 처리 중일 때 같은 키가 오면 충돌(409)로 응답해서 두 요청이 동시에 처리되지 않게 해요. 키를 며칠 동안 보관할지 정해서 문서에 적어요.

    동시 수정: 나중에 저장한 쪽이 앞의 변경을 지운다

    판매자 관리 화면에서 직원 두 명이 같은 주문을 열었어요. 한 명은 배송 메모를 고치고, 한 명은 송장 번호를 넣고 저장했어요. 둘 다 주문 전체를 보내는 방식이었다면, 나중에 저장한 쪽이 앞사람의 변경을 옛 값으로 덮어써요(갱신 손실).

    리소스에 버전을 나타내는 값(ETag)을 주고, 수정 요청에 "내가 읽은 버전"을 함께 보내게 해요.

    GET /orders/1042        → ETag: "v7"
      PATCH /orders/1042
      If-Match: "v7"          → 지금도 v7이면 수정, 아니면 412

    412를 받은 쪽은 최신 상태를 다시 읽고 판단해요. 서버 구현은 DB의 버전 컬럼을 조건으로 한 갱신이에요. 그리고 PATCH에서 "필드를 안 보냄"(건드리지 않음)과 "null로 보냄"(지움)을 구분해야 해요. 구분하지 않으면 클라이언트가 모르는 필드를 실수로 지워요.

    오래 걸리는 작업

    "최근 1년 주문 내보내기"처럼 수십 초 이상 걸리는 작업을 요청 한 번에 처리하면 타임아웃과 연결 끊김에 취약해요. 요청을 받으면 작업 리소스를 만들고 즉시 202 Accepted와 그 작업의 주소를 돌려줘요. 클라이언트는 작업 리소스를 조회해서 상태(대기, 진행 중, 완료, 실패)와 진행률을 확인하고, 완료되면 결과 파일의 위치를 받아요. 완료 시 알려 주는 웹훅을 더할 수 있지만 조회 API는 꼭 있어야 해요. 알림은 유실될 수 있으니까요.

    백엔드에서는 멱등성 키 구현의 핵심은 "키 선점"과 "업무 처리"의 관계예요. 키를 유니크 제약이 있는 테이블에 먼저 넣어 선점하고, 주문 저장과 결과 기록을 같은 트랜잭션으로 묶어요. 결제 대행사 호출처럼 외부 호출이 끼면 한 트랜잭션으로 묶을 수 없으니, "처리 중"으로 남은 키를 나중에 결제사 조회 API로 확인해 정리하는 절차가 필요해요(분산 시스템 챕터 부록 B).
    핵심 정리
    • 응답이 없으면 처리 여부를 알 수 없음. 멱등성 키로 재시도를 안전하게
    • 동시 수정은 ETag + If-Match, 불일치면 412. PATCH는 생략과 null을 구분
    • 오래 걸리는 작업은 202 + 작업 리소스 조회

    1. 클라이언트가 주문 요청을 보냈는데 타임아웃이 났습니다. 멱등성 키가 있을 때와 없을 때 클라이언트가 할 수 있는 일은 어떻게 다른가요?
    답 보기

    타임아웃은 요청이 처리됐는지 알려주지 않아요. 멱등성 키가 없으면 재시도는 이중 주문과 이중 결제의 위험이 있고, 재시도하지 않으면 주문이 안 됐을 위험이 있어요. 방금 만든 주문의 번호를 받지 못했으니 조회로 확인하기도 어려워요. 멱등성 키가 있으면 같은 키로 그냥 다시 보내면 돼요. 처음 요청이 처리됐다면 서버가 저장해 둔 결과를 돌려주고, 안 됐다면 이번에 처리돼요. 어느 쪽이든 주문은 한 번만 일어나요.

    6장 REST, gRPC, GraphQL, 이벤트

    스타일마다 잘하는 일이 다르다

    문제: 하나로 통일하자는 제안

    팀에서 "API 스타일을 하나로 통일하자"는 이야기가 나왔어요. 누구는 내부 서비스끼리 gRPC가 빠르니 전부 gRPC로 하자고 하고, 누구는 앱 화면마다 필요한 데이터가 달라 GraphQL이 낫다고 하고, 누구는 주문 이벤트는 Kafka로 보내고 있으니 이벤트로 통일하자고 해요. 하나를 고를 수 있을까요?

    각자 잘하는 일

    REST (JSON/HTTP)gRPCGraphQL
    모델리소스 + 표준 동작원격 함수 호출클라이언트가 필요한 모양을 질의
    계약OpenAPI(선택)proto(필수), 코드 생성스키마(필수), 타입 시스템
    전송텍스트, 어디서나 동작HTTP/2, 바이너리, 스트리밍보통 POST 하나
    캐시HTTP 캐시를 그대로 활용직접 구현직접 구현(주소가 하나라 어려움)
    강점범용, 도구가 많음, 디버깅 쉬움성능, 엄격한 타입, 양방향 스트림화면마다 다른 데이터 요구에 유연

    외부에 공개하는 API는 REST가 기본이에요. 제휴사가 어떤 언어와 도구를 쓰는지 가정하지 않아도 되고, 브라우저와 curl로 바로 확인할 수 있어요. 내부 서비스끼리의 동기 호출에는 gRPC가 잘 맞아요. 양쪽을 우리가 통제하고, 호출이 잦아 직렬화 비용과 연결 효율이 중요하고, 명세에서 코드를 생성해 타입을 맞출 수 있어요. 호출에 기한(deadline)을 실어 다음 서비스로 넘겨주는 기능도 기본으로 있어요.

    GraphQL의 대가

    GraphQL은 앱의 주문 상세 화면이 "주문 + 항목 + 각 항목의 상품 이름과 이미지 + 배송 상태"를 요청 한 번에 원하는 모양대로 가져오게 해 줘요. 클라이언트에게는 편하지만 대가는 서버가 내요.

    GraphQL 서버는 필드마다 그 값을 가져오는 함수를 따로 실행해요. 주문 20개를 조회하고 각 주문의 회원 필드를 요청하면, 회원 조회 함수가 20번 따로 불려요. 데이터베이스 챕터의 N+1이 그대로 생겨요. 한 요청 안에서 같은 종류의 조회를 모아 한 번에 실행하는 장치(데이터 로더)가 필수예요. 또 클라이언트가 깊고 넓은 질의를 마음대로 보낼 수 있으니, 질의의 깊이와 복잡도에 상한을 둬야 해요. 권한 검사도 엔드포인트가 아니라 필드 수준에서 해야 해요.

    이벤트: 결과를 기다리지 않는 통지

    주문이 생기면 알림, 정산, 추천 서비스가 각자 할 일이 있어요. 이것은 요청-응답이 아니라 "주문이 생겼다"는 사실을 발행하고 관심 있는 쪽이 받아 가는 이벤트가 맞아요(Kafka 챕터). 주문 서비스는 받는 쪽을 몰라도 되고, 받는 쪽이 죽어 있어도 주문은 성공해요. 대신 결과를 바로 알 수 없고, 흐름을 따라가기 어렵고, 순서와 중복을 받는 쪽이 다뤄야 해요.

    그래서 답은 하나로 통일하는 것이 아니라 섞어 쓰는 것이에요. 기준은 하나예요. 부르는 쪽이 결과를 보고 다음 행동을 정해야 하면 동기 호출(REST, gRPC), 결과와 무관하게 자기 일을 끝낼 수 있으면 이벤트예요. 결제 승인은 결과를 봐야 주문을 확정하니 동기 호출이고, 주문 확인 문자는 이벤트예요.

    백엔드에서는 스타일 선택보다 흔한 실수는 동기와 비동기를 잘못 고르는 것이에요. 결제 승인을 이벤트로 보내 놓고 응답 이벤트를 기다리는 코드는, 사실상 동기 호출을 더 복잡하고 느리게 구현한 거예요. 반대로 주문 확인 문자를 동기로 호출하면 문자 서비스가 느릴 때 주문까지 느려져요. "부르는 쪽이 결과를 기다려야 하는가"를 먼저 물으세요.
    핵심 정리
    • REST = 외부 공개·범용, gRPC = 내부 통신의 성능과 타입, GraphQL = 화면별 유연한 조회
    • GraphQL은 N+1(데이터 로더)과 질의 비용 상한이 서버의 숙제
    • 결과에 따라 다음 행동이 달라지면 동기, 아니면 이벤트

    1. GraphQL에서 N+1 문제가 REST보다 쉽게 생기는 이유를 설명하세요.

    GraphQL 서버는 질의의 각 필드를 그 필드 전용 함수가 따로 채우는 구조예요. 주문 목록과 각 주문의 회원을 요청하면, 주문 목록을 한 번 조회한 뒤 주문마다 회원 필드의 함수가 따로 불려 회원을 조회해요. 주문이 100개면 회원 조회가 100번이에요. REST에서는 엔드포인트 하나가 무엇을 반환할지 서버 개발자가 정하므로 조인이나 일괄 조회를 미리 넣을 수 있지만, GraphQL에서는 어떤 필드 조합이 올지 미리 알 수 없어요. 그래서 한 요청 안의 같은 종류 조회를 모아 한 번에 처리하는 장치가 필요해요.

    3부 운영

    7장 문서, 한도, 관측

    쓰는 사람의 경험까지가 API다

    문제: 문서와 실제가 다르다

    제휴사 개발자가 문의했어요. 문서에는 orderedAt 필드가 있다는데 실제 응답에는 orderDate가 온다고요. 6개월 전에 필드 이름을 바꾸면서 위키 문서를 고치는 것을 잊었던 거예요. 그 사이 다른 제휴사들은 문서를 믿지 않고 실제 응답을 보며 개발하고 있었어요.

    명세를 원본으로 삼는다

    문서를 코드와 따로 손으로 관리하면 반드시 어긋나요. 대신 기계가 읽을 수 있는 API 명세(OpenAPI, proto)를 코드와 같은 저장소에 두고, 그것을 원본으로 삼아요.

    명세 하나에서 여러 가지를 만들어요. 사람이 읽는 문서, 서버가 들어오는 요청을 검사하는 규칙, 제휴사가 쓸 클라이언트 코드, 프론트엔드가 개발할 때 쓰는 가짜 서버, 그리고 4장의 깨는 변경 검사예요. 서버가 실제로 명세대로 응답하는지는 테스트로 확인해요. 이렇게 하면 문서와 구현이 구조적으로 어긋날 수 없어요.

    명세를 구현보다 먼저 쓰는 방식(설계 우선)도 좋아요. 쓰는 쪽(앱 팀, 제휴사)이 구현 전에 검토할 수 있고, 프론트엔드와 백엔드가 가짜 서버를 두고 동시에 개발할 수 있어요.

    좋은 문서에 들어갈 것

    복사해서 그대로 실행되는 예제 요청과 응답이 가장 중요해요. 그다음은 인증 방법, 에러 코드 목록, 페이징 규칙, 요청 한도, 필드마다의 필수 여부·형식·제약·기본값, 그리고 변경 이력이에요.

    요청 한도와 입력 상한

    한도는 서버를 보호하고, 한 제휴사가 다른 제휴사의 몫까지 쓰지 않게 해요. 한도를 넘으면 429와 Retry-After를 주고, 남은 한도를 응답 헤더로 알려주면 클라이언트가 스스로 속도를 조절할 수 있어요. 기준은 API 키별, 사용자별, IP별로 정하고, 비싼 엔드포인트는 따로 낮게 잡아요.

    입력에도 상한을 둬요. 본문 크기, 배열 길이, 문자열 길이, 페이지 크기, JSON 중첩 깊이. 상한이 없는 입력은 언젠가 서버를 죽이는 요청이 돼요. 주문 일괄 조회 API에 ID를 몇 개까지 넣을 수 있는지 문서에 적어요.

    누가 무엇을 쓰는지 안다

    모든 요청에 요청 ID를 붙여 응답 헤더로 돌려주고, 엔드포인트별·클라이언트별로 호출 수, 에러율, 응답 시간을 봐요. 클라이언트 식별자(API 키, 앱 버전)를 기록해 두면 4장의 "옛 필드를 아직 누가 쓰는가"에 답할 수 있어요. 이것을 모르면 아무것도 지울 수 없어요.

    백엔드에서는 헬스 체크나 내부 관리용 엔드포인트가 공개 API와 같은 주소와 포트로 나가지 않게 하세요. 응답 압축과 필요한 필드만 고르는 기능(?fields=id,status)은 모바일 클라이언트에게 큰 차이를 만들어요. 로그에 요청 본문을 남길 때는 비밀번호, 토큰, 개인정보 필드를 가려요.
    시니어 심화 요청 수로만 한도를 걸면 공정하지 않아요. 그리고 사용 패턴을 보면 설계의 빈틈이 보여요.

    상황

    제휴사 API에 "분당 600회" 한도를 걸었어요. 그런데 DB 부하의 대부분은 한도를 지키고 있는 제휴사 한 곳이 만들고 있었어요. 그 제휴사는 분당 600회를 모두 "최근 1년 주문 검색"에 쓰고 있었어요. 다른 제휴사는 주문 단건 조회를 1초에 50번씩 연달아 불렀어요.

    깨지는 과정

    1. 주문 단건 조회는 인덱스로 1ms에 끝나고, 1년 치 검색은 수백 ms 동안 DB를 써요. 둘 다 "요청 1회"로 세면 비용 차이가 수백 배인데 같은 취급을 받아요.
    2. 한도를 지키는 제휴사 하나가 DB를 독차지해요.
    3. 단건 조회를 연달아 부르는 제휴사는 사실 "주문 50개의 상태"가 필요했던 거예요. 일괄 조회 API가 없어서 50번을 부르고 있었어요.

    해결책

    • 요청마다 비용 점수를 매겨요. 단건 조회 1점, 검색 10점, 내보내기 100점처럼 정하고, 한도를 점수로 걸어요(분당 1,000점). 비싼 호출이 자연스럽게 억제돼요. 응답 헤더에 남은 점수를 알려 주면 클라이언트가 스스로 속도를 조절해요. GraphQL API는 쿼리의 복잡도로 점수를 계산하는 방식을 많이 써요.
    • 사용 패턴에서 빠진 API를 찾아요. 같은 엔드포인트를 짧은 간격으로 연달아 부르는 패턴은 일괄 조회 API가 빠졌다는 신호예요. 늘 함께 불리는 두 엔드포인트는 합칠 후보예요. 주기적으로 전체를 다시 조회하는 패턴은 변경분만 주는 API나 웹훅이 필요하다는 신호예요.
    • 공식 클라이언트 라이브러리를 제공해요. 재시도와 백오프, 페이징, 인증 갱신, 한도 헤더 처리를 올바르게 구현한 라이브러리를 주면 서버를 지키는 데 도움이 돼요. 라이브러리가 없으면 제휴사마다 재시도를 제각각 구현하는데, 대개 간격 없이, 지터 없이, 무한히 재시도해서 장애 때 서버를 더 세게 두드려요.
    • 한도를 넘었을 때의 응답을 친절하게 해요. 429와 함께 Retry-After, 그리고 어떤 한도에 걸렸는지(분당 점수, 동시 요청 수)를 알려줘요.

    운영에서 알아채는 법

    • 클라이언트별 요청 수뿐 아니라 클라이언트별 DB 시간이나 처리 시간 합계를 지표로 남겨요. 요청 수와 비용 순위가 다르다면 점수 한도가 필요해요.
    • 클라이언트별 엔드포인트 호출 순서를 샘플링해서 보면, 일괄 API나 웹훅이 필요한 곳이 보여요.
    • 429 응답 직후의 재시도 간격을 봐요. 0초 간격 재시도가 많다면 클라이언트 가이드나 라이브러리가 필요해요.
    핵심 정리
    • 명세를 저장소에 두고 문서·검증·클라이언트·호환성 검사를 거기서 생성
    • 429 + Retry-After + 남은 한도. 모든 입력에 상한
    • 요청 ID와 클라이언트 식별로 누가 무엇을 쓰는지 파악

    답 보기

    코드를 바꿀 때 문서를 같이 고치는 것을 잊거나 미루게 되고, 시간이 지나면 문서와 실제 동작이 어긋나요. 쓰는 사람은 문서를 믿을 수 없게 되어 직접 호출해 보거나 문의하게 돼요. 대안은 기계가 읽을 수 있는 명세를 코드와 같은 저장소에 두고 그것을 원본으로 삼는 거예요. 명세에서 문서를 생성하고, 서버가 명세대로 응답하는지 테스트로 확인하고, 명세 변경이 깨는 변경인지 자동으로 검사하면 문서와 구현이 구조적으로 어긋나지 않아요.

    • 3장 같은 목록을 오프셋과 커서로 각각 구현하고, 조회 중 삽입이 일어날 때의 결과와 깊은 페이지의 속도 비교
    • 4장 명세의 이전 버전과 현재 버전을 비교해 깨는 변경을 찾는 검사를 CI에 추가. 필드 이름 변경을 다섯 단계로 진행해 보기
    • 5장 주문 생성에 멱등성 키를 구현하고 같은 요청을 동시에 10번 보내 주문이 하나만 생기는지 확인. ETag와 If-Match로 갱신 손실 막기
    • 5장 주문 내보내기를 202 + 작업 리소스로 구현하고 진행률 조회 추가
