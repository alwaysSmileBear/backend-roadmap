    도메인 주도 설계

    기준 교재: 도메인 주도 개발 시작하기(최범균) + 도메인 주도 설계(에릭 에반스) · 3~4주

    소프트웨어 설계 챕터는 객체 하나하나의 책임과 의존성을 다뤘어요. 이 챕터는 한 단계 위예요. 업무 지식을 코드에 어떻게 담고, 큰 시스템을 어디서 자를 것인가를 다뤄요.

    DDD는 두 부분으로 나뉘어요. 전술적 설계(애그리거트, 리포지토리 같은 코드 수준의 패턴)와 전략적 설계(바운디드 컨텍스트, 큰 그림의 경계). 패턴 이름보다 4장의 경계 긋기가 실제로는 더 큰 영향을 줘요.

    1부 전술적 설계

    1장 도메인 모델과 유비쿼터스 언어

    코드가 업무 용어로 읽히게 한다

    도메인과 모델

    도메인은 소프트웨어가 풀려는 문제의 영역이에요(쇼핑몰이면 주문, 결제, 배송, 정산). 도메인 모델은 그 영역의 개념과 규칙을 목적에 맞게 단순화한 표현이에요. 현실을 전부 옮기는 것이 아니라 풀려는 문제에 필요한 것만 골라요.

    복잡함은 어디서 오는가

    업무용 소프트웨어가 어려운 이유는 기술이 아니라 업무 규칙이에요. "배송 준비 중이면 주소를 바꿀 수 있지만 출고 후에는 안 된다", "쿠폰은 중복 적용이 안 되지만 등급 할인과는 함께 쓸 수 있다". 이 규칙들이 코드 여기저기에 흩어지면 아무도 전체를 알 수 없게 돼요.

    유비쿼터스 언어

    개발자, 기획자, 운영자가 같은 용어를 같은 뜻으로 쓰는 거예요. 그리고 그 용어가 대화, 문서, 코드에 그대로 나타나요.

    • 업무에서 "출고"라고 부르는 것을 코드에서 setStatus(3)이라고 쓰면, 읽는 사람이 매번 번역해야 해요. order.ship()이어야 해요.
    • 같은 것을 누구는 "회원", 누구는 "고객", 누구는 "유저"라고 부르면 서로 다른 것인지 같은 것인지부터 헷갈려요.
    • 대화에서 어색한 표현이 나오면 모델이 틀렸다는 신호예요.

    도메인 규칙의 자리

    규칙은 그 규칙이 다루는 데이터를 가진 객체 안에 둬요.

    // 규칙이 서비스에 흩어짐
      if (order.getStatus() == PAID || order.getStatus() == PREPARING) {
          order.setAddress(newAddress);
      }

      // 규칙이 도메인 객체 안에
      order.changeShippingAddress(newAddress);   // 안에서 가능 여부를 판단
    백엔드에서는 코드 리뷰에서 "이 이름을 기획자가 알아들을까"를 물어보세요. processData, handleRequest, type = 2 같은 코드는 업무 지식이 코드 밖(작성자의 머릿속)에 있다는 뜻이에요. 용어집을 만들어 두면 신규 입사자의 적응 시간과 기획과의 오해가 눈에 띄게 줄어요.
    시니어 심화
    • 모델은 한 번에 완성되지 않아요. 업무를 더 깊이 이해하면 용어와 구조가 바뀌어요. 그때 코드의 이름까지 바꾸는 리팩터링을 미루면 언어와 코드가 갈라지기 시작해요. 이름 변경을 싸게 할 수 있는 구조(테스트, 모듈 경계)가 모델을 살아 있게 해요.
    • 모든 곳에 도메인 모델이 필요하지는 않아요. 규칙이 거의 없는 단순 조회·입력 기능에 풍부한 모델을 만드는 것은 낭비예요. 사업에서 차별화되는 핵심 영역에 설계 노력을 집중하고, 나머지는 단순하게 두거나 사서 써요.
    • 업무 전문가와 함께 사건을 시간순으로 벽에 붙여 가며 흐름을 찾는 워크숍(이벤트 스토밍)이 용어와 경계를 빠르게 드러내요.
    핵심 정리
    • 도메인 모델 = 문제 해결에 필요한 개념과 규칙의 표현
    • 유비쿼터스 언어: 대화·문서·코드가 같은 용어
    • 규칙은 데이터를 가진 도메인 객체 안에
    셀프 체크
    1. order.setStatus(OrderStatus.SHIPPED) 대신 order.ship()으로 만들면 무엇이 좋아지나요?
    답 보기

    첫째, 코드가 업무 용어로 읽혀요. 출고라는 업무 행위가 이름에 드러나요. 둘째, 출고에 따르는 규칙을 한곳에 둘 수 있어요. 결제 완료 상태에서만 출고할 수 있다는 검사, 출고 시각 기록, 출고 이벤트 발행이 ship 안에 모여요. setStatus를 열어 두면 호출하는 모든 곳이 그 규칙을 각자 지켜야 하고, 한 곳이라도 빠뜨리면 규칙을 건너뛴 상태 변경이 일어나요. 셋째, 허용되지 않는 상태 전이를 아예 표현할 수 없게 만들 수 있어요.

    2장 엔티티, 밸류, 애그리거트

    무엇을 한 덩어리로 다룰 것인가

    엔티티와 밸류

    • 엔티티: 식별자로 구분해요. 속성이 전부 바뀌어도 같은 것이에요(주문, 회원).
    • 밸류: 값으로 구분해요. 속성이 같으면 같은 것이고 식별자가 없어요(금액, 주소, 기간).

    밸류는 불변으로 만들어요. 바꾸려면 새 객체를 만들어요. 그리고 관련 로직을 밸류 안에 담아요.

    // 원시 타입: 통화가 다른 금액을 더해도 컴파일러가 못 잡음
      int total = price + shippingFee;

      // 밸류: 규칙이 타입 안에
      Money total = price.add(shippingFee);   // 통화가 다르면 예외

    int, String만으로 짜면 금액과 수량을 바꿔 넣어도 아무도 모르고, 검증 코드가 사방에 흩어져요.

    애그리거트

    함께 일관성을 지켜야 하는 객체들의 묶음이에요. 주문과 주문 항목, 배송 정보가 한 애그리거트예요.

    • 루트: 애그리거트의 대표 엔티티. 밖에서는 루트를 통해서만 내부에 접근해요. 주문 항목을 바꾸려면 주문에게 시켜요.
    • 불변식: 애그리거트가 항상 만족해야 하는 조건("주문 금액 = 항목 금액의 합"). 루트가 책임지고 지켜요.

    애그리거트 규칙

    1. 트랜잭션 하나에 애그리거트 하나만 수정한다.
    2. 다른 애그리거트는 객체 참조가 아니라 ID로 참조한다.
    3. 애그리거트 사이의 일관성은 이벤트로 나중에 맞춘다.
    4. 애그리거트는 작게 유지한다.
    백엔드에서는 JPA에서 ID 참조는 @ManyToOne Member member 대신 Long memberId(또는 MemberId 밸류)를 두는 거예요. 객체 그래프를 따라 다른 애그리거트까지 지연 로딩하는 일이 없어지고, 애그리거트 경계가 코드에 드러나요. 밸류는 @Embeddable로, 밸류 컬렉션은 @ElementCollection이나 별도 테이블로 매핑해요.
    시니어 심화
    • 큰 애그리거트의 비용: 한 번 읽을 때 전부 불러오고, 서로 무관한 수정끼리 같은 버전을 두고 충돌해요. 주문에 수백 개의 댓글을 매달면 댓글 하나 달 때마다 주문 전체가 잠겨요. "같이 조회된다"가 아니라 "같이 바뀌어야 불변식이 지켜진다"가 묶는 기준이에요.
    • 애그리거트를 넘는 불변식이 있다면 선택해야 해요. 정말 즉시 지켜져야 하면 경계를 다시 그려 한 애그리거트로 합치고, 잠깐 어긋나도 되면 이벤트로 맞춰요. "재고가 음수가 되면 안 된다"처럼 즉시성이 필요한 규칙은 DB 제약이 최종 방어선이에요.
    • 낙관적 락은 루트에 둬요. 내부 객체만 바뀌어도 루트의 버전이 올라가야 애그리거트 전체의 동시 수정을 감지할 수 있어요.
    핵심 정리
    • 엔티티 = 식별자로 구분, 밸류 = 값으로 구분·불변·로직 포함
    • 애그리거트 = 일관성 경계. 루트를 통해서만 접근
    • 트랜잭션당 애그리거트 하나, 다른 애그리거트는 ID 참조, 작게 유지
    셀프 체크
    1. 애그리거트끼리 객체 참조 대신 ID로 참조하면 무엇이 좋아지나요?
    답 보기

    객체로 참조하면 한 애그리거트에서 다른 애그리거트의 내부를 따라가 수정할 수 있게 되어 일관성 경계가 무너져요. 한 트랜잭션에서 여러 애그리거트를 고치는 코드가 쉽게 생기고, 지연 로딩으로 의도하지 않은 조회가 늘어요. ID로 참조하면 다른 애그리거트가 필요할 때 리포지토리로 명시적으로 가져와야 하므로 경계가 코드에 드러나요. 또 애그리거트마다 저장소를 달리하거나 다른 서비스로 분리하기도 쉬워져요.

    3장 리포지토리, 도메인 서비스, 응용 서비스

    계층마다 하는 일이 다르다

    계층과 책임

    계층하는 일하지 않는 일
    표현요청 해석, 응답 변환, 형식 검증업무 규칙
    응용유스케이스 흐름 조율, 트랜잭션 경계, 권한 확인업무 규칙의 판단
    도메인업무 규칙과 상태 변경DB, HTTP, 프레임워크를 아는 것
    인프라DB, 메시징, 외부 API의 구현업무 규칙

    리포지토리

    애그리거트를 저장하고 꺼내는 창구예요. 애그리거트 단위로 하나씩 둬요. 주문 항목만 따로 저장하는 리포지토리는 만들지 않아요.

    인터페이스는 도메인 계층에, 구현은 인프라 계층에 둬요. 도메인은 "주문을 저장한다"만 알고 그것이 JPA인지 다른 것인지 몰라요.

    응용 서비스

    유스케이스 하나의 흐름을 조율해요. 로직이 없고 얇아야 해요.

    @Transactional
      public void changeShippingAddress(OrderId id, Address address) {
          Order order = orderRepository.findById(id).orElseThrow();   // 꺼낸다
          order.changeShippingAddress(address);                       // 도메인에 시킨다
      }                                                              // 저장된다

    응용 서비스에 if로 업무 조건을 판단하는 코드가 늘어난다면 그 로직은 도메인으로 내려가야 해요.

    도메인 서비스

    어느 한 애그리거트에 넣기 어색한 도메인 로직을 담아요. 여러 애그리거트의 정보가 필요한 계산(할인 금액 계산은 주문, 회원 등급, 쿠폰이 모두 필요)이 대표적이에요. 상태가 없고, 이름이 업무 용어예요.

    검증의 위치

    • 형식 검증(필수값, 길이, 형식): 표현 계층.
    • 업무 규칙 검증(이 상태에서 가능한가): 도메인 객체.
    • 존재·권한 확인: 응용 서비스.
    백엔드에서는 조회는 굳이 도메인 모델을 거치지 않아도 돼요. 목록 화면에 필요한 데이터를 애그리거트로 전부 읽어 DTO로 바꾸는 것은 느리고 번거로워요. 조회 전용 쿼리로 필요한 컬럼만 DTO에 바로 담으세요. 도메인 모델은 상태를 바꾸는 쪽을 위한 것이에요.
    시니어 심화
    • 리포지토리에 조회 메서드가 수십 개 쌓이면 화면 요구가 도메인 리포지토리로 새고 있다는 뜻이에요. 조회용 인터페이스를 따로 두면 리포지토리는 식별자로 찾기와 저장 정도로 단순해져요.
    • 도메인 계층의 순수성과 실용성 사이에서 선택이 필요해요. JPA 엔티티를 도메인 모델로 겸하면 매핑 코드가 없어 편하지만 기본 생성자, 프록시, 지연 로딩 같은 제약이 도메인으로 들어와요. 핵심 영역은 분리하고 주변 영역은 겸하는 절충이 흔해요.
    • 도메인 서비스가 외부 시스템을 호출해야 하면 인터페이스를 도메인에 정의하고 구현을 인프라에 둬요. 그래야 도메인 로직을 외부 시스템 없이 테스트할 수 있어요.
    핵심 정리
    • 응용 서비스 = 흐름 조율과 트랜잭션, 얇게. 규칙 판단은 도메인
    • 리포지토리는 애그리거트 단위. 인터페이스는 도메인에
    • 조회는 전용 쿼리와 DTO로 분리
    셀프 체크
    1. 응용 서비스에 업무 규칙을 판단하는 if 문이 많아졌습니다. 어떤 문제가 생기고 어떻게 고치나요?
    답 보기

    같은 애그리거트를 다루는 다른 응용 서비스가 같은 규칙을 다시 구현해야 하고, 한쪽만 고치면 규칙이 어긋나요. 규칙이 어디에 있는지 찾으려면 그 애그리거트를 쓰는 모든 서비스를 뒤져야 해요. 도메인 객체는 getter와 setter만 가진 데이터 덩어리가 돼요. 고치려면 판단에 필요한 데이터를 가진 도메인 객체로 그 로직을 옮겨, 의도를 드러내는 메서드로 만들어요. 여러 애그리거트가 필요한 판단이면 도메인 서비스로 옮겨요. 응용 서비스에는 꺼내고, 시키고, 저장하는 흐름만 남겨요.

    2부 전략적 설계

    4장 바운디드 컨텍스트와 컨텍스트 맵

    하나의 모델로 전부를 표현하려 하지 않는다

    같은 단어, 다른 뜻

    "상품"은 카탈로그에서는 이름·설명·이미지이고, 재고에서는 수량과 창고 위치이고, 주문에서는 주문 시점의 가격과 옵션이고, 정산에서는 수수료율이에요. 이것을 Product 클래스 하나로 표현하려 하면 필드가 100개인 괴물이 되고, 한 팀의 변경이 다른 팀의 코드를 깨뜨려요.

    바운디드 컨텍스트

    하나의 모델이 일관되게 적용되는 경계예요. 경계 안에서는 용어의 뜻이 하나예요. 경계가 다르면 같은 단어가 다른 모델이 될 수 있고, 그래도 괜찮아요.

    각 컨텍스트는 자기에게 필요한 속성만 가진 자기만의 "상품"을 가져요. 서로는 식별자로 연결돼요.

    경계를 찾는 단서

    • 같은 용어가 다른 뜻으로 쓰이는 지점.
    • 담당하는 팀이나 부서가 갈리는 지점.
    • 변경의 이유와 주기가 다른 지점.
    • 데이터의 일관성이 즉시 필요하지 않은 지점.

    하위 도메인의 구분

    • 핵심: 사업의 경쟁력이 나오는 곳. 가장 좋은 사람과 설계 노력을 투입해요.
    • 지원: 필요하지만 차별화 요소는 아닌 곳. 단순하게 만들어요.
    • 일반: 어느 회사나 같은 문제(인증, 결제 연동, 알림). 사거나 가져다 써요.

    컨텍스트 맵: 컨텍스트 사이의 관계

    관계의미
    고객-공급자상류가 하류의 요구를 계획에 반영해 준다
    순응하류가 상류의 모델을 그대로 따른다. 협상력이 없을 때
    부패 방지 계층하류가 변환 계층을 두어 상류의 모델이 자기 모델에 스며들지 않게 한다
    공개 호스트 서비스상류가 여러 하류를 위해 잘 정의된 공개 API를 제공한다
    공유 커널두 컨텍스트가 모델 일부를 공유한다. 변경에 양쪽 합의가 필요

    부패 방지 계층

    외부 시스템이나 레거시의 모델은 우리 것과 달라요. 그 구조와 용어를 그대로 받아들이면 우리 도메인이 남의 사정에 맞춰 뒤틀려요. 경계에 변환기를 두어 우리 용어로 번역한 뒤 안으로 들여요.

    백엔드에서는 바운디드 컨텍스트가 곧 마이크로서비스는 아니에요. 먼저 하나의 배포 단위 안에서 모듈로 경계를 나누세요(모듈러 모놀리스). 모듈 사이는 공개 인터페이스로만 호출하고, 다른 모듈의 테이블을 직접 조인하지 않아요. 경계가 맞는지 확인된 뒤에 필요한 것만 서비스로 떼어내요. 경계를 잘못 그은 채로 서비스부터 나누면 서비스 간 호출이 폭증하고 분산 트랜잭션이 필요해져요.
    핵심 정리
    • 같은 용어도 컨텍스트마다 다른 모델. 하나로 합치지 않음
    • 핵심 하위 도메인에 설계 노력 집중, 일반 영역은 가져다 씀
    • 컨텍스트 사이 관계를 명시. 외부 모델은 부패 방지 계층에서 번역
    셀프 체크
    1. 주문 서비스가 상품 서비스의 Product 클래스를 공유 라이브러리로 그대로 가져다 쓰면 어떤 문제가 생기나요?
    답 보기

    두 서비스가 같은 클래스에 결합돼요. 상품 쪽에서 자기 필요로 필드를 바꾸거나 지우면 주문 서비스가 깨지고, 공유 라이브러리 버전을 맞추느라 두 서비스를 함께 배포해야 해요. 주문에 필요한 것은 주문 시점의 상품 이름과 가격 정도인데, 상품 쪽의 모든 속성과 로직을 끌고 오게 돼요. 또 주문은 주문 시점의 값을 보존해야 하는데 상품 모델은 현재 값을 표현해서 의미도 달라요. 주문 컨텍스트가 자기에게 필요한 속성만 가진 자신의 모델을 두고, 상품 쪽 응답을 경계에서 변환해 받아야 해요.

    5장 도메인 이벤트

    일어난 일을 알려서 느슨하게 연결한다

    문제: 한 가지 일이 여러 후속 작업을 부른다

    주문이 취소되면 환불하고, 재고를 되돌리고, 쿠폰을 복구하고, 알림을 보내야 해요. 이것을 주문 취소 코드에 전부 넣으면 주문이 결제, 재고, 쿠폰, 알림을 모두 알게 되고, 후속 작업이 하나 추가될 때마다 주문 코드를 고쳐야 해요.

    도메인 이벤트

    "주문이 취소됐다"는 사실을 발행하고, 관심 있는 쪽이 각자 받아 처리해요. 주문은 누가 듣는지 몰라요.

    • 이름은 과거형이에요. 이미 일어난 일이에요(OrderCanceled).
    • 일어난 시각과, 받는 쪽이 처리하는 데 필요한 정보를 담아요.
    • 불변이에요. 일어난 일은 바뀌지 않아요.

    동기와 비동기

    • 같은 트랜잭션 안에서 동기로: 구현이 단순하지만 핸들러가 실패하면 원래 작업도 롤백되고, 핸들러가 느리면 원래 작업도 느려져요. 결합만 코드에서 사라졌을 뿐 실행은 묶여 있어요.
    • 커밋 후 비동기로: 원래 작업은 후속 작업의 성패와 무관하게 끝나요. 대신 후속 작업이 실패했을 때의 재시도와 보상을 따로 다뤄야 해요.

    유실 없이 내보내기

    DB 커밋과 메시지 발행은 한 트랜잭션으로 묶이지 않아요. 커밋은 됐는데 발행이 안 되면 이벤트가 사라져요. 이벤트를 업무 데이터와 같은 트랜잭션으로 DB 테이블에 저장하고, 별도 프로세스가 그 테이블을 읽어 발행하는 방식(트랜잭셔널 아웃박스)이 표준 해법이에요.

    받는 쪽의 책임

    같은 이벤트가 두 번 올 수 있어요. 받는 쪽은 멱등해야 해요. 순서가 바뀌어 올 수도 있어요.

    백엔드에서는 스프링에서는 애그리거트가 이벤트를 모아 두었다가 저장 시점에 발행하게 하고, 받는 쪽은 @TransactionalEventListener로 커밋 후에 실행되게 해요. 주의할 점은 커밋 후 리스너가 실패해도 원래 트랜잭션은 이미 끝났다는 거예요. 반드시 처리돼야 하는 후속 작업은 아웃박스로, 실패해도 괜찮은 것(알림)만 메모리 이벤트로 처리하세요.
    시니어 심화
    • 내부 이벤트와 외부 이벤트를 분리하세요. 컨텍스트 안에서 쓰는 도메인 이벤트는 자유롭게 바꿀 수 있어야 해요. 다른 팀이 구독하는 이벤트는 공개 API라서 호환성을 지켜야 해요. 내부 이벤트를 그대로 밖에 내보내면 내부 모델을 바꿀 수 없게 돼요.
    • 이벤트에 무엇을 담을까: ID만 담으면 받는 쪽이 다시 조회해야 하고 그 사이 상태가 바뀌어 있을 수 있어요. 상태 전체를 담으면 메시지가 커지고 민감한 정보가 퍼져요. 받는 쪽이 판단하는 데 필요한 사실을 담는 것이 기준이에요.
    • 흐름이 보이지 않게 돼요. 이벤트로 연결된 처리는 코드를 따라가서는 전체 흐름을 알 수 없어요. 어떤 이벤트를 누가 발행하고 누가 구독하는지의 목록과, 이벤트를 관통하는 추적 ID가 필요해요.
    핵심 정리
    • 이벤트 = 과거형 사실. 발행자는 구독자를 모름
    • 커밋 후 비동기 처리는 실패 대응이 필요. 아웃박스로 유실 방지
    • 받는 쪽은 중복과 순서 뒤바뀜을 견뎌야 함
    셀프 체크
    1. 주문 취소 트랜잭션 안에서 환불 API를 직접 호출하는 방식의 문제점은 무엇인가요?
    답 보기

    외부 호출이 트랜잭션 안에 있으면 환불 시스템이 느릴 때 DB 커넥션과 락을 그만큼 오래 쥐어요. 환불 호출이 실패하면 주문 취소 자체가 롤백돼서, 환불 시스템의 장애가 주문 취소 불가로 번져요. 반대로 환불은 성공했는데 그 뒤에 트랜잭션이 롤백되면 주문은 취소되지 않았는데 돈만 환불된 상태가 돼요. 주문은 취소 사실만 기록하고 이벤트를 남기며, 환불은 그 이벤트를 받아 별도로 처리하고 실패하면 재시도하는 구조가 두 문제를 모두 피해요.

    6장 CQRS와 이벤트 소싱

    읽기와 쓰기의 모델을 나눈다

    하나의 모델로 둘 다 하기 어려운 이유

    상태를 바꾸는 쪽은 규칙과 일관성이 중요해서 정규화된, 애그리거트 단위의 모델이 맞아요. 조회하는 쪽은 여러 애그리거트를 합친, 화면 모양에 맞는 데이터가 필요해요. 하나의 모델로 양쪽을 만족시키려 하면 도메인 객체에 화면용 연관과 조회 메서드가 계속 붙어요.

    CQRS

    명령(상태 변경) 모델과 조회 모델을 분리하는 거예요. 단계가 있어요.

    1. 코드만 분리: 같은 DB를 쓰되, 명령은 도메인 모델로, 조회는 전용 쿼리와 DTO로. 대부분은 여기까지면 충분해요.
    2. 조회용 테이블 분리: 조회에 맞게 비정규화한 테이블이나 뷰를 따로 유지해요.
    3. 저장소 분리: 조회 모델을 다른 저장소(검색 엔진, 캐시)에 두고 이벤트로 갱신해요.

    3단계에서는 명령이 성공한 직후 조회하면 아직 반영되지 않은 옛 데이터가 보일 수 있어요. 화면이 그것을 견디도록 설계해야 해요.

    이벤트 소싱

    현재 상태를 저장하는 대신 상태를 바꾼 이벤트를 전부 순서대로 저장해요. 현재 상태는 이벤트를 처음부터 다시 적용해서 얻어요.

    전통적 방식:  잔액 = 70,000
      이벤트 소싱:  입금 100,000 → 출금 20,000 → 출금 10,000   (재생하면 70,000)
    • 얻는 것: 완전한 변경 이력과 감사 기록, 과거 임의 시점의 상태 복원, 이벤트로 새로운 조회 모델을 나중에 만들 수 있음.
    • 치르는 것: 현재 상태를 조회하려면 별도의 조회 모델이 필수(CQRS가 따라옴), 이벤트 스키마가 바뀌어도 옛 이벤트를 영원히 읽어야 함, 이벤트가 많아지면 중간 스냅샷이 필요, 익숙하지 않은 방식이라 팀의 학습 비용이 큼.

    언제 쓰는가

    변경 이력 자체가 업무의 본질인 영역이에요. 회계 원장, 결제 흐름, 재고 이동처럼 "왜 이 값이 됐는가"를 설명해야 하는 곳. 단순한 CRUD에는 과해요. 시스템 전체가 아니라 필요한 애그리거트에만 적용해요.

    백엔드에서는 "CQRS를 도입한다"가 저장소를 나누고 메시지 브로커를 들이는 것을 뜻할 필요는 없어요. 조회 전용 쿼리 클래스를 따로 두는 것만으로 도메인 모델이 조회 요구에서 풀려나요. 조회 저장소를 실제로 분리했다면, 조회 모델이 원본과 어긋났을 때 처음부터 다시 만드는 절차를 준비해 두세요. 반드시 필요해져요.
    핵심 정리
    • CQRS = 명령 모델과 조회 모델 분리. 코드 수준 분리부터
    • 저장소까지 나누면 조회가 잠깐 뒤처질 수 있음
    • 이벤트 소싱 = 이벤트가 원본. 이력이 본질인 곳에만 부분 적용
    셀프 체크
    1. 조회 모델을 별도 저장소로 분리한 CQRS에서 사용자가 글을 수정한 직후 목록에 옛 내용이 보였습니다. 원인과 대응 방법을 말해보세요.
    답 보기

    명령 모델에 쓴 변경이 이벤트를 통해 조회 저장소에 반영되기까지 시간이 걸리는데, 그 전에 조회가 일어났기 때문이에요. 구조상 피할 수 없는 지연이에요. 대응 방법은 여러 가지예요. 수정 응답에 변경된 데이터를 담아 보내 화면이 조회 없이 그것을 보여주게 하거나, 수정한 사용자의 다음 조회만 명령 쪽 저장소에서 읽게 하거나, 명령이 반환한 버전까지 조회 모델이 따라올 때까지 기다린 뒤 응답해요. 어느 화면에서 지연이 허용되고 어디서는 안 되는지를 화면별로 정해야 해요.

    실습

    실습 과제

    지금 맡고 있는 서비스의 한 영역을 골라 적용해 보세요.

    • 1장 담당 도메인의 용어집을 만들고, 코드의 클래스·메서드 이름과 대조해 어긋나는 곳 찾기
    • 2장 int, String으로 표현된 금액·주소·기간을 불변 밸류로 바꾸고 관련 로직을 안으로 옮기기
    • 2장 엔티티 연관 관계 그래프를 그리고 애그리거트 경계를 표시. 경계를 넘는 객체 참조를 ID 참조로 변경
    • 3장 응용 서비스에서 업무 조건을 판단하는 if 문을 찾아 도메인 객체의 메서드로 옮기기
    • 4장 같은 용어가 다른 뜻으로 쓰이는 지점을 찾아 컨텍스트 지도를 그리기. 외부 API 연동부에 부패 방지 계층 넣기
    • 5장 한 트랜잭션에서 여러 후속 작업을 직접 호출하는 코드를 이벤트로 분리. 아웃박스 테이블로 유실 없는 발행 구현
