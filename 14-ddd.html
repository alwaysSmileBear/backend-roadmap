    도메인 주도 설계

    기준 교재: 도메인 주도 개발 시작하기(최범균) + 도메인 주도 설계(에릭 에반스) · 3~4주

    소프트웨어 설계 챕터는 객체 하나하나의 책임과 의존성을 다뤘어요. 이 챕터는 한 단계 위예요. 업무 지식을 코드에 어떻게 담고, 커다란 시스템을 어디서 나눌 것인가를 봐요.

    예시는 쇼핑몰의 주문 도메인이에요. 주문, 결제, 재고, 쿠폰, 정산이 얽혀 있는 곳이라 규칙이 많고 자주 바뀌어요. DDD는 코드 수준의 패턴(1~3장)과 큰 그림의 경계 긋기(4~6장)로 나뉘는데, 실제로 더 큰 영향을 주는 것은 4장의 경계예요.

    1장 도메인 모델과 유비쿼터스 언어

    코드가 업무 용어로 읽히게 한다

    문제: 배송지 변경 규칙이 다섯 군데에 있다

    "출고 전까지만 배송지를 바꿀 수 있다"는 규칙이 있어요. 그런데 이 규칙이 고객용 API, 판매자 관리 화면, 고객센터 도구, 일괄 변경 배치, 제휴사 API, 이렇게 다섯 곳의 서비스 코드에 각자 if문으로 들어 있었어요. 기획에서 "포장 중에도 바꿀 수 없다"로 규칙을 바꾸자, 네 곳만 고치고 한 곳을 놓쳤어요. 고객센터 도구로는 포장 중인 주문의 배송지가 계속 바뀌었어요.

    복잡함은 업무 규칙에서 온다

    업무용 소프트웨어가 어려운 이유는 기술이 아니라 업무 규칙이에요. "출고 전까지만 배송지 변경 가능", "쿠폰은 중복 적용이 안 되지만 회원 등급 할인과는 함께 가능", "부분 취소하면 쿠폰 할인을 다시 계산". 이런 규칙이 코드 여기저기에 흩어지면 아무도 전체를 알 수 없고, 바꿀 때마다 빠뜨려요.

    도메인은 소프트웨어가 풀려는 문제의 영역이에요(주문, 결제, 배송, 정산). 도메인 모델은 그 영역의 개념과 규칙을 문제 해결에 필요한 만큼 골라 표현한 거예요. 핵심은 규칙을 그 규칙이 다루는 데이터를 가진 객체 안에 두는 거예요.

    // 규칙이 서비스마다 흩어짐
      if (order.getStatus() == PAID || order.getStatus() == PREPARING) {
          order.setShippingAddress(newAddress);
      }

      // 규칙이 주문 안에 하나로
      order.changeShippingAddress(newAddress);   // 안에서 가능 여부를 판단

    이제 다섯 곳은 전부 changeShippingAddress를 불러요. 규칙이 바뀌면 이 메서드 하나만 고치면 돼요. setShippingAddress를 아예 공개하지 않으면 규칙을 건너뛰는 길도 막혀요.

    유비쿼터스 언어: 모두가 같은 말을 쓴다

    두 번째 문제는 말이에요. 기획자는 "출고", 개발자는 "배송 시작", 코드는 setStatus(3), 고객센터 매뉴얼은 "발송 처리"라고 불렀어요. 같은 것인지 다른 것인지부터 회의에서 확인해야 했어요.

    유비쿼터스 언어는 개발자, 기획자, 운영자가 같은 용어를 같은 뜻으로 쓰고, 그 용어가 대화와 문서와 코드에 그대로 나타나게 하는 거예요. 업무에서 "출고"라고 부르면 코드에도 order.ship()이 있어야 해요. 코드를 읽는 사람이 매번 업무 용어로 번역하지 않아도 되고, 기획자와 대화하며 코드를 바로 가리킬 수 있어요. 대화에서 어색한 표현이 자꾸 나온다면 모델이 업무와 어긋났다는 신호예요.

    백엔드에서는 코드 리뷰에서 "이 이름을 기획자가 알아들을까"를 물어보세요. processData, handleOrder, type == 2 같은 코드는 업무 지식이 코드 밖, 작성자의 머릿속에 있다는 뜻이에요. 팀의 용어집을 만들어 두면 신규 입사자가 적응하는 시간과 기획과의 오해가 눈에 띄게 줄어요. 용어집의 단어와 코드의 클래스·메서드 이름이 같아야 해요.
    시니어 심화 모든 영역에 정성 들인 도메인 모델이 필요하지는 않아요. 쇼핑몰에서 공지사항 관리, 배너 관리처럼 규칙이 거의 없는 기능은 테이블을 읽고 쓰는 단순한 코드(트랜잭션 스크립트)가 더 싸고 읽기 쉬워요. 거기에 엔티티, 밸류, 도메인 서비스를 다 갖추면 코드만 늘어요.

    설계 노력은 규칙이 복잡하고 자주 바뀌는 곳, 그리고 사업의 경쟁력이 나오는 곳에 몰아줘요. 주문과 할인 계산이 그런 곳이에요. 어디가 그런 곳인지 찾는 좋은 방법이 업무 전문가와 함께 "일어나는 일"을 시간 순서로 벽에 붙여 가며 흐름을 정리하는 워크숍(이벤트 스토밍)이에요. "주문됨 → 결제됨 → 포장 시작됨 → 출고됨"을 붙이다 보면 용어가 맞춰지고, 규칙이 몰린 곳과 팀의 경계(4장)가 함께 드러나요. 그리고 모델은 한 번에 완성되지 않아요. 업무를 더 이해하면 이름과 구조가 바뀌어야 하는데, 이름 변경 리팩터링을 미루면 언어와 코드가 다시 갈라져요.

    핵심 정리
    • 업무 규칙은 그 데이터를 가진 도메인 객체 안에 하나로
    • 유비쿼터스 언어: 대화·문서·코드가 같은 용어
    • 설계 노력은 규칙이 복잡하고 자주 바뀌는 핵심 영역에 집중
    셀프 체크
    1. order.setStatus(OrderStatus.SHIPPED) 대신 order.ship()으로 만들면 무엇이 좋아지나요?
    답 보기

    첫째, 코드가 업무 용어로 읽혀요. 출고라는 업무 행위가 이름에 드러나요. 둘째, 출고에 따르는 규칙을 한곳에 둘 수 있어요. 결제 완료 상태에서만 출고할 수 있다는 검사, 출고 시각 기록, 출고 이벤트 발행이 ship 안에 모여요. setStatus를 열어 두면 부르는 모든 곳이 그 규칙을 각자 지켜야 하고, 한 곳이라도 빠뜨리면 규칙을 건너뛴 상태 변경이 일어나요. 셋째, 허용되지 않는 상태 변화를 아예 표현할 수 없게 만들 수 있어요.

    2장 엔티티, 밸류, 애그리거트

    무엇을 한 덩어리로 다룰 것인가

    문제: 주문 금액과 항목 합계가 다르다

    정산 담당자가 이상한 주문을 찾아왔어요. 주문의 총액은 52,000원인데 주문 항목의 금액을 더하면 47,000원이었어요. 코드를 따라가 보니, 부분 취소 기능이 주문 항목 리포지토리로 항목을 직접 지우면서 주문의 총액은 다시 계산하지 않았어요. 주문과 주문 항목이 따로 고쳐질 수 있었던 거예요.

    엔티티와 밸류

    먼저 두 종류의 객체를 구분해요. 엔티티는 식별자로 구분하는 객체예요. 주문 1042는 배송지가 바뀌고 상태가 바뀌어도 여전히 주문 1042예요. 밸류는 값으로 구분하는 객체예요. 5,000원은 어떤 5,000원이든 같은 5,000원이에요. 식별자가 없어요.

    금액, 주소, 기간 같은 밸류는 바뀌지 않는 객체로 만들고, 관련 규칙을 그 안에 담아요.

    // 숫자만 쓰면: 원화와 달러를 더해도, 금액과 수량을 바꿔 넣어도 아무도 모름
      int total = price + shippingFee;

      // 밸류로 만들면: 규칙이 타입 안에
      Money total = price.add(shippingFee);   // 통화가 다르면 예외

    애그리거트: 함께 맞아야 하는 것을 묶는다

    주문 총액은 항상 항목 금액의 합과 같아야 해요. 이렇게 항상 지켜져야 하는 조건을 불변식이라고 해요. 불변식을 지키려면 주문과 항목이 함께 바뀌어야 하는데, 위 문제에서는 항목만 따로 바뀔 수 있었어요.

    애그리거트는 함께 일관성을 지켜야 하는 객체들의 묶음이에요. 주문, 주문 항목, 배송 정보가 하나의 애그리거트예요. 묶음의 대표인 루트(주문)를 정하고, 밖에서는 루트를 통해서만 안쪽을 바꿀 수 있게 해요. 항목을 취소하려면 order.cancelItem(itemId)를 부르고, 주문이 항목을 지우면서 총액도 다시 계산해요. 주문 항목 리포지토리를 따로 두지 않으니 항목만 따로 지울 길이 없어요.

    애그리거트를 다루는 규칙

    네 가지 규칙이 있어요. 첫째, 트랜잭션 하나에서는 애그리거트 하나만 고쳐요. 둘째, 다른 애그리거트는 객체로 들고 있지 않고 ID로만 가리켜요. 주문은 회원 객체가 아니라 회원 ID를 가져요. 셋째, 애그리거트 사이의 일관성은 즉시가 아니라 이벤트로 조금 뒤에 맞춰요(5장). 넷째, 애그리거트는 작게 유지해요.

    백엔드에서는 JPA로 구현하면 ID 참조는 @ManyToOne Member member 대신 Long memberId(또는 MemberId 밸류)를 두는 거예요. 객체를 따라 다른 애그리거트까지 지연 로딩하는 일이 없어지고, 경계가 코드에 드러나요. 밸류는 @Embeddable로, 밸류 목록은 @ElementCollection이나 별도 테이블로 매핑해요. 주문 항목처럼 루트를 통해서만 다뤄야 하는 엔티티에는 리포지토리를 만들지 마세요.
    시니어 심화 "관련이 있으니 같이 묶자"로 애그리거트를 크게 만들면 운영에서 대가를 치러요. 주문 애그리거트에 상품 리뷰와 배송 추적 이력까지 넣었다고 해 봐요. 주문을 조회할 때마다 리뷰와 이력을 전부 불러오고, 고객이 리뷰를 쓰는 순간과 택배사가 배송 상태를 갱신하는 순간이 같은 주문의 버전을 두고 충돌해요. 서로 아무 상관 없는 변경끼리 낙관적 락 실패로 재시도를 반복해요.

    묶는 기준은 "관련이 있는가"가 아니라 "함께 바뀌어야 불변식이 지켜지는가"예요. 리뷰는 주문과 관련이 있지만 주문 총액과 함께 맞을 필요가 없으니 별도 애그리거트예요. 반대로 정말 애그리거트를 넘는 규칙이 있다면 선택해야 해요. 즉시 지켜져야 하면 경계를 다시 그어 한 애그리거트로 합치고, 잠깐 어긋나도 되면 이벤트로 나중에 맞춰요. "재고가 음수가 되면 안 된다"처럼 여러 주문이 동시에 다투는 규칙은 DB의 조건부 갱신이나 제약이 최종 방어선이에요. 그리고 낙관적 락의 버전은 루트에 둬요. 안쪽 항목만 바뀌어도 루트의 버전이 올라가야 애그리거트 전체의 동시 수정을 잡을 수 있어요.

    핵심 정리
    • 엔티티 = 식별자로 구분, 밸류 = 값으로 구분·불변·규칙 포함
    • 애그리거트 = 불변식을 함께 지키는 묶음. 루트를 통해서만 변경
    • 트랜잭션당 애그리거트 하나, 다른 애그리거트는 ID로, 작게
    셀프 체크
    1. 애그리거트끼리 객체 참조 대신 ID로 참조하면 무엇이 좋아지나요?
    답 보기

    객체로 참조하면 한 애그리거트에서 다른 애그리거트의 안쪽을 따라가 고칠 수 있게 되어 일관성의 경계가 무너져요. 한 트랜잭션에서 여러 애그리거트를 고치는 코드가 쉽게 생기고, 지연 로딩으로 의도하지 않은 조회가 늘어요. ID로 참조하면 다른 애그리거트가 필요할 때 리포지토리로 명시적으로 가져와야 하므로 경계가 코드에 드러나요. 나중에 애그리거트마다 저장소를 달리하거나 다른 서비스로 떼어 내기도 쉬워져요.

    3장 리포지토리, 도메인 서비스, 응용 서비스

    계층마다 하는 일이 다르다

    문제: 주문 서비스가 2,000줄이 됐다

    OrderService 클래스가 2,000줄이 넘었어요. 주문 생성 메서드 하나에 재고 확인, 쿠폰 검증, 할인 계산, 포인트 차감, 결제 요청, 알림 발송이 전부 if와 for로 들어 있어요. 반면 Order 엔티티는 getter와 setter뿐이에요. 할인 규칙을 바꾸려면 2,000줄 안에서 해당 부분을 찾아야 하고, 테스트하려면 DB와 결제사 가짜 서버까지 띄워야 해요.

    계층마다 맡는 일

    표현 계층(컨트롤러)은 요청을 해석하고 응답으로 바꿔요. 필수값, 길이, 형식 같은 형식 검증도 여기서 해요. 응용 계층(응용 서비스)은 유스케이스 하나의 흐름을 조율하고 트랜잭션의 경계를 정해요. 도메인 계층은 업무 규칙과 상태 변경을 맡아요. DB, HTTP, 프레임워크를 몰라요. 인프라 계층은 DB, 메시징, 외부 API의 실제 구현이에요.

    응용 서비스는 얇게

    응용 서비스는 꺼내고, 시키고, 저장하는 일만 해요.

    @Transactional
      public void changeShippingAddress(OrderId id, Address address) {
          Order order = orderRepository.findById(id).orElseThrow();   // 꺼낸다
          order.changeShippingAddress(address);                       // 도메인에 시킨다
      }                                                              // 변경이 저장된다

    응용 서비스에 업무 조건을 판단하는 if가 늘어난다면, 그 로직은 도메인으로 내려가야 한다는 신호예요. 위 문제의 할인 계산과 쿠폰 검증이 그래요.

    리포지토리: 애그리거트를 꺼내고 넣는 곳

    리포지토리는 애그리거트 단위로 하나씩 둬요(2장). 인터페이스는 도메인 계층에, JPA 구현은 인프라 계층에 둬요. 도메인은 "주문을 저장한다"만 알고 그것이 어떤 기술인지 몰라요.

    도메인 서비스: 어느 한 객체에 두기 어색한 규칙

    할인 금액 계산에는 주문(금액), 회원(등급), 쿠폰(조건)의 정보가 모두 필요해요. 셋 중 어느 하나에 넣기 어색해요. 이런 도메인 로직은 도메인 서비스(DiscountCalculator)에 둬요. 상태가 없고, 이름이 업무 용어이고, DB를 직접 부르지 않고 필요한 객체를 인자로 받아요. 그래서 DB 없이 단위 테스트할 수 있어요.

    이렇게 나누면 2,000줄짜리 서비스는 흐름을 조율하는 짧은 응용 서비스, 할인 계산 도메인 서비스, 규칙을 담은 주문과 쿠폰 객체로 흩어져요. 할인 규칙을 바꿀 때는 할인 계산 클래스와 그 테스트만 보면 돼요.

    백엔드에서는 조회는 도메인 모델을 거치지 않아도 돼요. 판매자 주문 목록 화면에 필요한 데이터를 주문 애그리거트로 전부 읽은 뒤 DTO로 바꾸면 느리고 번거로워요(N+1도 생겨요). 필요한 컬럼만 조회하는 전용 쿼리로 DTO에 바로 담으세요. 도메인 모델은 상태를 바꾸는 쪽을 위한 거예요(6장 CQRS의 출발점).
    시니어 심화 JPA 엔티티를 도메인 모델로 함께 쓸지는 실무에서 가장 자주 부딪히는 선택이에요. 함께 쓰면 매핑 코드가 없어 편하지만, JPA의 사정이 도메인으로 들어와요. 기본 생성자가 필요하고, 지연 로딩 프록시 때문에 equals와 getClass가 예상과 다르게 동작하고, 양방향 연관 관계를 맞추는 코드가 업무 규칙 사이에 섞여요.

    분리하면 도메인은 깨끗하지만 도메인 객체와 JPA 엔티티를 오가는 변환 코드가 애그리거트마다 생겨요. 그래서 흔한 절충은 핵심 영역(주문, 할인)은 분리하고, 주변 영역(공지, 배너)은 함께 쓰는 거예요. 어느 쪽이든 지켜야 할 것은 의존 방향이에요. 도메인 계층의 코드가 org.springframework나 인프라 패키지를 import하지 않게 하고, 이것을 아키텍처 테스트(ArchUnit)로 강제해요. 그리고 리포지토리에 화면용 조회 메서드가 수십 개 쌓이면 조회 요구가 도메인으로 새고 있다는 신호예요. 조회용 인터페이스를 따로 두면 리포지토리는 "ID로 찾기, 저장하기" 정도로 단순해져요.

    핵심 정리
    • 응용 서비스 = 흐름 조율과 트랜잭션, 얇게. 규칙 판단은 도메인
    • 리포지토리는 애그리거트 단위, 인터페이스는 도메인에. 여러 객체가 필요한 규칙은 도메인 서비스
    • 조회는 전용 쿼리와 DTO로 도메인 모델과 분리
    셀프 체크
    1. 응용 서비스에 업무 규칙을 판단하는 if 문이 많아졌습니다. 어떤 문제가 생기고 어떻게 고치나요?
    답 보기

    같은 애그리거트를 다루는 다른 응용 서비스가 같은 규칙을 다시 구현해야 하고, 한쪽만 고치면 규칙이 어긋나요. 규칙이 어디 있는지 찾으려면 그 애그리거트를 쓰는 모든 서비스를 뒤져야 해요. 도메인 객체는 getter와 setter만 가진 데이터 덩어리가 되고, 규칙을 테스트하려면 DB와 외부 시스템까지 띄워야 해요. 고치려면 판단에 필요한 데이터를 가진 도메인 객체로 그 로직을 옮겨 의도를 드러내는 메서드로 만들고, 여러 애그리거트의 정보가 필요하면 도메인 서비스로 옮겨요. 응용 서비스에는 꺼내고, 시키고, 저장하는 흐름만 남겨요.

    2부 전략적 설계

    4장 바운디드 컨텍스트와 컨텍스트 맵

    하나의 모델로 전부를 표현하려 하지 않는다

    문제: 상품 클래스에 필드가 87개

    쇼핑몰의 Product 클래스에 필드가 87개 있어요. 카탈로그 팀은 상품 설명과 이미지를, 재고 팀은 창고별 수량을, 주문 팀은 옵션과 가격을, 정산 팀은 수수료율을 이 클래스에 추가해 왔어요. 재고 팀이 필드 하나를 바꾸면 정산 배치가 깨지고, 모든 팀의 배포가 이 클래스를 두고 줄을 서요.

    같은 단어, 다른 뜻

    문제는 "상품"이라는 단어가 팀마다 다른 것을 뜻한다는 거예요. 카탈로그에서 상품은 이름, 설명, 이미지예요. 재고에서 상품은 창고별 수량과 위치예요. 주문에서 상품은 주문한 그 순간의 가격과 옵션이에요(나중에 가격이 바뀌어도 주문의 가격은 그대로여야 해요). 정산에서 상품은 수수료율과 판매자예요. 이것을 클래스 하나로 표현하려 하니 87개의 필드가 된 거예요.

    바운디드 컨텍스트

    바운디드 컨텍스트는 하나의 모델이 일관되게 통하는 경계예요. 경계 안에서는 용어의 뜻이 하나예요. 경계가 다르면 같은 단어가 다른 모델이 될 수 있고, 그래도 괜찮아요. 위 그림처럼 각 컨텍스트가 자기에게 필요한 속성만 가진 자기만의 "상품"을 갖고, 서로는 상품 ID로 연결돼요.

    경계를 찾는 단서는 네 가지예요. 같은 용어가 다른 뜻으로 쓰이는 곳, 담당 팀이 갈리는 곳, 바뀌는 이유와 주기가 다른 곳, 그리고 데이터가 즉시 맞을 필요가 없는 곳이에요.

    어디에 공을 들일까

    모든 영역이 똑같이 중요하지 않아요. 사업의 경쟁력이 나오는 핵심 영역(이 쇼핑몰이라면 추천과 할인 정책)에는 가장 좋은 사람과 설계 노력을 써요. 필요하지만 차별화 요소는 아닌 지원 영역(판매자 정산)은 단순하게 만들어요. 어느 회사나 같은 일반 영역(로그인, 결제 연동, 문자 발송)은 사거나 가져다 써요.

    컨텍스트 사이의 관계

    컨텍스트끼리는 어떤 관계인지도 정해 둬요. 상류(제공하는 쪽)가 하류(쓰는 쪽)의 요구를 계획에 반영해 주는 고객-공급자, 하류가 협상력이 없어 상류의 모델을 그대로 따르는 순응, 상류가 여러 하류를 위해 잘 정의된 공개 API를 주는 공개 호스트 서비스, 두 컨텍스트가 모델 일부를 함께 쓰는 공유 커널(바꿀 때 양쪽 합의가 필요해요)이 있어요.

    외부 결제사나 오래된 레거시 시스템처럼 우리가 바꿀 수 없는 상류라면 부패 방지 계층을 둬요. 상대의 모델과 용어를 그대로 받아들이면 우리 도메인이 남의 사정에 맞춰 뒤틀려요. 경계에 변환기를 두어 우리 용어로 번역한 뒤 안으로 들여요. 결제사가 바뀌어도 변환기만 바꾸면 돼요.

    백엔드에서는 바운디드 컨텍스트가 곧 마이크로서비스는 아니에요. 먼저 하나의 배포 단위 안에서 모듈로 경계를 나누세요(모듈러 모놀리스). 모듈 사이는 공개 인터페이스로만 부르고, 다른 모듈의 테이블을 직접 조인하지 않아요. 경계가 맞는지 확인된 뒤에 정말 따로 배포하고 늘려야 하는 것만 서비스로 떼어 내요. 경계를 잘못 그은 채로 서비스부터 나누면 서비스 간 호출이 폭증하고 분산 트랜잭션이 필요해져요. 그때는 경계를 다시 그리기도 훨씬 어려워요.
    핵심 정리
    • 같은 용어도 컨텍스트마다 다른 모델. 억지로 하나로 합치지 않음
    • 핵심 영역에 설계 노력 집중, 일반 영역은 가져다 씀
    • 컨텍스트 사이 관계를 명시. 바꿀 수 없는 외부 모델은 부패 방지 계층에서 번역
    셀프 체크
    1. 주문 서비스가 상품 서비스의 Product 클래스를 공유 라이브러리로 그대로 가져다 쓰면 어떤 문제가 생기나요?
    답 보기

    두 서비스가 같은 클래스에 묶여요. 상품 쪽에서 자기 필요로 필드를 바꾸거나 지우면 주문 서비스가 깨지고, 공유 라이브러리 버전을 맞추느라 두 서비스를 함께 배포해야 해요. 주문에 필요한 것은 주문 시점의 상품 이름과 가격 정도인데 상품 쪽의 모든 속성과 로직을 끌고 와요. 게다가 주문은 주문한 순간의 값을 보존해야 하는데 상품 모델은 현재 값을 나타내서 의미부터 달라요. 주문 컨텍스트가 필요한 속성만 가진 자신의 모델을 두고, 상품 쪽 응답을 경계에서 변환해 받아야 해요.

    5장 도메인 이벤트

    일어난 일을 알려서 느슨하게 잇는다

    문제: 주문 취소에 환불, 재고, 쿠폰, 포인트, 알림이 다 들어 있다

    주문을 취소하면 결제를 환불하고, 재고를 되돌리고, 쿠폰을 복구하고, 포인트를 돌려주고, 고객에게 문자를 보내야 해요. 처음에는 이 다섯 가지를 주문 취소 메서드에서 차례로 불렀어요. 그러다 보니 문제가 겹쳤어요. 주문이 결제, 재고, 쿠폰, 포인트, 알림을 전부 알게 됐고, 후속 작업이 하나 추가될 때마다 주문 코드를 고쳐야 했고, 문자 서비스가 느리면 주문 취소까지 느려졌어요. 문자 발송이 실패하자 취소 전체가 롤백되기도 했어요.

    "주문이 취소됐다"고 알리기만 한다

    주문은 취소라는 자기 일만 하고, "주문이 취소됐다"는 사실을 발행해요. 관심 있는 쪽이 각자 받아서 자기 일을 해요. 주문은 누가 듣는지 몰라요. 이것이 도메인 이벤트예요.

    이벤트에는 몇 가지 성질이 있어요. 이름은 과거형이에요(OrderCanceled). 이미 일어난 일이라 받는 쪽이 거부할 수 없어요. 그래서 바뀌지 않는 객체로 만들어요. 그리고 받는 쪽이 처리하는 데 필요한 정보(주문 ID, 취소된 항목, 사용한 쿠폰, 취소 시각)를 담아요.

    같은 트랜잭션에서, 아니면 커밋 뒤에

    이벤트를 처리하는 시점은 두 가지예요. 같은 트랜잭션 안에서 바로 처리하면 구현이 단순하지만, 받는 쪽이 실패하면 주문 취소도 롤백되고, 받는 쪽이 느리면 취소도 느려져요. 코드에서 의존은 사라졌지만 실행은 여전히 묶여 있어요. 커밋한 뒤에 따로 처리하면 주문 취소는 후속 작업의 성패와 상관없이 끝나요. 대신 후속 작업이 실패했을 때 다시 시도하는 장치가 필요해요.

    이벤트를 잃지 않으려면

    커밋한 뒤에 메시지 브로커로 보내는 순간 서버가 죽으면, 주문은 취소됐는데 이벤트는 사라져요. 환불이 영영 안 돼요. DB 커밋과 메시지 발행은 하나의 트랜잭션으로 묶이지 않기 때문이에요. 표준 해법은 이벤트를 주문 데이터와 같은 트랜잭션으로 DB 테이블(아웃박스)에 저장하고, 별도 프로세스가 그 테이블을 읽어 발행하는 거예요(분산 시스템 챕터 부록 B). 커밋되면 이벤트도 반드시 남아요.

    그리고 받는 쪽은 같은 이벤트가 두 번 와도 견뎌야 해요. 발행 프로세스가 보내고 기록하기 전에 죽으면 다시 보내니까요. 이미 처리한 이벤트 ID를 기록해 두고 건너뛰어요(Kafka 챕터 3장).

    백엔드에서는 스프링에서는 애그리거트가 이벤트를 모아 두었다가 저장할 때 발행하게 하고(AbstractAggregateRoot), 받는 쪽은 @TransactionalEventListener로 커밋 뒤에 실행되게 해요. 주의할 점은 커밋 뒤 리스너가 실패해도 원래 트랜잭션은 이미 끝났다는 거예요. 메모리 안의 이벤트는 서버가 죽으면 사라지니, 반드시 처리돼야 하는 환불 같은 작업은 아웃박스로, 실패해도 괜찮은 문자 같은 작업만 메모리 이벤트로 처리하세요.
    시니어 심화 이벤트를 쓰기 시작하면 금방 생기는 문제가 내부 이벤트와 외부 이벤트의 구분이에요. 주문 컨텍스트 안에서 쓰는 이벤트는 주문 팀이 마음대로 바꿀 수 있어야 해요. 그런데 그 이벤트를 그대로 Kafka에 실어 정산 팀과 추천 팀이 구독하기 시작하면, 그 순간 공개 API가 돼요. 필드 하나 바꾸는 것도 다른 팀과 합의해야 하고, 주문 내부 모델을 바꿀 수 없게 돼요.

    그래서 컨텍스트 밖으로 내보내는 이벤트는 따로 정의해요. 내부 이벤트를 받아서 공개용 이벤트로 번역해 내보내는 계층을 두면, 내부는 자유롭게 바꾸고 외부 계약은 API 챕터 4장의 호환성 규칙으로 관리할 수 있어요. 이벤트에 무엇을 담을지도 정해야 해요. ID만 담으면 받는 쪽이 다시 조회해야 하는데 그 사이 상태가 바뀌어 있을 수 있고, 상태를 통째로 담으면 메시지가 커지고 개인정보가 여기저기 퍼져요. "받는 쪽이 판단하는 데 필요한 사실"이 기준이에요. 마지막으로 이벤트로 이어진 흐름은 코드를 따라가서는 보이지 않아요. 어떤 이벤트를 누가 내고 누가 받는지의 목록과, 이벤트를 관통하는 추적 ID가 있어야 장애 때 흐름을 따라갈 수 있어요.

    핵심 정리
    • 이벤트 = 과거형 사실. 발행하는 쪽은 받는 쪽을 모름
    • 커밋 뒤에 따로 처리하면 실패 대응이 필요. 아웃박스로 유실 방지
    • 받는 쪽은 중복과 순서 뒤바뀜을 견뎌야 함
    셀프 체크
    1. 주문 취소 트랜잭션 안에서 환불 API를 직접 호출하는 방식의 문제점은 무엇인가요?
    답 보기

    외부 호출이 트랜잭션 안에 있으면 결제사가 느릴 때 DB 커넥션과 락을 그만큼 오래 쥐어요. 환불 호출이 실패하면 주문 취소 자체가 롤백되어 결제사의 장애가 주문 취소 불가로 번져요. 반대로 환불은 성공했는데 그 뒤에 트랜잭션이 롤백되면, 주문은 취소되지 않았는데 돈만 환불된 상태가 돼요. 주문은 취소 사실만 기록하고 이벤트를 남기고, 환불은 그 이벤트를 받아 따로 처리하며 실패하면 다시 시도하는 구조가 두 문제를 모두 피해요.

    6장 CQRS와 이벤트 소싱

    바꾸는 모델과 읽는 모델을 나눈다

    문제: 주문 엔티티가 화면 때문에 비대해졌다

    판매자 대시보드에 "주문 목록 + 회원 이름 + 상품 이미지 + 배송 상태 + 정산 예정 금액"을 한 화면에 보여달라는 요구가 왔어요. 주문 애그리거트로 이것을 만들려니 주문 엔티티에 회원, 상품, 배송, 정산 연관을 걸고 조회용 메서드를 붙여야 했어요. 애그리거트는 작아야 한다는 2장의 규칙과 정면으로 부딪혀요.

    바꾸는 쪽과 읽는 쪽은 요구가 다르다

    상태를 바꾸는 쪽에는 규칙과 일관성이 중요해요. 애그리거트 단위의 작고 정규화된 모델이 맞아요. 상태를 읽는 쪽에는 여러 애그리거트를 합친, 화면 모양 그대로의 데이터가 필요해요. 하나의 모델로 둘 다 만족시키려 하면 위처럼 도메인 객체가 화면 요구에 끌려다녀요.

    CQRS는 명령(상태 변경) 모델과 조회 모델을 나누는 거예요. 나누는 정도에 따라 단계가 있어요.

    첫째, 코드만 나눠요. 같은 DB를 쓰되, 명령은 도메인 모델로 처리하고, 조회는 전용 쿼리로 DTO에 바로 담아요(3장의 "백엔드에서는"). 대부분의 서비스는 여기까지면 충분해요. 둘째, 조회용 테이블을 따로 둬요. 조회에 맞게 미리 합쳐 둔 테이블을 유지해요. 셋째, 저장소를 따로 둬요. 조회 모델을 검색 엔진이나 캐시처럼 조회에 강한 저장소에 두고, 변경 이벤트로 갱신해요.

    셋째 단계에서는 변경이 이벤트를 거쳐 조회 저장소에 반영되기까지 시간이 걸려요. 판매자가 송장 번호를 입력하고 목록으로 돌아왔는데 아직 옛 상태가 보일 수 있어요. 화면이 이것을 견디도록 설계해야 해요.

    이벤트 소싱: 상태 대신 변경 이력을 저장한다

    한 발 더 나간 방식이 이벤트 소싱이에요. 현재 상태를 저장하는 대신 상태를 바꾼 이벤트를 전부 순서대로 저장하고, 현재 상태는 이벤트를 처음부터 다시 적용해서 얻어요.

    전통적 방식:  포인트 잔액 = 7,000
      이벤트 소싱:  적립 10,000 → 사용 2,000 → 사용 1,000   (다시 적용하면 7,000)

    얻는 것은 완전한 변경 이력이에요. 감사 기록이 저절로 생기고, 과거 어느 시점의 상태든 복원할 수 있고, 저장된 이벤트로 새로운 조회 모델을 나중에 만들 수 있어요. 치르는 것도 커요. 현재 상태를 조회하려면 별도의 조회 모델이 반드시 필요하고(CQRS가 따라와요), 이벤트 형식이 바뀌어도 옛 이벤트를 영원히 읽을 수 있어야 하고, 이벤트가 많아지면 중간 스냅샷이 필요하고, 팀이 익숙해지는 데 시간이 걸려요.

    그래서 이벤트 소싱은 변경 이력 자체가 업무의 본질인 곳에만, 그리고 시스템 전체가 아니라 그 애그리거트에만 써요. 포인트 원장, 결제 흐름, 재고 이동처럼 "왜 이 값이 됐는가"를 설명해야 하는 곳이요. 상품 설명 같은 단순한 데이터에는 과해요.

    백엔드에서는 "CQRS를 도입한다"가 저장소를 나누고 메시지 브로커를 들이는 것일 필요는 없어요. 조회 전용 쿼리 클래스를 따로 두는 것만으로도 도메인 모델이 화면 요구에서 풀려나요. 조회 저장소를 실제로 나눴다면, 조회 모델이 원본과 어긋났을 때 처음부터 다시 만드는 절차를 미리 준비해 두세요. 버그, 이벤트 유실, 형식 변경 때문에 반드시 한 번은 필요해져요.
    핵심 정리
    • CQRS = 명령 모델과 조회 모델 분리. 코드 수준 분리부터
    • 저장소까지 나누면 조회가 잠깐 뒤처짐. 화면이 견디도록 설계
    • 이벤트 소싱 = 이벤트가 원본. 이력이 본질인 애그리거트에만
    셀프 체크
    1. 조회 모델을 별도 저장소로 나눈 CQRS에서 사용자가 글을 수정한 직후 목록에 옛 내용이 보였습니다. 원인과 대응 방법을 말해보세요.
    답 보기

    명령 쪽에 쓴 변경이 이벤트를 거쳐 조회 저장소에 반영되기까지 시간이 걸리는데, 그 전에 조회가 일어났기 때문이에요. 구조상 피할 수 없는 지연이에요. 대응 방법은 여러 가지예요. 수정 응답에 변경된 데이터를 담아 화면이 조회 없이 그것을 보여주게 하거나, 방금 수정한 사용자의 다음 조회만 명령 쪽 저장소에서 읽게 하거나, 명령이 돌려준 버전까지 조회 모델이 따라올 때까지 기다린 뒤 응답해요. 어느 화면에서는 지연이 괜찮고 어느 화면에서는 안 되는지를 화면별로 정해야 해요.

    실습

    실습 과제

    지금 맡고 있는 서비스의 한 영역을 골라 적용해 보세요.

    • 1장 담당 도메인의 용어집을 만들고, 코드의 클래스·메서드 이름과 대조해 어긋나는 곳 찾기. 같은 규칙이 여러 서비스에 흩어진 곳 찾기
    • 2장 int, String으로 표현된 금액·주소·기간을 불변 밸류로 바꾸고 관련 규칙을 안으로 옮기기
    • 2장 엔티티 연관 관계를 그리고 애그리거트 경계를 표시. 경계를 넘는 객체 참조를 ID 참조로 바꾸고, 루트가 아닌 엔티티의 리포지토리 제거
    • 3장 응용 서비스에서 업무 조건을 판단하는 if 문을 찾아 도메인 객체나 도메인 서비스로 옮기고, DB 없이 단위 테스트 작성
    • 4장 같은 용어가 다른 뜻으로 쓰이는 곳을 찾아 컨텍스트 지도 그리기. 외부 API 연동부에 부패 방지 계층 넣기
    • 5장 한 트랜잭션에서 여러 후속 작업을 직접 부르는 코드를 이벤트로 나누고, 아웃박스 테이블로 유실 없는 발행 구현
    • 6장 목록 조회를 도메인 모델 경유에서 조회 전용 쿼리 + DTO로 바꾸고 쿼리 수와 응답 시간 비교
