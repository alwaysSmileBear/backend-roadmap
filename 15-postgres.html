    PostgreSQL

    기준 자료: PostgreSQL 공식 문서 + The Internals of PostgreSQL · 2~3주

    데이터베이스 챕터는 MySQL(InnoDB)을 기준으로 했어요. 이 챕터는 같은 문제를 PostgreSQL이 어떻게 다르게 풀었는지를 봐요. 두 구현을 비교하면 "DB가 원래 그런 것"과 "이 제품이 그렇게 선택한 것"이 구분돼요.

    데이터베이스 챕터의 InnoDB 아키텍처와 트랜잭션 장을 먼저 읽고 오세요. PostgreSQL을 운영에서 쓴다면 2장(MVCC)과 3장(VACUUM)이 가장 중요해요. PostgreSQL 장애의 큰 부분이 여기서 나와요.

    1장 프로세스 구조와 메모리

    연결 하나가 프로세스 하나다

    프로세스 모델

    MySQL은 연결마다 스레드를 쓰고, PostgreSQL은 연결마다 프로세스를 하나씩 만들어요(백엔드 프로세스). 프로세스는 스레드보다 만드는 비용과 메모리가 커요.

    • 연결 수백 개까지는 괜찮지만 수천 개가 되면 메모리와 문맥 전환 부담이 커져요.
    • 그래서 PostgreSQL에서는 커넥션 풀러(PgBouncer 등)를 앞에 두는 것이 사실상 표준이에요.

    주요 프로세스

    • postmaster: 연결을 받아 백엔드 프로세스를 만드는 부모.
    • 백엔드: 클라이언트 하나의 쿼리를 처리.
    • WAL writer, checkpointer, background writer: 로그와 더티 페이지를 디스크에 씀.
    • autovacuum: 죽은 튜플을 정리(3장).

    메모리

    설정범위용도
    shared_buffers전체 공유데이터 페이지 캐시
    work_mem연산마다정렬, 해시 조인 한 번에 쓸 수 있는 메모리
    maintenance_work_mem작업마다VACUUM, 인덱스 생성

    이중 캐시

    InnoDB는 보통 OS 캐시를 우회하고 버퍼풀을 크게 잡아요. PostgreSQL은 OS 페이지 캐시에도 의존해요. 그래서 shared_buffers를 메모리의 대부분으로 잡지 않고 일부(흔히 4분의 1 정도에서 시작)만 주고 나머지를 OS에 남겨요.

    저장 구조: 힙 테이블

    InnoDB는 테이블 자체가 PK 순서로 정렬된 B-Tree예요(클러스터링 인덱스). PostgreSQL의 테이블은 정렬되지 않은 힙이에요. 행은 빈 곳에 들어가고, 모든 인덱스는 행의 물리 위치(TID)를 가리켜요. PK 인덱스도 다른 인덱스와 똑같은 보조 인덱스예요.

    백엔드에서는 work_mem은 쿼리 하나가 아니라 쿼리 안의 정렬·해시 연산 하나마다 적용돼요. 복잡한 쿼리는 여러 번 쓰고, 그게 연결 수만큼 곱해져요. 전역으로 크게 올리면 메모리가 터져요. 필요한 쿼리에서만 세션 단위로 올리세요. 그리고 풀러를 트랜잭션 단위 모드로 쓰면 세션에 묶인 기능(세션 변수, 일부 방식의 준비된 문장, 세션 수준 잠금)이 동작하지 않을 수 있어요.
    시니어 심화
    • 힙 구조의 장단점: PK를 무작위 값으로 써도 테이블 자체는 영향을 덜 받아요(인덱스는 여전히 받아요). 반면 PK 범위 조회가 물리적으로 흩어진 행을 읽어야 해서 InnoDB보다 불리할 수 있어요. 보조 인덱스 조회는 PK를 한 번 더 거치지 않고 바로 행으로 가요.
    • 연결 폭주가 PostgreSQL에서는 더 치명적이에요. 프로세스 생성 비용에 더해, 활성 연결이 많을수록 스냅샷을 만드는 비용도 커져요. 애플리케이션 인스턴스 수 × 풀 크기가 DB의 한도 안에 드는지 계산하고, 풀러에서 총량을 제한해요.
    • idle in transaction 상태로 방치된 연결은 잠금을 쥐고 VACUUM을 막아요. 시간 제한(idle_in_transaction_session_timeout)을 걸어 두세요.
    핵심 정리
    • 연결 = 프로세스. 커넥션 풀러가 사실상 필수
    • shared_buffers + OS 캐시의 이중 캐시. work_mem은 연산마다
    • 테이블은 힙, 모든 인덱스가 물리 위치를 가리킴
    셀프 체크
    1. PostgreSQL에서 커넥션 풀러를 DB 앞에 따로 두는 것이 MySQL보다 더 강조되는 이유는 무엇인가요?
    답 보기

    PostgreSQL은 연결마다 운영체제 프로세스를 하나씩 만들어요. 프로세스는 스레드보다 생성 비용이 크고 메모리를 더 쓰며, 수가 많아지면 문맥 전환과 내부 자료구조 경합이 커져요. 애플리케이션 서버가 여러 대이고 각자 풀을 가지면 DB 쪽 연결 수는 그 곱이 되는데, 대부분은 쉬고 있어요. 풀러를 두면 많은 클라이언트 연결을 적은 수의 실제 DB 연결로 묶어 쓸 수 있어서 DB 쪽 프로세스 수를 낮게 유지할 수 있어요.

    2장 MVCC와 튜플 버전

    UPDATE는 새 행을 쓰는 것이다

    InnoDB와의 차이

    둘 다 MVCC로 "읽기가 쓰기를 막지 않게" 해요. 옛 버전을 두는 곳이 달라요.

    • InnoDB: 행을 제자리에서 고치고, 옛 버전은 별도의 언두 로그에 둬요.
    • PostgreSQL: 옛 행을 그대로 두고 새 행을 테이블 안에 추가해요. 옛 버전과 새 버전이 같은 테이블에 나란히 있어요.

    튜플의 숨은 컬럼

    모든 행(튜플)에는 두 값이 붙어 있어요.

    • xmin: 이 튜플을 만든 트랜잭션의 ID.
    • xmax: 이 튜플을 삭제하거나 갱신한 트랜잭션의 ID. 아직 유효하면 비어 있어요.
    연산실제로 일어나는 일
    INSERT새 튜플 추가(xmin = 내 트랜잭션)
    DELETE기존 튜플의 xmax를 설정. 튜플은 그대로 남음
    UPDATE기존 튜플의 xmax 설정 + 새 튜플 추가

    가시성 판단

    쿼리는 시작할 때 스냅샷(어떤 트랜잭션이 커밋됐고 어떤 것이 진행 중인지)을 받아요. 튜플을 읽을 때마다 xmin과 xmax를 스냅샷과 비교해 "내게 보이는 버전인가"를 판단해요.

    죽은 튜플

    삭제되거나 갱신으로 대체된 옛 튜플은, 그것을 볼 수 있는 트랜잭션이 하나도 남지 않으면 죽은 튜플이 돼요. 공간을 차지하지만 아무에게도 보이지 않아요. 누군가 치워야 해요. 그것이 VACUUM이에요.

    UPDATE의 비용

    새 튜플은 위치가 달라서, 원칙적으로 모든 인덱스에 새 항목을 추가해야 해요. 바뀌지 않은 컬럼의 인덱스도요. 예외가 HOT 업데이트예요. 인덱스가 걸린 컬럼이 하나도 바뀌지 않았고 같은 페이지에 빈 공간이 있으면 인덱스를 건드리지 않아요.

    백엔드에서는 자주 갱신되는 컬럼(조회수, 마지막 접속 시각, 상태)에 인덱스를 걸면 그 컬럼이 바뀔 때마다 HOT 업데이트가 불가능해져서 모든 인덱스가 갱신돼요. 자주 바뀌는 값과 잘 안 바뀌는 큰 값(본문, JSON)이 한 행에 있으면 작은 값을 고칠 때마다 행 전체의 새 버전이 생겨요. 테이블을 나누는 것을 검토하세요.
    시니어 심화
    • fillfactor: 페이지를 꽉 채우지 않고 여유를 남기면 같은 페이지 안에서 새 버전을 쓸 수 있어 HOT 업데이트 비율이 올라가요. 갱신이 많은 테이블에서 낮춰 볼 만해요. pg_stat_user_tables의 HOT 갱신 수로 효과를 확인해요.
    • 롤백은 싸고 정리는 비싸요. InnoDB는 롤백할 때 언두를 적용해 되돌려야 해요. PostgreSQL은 그 트랜잭션이 취소됐다고 표시만 하면 끝이에요. 대신 취소된 트랜잭션이 쓴 튜플은 죽은 튜플로 남아 나중에 치워야 해요.
    • 큰 값은 따로 저장돼요(TOAST). 큰 컬럼을 건드리지 않는 갱신은 그 값을 다시 쓰지 않지만, SELECT *는 매번 따로 저장된 큰 값까지 읽어 와요.
    핵심 정리
    • PostgreSQL은 옛 버전을 테이블 안에 남김. UPDATE = 삭제 표시 + 새 튜플
    • xmin/xmax와 스냅샷으로 가시성 판단
    • 죽은 튜플이 쌓임. HOT 업데이트가 아니면 모든 인덱스 갱신
    셀프 체크
    1. PostgreSQL에서 인덱스가 5개인 테이블의, 인덱스가 걸리지 않은 컬럼 하나를 UPDATE할 때 인덱스는 어떻게 되나요?
    답 보기

    UPDATE는 새 튜플을 만드는데 새 튜플은 물리 위치가 달라요. 인덱스는 물리 위치를 가리키므로 원칙적으로는 인덱스 5개 모두에 새 위치를 가리키는 항목을 추가해야 해요. 다만 바뀐 컬럼이 어떤 인덱스에도 포함되지 않고, 새 튜플이 같은 페이지 안에 들어갈 공간이 있으면 HOT 업데이트가 적용돼요. 이 경우 인덱스는 건드리지 않고 옛 튜플에서 새 튜플로 이어지는 연결만 만들어요. 페이지에 빈 공간이 없으면 HOT이 안 돼서 5개 모두 갱신돼요.

    3장 VACUUM, 팽창, 트랜잭션 ID 고갈

    치우지 않으면 느려지고, 끝내는 멈춘다

    VACUUM이 하는 일

    • 죽은 튜플 회수: 그 공간을 "재사용 가능"으로 표시해요. 파일 크기를 줄이는 것이 아니에요. 이후의 INSERT와 UPDATE가 그 자리를 써요.
    • 가시성 맵 갱신: 모든 튜플이 누구에게나 보이는 페이지를 표시해요. 인덱스만으로 답하는 스캔이 이 맵 덕분에 테이블을 안 읽어요.
    • 통계 갱신(ANALYZE): 옵티마이저가 쓰는 분포 정보.
    • 트랜잭션 ID 동결: 아래에서 설명해요.

    autovacuum

    테이블별로 죽은 튜플이 임계값을 넘으면 자동으로 VACUUM을 돌려요. 임계값은 "고정 수 + 테이블 크기의 일정 비율"이라, 큰 테이블은 기본 설정으로는 너무 드물게 돌아요. 행이 수억 개면 수천만 개가 죽어야 시작해요. 큰 테이블은 테이블 단위로 비율을 낮춰요.

    팽창(bloat)

    죽은 튜플이 회수되는 속도보다 빨리 쌓이면 테이블과 인덱스가 실제 데이터보다 훨씬 커져요. 같은 데이터를 읽는 데 더 많은 페이지를 읽어야 하니 전부 느려져요.

    한번 커진 파일은 일반 VACUUM으로 줄지 않아요. VACUUM FULL은 테이블을 새로 쓰면서 줄이지만 테이블 전체를 잠가요. 운영 중에는 온라인으로 재구성하는 확장(pg_repack 등)을 써요.

    VACUUM을 막는 것

    VACUUM은 아직 누군가 볼 수 있는 튜플은 못 치워요. 아래가 있으면 그 시점 이후의 죽은 튜플은 전부 남아요.

    • 오래 열린 트랜잭션(idle in transaction 포함).
    • 따라오지 못하는 복제 슬롯.
    • 끝나지 않은 준비된(2단계 커밋) 트랜잭션.

    "autovacuum이 도는데도 테이블이 계속 커진다"면 이 셋을 먼저 봐요.

    트랜잭션 ID 고갈

    트랜잭션 ID는 32비트예요. 약 40억 개를 쓰면 한 바퀴 돌아요. 가시성 판단은 ID의 선후 비교라서, 한 바퀴 돌면 아주 오래된 튜플이 "미래의 것"으로 보여 사라진 것처럼 돼요.

    이를 막으려고 VACUUM이 충분히 오래된 튜플을 동결(항상 보이는 것으로 표시)해요. 동결이 계속 밀리면 PostgreSQL은 데이터 보호를 위해 새 쓰기 트랜잭션을 거부해요. 전체 서비스 중단이에요.

    백엔드에서는 모니터링할 것은 세 가지예요. 테이블별 죽은 튜플 수와 마지막 autovacuum 시각(pg_stat_user_tables), 가장 오래된 트랜잭션의 나이(pg_stat_activity의 xact_start), 데이터베이스별 트랜잭션 ID 나이(age(datfrozenxid)). 마지막 값이 계속 오르기만 하면 동결이 밀리고 있는 것이니, 한도에 가까워지기 훨씬 전에 알람이 울리게 하세요.
    핵심 정리
    • VACUUM = 죽은 튜플 공간 재사용 표시 + 가시성 맵 + 동결. 파일은 안 줄어듦
    • 큰 테이블은 autovacuum 임계값을 낮춤. 긴 트랜잭션이 VACUUM을 막음
    • 트랜잭션 ID는 유한. 동결이 밀리면 쓰기가 멈춤
    셀프 체크
    1. autovacuum이 정상적으로 실행되는데도 죽은 튜플이 줄지 않습니다. 무엇을 확인해야 하나요?
    답 보기

    VACUUM은 어떤 트랜잭션이라도 아직 볼 수 있는 튜플은 치우지 못해요. 그래서 가장 오래된 스냅샷을 붙잡고 있는 것을 찾아야 해요. 첫째, 오래 열려 있는 트랜잭션이에요. 쿼리는 끝났지만 커밋하지 않고 방치된 연결도 포함돼요. 둘째, 소비되지 않고 있는 복제 슬롯이에요. 셋째, 커밋도 롤백도 되지 않은 준비된 트랜잭션이에요. 넷째, 복제본에서 긴 쿼리가 돌고 있고 그 정보를 주 서버로 되먹이는 설정이 켜진 경우예요. 이 중 하나라도 있으면 그 시점 이후에 죽은 튜플은 VACUUM이 몇 번을 돌아도 남아요.

    GIN하나의 값 안에 여러 요소가 있는 것의 포함 검색배열, JSONB, 전문 검색
    GiST겹침, 포함, 가까움 같은 관계범위 타입, 지리 정보
    BRIN물리적 순서와 값이 연관된 아주 큰 테이블시간순으로 쌓이는 로그

    GIN

    행 하나가 여러 키를 가질 때 써요. 키마다 그 키를 가진 행의 목록을 저장하는 역색인 구조예요. JSONB 컬럼에 "이 키-값을 포함하는 문서"를 찾거나 배열에 "이 요소가 들어 있는 행"을 찾을 때 맞아요. 조회는 빠르지만 쓰기가 느려요. 행 하나가 인덱스 항목 여러 개를 만들어요.

    BRIN

    페이지 묶음마다 "이 구간의 최솟값과 최댓값"만 저장해요. 크기가 B-Tree의 수백분의 1이에요. 값이 물리적 순서와 맞을 때만 효과가 있어요. 시각 순으로만 추가되는 테이블의 시각 컬럼이 대표적이에요.

    MySQL에 없거나 다른 기능

    • 부분 인덱스: 조건에 맞는 행만 인덱스에 넣어요. WHERE status = 'PENDING'인 행만 색인하면 작고 빨라요.
    • 표현식 인덱스: lower(email)처럼 계산 결과에 인덱스.
    • 커버링(INCLUDE): 검색 키는 아니지만 인덱스에 함께 담아 둘 컬럼을 지정.
    • 동시 생성: CREATE INDEX CONCURRENTLY는 쓰기를 막지 않고 만들어요.

    인덱스 전용 스캔의 조건

    PostgreSQL의 인덱스에는 가시성 정보가 없어요. 인덱스에 필요한 컬럼이 다 있어도, 그 튜플이 내게 보이는지 확인하려면 테이블을 읽어야 해요. 가시성 맵에 "이 페이지는 전부 보임"으로 표시된 페이지만 테이블 읽기를 건너뛰어요. 그래서 VACUUM이 밀리면 인덱스 전용 스캔이 느려져요.

    백엔드에서는 부분 인덱스는 "소수의 행만 자주 찾는" 패턴에 아주 잘 맞아요. 처리 대기 중인 작업, 삭제되지 않은 행, 활성 사용자처럼요. 그리고 부분 유니크 인덱스로 "삭제되지 않은 행 중에서만 이메일이 유일"처럼 조건부 유일성을 표현할 수 있어요. 소프트 삭제와 유니크 제약의 충돌을 푸는 방법이에요.
    시니어 심화
    • CREATE INDEX CONCURRENTLY는 실패할 수 있고, 실패하면 무효 상태의 인덱스가 남아요. 그 인덱스는 조회에는 안 쓰이지만 쓰기 비용은 계속 내요. 마이그레이션 후 무효 인덱스가 없는지 확인하고 지워요. 트랜잭션 블록 안에서는 실행할 수 없어서 마이그레이션 도구의 설정도 봐야 해요.
    • 인덱스도 팽창해요. 갱신과 삭제가 많은 테이블의 인덱스는 시간이 갈수록 커지고 느려져요. REINDEX CONCURRENTLY로 잠금 없이 다시 만들어요.
    • 안 쓰는 인덱스는 비용만 내요. 쓰기마다 갱신되고 HOT 업데이트를 막아요. pg_stat_user_indexes의 스캔 횟수가 0인 인덱스를 주기적으로 찾아요. 복제본에서만 쓰이는 인덱스가 있을 수 있으니 복제본의 통계도 확인하세요.
    핵심 정리
    • B-Tree 외에 GIN(포함 검색), GiST(관계), BRIN(순서와 연관된 거대 테이블)
    • 부분·표현식·INCLUDE 인덱스, 동시 생성
    • 인덱스 전용 스캔은 가시성 맵에 의존 → VACUUM이 중요
    셀프 체크
    1. 작업 큐 테이블에서 status가 PENDING인 행만 자주 조회합니다. 전체의 1%뿐일 때 어떤 인덱스가 적합한가요?
    답 보기

    조건이 붙은 부분 인덱스가 맞아요. status가 PENDING인 행만 색인하도록 만들면 인덱스 크기가 전체의 1% 수준이라 메모리에 쉽게 올라가고 탐색이 빨라요. 완료된 99%의 행은 인덱스에 없으니 그 행들의 다른 컬럼이 바뀌어도 이 인덱스를 갱신할 일이 없어요. status 전체에 일반 인덱스를 걸면 거의 쓰이지 않는 값들까지 다 담아 크기만 커져요. 처리 순서가 필요하면 인덱스 컬럼을 생성 시각으로 하고 조건절에 상태를 두면 돼요.

    5장 격리 수준과 잠금

    MySQL과 이름은 같아도 동작이 다르다

    격리 수준

    수준PostgreSQL의 동작
    READ COMMITTED (기본)문장마다 새 스냅샷
    REPEATABLE READ트랜잭션의 첫 문장에서 스냅샷 고정. 스냅샷 격리
    SERIALIZABLE스냅샷 격리 + 직렬화 위반 탐지(SSI)

    기본값부터 달라요. MySQL은 REPEATABLE READ, PostgreSQL은 READ COMMITTED예요.

    REPEATABLE READ의 차이

    • 갱신 충돌: 내 스냅샷 이후에 다른 트랜잭션이 고치고 커밋한 행을 내가 고치려 하면, PostgreSQL은 에러를 내고 트랜잭션을 중단시켜요. 갱신 손실이 자동으로 막히는 대신 애플리케이션이 재시도해야 해요. InnoDB는 같은 상황에서 최신 값 위에 그대로 갱신해요.
    • 갭 락이 없어요. 범위 잠금으로 삽입을 막지 않아요. 팬텀은 스냅샷으로 안 보이게 할 뿐이에요.

    SERIALIZABLE (SSI)

    잠그지 않고 진행하다가, 트랜잭션들 사이의 읽기-쓰기 의존 관계에서 직렬 실행으로는 나올 수 없는 패턴을 탐지하면 한쪽을 중단시켜요. 쓰기 스큐까지 막아요. 대가는 직렬화 실패 에러에 대한 재시도가 필수라는 것과 추적 비용이에요.

    행 잠금

    SELECT ... FOR UPDATE, FOR SHARE가 있고, SKIP LOCKED와 NOWAIT를 지원해요. 읽기는 쓰기를 막지 않고 쓰기도 읽기를 막지 않아요.

    DDL과 잠금 대기열

    대부분의 ALTER TABLE은 테이블에 가장 강한 잠금을 요구해요. 잠금 자체는 순간이어도 위험한 것은 대기열이에요.

    1. 긴 조회가 테이블을 읽는 중이다.
    2. ALTER가 강한 잠금을 요청하고 그 조회가 끝나길 기다린다.
    3. 그 뒤에 온 모든 쿼리가 ALTER 뒤에 줄을 선다. 평범한 SELECT도요.

    긴 조회 하나와 ALTER 하나가 만나면 테이블 전체가 멈춰요. DDL을 실행할 때는 lock_timeout을 짧게 걸어, 잠금을 못 얻으면 빨리 포기하고 다시 시도하게 해요.

    백엔드에서는 PostgreSQL에서 REPEATABLE READ 이상을 쓰면 직렬화 실패(SQLSTATE 40001)를 받을 수 있어요. 이것은 버그가 아니라 정상 동작이고, 트랜잭션 전체를 처음부터 다시 실행해야 해요. 재시도 로직 없이 격리 수준만 올리면 간헐적인 에러로 나타나요. 그리고 DDL은 PostgreSQL에서 트랜잭션 안에서 실행되고 롤백도 돼요. 마이그레이션 여러 단계를 원자적으로 적용할 수 있어요.
    시니어 심화
    • 안전한 스키마 변경 패턴을 팀 규칙으로 두세요. 제약 추가는 "검증 없이 추가(NOT VALID) → 따로 검증(VALIDATE CONSTRAINT)" 두 단계로 나누면 긴 잠금을 피해요. 인덱스는 동시 생성으로, 컬럼 타입 변경처럼 테이블을 다시 쓰는 작업은 새 컬럼 추가와 점진적 복사로 대체해요.
    • 잠금 대기 진단: pg_stat_activity의 wait_event와 pg_blocking_pids()로 누가 누구를 막고 있는지 봐요. log_lock_waits를 켜면 일정 시간 이상 기다린 잠금이 로그에 남아요.
    • 권고 잠금(advisory lock)은 애플리케이션이 정한 키로 거는 잠금이에요. 배치 중복 실행 방지 같은 용도에 DB만으로 분산 락을 구현할 수 있어요. 세션 수준 잠금은 풀러의 트랜잭션 모드와 맞지 않으니 트랜잭션 수준 잠금을 써요.
    핵심 정리
    • 기본 격리 수준이 READ COMMITTED. RR은 갱신 충돌 시 에러(재시도 필요)
    • SERIALIZABLE = SSI. 쓰기 스큐까지 방지, 재시도 필수
    • DDL은 잠금 대기열로 테이블을 멈출 수 있음. lock_timeout 설정
    셀프 체크
    1. 잠금을 아주 짧게만 잡는 ALTER TABLE이 서비스를 수 분간 멈출 수 있는 이유를 설명하세요.
    답 보기

    ALTER TABLE은 테이블에 대한 가장 강한 잠금이 필요해서, 그 테이블을 쓰고 있는 다른 트랜잭션이 모두 끝날 때까지 기다려요. 긴 조회나 열려 있는 트랜잭션이 하나라도 있으면 ALTER는 대기 상태가 돼요. 문제는 그 뒤에 도착하는 쿼리들이에요. 잠금 요청은 순서대로 처리되므로 새로 온 쿼리들은 단순한 SELECT라도 대기 중인 ALTER의 뒤에 줄을 서요. 결과적으로 그 긴 조회가 끝날 때까지 테이블에 대한 모든 쿼리가 멈춰요. 잠금 대기 시간 제한을 짧게 걸어 두면 ALTER가 빨리 포기하고 물러나서 대기열이 풀려요.

    6장 WAL과 복제

    물리 복제와 논리 복제

    WAL

    모든 변경은 데이터 파일에 반영되기 전에 WAL(Write-Ahead Log)에 먼저 기록돼요. 커밋은 WAL이 디스크에 내려가면 완료예요. 장애 후에는 마지막 체크포인트부터 WAL을 다시 적용해 복구해요. 원리는 InnoDB의 리두 로그와 같아요.

    • 체크포인트: 더티 페이지를 디스크에 내려쓰고 "여기까지는 복구에 WAL이 필요 없다"를 표시해요.
    • 전체 페이지 기록: 체크포인트 후 어떤 페이지를 처음 고칠 때는 페이지 전체를 WAL에 기록해요. 쓰다 만 페이지로부터 복구하기 위한 것이고, 체크포인트 직후 WAL 양이 급증하는 이유예요.

    스트리밍 복제(물리 복제)

    주 서버의 WAL을 복제본으로 계속 보내고, 복제본이 그것을 그대로 재생해요. 복제본은 주 서버와 바이트 단위로 같은 사본이에요.

    • 복제본은 읽기 전용 쿼리를 받을 수 있어요.
    • 일부 테이블만 복제하거나 다른 버전 간에 복제할 수는 없어요.
    • synchronous_commit과 synchronous_standby_names로 "복제본이 어디까지 받았을 때 커밋을 완료로 볼지"를 정해요.

    복제본에서의 쿼리 충돌

    복제본에서 긴 쿼리가 옛 튜플을 읽는 중인데, 주 서버에서 VACUUM이 그 튜플을 지운 WAL이 도착하면 충돌이에요. 복제본은 WAL 적용을 미루다가(복제 지연 증가) 한도를 넘으면 쿼리를 취소해요.

    hot_standby_feedback을 켜면 복제본이 "나는 아직 이 튜플이 필요하다"를 주 서버에 알려 VACUUM이 미루게 해요. 대신 복제본의 긴 쿼리가 주 서버의 팽창을 만들어요.

    논리 복제

    WAL을 "어느 테이블의 어느 행이 어떻게 바뀌었다"는 논리적 변경으로 해석해서 보내요.

    • 테이블 단위로 골라 복제할 수 있고, 버전이 다른 서버 사이에도 돼요. 무중단 메이저 버전 업그레이드에 써요.
    • 변경 데이터 캡처(CDC)의 기반이에요. 변경을 Kafka 같은 곳으로 흘려보내요.
    • 스키마 변경(DDL)은 복제되지 않아요. 양쪽에 따로 적용해야 해요.

    복제 슬롯

    소비자가 어디까지 받았는지 주 서버가 기억하고, 아직 안 받은 WAL을 지우지 않게 해요. 소비자가 잠깐 끊겨도 이어받을 수 있어요. 위험은 소비자가 영영 돌아오지 않을 때예요. WAL이 끝없이 쌓여 디스크가 가득 차고 주 서버가 멈춰요.

    백엔드에서는 복제 슬롯을 만들었다면 슬롯별로 밀린 WAL 양을 모니터링하고, 한도를 넘으면 슬롯을 무효화하는 설정(max_slot_wal_keep_size)을 거세요. CDC 커넥터를 내렸는데 슬롯을 지우지 않아 운영 DB 디스크가 차는 사고가 흔해요. PostgreSQL에는 자동 장애 조치가 내장돼 있지 않아서 별도 도구(Patroni 등)나 관리형 서비스가 맡아요.
    핵심 정리
    • WAL 먼저, 커밋 = WAL 동기화. 체크포인트 후 전체 페이지 기록으로 WAL 급증
    • 물리 복제 = 바이트 단위 사본, 논리 복제 = 행 변경 단위(CDC, 버전 간 이전)
    • 복제 슬롯은 WAL을 붙잡음. 방치하면 디스크가 참
    셀프 체크
    1. 사용하지 않게 된 논리 복제 슬롯을 지우지 않으면 어떤 일이 일어나나요?
    답 보기

    복제 슬롯은 소비자가 아직 받아 가지 않은 WAL을 주 서버가 지우지 못하게 해요. 소비자가 사라졌는데 슬롯이 남아 있으면 그 시점 이후의 WAL이 전부 보존되어 계속 쌓여요. 결국 디스크가 가득 차고, WAL을 쓸 수 없게 된 주 서버는 쓰기를 처리하지 못하고 멈춰요. 슬롯은 죽은 튜플 정리도 붙잡을 수 있어서 테이블 팽창까지 일으켜요. 안 쓰는 슬롯은 즉시 삭제하고, 슬롯이 붙잡을 수 있는 WAL의 최대 크기를 설정해 한도를 넘으면 슬롯이 무효화되게 해 둬야 해요.

    실습

    실습 과제

    컨테이너로 PostgreSQL을 띄우고 직접 관찰하세요.

    • 1장 연결을 수백 개 열고 서버의 프로세스 수와 메모리 확인. PgBouncer를 앞에 두고 실제 DB 연결 수 비교
    • 2장 SELECT xmin, xmax, ctid, *로 행을 본 뒤 UPDATE하고 다시 조회해 값이 어떻게 바뀌는지 확인
    • 3장 한 세션에서 트랜잭션을 열어 둔 채, 다른 세션에서 대량 UPDATE 후 VACUUM VERBOSE를 실행해 회수되지 않는 것을 확인
    • 3장 같은 행을 반복 갱신하며 테이블 크기 변화 관찰. autovacuum을 끈 경우와 비교
    • 4장 JSONB 컬럼에 GIN 인덱스를, 상태 컬럼에 부분 인덱스를 만들고 EXPLAIN ANALYZE로 전후 비교
