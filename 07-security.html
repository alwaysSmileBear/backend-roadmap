    보안

    기준 자료: OWASP Top 10, OWASP ASVS · 3~4주

    보안은 기능이 아니라 성질이에요. 코드가 "의도한 일을 한다"는 것과 "의도하지 않은 일을 하지 않는다"는 것은 다른 문제이고, 보안은 뒤쪽을 다뤄요. 이 챕터는 백엔드 개발자가 직접 책임지는 범위(인증, 인가, 입력 처리, 비밀 관리)를 원리부터 정리해요.

    시간이 없으면 3장(비밀번호와 인증), 5장(인가), 6장(인젝션)을 먼저 읽으세요. 실제 사고의 대부분이 이 세 곳에서 나요.

    1장 위협 모델링과 보안 원칙

    무엇을, 누구로부터, 어떻게 지킬지를 먼저 정한다

    보안의 세 가지 목표

    • 기밀성: 권한 없는 사람이 읽지 못한다.
    • 무결성: 권한 없는 사람이 바꾸지 못한다.
    • 가용성: 필요할 때 쓸 수 있다.

    "안전한가"라는 질문은 답할 수 없어요. "누가 무엇을 얻으려고 어떤 경로로 공격할 때 안전한가"로 바꿔야 답이 나와요. 이것이 위협 모델링이에요.

    위협 모델링 순서

    1. 지킬 자산을 적는다(개인정보, 결제 정보, 관리자 권한).
    2. 데이터가 흐르는 경로와 신뢰 경계를 그린다. 브라우저와 서버 사이, 서비스와 서비스 사이, 서버와 DB 사이.
    3. 경계를 넘는 지점마다 "여기서 위조·변조·도청·권한 상승이 가능한가"를 묻는다.
    4. 가능성과 피해 크기로 우선순위를 정한다.

    설계 원칙

    • 최소 권한: 필요한 것만, 필요한 동안만. DB 계정, 클라우드 역할, API 토큰 전부에 적용돼요.
    • 심층 방어: 한 겹이 뚫려도 다음 겹이 막는다. 입력 검증을 했더라도 쿼리는 바인딩으로.
    • 기본 거부: 명시적으로 허용한 것만 통과. 새 엔드포인트가 기본으로 공개되면 안 돼요.
    • 안전한 실패: 오류가 나면 닫힌 쪽으로. 권한 서버가 응답하지 않으면 거부해요.
    백엔드에서는 클라이언트에서 온 모든 것은 신뢰할 수 없는 입력이에요. 본문, 쿼리, 헤더, 쿠키, 파일 이름, 그리고 프론트엔드가 숨긴 필드와 비활성화한 버튼까지요. 프론트의 검증은 사용성을 위한 것이고 보안은 서버의 검증이 책임져요.
    시니어 심화 보안 요구를 "나중에 점검"으로 미루면 설계를 뒤집어야 하는 지적이 출시 직전에 나와요. 설계 리뷰 때 신뢰 경계를 그린 그림 한 장을 같이 보는 것만으로 대부분 걸러져요.
    • 내부망은 신뢰 경계가 아니에요. 한 서비스가 뚫리면 내부의 모든 서비스에 접근할 수 있는 구조라면, 내부 호출에도 인증과 권한이 필요해요.
    • 감사 로그는 공격자가 지울 수 없는 곳에 둬요. 뚫린 서버가 자기 로그를 고칠 수 있으면 사후 조사가 불가능해요.
    핵심 정리
    • 기밀성·무결성·가용성. "누구로부터"가 정해져야 안전을 말할 수 있음
    • 신뢰 경계를 넘는 지점마다 검증
    • 최소 권한, 심층 방어, 기본 거부, 안전한 실패
    셀프 체크
    1. 프론트엔드에서 입력을 검증하는데도 서버에서 다시 검증해야 하는 이유를 말해보세요.
    답 보기

    프론트엔드 코드는 공격자의 기기에서 실행되므로 공격자가 마음대로 고치거나 건너뛸 수 있어요. 브라우저 없이 직접 HTTP 요청을 만들어 보낼 수도 있어요. 서버가 받는 요청은 신뢰 경계 밖에서 온 것이라 서버가 직접 검증한 것만 믿을 수 있어요. 프론트의 검증은 사용자에게 빠른 피드백을 주기 위한 것이에요.

    2장 암호화 기초

    해시, 대칭키, 비대칭키, MAC, 서명이 각각 무엇을 보장하는가

    기본 요소와 보장하는 것

    요소하는 일보장예
    해시임의 길이 → 고정 길이, 되돌릴 수 없음내용이 같은지 비교SHA-256
    대칭키 암호같은 키로 암호화·복호화기밀성AES
    MAC키 + 메시지 → 인증 태그무결성 + 키를 가진 쪽이 만들었음HMAC-SHA256
    비대칭키 암호공개키로 암호화, 개인키로 복호화키를 미리 공유하지 않고 기밀성RSA, ECDH(키 합의)
    전자 서명개인키로 서명, 공개키로 검증무결성 + 서명자 확인ECDSA, Ed25519

    자주 혼동하는 것

    • 인코딩은 암호화가 아니에요. Base64는 누구나 되돌려요. JWT의 본문은 Base64일 뿐이라 누구나 읽을 수 있어요.
    • 암호화는 무결성을 보장하지 않아요. 암호문을 조작하면 복호화 결과가 바뀌는데, 암호화만으로는 그 사실을 알 수 없어요. 그래서 암호화와 인증을 함께 하는 방식(AES-GCM 같은 인증 암호화)을 써요.
    • 해시는 비밀을 지키지 않아요. 입력 후보가 적으면(전화번호, 주민번호) 전부 해시해 보면 원문이 나와요.

    직접 만들지 않는다

    암호 알고리즘과 프로토콜은 직접 구현하지 않아요. 검증된 라이브러리의 높은 수준 API를 쓰고, 모드·패딩·IV를 직접 조합하지 마세요. 조합을 틀리는 것이 알고리즘이 깨지는 것보다 훨씬 흔한 사고예요.

    백엔드에서는 난수는 용도를 구분하세요. 세션 ID, 토큰, 비밀번호 재설정 코드는 암호학적 난수 생성기(SecureRandom)로 만들어야 해요. 일반 난수(Random, Math.random)는 출력 몇 개로 다음 값을 예측할 수 있어요.
    시니어 심화 운영에서 암호화의 어려움은 알고리즘이 아니라 키 관리예요.
    • 데이터를 암호화하는 키(데이터 키)를 다시 상위 키로 암호화해 두는 봉투 암호화를 쓰면, 상위 키만 키 관리 서비스(KMS)에 두고 회전시킬 수 있어요.
    • 키를 바꿀 수 있게 설계했는지 확인하세요. 암호문에 키 버전을 같이 저장하지 않으면 키를 교체할 방법이 없어요.
    • 비밀 값 비교는 걸린 시간으로 정보가 새지 않는 상수 시간 비교 함수를 써요. 일반 문자열 비교는 처음 다른 글자에서 멈춰요.
    핵심 정리
    • 해시 = 비교, 대칭키 = 기밀성, MAC·서명 = 무결성과 출처
    • 인코딩 ≠ 암호화, 암호화 ≠ 무결성
    • 직접 구현 금지, 인증 암호화 사용, 토큰은 암호학적 난수
    셀프 체크
    1. MAC과 전자 서명은 둘 다 무결성을 보장하는데, 무엇이 다른가요?
    답 보기

    MAC은 검증하는 쪽도 같은 비밀 키를 가져야 해요. 그래서 검증할 수 있는 쪽은 위조도 할 수 있고, 제3자에게 "상대가 만들었다"를 증명할 수 없어요. 전자 서명은 개인키로 만들고 공개키로 검증하므로 검증자는 위조할 수 없고, 누가 서명했는지를 제3자에게도 보일 수 있어요. 한 조직 안의 서비스끼리는 MAC이 빠르고 단순하고, 여러 주체가 검증해야 하면 서명을 써요.

    2부 인증과 인가

    3장 비밀번호 저장과 인증

    DB가 유출돼도 비밀번호는 유출되지 않게

    비밀번호는 암호화가 아니라 해시

    암호화하면 키를 가진 쪽이 원문을 볼 수 있어요. 서버도 원문을 알 필요가 없으니 되돌릴 수 없는 해시로 저장하고, 로그인할 때 입력을 같은 방식으로 해시해 비교해요.

    그냥 해시는 안 되는 이유

    • 빠른 해시는 공격자에게도 빨라요. SHA-256은 초당 수십억 번 계산돼요. 유출된 해시에 흔한 비밀번호를 대입하는 데 시간이 거의 안 들어요.
    • 같은 비밀번호는 같은 해시가 돼요. 미리 계산해 둔 표로 한꺼번에 풀려요.

    해결: 솔트 + 느린 해시

    • 솔트: 사용자마다 다른 무작위 값을 섞어요. 같은 비밀번호도 해시가 달라지고 미리 계산한 표가 무용지물이 돼요. 솔트는 비밀이 아니라 해시와 함께 저장해요.
    • 비밀번호 전용 해시 함수: 일부러 느리고 메모리를 많이 쓰게 만든 함수를 써요. Argon2id, bcrypt, scrypt. 비용 인자로 느린 정도를 조절해요.

    로그인 방어

    • 계정별·IP별 시도 횟수 제한. 유출된 계정 목록을 대입하는 공격(크리덴셜 스터핑)은 계정마다 한두 번만 시도하므로 계정별 제한만으로는 못 막아요.
    • "아이디가 없습니다"와 "비밀번호가 틀렸습니다"를 구분해서 알려주면 가입된 계정 목록을 수집할 수 있어요. 같은 메시지를 줘요.
    • 다중 인증(MFA): 비밀번호가 유출돼도 두 번째 요소가 막아요.
    백엔드에서는 Spring Security의 BCryptPasswordEncoder나 Argon2PasswordEncoder가 솔트 생성과 저장 형식까지 처리해요. 직접 MessageDigest로 해시하는 코드가 보이면 고쳐야 할 대상이에요. 비밀번호는 로그와 예외 메시지, 요청 덤프에 절대 남기지 마세요.
    시니어 심화
    • 비용 인자는 올려야 해요. 하드웨어가 빨라지므로 몇 년 전의 설정은 약해요. 해시 문자열에 알고리즘과 비용이 들어 있으니, 로그인에 성공했을 때 옛 설정이면 새 설정으로 다시 해시해 저장하는 방식으로 점진 이행해요.
    • 느린 해시는 서버 부하이기도 해요. 로그인 요청을 대량으로 보내면 CPU가 고갈돼요. 로그인 엔드포인트의 레이트 리밋이 가용성 방어이기도 한 이유예요.
    • 비밀번호 재설정이 가장 약한 고리예요. 재설정 토큰은 암호학적 난수로, 짧은 만료로, 한 번만 쓰이게, DB에는 해시로 저장해요. 재설정 후에는 기존 세션을 전부 끊어요.
    핵심 정리
    • 비밀번호 = 솔트 + 느린 전용 해시(Argon2id, bcrypt)
    • 빠른 해시(SHA 계열)로 저장 금지
    • 시도 제한 + 같은 오류 메시지 + MFA
    셀프 체크
    1. 솔트를 해시와 같은 테이블에 평문으로 저장해도 되는 이유는 무엇인가요?
    답 보기

    솔트의 목적은 비밀을 지키는 것이 아니라 같은 비밀번호가 사용자마다 다른 해시가 되게 하는 거예요. 공격자가 솔트를 알아도 사용자마다 따로 대입 공격을 해야 하고, 미리 계산한 표를 쓸 수 없어요. 대입 자체를 느리게 만드는 것은 솔트가 아니라 느린 해시 함수의 역할이에요.

    4장 OAuth 2.0과 OpenID Connect

    비밀번호를 넘기지 않고 권한을 위임한다

    풀려는 문제

    서드파티 앱이 내 캘린더를 읽게 하고 싶어요. 비밀번호를 알려주면 그 앱이 모든 것을 할 수 있고 회수하려면 비밀번호를 바꿔야 해요. OAuth 2.0은 범위가 제한되고 회수할 수 있는 토큰을 대신 발급해요.

    등장인물

    • 리소스 소유자: 사용자
    • 클라이언트: 권한을 받으려는 앱
    • 인가 서버: 사용자를 인증하고 토큰을 발급
    • 리소스 서버: 토큰을 받고 API를 제공

    인가 코드 흐름

    1. 클라이언트가 사용자를 인가 서버로 보낸다(요청 범위, 돌아올 주소, state 포함).
    2. 사용자가 인가 서버에서 로그인하고 동의한다.
    3. 인가 서버가 일회용 코드를 붙여 클라이언트로 돌려보낸다.
    4. 클라이언트가 서버 간 통신으로 코드를 액세스 토큰으로 바꾼다.

    토큰을 브라우저 주소창에 직접 싣지 않으려고 코드를 한 번 거쳐요. 공개 클라이언트(모바일, SPA)는 코드를 가로채도 쓸 수 없게 PKCE를 함께 써요.

    OAuth는 인가, OIDC는 인증

    OAuth의 액세스 토큰은 "이 토큰으로 이것을 할 수 있다"만 말해요. "이 사용자가 누구인가"는 말하지 않아요. OpenID Connect가 그 위에 사용자 정보를 담은 ID 토큰(JWT)을 더해서 로그인에 쓸 수 있게 해요.

    백엔드에서는 "구글로 로그인"을 구현할 때 액세스 토큰만 받아 사용자 식별에 쓰면 안 돼요. ID 토큰을 받아 서명, 발급자(iss), 대상(aud이 우리 앱인지), 만료를 검증하세요. aud를 확인하지 않으면 다른 앱용으로 발급된 토큰으로 우리 서비스에 로그인할 수 있어요.
    시니어 심화
    • 돌아올 주소(redirect URI)는 완전 일치로 등록하고 검증해요. 접두사 일치나 와일드카드를 허용하면 코드가 공격자 사이트로 넘어가요.
    • state는 CSRF 방어예요. 요청 때 만든 값을 세션에 묶어 두고 돌아왔을 때 같은지 확인해요. 없으면 공격자의 계정을 피해자의 세션에 연결시킬 수 있어요.
    • 서비스 간 호출에는 사용자가 없으니 클라이언트 자격 증명 흐름을 써요. 사용자의 토큰을 뒤쪽 서비스로 그대로 넘기면 그 토큰이 필요 이상으로 넓은 곳에서 유효해져요. 대상별로 범위를 좁힌 토큰으로 교환해요.
    • 암시적 흐름과 비밀번호 직접 전달 흐름은 더 이상 권장되지 않아요.
    핵심 정리
    • OAuth 2.0 = 범위가 제한된 권한 위임, 토큰은 회수 가능
    • 인가 코드 흐름 + PKCE가 기본
    • 로그인에는 OIDC의 ID 토큰, iss·aud·만료 검증
    셀프 체크
    1. 인가 코드 흐름에서 토큰을 바로 주지 않고 코드를 거치는 이유는 무엇인가요?
    답 보기

    사용자를 클라이언트로 돌려보내는 단계는 브라우저 주소를 통해 일어나서, 거기에 실린 값은 브라우저 기록과 로그, 중간 스크립트에 노출될 수 있어요. 그래서 그 경로에는 짧게 살고 한 번만 쓸 수 있는 코드만 싣고, 실제 토큰은 클라이언트의 서버가 인가 서버와 직접 통신해서 받아요. 그때 클라이언트 비밀이나 PKCE 검증값을 함께 내야 하므로 코드만 가로채서는 토큰을 얻을 수 없어요.

    5장 인가 — 접근 제어

    로그인했다는 것과 이 데이터를 볼 수 있다는 것은 다르다

    인증과 인가

    인증은 "누구인가", 인가는 "이것을 해도 되는가"예요. 인증을 통과한 사용자가 남의 데이터에 접근하는 것이 실제 사고의 가장 큰 비중을 차지해요.

    가장 흔한 취약점: 객체 수준 권한 누락

    GET /api/orders/1042        ← 내 주문
      GET /api/orders/1043        ← 숫자만 바꿨더니 남의 주문이 보임

    서버가 "로그인했는가"만 확인하고 "이 주문이 이 사용자의 것인가"를 확인하지 않은 거예요. IDOR라고 불러요. 식별자를 UUID로 바꾸는 것은 추측을 어렵게 할 뿐 해결이 아니에요.

    세 층의 검사

    • 기능 수준: 이 역할이 이 엔드포인트를 호출할 수 있는가(관리자 API).
    • 객체 수준: 이 사용자가 이 특정 객체에 접근할 수 있는가.
    • 필드 수준: 이 객체의 이 필드를 읽거나 바꿀 수 있는가. 요청 본문을 엔티티에 통째로 바인딩하면 role이나 isAdmin을 사용자가 직접 바꿀 수 있어요(대량 할당).

    모델

    • RBAC: 역할에 권한을 묶고 사용자에게 역할을 준다. 단순하고 감사하기 쉬움.
    • ABAC: 사용자·자원·환경의 속성으로 규칙을 평가한다("같은 부서의 문서만, 근무 시간에만"). 유연하지만 복잡함.
    백엔드에서는 객체 수준 검사는 조회 조건에 넣는 것이 가장 안전해요. findById(id) 후에 소유자를 비교하는 코드는 빼먹기 쉬워요. findByIdAndOwnerId(id, currentUserId)처럼 쿼리 자체가 남의 데이터를 못 가져오게 하세요. 요청 본문은 엔티티가 아니라 허용 필드만 가진 DTO로 받아요.
    시니어 심화
    • 멀티 테넌트 격리는 개발자가 매번 조건을 붙이는 것에 맡기면 언젠가 빠져요. 테넌트 조건을 자동으로 붙이는 계층(쿼리 필터, DB의 행 수준 보안)으로 강제하고, 테넌트 간 접근을 시도하는 테스트를 자동화해요.
    • 권한 검사를 테스트로 고정하세요. 엔드포인트마다 "다른 사용자의 토큰으로 호출하면 거부되는가"를 확인하는 테스트가 없으면 리팩터링 중에 조용히 사라져요.
    • 없는 것과 금지된 것: 남의 자원에 403을 주면 그 ID가 존재한다는 사실을 알려주게 돼요. 존재 자체가 민감하면 404로 통일해요.
    • 권한 정책이 복잡해지면 코드 곳곳의 if 대신 정책을 한곳에 모아 평가하는 구조로 옮겨요. 감사와 변경이 쉬워져요.
    핵심 정리
    • 인증 ≠ 인가. 기능·객체·필드 세 수준에서 검사
    • IDOR: 소유 여부를 서버가 확인. UUID는 해결책이 아님
    • 조회 쿼리에 소유 조건, 요청은 DTO로 받아 대량 할당 방지
    셀프 체크
    1. 주문 ID를 순차 숫자에서 UUID로 바꾸면 IDOR가 해결되나요?
    답 보기

    아니요. 추측하기 어려워질 뿐이에요. UUID는 로그, URL 공유, 다른 API 응답, 브라우저 기록 등으로 노출될 수 있고, 한번 알려지면 권한 검사가 없는 한 누구나 접근할 수 있어요. 해결은 서버가 요청마다 "이 객체가 요청한 사용자의 것인가"를 확인하는 것이에요. UUID는 그 위에 얹는 보조 수단이에요.

    3부 취약점

    6장 인젝션

    데이터가 코드로 해석되는 순간

    공통 원인

    인젝션은 전부 같은 구조예요. 명령과 데이터를 한 문자열에 섞어서 해석기에 넘겼기 때문이에요. 해석기는 어디까지가 개발자가 쓴 명령이고 어디부터가 사용자 입력인지 구분할 수 없어요.

    SQL 인젝션

    // 취약: 입력이 SQL의 일부가 됨
      "SELECT * FROM users WHERE name = '" + name + "'"
      // name에  ' OR '1'='1  을 넣으면 조건이 항상 참

      // 안전: 구조와 값을 분리(바인딩)
      "SELECT * FROM users WHERE name = ?"

    바인딩은 쿼리 구조를 먼저 확정하고 값은 나중에 값으로만 전달해요. 값 안에 무엇이 있든 SQL로 해석되지 않아요. 이스케이프로 막으려는 시도는 문자셋과 문맥에 따라 뚫려요.

    바인딩할 수 없는 자리

    테이블 이름, 컬럼 이름, 정렬 방향(ORDER BY ?)은 값이 아니라 구조라서 바인딩이 안 돼요. 여기에 사용자 입력이 필요하면 허용 목록과 대조해서 미리 정해 둔 문자열만 넣어요.

    같은 원리의 다른 인젝션

    • OS 명령: 셸 문자열에 입력을 이어 붙임. 셸을 거치지 않고 인자 배열로 실행해요.
    • 템플릿: 사용자 입력을 템플릿 소스로 컴파일. 입력은 템플릿의 데이터로만 넘겨요.
    • LDAP, XPath, NoSQL 쿼리, 로그: 전부 같은 문제예요.
    백엔드에서는 JPA를 쓴다고 안전하지 않아요. JPQL이나 네이티브 쿼리를 문자열로 이어 붙이면 똑같이 뚫려요. 동적 정렬 파라미터를 그대로 ORDER BY에 넣는 코드가 가장 흔한 구멍이에요. MyBatis에서는 #{}가 바인딩이고 ${}는 문자열 치환이에요.
    시니어 심화
    • 2차 인젝션: 입력할 때는 안전하게 저장했지만, 나중에 그 값을 DB에서 꺼내 다른 쿼리에 이어 붙이면 뚫려요. "DB에서 온 값은 안전하다"는 가정이 틀린 거예요. 출처와 무관하게 쿼리는 항상 바인딩으로 만들어요.
    • 피해 범위를 줄이는 것은 DB 계정 권한이에요. 애플리케이션 계정에 DDL이나 다른 스키마 접근 권한이 없으면 인젝션이 성공해도 할 수 있는 일이 제한돼요.
    • 로그 인젝션: 입력에 줄바꿈을 넣어 가짜 로그 줄을 만들 수 있어요. 구조화 로그(JSON)로 남기면 필드 안에 갇혀요.
    • 정적 분석 도구로 문자열 결합 쿼리를 CI에서 잡아요. 사람의 리뷰에만 기대면 놓쳐요.
    핵심 정리
    • 원인 = 명령과 데이터를 한 문자열에 섞음
    • 해결 = 구조와 값을 분리(바인딩). 이스케이프에 의존하지 않음
    • 식별자·정렬 방향은 바인딩 불가 → 허용 목록
    셀프 체크
    1. 사용자가 고른 컬럼으로 정렬하는 기능을 안전하게 구현하는 방법을 설명하세요.
    답 보기

    정렬 컬럼과 방향은 SQL의 구조라서 바인딩 변수로 넣을 수 없어요. 그래서 서버에 허용하는 정렬 키 목록을 두고, 사용자 입력을 그 목록과 대조해 일치하는 항목의 미리 정의된 컬럼 이름을 쿼리에 넣어요. 예를 들어 입력 "price"를 내부의 컬럼 이름으로 매핑하는 표를 두고, 표에 없으면 기본 정렬을 쓰거나 오류를 내요. 사용자 입력 문자열이 쿼리에 직접 들어가는 경로가 없어야 해요.

    7장 XSS, CSRF, 브라우저 보안 모델

    브라우저가 지켜 주는 것과 서버가 지켜야 하는 것

    동일 출처 정책

    브라우저는 한 출처(스킴 + 호스트 + 포트)의 스크립트가 다른 출처의 응답을 읽지 못하게 막아요. 웹 보안의 바탕이에요. 그런데 이 정책은 요청을 보내는 것까지는 막지 않고, 같은 출처 안에서 실행되는 스크립트는 막지 않아요. 아래 두 공격이 각각 그 틈을 써요.

    XSS: 우리 출처에서 공격자의 스크립트가 실행됨

    사용자 입력을 HTML에 그대로 넣으면 그 안의 스크립트가 우리 사이트의 권한으로 실행돼요. 세션 탈취, 화면 조작, 사용자 대신 요청 보내기가 전부 가능해요.

    • 저장형: 게시글처럼 저장된 입력이 다른 사용자에게 보여질 때 실행.
    • 반사형: 요청에 담긴 입력이 응답에 그대로 반사.
    • DOM 기반: 프론트 코드가 입력을 위험한 방식으로 DOM에 삽입.

    방어는 출력할 때 문맥에 맞게 인코딩하는 거예요. HTML 본문, 속성, 자바스크립트, URL은 각각 규칙이 달라요. 템플릿 엔진과 프레임워크의 자동 이스케이프를 끄지 않는 것이 기본이에요.

    CSRF: 사용자의 브라우저가 공격자 대신 요청을 보냄

    브라우저는 요청에 쿠키를 자동으로 붙여요. 공격자 사이트가 우리 서버로 요청을 보내게 만들면 로그인된 사용자의 쿠키가 실려 가요. 응답은 못 읽어도 송금이나 설정 변경은 이미 실행됐어요.

    • CSRF 토큰: 서버가 준 예측 불가능한 값을 요청에 함께 보내게 해요. 공격자 사이트는 이 값을 읽을 수 없어요.
    • SameSite 쿠키: 다른 사이트에서 시작된 요청에는 쿠키를 붙이지 않게 해요.
    • 상태를 바꾸는 요청을 GET으로 만들지 않아요.
    백엔드에서는 쿠키로 인증하는 API는 CSRF 방어가 필요하고, Authorization 헤더로 토큰을 보내는 API는 브라우저가 자동으로 붙이지 않으니 CSRF 대상이 아니에요. 대신 그 토큰을 스크립트가 읽을 수 있는 곳에 두면 XSS에 노출돼요. 세션 쿠키는 HttpOnly, Secure, SameSite를 전부 설정하세요.
    시니어 심화
    • 콘텐츠 보안 정책(CSP)은 XSS의 두 번째 방어선이에요. 인라인 스크립트를 금지하고 허용한 출처의 스크립트만 실행하게 해요. 기존 서비스에 도입할 때는 보고 전용 모드로 위반을 먼저 수집해요.
    • XSS가 있으면 CSRF 방어는 무력해요. 같은 출처에서 도는 스크립트는 CSRF 토큰도 읽을 수 있어요. 우선순위는 XSS 제거예요.
    • 리치 텍스트 입력(HTML을 허용하는 에디터)은 인코딩으로 해결할 수 없어요. 검증된 HTML 정화 라이브러리로 허용 태그와 속성만 남겨요. 직접 정규식으로 거르면 뚫려요.
    • 사용자가 올린 파일은 서비스와 다른 도메인에서 제공하세요. 같은 출처에서 HTML이나 SVG로 열리면 저장형 XSS가 돼요.
    핵심 정리
    • 동일 출처 정책은 읽기를 막을 뿐 요청 전송은 막지 않음
    • XSS = 출력 시 문맥별 인코딩, 자동 이스케이프 유지
    • CSRF = 토큰 + SameSite. 쿠키 인증일 때만 해당
    셀프 체크
    1. Authorization 헤더로 토큰을 보내는 API가 CSRF에 안전한 이유와, 그 대신 생기는 위험을 설명하세요.
    답 보기

    CSRF는 브라우저가 쿠키를 자동으로 붙이는 성질을 이용해요. Authorization 헤더는 브라우저가 자동으로 붙이지 않고 우리 스크립트가 직접 넣어야 해서, 다른 사이트가 요청을 보내게 해도 토큰이 실리지 않아요. 대신 스크립트가 토큰을 읽을 수 있어야 하므로 XSS가 생기면 토큰이 그대로 유출돼요. HttpOnly 쿠키는 스크립트가 읽을 수 없으니 탈취는 어렵지만 CSRF 방어가 필요해요. 어느 쪽이든 한 가지 위험을 다른 위험과 바꾸는 선택이에요.

    8장 SSRF, 역직렬화, 파일 업로드

    서버가 공격자를 대신해 움직이게 되는 경우

    SSRF: 서버가 대신 요청을 보냄

    사용자가 준 URL을 서버가 가져오는 기능(미리보기, 웹훅, 이미지 가져오기)이 있으면, 공격자는 외부에서는 닿지 않는 주소를 넣어요. 서버는 내부망 안에 있으니 내부 관리 API, 그리고 클라우드의 인스턴스 메타데이터 주소에 접근할 수 있어요. 메타데이터에서 임시 자격 증명을 얻으면 클라우드 계정으로 번져요.

    • 가능하면 대상 호스트를 허용 목록으로 제한해요.
    • 임의 URL이 필요하면 이름을 IP로 푼 뒤 사설·루프백·링크 로컬 대역을 거부하고, 검사한 그 IP로 연결해요. 검사와 연결 사이에 이름이 다른 IP로 바뀌는 공격이 있어요.
    • 리다이렉트를 자동으로 따라가지 않거나, 따라갈 때마다 다시 검사해요.
    • 외부 요청 전용의 격리된 네트워크 경로(전용 프록시)를 쓰는 것이 가장 확실해요.

    안전하지 않은 역직렬화

    언어 내장 직렬화 형식은 "어떤 클래스의 객체를 만들지"를 데이터가 지정해요. 신뢰할 수 없는 데이터를 역직렬화하면 공격자가 클래스패스에 있는 클래스를 골라 조립해서 코드 실행까지 이어갈 수 있어요.

    • 신뢰할 수 없는 입력에 언어 내장 직렬화를 쓰지 않아요. 데이터만 표현하는 형식(JSON, Protobuf)을 써요.
    • JSON 라이브러리도 타입 정보를 데이터에서 읽어 임의 클래스를 만드는 기능을 켜면 같은 문제가 생겨요.

    파일 업로드

    • 경로 조작: 파일 이름의 ../로 의도한 디렉터리 밖에 쓰기. 사용자 파일 이름을 저장 경로에 쓰지 말고 서버가 만든 이름을 써요.
    • 형식 위장: 확장자와 Content-Type은 사용자가 정해요. 실제 내용을 확인해요.
    • 크기와 압축: 크기 상한이 없으면 디스크가 차요. 압축 파일은 풀었을 때의 크기와 파일 수도 제한해요.
    • 업로드 디렉터리에서 코드가 실행되지 않게 하고, 가능하면 객체 저장소에 둬요.
    백엔드에서는 웹훅 URL을 등록받는 기능, URL로 프로필 사진을 가져오는 기능, PDF 생성기에 HTML을 넘기는 기능이 전부 SSRF 진입점이에요. 클라우드에서는 메타데이터 서비스를 토큰이 필요한 방식으로만 동작하게 설정하고, 인스턴스 역할의 권한을 최소로 두세요.
    핵심 정리
    • SSRF: 사용자 URL을 서버가 가져오면 내부망과 메타데이터가 노출
    • 역직렬화: 데이터가 클래스를 고르는 형식을 신뢰 못 할 입력에 쓰지 않음
    • 업로드: 이름·형식·크기를 서버가 통제
    셀프 체크
    1. SSRF 방어에서 "호스트 이름을 검사한 뒤 그 이름으로 요청"하는 방식이 왜 뚫릴 수 있나요?
    답 보기

    검사할 때와 실제로 연결할 때 이름 해석이 따로 일어나기 때문이에요. 공격자가 자기 도메인의 DNS 응답을 조작해서, 검사 시점에는 공개 IP를 돌려주고 직후의 연결 시점에는 내부 IP를 돌려주게 할 수 있어요. 그래서 이름을 한 번만 풀고, 그 결과 IP를 검사한 뒤, 같은 IP로 직접 연결해야 해요. 리다이렉트도 같은 이유로 매 단계마다 다시 검사해야 해요.

    4부 운영

    9장 비밀 관리와 공급망

    코드 밖에서 뚫리는 경로

    비밀은 코드에 두지 않는다

    DB 비밀번호, API 키, 서명 키가 저장소에 들어가면 저장소를 읽을 수 있는 모든 사람과 모든 복제본, 모든 과거 커밋에 남아요. 나중에 지워도 기록에는 남아 있으니, 한 번 커밋된 비밀은 유출된 것으로 보고 교체해야 해요.

    • 비밀은 비밀 저장소(Vault, 클라우드의 시크릿 매니저)에 두고 실행 시점에 주입해요.
    • 환경 변수는 코드보다 낫지만 프로세스 목록, 크래시 덤프, 디버그 엔드포인트로 새기 쉬워요.
    • 커밋 전에 비밀을 탐지하는 훅과 저장소 스캔을 걸어 둬요.

    회전할 수 있어야 한다

    비밀은 언젠가 유출된다고 가정하고, 무중단으로 바꿀 수 있는 절차를 미리 만들어요. 새 값과 옛 값을 동시에 받아들이는 기간을 두고 넘어가는 방식이 기본이에요. 한 번도 바꿔 본 적 없는 비밀은 사고가 났을 때도 바꾸지 못해요.

    가장 좋은 것은 장기 비밀을 없애는 거예요. 워크로드의 신원으로 그때그때 짧게 사는 자격 증명을 발급받으면 유출돼도 금방 만료돼요.

    공급망

    우리가 쓴 코드보다 가져다 쓴 코드가 훨씬 많아요. 의존성의 취약점이 곧 우리 취약점이에요.

    • 버전 고정: 잠금 파일로 전이 의존성까지 고정해요. 빌드할 때마다 최신을 받으면 어제와 다른 코드가 배포돼요.
    • 취약점 스캔: 알려진 취약점이 있는 의존성을 CI에서 알려요. 알림만 쌓이면 무시하게 되니 심각도 기준과 처리 기한을 정해요.
    • 이름 혼동: 내부 패키지와 같은 이름을 공개 저장소에 올려 두는 공격이 있어요. 내부 패키지는 조회 경로를 내부 저장소로 한정해요.
    • 빌드 파이프라인도 공격 대상이에요. CI가 가진 배포 권한과 비밀은 운영 서버만큼 보호해요.
    백엔드에서는 로그는 비밀이 새는 가장 흔한 경로예요. 요청 전체를 덤프하는 디버그 로그, 예외에 실린 연결 문자열, Authorization 헤더가 그대로 남아요. 로깅 계층에서 민감 필드를 가리고, 운영 환경에서 디버그·관리용 엔드포인트가 인증 없이 열려 있지 않은지 확인하세요.
    핵심 정리
    • 비밀은 코드 밖, 비밀 저장소에서 실행 시점 주입. 커밋된 비밀은 교체
    • 무중단 회전 절차를 미리 만들고 연습
    • 의존성 고정 + 취약점 스캔 + 빌드 파이프라인 보호
    셀프 체크
    1. 실수로 API 키를 커밋했다가 바로 다음 커밋에서 지웠습니다. 무엇을 해야 하나요?
    답 보기

    키를 즉시 폐기하고 새로 발급해야 해요. 다음 커밋에서 지워도 이전 커밋에는 그대로 남아 있고, 그 사이 저장소를 받은 모든 복제본과 CI 캐시, 포크에도 있어요. 기록을 다시 써서 지우는 것은 이미 퍼진 복사본을 회수하지 못하므로 교체를 대신할 수 없어요. 교체한 뒤에는 그 키가 유효했던 기간의 사용 기록을 확인해서 악용이 있었는지 살펴봐요.

    실습

    실습 과제

    공격을 직접 해 봐야 방어가 이해돼요. 반드시 자기 로컬 환경에서만 하세요.

    • 3장 같은 비밀번호를 SHA-256과 bcrypt(비용 10, 12, 14)로 각각 해시하는 데 걸리는 시간을 재고, 초당 시도 가능 횟수를 계산
    • 4장 공개 OIDC 제공자로 인가 코드 + PKCE 흐름을 라이브러리 없이 구현. ID 토큰의 서명·iss·aud·만료를 직접 검증
    • 5장 내 프로젝트의 모든 조회·수정 엔드포인트를 표로 만들고, 다른 사용자의 토큰으로 호출했을 때 거부되는지 테스트 작성
    • 6장 문자열 결합 쿼리로 로그인 폼을 만들고 인젝션으로 우회. 바인딩으로 고친 뒤 같은 입력이 실패하는지 확인
    • 7장 자동 이스케이프를 끈 페이지에 저장형 XSS를 재현하고, CSP 헤더를 추가해 실행이 막히는지 확인
    • 8장 URL을 받아 가져오는 엔드포인트를 만들고 루프백 주소로 SSRF 재현. IP 대역 검사와 리다이렉트 처리를 추가
    • 9장 저장소 전체 기록을 비밀 탐지 도구로 스캔. 의존성 취약점 스캔을 CI에 추가
