    보안

    기준 자료: OWASP Top 10, OWASP ASVS · 3~4주

    보안은 기능이 아니라 성질이에요. 코드가 "의도한 일을 한다"는 것과 "의도하지 않은 일을 하지 않는다"는 것은 다른 문제이고, 보안은 뒤쪽을 다뤄요. 이 챕터는 백엔드 개발자가 직접 책임지는 범위(인증, 인가, 입력 처리, 비밀 관리)를 사고 사례에서 출발해 정리해요.

    예시는 쇼핑몰이에요. 회원 로그인, 주문 조회, 배송지 변경, 상품 이미지 등록 기능에서 실제로 자주 나는 사고를 따라가요. 시간이 없으면 3장(비밀번호), 5장(인가), 6장(인젝션)을 먼저 읽으세요. 실제 사고의 대부분이 이 세 곳에서 나요.

    1장 위협 모델링과 보안 원칙

    무엇을, 누구로부터, 어디서 지킬지를 먼저 정한다

    문제: "보안 점검 해 주세요"

    출시 일주일 전에 보안 점검을 요청받았어요. 무엇부터 봐야 할까요? 모든 코드를 한 줄씩 읽을 수는 없어요. 그리고 "이 서비스는 안전한가?"라는 질문에는 답할 수 없어요. 무엇으로부터 안전한지가 빠져 있기 때문이에요.

    보안에는 세 가지 목표가 있어요. 권한 없는 사람이 읽지 못하게(기밀성), 바꾸지 못하게(무결성), 그리고 필요할 때 쓸 수 있게(가용성)예요. 질문은 "누가, 무엇을 얻으려고, 어떤 경로로 공격할 때 이 셋이 지켜지는가"로 바뀌어야 답할 수 있어요. 이렇게 공격을 미리 그려 보는 일을 위협 모델링이라고 해요.

    신뢰 경계를 그린다

    위협 모델링의 핵심 도구는 데이터가 흐르는 그림 위에 신뢰 경계를 긋는 거예요. 신뢰 경계는 "이 선 너머에서 온 것은 그대로 믿을 수 없다"는 지점이에요.

    쇼핑몰에서 가장 분명한 경계는 브라우저와 API 서버 사이예요. 브라우저는 사용자의 기기에서 돌기 때문에 사용자가 마음대로 고칠 수 있어요. 숨겨 둔 입력 필드, 비활성화한 버튼, 프론트엔드의 입력 검증은 전부 우회할 수 있고, 브라우저 없이 HTTP 요청을 직접 만들어 보낼 수도 있어요. 그래서 이 경계를 넘어온 모든 것, 즉 본문, 쿼리, 헤더, 쿠키, 파일 이름은 서버가 다시 검증해야 해요.

    경계가 정해지면 경계를 넘는 지점마다 같은 질문을 던져요. 여기서 다른 사람인 척할 수 있나? 내용을 바꿀 수 있나? 엿볼 수 있나? 받은 권한보다 많은 일을 할 수 있나? 그리고 일어날 가능성과 피해 크기로 우선순위를 정해요.

    설계 원칙

    경계마다 쓰는 원칙도 정해져 있어요. 최소 권한은 필요한 권한만 필요한 동안만 주는 거예요. 주문 서비스의 DB 계정이 상품 테이블을 지울 권한까지 가질 이유가 없어요. 심층 방어는 한 겹이 뚫려도 다음 겹이 막게 하는 거예요. 입력을 검증했더라도 쿼리는 따로 안전하게 만들어요. 기본 거부는 명시적으로 허용한 것만 통과시키는 거예요. 새로 만든 엔드포인트가 아무 설정 없이 공개되면 안 돼요. 안전한 실패는 오류가 나면 닫힌 쪽으로 가는 거예요. 권한 확인 서버가 응답하지 않으면 허용이 아니라 거부해요.

    백엔드에서는 클라이언트에서 온 모든 것은 신뢰할 수 없는 입력이에요. 프론트엔드의 검증은 사용자에게 빠른 안내를 주기 위한 것이고, 보안은 서버의 검증이 책임져요. 가격, 할인율, 사용자 ID처럼 서버가 이미 알고 있거나 계산할 수 있는 값은 요청에서 받지 말고 서버가 직접 정하세요. 장바구니 요청에 담긴 "가격"을 믿는 결제 코드가 실제로 자주 사고를 내요.
    시니어 심화 위 그림에서 서비스 안쪽의 화살표에도 "인증"을 붙여 둔 이유가 있어요. 많은 시스템이 내부망을 신뢰 경계 안쪽으로 취급해서, 서비스끼리의 호출에는 인증을 생략해요.

    상황

    상품 이미지 서버는 판매자가 준 URL에서 이미지를 받아 썸네일을 만들어요. 이 서버가 쓰는 이미지 처리 라이브러리의 취약점으로 공격자가 서버에서 명령을 실행했어요. 일주일 뒤 정산팀이 출처를 알 수 없는 환불 수백 건을 발견했어요. 결제 서비스의 내부 환불 API는 "내부망에서만 호출되니까" 인증이 없었어요.

    깨지는 과정

    1. 내부 API들은 방화벽 안쪽이라는 이유로 호출자를 확인하지 않았어요. 네트워크 위치가 곧 권한이었어요.
    2. 외부와 맞닿은 서버 하나(이미지 서버)가 뚫렸어요. 이 서버는 내부망 안에 있어요.
    3. 공격자는 그 서버에서 내부망의 모든 서비스를 마음대로 호출할 수 있어요. 결제 서비스에 "이 주문을 환불해 줘"를 보내도 막을 장치가 없어요.
    4. 공격자는 이미지 서버의 로그를 지웠어요. 언제부터 무엇을 했는지 알 수 없어서, 피해 범위를 정하는 데 몇 주가 걸렸어요.

    해결책

    • 서비스마다 신원을 줘요. 서비스끼리 상호 TLS(mTLS) 인증서로 서로를 확인하거나, 서비스용 토큰(OAuth의 클라이언트 자격 증명, 4장 시니어)을 써요. 서비스 메시(Istio, Linkerd)를 쓰면 인증서 발급과 갱신을 자동으로 해 줘요. 이렇게 네트워크 위치 대신 호출마다 "누가 부르는가"를 확인하는 방식을 제로 트러스트라고 해요.
    • 받는 쪽이 호출자별로 허용해요. 결제 서비스는 "환불 API는 주문 서비스와 고객센터 서비스만 부를 수 있다"처럼 호출자별 허용 목록을 둬요. 이미지 서버는 신원이 있어도 환불을 부를 수 없어요.
    • 네트워크 분리도 함께 해요. 신원 확인이 있어도 이미지 서버에서 결제 서비스로 가는 경로 자체를 NetworkPolicy로 막아 두면, 한 겹이 뚫려도 다음 겹이 있어요(심층 방어).
    • 감사 로그는 뚫린 서버가 고칠 수 없는 곳에 둬요. 누가(사용자와 서비스), 무엇을, 언제, 결과가 어땠는지를 별도 저장소로 실시간 전송하고, 추가만 되고 수정과 삭제가 안 되게 해요(예: S3 Object Lock). 공격자가 흔적을 지울 수 있다면 사후 조사가 불가능해요.
    • 위험한 작업에는 추가 제한을 둬요. 환불처럼 돈이 나가는 API에는 건당 금액 상한, 시간당 건수 상한, 이상 패턴 알림을 둬요.

    대가: 인증서와 토큰을 발급하고 교체하는 운영이 생기고, 호출마다 검증 비용이 조금 붙어요. 서비스 메시가 이 부담을 대부분 대신해요.

    운영에서 알아채는 법

    • 서비스 간 호출 그래프를 수집해서, 평소에 없던 경로(이미지 서버에서 결제 서비스로)가 생기면 알림을 보내요.
    • 감사 로그 전송이 끊기면 알림을 보내요. 공격자가 로그 전송을 끄면, 끊긴 것 자체가 신호예요.
    핵심 정리
    • "누구로부터"가 정해져야 안전을 말할 수 있음. 기밀성·무결성·가용성
    • 신뢰 경계를 긋고, 넘는 지점마다 검증
    • 최소 권한, 심층 방어, 기본 거부, 안전한 실패
    셀프 체크
    1. 프론트엔드에서 입력을 검증하는데도 서버에서 다시 검증해야 하는 이유를 말해보세요.
    답 보기

    프론트엔드 코드는 사용자의 기기에서 실행되므로 사용자가 마음대로 고치거나 건너뛸 수 있어요. 브라우저 없이 HTTP 요청을 직접 만들어 보낼 수도 있어요. 서버가 받는 요청은 신뢰 경계 밖에서 온 것이라 서버가 직접 검증한 것만 믿을 수 있어요. 프론트엔드의 검증은 사용자에게 빠른 안내를 주기 위한 것이고 보안 장치가 아니에요.

    2장 암호화 기초

    해시, 암호화, MAC, 서명은 각각 다른 것을 보장한다

    문제: 결제 완료 알림을 어떻게 믿나

    결제 대행사가 결제가 끝나면 우리 서버로 "주문 1042 결제 완료"라는 알림을 보내요. 그런데 이 주소는 인터넷에 열려 있어서 아무나 같은 형식의 요청을 보낼 수 있어요. 결제하지 않고 "결제 완료" 요청을 보내면 상품이 발송될까요? 이 요청이 정말 결제사가 보낸 것인지, 중간에 바뀌지 않았는지 어떻게 확인할까요?

    도구마다 보장하는 것이 다르다

    암호 기술은 여러 가지이고 각자 보장하는 것이 달라요. 잘못 고르면 보호한다고 생각했는데 아무것도 보호하지 못해요.

    도구하는 일보장하는 것
    해시임의 길이 입력을 고정 길이 값으로. 되돌릴 수 없음두 내용이 같은지 비교
    대칭키 암호같은 키로 잠그고 품키 없는 사람이 못 읽음(기밀성)
    MAC비밀 키와 메시지로 확인값을 만듦바뀌지 않았고, 키를 가진 쪽이 만들었음
    공개키 암호공개키로 잠그고 개인키로 품미리 키를 나누지 않고 기밀성
    전자 서명개인키로 서명하고 공개키로 확인바뀌지 않았고, 개인키 주인이 만들었음

    결제 알림에 필요한 것은 기밀성이 아니라 "결제사가 보냈고 바뀌지 않았다"예요. 그래서 MAC이나 서명이에요.

    MAC은 결제사와 우리가 같은 비밀 키를 나눠 갖고, 결제사가 알림 본문으로 확인값을 만들어 함께 보내요. 우리는 같은 키로 다시 계산해서 비교해요. 키를 모르는 공격자는 맞는 확인값을 만들 수 없어요. 서명은 결제사만 가진 개인키로 서명하고 우리는 공개된 공개키로 확인해요. 우리는 확인만 할 수 있고 서명을 만들 수는 없어요.

    자주 혼동하는 것

    인코딩은 암호화가 아니에요. Base64는 누구나 되돌려요. JWT의 본문도 Base64일 뿐이라 누구나 읽을 수 있어요. 비밀을 넣으면 안 돼요. 암호화는 바뀌지 않았음을 보장하지 않아요. 암호문을 조작하면 풀었을 때 내용이 바뀌는데, 암호화만으로는 그 사실을 알 수 없어요. 그래서 암호화와 확인을 함께 해 주는 방식(AES-GCM 같은 인증 암호화)을 써요. 해시는 비밀을 지키지 않아요. 전화번호처럼 가능한 입력이 적으면 전부 해시해 보면 원문을 찾을 수 있어요.

    그리고 암호 알고리즘이나 그 조합을 직접 만들지 마세요. 검증된 라이브러리의 높은 수준 기능을 쓰세요. 알고리즘이 깨져서 나는 사고보다 쓰는 방법을 틀려서 나는 사고가 훨씬 많아요.

    백엔드에서는 토큰, 세션 ID, 비밀번호 재설정 코드처럼 추측되면 안 되는 값은 암호학적 난수(SecureRandom)로 만드세요. 일반 난수(Random, Math.random)는 출력 몇 개로 다음 값을 예측할 수 있어요. 그리고 결제 알림의 확인값을 비교할 때는 일반 문자열 비교 대신 걸리는 시간이 일정한 비교 함수를 써요. 일반 비교는 처음 다른 글자에서 멈추기 때문에, 응답 시간 차이로 맞는 확인값을 한 글자씩 알아낼 여지가 생겨요.
    시니어 심화 운영에서 암호의 어려움은 알고리즘이 아니라 키 관리예요. 특히 키를 바꾸는 방법이 설계에 없으면, 키가 유출돼도 대응할 수 없어요.

    상황

    제휴사에 보내는 결제 알림(웹훅)의 HMAC 서명 키가 실수로 공개 저장소에 올라갔어요. 키를 바꾸려 했는데, 키는 설정에 하나만 있고 제휴사 50곳도 그 키 하나로 검증하고 있었어요. 같은 시기에 회원 개인정보 컬럼을 암호화하는 키도 3년째 그대로라는 감사 지적을 받았어요.

    깨지는 과정

    1. 새 키로 바꾸는 순간, 이미 발송 대기열에 있던 옛 키 서명 알림과, 아직 새 키를 받지 못한 제휴사의 검증이 전부 실패해요.
    2. 그렇다고 50곳과 같은 순간에 동시에 바꿀 수는 없어요. 결국 유출된 키를 몇 주 동안 계속 써요.
    3. 개인정보 컬럼은 키를 바꾸려면 수억 행을 옛 키로 풀고 새 키로 다시 암호화해야 해요. 며칠이 걸리고 실패하면 되돌리기도 어려워서 아무도 시작하지 않아요.

    해결책

    • 키에 ID를 붙여요. 서명이나 암호문에 "어느 키로 만들었는지"(키 ID)를 함께 실어요. 받는 쪽은 여러 키를 동시에 알고 있다가 키 ID에 맞는 키로 확인해요. 교체는 세 단계예요. 받는 쪽에 새 키를 추가하고, 보내는 쪽을 새 키로 바꾸고, 옛 키로 만든 것이 더 이상 오지 않을 때 옛 키를 지워요. 어느 단계에서도 실패가 없어요.
    • 저장 데이터는 봉투 암호화로 해요. 데이터는 데이터 키로 암호화하고, 데이터 키는 상위 키로 한 번 더 암호화해서 데이터 옆에 저장해요. 상위 키는 키 관리 서비스(KMS) 안에서만 쓰이고 밖으로 나오지 않아요. 상위 키를 바꿀 때는 작은 데이터 키들만 다시 감싸면 되고, 데이터 전체를 다시 암호화할 필요가 없어요. 클라우드 KMS는 상위 키를 자동으로 교체하면서 옛 버전도 계속 복호화할 수 있게 해 줘요.
    • 키를 코드와 저장소에 두지 않아요. 키는 비밀 관리 서비스(Vault, 클라우드 Secrets Manager)에 두고 실행할 때 받아 와요. gitleaks 같은 비밀 탐지 도구를 CI와 커밋 훅에 넣어 저장소에 올라가는 것을 막아요.
    • 교체를 정기적으로 연습해요. 유출이 없어도 정해진 주기로 키를 바꿔요. 한 번도 안 해 본 교체 절차는 사고 때 동작하지 않아요.

    대가: 복호화할 때마다 KMS를 부르면 지연과 비용이 생겨요. 풀어 둔 데이터 키를 메모리에 짧게 캐시해서 호출 수를 줄여요.

    운영에서 알아채는 법

    • 키 ID별 검증 건수를 지표로 남겨요. 옛 키 사용이 0이 된 것을 확인하고 지워요.
    • 키마다 마지막 교체일을 대시보드에 두고, 정해진 주기를 넘으면 알림을 보내요.
    • 비밀 탐지 도구의 알림은 "지우면 끝"이 아니라 "이미 유출됨"으로 다뤄요. 저장소 이력에 남은 키는 반드시 교체해요.
    핵심 정리
    • 해시 = 비교, 대칭키 = 기밀성, MAC·서명 = 바뀌지 않음과 출처
    • 인코딩 ≠ 암호화, 암호화 ≠ 무결성. 인증 암호화 사용
    • 추측되면 안 되는 값은 암호학적 난수. 직접 구현 금지
    셀프 체크
    1. MAC과 전자 서명은 둘 다 내용이 바뀌지 않았음을 보장하는데, 무엇이 다른가요?
    답 보기

    MAC은 확인하는 쪽도 같은 비밀 키를 가져야 해요. 그래서 확인할 수 있는 쪽은 똑같이 만들 수도 있고, 제3자에게 "상대가 만들었다"를 증명할 수 없어요. 전자 서명은 개인키로 만들고 공개키로 확인하므로 확인하는 쪽은 위조할 수 없고, 누가 서명했는지를 제3자에게도 보일 수 있어요. 두 당사자끼리면 MAC이 빠르고 단순하고, 여러 주체가 확인해야 하거나 누가 만들었는지 증명해야 하면 서명을 써요.

    2부 인증과 인가

    3장 비밀번호 저장과 인증

    DB가 유출돼도 비밀번호는 유출되지 않게

    문제: 회원 DB가 유출됐다

    최악의 상황을 가정해 봐요. 백업 파일이 잘못 공개되어 회원 테이블이 통째로 유출됐어요. 사람들은 여러 사이트에서 같은 비밀번호를 쓰기 때문에, 우리 DB의 비밀번호가 풀리면 고객의 이메일과 은행 계정까지 위험해져요. 유출 자체는 막지 못했더라도 비밀번호만은 지킬 수 있을까요?

    암호화가 아니라 해시

    비밀번호를 암호화해서 저장하면, 키를 가진 쪽은 원래 비밀번호를 볼 수 있어요. DB와 함께 키도 유출되면 끝이에요. 그런데 서버는 원래 비밀번호를 알 필요가 없어요. 로그인할 때 입력한 값이 맞는지만 확인하면 돼요. 그래서 되돌릴 수 없는 해시로 저장하고, 로그인 때 입력값을 같은 방식으로 해시해서 비교해요.

    그냥 해시하면 금방 풀린다

    SHA-256 같은 일반 해시로 저장했다고 해 봐요. 이 해시는 빠르게 계산되도록 만들어져서, 공격자는 그래픽카드로 초당 수십억 개를 계산할 수 있어요. 흔한 비밀번호 목록을 전부 해시해서 유출된 값과 비교하면 대부분이 금방 풀려요. 게다가 같은 비밀번호는 같은 해시가 되니, 한 번 계산한 결과로 그 비밀번호를 쓰는 모든 사용자를 한꺼번에 찾아요.

    솔트와 느린 해시

    두 가지로 막아요. 첫째, 솔트예요. 사용자마다 다른 무작위 값을 만들어 비밀번호에 섞은 뒤 해시해요. 같은 비밀번호도 사용자마다 해시가 달라져서, 공격자는 사용자 한 명 한 명을 따로 공격해야 해요. 솔트는 비밀이 아니라 해시와 함께 저장해요.

    둘째, 일부러 느린 해시예요. 비밀번호 전용 해시 함수(Argon2id, bcrypt, scrypt)는 한 번 계산하는 데 수십에서 수백 밀리초가 걸리고 메모리도 많이 쓰게 만들어져 있어요. 정상 사용자는 로그인할 때 한 번만 계산하니 상관없지만, 수십억 번 대입해야 하는 공격자에게는 수천만 배 느려져요. 얼마나 느리게 할지는 비용 인자로 정해요.

    로그인 자체를 지키기

    다른 사이트에서 유출된 이메일과 비밀번호 목록을 우리 로그인에 대입하는 공격(크리덴셜 스터핑)도 막아야 해요. 이 공격은 계정마다 한두 번만 시도하기 때문에 "계정당 5회 실패하면 잠금"으로는 못 막아요. IP별, 전체 로그인 실패율 기준의 제한과 이상 탐지를 함께 써요. 그리고 "가입되지 않은 이메일입니다"와 "비밀번호가 틀렸습니다"를 따로 알려주면 가입 여부를 확인하는 도구가 되니, 같은 메시지를 줘요. 가장 확실한 방어는 다중 인증이에요. 비밀번호가 맞아도 두 번째 요소가 없으면 들어올 수 없어요.

    백엔드에서는 스프링 시큐리티의 BCryptPasswordEncoder나 Argon2PasswordEncoder가 솔트 생성과 저장 형식까지 처리해요. 직접 MessageDigest로 비밀번호를 해시하는 코드가 보이면 고쳐야 할 대상이에요. 비밀번호는 로그, 예외 메시지, 요청 덤프 어디에도 남기지 마세요. 로그인 요청 본문을 통째로 디버그 로그에 남기는 필터가 흔한 유출 경로예요.
    시니어 심화 비밀번호 정책보다 자주 뚫리는 곳이 비밀번호 재설정이에요. 재설정은 비밀번호 없이 계정을 넘겨받는 경로라서, 여기가 약하면 비밀번호 저장을 아무리 잘해도 소용없어요.

    상황

    재설정을 요청하면 6자리 숫자 코드를 메일로 보내고, 코드는 24시간 유효하며, DB에 그대로 저장했어요. 어느 날 VIP 회원 계정 수십 개가 탈취됐어요. 공격자는 비밀번호를 한 번도 맞히지 않았어요.

    깨지는 과정

    1. 6자리 숫자는 100만 가지예요. 재설정 코드 입력에 시도 횟수 제한이 없어서, 공격자가 IP를 바꿔 가며 하루 동안 전부 시도할 수 있었어요.
    2. 재설정 요청 화면이 "가입되지 않은 이메일입니다"라고 답해서, 공격자는 어떤 이메일이 가입돼 있는지 먼저 확인할 수 있었어요(계정 열거).
    3. 재설정 링크 주소를 요청의 Host 헤더로 만들고 있었어요. 공격자가 피해자 이메일로 재설정을 요청하면서 Host 헤더에 자기 도메인을 넣으면, 피해자는 진짜 메일 안에서 공격자 도메인을 가리키는 링크를 받아요. 피해자가 누르는 순간 토큰이 공격자에게 가요(네트워크 챕터 5.3 시니어와 같은 원리예요).
    4. 비밀번호를 바꾼 뒤에도 공격자가 이미 로그인해 둔 세션은 그대로 살아 있었어요.

    해결책

    • 토큰은 길고, 짧게 살고, 한 번만 써요. 링크 방식이라면 암호학적 난수로 128비트 이상(SecureRandom)을 만들고, 만료는 30분 정도, 한 번 쓰면 무효로 해요. 숫자 코드 방식이라면 시도 횟수를 코드당 5회 정도로 제한하고 넘으면 코드를 폐기해요.
    • DB에는 토큰의 해시를 저장해요. DB나 백업이 유출돼도 유효한 토큰이 넘어가지 않아요. 토큰 자체가 충분히 무작위라서 비밀번호용 느린 해시가 아니라 SHA-256이면 충분해요.
    • 계정 존재 여부를 알려 주지 않아요. 재설정 요청에는 계정이 있든 없든 "메일을 보냈어요"로 똑같이 답해요.
    • 링크 주소는 설정값으로 만들어요. 요청 헤더로 만들지 않아요.
    • 재설정이 끝나면 기존 세션과 토큰을 전부 끊어요. 그리고 "비밀번호가 바뀌었어요" 알림을 보내서, 본인이 하지 않은 변경이면 바로 알 수 있게 해요.
    • 비용 인자는 사용자 모르게 올려요. 해시 값에 알고리즘과 비용이 함께 저장돼 있으니, 로그인에 성공한 순간 옛 설정이면 입력받은 비밀번호로 새 설정의 해시를 만들어 저장해요.

    운영에서 알아채는 법

    • 계정별, IP별 재설정 요청 수와 코드 검증 실패 수를 지표로 남기고, 급증하면 알림을 보내요.
    • 재설정 직후 평소와 다른 국가나 기기에서 로그인하는 패턴을 탐지해요.
    • 재설정 메일 링크의 도메인이 우리 도메인이 아닌 경우가 로그에 있다면 Host 헤더 공격 시도예요.
    핵심 정리
    • 비밀번호 = 솔트 + 비밀번호 전용 느린 해시(Argon2id, bcrypt)
    • 일반 해시(SHA 계열)는 공격자에게도 빨라서 금방 풀림
    • 시도 제한 + 같은 오류 메시지 + 다중 인증. 재설정 경로도 같은 수준으로
    셀프 체크
    1. 솔트를 해시와 같은 테이블에 평문으로 저장해도 되는 이유는 무엇인가요?
    답 보기

    솔트의 목적은 비밀을 지키는 것이 아니라 같은 비밀번호가 사용자마다 다른 해시가 되게 하는 거예요. 공격자가 솔트를 알아도 사용자마다 따로 대입 공격을 해야 하고, 미리 계산해 둔 표를 쓸 수 없어요. 대입 공격 자체를 느리게 만드는 것은 솔트가 아니라 느린 해시 함수의 역할이에요.

    4장 OAuth 2.0과 OpenID Connect

    비밀번호를 넘기지 않고 권한을 위임하고, 로그인한다

    문제: 다른 서비스의 권한을 빌려 쓰고 싶다

    쇼핑몰에 "구글 캘린더에 배송 예정일 추가" 기능을 넣으려고 해요. 사용자의 캘린더에 쓰려면 권한이 필요한데, 사용자에게 구글 비밀번호를 달라고 할 수는 없어요. 비밀번호를 받으면 우리 서버가 그 사용자의 구글 계정 전체를 쓸 수 있게 되고, 사용자가 권한을 거두려면 비밀번호를 바꾸는 수밖에 없어요.

    OAuth 2.0: 범위가 정해진 토큰을 발급받는다

    OAuth 2.0은 비밀번호 대신 할 수 있는 일의 범위가 정해져 있고 언제든 취소할 수 있는 토큰을 발급받는 방식이에요. 등장인물은 넷이에요. 권한의 주인인 사용자, 권한을 받으려는 클라이언트(우리 쇼핑몰 서버), 사용자를 확인하고 토큰을 발급하는 인가 서버(구글 로그인), 토큰을 받고 API를 제공하는 리소스 서버(구글 캘린더 API)예요.

    인가 코드 흐름

    사용자가 "캘린더 연결"을 누르면 우리 서버는 사용자의 브라우저를 구글로 보내요. 이때 원하는 권한 범위와 돌아올 주소, 그리고 state라는 무작위 값을 함께 실어요. 사용자는 구글에서 직접 로그인하고 "이 쇼핑몰이 캘린더에 쓰는 것을 허용"에 동의해요. 비밀번호는 구글에만 입력되고 우리는 보지 못해요.

    구글은 브라우저를 우리 주소로 돌려보내면서 일회용 코드를 붙여요. 우리 서버는 이 코드를 받아, 브라우저를 거치지 않고 서버끼리 직접 구글에 보내서 액세스 토큰으로 바꿔요. 토큰을 브라우저 주소로 바로 주지 않고 코드를 한 번 거치는 이유는, 브라우저 주소는 기록과 로그에 남아 노출되기 쉽기 때문이에요. 코드만으로는 토큰을 얻을 수 없도록 교환할 때 우리 서버의 비밀이나 검증값을 함께 내요. 비밀을 안전하게 둘 수 없는 모바일 앱이나 브라우저 앱은 PKCE라는 방식으로, 요청할 때 만든 값을 교환할 때 증명해요.

    OAuth는 인가, OIDC는 인증

    여기서 자주 하는 실수가 있어요. "구글로 로그인" 기능을 액세스 토큰으로 만드는 거예요. 액세스 토큰은 "이 토큰으로 캘린더에 쓸 수 있다"만 말하고, "이 사람이 누구인가"는 말하지 않아요. 그 토큰이 우리 서비스를 위해 발급됐다는 보장도 없어요. 다른 서비스를 위해 발급된 토큰을 공격자가 가져와 내밀 수도 있어요.

    로그인에는 OAuth 위에 사용자 확인을 더한 OpenID Connect(OIDC)를 써요. OIDC는 토큰 교환 때 사용자 정보가 담긴 ID 토큰을 함께 줘요. ID 토큰은 서명된 JWT이고, 누가 발급했는지(iss), 누구를 위해 발급됐는지(aud), 언제 만료되는지가 들어 있어요.

    백엔드에서는 "구글로 로그인"을 직접 구현한다면 ID 토큰을 받아 네 가지를 확인하세요. 서명이 맞는지, iss가 구글인지, aud가 우리 앱의 클라이언트 ID인지, 만료되지 않았는지. aud를 확인하지 않으면 다른 앱을 위해 발급된 토큰으로 우리 서비스에 로그인할 수 있어요. 가능하면 직접 구현하지 말고 검증된 라이브러리(스프링 시큐리티의 OAuth2 클라이언트)를 쓰세요.
    시니어 심화 OAuth 흐름 중 브라우저를 거치는 단계가 공격 지점이에요. 그리고 서비스끼리 토큰을 넘길 때도 흔한 실수가 있어요.

    상황 1: 돌아올 주소를 넓게 허용

    구글 로그인을 붙이면서 인가 서버에 돌아올 주소를 https://shop.example.com/*로 등록했어요. 여러 화면에서 로그인 후 원래 페이지로 돌아가게 하려고요.

    1. 쇼핑몰에는 /redirect?to=...처럼 다른 주소로 보내 주는 페이지가 있었어요.
    2. 공격자는 돌아올 주소를 https://shop.example.com/redirect?to=공격자사이트로 바꾼 로그인 링크를 피해자에게 보내요. 등록 규칙에 맞으니 인가 서버가 통과시켜요.
    3. 피해자가 로그인하면 인가 코드가 붙은 채로 그 주소로 돌아오고, 다시 공격자 사이트로 넘어가요. 공격자가 코드를 가져가요.

    해결: 돌아올 주소는 완전히 일치하는 주소만 등록해요. 로그인 후 원래 페이지로 돌아가는 것은 state에 담거나 세션에 저장해서 처리해요. 그리고 PKCE를 써요. 흐름을 시작할 때 만든 비밀 값을 토큰 교환 때 증명해야 해서, 코드만 가로채서는 토큰을 받을 수 없어요. OAuth 2.1 초안은 기밀 클라이언트까지 포함해 사실상 모든 클라이언트에 PKCE를 요구해요.

    상황 2: state 확인이 없음

    1. 공격자가 자기 구글 계정으로 로그인 흐름을 시작해서 인가 코드를 받아요. 그리고 그 코드가 붙은 돌아올 주소를 피해자가 열게 만들어요(이미지 태그, 링크).
    2. state 확인이 없으면 쇼핑몰은 이 요청을 정상으로 처리하고, 피해자의 쇼핑몰 계정에 공격자의 구글 계정을 연결해요.
    3. 이제 공격자는 자기 구글 계정으로 피해자의 쇼핑몰 계정에 로그인할 수 있어요. 피해자가 그 뒤에 저장하는 주소와 카드 정보까지 보여요.

    해결: 흐름을 시작할 때 무작위 state를 만들어 사용자 세션에 묶어 두고, 돌아왔을 때 같은지 확인해요. 다르면 거부해요. 계정 연결 같은 민감한 동작은 연결 직전에 사용자에게 한 번 더 확인받아요.

    상황 3: 사용자 토큰을 뒤로 넘김

    주문 서비스가 사용자의 액세스 토큰을 그대로 재고, 결제, 포인트 서비스에 넘겨요. 그러면 그 토큰은 모든 서비스에서 유효해야 하고, 어느 한 서비스의 로그에 토큰이 남으면 다른 모든 서비스를 호출할 수 있어요.

    해결: 서비스끼리 호출할 때는 클라이언트 자격 증명 방식으로 서비스 자신의 토큰을 받아요. 사용자 정보가 필요하면 토큰 교환(token exchange)으로 대상 서비스 전용의 좁은 토큰을 새로 받아요. 받는 서비스는 토큰의 대상(aud)이 자기인지 반드시 확인해요.

    운영에서 알아채는 법

    • 등록되지 않은 돌아올 주소로 시도된 요청과 state 불일치 건수를 지표로 남겨요. 꾸준히 있다면 누군가 공격을 시도하고 있어요.
    • 서비스마다 aud 검증 실패 건수를 봐요. 다른 서비스용 토큰이 들어온다면 토큰이 엉뚱한 곳으로 흘러가고 있어요.
    핵심 정리
    • OAuth 2.0 = 범위가 정해지고 취소 가능한 토큰으로 권한 위임
    • 인가 코드 흐름: 코드는 브라우저로, 토큰은 서버끼리. 공개 클라이언트는 PKCE
    • 로그인은 OIDC의 ID 토큰으로. 서명·iss·aud·만료 확인
    셀프 체크
    1. 인가 코드 흐름에서 토큰을 바로 주지 않고 코드를 한 번 거치는 이유는 무엇인가요?
    답 보기

    인가 서버가 사용자를 클라이언트로 돌려보내는 단계는 브라우저 주소를 통해 일어나서, 거기에 실린 값은 브라우저 기록, 서버 로그, 중간 스크립트에 노출될 수 있어요. 그래서 그 경로에는 짧게 살고 한 번만 쓸 수 있는 코드만 싣고, 실제 토큰은 클라이언트 서버가 인가 서버와 직접 통신해서 받아요. 이때 클라이언트 비밀이나 PKCE 검증값을 함께 내야 하므로 코드만 가로채서는 토큰을 얻을 수 없어요.

    5장 인가 — 접근 제어

    로그인했다는 것과 이 데이터를 볼 수 있다는 것은 다르다

    문제: 주소의 숫자를 바꿨더니 남의 주문이 보인다

    고객 문의가 들어왔어요. 내 주문 상세 페이지 주소가 /orders/1042인데, 호기심에 1043으로 바꿔 봤더니 다른 사람의 이름, 주소, 전화번호가 담긴 주문이 보였다는 거예요. 로그인은 분명히 확인하고 있었어요. 무엇이 빠졌을까요?

    인증과 인가는 다른 질문이다

    인증은 "당신은 누구인가"를, 인가는 "당신이 이것을 해도 되는가"를 묻는 거예요. 위 코드는 인증만 했어요. 요청한 사람이 로그인한 회원인지는 확인했지만, 1043번 주문이 그 회원의 것인지는 확인하지 않았어요.

    이런 취약점을 IDOR(안전하지 않은 직접 객체 참조)라고 해요. 실제 사고에서 가장 흔한 유형이에요. 주문 번호를 추측하기 어려운 UUID로 바꾸면 해결될 것 같지만 아니에요. UUID도 공유된 링크, 로그, 다른 API의 응답을 통해 알려질 수 있고, 알려지면 권한 검사가 없는 한 누구나 볼 수 있어요. 추측을 어렵게 하는 것은 보조 수단이고, 해결은 서버가 요청마다 소유 여부를 확인하는 거예요.

    세 수준에서 확인한다

    권한은 세 수준에서 확인해야 해요. 기능 수준은 이 역할이 이 기능을 쓸 수 있는가예요. 일반 회원이 관리자 API를 호출할 수 없어야 해요. 객체 수준은 위의 문제예요. 이 회원이 이 특정 주문에 접근할 수 있는가. 필드 수준은 이 객체의 이 필드를 읽거나 바꿀 수 있는가예요.

    필드 수준의 대표적인 사고가 대량 할당이에요. 회원 정보 수정 API가 요청 본문을 회원 엔티티에 통째로 넣는다고 해 봐요. 사용자가 본문에 "grade": "VIP"나 "role": "ADMIN"을 끼워 넣으면 그 필드까지 바뀌어요. 화면에 그런 입력 칸이 없어도 요청은 직접 만들 수 있으니까요.

    권한 모델

    간단한 서비스는 역할에 권한을 묶고 사용자에게 역할을 주는 RBAC(역할 기반)로 충분해요. "같은 판매자의 상품만, 판매 중인 것만 수정 가능"처럼 사용자, 자원, 상황의 속성을 조합해야 하면 ABAC(속성 기반)를 써요. 유연하지만 규칙이 복잡해지니 한곳에 모아 관리해야 해요.

    백엔드에서는 객체 수준 확인은 조회 조건에 넣는 것이 가장 안전해요. findById(id)로 가져온 뒤 소유자를 비교하는 코드는 빠뜨리기 쉬워요. findByIdAndMemberId(id, currentMemberId)처럼 쿼리 자체가 남의 데이터를 가져오지 못하게 하세요. 그리고 요청 본문은 엔티티가 아니라 수정을 허용하는 필드만 가진 DTO로 받으세요.
    시니어 심화 권한 확인은 처음 만들 때보다 리팩터링하면서 사라지는 경우가 많아요. 코드에 "없는 것"은 리뷰에서 눈에 띄지 않기 때문이에요.

    상황

    판매자 정산 API를 리팩터링하면서 여러 조회 메서드를 settlementRepository.findById(id) 하나로 공통화했어요. 원래 메서드에 있던 AND seller_id = ? 조건이 이 과정에서 빠졌어요. 정산 ID는 순서대로 증가하는 숫자였어요. 석 달 뒤 한 판매자가 ID를 바꿔 가며 경쟁 판매자의 매출을 보고 있었다는 것이 드러났어요.

    깨지는 과정

    1. 리팩터링 PR은 "중복 제거"였고, 테스트는 모두 통과했어요. 기존 테스트는 "자기 정산을 조회하면 성공"만 확인했어요.
    2. 리뷰어는 바뀐 코드를 봤지만, 사라진 한 줄의 조건은 눈에 띄지 않았어요.
    3. API는 로그인한 판매자인지만 확인했어요(인증). 그 정산이 이 판매자의 것인지는 확인하지 않았어요(인가).
    4. 순차 ID라 다른 판매자의 정산을 찾기도 쉬웠어요. 다만 UUID였더라도 ID가 어딘가 노출되면 같은 일이 생기니, ID를 숨기는 것은 해결책이 아니에요.

    해결책

    • 권한을 테스트로 고정해요. 엔드포인트마다 "다른 회원(판매자)의 토큰으로 호출하면 거부되는가"를 확인하는 테스트를 둬요. 성공 경로만이 아니라 실패해야 하는 경로를 테스트해요.
    • 빠진 엔드포인트를 기계가 찾게 해요. 스프링이라면 등록된 모든 엔드포인트 목록을 꺼내서, 권한 테스트 목록에 없는 엔드포인트가 있으면 실패하는 메타 테스트를 둬요. 새 API를 추가하면 권한 테스트도 추가할 수밖에 없게 돼요.
    • 멀티 테넌트라면 조건을 강제해요. 여러 판매자나 기업 고객의 데이터를 한 DB에 둔다면, 개발자가 매번 테넌트 조건을 붙이는 것에 맡기지 않아요. Hibernate의 필터나 @TenantId로 모든 쿼리에 자동으로 조건이 붙게 하거나, PostgreSQL의 행 단위 보안(PostgreSQL 챕터)으로 DB가 직접 막게 해요.
    • 존재 여부도 숨겨요. 남의 자원에 403을 주면 "그 번호의 정산이 존재한다"는 사실을 알려줘요. 존재 자체가 민감하면 404로 통일해요.

    운영에서 알아채는 법

    • 계정별 403, 404 응답 수를 지표로 남겨요. 한 계정에서 급증하면 남의 자원을 찾고 있을 수 있어요.
    • 한 계정이 짧은 시간에 연속된 ID를 차례로 조회하는 패턴을 탐지해요. 정상 사용에서는 거의 나오지 않는 모양이에요.
    • 권한 관련 코드(조회 조건, 필터)를 바꾸는 PR에는 보안 담당자 리뷰를 필수로 걸어요.
    핵심 정리
    • 인증 ≠ 인가. 기능·객체·필드 세 수준에서 확인
    • IDOR: 서버가 요청마다 소유 여부를 확인. UUID는 해결책이 아님
    • 조회 쿼리에 소유 조건, 요청은 DTO로 받아 대량 할당 방지
    셀프 체크
    1. 주문 ID를 순차 숫자에서 UUID로 바꾸면 IDOR가 해결되나요?
    답 보기

    아니요. 추측하기 어려워질 뿐이에요. UUID는 공유된 링크, 로그, 다른 API 응답, 브라우저 기록을 통해 알려질 수 있고, 한번 알려지면 권한 검사가 없는 한 누구나 접근할 수 있어요. 해결은 서버가 요청마다 "이 주문이 요청한 회원의 것인가"를 확인하는 거예요. UUID는 그 위에 얹는 보조 수단이에요.

    6장 인젝션

    입력한 데이터가 명령으로 해석되는 순간

    문제: 로그인 화면에 이상한 문자열을 넣었더니 통과됐다

    관리자 로그인 화면의 아이디 칸에 admin' --를 넣었더니 비밀번호 없이 로그인됐어요. 코드를 보니 이렇게 돼 있었어요.

    String sql = "SELECT * FROM admins WHERE id = '" + id + "' AND pw = '" + pw + "'";

    입력이 그대로 SQL 문자열에 이어 붙여지면, 완성된 SQL은 이렇게 돼요.

    SELECT * FROM admins WHERE id = 'admin' --' AND pw = '...'

    --는 SQL의 주석이라 그 뒤의 비밀번호 조건이 통째로 무시돼요.

    원인: 명령과 데이터를 한 문자열에 섞었다

    모든 인젝션은 같은 구조예요. 개발자가 쓴 명령과 사용자가 넣은 데이터를 하나의 문자열로 합쳐서 해석기에 넘겼기 때문이에요. DB는 받은 문자열에서 어디까지가 개발자의 명령이고 어디부터가 사용자의 데이터인지 구분할 방법이 없어요. 데이터 안에 따옴표가 있으면 그것을 문자열의 끝으로 읽어요.

    해결: 구조와 값을 따로 보낸다

    해결은 둘을 처음부터 따로 보내는 거예요. 이것을 바인딩(준비된 문장)이라고 해요.

    String sql = "SELECT * FROM admins WHERE id = ? AND pw_hash = ?";
      // 쿼리 구조를 먼저 확정하고, 값은 나중에 값으로만 전달

    DB는 ? 자리가 들어간 쿼리 구조를 먼저 해석해서 확정해요. 그 뒤에 들어오는 값은 무엇이 들어 있든 그 자리의 값으로만 다뤄요. 따옴표도 주석 기호도 그냥 문자예요. 특수 문자를 이스케이프해서 막으려는 시도는 문자 인코딩이나 문맥에 따라 뚫리는 경우가 있어서 근본 해결이 아니에요.

    바인딩할 수 없는 자리

    상품 목록을 사용자가 고른 기준으로 정렬하는 기능을 생각해 봐요. ORDER BY ?는 동작하지 않아요. 컬럼 이름과 정렬 방향은 값이 아니라 쿼리의 구조이기 때문이에요. 그래서 개발자가 사용자의 입력을 그대로 ORDER BY 뒤에 붙이고, 그곳이 뚫려요. 이런 자리는 허용 목록으로 처리해요. 입력 "price"를 미리 정해 둔 컬럼 이름으로 바꾸는 표를 두고, 표에 없는 값이면 기본 정렬을 써요. 사용자 입력이 쿼리에 직접 들어가는 경로가 없어야 해요.

    같은 원리가 SQL 밖에서도 적용돼요. 입력을 셸 명령 문자열에 붙이면 OS 명령 인젝션, 템플릿 소스에 붙이면 템플릿 인젝션이에요. 해결도 같아요. 셸을 거치지 않고 인자를 배열로 넘기고, 입력은 템플릿의 데이터로만 넘겨요.

    백엔드에서는 JPA를 쓴다고 안전하지 않아요. JPQL이나 네이티브 쿼리를 문자열로 이어 붙이면 똑같이 뚫려요. 검색 조건이 많은 화면에서 동적 쿼리를 문자열로 조립하는 코드가 가장 흔한 구멍이에요. QueryDSL이나 Criteria처럼 값을 바인딩하는 도구를 쓰세요. MyBatis에서는 #{}가 바인딩이고 ${}는 문자열을 그대로 붙여요. ${}가 보이면 허용 목록 처리가 되어 있는지 확인하세요.
    시니어 심화 "DB에서 꺼낸 값은 안전하다"는 가정이 2차 인젝션을 만들어요. 입력할 때는 안전하게 저장된 값이, 나중에 다른 곳에서 쿼리에 이어 붙여질 때 실행돼요.

    상황

    회원 가입 API는 닉네임을 바인딩으로 안전하게 저장해요. 몇 달 뒤 관리자용 "닉네임별 주문 통계" 배치가 추가됐어요. 이 배치는 닉네임을 DB에서 읽어 "... WHERE nickname = '" + nickname + "'"로 쿼리를 만들었어요. 어느 날 통계 배치가 회원 테이블 전체를 외부로 내보내는 쿼리를 실행했어요.

    깨지는 과정

    1. 공격자가 닉네임을 x' UNION SELECT ... -- 같은 문자열로 가입했어요. 가입 API는 바인딩을 쓰니 이 문자열이 그대로 저장될 뿐 아무 일도 일어나지 않았어요.
    2. 통계 배치는 "우리 DB에서 꺼낸 값"이라 안전하다고 보고 문자열을 이어 붙였어요.
    3. 그 순간 저장돼 있던 공격 문자열이 쿼리의 일부로 실행됐어요.
    4. 입력 시점에는 아무 문제가 없었으니, 입력 검증 로그를 아무리 봐도 흔적이 없어요. 공격 문자열이 저장된 시점과 실행된 시점이 몇 달 떨어져 있어서 찾기도 어려워요.

    해결책

    • 값이 어디서 왔든 쿼리는 항상 바인딩으로 만들어요. 출처로 안전을 판단하지 않아요. JPA라면 :param, MyBatis라면 #{}를 쓰고 ${}는 쓰지 않아요. ${}는 값을 문자열로 그대로 끼워 넣어요.
    • 바인딩할 수 없는 부분은 허용 목록으로 해요. 정렬 컬럼, 정렬 방향, 테이블 이름은 바인딩이 안 돼요. 사용자가 고른 값을 미리 정한 목록과 비교해서 목록에 있는 값만 써요.
    • DB 계정 권한을 최소로 줘요. 애플리케이션 계정은 필요한 테이블의 읽기와 쓰기만 하고, 테이블 구조 변경이나 다른 스키마 조회, 파일 쓰기 권한은 없게 해요. 통계 배치처럼 읽기만 하는 작업은 읽기 전용 계정으로 돌려요. 인젝션이 성공해도 할 수 있는 일이 제한돼요.
    • 문자열 결합 쿼리는 CI에서 잡아요. Semgrep, SpotBugs(Find Security Bugs) 같은 정적 분석 도구로 쿼리 문자열에 변수를 이어 붙이는 코드를 찾아 빌드를 실패시켜요. 사람의 리뷰만으로는 놓쳐요.

    운영에서 알아채는 법

    • DB의 SQL 문법 오류 로그를 지표로 남겨요. 인젝션을 탐색하는 공격자는 문법 오류를 많이 만들어요. 평소 0에 가까운 값이 튀면 의심해요.
    • 애플리케이션 계정이 평소에 실행하지 않는 종류의 쿼리(information_schema 조회, UNION이 들어간 쿼리)를 DB 감사 로그로 탐지해요.
    핵심 정리
    • 원인 = 명령과 데이터를 한 문자열에 섞어 해석기에 넘김
    • 해결 = 구조와 값을 분리(바인딩). 이스케이프에 기대지 않음
    • 컬럼 이름·정렬 방향은 바인딩 불가 → 허용 목록
    셀프 체크
    1. 사용자가 고른 컬럼으로 정렬하는 기능을 안전하게 구현하는 방법을 설명하세요.
    답 보기

    정렬 컬럼과 방향은 SQL의 구조라서 바인딩 변수로 넣을 수 없어요. 그래서 서버에 허용하는 정렬 키 목록을 두고, 사용자 입력을 그 목록과 대조해 일치하는 항목에 대응하는 미리 정의된 컬럼 이름을 쿼리에 넣어요. 예를 들어 입력 "price"를 내부 컬럼 이름으로 바꾸는 표를 두고, 표에 없으면 기본 정렬을 쓰거나 오류를 내요. 사용자 입력 문자열이 쿼리에 직접 들어가는 경로가 없어야 해요.

    7장 XSS, CSRF, 브라우저 보안 모델

    브라우저가 지켜 주는 것과 서버가 지켜야 하는 것

    문제: 상품 후기를 열었더니 배송지가 바뀌었다

    두 가지 사고가 같은 주에 접수됐어요. 하나는 어떤 상품 후기를 연 사용자들의 계정에서 이상한 주문이 나간 것이고, 다른 하나는 수상한 이벤트 페이지를 방문한 사용자들의 배송지가 바뀐 거예요. 둘 다 사용자는 쇼핑몰에 로그인한 상태였어요.

    브라우저의 기본 규칙: 동일 출처 정책

    브라우저는 한 출처(스킴 + 호스트 + 포트)의 스크립트가 다른 출처의 응답을 읽지 못하게 막아요. 이벤트 페이지의 스크립트는 쇼핑몰 API의 응답을 읽을 수 없어요. 웹 보안의 바탕이 되는 규칙이에요. 그런데 이 규칙에는 두 가지 틈이 있고, 위의 두 사고가 각각 그 틈을 썼어요.

    XSS: 우리 출처에서 공격자의 스크립트가 돈다

    첫 번째 틈은 동일 출처 정책이 같은 출처 안에서 도는 스크립트는 막지 않는다는 거예요. 후기 본문에 <script>가 들어 있었는데, 서버가 그 본문을 HTML에 그대로 넣어 내보냈어요. 다른 사용자가 그 후기를 열면 스크립트가 쇼핑몰의 출처로 실행돼요. 쇼핑몰 화면을 조작하고, 사용자 대신 주문 API를 호출할 수 있어요. 이것이 XSS(크로스 사이트 스크립팅)예요.

    방어는 출력할 때 문맥에 맞게 인코딩하는 거예요. HTML 본문에 넣을 때는 <를 &lt;로 바꾸는 식이에요. HTML 속성, 자바스크립트 안, URL 안은 규칙이 각각 달라요. 템플릿 엔진과 프론트엔드 프레임워크는 기본으로 이 인코딩을 해 주니, 그 기본 기능을 끄는 코드(innerHTML, th:utext, dangerouslySetInnerHTML)가 검토 대상이에요.

    CSRF: 사용자의 브라우저가 공격자 대신 요청을 보낸다

    두 번째 틈은 동일 출처 정책이 요청을 보내는 것 자체는 막지 않는다는 거예요. 응답을 못 읽을 뿐이에요.

    이벤트 페이지에는 쇼핑몰의 배송지 변경 주소로 자동 제출되는 숨은 폼이 있었어요. 브라우저는 쇼핑몰로 가는 요청에 쇼핑몰 쿠키를 자동으로 붙여요. 로그인 세션 쿠키도요. 서버가 보기에는 정상적으로 로그인한 사용자의 요청이에요. 이벤트 페이지는 응답을 읽지 못하지만, 배송지는 이미 바뀌었어요. 이것이 CSRF(크로스 사이트 요청 위조)예요.

    방어는 두 가지예요. CSRF 토큰은 서버가 폼마다 예측할 수 없는 값을 넣어 주고 요청에 그 값이 함께 와야 처리하는 방식이에요. 다른 출처의 페이지는 그 값을 읽을 수 없어서 맞는 요청을 만들지 못해요. SameSite 쿠키 속성은 다른 사이트에서 시작된 요청에 쿠키를 붙이지 않게 해요. 그리고 상태를 바꾸는 요청을 GET으로 만들지 마세요. 이미지 태그 하나로도 GET 요청은 보내져요.

    백엔드에서는 쿠키로 인증하는 API는 CSRF 방어가 필요하고, Authorization 헤더에 토큰을 넣는 API는 브라우저가 자동으로 붙이지 않으니 CSRF 대상이 아니에요. 대신 그 토큰을 스크립트가 읽을 수 있는 곳(로컬 스토리지)에 두면 XSS 한 번에 토큰이 통째로 유출돼요. 세션 쿠키에는 HttpOnly(스크립트가 못 읽음), Secure(HTTPS에서만), SameSite를 모두 설정하세요.
    시니어 심화 XSS와 CSRF 중 무엇이 먼저인지는 분명해요. XSS가 있으면 CSRF 방어는 무력해요. 그래서 XSS 제거가 최우선이고, 그다음에 XSS가 남아 있을 때의 피해를 줄이는 두 번째 방어선을 둬요.

    상황

    상품 후기에 굵게, 기울임, 링크를 쓸 수 있는 에디터를 붙였어요. 서버는 정규식으로 <script> 태그를 지워서 저장했어요. CSRF 토큰과 SameSite 쿠키도 적용돼 있었어요. 그런데 인기 상품 후기를 연 사용자들의 배송지가 공격자 주소로 바뀌는 일이 생겼어요.

    깨지는 과정

    1. 공격자는 <img src=x onerror="...">처럼 script 태그가 없는 방법으로 스크립트를 넣었어요. 정규식 필터는 이것을 통과시켰어요.
    2. 후기를 연 사용자의 브라우저에서 그 스크립트가 쇼핑몰과 같은 출처로 실행돼요.
    3. 같은 출처의 스크립트는 페이지에 들어 있는 CSRF 토큰을 읽을 수 있어요. SameSite 쿠키도 같은 사이트의 요청이니 그대로 붙어요.
    4. 스크립트가 CSRF 토큰을 붙여 "배송지 변경" 요청을 보내요. 서버가 보기에는 사용자가 직접 보낸 정상 요청과 구별되지 않아요.

    해결책

    • HTML 서식을 허용한다면 검증된 정화 라이브러리를 써요. 인코딩하면 서식이 사라지니, 허용한 태그와 속성만 남기고 나머지를 지우는 정화가 필요해요. 서버에서는 OWASP Java HTML Sanitizer, 브라우저에서는 DOMPurify 같은 검증된 라이브러리를 써요. 정규식으로 직접 걸러내면 반드시 뚫려요. 이벤트 속성, javascript: 링크, 인코딩을 섞은 우회 방법이 수없이 많아요.
    • 두 번째 방어선으로 콘텐츠 보안 정책(CSP)을 둬요. 응답 헤더로 "이 페이지는 이 출처의 스크립트만 실행하고, 인라인 스크립트와 이벤트 속성은 실행하지 않는다"를 선언하면, 후기에 스크립트가 끼어들어도 브라우저가 실행하지 않아요. 페이지마다 무작위 값(nonce)을 만들어 우리 스크립트에만 붙이는 방식이 가장 효과적이에요.
    • CSP는 보고 모드로 먼저 켜요. 기존 서비스에 바로 적용하면 정상 기능이 깨져요. Content-Security-Policy-Report-Only로 위반을 차단하지 않고 보고만 받아서, 위반 목록을 정리한 뒤 차단 모드로 바꿔요.
    • 중요한 동작에는 재확인을 둬요. 배송지 변경, 결제 수단 변경, 비밀번호 변경은 비밀번호 재입력이나 추가 인증을 요구해요. XSS가 있어도 스크립트가 이 단계를 넘기 어려워요.
    • 세션 쿠키는 HttpOnly로 둬요. 스크립트가 쿠키 값을 읽어 가는 것은 막아요. 다만 위 예처럼 스크립트가 사용자 대신 요청을 보내는 것은 막지 못하니, 이것만으로는 부족해요.

    운영에서 알아채는 법

    • CSP 위반 보고를 수집하는 엔드포인트를 두고 건수를 지표로 남겨요. 평소에 없던 출처나 인라인 스크립트 위반이 특정 페이지에서 급증하면 XSS가 들어온 거예요.
    • 배송지, 결제 수단 같은 민감 정보의 변경 건수를 시간대별로 봐요. 평소보다 튀면 계정 탈취나 XSS를 의심해요.
    핵심 정리
    • 동일 출처 정책은 다른 출처의 응답 읽기를 막을 뿐, 요청 전송과 같은 출처의 스크립트는 막지 않음
    • XSS = 출력할 때 문맥별 인코딩, 프레임워크의 자동 이스케이프를 끄지 않음
    • CSRF = 쿠키 자동 첨부를 이용. 토큰 + SameSite
    셀프 체크
    1. Authorization 헤더로 토큰을 보내는 API가 CSRF에 안전한 이유와, 그 대신 생기는 위험을 설명하세요.
    답 보기

    CSRF는 브라우저가 쿠키를 자동으로 붙이는 성질을 이용해요. Authorization 헤더는 브라우저가 자동으로 붙이지 않고 우리 스크립트가 직접 넣어야 하므로, 다른 사이트가 요청을 보내게 만들어도 토큰이 실리지 않아요. 대신 스크립트가 토큰을 읽을 수 있어야 해서 XSS가 생기면 토큰이 그대로 유출돼요. HttpOnly 쿠키는 스크립트가 읽을 수 없어 탈취가 어렵지만 CSRF 방어가 필요해요. 어느 쪽이든 한 가지 위험을 다른 위험과 바꾸는 선택이에요.

    8장 SSRF, 역직렬화, 파일 업로드

    서버가 공격자를 대신해 움직이게 되는 경우

    문제: 이미지 주소 하나로 클라우드 계정이 넘어갔다

    판매자가 상품 이미지를 올릴 때 파일 대신 이미지 주소를 입력할 수 있게 했어요. 서버가 그 주소에서 이미지를 받아 저장해요. 어느 날 판매자 한 명이 이미지 주소에 http://169.254.169.254/...를 넣었어요. 이 주소는 클라우드 서버 안에서만 접근할 수 있는 인스턴스 메타데이터 서비스의 주소이고, 그 서버에 부여된 임시 자격 증명을 돌려줘요. 서버는 성실하게 그 응답을 받아 "이미지"로 저장했고, 판매자는 그 파일을 내려받아 클라우드 자격 증명을 얻었어요.

    SSRF: 서버가 대신 요청을 보낸다

    이것을 SSRF(서버 측 요청 위조)라고 해요. 서버는 내부망 안에 있어서, 외부에서는 닿지 않는 곳(메타데이터 서비스, 내부 관리 API, DB 관리 화면)에 접근할 수 있어요. 사용자가 준 주소를 서버가 가져오는 기능은 전부 이 통로가 될 수 있어요. 이미지 가져오기, 링크 미리보기, 웹훅 등록, HTML을 PDF로 바꾸는 기능이 대표적이에요.

    방어는 단계적이에요. 가장 좋은 것은 가져올 수 있는 호스트를 허용 목록으로 제한하는 거예요. 임의의 주소를 허용해야 한다면, 주소의 이름을 IP로 바꾼 뒤 사설망, 루프백, 링크 로컬 대역이면 거부해요. 이때 검사한 그 IP로 연결해야 해요. 이름을 검사하고 연결할 때 다시 이름을 풀면, 공격자가 DNS 응답을 바꿔 검사 때는 공개 IP를, 연결 때는 내부 IP를 돌려줄 수 있어요. 리다이렉트를 따라갈 때도 매번 다시 검사해요. 가장 확실한 것은 외부 요청 전용의 격리된 경로(내부망에 닿지 않는 프록시)로만 나가게 하는 거예요.

    안전하지 않은 역직렬화

    자바 기본 직렬화 같은 언어 내장 형식은 "어떤 클래스의 객체를 만들지"를 데이터가 정해요. 신뢰할 수 없는 데이터를 이 방식으로 읽으면, 공격자가 우리 클래스패스에 있는 클래스들을 골라 조립해서 코드 실행까지 이어 갈 수 있어요. 외부에서 온 데이터에는 데이터만 표현하는 형식(JSON, Protobuf)을 써요. JSON 라이브러리도 데이터에 적힌 타입 이름으로 객체를 만드는 기능을 켜면 같은 문제가 생겨요.

    파일 업로드

    상품 이미지 업로드에도 구멍이 여럿이에요. 파일 이름에 ../를 넣어 저장 폴더 밖에 쓰는 경로 조작이 있어요. 사용자가 준 파일 이름을 저장 경로에 쓰지 말고 서버가 만든 이름을 써요. 확장자와 Content-Type은 사용자가 정하는 값이라 믿을 수 없으니 실제 내용을 확인해요. 크기 상한이 없으면 디스크가 차고, 압축 파일은 풀었을 때의 크기와 파일 수도 제한해야 해요. 업로드한 파일은 코드가 실행되지 않는 곳, 가능하면 객체 저장소에 두고 서비스와 다른 도메인에서 내려보내요.

    백엔드에서는 클라우드에서는 메타데이터 서비스를 토큰이 있어야 응답하는 방식(AWS의 IMDSv2 등)으로만 쓰게 설정하세요. 단순한 GET 한 번으로는 자격 증명을 얻지 못하게 돼서 많은 SSRF가 무력화돼요. 그리고 인스턴스에 부여한 역할의 권한을 최소로 두세요. 이미지 수집 서버의 자격 증명이 유출돼도 이미지 버킷에만 쓸 수 있다면 피해가 작아요.
    핵심 정리
    • SSRF: 사용자가 준 주소를 서버가 가져오면 내부망과 메타데이터가 노출
    • 방어 순서: 허용 목록, IP 대역 검사(검사한 IP로 연결, 리다이렉트 재검사), 격리된 경로
    • 역직렬화는 데이터만 표현하는 형식으로. 업로드는 이름·형식·크기를 서버가 통제
    셀프 체크
    1. SSRF 방어에서 "호스트 이름을 검사한 뒤 그 이름으로 요청"하는 방식이 왜 뚫릴 수 있나요?
    답 보기

    검사할 때와 실제로 연결할 때 이름 해석이 따로 일어나기 때문이에요. 공격자가 자기 도메인의 DNS 응답을 조작해서, 검사 시점에는 공개 IP를, 바로 뒤의 연결 시점에는 내부 IP를 돌려주게 할 수 있어요. 그래서 이름을 한 번만 풀고, 그 결과 IP를 검사한 뒤, 같은 IP로 직접 연결해야 해요. 리다이렉트도 같은 이유로 단계마다 다시 검사해야 해요.

    4부 운영

    9장 비밀 관리와 공급망

    코드 밖에서 뚫리는 경로

    문제: 지운 커밋의 결제 API 키가 악용됐다

    개발자가 결제 대행사 API 키를 설정 파일에 넣은 채 커밋했다가, 몇 분 뒤 알아채고 다음 커밋에서 지웠어요. 한 달 뒤 누군가 그 키로 환불 API를 호출한 기록이 발견됐어요. 키는 분명히 지웠는데 어떻게 된 걸까요?

    저장소에 들어간 비밀은 지워지지 않는다

    다음 커밋에서 지워도 이전 커밋에는 그대로 남아 있어요. 그 사이에 저장소를 받아 간 모든 사람의 복제본, CI의 캐시, 포크에도 있어요. 기록을 다시 써서 지우더라도 이미 퍼진 복사본은 회수할 수 없어요. 그래서 한 번이라도 커밋된 비밀은 유출된 것으로 보고 교체해야 해요.

    비밀은 처음부터 코드 밖에 둬요. 비밀 저장소(Vault, 클라우드의 시크릿 매니저)에 두고 애플리케이션이 시작할 때 주입받아요. 환경 변수는 코드보다는 낫지만 프로세스 목록, 크래시 덤프, 디버그 화면으로 새기 쉬워요. 그리고 커밋 전에 비밀을 탐지하는 훅과 저장소 전체를 주기적으로 훑는 스캔을 걸어 둬요.

    교체할 수 있어야 한다

    유출이 확인되면 바로 바꿔야 하는데, 바꾸는 절차가 없으면 바꾸는 순간 결제가 멈춰요. 그래서 무중단 교체 절차를 미리 만들어 둬요. 새 키를 발급하고, 일정 기간 옛 키와 새 키를 모두 받아들이게 하고, 모든 사용처를 새 키로 바꾼 것을 확인한 뒤 옛 키를 폐기해요. 한 번도 바꿔 본 적 없는 비밀은 사고 때도 바꾸지 못해요. 평소에 주기적으로 교체하며 절차를 연습해 두세요.

    더 나은 방법은 오래 사는 비밀을 아예 없애는 거예요. 서버나 컨테이너 자체의 신원으로 그때그때 짧게 사는 자격 증명을 발급받으면, 유출돼도 금방 만료돼요.

    가져다 쓴 코드가 더 많다

    우리 서비스의 코드 대부분은 우리가 쓴 것이 아니라 의존성이에요. 의존성의 취약점이 곧 우리 취약점이에요. 이것을 공급망 보안이라고 해요.

    먼저 버전을 고정해요. 잠금 파일로 의존성의 의존성까지 고정하지 않으면, 빌드할 때마다 다른 코드가 들어와요. 다음으로 알려진 취약점이 있는 의존성을 CI에서 스캔해요. 알림만 쌓이면 아무도 보지 않으니, 심각도별 처리 기한을 정해요. 내부 패키지와 같은 이름을 공개 저장소에 올려 두는 공격도 있어서, 내부 패키지는 내부 저장소에서만 찾도록 설정해요. 마지막으로 빌드 파이프라인도 공격 대상이에요. CI가 가진 배포 권한과 비밀은 운영 서버만큼 보호해야 해요.

    백엔드에서는 로그는 비밀이 새는 가장 흔한 경로예요. 요청 전체를 남기는 디버그 로그, 연결 문자열이 담긴 예외 메시지, Authorization 헤더가 그대로 남아요. 로깅 계층에서 민감한 필드를 가리고, 운영 환경에서 디버그용·관리용 엔드포인트가 인증 없이 열려 있지 않은지 확인하세요.
    핵심 정리
    • 비밀은 코드 밖, 비밀 저장소에서 실행 시점 주입. 커밋된 비밀은 무조건 교체
    • 무중단 교체 절차를 미리 만들고 주기적으로 연습. 짧게 사는 자격 증명이 최선
    • 의존성 고정 + 취약점 스캔 + 빌드 파이프라인 보호
    셀프 체크
    1. 실수로 API 키를 커밋했다가 바로 다음 커밋에서 지웠습니다. 무엇을 해야 하나요?
    답 보기

    키를 즉시 폐기하고 새로 발급해야 해요. 다음 커밋에서 지워도 이전 커밋에는 그대로 남아 있고, 그 사이 저장소를 받아 간 모든 복제본과 CI 캐시, 포크에도 있어요. 기록을 다시 써서 지우는 것은 이미 퍼진 복사본을 회수하지 못하므로 교체를 대신할 수 없어요. 교체한 뒤에는 그 키가 유효했던 기간의 사용 기록을 확인해서 악용이 있었는지 살펴봐요.

    실습 과제

    공격을 직접 해 봐야 방어가 이해돼요. 반드시 자기 로컬 환경에서만 하세요.

    • 3장 같은 비밀번호를 SHA-256과 bcrypt(비용 10, 12, 14)로 해시하는 시간을 재고, 초당 시도 가능 횟수 계산

    • 6장 문자열 결합 쿼리로 로그인 폼을 만들어 인젝션으로 우회한 뒤, 바인딩으로 고쳐 같은 입력이 실패하는지 확인
    • 7장 자동 이스케이프를 끈 후기 화면으로 저장형 XSS를 재현하고, CSP 헤더를 추가해 실행이 막히는지 확인
    • 8장 주소를 받아 가져오는 엔드포인트로 루프백 주소 SSRF를 재현하고, IP 대역 검사와 리다이렉트 재검사 추가
    • 9장 저장소 전체 기록을 비밀 탐지 도구로 스캔하고, 의존성 취약점 스캔을 CI에 추가
