    컨테이너와 쿠버네티스

    기준 교재: 쿠버네티스 인 액션(Kubernetes in Action) · 3~4주

    백엔드 개발자에게 쿠버네티스는 "배포하면 알아서 도는 곳"이기 쉬워요. 그러다 Pod가 이유 없이 죽거나, 배포할 때마다 에러가 나거나, CPU가 남는데 느려지면 내부를 알아야 풀 수 있어요. 이 챕터는 애플리케이션 개발자가 알아야 하는 범위를 다뤄요. 클러스터 구축과 운영은 범위 밖이에요.

    운영체제 챕터(프로세스, 스케줄링, 메모리)와 네트워크 챕터(로드밸런서, NAT)가 전제예요. 시간이 없으면 5장(리소스 관리), 7장(프로브와 종료)을 먼저 읽으세요. 개발자가 직접 설정하고 가장 자주 틀리는 곳이에요.

    쿠버네티스 인 액션 기준 교재개념을 왜 그렇게 만들었는지부터 설명

    1부 컨테이너

    1장 컨테이너의 실체

    컨테이너는 가벼운 VM이 아니라 격리된 프로세스다

    가상 머신과의 차이

    가상 머신은 하드웨어를 흉내 내고 그 위에 운영체제를 통째로 올려요. 컨테이너는 호스트의 커널을 그대로 쓰는 보통의 프로세스예요. 커널의 기능 두 가지로 "혼자 있는 것처럼" 보이게 할 뿐이에요.

    네임스페이스: 무엇이 보이는가

    프로세스가 볼 수 있는 시스템의 범위를 나눠요.

    • PID: 자기 컨테이너의 프로세스만 보이고, 첫 프로세스가 PID 1이 돼요.
    • 네트워크: 자기만의 네트워크 인터페이스, IP, 포트 공간.
    • 마운트: 자기만의 파일 시스템 뷰.
    • 그 외 호스트 이름, 사용자 ID, IPC.

    cgroup: 얼마나 쓸 수 있는가

    프로세스 그룹이 쓸 수 있는 CPU, 메모리, I/O의 양을 제한하고 측정해요. 컨테이너의 CPU·메모리 한도가 이것이에요.

    이미지와 레이어

    이미지는 파일 시스템의 스냅샷이에요. 여러 개의 읽기 전용 레이어가 쌓여 있고, Dockerfile의 명령 하나하나가 레이어 하나를 만들어요. 컨테이너를 실행하면 그 위에 쓰기 가능한 얇은 층이 하나 더 올라가요.

    • 레이어는 내용이 같으면 이미지 간에 공유되고 캐시돼요.
    • 한 레이어가 바뀌면 그 위의 레이어는 전부 다시 만들어요. 그래서 잘 안 바뀌는 것(의존성 설치)을 아래에, 자주 바뀌는 것(소스 코드)을 위에 둬요.
    • 컨테이너의 쓰기 층은 컨테이너가 사라지면 함께 사라져요.
    백엔드에서는 빌드 도구와 런타임을 분리하세요(멀티 스테이지 빌드). 빌드 단계에서 컴파일하고, 최종 이미지에는 실행에 필요한 것만 복사해요. 이미지가 작아지고 공격 표면이 줄어요. 태그는 latest가 아니라 변하지 않는 버전이나 커밋 해시로 고정하세요. latest는 어제와 오늘이 다른 이미지일 수 있어서 롤백도 재현도 안 돼요.
    시니어 심화
    • 격리는 VM보다 약해요. 커널을 공유하므로 커널 취약점이 곧 컨테이너 탈출 경로예요. 루트가 아닌 사용자로 실행하고, 루트 파일 시스템을 읽기 전용으로 하고, 불필요한 권한을 떼는 것이 기본 방어예요. 서로 신뢰하지 않는 워크로드를 같은 노드에 둔다면 더 강한 격리(샌드박스 런타임)가 필요해요.
    • 이미지 레이어에 넣은 비밀은 지워지지 않아요. 뒤의 레이어에서 파일을 삭제해도 앞 레이어에는 그대로 남아 있어요. 빌드 중에 필요한 비밀은 빌드 도구의 비밀 전달 기능으로 넘겨요.
    • PID 1의 책임: 컨테이너의 첫 프로세스는 시그널을 직접 처리하고 고아 프로세스를 거둬야 해요. 셸 스크립트로 앱을 띄우면 셸이 PID 1이 되어 종료 신호가 앱에 전달되지 않아요. exec로 앱이 셸을 대체하게 하세요.
    핵심 정리
    • 컨테이너 = 네임스페이스(격리) + cgroup(제한)이 걸린 프로세스. 커널 공유
    • 이미지 = 읽기 전용 레이어 스택. 자주 바뀌는 것을 위에
    • 컨테이너 안에 쓴 것은 사라짐. 태그는 고정
    셀프 체크
    1. Dockerfile에서 소스 코드 복사를 의존성 설치보다 뒤에 두는 이유를 설명하세요.
    답 보기

    이미지 빌드는 명령마다 레이어를 만들고, 입력이 바뀌지 않은 레이어는 캐시를 재사용해요. 그런데 어떤 레이어가 바뀌면 그 뒤의 레이어는 전부 다시 만들어야 해요. 소스 코드는 커밋마다 바뀌고 의존성 목록은 가끔만 바뀌어요. 소스 복사를 먼저 두면 코드 한 줄만 고쳐도 의존성 설치를 매번 다시 하게 돼요. 의존성 목록 파일만 먼저 복사해 설치하고 그 뒤에 소스를 복사하면, 의존성이 그대로인 한 설치 레이어는 캐시에서 가져와요.

    2부 쿠버네티스 핵심

    2장 아키텍처와 선언적 모델

    원하는 상태를 적으면 시스템이 맞춘다

    명령형과 선언형

    명령형은 "컨테이너 3개를 띄워라"예요. 하나가 죽으면 누군가 다시 명령해야 해요. 선언형은 "컨테이너가 3개 떠 있어야 한다"예요. 시스템이 현재 상태를 계속 관찰해서, 다르면 맞춰요.

    조정 루프

    쿠버네티스의 거의 모든 동작이 같은 구조예요.

    1. 원하는 상태를 읽는다.
    2. 현재 상태를 관찰한다.
    3. 다르면 차이를 줄이는 행동을 한다.
    4. 반복한다.

    이 일을 하는 프로그램이 컨트롤러예요. 리소스 종류마다 컨트롤러가 있어요.

    구성 요소

    위치구성 요소역할
    컨트롤 플레인API 서버모든 읽기·쓰기의 유일한 창구
    etcd클러스터 상태 전체를 저장하는 합의 기반 저장소
    스케줄러Pod를 어느 노드에 둘지 결정
    컨트롤러 매니저내장 컨트롤러들을 실행
    노드kubelet자기 노드에 배정된 Pod의 컨테이너를 실행하고 상태를 보고
    kube-proxyService의 트래픽 전달 규칙을 노드에 설정

    구성 요소끼리 직접 통신하지 않고 전부 API 서버를 통해 상태를 읽고 써요.

    리소스의 모양

    모든 리소스는 spec(원하는 상태, 사용자가 씀)과 status(현재 상태, 시스템이 씀)를 가져요. 레이블로 리소스를 분류하고, 셀렉터로 레이블이 맞는 리소스를 골라요. 리소스 사이의 연결은 대부분 이름이 아니라 레이블 셀렉터로 이뤄져요.

    백엔드에서는 클러스터 상태는 매니페스트 파일로 저장소에 두고 거기서 적용하세요. 누군가 직접 명령으로 고친 것은 기록이 남지 않고, 다음 적용 때 덮어써지거나 영영 어긋난 채로 남아요. 문제가 생기면 kubectl describe의 Events와 kubectl get -o yaml의 status를 먼저 보세요. 시스템이 무엇을 하려다 왜 못 했는지가 거기 적혀 있어요.
    시니어 심화
    • 최종 일관성이에요. 적용이 성공했다는 것은 원하는 상태가 저장됐다는 뜻이지 그 상태에 도달했다는 뜻이 아니에요. 배포 스크립트는 적용 뒤에 실제로 준비 상태가 될 때까지 기다리고 확인해야 해요.
    • 수준 기반 동작: 컨트롤러는 "무슨 일이 일어났는가"가 아니라 "지금 상태가 어떤가"로 움직여요. 이벤트를 놓쳐도 다음 관찰에서 따라잡아요. 직접 컨트롤러(오퍼레이터)를 만들 때도 조정 함수를 여러 번 실행해도 안전하게 짜야 해요.
    • API 서버와 etcd가 병목이에요. 리소스를 지나치게 많이 만들거나 자주 갱신하는 워크로드, 전체 목록을 반복해서 가져오는 클라이언트는 컨트롤 플레인 전체를 느리게 해요.
    핵심 정리
    • 선언형: 원하는 상태를 저장하면 컨트롤러가 현재 상태를 맞춤
    • 모든 통신은 API 서버를 거치고 상태는 etcd에
    • spec = 원하는 상태, status = 현재 상태. 연결은 레이블 셀렉터
    셀프 체크
    1. kubectl apply가 성공했는데 애플리케이션이 뜨지 않았습니다. 왜 이런 일이 가능한가요?
    답 보기

    apply의 성공은 API 서버가 원하는 상태를 받아 저장했다는 뜻이에요. 그 상태를 실제로 만드는 일은 그 뒤에 컨트롤러, 스케줄러, kubelet이 비동기로 해요. 그 과정에서 이미지를 가져오지 못하거나, 자원이 부족해 배치할 노드가 없거나, 컨테이너가 시작하자마자 죽거나, 준비 상태 검사를 통과하지 못할 수 있어요. 이런 실패는 apply 명령의 결과가 아니라 리소스의 status와 이벤트에 나타나요. 그래서 배포 절차는 적용 후 롤아웃 상태를 확인하는 단계를 포함해야 해요.

    3장 Pod, Deployment, 배포 전략

    무엇을 띄우고 어떻게 교체하는가

    Pod

    배포의 최소 단위예요. 컨테이너 하나 이상을 묶은 것으로, 같은 Pod의 컨테이너는 네트워크 네임스페이스를 공유해요(같은 IP, 서로 localhost로 통신). 볼륨도 공유할 수 있어요.

    Pod는 일회용이에요. 죽으면 고쳐지지 않고 새 Pod가 만들어져요. 새 Pod는 이름도 IP도 달라요.

    한 Pod에 여러 컨테이너

    기본은 Pod 하나에 컨테이너 하나예요. 여러 개를 넣는 것은 생명 주기를 함께해야 하는 보조 프로세스일 때예요(로그 수집기, 프록시). 앱과 DB를 한 Pod에 넣지 않아요. 따로 확장해야 하니까요.

    Deployment

    Pod를 직접 만들지 않고 Deployment를 만들어요. 계층은 이래요.

    Deployment  →  ReplicaSet  →  Pod × N
      (버전 관리)     (개수 유지)

    ReplicaSet은 Pod 개수를 유지해요. Deployment는 Pod 템플릿이 바뀔 때마다 새 ReplicaSet을 만들고 옛것에서 새것으로 옮겨 가요.

    롤링 업데이트

    새 Pod를 조금 띄우고, 준비되면 옛 Pod를 조금 내리는 것을 반복해요.

    • maxSurge: 원하는 개수보다 몇 개까지 더 띄울 수 있나.
    • maxUnavailable: 원하는 개수보다 몇 개까지 모자라도 되나.

    새 Pod가 준비 상태가 되어야 다음 단계로 넘어가요. 준비 상태 검사가 없으면 뜨자마자 준비된 것으로 보고 진행해요.

    다른 워크로드 종류

    • StatefulSet: 고정된 이름과 전용 저장소가 필요한 것(DB, 브로커).
    • DaemonSet: 모든 노드에 하나씩(로그·메트릭 수집기).
    • Job / CronJob: 끝나는 작업, 주기적 작업.
    백엔드에서는 롤링 업데이트 중에는 옛 버전과 새 버전이 동시에 트래픽을 받아요. 그래서 DB 스키마 변경과 API 변경은 두 버전이 공존할 수 있게 해야 해요. 컬럼을 지우는 변경을 코드와 같이 배포하면 옛 Pod가 에러를 내요. 롤백은 kubectl rollout undo로 이전 ReplicaSet으로 돌아가지만, 그 사이 DB에 일어난 변경은 돌아가지 않아요.
    시니어 심화
    • 롤링 업데이트는 검증이 아니에요. 준비 상태 검사만 통과하면 끝까지 진행하므로, 뜨기는 하는데 에러를 내는 버전은 전체로 퍼져요. 일부에만 먼저 내보내 지표를 보고 넓히는 카나리, 새 버전을 통째로 준비한 뒤 트래픽을 한 번에 넘기는 블루-그린은 별도 도구가 필요해요.
    • 자발적 중단에 대한 보호: 노드 업그레이드나 축소로 Pod가 쫓겨날 때 한꺼번에 너무 많이 내려가지 않도록 PodDisruptionBudget으로 최소 가용 개수를 정해요. 없으면 노드 작업 한 번에 서비스가 전부 내려갈 수 있어요.
    • CronJob은 정확히 한 번 실행을 보장하지 않아요. 드물게 두 번 실행되거나 건너뛸 수 있어요. 작업을 멱등하게 만들고, 이전 실행이 끝나지 않았을 때의 동작(동시 실행 정책)을 정해요.
    핵심 정리
    • Pod = 일회용, IP가 바뀜. 직접 만들지 않고 Deployment로
    • 롤링 업데이트: 새 Pod가 준비돼야 진행. 두 버전이 공존
    • 상태가 있으면 StatefulSet, 노드마다면 DaemonSet, 끝나는 작업은 Job
    셀프 체크
    1. 롤링 업데이트로 배포할 때 DB 컬럼 삭제를 같은 배포에 넣으면 왜 문제가 되나요?
    답 보기

    롤링 업데이트는 옛 Pod와 새 Pod가 한동안 함께 트래픽을 받는 방식이에요. 컬럼을 삭제하는 스키마 변경이 적용되면, 아직 내려가지 않은 옛 Pod는 그 컬럼을 읽거나 쓰려다 에러를 내요. 그래서 먼저 그 컬럼을 쓰지 않는 코드를 배포해 모든 Pod가 교체된 것을 확인하고, 그다음 배포에서 컬럼을 삭제해야 해요. 문제가 생겨 이전 버전으로 롤백해야 할 때도 컬럼이 아직 남아 있어야 옛 코드가 동작해요.

    4장 Service와 네트워킹

    계속 바뀌는 Pod에 고정된 주소를 준다

    네트워크 모델

    모든 Pod는 고유한 IP를 받고, 모든 Pod는 다른 모든 Pod와 NAT 없이 통신할 수 있어요. 이것을 실제로 구현하는 것은 네트워크 플러그인(CNI)이에요.

    Service가 필요한 이유

    Pod의 IP는 Pod가 다시 만들어질 때마다 바뀌어요. Service는 변하지 않는 가상 IP와 DNS 이름을 주고, 레이블 셀렉터에 맞는 Pod들로 트래픽을 나눠 보내요.

    중요한 점: Service는 준비 상태인 Pod만 대상에 넣어요. 준비 상태 검사에 실패한 Pod는 자동으로 빠져요.

    Service 종류

    종류접근 범위
    ClusterIP클러스터 내부에서만. 기본값
    NodePort모든 노드의 특정 포트로 외부에서 접근
    LoadBalancer클라우드의 로드밸런서를 만들어 외부에 노출
    Headless가상 IP 없이 DNS가 Pod IP들을 직접 반환

    DNS

    클러스터 DNS가 Service 이름을 가상 IP로 풀어줘요. 같은 네임스페이스에서는 orders, 다른 네임스페이스에서는 orders.shop, 전체 이름은 orders.shop.svc.cluster.local이에요.

    Ingress

    Service마다 로드밸런서를 만드는 대신, HTTP 수준에서 호스트 이름과 경로로 여러 Service에 나눠 주는 진입점이에요. TLS 종료도 여기서 해요. Ingress 리소스는 규칙일 뿐이고, 실제로 트래픽을 받는 것은 Ingress 컨트롤러예요.

    NetworkPolicy

    기본적으로 모든 Pod가 서로 통신할 수 있어요. NetworkPolicy로 어떤 Pod가 어떤 Pod에 접근할 수 있는지 제한해요.

    백엔드에서는 Service의 부하 분산은 연결 단위예요. HTTP/2나 gRPC처럼 연결 하나를 오래 쓰며 여러 요청을 보내는 프로토콜은 처음 연결된 Pod 하나에 요청이 전부 몰려요. Pod를 늘려도 새 Pod는 한가해요. 요청 단위로 분산하려면 클라이언트 쪽 로드밸런싱(Headless Service로 Pod IP 목록을 받아 직접 분산)이나 L7 프록시가 필요해요.
    시니어 심화
    • 엔드포인트 갱신은 비동기로 퍼져요. Pod가 종료를 시작해도, 그 Pod가 대상에서 빠졌다는 사실이 모든 노드의 전달 규칙과 Ingress 컨트롤러에 반영되기까지 시간이 걸려요. 그동안 종료 중인 Pod로 새 요청이 와요. 7장의 종료 절차가 필요한 이유예요.
    • 연결 추적 테이블: Service의 가상 IP는 노드에서 주소 변환으로 구현돼요. 짧은 연결을 대량으로 만들면 연결 추적 테이블이 차거나 포트가 고갈돼 간헐적인 연결 실패가 나요.
    • DNS 조회 비용: 기본 설정에서는 점이 적은 이름을 클러스터 검색 도메인에 차례로 붙여 조회해요. 외부 도메인을 호출할 때마다 실패하는 조회가 여러 번 먼저 나가요. 외부 호출이 많으면 끝에 점을 붙인 전체 이름을 쓰거나 노드 로컬 DNS 캐시를 둬요.
    핵심 정리
    • Pod는 서로 직접 통신 가능. IP는 바뀌므로 Service로 고정 주소 제공
    • Service는 준비 상태인 Pod만 대상. 분산은 연결 단위
    • Ingress = HTTP 수준 진입점. NetworkPolicy로 통신 제한
    셀프 체크
    1. gRPC 서비스의 Pod를 3개에서 10개로 늘렸는데 기존 Pod의 부하가 줄지 않았습니다. 이유는 무엇인가요?
    답 보기

    gRPC는 HTTP/2 위에서 연결 하나를 오래 유지하며 그 위로 많은 요청을 보내요. Service의 부하 분산은 연결을 맺는 순간에 대상 Pod를 고르는 방식이라, 이미 맺어진 연결은 처음 고른 Pod에 계속 붙어 있어요. 새 Pod를 추가해도 클라이언트가 새 연결을 맺지 않는 한 요청이 가지 않아요. 요청 단위로 분산하려면 클라이언트가 Pod 주소 목록을 받아 요청마다 대상을 고르게 하거나, 요청을 이해하는 프록시를 사이에 둬요. 서버가 연결의 최대 수명을 정해 주기적으로 다시 맺게 하는 것도 완화책이에요.

    5장 리소스 관리와 스케줄링

    requests는 스케줄링의 기준, limits는 실행 중의 상한

    requests와 limits

    • requests: 이 컨테이너에 보장해 줄 양. 스케줄러는 노드에 남은 requests 여유만 보고 배치해요. 실제 사용량은 보지 않아요.
    • limits: 이 컨테이너가 넘을 수 없는 양. 실행 중에 커널이 강제해요.

    CPU와 메모리는 한도 초과 시 동작이 다르다

    자원성격limit을 넘으면
    CPU압축 가능. 덜 주면 느려질 뿐스로틀링: 주기 안의 할당량을 다 쓰면 다음 주기까지 멈춤
    메모리압축 불가능. 못 주면 실행 불가OOM kill: 컨테이너가 죽고 재시작

    QoS 등급

    노드의 메모리가 부족해지면 kubelet이 Pod를 쫓아내요. 그 순서를 QoS 등급이 정해요.

    • Guaranteed: 모든 컨테이너의 requests와 limits가 같음. 가장 나중에 쫓겨남.
    • Burstable: requests가 limits보다 작음.
    • BestEffort: 둘 다 없음. 가장 먼저 쫓겨남.

    스케줄링에 영향을 주는 것

    • 노드 셀렉터, 노드 어피니티: 특정 조건의 노드에만 또는 우선적으로.
    • 테인트와 톨러레이션: 노드가 "아무나 오지 마"라고 표시하고, 허용된 Pod만 들어가요.
    • Pod 안티 어피니티, 토폴로지 분산: 같은 앱의 Pod를 서로 다른 노드와 가용 영역에 흩어 놓아요.

    Pod가 Pending에 머물면 어느 노드에도 조건이 맞지 않는 거예요. 이유는 이벤트에 나와요.

    백엔드에서는 requests를 실제 사용량보다 훨씬 작게 잡으면 노드에 Pod가 과하게 몰려 서로 자원을 빼앗고, 훨씬 크게 잡으면 노드가 비어 있는데도 배치가 안 돼 비용이 낭비돼요. 실제 사용량 지표를 보고 정하세요. 런타임이 컨테이너 한도를 인식하는지도 확인하세요. JVM은 메모리 한도의 비율로 힙을 잡게 하고, 힙 외 메모리(메타스페이스, 스레드 스택, 다이렉트 버퍼)를 위한 여유를 남겨야 OOM kill을 피해요.
    시니어 심화
    • CPU limit과 꼬리 지연: 여러 스레드가 동시에 돌면 주기의 할당량을 순식간에 쓰고 나머지 시간 동안 전부 멈춰요. 평균 CPU 사용률은 낮은데 p99가 튀는 전형적인 원인이에요. 스로틀링 지표를 확인하고, 지연에 민감한 서비스는 CPU limit을 두지 않고 requests만 정확히 두는 운영 방식도 널리 쓰여요.
    • 메모리는 requests와 limits를 같게 두는 것이 안전해요. requests보다 많이 쓰고 있는 Pod는 노드가 메모리 압박을 받을 때 먼저 쫓겨나요.
    • 네임스페이스 단위 통제: ResourceQuota로 팀별 총량을 제한하고, LimitRange로 지정하지 않은 컨테이너에 기본값을 넣어요. 값 없이 뜬 BestEffort Pod가 노드를 불안정하게 만드는 것을 막아요.
    핵심 정리
    • requests = 스케줄링 기준(보장), limits = 실행 상한(강제)
    • CPU 초과 → 스로틀링(느려짐), 메모리 초과 → OOM kill(죽음)
    • QoS 등급이 축출 순서를 결정. 토폴로지 분산으로 장애 영역 분리
    셀프 체크
    1. 컨테이너가 메모리 limit을 넘었을 때와 CPU limit을 넘으려 할 때 각각 어떤 일이 일어나나요?
    답 보기

    메모리는 덜 줄 방법이 없는 자원이라, 한도를 넘으면 커널이 컨테이너의 프로세스를 강제 종료해요. Pod의 상태에 OOMKilled로 표시되고 재시작 정책에 따라 다시 떠요. CPU는 덜 주면 느려질 뿐인 자원이라 프로세스를 죽이지 않아요. 정해진 주기 안에서 쓸 수 있는 CPU 시간을 다 쓰면 다음 주기가 올 때까지 실행을 멈춰요. 프로세스는 살아 있지만 그 시간만큼 응답이 늦어지고, 이것이 지연의 튐으로 나타나요.

    6장 설정, 시크릿, 상태 저장

    이미지는 그대로 두고 환경만 바꾼다

    ConfigMap과 Secret

    설정을 이미지에서 분리해 같은 이미지를 여러 환경에 쓸 수 있게 해요. 컨테이너에 주입하는 방법은 둘이에요.

    • 환경 변수: 컨테이너가 시작할 때 한 번 읽혀요. ConfigMap을 바꿔도 Pod를 다시 띄우기 전에는 반영되지 않아요.
    • 볼륨으로 마운트: 파일로 보여요. ConfigMap을 바꾸면 얼마 뒤 파일이 갱신돼요. 앱이 파일 변경을 감지해 다시 읽어야 효과가 있어요.

    Secret은 암호화가 아니다

    Secret의 값은 Base64로 인코딩돼 있을 뿐이에요. 기본 설정에서는 etcd에 평문과 다름없이 저장되고, 읽기 권한이 있는 누구나 볼 수 있어요.

    • etcd 저장 시 암호화를 켜요.
    • 접근 권한(RBAC)으로 Secret을 읽을 수 있는 주체를 좁혀요.
    • 매니페스트를 저장소에 둘 때 Secret을 평문으로 커밋하지 않아요. 외부 비밀 저장소와 동기화하거나 암호화된 형태로 둬요.

    볼륨

    컨테이너의 파일 시스템은 컨테이너가 재시작하면 초기화돼요. 유지해야 하는 데이터는 볼륨에 둬요.

    • emptyDir: Pod와 수명을 같이하는 임시 공간. 같은 Pod의 컨테이너끼리 파일을 주고받을 때.
    • PersistentVolumeClaim: "이만큼의 저장소가 필요하다"는 요청. Pod가 사라져도 데이터가 남아요. 스토리지 클래스가 실제 디스크를 동적으로 만들어 연결해요.

    StatefulSet

    Deployment의 Pod는 서로 구분되지 않고 교체 가능해요. DB나 브로커는 그렇지 않아요. StatefulSet은 다음을 보장해요.

    • 고정된 이름: db-0, db-1처럼 순번이 붙고, 다시 만들어져도 같은 이름.
    • 고정된 저장소: Pod마다 전용 볼륨이 있고, 다시 만들어지면 같은 볼륨에 붙음.
    • 순서 있는 생성과 종료.

    상태가 있는 것을 쿠버네티스에 둘 것인가

    StatefulSet은 Pod와 볼륨을 관리할 뿐, 복제 구성, 장애 조치, 백업, 버전 업그레이드 같은 DB 운영 지식은 갖고 있지 않아요. 그 부분은 오퍼레이터가 맡거나 사람이 맡아야 해요. 관리형 DB 서비스를 쓸 수 있다면 그쪽이 보통 운영 부담이 적어요.

    백엔드에서는 환경 변수로 주입한 설정은 프로세스 목록, 크래시 덤프, 디버그 엔드포인트로 새기 쉬워요. 민감한 값은 파일로 마운트하는 편이 낫고, 앱이 시작할 때 설정 전체를 로그로 찍는 코드가 없는지 확인하세요. 설정을 바꿨는데 반영이 안 되는 사고를 막으려면, 설정 내용의 해시를 Pod 템플릿의 애너테이션에 넣어 설정이 바뀌면 롤링 업데이트가 일어나게 해요.
    핵심 정리
    • 환경 변수 주입은 재시작해야 반영. 볼륨 마운트는 파일이 갱신됨
    • Secret은 Base64일 뿐. 저장 시 암호화 + 접근 권한 제한
    • StatefulSet = 고정 이름 + 전용 볼륨. DB 운영 지식은 포함하지 않음
    셀프 체크
    1. ConfigMap의 값을 수정했는데 애플리케이션이 옛 값을 계속 씁니다. 가능한 원인과 해결을 말해보세요.
    답 보기

    환경 변수로 주입했다면 환경 변수는 컨테이너가 시작할 때 한 번 정해지므로 ConfigMap을 바꿔도 실행 중인 Pod에는 반영되지 않아요. Pod를 다시 띄워야 해요. 볼륨으로 마운트했다면 파일은 얼마 뒤 갱신되지만, 애플리케이션이 시작할 때 한 번만 읽고 메모리에 들고 있으면 역시 옛 값을 써요. 해결은 설정 변경 시 롤링 재시작이 일어나게 하는 거예요. 설정 내용의 해시를 Pod 템플릿에 넣어 두면 설정이 바뀔 때 템플릿이 바뀐 것으로 인식돼 자동으로 새 Pod로 교체돼요.

    7장 프로브, 종료, 오토스케일링

    배포할 때 에러가 나지 않으려면

    세 가지 프로브

    프로브묻는 것실패하면
    startup시작이 끝났는가그동안 다른 프로브를 미룸. 계속 실패하면 재시작
    readiness지금 트래픽을 받을 수 있는가Service 대상에서 뺌. 재시작하지 않음
    liveness살아 있는가(스스로 회복 불가능한 상태가 아닌가)컨테이너를 재시작

    잘못 쓰는 방법

    • liveness에서 DB나 외부 서비스를 확인: DB가 느려지면 모든 Pod가 동시에 재시작돼요. 재시작해도 DB는 그대로니 장애만 키워요. liveness는 프로세스 자신의 상태만 봐요.
    • readiness와 liveness를 같은 검사로: 일시적으로 바쁜 것과 죽은 것을 구분하지 못해요.
    • 시작이 느린 앱에 liveness만: 뜨기도 전에 죽은 것으로 판정해 재시작을 반복해요. startup 프로브를 써요.

    종료 절차

    1. Pod가 종료 상태로 표시된다. 동시에 두 일이 병렬로 시작돼요.
    2. (가) Service 대상에서 Pod를 빼는 작업이 클러스터에 퍼진다.
    3. (나) preStop 훅이 있으면 실행되고, 그 뒤 컨테이너에 SIGTERM이 간다.
    4. 유예 시간(terminationGracePeriodSeconds, 기본 30초) 안에 끝나지 않으면 SIGKILL.

    (가)가 끝나기 전에 (나)로 앱이 먼저 내려가면, 아직 그 Pod로 향하는 요청이 실패해요. 그래서 preStop에서 몇 초 기다린 뒤 종료를 시작하고, 앱은 SIGTERM을 받으면 새 요청을 받지 않으면서 진행 중인 요청을 끝내요.

    오토스케일링

    • HPA(수평): 지표(CPU 사용률, 사용자 정의 지표)에 따라 Pod 수를 조절.
    • VPA(수직): 사용량을 보고 requests를 조절.
    • 클러스터 오토스케일러: 배치할 곳이 없는 Pod가 있으면 노드를 늘리고, 비면 줄임.

    HPA의 CPU 사용률은 requests 대비 비율이에요. requests가 없으면 계산할 수 없어요.

    백엔드에서는 앱 쪽에서 해야 할 일은 세 가지예요. SIGTERM을 받아 우아하게 종료할 것(프레임워크의 graceful shutdown 설정을 켜고 유예 시간보다 짧게), 준비 상태 엔드포인트가 "지금 받을 수 있는가"를 정직하게 답할 것(커넥션 풀 초기화나 캐시 워밍업이 끝난 뒤에 통과), 컨테이너의 PID 1이 시그널을 앱에 전달할 것. 이 중 하나라도 빠지면 배포할 때마다 소량의 에러가 나요.
    시니어 심화
    • 오토스케일링은 반응이 늦어요. 지표 수집, 판단, Pod 시작, 준비까지 분 단위가 걸려요. 노드까지 늘려야 하면 더 걸려요. 급증하는 트래픽은 그 시간 동안 기존 Pod가 버텨야 하므로 평소에 여유를 두거나 예정된 이벤트 전에 미리 늘려요.
    • CPU가 맞는 지표가 아닐 수 있어요. I/O 대기가 대부분인 서비스는 과부하에서도 CPU가 낮아요. 요청 수, 큐 길이, 동시 처리 중인 요청 수 같은 지표로 확장해야 해요.
    • 확장의 상한은 하위 시스템이에요. Pod가 늘면 DB 커넥션도 늘어요. HPA의 최대 개수를 DB가 받을 수 있는 커넥션 수에서 역산하지 않으면, 확장이 DB를 넘어뜨려요.
    핵심 정리
    • readiness = 트래픽 제외, liveness = 재시작. liveness에 외부 의존성 금지
    • 종료: preStop 대기 → SIGTERM → 진행 중 요청 완료 → 유예 시간 내 종료
    • HPA는 requests 대비 비율. 반응이 늦으므로 여유 필요
    셀프 체크
    1. liveness 프로브에서 DB 연결을 확인하도록 설정하면 어떤 위험이 있나요?
    답 보기

    DB가 일시적으로 느려지거나 끊기면 모든 Pod의 liveness 검사가 동시에 실패하고, 쿠버네티스가 모든 컨테이너를 재시작해요. 재시작해도 DB 문제는 해결되지 않고, 오히려 모든 Pod가 한꺼번에 내려갔다가 다시 뜨면서 DB에 재연결 요청이 몰려 복구를 더 어렵게 만들어요. DB와 무관한 기능까지 함께 중단돼요. liveness는 재시작으로 고칠 수 있는 자기 자신의 문제(교착 상태 등)만 확인하고, 의존성의 상태는 필요하면 readiness에서 신중하게 반영해요.

    실습 과제

    로컬 클러스터(kind, minikube)로 충분해요.

    • 1장 같은 앱을 단일 스테이지와 멀티 스테이지로 빌드해 이미지 크기 비교. 소스만 바꿔 다시 빌드할 때 캐시가 어디까지 쓰이는지 확인
    • 2장 Deployment의 Pod를 직접 삭제하고 다시 생기는 과정을 kubectl get events --watch로 관찰
    • 3장 준비 상태 검사가 실패하는 버전을 배포해 롤링 업데이트가 멈추는 것을 확인하고 롤백
    • 4장 gRPC 서버를 여러 Pod로 띄우고 클라이언트 하나의 요청이 어느 Pod로 가는지 확인. Headless Service로 바꿔 비교
    • 5장 CPU limit을 작게 준 컨테이너에 멀티스레드 부하를 주고 스로틀링 지표와 응답 시간 분포 관찰. 메모리 limit 초과로 OOMKilled 재현
    • 6장 ConfigMap을 환경 변수와 볼륨으로 각각 주입하고 값을 바꿨을 때의 차이 확인
    • 7장 부하를 주는 중에 롤링 업데이트를 하며 에러 수 측정. preStop 대기와 우아한 종료를 넣기 전후 비교
