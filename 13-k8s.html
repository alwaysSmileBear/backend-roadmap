    컨테이너와 쿠버네티스

    기준 교재: 쿠버네티스 인 액션(Kubernetes in Action) · 3~4주

    백엔드 개발자에게 쿠버네티스는 "배포하면 알아서 도는 곳"이기 쉬워요. 그러다 Pod가 이유 없이 재시작되거나, 배포할 때마다 에러가 몇 건씩 나거나, CPU가 남는데 느려지면 내부를 알아야 풀 수 있어요. 이 챕터는 애플리케이션 개발자가 알아야 하는 범위를 다뤄요. 클러스터를 직접 구축하고 운영하는 일은 범위 밖이에요.

    예시는 쇼핑몰의 주문 API를 쿠버네티스에 배포하는 과정이에요. 운영체제 챕터(프로세스, 스케줄링, 메모리)와 네트워크 챕터(로드밸런서, NAT)가 바탕이에요. 시간이 없으면 5장(리소스 관리)과 7장(프로브와 종료)을 먼저 읽으세요. 개발자가 직접 설정하고 가장 자주 틀리는 곳이에요.

    1부 컨테이너

    1장 컨테이너의 실체

    컨테이너는 가벼운 가상 머신이 아니라 격리된 프로세스다

    문제: 컨테이너 안에서 top을 봤더니

    주문 API 컨테이너 안에 들어가서 free를 쳐 보니 메모리가 64GB로 나와요. 컨테이너에는 2GB만 줬는데요. top의 CPU 개수도 서버 전체의 32개로 나와요. 컨테이너가 자기만의 컴퓨터라면 이상한 일이에요. 컨테이너는 정확히 무엇일까요?

    커널을 공유하는 보통의 프로세스

    가상 머신은 하드웨어를 흉내 내고 그 위에 운영체제를 통째로 올려요. 컨테이너는 그렇지 않아요. 컨테이너는 호스트의 커널을 그대로 쓰는 보통의 프로세스예요. 호스트에서 ps를 치면 컨테이너 안의 자바 프로세스가 그냥 보여요. 리눅스 커널의 기능 두 가지가 이 프로세스를 "혼자 있는 것처럼" 보이게 할 뿐이에요.

    네임스페이스는 프로세스가 무엇을 볼 수 있는지를 나눠요. 자기 컨테이너의 프로세스만 보이고 첫 프로세스가 PID 1이 돼요(PID 네임스페이스). 자기만의 네트워크 인터페이스와 IP, 포트를 가져요(네트워크 네임스페이스). 자기만의 파일 시스템이 보여요(마운트 네임스페이스).

    cgroup은 프로세스 묶음이 얼마나 쓸 수 있는지를 제한하고 측정해요. 컨테이너의 CPU와 메모리 한도가 이것이에요.

    이제 문제가 풀려요. free와 top은 /proc에서 시스템 전체 정보를 읽는데, 이 정보는 네임스페이스로 가려지지 않아요. 한도는 cgroup이 걸고 있지만 이 명령들은 cgroup을 보지 않아요. 그래서 호스트 전체가 보여요. 컨테이너의 실제 한도와 사용량은 cgroup 파일(/sys/fs/cgroup)이나 쿠버네티스 지표로 봐야 해요.

    이미지와 레이어

    컨테이너 이미지는 파일 시스템의 사진이에요. 여러 개의 읽기 전용 레이어가 겹쳐 있고, Dockerfile의 명령 하나가 레이어 하나를 만들어요. 컨테이너를 실행하면 그 위에 쓰기 가능한 얇은 층이 하나 올라가는데, 이 층은 컨테이너가 사라지면 함께 사라져요. 그래서 컨테이너 안에 쓴 파일(업로드 이미지, 로그 파일)은 재시작하면 없어져요.

    레이어는 내용이 같으면 캐시돼요. 그런데 한 레이어가 바뀌면 그 위의 레이어는 전부 다시 만들어요. 그래서 잘 안 바뀌는 것(의존성 설치)을 아래에, 자주 바뀌는 것(소스 코드)을 위에 둬요. 순서가 반대면 코드 한 줄을 고칠 때마다 의존성을 처음부터 다시 받아요.

    백엔드에서는 빌드 도구와 실행 환경을 나누세요(멀티 스테이지 빌드). 빌드 단계에서 JDK와 Gradle로 jar를 만들고, 최종 이미지에는 JRE와 jar만 복사해요. 이미지가 작아지고 공격받을 수 있는 도구도 줄어요. 이미지 태그는 latest 대신 버전이나 커밋 해시로 고정하세요. latest는 어제와 오늘이 다른 이미지일 수 있어서 롤백도 재현도 안 돼요.
    시니어 심화 커널을 공유한다는 것은 격리가 가상 머신보다 약하다는 뜻이에요. 그리고 이미지에 실수로 넣은 비밀은 생각보다 오래 남아요.

    상황

    주문 API가 쓰는 라이브러리에 원격 코드 실행 취약점이 있었어요. 공격자는 주문 API 컨테이너 안에서 명령을 실행했어요. 컨테이너는 루트 사용자로 돌고 있었고, 로그 수집을 위해 노드의 디렉터리를 마운트하고 있었어요. 공격자는 그 디렉터리를 통해 같은 노드의 다른 컨테이너 로그에서 결제 서비스의 접속 정보를 찾아냈어요.

    깨지는 과정

    1. 컨테이너는 같은 노드의 커널을 함께 써요. 네임스페이스와 cgroup으로 "보이는 것"과 "쓰는 양"을 나눌 뿐, 커널 자체는 하나예요.
    2. 컨테이너 안의 루트는 기본적으로 호스트의 루트와 같은 사용자 ID예요. 컨테이너를 탈출하는 커널 취약점이 하나만 있어도 노드 전체의 권한이 돼요.
    3. 노드 디렉터리 마운트(hostPath), 특권 컨테이너(privileged), 넓은 리눅스 권한(capabilities)은 탈출에 취약점조차 필요 없게 만들어요.
    4. 이미지에도 구멍이 있었어요. 빌드할 때 넣은 저장소 접근 토큰을 마지막 레이어에서 지웠지만, 이미지 레이어는 덧붙이는 구조라서 앞 레이어에 그대로 남아 있었어요. 이미지를 받은 누구나 꺼낼 수 있어요.

    해결책

    • 루트가 아닌 사용자로 실행해요. 이미지에 일반 사용자를 만들고, Pod에 runAsNonRoot: true를 설정해요.
    • 권한을 최소로 줘요. 루트 파일 시스템은 읽기 전용(readOnlyRootFilesystem), 권한 상승 금지(allowPrivilegeEscalation: false), 리눅스 권한은 전부 떼고(drop: ["ALL"]) 필요한 것만 추가해요. hostPath와 privileged는 꼭 필요한 시스템 컴포넌트에만 허용해요.
    • 규칙을 클러스터가 강제하게 해요. 쿠버네티스의 Pod Security Admission을 네임스페이스에 restricted 수준으로 걸면, 위 규칙을 어기는 Pod는 아예 만들어지지 않아요.
    • 신뢰할 수 없는 코드는 더 강하게 격리해요. 사용자가 올린 코드를 실행하는 것처럼 신뢰할 수 없는 워크로드는, 커널 호출을 가로채는 gVisor나 경량 가상 머신을 쓰는 Kata Containers 같은 샌드박스 런타임으로 돌리거나 별도 노드에 둬요.
    • 빌드용 비밀은 레이어에 남기지 않아요. Docker BuildKit의 비밀 마운트(RUN --mount=type=secret)로 빌드 중에만 쓰게 하고, 멀티 스테이지 빌드로 최종 이미지에는 결과물만 담아요.

    운영에서 알아채는 법

    • 이미지 스캐너(Trivy 등)를 CI에 넣어 알려진 취약점과 이미지 안의 비밀을 찾아요. 운영 중인 이미지도 주기적으로 다시 스캔해요. 새 취약점은 배포 뒤에 발표되기 때문이에요.
    • Falco 같은 런타임 탐지 도구로 "컨테이너 안에서 셸 실행", "민감한 파일 읽기" 같은 이상 행동에 알림을 걸어요. 주문 API 컨테이너에서 셸이 뜰 일은 없어요.
    핵심 정리
    • 컨테이너 = 네임스페이스(보이는 범위) + cgroup(쓸 수 있는 양)이 걸린 프로세스. 커널 공유
    • 컨테이너 안의 free, top은 호스트 전체를 보여줌. 한도는 cgroup에서
    • 이미지는 읽기 전용 레이어. 자주 바뀌는 것을 위에. 컨테이너 안에 쓴 것은 사라짐
    셀프 체크
    1. Dockerfile에서 소스 코드 복사를 의존성 설치보다 뒤에 두는 이유를 설명하세요.
    답 보기

    이미지 빌드는 명령마다 레이어를 만들고, 입력이 바뀌지 않은 레이어는 캐시를 재사용해요. 그런데 어떤 레이어가 바뀌면 그 뒤의 레이어는 전부 다시 만들어야 해요. 소스 코드는 커밋마다 바뀌고 의존성 목록은 가끔만 바뀌어요. 소스 복사를 먼저 두면 코드 한 줄만 고쳐도 의존성 설치를 매번 다시 해요. 의존성 목록 파일만 먼저 복사해 설치하고 그 뒤에 소스를 복사하면, 의존성이 그대로인 한 설치 레이어는 캐시에서 가져와요.

    2부 쿠버네티스 핵심

    2장 아키텍처와 선언적 모델

    원하는 상태를 적으면 시스템이 맞춘다

    문제: apply는 성공했는데 서비스가 안 떴다

    주문 API의 새 버전을 kubectl apply로 배포했어요. "configured"라고 성공 메시지가 떴고 배포 스크립트도 성공으로 끝났어요. 그런데 30분 뒤 확인해 보니 새 버전 Pod는 하나도 떠 있지 않았어요. 성공했다는 것은 무엇이 성공했다는 뜻이었을까요?

    명령이 아니라 원하는 상태를 적는다

    "컨테이너 3개를 띄워라"는 명령이에요. 하나가 죽으면 누군가 다시 명령해야 해요. 쿠버네티스는 "주문 API 컨테이너가 3개 떠 있어야 한다"는 원하는 상태를 받아요. 그러면 시스템이 현재 상태를 계속 지켜보다가, 원하는 상태와 다르면 맞추는 행동을 해요. 하나가 죽으면 아무도 명령하지 않아도 새로 띄워요.

    조정 루프

    쿠버네티스의 거의 모든 동작이 이 구조예요. 원하는 상태를 읽고, 현재 상태를 관찰하고, 차이가 있으면 줄이는 행동을 하고, 이것을 계속 반복해요. 이 일을 하는 프로그램을 컨트롤러라고 하고, 리소스 종류마다 컨트롤러가 있어요.

    그래서 위 문제의 답이 나와요. apply의 성공은 "원하는 상태가 저장됐다"는 뜻이에요. 그 상태를 실제로 만드는 일은 그 뒤에 컨트롤러들이 따로 해요. 이번에는 새 이미지의 태그를 잘못 적어서 이미지를 받지 못했고(ImagePullBackOff), 그 사실은 apply가 아니라 리소스의 상태와 이벤트에 남아 있었어요.

    누가 무엇을 하나

    컨트롤 플레인에는 네 가지가 있어요. API 서버는 모든 읽기와 쓰기의 유일한 창구예요. etcd는 클러스터의 원하는 상태와 현재 상태를 전부 저장하는 저장소예요. 스케줄러는 새 Pod를 어느 노드에 둘지 정하고, 컨트롤러 매니저는 기본 컨트롤러들을 실행해요. 각 노드에는 자기 노드에 배정된 Pod의 컨테이너를 실제로 띄우고 상태를 보고하는 kubelet이 있어요. 이들은 서로 직접 대화하지 않고 전부 API 서버를 통해 상태를 읽고 써요.

    리소스의 모양

    모든 리소스는 spec(원하는 상태, 사람이 씀)과 status(현재 상태, 시스템이 씀)를 가져요. 리소스에는 레이블(app=order-api)을 붙이고, 다른 리소스가 레이블 셀렉터로 골라요. Service가 "어느 Pod에 트래픽을 보낼지"를 Pod 이름이 아니라 레이블로 고르는 식이에요. 이름은 계속 바뀌지만 레이블은 유지되니까요.

    백엔드에서는 클러스터 상태는 매니페스트 파일로 저장소에 두고 거기서 적용하세요. 누군가 kubectl edit로 직접 고친 것은 기록이 남지 않고, 다음 적용 때 덮어써지거나 영영 어긋난 채로 남아요. 문제가 생기면 kubectl describe의 Events와 kubectl get -o yaml의 status를 먼저 보세요. 시스템이 무엇을 하려다 왜 못 했는지가 거기 적혀 있어요.
    시니어 심화 컨트롤러는 "무슨 일이 일어났는가"(이벤트)가 아니라 "지금 상태가 어떤가"를 보고 움직여요. 이 성질이 시스템을 튼튼하게 만들지만, 대가로 "적용했다"와 "도달했다"가 다르다는 점을 다뤄야 해요.

    상황 1: 배포 파이프라인이 성공했는데 배포는 실패

    CI 파이프라인은 kubectl apply가 성공하면 "배포 완료"를 알렸어요. 어느 날 새 이미지의 태그가 잘못돼 Pod가 이미지를 받지 못했는데(ImagePullBackOff), 파이프라인은 초록색이었어요. 옛 버전이 계속 돌고 있다는 것을 사흘 뒤에야 알았어요.

    1. apply는 "원하는 상태"를 API 서버에 저장하는 것까지만 해요. 저장에 성공하면 성공이에요.
    2. 실제로 그 상태에 도달하는 일은 컨트롤러가 비동기로 해요. 이미지 받기, 스케줄링, 준비 상태 검사는 그 뒤의 일이에요.
    3. 그래서 apply의 성공은 배포의 성공을 뜻하지 않아요.

    해결: 배포 파이프라인은 apply 뒤에 kubectl rollout status deployment/order-api --timeout=5m처럼 실제 도달을 기다리고 확인해요. 시간 안에 도달하지 않으면 실패로 처리하고 알려요. Deployment의 progressDeadlineSeconds를 설정하면 쿠버네티스도 진행이 멈춘 배포를 실패 상태로 표시해요.

    상황 2: 직접 만든 오퍼레이터가 리소스를 두 개씩 만듦

    팀이 만든 오퍼레이터가 "DB 사용자 생성 요청" 리소스를 보고 DB 계정을 만들어요. 오퍼레이터가 재시작될 때마다 같은 계정을 또 만들려다 에러가 나고, 어떤 경우엔 비슷한 이름의 계정이 두 개 생겼어요.

    1. 조정 함수는 같은 상태를 보고 여러 번 실행될 수 있어요. 재시작, 재시도, 주기적 재동기화 때마다 실행돼요.
    2. "생성 요청이 왔으니 만든다"는 이벤트식 코드는 실행될 때마다 만들어요.

    해결: 조정 함수는 몇 번을 실행해도 안전하게 만들어요. "지금 있는가"를 먼저 확인하고, 이미 원하는 상태면 아무것도 하지 않아요. 외부 자원의 이름은 리소스의 UID처럼 결정적인 값으로 정해서, 두 번 실행돼도 같은 자원을 가리키게 해요.

    API 서버도 공유 자원이에요

    API 서버와 etcd는 모든 컨트롤러와 사용자가 거치는 곳이에요. 전체 목록을 몇 초마다 반복해서 가져오는 스크립트, 리소스를 수만 개 만드는 작업은 클러스터 전체를 느리게 해요. 직접 만드는 도구는 목록을 한 번 가져온 뒤 변경만 구독하는 방식(informer, watch)으로 만들어요.

    운영에서 알아채는 법

    • Deployment의 원하는 복제 수와 실제 준비된 복제 수가 일정 시간 이상 다르면 알림을 보내요(kube-state-metrics의 지표로 만들 수 있어요).
    • API 서버의 요청 지연과 클라이언트별 요청 수를 봐요. 특정 도구가 요청의 대부분을 차지하면 그 도구가 범인이에요.
    핵심 정리
    • 선언형: 원하는 상태를 저장하면 컨트롤러가 현재 상태를 맞춤
    • apply 성공 = 원하는 상태 저장. 실제 도달은 status와 이벤트로 확인
    • 모든 구성 요소는 API 서버를 거침. 리소스 연결은 레이블 셀렉터
    셀프 체크
    1. kubectl apply가 성공했는데 애플리케이션이 뜨지 않았습니다. 왜 이런 일이 가능한가요?
    답 보기

    apply의 성공은 API 서버가 원하는 상태를 받아 저장했다는 뜻이에요. 그 상태를 실제로 만드는 일은 그 뒤에 컨트롤러, 스케줄러, kubelet이 따로 해요. 그 과정에서 이미지를 받지 못하거나, 자원이 부족해 배치할 노드가 없거나, 컨테이너가 시작하자마자 죽거나, 준비 상태 검사를 통과하지 못할 수 있어요. 이런 실패는 apply의 결과가 아니라 리소스의 status와 이벤트에 나타나요. 그래서 배포 절차는 적용 후 롤아웃 상태를 확인하는 단계를 포함해야 해요.

    3장 Pod, Deployment, 배포 전략

    무엇을 띄우고, 새 버전으로 어떻게 바꾸는가

    문제: 배포 중에 옛 코드가 에러를 냈다

    주문 API 새 버전에 "주문 테이블의 coupon_code 컬럼 삭제"를 넣어 배포했어요. 마이그레이션은 배포 시작 때 실행됐어요. 그런데 배포가 끝나기까지 몇 분 동안 주문 조회 에러가 쏟아졌어요. 새 버전은 그 컬럼을 안 쓰는데, 에러는 어디서 났을까요?

    Pod: 배포의 가장 작은 단위

    Pod는 컨테이너 하나 이상을 묶은 단위예요. 같은 Pod의 컨테이너는 네트워크를 공유해서 같은 IP를 쓰고 서로 localhost로 통신해요. 보통은 Pod 하나에 컨테이너 하나예요. 여러 개를 넣는 것은 생명 주기를 함께해야 하는 보조 프로그램(로그 수집기, 프록시)일 때뿐이에요. 주문 API와 DB를 한 Pod에 넣지 않는 이유는 둘을 따로 늘리고 따로 재시작해야 하기 때문이에요.

    Pod는 일회용이에요. 죽으면 고쳐지는 것이 아니라 새 Pod가 만들어지고, 새 Pod는 이름도 IP도 달라요.

    Deployment: 개수를 지키고 버전을 바꾼다

    Pod를 직접 만들지 않고 Deployment를 만들어요. Deployment는 Pod의 개수를 유지하는 ReplicaSet을 관리하고, Pod 템플릿(이미지 버전 등)이 바뀔 때마다 새 ReplicaSet을 만들어 옛것에서 새것으로 옮겨 가요.

    롤링 업데이트: 조금씩 바꾼다

    기본 배포 방식은 롤링 업데이트예요. 새 버전 Pod를 조금 띄우고, 그것이 준비 상태가 되면 옛 버전 Pod를 조금 내리는 것을 반복해요. 원하는 개수보다 몇 개까지 더 띄울지(maxSurge), 몇 개까지 모자라도 될지(maxUnavailable)로 속도를 정해요. 그래서 서비스가 멈추지 않아요.

    대가는 그림 그대로예요. 배포가 진행되는 동안 옛 버전과 새 버전이 함께 트래픽을 받아요. 위 문제에서 컬럼이 삭제된 순간에도 아직 내려가지 않은 옛 버전 Pod들이 있었고, 그 Pod들이 coupon_code를 조회하다 에러를 냈어요. 그래서 컬럼 삭제는 "먼저 그 컬럼을 안 쓰는 코드를 배포해 모든 Pod가 바뀐 것을 확인하고, 다음 배포에서 컬럼을 지운다"로 나눠야 해요(API 챕터 4장의 확장-축소와 같은 원리).

    다른 워크로드 종류

    고정된 이름과 전용 디스크가 필요한 것(DB, 메시지 브로커)은 StatefulSet(6장), 모든 노드에 하나씩 떠야 하는 것(로그 수집기)은 DaemonSet, 끝나는 작업은 Job, 주기적인 작업(매일 밤 정산)은 CronJob이에요.

    백엔드에서는 롤백은 kubectl rollout undo로 이전 ReplicaSet으로 돌아가는 거예요. 빠르지만 DB에 일어난 변경은 돌아가지 않아요. 새 버전이 새 형식으로 데이터를 썼다면 옛 버전이 그것을 읽을 수 있어야 롤백이 돼요. 배포 하나에 "코드 변경"과 "되돌릴 수 없는 데이터 변경"을 함께 넣지 마세요.
    시니어 심화 롤링 업데이트는 검증 장치가 아니에요. 준비 상태 검사만 통과하면 끝까지 진행하므로, 뜨기는 하는데 잘못 동작하는 버전도 전체로 퍼져요.

    상황

    할인 계산 로직을 바꾼 새 버전을 롤링 업데이트로 배포했어요. 5분 만에 모든 Pod가 새 버전이 됐어요. 그런데 특정 쿠폰 조합에서 할인이 두 번 적용되는 버그가 있었어요. 에러는 하나도 없었고 응답 코드는 모두 200이었어요. 두 시간 뒤 정산팀이 이상한 매출을 발견했을 때는 이미 수천 건이 처리된 뒤였어요.

    깨지는 과정

    1. 롤링 업데이트는 새 Pod가 준비 상태 검사를 통과하면 옛 Pod를 하나씩 내려요. 준비 상태 검사는 "요청을 받을 수 있는가"만 봐요.
    2. 계산이 틀리는 버그는 준비 상태 검사도, 에러율도 건드리지 않아요.
    3. 그래서 롤링 업데이트는 몇 분 안에 버그를 전체 트래픽으로 퍼뜨려요. 되돌릴 때도 같은 시간이 걸려요.

    해결책

    • 카나리 배포: 새 버전을 전체 트래픽의 5% 같은 일부에만 먼저 보내요. 그 5%와 나머지 95%의 에러율, 응답 시간, 그리고 업무 지표(주문 성공률, 주문당 평균 할인율)를 비교한 뒤 문제없으면 넓혀요. 위 버그는 "주문당 할인율"이 카나리에서만 튀는 것으로 잡혔을 거예요. 문제가 보이면 5%만 되돌리면 돼요.
    • 블루-그린 배포: 새 버전을 옛 버전과 같은 규모로 통째로 띄워 두고, 내부 확인이 끝나면 트래픽을 한 번에 넘겨요. 되돌릴 때도 한 번에 넘기면 돼서 롤백이 가장 빨라요. 대신 잠깐 두 배의 자원이 필요해요.
    • 분석을 자동화해요. 둘 다 Deployment만으로는 안 되고 Argo Rollouts나 Flagger 같은 도구가 필요해요. 이 도구들은 단계마다 지표를 조회해서 기준을 넘으면 자동으로 되돌려요.
    • 기능 플래그도 함께 써요. 위험한 로직은 배포와 별개로 플래그로 켜고 끄게 하면, 배포를 되돌리지 않고 기능만 끌 수 있어요.

    클러스터 작업에 대비하기

    노드 업그레이드나 축소처럼 클러스터 작업으로 Pod가 쫓겨날 때도 같은 위험이 있어요. 노드를 비우는 작업(drain)이 주문 API Pod를 한꺼번에 내리면 서비스가 멈춰요. PodDisruptionBudget으로 "주문 API는 최소 2개는 떠 있어야 한다"(minAvailable: 2)를 정해 두면, 쿠버네티스가 그 조건을 지키며 하나씩 내려요.

    운영에서 알아채는 법

    • 배포 버전별로 에러율과 업무 지표를 나눠 볼 수 있게 지표에 버전 라벨을 붙여요. 버전을 나눠 볼 수 없으면 카나리를 해도 비교할 수 없어요.
    • 모든 Deployment에 PodDisruptionBudget이 있는지 주기적으로 검사해요.
    핵심 정리
    • Pod = 일회용, IP가 바뀜. 직접 만들지 않고 Deployment로
    • 롤링 업데이트: 새 Pod가 준비돼야 진행. 진행 중에는 두 버전이 공존
    • 상태가 있으면 StatefulSet, 노드마다면 DaemonSet, 끝나는 작업은 Job·CronJob
    셀프 체크
    1. 롤링 업데이트로 배포할 때 DB 컬럼 삭제를 같은 배포에 넣으면 왜 문제가 되나요?
    답 보기

    롤링 업데이트는 옛 Pod와 새 Pod가 한동안 함께 트래픽을 받는 방식이에요. 컬럼을 삭제하는 스키마 변경이 적용된 순간에도 아직 내려가지 않은 옛 Pod가 그 컬럼을 읽거나 쓰려다 에러를 내요. 그래서 먼저 그 컬럼을 쓰지 않는 코드를 배포해 모든 Pod가 바뀐 것을 확인하고, 다음 배포에서 컬럼을 삭제해야 해요. 문제가 생겨 이전 버전으로 롤백할 때도 컬럼이 남아 있어야 옛 코드가 동작해요.

    4장 Service와 네트워킹

    계속 바뀌는 Pod에 변하지 않는 주소를 준다

    문제: Pod를 늘렸는데 부하가 그대로다

    주문 API가 재고 서비스를 gRPC로 호출해요. 재고 서비스가 바빠져서 Pod를 3개에서 10개로 늘렸는데, 기존 3개의 CPU는 여전히 꽉 차 있고 새 7개는 놀고 있어요. 쿠버네티스가 부하를 나눠 주지 않는 걸까요?

    Service: 바뀌지 않는 주소

    Pod의 IP는 Pod가 다시 만들어질 때마다 바뀌어요. 주문 API가 재고 서비스 Pod의 IP를 직접 들고 있으면, 재고 서비스를 배포할 때마다 연결이 끊겨요. Service는 변하지 않는 가상 IP와 DNS 이름(stock.shop.svc.cluster.local, 같은 네임스페이스에서는 그냥 stock)을 주고, 레이블 셀렉터에 맞는 Pod들로 트래픽을 나눠 보내요.

    중요한 점은 Service가 준비 상태인 Pod만 대상에 넣는다는 거예요. 준비 상태 검사(7장)에 실패한 Pod는 자동으로 빠져요. 그래서 막 뜬 Pod나 일시적으로 바쁜 Pod에는 트래픽이 가지 않아요.

    나누는 단위는 연결이다

    그런데 Service의 기본 분산은 연결을 맺는 순간 대상 Pod를 고르는 방식이에요. HTTP/1.1처럼 요청마다 연결을 새로 맺거나 짧게 쓰면 잘 분산돼요. 하지만 gRPC는 HTTP/2 위에서 연결 하나를 오래 유지하며 그 위로 수많은 요청을 보내요. 주문 API 서버가 처음 연결을 맺을 때 재고 Pod 3개 중 하나에 붙었다면, 그 뒤의 모든 요청이 그 Pod로만 가요. Pod를 10개로 늘려도 이미 맺어진 연결은 그대로라 새 Pod에는 요청이 가지 않아요.

    요청 단위로 나누려면 클라이언트가 Pod 주소 목록을 직접 받아 요청마다 대상을 고르거나(가상 IP 없이 Pod 주소를 돌려주는 Headless Service와 클라이언트 쪽 로드밸런싱), 요청을 이해하는 프록시를 사이에 둬야 해요. 서버가 연결의 최대 수명을 정해 주기적으로 다시 맺게 하는 것도 도움이 돼요.

    클러스터 밖에서 들어오는 길

    Service에는 종류가 있어요. 클러스터 안에서만 쓰는 ClusterIP(기본), 모든 노드의 특정 포트로 여는 NodePort, 클라우드 로드밸런서를 만들어 외부에 여는 LoadBalancer예요. 외부 HTTP 트래픽은 보통 Ingress로 받아요. 호스트 이름과 경로로 여러 Service에 나눠 주고(shop.com/api/orders → 주문 API), TLS도 여기서 처리해요. 그리고 기본적으로 모든 Pod는 서로 통신할 수 있으니, NetworkPolicy로 "결제 Pod에는 주문 API만 접근할 수 있다"처럼 제한해요.

    백엔드에서는 로드밸런서 뒤에서 클라이언트의 실제 IP는 X-Forwarded-For 헤더로 와요(네트워크 챕터 5장). 그리고 외부 도메인을 많이 호출하는 서비스라면 DNS 설정을 확인하세요. 기본 설정에서는 점이 적은 이름에 클러스터의 검색 도메인을 차례로 붙여 보느라, 외부 결제사 도메인을 조회할 때마다 실패하는 조회가 여러 번 먼저 나가요. 끝에 점을 붙인 전체 이름(api.pg.com.)을 쓰거나 노드 로컬 DNS 캐시를 둬요.
    시니어 심화 Pod가 종료될 때 그 Pod를 Service 대상에서 빼는 정보는 비동기로 퍼져요. 그리고 Service의 가상 IP를 구현하는 장치에도 숨은 한도가 있어요.

    상황 1: 배포할 때마다 연결 거부

    주문 API를 배포할 때마다 다른 서비스에서 "connection refused" 에러가 수십 건씩 났어요. 애플리케이션은 종료 신호를 받으면 진행 중인 요청을 마치고 종료하도록 잘 만들어져 있었어요.

    1. Pod가 종료되기 시작하면, 쿠버네티스는 두 가지를 동시에 해요. 컨테이너에 종료 신호를 보내고, 엔드포인트 목록(EndpointSlice)에서 그 Pod를 빼요.
    2. 엔드포인트 변경은 모든 노드의 kube-proxy(전달 규칙)와 Ingress 컨트롤러에 퍼지기까지 수백 ms에서 몇 초가 걸려요.
    3. 애플리케이션은 종료 신호를 받자마자 새 연결을 받지 않고 내려가요. 그 사이 아직 변경을 모르는 노드에서 보낸 새 요청은 이미 닫힌 포트로 가서 연결 거부를 받아요.

    해결: 종료 신호를 받아도 몇 초 동안은 평소처럼 요청을 받다가 내려가요. 쿠버네티스에서는 preStop 훅에 5~10초의 sleep을 넣는 방식이 흔해요(7장, 네트워크 챕터 2.4 시니어). 이 시간과 요청 마무리 시간을 합친 것이 terminationGracePeriodSeconds보다 짧아야 해요.

    상황 2: 트래픽이 많을 때만 간헐적인 연결 실패

    세일 때 주문 API에서 재고 서비스로 가는 호출이 0.5% 정도 연결 단계에서 실패했어요. 재고 서비스는 한가했어요. 노드의 커널 로그에는 "nf_conntrack: table full, dropping packet"이 찍혀 있었어요.

    1. Service의 가상 IP는 각 노드에서 주소 변환(NAT)으로 구현돼요. 커널은 변환한 연결마다 연결 추적 테이블(conntrack)에 항목을 남겨요.
    2. 주문 API는 재고 서비스를 부를 때마다 새 HTTP 연결을 맺었어요. 닫힌 연결의 항목도 한동안 테이블에 남아요.
    3. 세일 때 연결 생성이 몰리자 테이블이 가득 찼고, 커널은 새 연결의 패킷을 버렸어요.

    해결: 연결을 재사용해요. HTTP 클라이언트의 커넥션 풀과 keep-alive를 켜면 새 연결 자체가 거의 생기지 않아요(네트워크 챕터 1.4 시니어의 포트 고갈과 같은 처방이에요). 그래도 부족하면 노드의 nf_conntrack_max를 늘려요. gRPC처럼 오래 사는 연결은 반대로 한 Pod에 몰리지 않게 연결 수명을 둬요.

    운영에서 알아채는 법

    • 배포 시각에 호출하는 쪽의 "connection refused"가 튀면 종료 순서 문제예요.
    • 노드의 conntrack 사용량(node_nf_conntrack_entries ÷ node_nf_conntrack_entries_limit)을 지표로 남기고 80%에서 알림을 걸어요.
    • 노드 커널 로그의 "table full" 메시지를 로그 수집 대상에 넣어요.
    핵심 정리
    • Pod IP는 바뀜. Service가 고정 주소와 DNS를 주고 준비된 Pod에만 보냄
    • 분산 단위는 연결. 오래 사는 연결(gRPC)은 한 Pod에 몰림
    • 외부는 Ingress로, Pod 간 통신은 NetworkPolicy로 제한
    셀프 체크
    1. gRPC 서비스의 Pod를 3개에서 10개로 늘렸는데 기존 Pod의 부하가 줄지 않았습니다. 이유는 무엇인가요?
    답 보기

    gRPC는 HTTP/2 위에서 연결 하나를 오래 유지하며 그 위로 많은 요청을 보내요. Service의 부하 분산은 연결을 맺는 순간에 대상 Pod를 고르는 방식이라, 이미 맺어진 연결은 처음 고른 Pod에 계속 붙어 있어요. 새 Pod를 추가해도 클라이언트가 새 연결을 맺지 않는 한 요청이 가지 않아요. 요청 단위로 나누려면 클라이언트가 Pod 주소 목록을 받아 요청마다 대상을 고르게 하거나, 요청을 이해하는 프록시를 사이에 둬요. 서버가 연결의 최대 수명을 정해 주기적으로 다시 맺게 하는 것도 완화책이에요.

    5장 리소스 관리와 스케줄링

    requests는 배치의 기준, limits는 실행 중의 상한

    문제: CPU는 남는데 응답이 튄다, 그리고 가끔 죽는다

    주문 API Pod에 CPU limit 1개, 메모리 limit 2GB를 줬어요. 대시보드의 CPU 사용률은 평균 40%인데 p99 응답 시간이 자꾸 튀어요. 그리고 가끔 Pod 상태에 OOMKilled가 찍히며 재시작돼요. CPU도 메모리도 한도를 걸었는데 증상이 왜 이렇게 다를까요?

    requests와 limits는 하는 일이 다르다

    requests는 이 컨테이너에 보장해 줄 양이에요. 스케줄러는 Pod를 배치할 때 노드에 남은 requests 여유만 보고 정해요. 실제로 얼마나 쓰는지는 보지 않아요. limits는 이 컨테이너가 넘을 수 없는 양이에요. 실행 중에 커널(cgroup)이 강제해요.

    CPU와 메모리는 넘을 때의 결과가 다르다

    CPU는 덜 주면 느려질 뿐인 자원이에요. 그래서 limit을 넘으려 하면 죽이지 않고 멈춰 세워요. 커널은 짧은 주기(보통 100ms)마다 쓸 수 있는 CPU 시간을 나눠 주는데, 주문 API처럼 스레드가 많은 프로세스는 여러 스레드가 동시에 돌면서 그 주기의 할당량을 몇십 밀리초 만에 다 써 버려요. 그러면 주기의 나머지 시간 동안 모든 스레드가 멈춰요(스로틀링). 1초 평균 사용률은 40%로 낮아 보여도, 요청 하나가 그 멈춤에 걸리면 수십 밀리초가 그냥 더해져요. 위 문제의 응답 시간 튐이 이것이에요.

    메모리는 덜 줄 방법이 없는 자원이에요. 그래서 limit을 넘으면 커널이 프로세스를 죽여요(OOM kill). JVM의 힙이 아니라 프로세스 전체 메모리가 기준이라, 힙 외 메모리(JVM 챕터 3장)를 생각하지 않고 힙을 limit에 가깝게 잡으면 이렇게 돼요.

    QoS: 노드가 모자랄 때 누가 먼저 나가나

    노드의 메모리가 부족해지면 kubelet이 Pod를 쫓아내요. 순서는 requests와 limits를 어떻게 줬느냐로 정해지는 QoS 등급이 정해요. 모든 컨테이너가 requests와 limits를 같게 준 Guaranteed는 가장 나중에, requests가 limits보다 작은 Burstable은 그다음, 둘 다 안 준 BestEffort는 가장 먼저 쫓겨나요.

    어디에 배치할지 정하기

    특정 조건의 노드에만 두려면 노드 셀렉터나 어피니티를, 특정 노드에 아무나 오지 못하게 하려면 테인트와 톨러레이션을 써요. 주문 API의 Pod 3개가 같은 노드에 몰려 있으면 노드 하나가 죽을 때 셋이 함께 죽어요. 토폴로지 분산 제약으로 서로 다른 노드와 가용 영역에 흩어 놓으세요. Pod가 Pending에 머물면 조건에 맞는 노드가 없는 거예요. 이유는 이벤트에 나와요.

    백엔드에서는 requests는 실제 사용량 지표를 보고 정하세요. 실제보다 훨씬 작게 잡으면 한 노드에 Pod가 과하게 몰려 서로 자원을 빼앗고, 훨씬 크게 잡으면 노드가 비어 있는데도 배치가 안 돼 비용이 새요. JVM은 메모리 limit의 비율로 힙을 잡게 하고(-XX:MaxRAMPercentage), 힙 밖 메모리를 위한 여유를 남겨요. JVM 버전이 컨테이너의 CPU 한도를 인식하는지도 확인하세요. 호스트의 코어 수를 기준으로 GC 스레드와 스레드풀을 만들면 스로틀링이 더 심해져요.
    시니어 심화 CPU limit과 스로틀링은 OS 챕터 7장 시니어에서 다뤘어요. 여기서는 메모리 쪽을 볼게요. 메모리 requests를 실제보다 낮게 잡으면, 노드가 바쁠 때 가장 먼저 쫓겨나요.

    상황

    주문 API Pod는 메모리 requests 512Mi, limits 2Gi로 설정돼 있었고 평소 1.5Gi를 썼어요. 세일 날 같은 노드의 다른 Pod들도 메모리를 많이 쓰면서 노드 메모리가 부족해졌어요. 쿠버네티스는 주문 API Pod를 쫓아냈고(eviction), 세일의 가장 바쁜 순간에 주문 API의 절반이 재시작했어요.

    깨지는 과정

    1. 스케줄러는 requests를 보고 노드에 Pod를 배치해요. requests를 512Mi로 적으면 그만큼만 자리를 잡아요. 실제 1.5Gi를 쓰는 Pod들이 그런 식으로 노드에 빽빽하게 들어가요.
    2. 모두가 동시에 메모리를 많이 쓰면 노드의 실제 메모리가 모자라요.
    3. 쿠버네티스(kubelet)는 노드를 지키려고 Pod를 쫓아내요. 이때 requests보다 많이 쓰고 있는 Pod를 먼저 쫓아내요. 주문 API는 requests의 세 배를 쓰고 있었으니 첫 번째 대상이었어요.
    4. 노드가 바빠지는 시점은 대개 트래픽이 많은 시점이에요. 최악의 순간에 Pod가 사라져요.

    해결책

    • 메모리는 requests와 limits를 같게 둬요. 실제 사용량(최대치 기준)에 맞춰 둘을 같게 잡으면, 스케줄러가 정확한 자리를 잡고, Pod가 requests를 넘을 일이 없어 쫓겨날 우선순위가 낮아져요. CPU와 메모리 모두 requests와 limits가 같으면 Guaranteed 등급이 돼서 가장 마지막에 쫓겨나요.
    • CPU는 limit을 빼는 선택지도 있어요. CPU는 모자라면 느려질 뿐 죽지 않아요. requests만 정확히 두고 limit을 빼면 스로틀링이 사라져요. 지연에 민감한 서비스는 limit 없이, 이웃을 괴롭힐 수 있는 배치는 limit을 두는 식으로 나눠요.
    • 실제 사용량을 보고 정해요. requests는 추측이 아니라 지표로 정해요. 지난 2주의 p95~최대 사용량을 기준으로 잡고, VPA(Vertical Pod Autoscaler)의 추천 모드로 권장값을 참고할 수 있어요.
    • 팀이 여럿이면 네임스페이스에 상한과 기본값을 둬요. ResourceQuota로 네임스페이스의 총량을 제한하고, LimitRange로 값을 지정하지 않은 컨테이너에 기본값을 넣어요. requests 없이 뜬 Pod(BestEffort)는 노드 자원을 마음대로 쓰다가 노드 전체를 불안정하게 만들어요.
    • 중요한 서비스에 우선순위를 줘요. PriorityClass로 주문, 결제 Pod의 우선순위를 높이면 자원이 모자랄 때 낮은 우선순위의 Pod가 먼저 밀려나요.

    운영에서 알아채는 법

    • Pod의 실제 메모리 사용량 ÷ requests 비율을 지표로 봐요. 1을 크게 넘는 Pod가 많다면 쫓겨날 후보들이에요.
    • 쿠버네티스 이벤트의 Evicted와 노드의 MemoryPressure 상태에 알림을 걸어요.
    핵심 정리
    • requests = 스케줄링 기준(보장), limits = 실행 중 상한(강제)
    • CPU 초과 → 스로틀링(느려짐, 평균 사용률은 낮게 보임), 메모리 초과 → OOM kill
    • QoS 등급이 축출 순서를 결정. 토폴로지 분산으로 장애 영역을 나눔
    셀프 체크
    1. 컨테이너가 메모리 limit을 넘었을 때와 CPU limit을 넘으려 할 때 각각 어떤 일이 일어나나요?
    답 보기

    메모리는 덜 줄 방법이 없는 자원이라, 한도를 넘으면 커널이 컨테이너의 프로세스를 강제 종료해요. Pod 상태에 OOMKilled로 표시되고 재시작 정책에 따라 다시 떠요. CPU는 덜 주면 느려질 뿐인 자원이라 프로세스를 죽이지 않아요. 정해진 주기 안에서 쓸 수 있는 CPU 시간을 다 쓰면 다음 주기가 올 때까지 실행을 멈춰요. 프로세스는 살아 있지만 그 시간만큼 응답이 늦어지고, 이것이 응답 시간의 튐으로 나타나요.

    6장 설정, 시크릿, 상태 저장

    이미지는 그대로 두고 환경만 바꾼다

    문제: 설정을 바꿨는데 반영이 안 된다

    결제 대행사의 타임아웃 값을 ConfigMap에서 3초에서 5초로 바꿨어요. 그런데 주문 API는 여전히 3초에 타임아웃을 냈어요. ConfigMap을 다시 확인해 봐도 5초로 잘 바뀌어 있었어요.

    ConfigMap과 Secret

    설정을 이미지에서 떼어 내면 같은 이미지를 개발, 스테이징, 운영에서 그대로 쓸 수 있어요. 일반 설정은 ConfigMap, 비밀번호나 API 키는 Secret에 둬요. 컨테이너에 넣는 방법은 두 가지이고, 바뀐 값이 반영되는 방식이 달라요.

    환경 변수로 넣으면 값은 컨테이너가 시작할 때 한 번 정해져요. ConfigMap을 바꿔도 Pod를 다시 띄우기 전에는 반영되지 않아요. 위 문제가 이것이에요. 볼륨으로 마운트하면 파일로 보이고, ConfigMap을 바꾸면 얼마 뒤 파일 내용이 갱신돼요. 하지만 앱이 시작할 때 한 번만 읽고 메모리에 들고 있으면 역시 옛 값을 써요. 파일이 바뀐 것을 감지해 다시 읽는 코드가 있어야 효과가 있어요.

    가장 확실한 방법은 설정이 바뀌면 롤링 재시작이 일어나게 하는 거예요. 설정 내용의 해시를 Pod 템플릿의 애너테이션에 넣어 두면, 설정이 바뀔 때 템플릿이 바뀐 것으로 인식되어 새 Pod로 교체돼요.

    Secret은 암호화가 아니다

    Secret의 값은 Base64로 인코딩돼 있을 뿐이에요. 기본 설정에서는 etcd에 사실상 평문으로 저장되고, Secret을 읽을 권한이 있는 누구나 볼 수 있어요. etcd에 저장할 때의 암호화를 켜고, 접근 권한(RBAC)으로 Secret을 읽을 수 있는 주체를 좁혀요. 매니페스트를 저장소에 둘 때 Secret을 평문으로 커밋하지 말고, 외부 비밀 저장소에서 동기화하거나 암호화된 형태로 둬요.

    볼륨: 컨테이너가 사라져도 남아야 하는 것

    컨테이너의 파일 시스템은 재시작하면 초기화돼요(1장). Pod 안의 컨테이너끼리 잠깐 파일을 주고받는 용도면 Pod와 수명을 같이하는 emptyDir을 써요. Pod가 사라져도 남아야 하는 데이터는 PersistentVolumeClaim으로 "이만큼의 디스크가 필요하다"고 요청하고, 스토리지 클래스가 실제 디스크를 만들어 붙여 줘요.

    StatefulSet

    Deployment의 Pod는 서로 구분되지 않고 아무것이나 교체해도 돼요. DB나 Kafka 브로커는 그렇지 않아요. 각자 자기 데이터를 갖고 있고 서로를 이름으로 찾아요. StatefulSet은 Pod마다 고정된 이름(db-0, db-1)과 전용 디스크를 주고, 다시 만들어져도 같은 이름과 같은 디스크로 돌아오게 해요. 생성과 종료도 순서대로 해요.

    하지만 StatefulSet은 Pod와 디스크를 관리할 뿐, 복제 구성, 장애 조치, 백업, 버전 업그레이드 같은 DB 운영 지식은 갖고 있지 않아요. 그 부분은 그 DB용 오퍼레이터나 사람이 맡아야 해요. 관리형 DB 서비스를 쓸 수 있다면 보통 그쪽이 운영 부담이 훨씬 적어요.

    백엔드에서는 환경 변수로 넣은 비밀은 프로세스 목록, 크래시 덤프, 디버그 엔드포인트로 새기 쉬워요. 민감한 값은 파일로 마운트하는 편이 나아요. 그리고 애플리케이션이 시작할 때 설정 전체를 로그로 찍는 코드가 없는지 확인하세요. 스프링 부트의 액추에이터 env 엔드포인트를 인증 없이 열어 두는 것도 같은 유출 경로예요.
    핵심 정리
    • 환경 변수 주입은 재시작해야 반영. 볼륨은 파일이 갱신되지만 앱이 다시 읽어야 함
    • 설정 해시를 Pod 템플릿에 넣어 변경 시 자동 롤링 재시작
    • Secret은 Base64일 뿐. StatefulSet = 고정 이름 + 전용 디스크, DB 운영 지식은 별도
    셀프 체크
    1. ConfigMap의 값을 수정했는데 애플리케이션이 옛 값을 계속 씁니다. 가능한 원인과 해결을 말해보세요.
    답 보기

    환경 변수로 주입했다면 값은 컨테이너가 시작할 때 한 번 정해지므로 ConfigMap을 바꿔도 실행 중인 Pod에는 반영되지 않아요. Pod를 다시 띄워야 해요. 볼륨으로 마운트했다면 파일은 얼마 뒤 갱신되지만, 앱이 시작할 때 한 번만 읽고 메모리에 들고 있으면 역시 옛 값을 써요. 해결은 설정이 바뀌면 롤링 재시작이 일어나게 하는 거예요. 설정 내용의 해시를 Pod 템플릿의 애너테이션에 넣어 두면 설정 변경이 템플릿 변경으로 인식되어 자동으로 새 Pod로 교체돼요.

    7장 프로브, 종료, 오토스케일링

    배포할 때마다 에러가 몇 건씩 나는 이유

    문제: 배포할 때마다 502가 난다

    주문 API를 배포할 때마다 몇 초 동안 502와 503 에러가 수십 건씩 나요. 롤링 업데이트를 쓰니 무중단이어야 하는데요. 그리고 지난주에는 DB가 잠깐 느려졌을 뿐인데 주문 API Pod가 전부 한꺼번에 재시작되는 일도 있었어요. 두 문제 모두 프로브와 종료 절차에 원인이 있어요.

    세 가지 프로브

    쿠버네티스는 Pod 상태를 세 가지 질문으로 확인해요. 각각 실패했을 때 하는 일이 달라요.

    프로브묻는 것실패하면
    startup시작이 끝났는가그동안 다른 프로브를 미룸. 계속 실패하면 재시작
    readiness지금 트래픽을 받을 수 있는가Service 대상에서 뺌. 재시작하지 않음
    liveness스스로 회복할 수 없는 상태인가컨테이너를 재시작

    지난주의 일괄 재시작은 liveness 검사에서 DB 연결을 확인하고 있었기 때문이에요. DB가 느려지자 모든 Pod의 liveness가 동시에 실패했고, 쿠버네티스는 모든 컨테이너를 재시작했어요. 재시작해도 DB는 그대로니 아무것도 나아지지 않았고, 오히려 모든 Pod가 동시에 다시 뜨면서 DB에 연결 요청이 몰려 회복이 늦어졌어요. liveness는 재시작으로 고칠 수 있는 자기 자신의 문제(교착 상태 등)만 확인해야 해요. 시작이 느린 앱(JVM)에 liveness만 두면 뜨기도 전에 죽은 것으로 판정해 재시작을 반복하니, startup 프로브로 시작 시간을 따로 줘요.

    종료는 두 가지가 동시에 시작된다

    배포 중의 502는 종료 절차에서 나와요. Pod가 종료되기 시작하면 두 가지가 동시에 일어나요. 하나는 이 Pod를 Service 대상에서 빼는 변경이 클러스터 전체로 퍼지는 것이고(4장 시니어 심화), 다른 하나는 컨테이너에 종료 신호(SIGTERM)가 가는 거예요.

    앱이 SIGTERM을 받자마자 내려가면, 아직 대상에서 빠진 사실을 모르는 로드밸런서가 보낸 요청이 연결 거부로 실패해요. 그래서 preStop 훅에서 몇 초 기다린 뒤 종료를 시작해요. 그동안 대상에서 빠진 사실이 퍼져요. 그다음 앱은 SIGTERM을 받으면 새 요청을 받지 않고, 진행 중인 요청을 끝낸 뒤 종료해요. 이 전체가 유예 시간(terminationGracePeriodSeconds, 기본 30초) 안에 끝나야 해요. 넘으면 강제 종료(SIGKILL)돼요.

    오토스케일링

    HPA는 지표(CPU 사용률, 초당 요청 수 같은 사용자 정의 지표)를 보고 Pod 수를 조절해요. 여기서 CPU 사용률은 requests 대비 비율이라, requests를 주지 않으면 계산할 수 없어요. VPA는 실제 사용량을 보고 requests를 조절하고, 클러스터 오토스케일러는 배치할 곳이 없는 Pod가 있으면 노드를 늘리고 비면 줄여요.

    백엔드에서는 앱 쪽에서 할 일은 세 가지예요. SIGTERM을 받으면 우아하게 종료할 것(스프링 부트의 server.shutdown=graceful, 유예 시간보다 짧게), 준비 상태 엔드포인트가 "지금 받을 수 있는가"를 정직하게 답할 것(커넥션 풀 초기화와 워밍업이 끝난 뒤에 통과), 컨테이너의 PID 1이 시그널을 앱에 전달할 것(셸 스크립트로 띄우면 셸이 신호를 삼켜요). 하나라도 빠지면 배포할 때마다 에러가 나요.
    시니어 심화 오토스케일링은 반응이 늦고, 잘못된 지표를 보면 늘려야 할 때 늘리지 않고, 상한을 잘못 잡으면 하위 시스템을 넘어뜨려요.

    상황

    오후 8시 정각에 시작한 타임 세일에서 트래픽이 10초 만에 다섯 배가 됐어요. HPA는 CPU 70%를 기준으로 Pod를 늘리게 돼 있었어요. 첫 3분 동안 주문 API의 에러율은 30%였어요. HPA가 Pod를 늘리기 시작했을 때는 이미 고객들이 떠난 뒤였고, 늘어난 Pod들이 한꺼번에 DB 커넥션을 맺으면서 이번에는 DB가 넘어졌어요.

    깨지는 과정

    1. 반응이 늦어요. 지표 수집 주기, HPA의 판단 주기, Pod 스케줄링, 이미지 받기, 애플리케이션 시작, JVM 워밍업을 더하면 몇 분이에요. 노드까지 늘려야 하면 노드가 뜨는 시간이 더해져요. 10초 만에 오는 트래픽에는 늦어요.
    2. CPU가 맞는 지표가 아니었어요. 주문 API는 대부분의 시간을 DB와 결제사 응답을 기다리며 보내요. 과부하로 요청이 밀려도 CPU는 50%였어요. CPU 기준 HPA는 늘릴 이유를 못 찾았어요.
    3. 상한이 하위 시스템을 넘었어요. HPA 최대 Pod 수는 100이었고 Pod마다 커넥션 풀이 20이었어요. 100 × 20 = 2,000개의 커넥션은 DB의 max_connections를 넘어요.

    해결책

    • 예정된 이벤트는 미리 늘려요. 세일 시작 30분 전에 최소 Pod 수를 올려 두는 예약 스케일링을 해요. KEDA의 cron 트리거나 배포 파이프라인의 예약 작업으로 할 수 있어요. 끝난 뒤에는 천천히 줄여요.
    • 평소에도 여유를 둬요. 목표 CPU를 70%가 아니라 50%로 두면, 늘리는 동안 기존 Pod가 받아낼 여유가 생겨요.
    • 서비스의 성격에 맞는 지표로 늘려요. 기다림이 많은 서비스는 초당 요청 수, 동시 처리 중인 요청 수, 응답 시간으로, 큐를 소비하는 워커는 큐 길이나 컨슈머 랙으로 늘려요. 사용자 정의 지표는 Prometheus Adapter나 KEDA로 HPA에 연결해요.
    • 상한은 하위 시스템에서 거꾸로 계산해요. HPA 최대 Pod 수 × Pod당 커넥션 풀 크기가 DB가 받을 수 있는 커넥션 수보다 작아야 해요. 더 늘려야 한다면 커넥션 풀 크기를 줄이거나 중간 풀(ProxySQL, PgBouncer)을 둬요(DB 챕터 4.1 시니어).
    • 줄일 때는 천천히 줄여요. HPA의 behavior 설정으로 줄이는 속도와 안정화 시간을 정해서, 트래픽이 잠깐 줄었다고 바로 줄였다가 다시 늘리는 반복을 막아요.

    운영에서 알아채는 법

    • 트래픽이 늘기 시작한 시각과 새 Pod가 준비된 시각의 차이를 재요. 이 차이가 우리 서비스의 "오토스케일 반응 시간"이고, 이보다 빠른 트래픽 증가는 여유로 받아내야 해요.
    • HPA의 현재 복제 수가 최대값에 닿은 시간을 지표로 남겨요. 자주 닿는다면 상한이나 하위 용량을 다시 봐야 해요.
    핵심 정리
    • readiness 실패 = 트래픽 제외, liveness 실패 = 재시작. liveness에 외부 의존성 금지
    • 종료: preStop 대기 → SIGTERM → 진행 중 요청 완료 → 유예 시간 안에 종료
    • HPA의 CPU는 requests 대비. 반응이 늦으니 여유, 상한은 하위 시스템 기준
    셀프 체크
    1. liveness 프로브에서 DB 연결을 확인하도록 설정하면 어떤 위험이 있나요?
    답 보기

    DB가 잠깐 느려지거나 끊기면 모든 Pod의 liveness 검사가 동시에 실패하고, 쿠버네티스가 모든 컨테이너를 재시작해요. 재시작해도 DB 문제는 해결되지 않고, 오히려 모든 Pod가 한꺼번에 내려갔다가 다시 뜨면서 DB에 연결 요청이 몰려 회복을 더 어렵게 만들어요. DB와 무관한 기능까지 함께 멈춰요. liveness는 재시작으로 고칠 수 있는 자기 자신의 문제만 확인하고, 의존성의 상태는 필요하면 readiness에서 신중하게 반영해요.

    실습 과제

    로컬 클러스터(kind, minikube)로 충분해요.

    • 1장 컨테이너 안에서 free와 /sys/fs/cgroup의 메모리 한도를 비교. 같은 앱을 단일 스테이지와 멀티 스테이지로 빌드해 이미지 크기 비교
    • 2장 존재하지 않는 이미지 태그로 apply하고, apply 결과와 kubectl describe의 Events 비교
