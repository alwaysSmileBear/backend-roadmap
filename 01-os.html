    운영체제

    기준 교재: OSTEP (Operating Systems: Three Easy Pieces) · 4~6주

    OSTEP은 운영체제를 가상화 · 병행성 · 영속성 세 조각으로 나눠요. OS는 CPU와 메모리를 "각 프로세스가 혼자 쓰는 것처럼" 보이게 만들고(가상화), 여러 흐름이 동시에 돌아도 안전하게 하고(병행성), 전원이 꺼져도 데이터가 남게 해요(영속성). 이 페이지는 그 장 순서를 그대로 따라가요.

    백엔드 개발자에게 특히 중요한 장은 6장(제한적 직접 실행), 19장(TLB), 21~22장(스왑), 2부 전체(병행성), 33장(이벤트 기반), 42장(저널링)이에요. 시간이 없으면 이 장들을 먼저 읽으세요.

    2장 운영체제 개요

    OS가 하는 일 세 가지와, 이 책이 왜 그 순서로 가는지

    OS는 자원 관리자

    프로그램이 실행된다는 건 CPU가 메모리에서 명령어를 가져와(fetch) 해석하고(decode) 실행하는(execute) 일을 반복하는 거예요. 그런데 프로그램은 수십 개가 동시에 돌고, CPU와 메모리는 한정돼 있어요. OS는 이 물리 자원을 나눠 주고, 서로 침범하지 못하게 보호하는 자원 관리자예요.

    세 가지 핵심 개념

    • 가상화(Virtualization): 물리 CPU 1개를 "프로세스마다 CPU가 하나씩 있는 것처럼", 물리 메모리를 "프로세스마다 독립된 큰 메모리가 있는 것처럼" 보이게 해요. 1부 내용이에요.
    • 병행성(Concurrency): 여러 실행 흐름이 같은 메모리를 건드릴 때 생기는 문제를 다뤄요. 락, 조건 변수, 세마포어. 2부 내용이에요.
    • 영속성(Persistence): 디스크와 파일 시스템. 전원이 나가도 데이터를 안전하게 남기는 방법. 3부 내용이에요.

    설계 목표

    추상화(복잡한 하드웨어를 단순한 인터페이스로), 성능(OS 자체 오버헤드 최소화), 보호와 격리, 신뢰성, 에너지 효율. 이 중 어느 것을 우선할지가 OS마다 달라요.

    백엔드에서는 우리가 쓰는 스레드풀, 커넥션 풀, 비동기 프레임워크, JVM GC는 전부 이 세 조각 위에 얹혀 있어요. "왜 스레드가 많으면 느려지나", "왜 디스크 쓰기는 순차로 해야 하나" 같은 질문의 답이 이 책에 있어요.
    시니어 심화 OS가 숨겨 주는 층(스케줄링, 페이지 캐시, 쓰기 버퍼링)은 평소에는 몰라도 되지만, 꼬리 지연과 장애의 원인은 대개 그 숨겨진 층에 있어요. 문제는 그 층의 상태가 사용률 하나로는 보이지 않는다는 거예요.

    상황

    주문 API의 p99가 가끔 300ms까지 튀어요. 대시보드의 CPU 사용률은 40%, 메모리는 절반이 비어 있어요. "서버는 여유롭다"는 결론이 났고, 원인은 몇 주째 못 찾았어요.

    왜 사용률로는 안 보이나

    1. 사용률은 평균이에요. 1분 평균 CPU 40%는 "1분 내내 40%"일 수도, "몇 초는 100%, 나머지는 한가"일 수도 있어요. 요청이 순간적으로 몰리는 몇 초 동안에는 실행을 기다리는 줄이 생기고, 그 줄이 지연이 돼요.
    2. 사용률은 기다림을 세지 않아요. 자원이 바쁜 정도와 그 자원을 기다리는 작업의 수는 다른 숫자예요. 사용자가 느끼는 지연은 뒤쪽에 가까워요.
    3. 컨테이너에는 한 겹이 더 있어요. cgroup은 컨테이너마다 CPU와 메모리 한도를 따로 걸어요. 호스트 CPU가 40%여도 그 컨테이너는 자기 CPU 한도에 걸려 잠깐씩 멈출 수 있어요(스로틀링, 7장 시니어). 호스트 메모리가 남아도 컨테이너는 한도를 넘는 순간 OOM으로 죽어요. 위 상황의 원인도 이것이었어요.

    해결책: 자원마다 세 가지를 보기

    • USE 방법: CPU, 메모리, 디스크, 네트워크 각각에 대해 사용률(Utilization), 포화(Saturation, 기다리는 줄), 에러(Errors)를 따로 봐요(성능 분석 챕터 1장). CPU의 포화는 실행 대기 수, 메모리의 포화는 회수와 스왑 활동, 디스크의 포화는 I/O 대기열이에요.
    • 압력 지표(PSI)를 봐요. 리눅스의 /proc/pressure/cpu, memory, io는 "작업이 그 자원을 기다리느라 멈춰 있던 시간의 비율"이에요. 사용률보다 지연에 훨씬 가까운 숫자예요(4장 시니어).
    • 호스트와 컨테이너를 구분해요. 컨테이너 지표(스로틀링 횟수, 컨테이너 메모리 working set)를 호스트 지표와 따로 대시보드에 둬요.
    • 평균 대신 분포를 봐요. 1분 평균 대신 1초 단위의 최댓값이나 응답 시간의 p99를 함께 봐요.

    운영에서 알아채는 법

    • "사용률은 낮은데 지연이 튄다"면 포화 지표를 먼저 봐요. 컨테이너라면 container_cpu_cfs_throttled_periods_total이 오르는지 확인해요.
    • 지연이 튀는 시각과 각 자원의 포화 지표가 튀는 시각을 겹쳐 보면, 어느 숨겨진 층이 원인인지 좁혀져요.

    • 가상화(CPU·메모리) → 병행성 → 영속성 순서로 공부

    4장 프로세스

    실행 중인 프로그램을 OS는 어떻게 표현하는가

    프로세스란

    프로세스는 실행 중인 프로그램이에요. 디스크의 프로그램 파일은 그냥 바이트 덩어리이고, OS가 그것을 메모리에 올리고 실행 상태를 만들어 줘야 프로세스가 돼요. 프로세스의 상태를 이루는 것들(machine state)은 다음과 같아요.

    • 메모리(주소 공간): 코드, 데이터, 힙, 스택
    • 레지스터: 특히 PC(다음 실행할 명령 주소), SP(스택 포인터)
    • 열린 파일 목록, 현재 디렉터리 같은 I/O 정보

    프로세스 생성 과정

    1. 프로그램 코드와 정적 데이터를 디스크에서 메모리로 로드 (현대 OS는 필요한 페이지만 lazy하게 로드)
    2. 스택 할당, main()의 argc/argv 설정
    3. 힙 할당
    4. 표준 입출력 fd(0, 1, 2) 등 초기화
    5. main()으로 점프

    프로세스 상태

    상태의미
    RunningCPU에서 실행 중
    Ready실행할 수 있지만 CPU를 기다리는 중
    BlockedI/O 등 다른 사건을 기다리느라 실행할 수 없음

    I/O를 요청하면 Running → Blocked가 되고, 그 사이 OS는 다른 Ready 프로세스를 실행해요. I/O가 끝나면 Blocked → Ready. 이 전환이 CPU를 놀리지 않는 핵심이에요.

    자료구조

    OS는 프로세스마다 PCB(Process Control Block)를 두고 레지스터 값, 상태, PID, 메모리 정보, 열린 파일을 저장해요. 컨텍스트 스위칭 때 여기에 레지스터를 저장했다가 복원해요.

    백엔드에서는 DB 쿼리를 기다리는 요청 스레드는 Blocked 상태예요. 스레드가 100개인데 CPU 사용률이 10%라면, 대부분 Blocked라는 뜻이고 스레드 수를 늘리거나 비동기 I/O로 바꿀 여지가 있다는 신호예요. ps, top의 STAT 열(R, S, D)이 이 상태예요.
    시니어 심화 본문의 "CPU 10%인데 스레드 100개"는 스레드들이 무엇을 기다리는지 모르면 다음 행동을 정할 수 없어요. 리눅스의 로드 애버리지가 이 판단을 흐리게 만드는 대표적인 숫자예요.

    상황

    정산 서버의 로드 애버리지가 120으로 치솟아 알람이 울렸어요. 코어는 16개라 "CPU가 7배 과부하"라고 판단하고 서버를 두 배로 늘렸어요. 그런데 로드도 증상도 그대로였어요. CPU 사용률은 계속 10% 안팎이었어요.

    왜 헷갈리나

    1. 리눅스의 로드 애버리지는 실행 중이거나 실행을 기다리는 프로세스(R 상태)뿐 아니라, 중단할 수 없는 대기(D 상태)에 있는 프로세스도 세요. D 상태는 주로 디스크 I/O나 NFS 같은 네트워크 파일 시스템 응답을 기다리는 상태예요.
    2. 정산 서버는 NFS로 마운트한 공유 폴더에 리포트를 쓰고 있었어요. NFS 서버가 느려지자 쓰기 스레드 100여 개가 D 상태로 멈췄고, 그것이 전부 로드에 더해졌어요.
    3. 그래서 "로드는 높은데 CPU는 한가한" 서버는 CPU가 아니라 I/O가 병목이에요. 서버를 늘려도 같은 NFS를 기다릴 뿐이에요.

    해결책: 기다림의 종류를 나누기

    • vmstat 1로 나눠 봐요. r 열은 실행 대기(CPU를 기다림), b 열은 블록(I/O를 기다림)이에요. r이 코어 수보다 크면 CPU 부족, b가 크면 I/O 문제예요.
    • PSI를 봐요. /proc/pressure/cpu, io, memory의 some avg10은 "최근 10초 동안 적어도 한 작업이 그 자원을 기다린 시간의 비율"이에요. 위 상황이라면 cpu는 낮고 io가 높게 나와서 바로 구분돼요. 쿠버네티스와 systemd도 이 값을 판단 근거로 써요.
    • 어떤 스레드가 어디서 멈췄는지 봐요. ps -eo state,pid,wchan:30,cmd | grep ^D로 D 상태 프로세스와 커널 안에서 기다리는 지점을 볼 수 있어요. 자바라면 스레드 덤프에서 같은 I/O 호출에 멈춘 스레드가 몰려 있는지 봐요.
    • 원인에 맞게 대응해요. 느린 공유 저장소에 대한 쓰기는 타임아웃을 두거나, 로컬 디스크에 먼저 쓰고 비동기로 옮기는 구조로 바꿔요.

    운영에서 알아채는 법

    • 로드 애버리지 알람은 단독으로 쓰지 말고 CPU 사용률, PSI와 함께 봐요. 로드 알람보다 PSI 알람이 더 정확한 신호예요.
    • 로드가 코어 수를 크게 넘는데 CPU가 한가하다면, 무엇보다 먼저 디스크와 네트워크 파일 시스템을 확인해요.
    핵심 정리
    • 프로세스 = 주소 공간 + 레지스터 + I/O 상태
    • Running / Ready / Blocked 세 상태, I/O 대기 중엔 다른 프로세스가 CPU 사용

    2. 프로세스가 I/O를 요청하면 OS는 무엇을 하나요?
    답 보기

    1. Ready는 CPU만 주면 바로 실행 가능한 상태, Blocked는 I/O 완료 같은 외부 사건이 있어야 실행 가능한 상태예요.

    2. 그 프로세스를 Blocked로 바꾸고, Ready 큐에서 다른 프로세스를 골라 CPU를 줘요. I/O가 끝나면 인터럽트로 알림을 받아 Ready로 되돌려요.

    5장 프로세스 API

    fork, exec, wait — UNIX가 프로세스를 다루는 방식

    fork()

    호출한 프로세스를 거의 똑같이 복제해요. 자식은 부모의 주소 공간 복사본을 갖고, fork() 다음 줄부터 실행돼요. 부모에겐 자식 PID가, 자식에겐 0이 반환돼서 둘을 구분해요. 실제로는 전체를 복사하지 않고 copy-on-write로 페이지를 공유하다가 쓰기가 일어날 때만 복사해요.

    exec()

    현재 프로세스의 코드와 데이터를 다른 프로그램으로 덮어써요. 새 프로세스를 만들지 않아요. 그래서 쉘은 fork() → 자식에서 exec() 순서로 명령을 실행해요.

    wait()

    자식이 끝날 때까지 기다리고 종료 상태를 거둬요. 부모가 wait()를 하지 않으면 자식은 종료 후에도 PCB가 남는 좀비 프로세스가 돼요. 부모가 먼저 죽으면 자식은 init(PID 1)에 입양돼요.

    왜 fork와 exec을 나눴나

    fork와 exec 사이에 자식이 자기 환경을 바꿀 수 있어서예요. 쉘의 리다이렉션(ls > out.txt)은 fork 후 자식이 표준 출력 fd를 파일로 바꾼 뒤 exec하는 거예요. 파이프도 같은 원리예요.

    백엔드에서는 컨테이너 안에서 애플리케이션이 PID 1이 되면 입양된 좀비를 거두는 역할도 떠안아요. 그래서 tini 같은 init 프로세스를 두거나 docker run --init을 써요. Node.js의 child_process, Python의 subprocess, JVM의 ProcessBuilder가 전부 "새 프로세스 만들기 + exec" 구조예요. 다만 큰 프로세스에서 fork는 페이지 테이블 복사 비용이 커서, JVM은 리눅스에서 fork 대신 posix_spawn(vfork 계열)을 써서 이 비용을 피해요.
    시니어 심화 본문에서 큰 JVM의 fork가 비싸다고 했는데, fork에는 비용 말고도 운영에서 부딪히는 함정이 두 가지 있어요. 메모리가 큰 프로세스의 fork가 서비스를 멈추게 하는 것과, 멀티스레드 프로세스에서 fork한 자식이 영원히 멈추는 것이에요.

    상황 1: Redis가 저장할 때마다 멈춤

    메모리 40GB를 쓰는 Redis가 RDB 스냅샷을 만들 때마다 수백 ms 동안 응답하지 않았어요. 그리고 가끔 메모리 사용량이 갑자기 두 배 가까이 늘었어요.

    1. Redis는 스냅샷을 만들 때 fork로 자식 프로세스를 만들고, 자식이 메모리 내용을 파일로 써요. 부모는 계속 요청을 받아요.
    2. fork는 메모리 내용을 복사하지 않고 공유하지만(copy-on-write), 페이지 테이블은 복사해야 해요. 40GB면 페이지 테이블만 수십~수백 MB이고, 이것을 복사하는 동안 부모가 멈춰요.
    3. fork 뒤에 부모가 데이터를 고치면 그 페이지는 그때 복사돼요. 쓰기가 많으면 복사되는 페이지가 늘어 메모리가 두 배 가까이 필요해질 수 있어요. 투명한 큰 페이지(THP)가 켜져 있으면 몇 바이트를 고쳐도 2MB가 통째로 복사돼서 더 심해요.

    해결: 큰 Redis는 메모리 한도를 서버 메모리의 절반 정도로 두고, THP를 끄고, 스냅샷은 부하가 적은 복제본에서 만들어요. Redis의 INFO에 나오는 latest_fork_usec로 fork에 걸린 시간을 확인할 수 있어요.

    상황 2: fork한 자식이 영원히 멈춤

    JNI로 붙인 네이티브 라이브러리가 외부 도구를 실행하려고 fork를 직접 불렀어요. 대부분은 동작했지만, 부하가 높을 때 가끔 자식 프로세스가 아무것도 하지 않고 영원히 멈췄어요.

    1. 멀티스레드 프로세스에서 fork하면, 자식에는 fork를 호출한 스레드 하나만 복제돼요.
    2. 다른 스레드가 그 순간 쥐고 있던 락(예: 메모리 할당기의 락, 로깅 라이브러리의 락)은 자식의 메모리에 "잠긴 상태"로 그대로 복사돼요. 그 락을 풀어 줄 스레드는 자식에 없어요.
    3. 자식이 메모리를 할당하거나 로그를 쓰려고 그 락을 잡는 순간 영원히 멈춰요. 부하가 높을수록 fork 순간에 누군가 락을 쥐고 있을 확률이 높아요.

    해결: 멀티스레드 프로세스는 fork한 뒤 곧바로 exec해서 메모리를 통째로 새 프로그램으로 갈아엎어야 해요. fork와 exec 사이에서는 락이 필요한 함수를 부르면 안 돼요. 더 안전한 방법은 둘을 한 번에 하는 posix_spawn이에요. 자바의 ProcessBuilder는 최근 JDK에서 리눅스 기본으로 이 방식을 써요. 직접 fork할 일이 있다면 이 규칙을 지키세요.

    운영에서 알아채는 법

    • Redis의 지연 그래프에 스냅샷 시각을 겹쳐 봐요. 스냅샷마다 지연이 튀면 fork 비용이에요.
    • 상태가 S인데 CPU를 전혀 쓰지 않고 오래 남아 있는 자식 프로세스가 있다면, gdb나 /proc/<pid>/stack으로 어떤 락에서 멈췄는지 확인해요.
    핵심 정리
    • fork = 복제, exec = 덮어쓰기, wait = 종료 회수
    • 좀비는 wait 안 한 자식, 고아는 init이 입양
    셀프 체크
    1. 좀비 프로세스가 생기는 조건은 무엇인가요?
    2. 쉘이 ls > out.txt를 처리하는 과정을 fork/exec으로 설명해보세요.
    답 보기

    1. 자식은 종료했는데 부모가 wait()로 상태를 거두지 않았을 때예요.

    2. 쉘이 fork → 자식에서 표준 출력(fd 1)을 닫고 out.txt를 열어 fd 1에 할당 → exec("ls") → ls는 fd 1에 쓰는 줄만 알지만 실제로는 파일에 써져요.

    6장 제한적 직접 실행

    프로세스를 CPU에서 직접 실행하면서도 OS가 통제권을 잃지 않는 방법

    문제

    성능을 위해 프로그램을 CPU에서 직접 실행하고 싶어요. 그런데 그러면 (1) 프로그램이 멋대로 디스크에 접근하거나 다른 프로세스 메모리를 읽는 걸 어떻게 막나, (2) 프로그램이 CPU를 영원히 쓰면 OS가 어떻게 되찾나, 두 문제가 생겨요.

    문제 1: 제한된 연산 — 사용자 모드와 커널 모드

    CPU는 두 모드를 가져요. 사용자 모드에서는 I/O 같은 특권 명령을 실행할 수 없어요. 프로세스가 특권 작업이 필요하면 시스템 콜을 해요.

    1. 프로세스가 trap 명령을 실행하면 CPU가 커널 모드로 바뀌고 미리 등록된 트랩 핸들러로 점프해요.
    2. OS가 요청을 검증하고 처리해요 (예: read() → 디스크 읽기).
    3. return-from-trap으로 사용자 모드로 돌아가 다음 명령을 실행해요.

    트랩 핸들러 주소는 부팅 때 OS가 트랩 테이블에 등록해요. 프로세스는 "몇 번 시스템 콜"만 지정할 수 있고 주소는 지정할 수 없어서 안전해요.

    문제 2: 프로세스 전환 — 타이머 인터럽트

    프로세스가 실행 중이면 OS는 실행 중이 아니에요. OS가 CPU를 되찾는 방법은 두 가지예요.

    • 협조적: 프로세스가 시스템 콜이나 yield()를 호출할 때까지 기다려요. 무한 루프에 빠지면 방법이 없어요.
    • 비협조적: 타이머 인터럽트. 수 밀리초마다 하드웨어가 인터럽트를 걸고, 커널 모드로 들어가 OS가 실행돼요. 이때 스케줄러가 다른 프로세스로 바꿀 수 있어요.

    컨텍스트 스위치

    프로세스 A에서 B로 바꾸려면 (1) A의 레지스터를 A의 커널 스택/PCB에 저장하고, (2) B의 레지스터를 복원하고, (3) B의 커널 스택으로 바꾼 뒤 return-from-trap하면 B가 실행돼요. 수백 나노초~수 마이크로초가 들어요. 숨은 비용은 CPU 캐시, TLB, 분기 예측기가 비워지는 것이고, 이게 직접 비용보다 커요.

    백엔드에서는 모든 I/O(네트워크 읽기, 파일 쓰기, System.nanoTime()도 가끔)는 시스템 콜이고, 시스템 콜마다 모드 전환 비용이 있어요. 작은 쓰기를 수천 번 하는 것보다 버퍼에 모아 한 번 쓰는 게 빠른 이유예요. strace -c로 어떤 시스템 콜을 몇 번 하는지 볼 수 있어요. 또 스레드가 많아 컨텍스트 스위칭이 잦으면 vmstat의 cs 열이 치솟아요.
    시니어 심화 본문은 시스템 콜마다 모드 전환 비용이 있다고 했는데, 그 비용은 고정값이 아니에요. 같은 코드가 커널 버전, 보안 패치, 가상화 환경에 따라 다른 속도로 돌아요.

    상황

    같은 API 서버를 새로운 클라우드 인스턴스 종류로 옮겼더니 CPU 사용률이 15% 올랐어요. 코드도 JVM도 같았어요. 프로파일링해 보니 시각을 읽는 코드(로그의 타임스탬프, 메트릭, 분산 추적)가 CPU를 눈에 띄게 쓰고 있었어요.

    깨지는 과정

    1. 시각 조회(clock_gettime, 자바의 System.nanoTime())는 초당 수십만 번 불릴 만큼 흔해요.
    2. 리눅스는 이 호출을 보통 모드 전환 없이 처리해요. 커널이 사용자 공간에 올려 둔 작은 코드(vDSO)가 CPU의 시간 카운터(TSC)를 직접 읽어요.
    3. 그런데 가상 머신의 클록 소스가 tsc가 아니라 xen이나 hpet 같은 것으로 잡혀 있으면, 커널 버전과 환경에 따라 vDSO가 이 방식을 쓸 수 없어서 진짜 시스템 콜이 돼요. 옛 Xen 기반 클라우드 인스턴스에서 실제로 흔했던 일이에요.
    4. 호출 하나는 몇십 ns에서 수백 ns로 느려질 뿐이지만, 초당 수십만 번이면 CPU 몇 %가 돼요.

    보안 패치도 모드 전환 비용을 바꿔요. Meltdown 같은 CPU 취약점을 막는 커널 패치(KPTI)는 모드를 전환할 때마다 페이지 테이블을 바꾸게 해서, 시스템 콜이 잦은 워크로드(작은 패킷을 많이 주고받는 프록시, 작은 파일 I/O)일수록 느려졌어요.

    해결책

    • 클록 소스를 확인해요. cat /sys/devices/system/clocksource/clocksource0/current_clocksource로 지금 클록 소스를, available_clocksource로 쓸 수 있는 목록을 봐요. 클라우드 업체가 권장하는 경우 tsc로 바꿔요.
    • 시스템 콜 수를 줄여요. 작은 쓰기를 여러 번 하는 대신 버퍼에 모아 한 번에 써요. 로그는 비동기 어펜더로 묶어서 써요.
    • 새 환경으로 옮길 때는 기준 측정을 해요. 인스턴스 종류, 커널 버전, 가상화 방식이 바뀌면 같은 부하로 CPU 사용률을 비교하는 테스트를 돌려요.

    운영에서 알아채는 법

    • strace -c -f -p <pid>를 몇 초 돌려 보면 시스템 콜별 호출 횟수가 나와요. vDSO로 처리되면 clock_gettime은 목록에 보이지 않아야 해요. 많이 보인다면 클록 소스를 확인해요. strace는 대상 프로세스를 크게 느리게 하니 운영에서는 아주 짧게만 써요.
    • perf top에서 커널 쪽 시간 관련 함수가 상위에 보이면 같은 신호예요.
    • "같은 코드가 어떤 인스턴스 종류에서만 느리다"면 한 번 볼 만한 곳이에요.
    핵심 정리
    • 사용자/커널 모드 + 시스템 콜(trap) = 제한된 연산 해결
    • 타이머 인터럽트 = OS가 CPU를 되찾는 보장
    • 컨텍스트 스위치 비용은 레지스터 저장보다 캐시/TLB 오염이 큼
    셀프 체크
    1. 시스템 콜이 일반 함수 호출보다 비싼 이유는?
    2. 타이머 인터럽트가 없으면 어떤 문제가 생기나요?
    답 보기

    1. 사용자 모드 → 커널 모드 전환(trap), 레지스터 저장, 커널 스택 전환, 보안 검증, 그리고 돌아올 때 역순. 함수 호출은 같은 모드에서 점프만 해요.

    2. 무한 루프에 빠진 프로세스가 CPU를 영원히 점유해도 OS가 개입할 수 없어요. 재부팅밖에 방법이 없어요.

    7~8장 스케줄링

    누구에게 CPU를 줄 것인가 — FIFO에서 MLFQ까지

    평가 기준

    • 반환 시간(turnaround): 도착 → 완료까지. 배치 작업에서 중요.
    • 응답 시간(response): 도착 → 처음 실행까지. 대화형 작업에서 중요.
    • 공정성: 굶는 작업이 없는가.

    기본 정책

    정책동작문제
    FIFO온 순서대로 끝까지긴 작업 뒤의 짧은 작업이 기다림(convoy effect)
    SJF짧은 작업 먼저작업 길이를 미리 알아야 함, 긴 작업 기아
    STCFSJF + 선점 (남은 시간이 더 짧은 작업이 오면 바꿈)반환 시간 최적이지만 응답 시간 나쁨
    RR타임 슬라이스마다 돌아가며응답 시간 최고, 반환 시간 나쁨. 슬라이스가 짧으면 스위칭 비용 증가

    I/O를 하는 작업은 Blocked 동안 CPU를 다른 작업에 주는 중첩(overlap)으로 전체 효율을 높여요.

    MLFQ (Multi-Level Feedback Queue)

    작업 길이를 모르면서도 SJF처럼 동작하고 싶을 때. 우선순위가 다른 큐를 여러 개 두고, 과거 행동으로 우선순위를 조정해요.

    1. 새 작업은 최상위 큐에 넣어요 (짧은 대화형 작업이라 가정).
    2. 한 큐에서 타임 슬라이스를 다 쓰면(= CPU를 오래 쓰는 작업) 한 단계 내려요.
    3. I/O로 CPU를 일찍 놓는 작업은 우선순위를 유지해요.
    4. 주기적으로 모든 작업을 최상위로 올려요 (기아 방지, 행동 변화 반영).
    5. CPU 사용량은 슬라이스가 아니라 누적 할당량으로 세요 (슬라이스 끝나기 직전 I/O하는 꼼수 방지).

    리눅스 CFS

    실제 리눅스는 CFS(Completely Fair Scheduler)를 써요. 각 작업의 가상 실행 시간(vruntime)을 Red-Black 트리로 관리하고 가장 적게 실행된 작업을 다음에 실행해요. nice 값이 vruntime 증가 속도를 바꿔 가중치를 줘요. 6.6부터는 EEVDF로 바뀌었지만 공정 분배라는 원리는 같아요.

    백엔드에서는 쿠버네티스 CPU limit은 CFS 쿼터(cgroup)로 구현돼요. 100ms 주기에 limit만큼만 쓰고 나머지는 스로틀링돼요. limit 0.5 CPU면 주기마다 50ms어치 CPU 시간을 받는데, 멀티스레드 JVM의 스레드 10개가 동시에 돌면 5ms 만에 다 쓰고 나머지 95ms를 멈추는 일이 반복돼서 p99 지연이 튀어요. container_cpu_cfs_throttled_seconds_total 메트릭으로 확인해요.
    시니어 심화 본문의 스로틀링 예시에서 "멀티스레드 JVM이 쿼터를 몇 ms 만에 다 쓰고 멈춘다"고 했는데, 이것이 심해지는 흔한 원인은 limit이 작아서가 아니라 런타임이 코어 수를 잘못 아는 것이에요.

    상황

    쿠버네티스에서 CPU limit 2를 준 API 파드의 p99가 120ms 언저리에서 자주 튀어요. CPU 사용률 그래프는 평균 1.2코어로 한도에 한참 못 미쳐요. 파드는 코어가 64개인 노드에서 돌고 있었어요.

    깨지는 과정

    1. CPU limit 2는 "100ms 주기마다 CPU 시간 200ms까지"라는 뜻이에요. 주기 안에서 할당량을 다 쓰면 다음 주기가 시작될 때까지 컨테이너의 모든 스레드가 멈춰요.
    2. 오래된 런타임이나 설정은 컨테이너 한도 대신 호스트의 코어 수 64를 보고 GC 스레드, 공용 스레드풀(ForkJoinPool.commonPool()), 이벤트 루프 스레드를 만들어요.
    3. GC가 시작되면 GC 스레드 수십 개가 64개 코어에서 동시에 돌아요. 40개 스레드가 동시에 돌면 200ms의 할당량을 5ms 만에 다 써요.
    4. 남은 95ms 동안 컨테이너 전체가 멈춰요. 그때 처리 중이던 요청은 95ms가 그대로 더해져요.
    5. 1분 평균 CPU 사용률은 1.2코어라 한도에 여유가 있어 보여요. 할당량은 평균이 아니라 100ms 단위의 순간 사용량으로 소진돼요.

    해결책

    • 런타임이 한도를 알게 해요. JDK 10 이상(8u191 이상)은 cgroup의 CPU 한도를 인식해서 그에 맞게 스레드 수를 정해요. 확인하려면 컨테이너 안에서 Runtime.getRuntime().availableProcessors()가 2를 돌려주는지 봐요. 필요하면 -XX:ActiveProcessorCount=2로 직접 지정해요. Go는 오랫동안 호스트 코어 수를 써서 automaxprocs 같은 라이브러리로 맞췄어요(Go 1.25부터는 기본으로 컨테이너의 CPU 한도를 반영해요). 런타임마다 확인이 필요해요.
    • 스레드 수를 명시해요. GC 스레드(-XX:ParallelGCThreads, -XX:ConcGCThreads)와 애플리케이션 스레드풀 크기를 한도에 맞게 직접 정해요.
    • 지연에 민감한 서비스는 limit을 빼는 방법도 있어요. CPU request만 정확히 두고 limit을 걸지 않으면 스로틀링 자체가 없어요. 대신 같은 노드의 다른 파드와 남는 CPU를 나눠 쓰게 되니, request를 실제 사용량에 맞게 잡는 것이 중요해요(쿠버네티스 챕터 5장).

    운영에서 알아채는 법

    • cgroup의 cpu.stat에 있는 nr_throttled(스로틀된 주기 수)와 throttled_usec(멈춘 총 시간)가 원본 수치예요. 쿠버네티스에서는 container_cpu_cfs_throttled_periods_total을 전체 주기 수로 나눈 비율을 봐요. 이 비율이 몇 %만 돼도 p99에 드러나요.
    • 평균 CPU 사용률이 한도보다 한참 낮은데 스로틀링이 있다면, 짧은 순간에 스레드가 몰려 도는 거예요. GC 로그의 GC 시각과 스로틀링 시각을 겹쳐 보면 확인돼요.
    핵심 정리
    • 반환 시간 vs 응답 시간은 트레이드오프 (STCF vs RR)
    • MLFQ = 과거 행동으로 우선순위 학습 + 주기적 부스트
    • 리눅스 CFS = vruntime 기반 공정 분배, 컨테이너 limit은 CFS 쿼터
    셀프 체크
    1. RR의 타임 슬라이스를 너무 짧게 하면 왜 나쁜가요?
    2. MLFQ에서 주기적으로 우선순위를 올려주는 이유는?
    답 보기

    1. 컨텍스트 스위칭 비용(캐시 오염 포함)이 실제 작업 시간 대비 커져서 전체 처리량이 떨어져요.

    2. CPU 집약 작업이 하위 큐에서 영원히 굶는 걸 막고, 대화형으로 바뀐 작업이 다시 높은 우선순위를 받을 수 있게 하기 위해서예요.

    1부 가상화 — 메모리

    13~14장 주소 공간과 메모리 API

    프로세스가 보는 메모리의 모습, 그리고 malloc/free

    주소 공간

    각 프로세스는 자기만의 가상 주소 공간을 봐요. 0번지부터 시작하는 큰 연속 메모리처럼 보이지만 실제 물리 메모리 어디에 있는지는 몰라요.

    높은 주소  ┌────────────┐
           │   stack    │  ← 아래로 자람 (지역 변수, 호출 정보)
           │     ↓      │
           │            │
           │     ↑      │
           │    heap    │  ← 위로 자람 (malloc/new)
           ├────────────┤
           │    data    │  전역/정적 변수
           ├────────────┤
낮은 주소  │    code    │  명령어
           └────────────┘

    메모리 가상화의 목표는 투명성(프로세스가 모르게), 효율성(하드웨어 지원), 보호(다른 프로세스 침범 불가)예요.

    메모리 API

    • 스택 메모리: 함수 안 지역 변수. 컴파일러가 자동으로 할당/해제. 함수가 끝나면 사라져요.
    • 힙 메모리: malloc(size)로 할당, free(ptr)로 해제. 프로그래머 책임.

    흔한 오류: 할당 안 하고 쓰기, 크기 부족(버퍼 오버플로), 초기화 안 함, 해제 안 함(메모리 누수), 해제 후 사용(dangling pointer), 두 번 해제.

    malloc은 시스템 콜이 아니라 라이브러리 함수예요. 내부적으로 brk/mmap 시스템 콜로 큰 덩어리를 받아서 잘라 써요.

    백엔드에서는 GC 언어도 힙을 써요. 다만 free를 GC가 대신 해요. "메모리 누수"는 GC 언어에서도 생겨요. 더 이상 안 쓰는 객체를 static Map이나 캐시가 계속 참조하면 GC가 회수 못 해요. 스레드 스택은 스레드마다 따로 있어서(JVM 기본 512KB~1MB 예약) 스레드 1만 개면 스택만 수 GB를 예약해요. 가상 스레드(Java 21)가 스택을 힙에 두는 이유예요.
    시니어 심화 본문에서 스레드 스택이 메모리를 차지한다고 했는데, 컨테이너에서 JVM이 OOMKilled되는 가장 흔한 이유가 바로 이런 힙 밖의 메모리예요.

    상황

    메모리 한도 2GB인 컨테이너에 -Xmx2g로 JVM을 띄웠어요. 힙 사용량 그래프는 1.5GB를 넘은 적이 없는데, 하루에 몇 번씩 파드가 OOMKilled로 재시작됐어요. 애플리케이션 로그에는 OutOfMemoryError가 한 줄도 없었어요.

    깨지는 과정

    1. JVM 프로세스의 메모리는 힙만이 아니에요. 메타스페이스(클래스 정보), 스레드 스택(스레드 200개 × 1MB), 다이렉트 버퍼(Netty, NIO), JIT 코드 캐시, GC 자체의 자료구조가 모두 힙 밖에서 메모리를 써요.
    2. -Xmx를 컨테이너 한도와 같게 잡으면, 힙이 다 차지 않아도 힙 밖 메모리를 더하는 순간 한도를 넘어요.
    3. 리눅스는 메모리를 미리 약속만 해 두는 방식(오버커밋)이라, 메모리 할당이 성공해도 실제 물리 메모리는 그 페이지를 처음 쓸 때 잡혀요. 그 순간 컨테이너 한도를 넘으면 할당 실패가 아니라 커널의 OOM killer가 프로세스를 바로 죽여요.
    4. JVM은 죽는 순간을 알 수 없으니 OutOfMemoryError도 힙 덤프도 남기지 못해요. 흔적은 커널 로그(dmesg)와 쿠버네티스의 종료 사유(OOMKilled, 종료 코드 137)에만 남아요.

    해결책

    • 힙은 한도의 일부로 잡아요. -Xmx 대신 -XX:MaxRAMPercentage=70처럼 컨테이너 한도의 비율로 정하면 한도가 바뀌어도 따라가요. 나머지 30%가 힙 밖 메모리의 몫이에요. 스레드가 많거나 다이렉트 버퍼를 많이 쓰면 비율을 더 낮춰요.
    • 힙 밖 영역에도 상한을 둬요. -XX:MaxMetaspaceSize, -XX:MaxDirectMemorySize로 영역별 상한을 정하면, 넘을 때 OOM killer 대신 JVM이 해당 영역의 OutOfMemoryError(Metaspace, Direct buffer memory)를 내서 원인을 알 수 있어요. JIT 코드 캐시는 -XX:ReservedCodeCacheSize로 처음부터 크기가 정해져 있고, 다 차면 에러 대신 JIT 컴파일이 멈추고 "CodeCache is full" 경고가 남아요.
    • 스레드 수를 확인해요. 스레드마다 스택이 있으니 스레드 수가 끝없이 늘어나는 코드(요청마다 새 스레드나 새 스레드풀을 만드는 코드)가 없는지 봐요.

    운영에서 알아채는 법

    • 영역별 사용량은 -XX:NativeMemoryTracking=summary를 켜고 jcmd <pid> VM.native_memory summary로 봐요. 몇 시간 간격으로 비교하면 어느 영역이 자라는지 보여요(JVM 챕터 3장). 켜면 약간의 오버헤드가 있으니 문제를 조사할 때 켜요.
    • 컨테이너 메모리(container_memory_working_set_bytes)와 JVM 힙 사용량을 한 그래프에 겹쳐 봐요. 둘의 차이가 계속 벌어진다면 힙 밖에서 새고 있어요.
    • 파드 재시작 사유가 OOMKilled인데 애플리케이션 로그에 OOM이 없다면, 힙이 아니라 프로세스 전체가 한도를 넘은 거예요.
    핵심 정리
    • 주소 공간 = code / data / heap / stack, 스택과 힙이 마주보며 자람
    • 힙은 명시적 관리(malloc/free) 또는 GC, 누수는 GC 언어에도 있음
    셀프 체크
    1. 스택과 힙 메모리의 수명 차이는?
    2. GC 언어에서 메모리 누수가 생기는 예를 하나 들어보세요.
    답 보기

    1. 스택은 함수 호출 동안만 살고 반환하면 자동 해제. 힙은 명시적으로 해제하거나 GC가 회수할 때까지 살아요.

    2. 요청마다 객체를 static List에 add하고 제거하지 않는 경우, 리스너를 등록하고 해제하지 않는 경우, ThreadLocal을 비우지 않고 스레드풀 스레드가 재사용되는 경우.

    15~17장 주소 변환, 세그멘테이션, 빈 공간 관리

    가상 주소를 물리 주소로 바꾸는 첫 번째 방법들

    주소 변환의 기본 아이디어

    프로그램이 메모리 접근을 할 때마다 하드웨어(MMU)가 가상 주소를 물리 주소로 바꿔요. OS는 변환 규칙을 설정하고, 변환 자체는 하드웨어가 해서 빨라요. 이걸 하드웨어 기반 주소 변환이라고 해요.

    베이스-바운드 (동적 재배치)

    가장 단순한 방법. CPU에 base와 bounds 레지스터를 두고, 물리 주소 = 가상 주소 + base, 그리고 가상 주소 < bounds를 검사해요. 넘으면 예외(segfault). 컨텍스트 스위치 때 OS가 두 레지스터를 바꿔요.

    문제: 주소 공간 전체를 물리 메모리에 연속으로 둬야 해서, 스택과 힙 사이의 빈 공간까지 전부 차지해요(내부 단편화).

    세그멘테이션

    code, heap, stack을 각각 별도 세그먼트로 두고 세그먼트마다 base/bounds를 가져요. 가상 주소의 상위 비트로 세그먼트를 고르고 나머지를 오프셋으로 써요. 빈 공간을 할당하지 않아도 되고, 코드 세그먼트를 여러 프로세스가 공유할 수도 있어요(보호 비트).

    문제: 세그먼트 크기가 제각각이라 물리 메모리에 작은 구멍이 많이 생겨요(외부 단편화).

    빈 공간 관리

    크기가 가변인 조각을 관리하는 문제는 세그먼트 배치와 malloc 구현 둘 다에 나와요.

    • 분할(splitting)과 병합(coalescing): 큰 빈 덩어리를 잘라 주고, 해제 시 인접한 빈 덩어리와 합쳐요.
    • 헤더: 할당한 덩어리 앞에 크기를 기록해서 free(ptr)만으로 크기를 알아요.
    • 전략: best fit(가장 작은 맞는 것, 작은 조각 남음), worst fit, first fit(처음 맞는 것, 빠름), next fit.
    • 분리 리스트(segregated list): 자주 쓰는 크기별로 전용 리스트. 커널 slab 할당자, jemalloc/tcmalloc의 size class가 이 방식이에요.
    • 버디 할당자: 2의 거듭제곱 크기로 쪼개고, 해제 시 "버디"와 병합. 병합이 빨라요.
    백엔드에서는 JVM 힙은 세대별로 나눠 young은 bump pointer로 순차 할당(매우 빠름)하고, old는 compaction으로 단편화를 없애요. Redis는 jemalloc을 써요. 메모리를 많이 썼다 해제해도 RSS가 안 줄어드는 건 할당자가 OS에 바로 반환하지 않고 단편화된 조각을 들고 있기 때문이에요(mem_fragmentation_ratio).
    핵심 정리
    • MMU가 하드웨어로 변환, OS는 규칙 설정
    • 베이스-바운드 → 내부 단편화, 세그멘테이션 → 외부 단편화
    • 가변 크기 관리는 분할/병합 + 분리 리스트가 실무 표준
    셀프 체크
    1. 내부 단편화와 외부 단편화의 차이는?
    답 보기

    내부 단편화: 할당받은 덩어리 안에 안 쓰는 공간이 남는 것(베이스-바운드에서 스택-힙 사이). 외부 단편화: 할당 사이사이에 작은 빈 공간이 흩어져 총합은 충분한데 연속된 큰 공간이 없는 것(세그멘테이션, malloc).

    18장 페이징

    가변 크기 대신 고정 크기 페이지로 나누면 단편화가 사라진다

    기본 개념

    가상 주소 공간을 고정 크기 페이지(보통 4KB)로, 물리 메모리를 같은 크기 페이지 프레임으로 나눠요. 어떤 페이지든 어떤 프레임에나 들어갈 수 있어요. 그래서 외부 단편화가 없고, 빈 공간 관리가 "빈 프레임 목록"으로 단순해져요.

    페이지 테이블

    프로세스마다 "가상 페이지 번호(VPN) → 물리 프레임 번호(PFN)" 매핑을 담은 페이지 테이블이 있어요. 주소 변환은 이렇게 해요.

    가상 주소 (32비트, 4KB 페이지):
  ┌──────────── VPN (20비트) ────────────┬── offset (12비트) ──┐

1. VPN으로 페이지 테이블 조회 → PFN
2. 물리 주소 = PFN ‖ offset   (offset은 그대로)

    페이지 테이블 엔트리(PTE)에는 PFN 외에 valid 비트(매핑 여부), protection 비트(읽기/쓰기/실행), present 비트(메모리에 있는지, 스왑됐는지), dirty 비트(수정됨), accessed 비트(최근 접근) 등이 있어요.

    두 가지 문제

    • 느림: 메모리 접근 1번에 페이지 테이블 조회가 추가돼서 메모리 접근이 2번이 돼요. → 19장 TLB
    • 큼: 32비트 주소 공간, 4KB 페이지면 페이지가 220개 = 엔트리 100만 개 × 4바이트 = 4MB. 프로세스마다. 64비트는 더 심해요. → 20장 다단계 페이지 테이블
    백엔드에서는 mmap으로 파일을 메모리에 매핑하면 페이지 단위로 lazy하게 읽혀요. Kafka, RocksDB, MongoDB(WiredTiger 이전)가 이걸 써요. 또 JVM의 -XX:+UseLargePages나 Redis의 THP(Transparent Huge Pages) 경고는 페이지 크기 얘기예요. 페이지를 2MB로 키우면 TLB 효율은 좋지만 Redis처럼 fork + copy-on-write를 쓰는 프로세스는 쓰기 한 번에 2MB를 복사해서 지연이 튀어요.
    시니어 심화 본문에서 mmap은 페이지 단위로 lazy하게 읽힌다고 했는데, 이 "lazy"가 지연에 민감한 코드에서는 함정이에요. 페이지 폴트는 그 스레드를 예고 없이 멈추는 블로킹 I/O예요.

    상황

    Elasticsearch 노드의 검색 p99가 평소 30ms인데, 하루 몇 번씩 수 초로 튀었어요. 그 시각에 GC도 없었고 CPU도 한가했어요. 같은 서버에서 매시간 로그 압축 배치가 돌고 있었어요.

    깨지는 과정

    1. Elasticsearch(Lucene)는 인덱스 파일을 mmap으로 메모리에 매핑해서 읽어요. 코드에서는 메모리를 읽는 것처럼 보이고 read 호출이 없어요.
    2. 처음 보는 페이지를 건드리면 페이지 폴트가 나요. 이미 페이지 캐시에 있으면 연결만 하고 끝나지만(minor fault, 마이크로초), 없으면 디스크에서 읽어 올 때까지 그 스레드가 멈춰요(major fault, 밀리초 이상).
    3. 로그 압축 배치가 큰 파일들을 읽으면서 페이지 캐시를 채웠고, 그동안 자주 쓰던 인덱스 페이지가 캐시에서 밀려났어요.
    4. 다음 검색이 그 페이지들을 건드리면서 major fault가 연달아 났어요. 코드에는 I/O 호출이 하나도 없는데 검색 스레드가 디스크를 기다리며 멈췄어요.

    이벤트 루프 스레드가 mmap 영역을 읽는다면 더 위험해요. 폴트 하나로 그 루프에 붙은 모든 연결이 멈춰요.

    해결책

    • 페이지 캐시에 기대는 서비스는 메모리를 남겨 둬요. Elasticsearch가 JVM 힙을 서버 메모리의 절반 이하로 두라고 권하는 이유가 이것이에요. 나머지 절반은 인덱스 파일을 담을 페이지 캐시의 몫이에요.
    • 무거운 I/O 이웃을 떼어 놓아요. 한 번만 읽는 대용량 배치는 다른 서버에서 돌리거나, 캐시를 오염시키지 않게 읽어요(40장 시니어).
    • 미리 올려 둘 수 있어요. 꼭 메모리에 있어야 하는 영역은 MAP_POPULATE로 매핑할 때 미리 읽거나, madvise(MADV_WILLNEED)로 곧 쓸 것이라고 알려 줘요.
    • I/O 에러는 시그널로 와요. mmap한 파일을 읽다가 디스크 에러가 나거나 다른 프로세스가 파일을 잘라 버리면, 반환값이 아니라 SIGBUS 시그널로 프로세스가 죽어요. 일반 read처럼 에러를 처리할 수 없으니, 다른 프로세스가 바꿀 수 있는 파일은 mmap하지 않아요.

    운영에서 알아채는 법

    • pidstat -r 1 -p <pid>의 majflt/s가 major fault 수예요. 평소 0에 가까운데 튀는 시각이 지연이 튀는 시각과 겹치면 이 문제예요.
    • 그 시각에 같은 서버에서 무엇이 대량 I/O를 했는지 iotop이나 cgroup의 I/O 지표로 찾아요.
    핵심 정리
    • 고정 크기 페이지 → 외부 단편화 없음, 관리 단순
    • 주소 = VPN + offset, 페이지 테이블로 VPN→PFN
    • 문제: 변환 느림(TLB로 해결), 테이블 큼(다단계로 해결)

    19장 TLB — 변환 캐시

    페이징을 빠르게 만드는 하드웨어 캐시

    TLB란

    Translation Lookaside Buffer. MMU 안에 있는 작은 캐시로 최근 VPN→PFN 변환 결과를 저장해요. 주소 변환 때 먼저 TLB를 보고, 있으면(TLB hit) 페이지 테이블을 안 읽어요. 없으면(TLB miss) 페이지 테이블을 읽고 TLB에 채워요.

    보통 64~2048 엔트리 정도로 작아요. 그런데도 hit rate가 99%를 넘는 건 지역성 때문이에요.

    • 공간 지역성: 배열을 순회하면 같은 페이지 안의 주소를 연속으로 접근 → 첫 접근만 miss.
    • 시간 지역성: 최근 쓴 페이지를 곧 다시 씀.

    TLB miss 처리

    x86은 하드웨어가 페이지 테이블을 걸어서(page table walk) 채워요. MIPS 등은 OS가 트랩 핸들러에서 채워요.

    컨텍스트 스위치와 TLB

    TLB 엔트리는 특정 프로세스의 매핑이라 프로세스가 바뀌면 유효하지 않아요. 전환 때 TLB를 전부 비우거나(flush), 엔트리에 ASID(주소 공간 ID)를 붙여 구분해요. 비우면 전환 직후 miss가 폭증해요. 이게 컨텍스트 스위칭의 숨은 비용이에요.

    백엔드에서는 큰 힙을 랜덤하게 접근하는 워크로드(큰 해시맵, 인메모리 캐시)는 TLB miss가 잦아요. 2MB huge page를 쓰면 TLB 하나가 512배 넓은 범위를 커버해서 효과가 커요. 데이터 레이아웃을 순차로(배열, 컬럼 지향) 바꾸는 것도 같은 이유로 빨라져요. 이게 "캐시 친화적 코드"의 핵심이에요.
    시니어 심화 본문의 "huge page로 TLB 커버리지를 늘린다"는 효과를 측정할 수 있지만, 메모리 매핑 비용에는 반대 방향의 함정도 있어요. TLB를 비우는 비용이 코어 수에 비례해 커지는 것과, 투명한 큰 페이지가 지연을 튀게 하는 것이에요.

    상황 1: 큰 서버로 옮겼더니 느려짐

    메모리를 아주 자주 할당하고 반납하는 이미지 처리 서비스를 16코어 서버에서 96코어 서버로 옮겼어요. 처리량이 늘 줄 알았는데 코어당 처리량이 크게 떨어졌어요.

    1. 멀티스레드 프로세스가 munmap이나 mprotect로 메모리 매핑을 바꾸면, 그 프로세스의 스레드가 돌고 있는 모든 코어의 TLB에서 해당 항목을 지워야 해요. 옛 주소 변환이 남아 있으면 안 되니까요.
    2. 커널은 다른 코어들에 인터럽트를 보내 지우게 하고, 모두 끝날 때까지 기다려요. 이것을 TLB shootdown이라고 해요.
    3. 코어가 많을수록 인터럽트를 보내고 기다리는 대상이 늘어요. 매핑을 자주 바꾸는 프로그램은 코어를 늘릴수록 이 비용이 커져요.

    해결: 큰 메모리 블록을 자주 할당하고 반납하지 않게 해요. 버퍼를 풀로 재사용하거나, 반납을 늦추는 메모리 할당기(jemalloc, tcmalloc)를 써요. 자바라면 힙 안에서 처리되니 대부분 문제없지만, 다이렉트 버퍼를 자주 만들고 버리는 코드는 같은 문제를 일으켜요.

    상황 2: 투명한 큰 페이지(THP)로 지연이 튐

    리눅스의 THP는 애플리케이션이 아무것도 하지 않아도 커널이 알아서 4KB 페이지들을 2MB 큰 페이지로 합쳐 줘요. 편하지만 지연에 민감한 서비스에서는 문제가 돼요.

    1. 큰 페이지를 만들려면 연속된 2MB의 물리 메모리가 필요해요. 메모리가 조각나 있으면 커널이 페이지를 옮겨 빈 공간을 만들어요(compaction).
    2. 이 작업이 메모리를 할당하려던 스레드에서 직접 일어나면, 그 스레드가 수 ms에서 수백 ms까지 멈춰요.
    3. 그래서 Redis, MongoDB 같은 여러 DB가 THP를 끄라고 권해요. Redis는 THP가 켜져 있으면 시작할 때 경고를 남겨요.

    해결: 지연에 민감한 서비스는 /sys/kernel/mm/transparent_hugepage/enabled를 never나 madvise(요청한 영역에만 적용)로 둬요. 큰 페이지가 꼭 필요하면 JVM의 -XX:+UseLargePages처럼 미리 예약한 큰 페이지를 명시적으로 쓰는 방식이 예측 가능해요.

    측정하고 알아채는 법

    • perf stat -e dTLB-load-misses,iTLB-load-misses -p <pid>로 TLB 미스를 재요. 큰 페이지 적용 전후에 이 값과 처리량을 함께 비교해요.
    • /proc/interrupts의 TLB shootdown 줄(TLB)이 빠르게 늘면 매핑 변경이 잦다는 뜻이에요.
    • /proc/vmstat의 compact_stall이 늘면 할당 중 compaction으로 멈춘 일이 있었다는 뜻이에요.
    핵심 정리
    • TLB = 주소 변환 캐시, 지역성 덕분에 hit rate 99%+
    • 컨텍스트 스위치 시 flush 또는 ASID
    • huge page = TLB 커버리지 확대

    20장 작은 페이지 테이블

    다단계 페이지 테이블로 크기 문제를 해결한다

    문제

    선형 페이지 테이블은 주소 공간 전체에 대해 엔트리를 가져요. 대부분의 프로세스는 주소 공간의 아주 일부만 쓰는데도요. 힙과 스택 사이의 거대한 빈 공간에 대한 엔트리는 전부 낭비예요.

    해결책들

    • 큰 페이지: 엔트리 수가 줄지만 내부 단편화가 커져요.
    • 페이징 + 세그멘테이션: 세그먼트마다 페이지 테이블. 세그먼트 크기만큼만 테이블을 둬요. 하지만 세그멘테이션의 단점을 다시 가져와요.
    • 다단계 페이지 테이블: 페이지 테이블 자체를 페이지 단위로 쪼개고, 쓰지 않는 조각은 할당하지 않아요. 최상위 페이지 디렉터리가 "이 조각이 존재하는가"를 가리켜요. 현대 OS의 표준이에요.

    다단계 페이지 테이블의 트레이드오프

    공간은 사용량에 비례해서 작아지지만, TLB miss 때 메모리를 여러 번 읽어야 해요. x86-64는 4단계(최근 5단계 지원)라서 TLB miss 한 번에 메모리를 4번 읽어요. 그래서 TLB가 더 중요해져요.

    역 페이지 테이블

    프로세스별이 아니라 물리 프레임마다 하나씩 "어느 프로세스의 어느 페이지인가"를 기록하는 방법. 테이블이 하나뿐이라 작지만 검색이 필요해서 해시를 써요.

    백엔드에서는 이 장은 직접 다룰 일은 적지만, "fork가 큰 프로세스에서 왜 느린가"의 답이에요. fork는 페이지 테이블 전체를 복사해야 하고, 수십 GB 힙이면 페이지 테이블만 수십 MB예요. Redis가 RDB 저장 때 fork하면 큰 인스턴스에서 수백 ms 멈추는 이유 중 하나예요.
    핵심 정리
    • 다단계 페이지 테이블 = 쓰는 부분만 할당
    • 단계가 깊을수록 TLB miss 비용 증가

    1. 다단계 페이지 테이블이 공간을 절약하는 원리와 그 대가는?
    답 보기

    원리: 페이지 테이블을 페이지 크기로 쪼개고, 가상 주소 공간에서 안 쓰는 영역의 조각은 아예 할당하지 않음. 페이지 디렉터리가 조각의 존재 여부만 가리킴. 대가: TLB miss 시 단계 수만큼 메모리 접근이 늘어남.

    21~22장 물리 메모리 크기의 극복 — 스왑

    메모리보다 큰 주소 공간을 지원하는 방법과 페이지 교체 정책

    스왑 공간과 페이지 폴트

    디스크의 일부를 스왑 공간으로 두고, 물리 메모리에 없는 페이지를 거기 보관해요. PTE의 present 비트가 0이면 메모리에 없다는 뜻이고, 접근하면 페이지 폴트가 발생해요. OS의 페이지 폴트 핸들러가 디스크에서 페이지를 읽어 프레임에 올리고, PTE를 갱신한 뒤 명령을 재실행해요. 그동안 프로세스는 Blocked예요.

    페이지 폴트는 두 가지예요.

    • Minor fault: 디스크 I/O 없이 처리. 처음 접근하는 힙 페이지 할당(zero page), 파일 캐시에 이미 있는 페이지 매핑, copy-on-write.
    • Major fault: 디스크에서 읽어야 함. 수 ms. 이게 많으면 성능이 무너져요.

    메모리가 부족할 때

    빈 프레임이 없으면 누군가를 내보내야(evict) 해요. 실제로는 워터마크를 두고 빈 프레임이 low 아래로 떨어지면 백그라운드 스레드(리눅스 kswapd)가 high까지 미리 내보내요.

    dirty 페이지는 디스크에 써야 해서 clean 페이지를 우선 내보내요. 프리페칭(다음 페이지 미리 읽기)과 클러스터링(쓰기 모아서)으로 디스크 I/O를 줄여요.

    스래싱

    프로세스들의 작업 집합(working set)이 메모리보다 크면 페이지를 올리자마자 내보내는 일이 반복돼요. CPU는 놀고 디스크만 바빠요. 해결은 프로세스 수를 줄이거나(admission control), 메모리를 늘리거나, 리눅스처럼 OOM killer로 프로세스를 죽이는 것뿐이에요.

    백엔드에서는 서버에서 스왑은 사실상 장애예요. JVM 힙이 스왑되면 GC가 디스크를 긁어서 수십 초씩 멈춰요. 보통 vm.swappiness=1로 낮추거나 스왑을 끄고, 대신 메모리 limit을 명확히 잡아 OOM으로 빨리 죽고 재시작하게 해요. DB 서버의 innodb_buffer_pool_size를 물리 메모리의 70~80%로 두는 것도 스왑을 피하면서 페이지 캐시 공간을 남기는 타협이에요. 그리고 LRU/Clock은 DB 버퍼풀, Redis maxmemory 정책에서도 똑같이 나와요.
    시니어 심화 본문은 "스왑을 끄고 OOM으로 빨리 죽게 하라"고 했는데, 스왑을 꺼도 스래싱은 생겨요. 다른 모양으로요.

    상황

    스왑을 끈 API 서버가 메모리 누수로 천천히 메모리를 채워 갔어요. OOM으로 빨리 죽을 거라 생각했는데, 실제로는 20분 동안 응답이 점점 느려지다가 거의 멈췄고, 그 뒤에야 OOM killer가 프로세스를 죽였어요. 그 20분 동안 디스크 읽기가 폭증했어요. 스왑 사용량은 계속 0이었어요.

    깨지는 과정

    1. 메모리가 모자라면 커널은 회수할 수 있는 페이지를 찾아요. 스왑이 없으면 익명 메모리(힙 같은 것)는 내보낼 곳이 없어서 회수할 수 없어요.
    2. 그래서 커널은 파일 기반 페이지를 버려요. 페이지 캐시와, 실행 중인 프로그램의 코드(실행 파일과 공유 라이브러리)와, mmap한 파일이에요. 이것들은 디스크에 원본이 있으니 버렸다가 다시 읽을 수 있어요.
    3. 그런데 프로그램 코드는 계속 실행되니 금방 다시 필요해요. 버리고, 다시 읽고, 또 버리는 일이 반복돼요. 디스크 읽기가 폭증하고 모든 것이 느려져요. 스왑 없는 스래싱이에요.
    4. 이 상태는 메모리가 완전히 바닥나기 전까지 이어져서, OOM이 나기 전에 지연으로 먼저 나타나요. 서버는 죽지도 않고 일하지도 않는 상태로 오래 머물러요.

    해결책

    • 메모리 압력으로 일찍 끊어요. systemd-oomd나 earlyoom은 PSI의 메모리 압력이 일정 수준을 넘으면, 커널의 OOM killer보다 먼저 프로세스를 정리해요. 죽지도 살지도 않는 상태를 짧게 만들어요.
    • 컨테이너에서는 한도를 정확히 둬요. 컨테이너 메모리 한도가 있으면 그 안에서 같은 일이 일어나요. 쿠버네티스는 축출을 판단할 때 RSS가 아니라 working set(최근에 쓴 페이지, 페이지 캐시 일부 포함)을 기준으로 해요.
    • 누수 자체를 일찍 잡아요. 메모리 사용량이 배포 이후 계속 오르기만 한다면 누수예요. 증상이 지연으로 오기 전에 증가 추세로 알람을 걸어요.

    • 쿠버네티스에서는 container_memory_working_set_bytes를 한도와 비교해 80~90%에서 알람을 걸어요.

    2부 병행성

    26~27장 스레드 개요와 API

    왜 스레드가 필요하고, 왜 어려운가

    스레드란

    프로세스 안의 실행 흐름이에요. 같은 프로세스의 스레드는 주소 공간(code, data, heap)을 공유하고, 각자 PC와 레지스터, 스택을 가져요. 그래서 스레드 전환은 페이지 테이블을 바꾸지 않아 프로세스 전환보다 싸요.

    왜 쓰나: (1) 멀티코어 병렬 처리, (2) I/O 대기 중 다른 일 하기(중첩). 프로세스로도 되지만 메모리 공유가 쉬운 스레드가 편해요.

    문제: 공유 데이터

    두 스레드가 전역 counter를 100만 번씩 증가시키면 200만이 나와야 하는데 그보다 작게 나와요. counter++가 사실 세 명령이기 때문이에요.

    mov  counter, %eax    ; 읽기
add  $1, %eax         ; 더하기
mov  %eax, counter    ; 쓰기

    스레드 1이 읽은 직후(50) 타이머 인터럽트로 스레드 2가 실행돼 51을 쓰고, 다시 스레드 1이 돌아와 51을 쓰면 증가가 한 번 사라져요.

    용어

    • 경쟁 조건(race condition): 결과가 실행 타이밍에 따라 달라지는 상황
    • 임계 영역(critical section): 공유 자원에 접근하는 코드 조각
    • 상호 배제(mutual exclusion): 한 번에 한 스레드만 임계 영역에 들어가게 보장
    • 원자적(atomic): 중간에 끊기지 않고 전부 실행되거나 전혀 실행되지 않음

    스레드 API (pthread)

    pthread_create로 생성, pthread_join으로 종료 대기, pthread_mutex_lock/unlock, pthread_cond_wait/signal. Java의 Thread, synchronized, Object.wait/notify와 1:1로 대응돼요. 주의: 스레드에 넘기는 인자를 스택 변수의 주소로 주면 함수가 반환된 뒤 dangling이 돼요.

    백엔드에서는 웹 서버의 요청 하나 = 스레드 하나(톰캣 기본)예요. 요청 처리 중 공유하는 모든 것(static 필드, 싱글톤 빈의 필드, 캐시 Map)은 임계 영역이에요. 스프링 빈은 싱글톤이라 필드에 요청별 상태를 두면 바로 race condition이에요. 이게 "컨트롤러/서비스는 상태가 없어야 한다"는 규칙의 이유예요.
    시니어 심화 본문의 "싱글톤 빈의 필드에 요청별 상태를 두면 경쟁 조건"과 짝을 이루는 실수가 있어요. 상태를 필드가 아니라 ThreadLocal에 두는 거예요. 스레드마다 따로라서 안전해 보이지만, 스레드풀에서는 함정이 돼요.

    상황

    인증 필터가 요청의 토큰을 읽어 "현재 사용자"를 ThreadLocal에 넣고, 서비스 코드는 그것을 꺼내 써요. 어느 날 로그인하지 않은 사용자가 주문 내역 페이지를 열었는데 다른 회원의 주문이 보였다는 신고가 들어왔어요. 재현은 잘 되지 않았어요.

    깨지는 과정

    1. 톰캣의 요청 스레드는 요청이 끝나도 사라지지 않고 풀로 돌아가서 다음 요청에 재사용돼요.
    2. 요청 A(회원 7)가 처리되면서 ThreadLocal에 "현재 사용자 = 회원 7"이 들어갔어요.
    3. 요청 A에서 예외가 났고, 필터의 정리 코드가 예외 경로에서 실행되지 않아 값이 남았어요.
    4. 같은 스레드가 요청 B를 받았어요. B는 토큰이 없는 요청이라 인증 필터가 값을 새로 넣지 않았어요.
    5. 서비스 코드가 ThreadLocal을 읽으니 회원 7이 나와요. B는 회원 7로 처리돼요.

    재현이 어려운 이유는 "예외로 정리를 놓친 스레드"가 "인증 없는 요청"을 받아야 하기 때문이에요. 트래픽이 많으면 하루에 몇 번은 일어나요.

    반대 방향의 문제도 있어요. @Async, CompletableFuture, 병렬 스트림으로 작업을 다른 스레드에 넘기면 ThreadLocal 값이 따라가지 않아요. 로그의 추적 ID(MDC)가 비거나, 보안 컨텍스트가 없어서 권한 검사에 실패해요.

    해결책

    • 넣었으면 반드시 finally에서 remove()해요. 예외가 나도 정리되게 해요. set(null)이 아니라 remove()여야 항목 자체가 지워져요.
    • 읽는 쪽은 값이 없으면 실패하게 해요. 인증이 필요한 코드가 "현재 사용자"를 꺼냈는데 이번 요청에서 설정된 값인지 확인할 수 없다면 위험해요. 요청마다 필터가 항상 새 값(없으면 "익명")으로 덮어쓰게 해요.
    • 프레임워크의 장치를 써요. 스프링 시큐리티의 SecurityContextHolder는 필터 체인이 요청이 끝날 때 정리해 줘요. 직접 ThreadLocal을 만들기보다 요청 스코프 빈이나 프레임워크가 관리하는 컨텍스트를 써요.
    • 다른 스레드로 넘길 때는 복사해요. 스프링의 TaskDecorator로 작업을 넘기는 순간 MDC와 보안 컨텍스트를 복사하고, 작업이 끝나면 지우게 해요.
    • 가상 스레드에서는 비용도 생각해요. 가상 스레드는 요청마다 새로 만들어서 재사용 문제는 줄지만, 수백만 개가 각자 ThreadLocal을 가지면 메모리가 커져요. JDK의 ScopedValue는 범위가 끝나면 자동으로 사라지는 대안이에요.

    테스트와 운영에서 알아채는 법

    • 스레드풀 크기를 1로 줄인 테스트에서 "인증 요청 후 예외, 다음에 익명 요청" 순서로 보내 보면 바로 재현돼요.
    • 요청이 끝날 때 ThreadLocal에 값이 남아 있으면 경고 로그를 남기는 필터를 넣어 두면, 정리를 놓친 경로를 운영에서 찾을 수 있어요.
    핵심 정리
    • 스레드 = 주소 공간 공유 + 스택·레지스터 독립
    • counter++는 3명령, 중간에 끊기면 증가가 사라짐
    • 임계 영역을 상호 배제로 보호해야 함

    28장 락

    상호 배제를 하드웨어와 OS로 구현하는 방법

    락의 조건

    좋은 락은 (1) 상호 배제를 보장하고, (2) 공정해서 굶는 스레드가 없고, (3) 성능이 좋아야 해요(경쟁 없을 때 오버헤드, 경쟁 있을 때 처리량).

    잘못된 시도: 인터럽트 끄기, 플래그

    인터럽트를 끄면 싱글 코어에서는 되지만 멀티코어에서는 안 되고, 악의적 프로그램이 영원히 끌 수 있어요. 단순 플래그(while(flag); flag=1;)는 검사와 설정 사이에 끊길 수 있어서 상호 배제가 깨져요.

    하드웨어 원자 명령

    • Test-and-Set: 옛 값을 반환하면서 새 값을 쓰는 걸 원자적으로. 이걸로 스핀 락을 만들어요: while (TestAndSet(&flag, 1) == 1);
    • Compare-and-Swap (CAS): "현재 값이 expected면 new로 바꾸고 성공 반환". Test-and-Set보다 강력해서 lock-free 자료구조의 기초예요.
    • Fetch-and-Add: 값을 원자적으로 1 올리고 옛 값 반환. 이걸로 티켓 락을 만들면 공정해져요(번호표 순서).

    스핀 vs 슬립

    스핀 락은 락을 못 얻으면 CPU를 태우며 돌아요. 싱글 코어에서 락 가진 스레드가 선점되면 타임 슬라이스를 통째로 낭비해요. 대안:

    • yield(): 못 얻으면 CPU 양보. 스레드가 많으면 여전히 낭비.
    • 큐 + 슬립: 못 얻으면 대기 큐에 넣고 잠들기(park), 해제 시 하나 깨우기(unpark). 리눅스 futex가 이 방식. 경쟁 없으면 사용자 공간에서 CAS만으로 끝나고, 경쟁 있을 때만 커널로 들어가요.
    • 2단계 락: 잠깐 스핀하다가(곧 풀릴 것 같으면) 안 되면 슬립. 실제 뮤텍스 대부분이 이 방식이에요.
    백엔드에서는 Java synchronized는 경쟁 없으면 CAS로 얻는 얇은 락, 경쟁이 생기면 OS 뮤텍스로 부풀어요(lock inflation). AtomicInteger.incrementAndGet()은 CAS 루프예요. 경쟁이 심하면 CAS 실패-재시도가 반복되므로 LongAdder처럼 셀을 나눠 경쟁을 분산해요. DB의 SELECT ... FOR UPDATE도 결국 락이고, 스핀 vs 슬립 문제가 innodb_lock_wait_timeout으로 나타나요.
    시니어 심화 본문은 락의 동작을 다뤘는데, 운영에서 락 문제를 실제로 푸는 데 필요한 것은 "어느 락에서 얼마나 기다리는가"를 재는 거예요. 그리고 가장 흔한 원인은 락을 쥔 채로 하는 I/O예요.

    상황

    환율 정보를 캐시하는 서비스에 synchronized 메서드가 있어요. 캐시가 만료되면 메서드 안에서 외부 환율 API를 불러 갱신해요. 환율 API가 평소 50ms에서 2초로 느려진 날, 환율과 무관한 상품 조회 API까지 모두 2초씩 느려졌어요.

    깨지는 과정

    1. 캐시가 만료된 순간 요청 하나가 락을 잡고 환율 API를 불러요. 2초 동안 락을 쥐고 있어요.
    2. 그 2초 동안 환율이 필요한 모든 요청이 그 락 앞에서 기다려요. 락을 기다리는 시간이 그대로 모든 대기 스레드의 지연이 돼요.
    3. 상품 조회 API도 가격 표시에 환율이 필요해서 같이 기다려요. 톰캣 스레드가 하나둘 락 앞에 묶여요.
    4. 스레드풀이 고갈되면서 환율과 상관없는 API까지 응답하지 못해요. 외부 API 하나의 지연이 서비스 전체의 지연이 돼요.

    해결책

    • 락 안에서는 메모리 연산만 해요. I/O 결과는 락 밖에서 준비하고, 락 안에서는 결과를 바꿔 끼우기만 해요. 위 예라면 환율 API 호출을 락 밖으로 빼고, 받아 온 값을 volatile 필드나 AtomicReference에 넣어요.
    • 갱신하는 동안 옛 값을 돌려줘요. 만료됐을 때 모든 요청이 기다리게 하지 말고, 한 스레드만 비동기로 갱신하고 나머지는 옛 값을 쓰게 해요. Caffeine 캐시의 refreshAfterWrite가 이 방식이에요.
    • 락 획득에도 시간 제한을 둬요. ReentrantLock.tryLock(timeout)으로 기다리는 시간에 상한을 두면, 최악의 경우에도 스레드가 무한히 묶이지 않아요.
    • 가상 스레드라면 한 가지 더 조심해요. JDK 21의 가상 스레드는 synchronized 블록 안에서 블로킹 I/O를 하면 플랫폼 스레드에 고정(pinning)돼서, 소수의 플랫폼 스레드가 금방 고갈돼요. JDK 24에서 이 제약이 대부분 풀렸지만, 그 전 버전에서는 ReentrantLock을 쓰세요.

    운영에서 알아채는 법

    • 스레드 덤프를 몇 초 간격으로 여러 번 떠서, 같은 모니터 주소(waiting to lock <0x...>)를 기다리는 BLOCKED 스레드가 반복해서 보이는지 봐요. 그 락을 쥔 스레드의 스택을 보면 락 안에서 무엇을 하는지 나와요(JVM 챕터 9장).
    • JFR의 jdk.JavaMonitorEnter 이벤트는 어느 락에서 얼마나 기다렸는지를 시간까지 알려줘요. 운영 중에도 켜 둘 수 있을 만큼 가벼워요.
    • 외부 API의 지연 그래프와 무관한 API의 지연 그래프가 같이 움직인다면, 둘을 잇는 공유 자원(락, 스레드풀)을 찾아요.
    핵심 정리
    • 락은 하드웨어 원자 명령(TAS, CAS, FAA) 위에 세워짐
    • 스핀은 짧은 임계 영역·멀티코어에 적합, 슬립은 긴 대기에 적합
    • 실제 뮤텍스 = 잠깐 스핀 → futex로 슬립
    셀프 체크
    1. CAS로 락 없이 카운터를 증가시키는 코드를 의사코드로 써보세요.
    2. 스핀 락이 싱글 코어에서 특히 나쁜 이유는?
    답 보기

    1.

    do {
  old = counter;
} while (!CAS(&counter, old, old + 1));

    2. 락을 가진 스레드가 선점당하면, 스핀하는 스레드는 락이 풀릴 수 없는데도 타임 슬라이스를 끝까지 태워요. 락 소유자가 다시 스케줄될 때까지 아무 진전이 없어요.

    29장 락 기반 병행 자료구조

    락을 어디에, 얼마나 잘게 걸 것인가

    병행 카운터

    가장 단순한 건 카운터 하나에 락 하나. 정확하지만 코어가 늘수록 느려져요(락 경쟁). 해결은 근사 카운터: 코어마다 지역 카운터를 두고 각자 락으로 증가시키다가, 임계값 S에 도달하면 전역 카운터로 옮겨요. S가 크면 빠르지만 전역 값이 부정확해요.

    병행 연결 리스트, 큐, 해시 테이블

    • 리스트: 리스트 전체에 락 하나(단순), 또는 노드마다 락(hand-over-hand locking). 후자는 이론상 병행성이 높지만 락 비용이 커서 실제로는 더 느린 경우가 많아요.
    • 큐: head 락과 tail 락을 분리하면 enqueue와 dequeue가 동시에 가능해요(Michael & Scott 큐). 더미 노드로 둘을 분리해요.
    • 해시 테이블: 버킷마다 락. 서로 다른 버킷 접근은 병렬. 확장성이 매우 좋아요.

    교훈

    "더 많은 병행성 = 더 빠름"이 아니에요. 락을 잘게 쪼개면 락 획득/해제 비용이 늘어요. 먼저 단순하게 만들고, 측정해서 병목일 때만 정교하게 가세요. 그리고 주의: 락을 잡은 채로 return하는 경로(에러 처리)에서 락을 놓지 않는 버그가 매우 흔해요.

    백엔드에서는 Java ConcurrentHashMap이 버킷 단위 락 + CAS예요(Java 7까지는 세그먼트 단위 락). Collections.synchronizedMap은 전체 락이라 경쟁 시 훨씬 느려요. LongAdder가 근사 카운터예요. DB에서도 같은 원리예요. 테이블 락보다 행 락이, 행 락보다 낙관적 락이 병행성이 높지만 비용이 달라요. 그리고 "핫 로우"(모든 요청이 같은 행을 UPDATE)는 아무리 행 락이라도 직렬화돼요. 카운터를 샤딩하거나 Redis로 빼는 이유예요.
    시니어 심화 본문의 "핫 로우는 행 락이어도 직렬화된다"를 메모리 안의 자료구조로 옮기면 거짓 공유가 돼요. 락을 잘게 쪼개고 카운터를 나눠도, 나눈 조각들이 같은 캐시 라인에 있으면 하드웨어 수준에서 여전히 다퉈요.

    상황

    API 서버의 요청 수를 세는 카운터가 병목이 되자, 스레드마다 자기 칸에만 쓰도록 long[] counts = new long[threads]로 나눴어요. 코드상으로는 스레드끼리 공유하는 변수가 없어졌어요. 그런데 성능은 거의 그대로였고, 코어가 많은 서버일수록 오히려 느렸어요.

    깨지는 과정

    1. CPU는 메모리를 바이트 단위가 아니라 64바이트 캐시 라인 단위로 가져오고 관리해요.
    2. long은 8바이트라서, 배열의 연속된 칸 8개가 한 캐시 라인에 들어가요. 스레드 0~7의 카운터가 같은 라인에 있어요.
    3. 코어 A가 스레드 0의 칸을 쓰면, 그 라인 전체가 "코어 A가 수정함"이 되고 다른 코어들에 있던 같은 라인의 복사본은 무효가 돼요.
    4. 코어 B가 스레드 1의 칸을 쓰려면 그 라인을 코어 A에서 다시 가져와야 해요. 서로 다른 변수를 쓰는데도 라인 하나를 두고 코어들이 계속 주고받아요.
    5. 코드상으로는 공유가 없는데 코어를 늘릴수록 주고받는 횟수가 늘어 느려져요. 이것을 거짓 공유(false sharing)라고 해요.

    해결책

    • 조각 사이에 빈 공간을 넣어요. 각 카운터가 서로 다른 캐시 라인에 있도록 칸 사이를 64바이트 이상 띄워요. 배열이라면 인덱스를 8칸 간격으로 쓰는 식이에요.
    • 이미 만들어진 것을 써요. 자바의 LongAdder는 내부적으로 칸을 나누고 칸 사이를 띄워서 거짓 공유를 피해요. 직접 만들 일은 거의 없어요(컴퓨터 구조 챕터 4장, 6장).
    • 필드 단위로는 @Contended가 있어요. JDK 내부 클래스는 이 애너테이션으로 필드 주변에 공간을 넣어요. 애플리케이션 코드에서 쓰려면 -XX:-RestrictContended 옵션이 필요하고 내부 API라서, 꼭 필요한 경우에만 써요.

    대가: 빈 공간만큼 메모리를 더 써요. 카운터가 수천 개라면 그 비용이 커지니, 정말 여러 코어가 동시에 쓰는 곳에만 적용해요.

    측정하고 알아채는 법

    • "스레드를 늘렸는데 처리량이 늘지 않거나 줄어든다"면 의심해요. 스레드 수를 1, 2, 4, 8, 16으로 바꿔 가며 처리량을 재는 JMH 벤치마크로 확인해요.
    • 리눅스의 perf c2c는 여러 코어가 같은 캐시 라인을 두고 다투는 지점을 코드 위치와 함께 보여 줘요.
    핵심 정리
    • 락 하나 = 단순하지만 확장 안 됨, 잘게 쪼개면 경쟁은 줄지만 오버헤드 증가
    • 근사 카운터, 버킷별 락, head/tail 분리 큐가 대표 기법
    • 측정 없이 최적화하지 말 것
    셀프 체크
    1. 상품 조회수 카운터가 핫 로우가 되어 DB 락 경쟁이 심해요. 이 장의 아이디어로 어떻게 풀까요?
    답 보기

    근사 카운터 아이디어: 서버 메모리나 Redis에서 증가시키고, 주기적으로(또는 임계값마다) DB에 합산해서 반영해요. 정확한 실시간 값은 포기하고 처리량을 얻어요. 또는 카운터 행을 N개로 쪼개 랜덤하게 증가시키고 읽을 때 합산해요.

    30장 조건 변수

    "어떤 조건이 참이 될 때까지 기다리기"를 올바르게 하는 법

    문제

    부모 스레드가 자식이 끝나길 기다리고 싶어요. while (!done);으로 스핀하면 CPU를 낭비해요. 락만으로는 "조건을 기다린다"를 표현할 수 없어요.

    조건 변수

    조건 변수는 대기 큐예요. wait(cond, mutex)는 뮤텍스를 풀고 잠들었다가, 깨어나면 뮤텍스를 다시 잡고 반환해요. signal(cond)은 대기 중인 스레드 하나를 깨워요.

    // 기다리는 쪽
lock(m);
while (done == 0)      // if가 아니라 while!
    wait(c, m);
unlock(m);

// 알리는 쪽
lock(m);
done = 1;
signal(c);
unlock(m);

    규칙 두 가지

    1. 상태 변수(done)를 꼭 둬요. 조건 변수만 쓰면 signal이 wait보다 먼저 일어났을 때 신호가 사라져 영원히 기다려요.
    2. 항상 while로 재검사해요. 깨어났을 때 조건이 이미 다시 거짓일 수 있어요(다른 스레드가 먼저 가져감). 또 가짜 깨어남(spurious wakeup)도 있어요.

    생산자/소비자 (유한 버퍼)

    생산자는 버퍼가 꽉 차면 기다리고, 소비자는 비면 기다려요. 조건 변수를 하나만 쓰면 소비자가 소비자를 깨우는 일이 생겨 멈출 수 있어요. empty와 fill 두 개를 써서 생산자는 fill을 signal하고 empty를 wait, 소비자는 반대로 해요.

    Covering condition

    누구를 깨워야 할지 모를 때 broadcast로 전부 깨우고 각자 while로 재검사하게 해요. 불필요한 깨움이 생기지만 정확해요.

    백엔드에서는 BlockingQueue(스레드풀의 작업 큐)가 정확히 유한 버퍼 생산자/소비자예요. Java의 Object.wait()는 반드시 synchronized 안에서, while 루프로 써야 하는 이유가 이 장이에요. 커넥션 풀에서 커넥션이 반납될 때까지 기다리는 것도 조건 변수예요(HikariCP는 더 정교한 구조를 쓰지만 원리는 같아요).
    시니어 심화 본문의 커넥션 풀 대기도 조건 변수인데, 운영에서 중요한 것은 "대기에는 반드시 끝이 있어야 한다"는 거예요. 타임아웃 없는 대기는 한 곳의 고갈을 시스템 전체로 퍼뜨려요.

    상황

    주문 DB가 30초 동안 느려졌어요. 그 30초 동안 주문 API뿐 아니라 DB를 전혀 쓰지 않는 헬스 체크, 상품 이미지 프록시 API까지 응답하지 않았어요. 헬스 체크가 실패하자 쿠버네티스가 파드들을 재시작하면서 장애가 더 커졌어요.

    깨지는 과정

    1. DB가 느려지자 커넥션을 빌린 요청들이 커넥션을 늦게 돌려줘요. 풀이 금방 바닥나요.
    2. 새 요청은 커넥션을 얻으려고 풀 앞에서 기다려요. 기다리는 시간에 상한이 없거나 너무 길면(30초), 스레드가 그대로 묶여요.
    3. 톰캣의 요청 스레드 200개가 전부 풀 앞에 묶여요. DB와 상관없는 요청도 처리할 스레드가 없어요.
    4. 헬스 체크도 응답하지 못해 실패로 판정되고, 재시작으로 이어져요. DB 한 곳의 느려짐이 서비스 전체 장애가 됐어요.

    큐도 같은 문제를 가져요. 기다린 시간이 길어지면, 작업을 꺼냈을 때 그 요청을 보낸 클라이언트는 이미 타임아웃으로 포기했을 수 있어요. 아무도 기다리지 않는 결과를 만드느라 자원을 쓰는 거예요.

    해결책

    • 획득 대기에 짧은 상한을 둬요. HikariCP의 connectionTimeout을 요청 전체 타임아웃보다 훨씬 짧게(예: 1~3초) 잡아서, 풀이 고갈되면 빨리 실패하게 해요. 빠른 실패는 스레드를 풀어서 다른 요청이 처리되게 해요.
    • 마감 시간을 전파해요. 요청이 처음 들어올 때 "언제까지 응답해야 하는가"를 정하고, 하위 호출마다 남은 시간을 넘겨요. gRPC의 deadline이 이 방식이에요. 남은 시간이 없으면 하위 호출을 하지 않고 바로 실패해요.
    • 큐에서 꺼낼 때 나이를 확인해요. 작업에 넣은 시각을 기록하고, 꺼냈을 때 클라이언트 타임아웃보다 오래됐으면 처리하지 않고 버려요.
    • 헬스 체크를 의존성과 분리해요. 살아 있는지 보는 검사(liveness)는 DB 상태와 무관하게 응답하게 하고, 요청을 받을 준비가 됐는지 보는 검사(readiness)만 의존성을 봐요. DB 문제로 파드가 재시작되는 일을 막아요.

    운영에서 알아채는 법

    • 큐나 풀의 길이보다 대기 시간을 지표로 봐요. 길이 100이 괜찮은지는 처리 속도에 따라 다르지만, 대기 시간 3초는 그 자체로 문제라는 뜻이에요.
    • HikariCP의 hikaricp_connections_pending(기다리는 스레드 수)과 커넥션 획득 시간을 봐요. 이 값이 오를 때 DB와 무관한 API의 지연도 같이 오르면 스레드 고갈이 퍼지고 있는 거예요.
    핵심 정리
    • 조건 변수 = 조건을 기다리는 큐, wait는 락을 풀고 잠듦
    • 상태 변수 + while 재검사는 필수
    • 생산자/소비자는 조건 변수 2개
    셀프 체크
    1. wait 전 조건 검사를 if로 하면 생기는 문제 두 가지는?
    답 보기

    (1) 깨어난 뒤 락을 다시 잡기 전에 다른 스레드가 조건을 다시 거짓으로 만들 수 있어요(예: 소비자 둘이 깨어나 하나가 먼저 가져감). (2) 가짜 깨어남으로 signal 없이 반환될 수 있어요. 둘 다 조건이 거짓인 채 진행해서 버그가 돼요.

    31장 세마포어

    락과 조건 변수를 하나로 — Dijkstra의 세마포어

    정의

    정수 값을 가진 객체예요. sem_wait()(P)는 값을 1 줄이고, 음수면 잠들어요. sem_post()(V)는 값을 1 늘리고, 기다리는 스레드가 있으면 하나 깨워요. 초기값이 의미를 결정해요.

    용도

    • 이진 세마포어 = 락: 초기값 1. wait = lock, post = unlock.
    • 순서 맞추기: 초기값 0. 부모가 wait, 자식이 끝나면 post. 조건 변수 대용.
    • 생산자/소비자: empty(초기값 = 버퍼 크기), full(초기값 0), 그리고 버퍼 보호용 mutex. 주의: mutex를 empty/full wait 바깥에 걸면 생산자가 mutex 잡고 empty에서 잠들어 데드락이 나요. mutex는 안쪽에.
    • 카운팅: 초기값 N. 동시에 N개까지 허용. 읽기-쓰기 락, 동시 접속 제한.

    읽기-쓰기 락

    읽기는 여러 스레드가 동시에, 쓰기는 혼자. 첫 번째 읽기가 쓰기 락을 잡고 마지막 읽기가 풀어요. 단순 구현은 읽기가 계속 들어오면 쓰기가 굶어요(writer starvation). 실제로는 복잡도 대비 이득이 작은 경우가 많아요.

    식사하는 철학자

    5명이 원탁에서 양옆 포크 2개가 있어야 먹어요. 모두 왼쪽 포크를 잡으면 데드락. 해결: 한 명만 순서를 바꿔 오른쪽부터 잡게 해요(순환 대기 깨기). 32장 데드락의 예고편이에요.

    백엔드에서는 Java Semaphore(N)으로 외부 API 동시 호출 수를 제한해요(bulkhead). 커넥션 풀의 "최대 N개"가 카운팅 세마포어예요. Resilience4j Bulkhead, Go의 버퍼 채널도 같은 것이에요.
    시니어 심화 본문의 "Semaphore로 외부 API 동시 호출 수를 제한"을 운영에 적용할 때 가장 자주 틀리는 점은 한도가 인스턴스마다 따로라는 거예요.

    상황

    결제사가 "동시 요청 100개까지"를 요구해서, 결제 호출에 new Semaphore(10)을 걸었어요. 서버가 10대니 합쳐서 100개라고 계산했어요. 세일 날 오토스케일링으로 서버가 30대가 되자 결제사가 한도 초과로 요청을 거절하기 시작했어요.

    깨지는 과정

    1. 세마포어는 그 프로세스 안에서만 세요. 서버 30대면 결제사에는 동시에 최대 300개가 가요.
    2. 하위 시스템을 보호하려고 건 한도가, 정작 트래픽이 몰려 서버가 늘어나는 순간 함께 커져요. 가장 보호가 필요한 순간에 보호가 약해지는 구조예요.
    3. 결제사가 거절하자 클라이언트가 재시도했고, 재시도까지 더해져 거절이 더 늘었어요.
    4. 게다가 세마포어 획득에 타임아웃이 없었어요. 결제사가 느려지자 요청 스레드들이 세마포어 앞에 무한히 줄을 섰고, 격벽(벌크헤드)이 아니라 그냥 대기열이 됐어요.

    해결책

    • 전체 합계는 한 곳에서 지켜요. 결제 호출을 모두 결제 서비스 하나(또는 API 게이트웨이)를 거치게 하고 거기서 제한해요. 또는 Redis 같은 중앙 저장소로 전체 동시 호출 수를 세요(자료구조 챕터 9장 시니어). 중앙 저장소를 쓰면 그 저장소가 장애일 때의 동작도 정해야 해요.
    • 인스턴스별 한도라면 서버 수와 함께 관리해요. 오토스케일 최대 서버 수 × 인스턴스 한도가 하위 시스템의 한도를 넘지 않게 정해요.
    • 획득에 시간 제한을 둬요. tryAcquire(200, MILLISECONDS)처럼 기다리는 시간을 정하고, 못 얻으면 빠르게 실패하거나 대체 응답(예: "결제 대기 중" 상태로 접수)을 줘요. Resilience4j의 Bulkhead는 maxWaitDuration으로 같은 설정을 해요.
    • 재시도도 한도 안에서 해요. 재시도 요청도 같은 세마포어를 거치게 해서, 재시도가 한도를 우회하지 않게 해요.

    운영에서 알아채는 법

    • 하위 시스템이 보는 동시 요청 수(결제사가 제공하는 지표나 우리 쪽 전체 합계)를 서버 수 그래프와 겹쳐 봐요. 서버 수에 비례해 오른다면 한도가 인스턴스별이에요.
    • 세마포어 대기 시간과 획득 실패 수를 지표로 남겨요. 실패가 늘면 한도가 실제 수요보다 작거나 하위가 느려진 거예요.
    핵심 정리
    • 세마포어 = 카운터 + 대기 큐, 초기값이 역할을 정함
    • 1이면 락, 0이면 순서, N이면 동시 N개 제한
    셀프 체크
    1. 외부 결제 API 동시 호출을 10개로 제한하고 싶어요. 세마포어로 어떻게?
    답 보기

    Semaphore(10)을 만들고, 호출 전 acquire(), 완료 후 finally에서 release(). 11번째 요청은 하나가 끝날 때까지 블록돼요. 무한 대기 대신 tryAcquire(timeout)으로 빠르게 실패시키는 게 보통 더 좋아요.

    32장 병행성 버그

    실제 소프트웨어의 동시성 버그는 어떤 모양인가

    비-데드락 버그 (조사한 버그의 약 70%)

    • 원자성 위반: "검사 후 사용"이 원자적이어야 하는데 중간에 끊김. if (p != null) use(p) 사이에 다른 스레드가 p를 null로. 해결: 락으로 묶기.
    • 순서 위반: A가 B보다 먼저 실행된다고 가정했는데 아닐 수 있음. 스레드 생성 후 초기화가 끝나기 전에 사용. 해결: 조건 변수/세마포어로 순서 강제.

    데드락

    스레드 1이 L1 잡고 L2 기다림, 스레드 2가 L2 잡고 L1 기다림. 큰 코드베이스에서 캡슐화 때문에 생겨요. Vector.addAll(other)가 this와 other를 잠그는데 두 스레드가 반대 방향으로 호출하면 데드락.

    데드락의 4조건

    1. 상호 배제: 자원을 배타적으로 점유
    2. 점유 대기: 자원을 가진 채 다른 자원을 기다림
    3. 비선점: 자원을 강제로 뺏을 수 없음
    4. 순환 대기: 대기 그래프에 사이클

    하나만 깨면 데드락이 없어요.

    예방

    깨는 조건방법
    순환 대기락 순서 고정(전역 순서 또는 주소 순). 가장 실용적.
    점유 대기모든 락을 한 번에 잡기(큰 락으로 감싸기). 병행성 저하.
    비선점trylock 실패 시 가진 것 풀고 재시도. 라이브락 가능 → 랜덤 지연.
    상호 배제락 없이 CAS 기반 자료구조. 어려움.

    그 외: 회피(스케줄러가 락을 함께 쓰는 스레드를 동시에 안 돌림, 비실용적), 탐지와 복구(주기적으로 대기 그래프 사이클 검사, DB가 쓰는 방식).

    백엔드에서는 DB 데드락이 가장 흔해요. 트랜잭션 A가 행 1 → 행 2 순으로, B가 행 2 → 행 1 순으로 UPDATE하면 발생해요. InnoDB는 탐지해서 한쪽을 롤백해요. 애플리케이션은 항상 같은 순서(PK 오름차순)로 접근하고, 데드락 에러를 재시도해요. JVM 데드락은 jstack이 "Found one Java-level deadlock"으로 알려줘요. 그리고 "검사 후 사용" 원자성 위반은 if (!exists) insert로 유니크 제약 위반이 나는 바로 그 패턴이에요.
    시니어 심화 본문의 데드락은 락 두 개 사이의 이야기였는데, 백엔드에서는 락이 하나도 없는 데드락도 흔해요. 스레드풀 자체가 자원이기 때문이에요.

    상황

    상품 상세 API가 가격, 재고, 리뷰를 동시에 가져오려고 공용 스레드풀(크기 10)에 작업을 넣어요. 그런데 이 API 자체도 같은 풀에서 실행되고 있었어요. 평소에는 멀쩡하다가, 세일 시작 순간 API가 완전히 멈췄고 CPU는 0%였어요. 데드락 탐지 도구는 아무것도 찾지 못했어요.

    깨지는 과정

    1. 상품 상세 요청 10개가 동시에 들어와 풀의 스레드 10개를 모두 차지해요.
    2. 각 요청은 가격, 재고, 리뷰 조회를 같은 풀에 넣고 get()으로 결과를 기다려요.
    3. 하위 작업 30개는 큐에 들어갔지만, 실행할 스레드가 없어요. 스레드 10개는 전부 그 하위 작업의 결과를 기다리고 있어요.
    4. 부모는 자식을 기다리고, 자식은 부모가 차지한 스레드를 기다려요. 아무도 진행하지 못해요. 락이 없으니 JVM의 데드락 탐지에도 잡히지 않아요.

    부하가 낮을 때는 스레드가 남아서 자식 작업이 바로 실행되니 멀쩡해요. 동시 요청 수가 풀 크기에 닿는 순간에만 멈추니 재현이 어려워요.

    같은 일이 다른 곳에서도 생겨요. CompletableFuture.supplyAsync()와 병렬 스트림은 따로 지정하지 않으면 JVM 전체가 공유하는 ForkJoinPool.commonPool()을 써요. 서로 모르는 코드가 같은 풀을 쓰다가 같은 모양으로 막혀요.

    해결책

    • 부모와 자식 작업은 다른 풀에 둬요. 요청을 처리하는 풀과 하위 조회를 실행하는 풀을 분리하면, 부모가 모든 스레드를 차지해도 자식이 실행될 자리가 있어요.
    • 기다리지 말고 이어 붙여요. get()으로 스레드를 묶어 두는 대신 thenCombine, allOf로 결과가 모이면 다음 단계가 실행되게 해요. 기다리는 스레드가 없으니 이 데드락이 생기지 않아요.
    • 공용 풀을 쓰지 말고 풀을 명시해요. supplyAsync(task, executor)처럼 항상 전용 풀을 넘겨요.
    • 기다림에는 시간 제한을 둬요. get(2, SECONDS)처럼 상한을 두면, 막혀도 무한히 멈추지는 않아요.

    서비스 사이에서도 같은 일이 생겨요. A 서비스가 B를 동기로 부르고, B가 처리 중에 다시 A를 부르면, 양쪽 스레드풀이 서로를 기다리며 고갈돼요. 이때는 탐지 도구가 없어서 타임아웃이 유일한 방어예요. 서비스 간 호출 그래프에 순환이 없게 설계하는 것이 근본 해결이에요.

    운영에서 알아채는 법

    • CPU는 한가한데 응답이 전혀 없다면 스레드 덤프를 떠 봐요. 풀의 스레드가 전부 CompletableFuture.get이나 FutureTask.get에서 WAITING이고, 그 풀의 큐에 작업이 쌓여 있다면 이 데드락이에요.
    • 풀별로 활성 스레드 수와 큐 길이를 지표로 남겨요. 활성 스레드가 최대에 붙어 있는데 완료 작업 수가 늘지 않는다면 멈춘 거예요.
    핵심 정리
    • 대부분은 원자성 위반·순서 위반, 데드락은 소수지만 치명적
    • 4조건 중 하나 깨기, 실무는 락 순서 고정 + 타임아웃 + 재시도
    셀프 체크
    1. 계좌 이체(A→B, B→A 동시)에서 데드락이 나는 이유와 해결책은?
    답 보기

    이체 1은 A 행 잠금 후 B 행, 이체 2는 B 후 A를 잠가 순환 대기. 해결: 두 계좌 ID를 정렬해서 항상 작은 ID부터 잠가요. 그러면 둘 다 A → B 순서라 한쪽이 기다렸다가 진행해요.

    33장 이벤트 기반 병행성

    스레드 없이 동시성을 다루는 방법 — Node.js와 Nginx의 원리

    기본 아이디어

    스레드 대신 이벤트 루프 하나가 "이벤트가 오면 처리"를 반복해요. 루프는 단일 스레드라서 락이 필요 없고, 스케줄링을 애플리케이션이 직접 통제해요.

    while (1) {
    events = getEvents();      // 준비된 것 기다리기
    for (e in events)
        processEvent(e);       // 핸들러 실행
}

    이벤트 받기: select / poll / epoll

    select()는 fd 집합을 주면 읽기/쓰기 가능한 것을 알려줘요. 호출마다 집합 전체를 커널에 복사하고 전부 검사해서 O(n)이에요. 리눅스 epoll은 관심 fd를 커널에 한 번 등록하고, 준비된 것만 받아요. 커넥션이 수만 개라도 비용이 준비된 수에만 비례해요.

    블로킹 호출 문제

    핸들러 안에서 블로킹 시스템 콜(디스크 읽기, 동기 DB 호출)을 하면 루프 전체가 멈춰요. 다른 모든 이벤트가 기다려요. 해결은 비동기 I/O: 요청만 보내고 바로 반환, 완료되면 이벤트로 받기. 리눅스 AIO, io_uring, 또는 블로킹 작업을 별도 스레드풀에 보내기(Node.js libuv가 파일 I/O에 이렇게 해요).

    상태 관리

    스레드는 스택에 상태가 자연스럽게 남지만, 이벤트 기반은 요청을 보낼 때와 결과를 받을 때가 다른 핸들러라서 상태를 수동으로 넘겨야 해요(continuation). 콜백 지옥의 원인이고, async/await가 이걸 문법으로 숨겨 줘요.

    남는 문제

    멀티코어를 쓰려면 루프를 여러 개 돌려야 하고 그러면 다시 동기화 문제가 생겨요. 페이징(페이지 폴트)은 암묵적 블로킹이라 피할 수 없어요. 라이브러리가 내부에서 블로킹하면 알기 어려워요.

    백엔드에서는 Node.js, Netty(Spring WebFlux), Nginx, Redis가 전부 이 모델이에요. 그래서 "이벤트 루프를 막지 마라"가 철칙이에요. WebFlux에서 JDBC(블로킹)를 쓰면 루프가 멈춰요. R2DBC나 별도 스케줄러(subscribeOn(boundedElastic))를 쓰는 이유예요. Redis가 단일 스레드인데 빠른 이유도 이 모델 + 모든 데이터가 메모리라 블로킹이 없어서예요. KEYS *처럼 O(n) 명령이 루프를 막으면 전체가 멈춰요.
    시니어 심화 본문은 블로킹 호출이 이벤트 루프를 막는다고 했는데, 이벤트 루프에는 스레드 모델에 없는 또 하나의 위험이 있어요. 동시에 처리하는 요청 수에 자연스러운 상한이 없다는 거예요.

    상황

    스레드 기반 API 서버를 WebFlux로 바꾸고 나서 처리량이 크게 늘었어요. 그런데 추천 서비스가 느려진 날, WebFlux 서버는 메모리가 계속 늘다가 OOM으로 죽었어요. 같은 날 예전 스레드 기반 서버였다면 느려지기만 했을 거예요.

    깨지는 과정

    1. 스레드 모델에서는 요청 하나가 스레드 하나를 차지해요. 스레드 200개가 다 차면 더 이상 요청을 처리하지 못하고, 새 요청은 accept 큐에서 기다리거나 거절돼요. 과부하가 자연스럽게 "더 못 받음"으로 드러나요.
    2. 이벤트 루프는 스레드를 기다리게 하지 않으니 연결을 계속 받아들여요. 하위 호출이 느려져도 요청마다 콜백과 버퍼만 메모리에 걸어 두고 다음 요청을 받아요.
    3. 추천 서비스가 평소 50ms에서 5초로 느려지자, 동시에 진행 중인 요청이 평소의 100배로 늘었어요. 요청마다 붙은 요청 객체, 응답 버퍼, 하위 호출 상태가 메모리에 쌓였어요.
    4. 상한이 없으니 메모리가 다 찰 때까지 받아들이다가 한꺼번에 죽었어요.

    가상 스레드와 고루틴도 같아요. 이 기술들은 이벤트 루프와 같은 다중화를 런타임 안에 숨기고 코드는 동기식으로 쓰게 해 주지만, 스레드가 싸서 수만 개를 만들 수 있으니 "스레드 수가 곧 상한"이던 자연스러운 제한이 사라져요(JVM 챕터 8장). 그 제한은 다음 병목, 보통 DB 커넥션 풀로 옮겨 가요.

    해결책

    • 동시 처리 요청 수에 상한을 명시해요. 서버 입구에서 진행 중인 요청 수를 세고, 상한을 넘으면 즉시 503을 돌려줘요. 상한은 "메모리 여유 ÷ 요청당 메모리"와 하위 시스템의 처리 능력으로 정해요.
    • 하위 호출마다 동시성 제한을 둬요. 느려진 하위 서비스 하나가 전체 상한을 다 차지하지 않게, 하위 호출별로 동시 호출 수를 제한해요(31장 시니어).
    • 하위 호출에 타임아웃을 둬요. 5초짜리 응답을 기다리는 요청이 쌓이지 않게, 하위 호출의 타임아웃을 짧게 둬요. 이벤트 루프에서는 기다림이 싸 보여서 타임아웃을 빼먹기 쉬워요.
    • 상한을 자동으로 조정할 수도 있어요. Netflix의 concurrency-limits 같은 라이브러리는 응답 시간을 보고 동시 처리 상한을 자동으로 늘리고 줄여요.

    운영에서 알아채는 법

    • "진행 중인 요청 수"를 지표로 남겨요. 스레드 모델에서는 스레드 수로 저절로 보이던 값이, 이벤트 루프와 가상 스레드에서는 직접 재지 않으면 안 보여요.
    • 하위 서비스가 느려진 시각에 진행 중인 요청 수와 힙 사용량이 함께 오른다면 상한이 없는 거예요.
    핵심 정리
    • 이벤트 루프 = 단일 스레드 + epoll, 락 불필요
    • 블로킹 호출 하나가 전체를 멈춤 → 비동기 I/O 또는 별도 스레드풀
    • 상태를 수동으로 전달해야 함 → async/await
    셀프 체크
    1. 스레드 기반과 이벤트 기반 서버의 장단점을 각각 두 가지씩 말해보세요.
    2. Redis에서 KEYS *가 위험한 이유는?
    답 보기

    1. 스레드: 코드가 순차적이라 쉽고 블로킹 호출이 자연스러움 / 스레드당 메모리와 컨텍스트 스위칭 비용, 락 필요. 이벤트: 커넥션당 비용이 매우 작고 락 불필요 / 블로킹 하나가 전체를 멈추고, 상태를 수동 전달해야 해 코드가 복잡.

    2. 단일 이벤트 루프에서 O(n) 명령을 실행하는 동안 다른 모든 클라이언트 요청이 멈춰요. 키가 수백만 개면 수 초 동안 Redis가 응답하지 않아요. SCAN으로 나눠서 해야 해요.

    3부 영속성

    36장 I/O 장치

    CPU가 장치와 대화하는 방법 — 폴링, 인터럽트, DMA

    시스템 구조

    CPU와 메모리는 빠른 메모리 버스로, 그래픽은 PCIe로, 디스크와 네트워크는 더 느린 I/O 버스로 연결돼요. 빠른 장치일수록 CPU 가까이 있어요.

    장치 인터페이스

    장치는 상태(status), 명령(command), 데이터(data) 레지스터를 노출해요. OS는 상태 레지스터를 읽어 바쁜지 확인하고, 데이터와 명령을 써서 작업을 시켜요.

    폴링 vs 인터럽트

    • 폴링: 상태 레지스터를 반복해서 읽으며 끝났는지 확인. 단순하지만 CPU 낭비.
    • 인터럽트: 요청 보내고 다른 프로세스 실행. 장치가 끝나면 인터럽트를 걸고, 핸들러가 깨워요. CPU와 I/O의 중첩이 가능해요.

    인터럽트가 항상 좋은 건 아니에요. 장치가 아주 빠르면(첫 폴링에 끝나는 수준) 인터럽트 처리와 컨텍스트 스위치가 더 비싸요. 네트워크 패킷이 폭주하면 인터럽트 처리만 하다 라이브락에 빠져요. 그래서 하이브리드(잠깐 폴링 후 인터럽트), 병합(여러 인터럽트를 모아 한 번)을 써요.

    DMA

    큰 데이터를 장치로 옮길 때 CPU가 한 워드씩 복사하면 낭비예요. DMA 엔진에 "이 메모리를 이 장치로"라고 시키면 CPU 없이 복사하고 끝나면 인터럽트를 걸어요.

    장치 드라이버

    장치마다 다른 인터페이스를 OS가 추상화하려고 드라이버 계층을 둬요. 리눅스 커널 코드의 70%가 드라이버예요.

    백엔드에서는 리눅스 NAPI가 네트워크 드라이버의 하이브리드 폴링이에요. 고성능 서버에서 패킷 폭주 시 softirq가 CPU를 다 먹는 걸 top의 si 열로 봐요. sendfile, zero-copy는 "커널 버퍼 → 사용자 버퍼 → 소켓 버퍼" 복사를 DMA로 줄이는 거예요. Kafka가 디스크에서 네트워크로 빠른 이유예요.
    시니어 심화 본문의 zero-copy는 Kafka가 빠른 이유로 자주 언급되는데, 이 최적화는 데이터를 가공하지 않을 때만 성립해요. 설정 하나로 조용히 꺼질 수 있어요.

    상황

    보안 감사 요구로 Kafka 클라이언트와 브로커 사이 통신에 TLS를 켰어요. 그 뒤 같은 트래픽에서 브로커의 CPU 사용률이 두 배 가까이 올랐고, 컨슈머 처리량이 떨어졌어요.

    깨지는 과정

    1. Kafka는 컨슈머에게 데이터를 보낼 때 sendfile을 써요. 디스크의 로그 파일 바이트를 커널 안에서 곧바로 소켓으로 넘겨요. 브로커 프로세스가 데이터를 한 번도 메모리로 읽지 않으니 복사도 CPU도 거의 들지 않아요.
    2. TLS를 켜면 소켓으로 나가기 전에 데이터를 암호화해야 해요. 암호화는 TLS 라이브러리가 하니, 브로커가 데이터를 자기 메모리로 읽어서 암호화한 뒤 다시 써야 해요.
    3. sendfile 경로가 깨지고, 읽기, 암호화, 쓰기 복사가 생겨요. CPU 사용이 늘고 처리량이 떨어져요.

    zero-copy를 깨는 경우가 하나 더 있어요. 브로커에 저장된 메시지 형식과 컨슈머가 기대하는 형식이 다르면, 브로커가 메시지를 읽어 형식을 바꿔(down-conversion) 보내야 해요. 아주 오래된 클라이언트가 하나 섞여 있으면 그 클라이언트에 대해 같은 일이 생겨요.

    해결책

    • 성능 수치를 볼 때 조건을 확인해요. "Kafka는 zero-copy라 빠르다"는 벤치마크가 TLS를 끈 상태인지 꼭 봐요. 용량 계획은 실제로 쓸 설정(TLS 포함)으로 측정한 값으로 해요.
    • 커널 TLS를 고려해요. 최근 리눅스는 커널 안에서 TLS 암호화를 하는 기능(kTLS)이 있어서, sendfile과 TLS를 함께 쓸 수 있어요. 커널, JDK, 네트워크 카드 지원 여부를 확인해야 하고, 아직 모든 환경에서 쓸 수 있는 것은 아니에요.
    • TLS가 필요한 구간을 정해요. 같은 보안 구역 안의 브로커 사이 통신과 외부에서 오는 클라이언트 통신을 구분해서, 정말 필요한 리스너에만 TLS를 켜는 구성도 가능해요. 보안 요구사항과 함께 판단해요.
    • 클라이언트 버전을 맞춰요. 오래된 클라이언트를 업그레이드해서 형식 변환이 일어나지 않게 해요.

    운영에서 알아채는 법

    • 브로커의 CPU 사용률을 "초당 내보낸 바이트"로 나눈 값을 지표로 봐요. TLS를 켜거나 클라이언트가 바뀐 뒤 이 값이 뛰면 zero-copy가 깨진 거예요.
    • Kafka 브로커의 형식 변환 관련 지표(FetchMessageConversionsPerSec)가 0이 아니라면, 어떤 컨슈머가 변환을 일으키는지 찾아요.
    핵심 정리
    • 폴링은 빠른 장치, 인터럽트는 느린 장치, 실제는 하이브리드
    • DMA = CPU 없이 메모리↔장치 복사
    셀프 체크
    1. 인터럽트 방식이 오히려 느린 경우는?
    답 보기

    장치가 매우 빨라 폴링 한두 번이면 끝날 때(인터럽트 + 컨텍스트 스위치 비용이 더 큼), 그리고 인터럽트가 폭주해 처리만 하다가 실제 일을 못 하는 라이브락 상황.

    37장 & 44장 하드 디스크와 SSD

    저장 장치의 물리 특성이 DB 설계를 결정한다

    하드 디스크

    회전하는 플래터 위를 헤드가 움직여 트랙과 섹터(512B 또는 4KB)를 읽어요. I/O 시간은 세 요소의 합이에요.

    • 탐색(seek): 헤드를 트랙으로 이동. 수 ms.
    • 회전 지연: 섹터가 헤드 아래 올 때까지. 7200rpm이면 평균 약 4ms.
    • 전송: 실제 읽기. 빠름.

    그래서 랜덤 I/O는 수 ms, 순차 I/O는 100MB/s 이상이에요. 차이가 100배 이상. 디스크 스케줄러(SSTF, SCAN/엘리베이터)는 탐색을 줄이려고 요청 순서를 바꿔요. OS는 "작은 랜덤 쓰기"를 모아 "큰 순차 쓰기"로 바꾸려 노력해요.

    SSD (플래시)

    움직이는 부품이 없어 랜덤 읽기가 수십 µs예요. 하지만 플래시의 특성 때문에 복잡해요.

    • 읽기/쓰기(program)는 페이지(4KB~16KB) 단위, 지우기(erase)는 블록(수 MB) 단위.
    • 페이지는 덮어쓸 수 없고, 블록 전체를 지운 뒤에만 다시 쓸 수 있어요.
    • 블록마다 지우기 횟수 한계(수천~수만 회)가 있어요 → wear leveling 필요.

    그래서 SSD 안의 FTL(Flash Translation Layer)이 논리 주소 → 물리 페이지 매핑을 관리하면서 로그 구조로 동작해요. 새 쓰기는 항상 빈 페이지에 쓰고 매핑만 바꿔요. 옛 페이지는 무효 표시했다가 나중에 가비지 컬렉션으로 블록을 정리해요. 랜덤 쓰기가 많으면 GC가 바빠져 성능이 떨어지고(write amplification), 수명이 줄어요.

    백엔드에서는 DB가 WAL(로그)을 순차로 먼저 쓰고 데이터 페이지는 나중에 모아서 쓰는 이유가 이 장이에요. 순차 쓰기는 HDD에서도 SSD에서도 빨라요. LSM 트리(RocksDB, Cassandra)는 아예 모든 쓰기를 순차로 만들어요. 클라우드 디스크(EBS 등)는 IOPS와 처리량이 따로 제한돼서, 작은 랜덤 I/O는 IOPS 한도에 먼저 걸려요. iostat -x의 await, %util로 봐요.
    시니어 심화 본문은 iostat -x의 %util을 보라고 했는데, 이 지표는 SSD와 클라우드 디스크에서 포화를 뜻하지 않아요. 그리고 클라우드 디스크에는 보이지 않는 한도가 따로 있어요.

    상황 1: 100%인데 여유로움

    DB 서버의 NVMe 디스크 %util이 늘 95~100%라서 디스크를 바꾸자는 의견이 나왔어요. 그런데 요청당 대기 시간은 0.2ms로 아주 짧았어요.

    1. %util은 "처리 중인 요청이 하나라도 있었던 시간의 비율"이에요. 얼마나 많이 처리했는지가 아니라 "놀지 않은 시간"을 재요.
    2. 요청을 하나씩만 처리하던 옛 HDD에서는 놀지 않는다는 것이 곧 포화였어요.
    3. SSD와 NVMe는 요청 수십~수백 개를 동시에 처리해요. 요청이 늘 하나 이상 있으면 100%가 되지만, 동시에 처리할 여유는 아직 많아요.

    판단 기준: 포화는 대기열 길이(aqu-sz)와 요청당 대기 시간(r_await, w_await)이 함께 늘어나는 것으로 판단해요. 부하가 늘 때 대기 시간이 그대로면 여유가 있는 거예요.

    상황 2: 평소엔 멀쩡한데 배치 시간에만 느림

    클라우드의 주문 DB가 평소에는 빠른데, 매일 새벽 정산 배치가 시작되고 30분쯤 지나면 쿼리가 열 배 느려졌어요. 디스크 지표만 보면 IOPS는 오히려 떨어져 있었어요.

    1. 일부 클라우드 디스크(예: AWS의 gp2)는 버스트 크레딧 방식이에요. 평소에는 기본 IOPS보다 적게 쓰면서 크레딧을 모으고, 몰릴 때 크레딧을 써서 높은 IOPS를 내요.
    2. 배치가 30분 동안 높은 IOPS를 쓰자 크레딧이 바닥났어요. 그 순간 IOPS가 기본값으로 급락해요.
    3. 디스크는 "느려진" 것이 아니라 "한도에 걸린" 거라서, IOPS 그래프는 떨어지고 대기 시간만 치솟아요.
    4. 인스턴스 자체에도 디스크 대역폭 한도가 있어서, 디스크를 크게 잡아도 인스턴스 종류가 작으면 거기서 막혀요.

    해결: 크레딧 잔량을 모니터링하고, 지속적인 I/O가 필요한 DB는 IOPS가 고정된 디스크 종류(예: gp3, 프로비저닝 IOPS)를 써요. 인스턴스 종류의 디스크 대역폭 한도도 함께 확인해요.

    운영에서 알아채는 법

    • 디스크 대시보드에는 %util 대신 r_await, w_await, aqu-sz를 둬요.
    • 클라우드 디스크라면 크레딧 잔량 지표(AWS의 BurstBalance)에 알람을 걸어요. 매일 같은 시각에 바닥나는 패턴이 보이면 디스크 종류를 바꿀 때예요.
    • "IOPS는 떨어졌는데 대기 시간은 오른다"는 모양은 한도에 걸렸다는 강한 신호예요.
    핵심 정리
    • HDD: 탐색+회전 = 랜덤 I/O ms 단위, 순차는 100배 빠름
    • SSD: 덮어쓰기 불가, FTL이 로그 구조로 관리, 랜덤 쓰기는 GC 부담
    • 저장소는 순차 쓰기를 좋아함 → WAL, LSM
    셀프 체크
    1. SSD는 왜 랜덤 쓰기를 싫어하나요?
    2. DB가 WAL을 쓰는 이유를 디스크 특성으로 설명하세요.
    답 보기

    1. 페이지를 덮어쓸 수 없어서 랜덤 쓰기는 흩어진 무효 페이지를 많이 만들고, 블록 단위 지우기 전에 유효 페이지를 옮기는 GC(write amplification)가 늘어 성능과 수명이 떨어져요.

    2. 변경을 데이터 페이지에 바로 쓰면 랜덤 I/O가 돼요. 대신 변경 내용을 로그 파일 끝에 순차로 추가(append)하고 fsync하면 빠르고 안전해요. 데이터 페이지는 나중에 체크포인트 때 모아서 써요.

    39장 파일과 디렉터리

    파일 시스템 인터페이스 — open, read, write, fsync

    파일과 디렉터리

    파일은 바이트 배열이고 저수준 이름인 inode 번호를 가져요. 디렉터리는 "이름 → inode 번호" 목록을 담은 특수한 파일이에요. 경로 /a/b/c는 루트부터 디렉터리를 하나씩 따라가며 찾아요.

    파일 디스크립터

    open()은 fd(작은 정수)를 반환해요. 프로세스마다 fd 테이블이 있고, 각 항목은 시스템 전역 open file table의 엔트리(현재 오프셋, 모드, inode 참조)를 가리켜요. 0/1/2는 stdin/stdout/stderr. fork하면 fd 테이블이 복사되고 open file 엔트리는 공유돼요(오프셋 공유). dup()도 같은 엔트리를 가리키는 새 fd를 만들어요(리다이렉션 원리).

    읽기와 쓰기

    read(fd, buf, n), write(fd, buf, n)은 현재 오프셋에서 동작하고 오프셋을 옮겨요. lseek()으로 오프셋을 바꿔요(랜덤 접근). pread/pwrite는 오프셋을 명시해서 멀티스레드에서 안전해요.

    fsync — 즉시 쓰기

    write()가 반환돼도 데이터는 메모리(페이지 캐시)에만 있어요. OS는 5~30초 뒤에 모아서 디스크에 써요. 그 사이 전원이 나가면 사라져요. fsync(fd)는 그 파일의 dirty 데이터를 디스크에 쓰고 완료될 때까지 기다려요. 새 파일은 디렉터리 엔트리도 영속해야 하므로 디렉터리도 fsync해야 해요.

    그 외

    • rename()은 원자적이에요. 임시 파일에 쓰고 fsync 후 rename하면 "전부 아니면 전무" 갱신이 돼요. 에디터와 DB가 쓰는 패턴.
    • 하드 링크: 같은 inode에 이름 하나 더. inode의 참조 수가 0이 될 때 삭제. rm은 사실 unlink().
    • 심볼릭 링크: 경로를 담은 별도 파일. 대상이 없으면 dangling.
    • 퍼미션: owner/group/other × rwx. chmod.
    • 마운트: 여러 파일 시스템을 하나의 트리에 붙여요.
    백엔드에서는 "로그 파일에 write했는데 서버가 죽으니 마지막 몇 초가 사라졌다"가 fsync 문제예요. MySQL innodb_flush_log_at_trx_commit=1은 커밋마다 fsync(안전, 느림), 2는 1초마다(빠름, 1초 유실 가능)예요. Kafka의 acks와 flush 설정, Redis AOF의 appendfsync도 같은 결정이에요. 그리고 삭제한 파일이 열려 있으면 디스크가 안 비워지는 것(lsof | grep deleted)은 inode 참조 수 때문이에요.
    시니어 심화 본문의 fsync 이야기에는 놀라운 뒷면이 있어요. fsync는 실패할 수 있고, 실패한 뒤에 다시 부르면 성공처럼 보일 수 있어요.

    상황

    정산 서비스가 결과를 로컬 파일에 쓰고 fsync로 디스크에 내린 뒤 "완료"를 기록해요. fsync가 에러를 내면 다시 시도하도록 짜 두었어요. 디스크에 일시적인 오류가 났던 날, 재시도한 fsync는 성공했고 서비스는 정상으로 기록했어요. 며칠 뒤 그 파일의 일부가 비어 있는 것이 발견됐어요.

    깨지는 과정

    1. write는 데이터를 페이지 캐시에 넣고 바로 돌아와요. 이 페이지는 "아직 디스크에 써야 할 것"(더티)으로 표시돼요.
    2. fsync가 그 더티 페이지들을 디스크에 쓰다가 에러를 만났어요. fsync는 에러를 반환해요.
    3. 리눅스에서는 이때 쓰기에 실패한 페이지가 더 이상 "더티"로 남지 않고 정리될 수 있어요. 데이터는 디스크에 없는데, 커널은 쓸 것이 없다고 기억해요.
    4. 애플리케이션이 "다시 해 보자"며 fsync를 또 부르면, 쓸 것이 없으니 성공을 반환해요. 데이터는 사라졌는데 성공으로 기록돼요.

    2018년 PostgreSQL 개발자들이 이 동작을 발견했어요(fsyncgate). 수십 년 동안 "fsync가 실패하면 재시도하면 된다"고 가정해 온 DB들이 영향을 받았어요. PostgreSQL은 그 뒤 fsync가 실패하면 재시도하지 않고 프로세스를 멈춘 다음, 재시작할 때 WAL로 복구하도록 바꿨어요.

    해결책

    • fsync 실패를 재시도로 덮지 않아요. fsync가 실패하면 그 파일의 내용을 믿지 말고, 원본 데이터에서 다시 만들거나 작업 전체를 실패로 처리해요.
    • 원자적 쓰기 패턴을 써요. 파일을 제자리에서 고치지 말고, 임시 파일에 쓰고 fsync하고, rename으로 원래 이름으로 바꾸고, 그 디렉터리도 fsync해요. 디렉터리를 fsync해야 이름 바꾸기 자체가 디스크에 남아요. 중간에 실패해도 옛 파일이나 새 파일 중 하나는 온전히 남아요.
    • 내구성은 가능하면 DB에 맡겨요. 직접 파일에 쓰는 대신 이런 문제를 이미 다루는 DB나 저장소를 쓰는 것이 대개 안전해요.
    • 체크섬을 남겨요. 중요한 파일은 내용의 체크섬을 함께 저장하고, 읽을 때 검증해요. 조용히 깨진 데이터를 늦게라도 찾을 수 있어요.

    운영에서 알아채는 법

    • 커널 로그(dmesg)의 I/O 에러 메시지에 알람을 걸어요. 애플리케이션이 에러를 삼켜도 커널 로그에는 남아요.
    • 애플리케이션의 fsync 실패를 반드시 에러 로그와 지표로 남겨요. "재시도 후 성공"도 성공이 아니라 사고로 다뤄요.
    핵심 정리
    • 파일 = inode, 디렉터리 = 이름→inode 목록, fd → open file → inode
    • write는 캐시, fsync해야 디스크. 디렉터리도 fsync
    • rename은 원자적 → 임시파일+rename 패턴
    셀프 체크
    1. 설정 파일을 안전하게(중간에 죽어도 깨지지 않게) 갱신하는 절차는?
    2. write()가 성공을 반환했는데 데이터가 유실될 수 있는 이유는?
    답 보기

    1. 임시 파일에 전체 내용 write → 임시 파일 fsync → rename(temp, target) → 디렉터리 fsync. rename이 원자적이라 옛 파일 또는 새 파일 둘 중 하나만 보여요.

    2. write는 페이지 캐시에 복사하고 반환해요. 디스크 쓰기는 나중에 비동기로 일어나서 그 전에 전원이 나가면 사라져요. fsync로 강제해야 해요.

    40장 파일 시스템 구현

    아주 단순한 파일 시스템(vsfs)으로 보는 디스크 레이아웃

    디스크 구조

    디스크를 4KB 블록으로 나누고, 대부분은 데이터 블록, 일부는 메타데이터예요.

    ┌───┬───┬───┬────────────┬──────────────────────────────┐
│ S │ i │ d │  inode 테이블 │         데이터 블록            │
└───┴───┴───┴────────────┴──────────────────────────────┘
 S: 슈퍼블록 (FS 정보)   i/d: inode·데이터 비트맵 (빈 블록 추적)

    inode

    파일 하나의 메타데이터: 크기, 퍼미션, 시간, 그리고 데이터 블록 포인터. 포인터가 고정 개수면 큰 파일을 못 담으니 간접 포인터를 써요. 직접 포인터 12개 + 1단 간접(포인터 블록) + 2단 + 3단. 대부분 파일은 작아서 직접 포인터로 끝나고, 큰 파일만 간접 포인터를 타요. ext4는 대신 extent(연속 블록 범위)를 써서 큰 파일을 효율적으로 표현해요.

    읽기 경로 예: /foo/bar 읽기

    1. 루트 inode(번호 고정, 보통 2) 읽기 → 루트 데이터 블록에서 foo 찾기
    2. foo inode 읽기 → 데이터 블록에서 bar 찾기
    3. bar inode 읽기 → 데이터 블록 읽기

    경로가 깊을수록 I/O가 늘어요. 쓰기는 더 비싸요. 새 파일 만들기는 비트맵, inode, 디렉터리 데이터, 디렉터리 inode까지 여러 블록을 갱신해요.

    캐싱과 버퍼링

    이 I/O들은 대부분 페이지 캐시에 맞아요. 리눅스는 남는 메모리를 전부 파일 캐시로 써요(free의 buff/cache). 쓰기는 모아서(write buffering) 한 번에 하고, 같은 블록을 여러 번 쓰면 한 번만 디스크에 가요. 대가는 유실 위험, 그래서 fsync.

    백엔드에서는 DB의 데이터 파일 읽기도 페이지 캐시를 거쳐요. 그래서 MySQL은 자기 버퍼풀과 OS 캐시에 같은 데이터가 이중으로 있는 걸 피하려고 innodb_flush_method=O_DIRECT로 캐시를 우회해요. 반대로 Kafka는 자체 캐시 없이 페이지 캐시에 전적으로 의존해요. 그래서 Kafka 브로커의 JVM 힙은 작게 잡고 OS 메모리를 남겨둬요. "메모리를 다 쓴 것 같은데 실제로는 캐시"인 상황을 구분하려면 free -m의 available을 봐야 해요.
    시니어 심화 본문은 MySQL이 O_DIRECT로 페이지 캐시를 피하고 Kafka는 페이지 캐시에 기댄다고 했는데, 페이지 캐시에 기대는 쪽에는 내가 제어할 수 없는 이웃이 생겨요.

    상황

    Kafka 컨슈머의 지연이 평소 수 ms인데, 매일 새벽 2시에 몇 분 동안 수백 ms로 튀었어요. 그 시각에 Kafka 브로커 서버에서 로그 파일 백업 스크립트가 돌고 있었어요.

    깨지는 과정

    1. Kafka는 메시지를 자기 메모리에 캐시하지 않고 운영체제의 페이지 캐시에 맡겨요. 최근 메시지는 페이지 캐시에 있어서, 컨슈머가 읽을 때 디스크가 아니라 메모리에서 나가요.
    2. 페이지 캐시는 같은 서버의 모든 프로세스가 함께 써요. 백업 스크립트가 수백 GB의 오래된 세그먼트 파일을 한 번 쭉 읽으면, 그 파일들이 페이지 캐시를 채워요.
    3. 캐시가 가득 차면 커널은 오래 안 쓴 페이지부터 내보내는데, 그중에 Kafka가 곧 읽을 최신 세그먼트도 있어요.
    4. 컨슈머의 읽기가 메모리 대신 디스크로 가면서 지연이 튀어요. 백업은 다시 읽지 않을 데이터로 캐시를 채운 셈이에요.

    컨테이너에서는 한 겹이 더 있어요. cgroup v2는 페이지 캐시도 그 컨테이너의 메모리 사용량으로 세요. 큰 파일을 읽는 컨테이너는 페이지 캐시 때문에 메모리 한도에 다가가고, 그 컨테이너 안의 다른 캐시가 밀려나요.

    해결책

    • 한 번만 읽는 대용량 작업은 캐시를 오염시키지 않게 읽어요. O_DIRECT로 읽거나, 읽은 뒤 posix_fadvise(POSIX_FADV_DONTNEED)로 "이 페이지는 다시 안 쓴다"고 알려 줘요. 이런 옵션을 지원하는 백업 도구도 있어요.
    • 무거운 I/O 이웃과 같은 서버에 두지 않아요. 페이지 캐시에 기대는 서비스(Kafka, Elasticsearch)는 백업, 로그 압축, 대량 복사 같은 작업과 서버를 나눠요.
    • 백업은 다른 경로로 해요. 브로커 서버에서 파일을 직접 읽는 대신, 복제본이나 별도의 저장소 계층에서 백업해요.
    • I/O 우선순위를 낮춰요. 꼭 같은 서버에서 돌려야 한다면 ionice와 nice로 우선순위를 낮추고 속도를 제한해요. 캐시 오염 자체는 막지 못하지만 디스크 경쟁은 줄어요.

    운영에서 알아채는 법

    • Kafka 브로커의 디스크 읽기량을 봐요. 컨슈머가 최신 메시지만 읽는다면 디스크 읽기는 거의 0이어야 해요. 특정 시각에 읽기가 튀면 캐시에서 밀려난 거예요.
    • 그 시각에 서버의 다른 프로세스가 무엇을 읽었는지 iotop이나 cgroup별 I/O 지표로 찾아요.
    핵심 정리
    • 슈퍼블록 + 비트맵 + inode 테이블 + 데이터 블록
    • inode = 메타데이터 + 블록 포인터(간접 포인터 또는 extent)
    • 페이지 캐시가 I/O를 흡수, 쓰기 버퍼링은 성능 vs 유실 트레이드오프
    셀프 체크
    1. Kafka는 왜 JVM 힙을 작게 잡으라고 할까요?
    답 보기

    Kafka는 메시지를 자체 메모리에 캐시하지 않고 OS 페이지 캐시에 맡겨요. 힙을 크게 잡으면 페이지 캐시 공간이 줄어 디스크 읽기가 늘어요. 또 큰 힙은 GC 일시정지가 길어요. 보통 힙 4~6GB에 나머지는 OS에 남겨요.

    41~42장 지역성(FFS)과 크래시 일관성(저널링)

    파일 시스템이 디스크를 똑똑하게 쓰는 법, 그리고 중간에 죽어도 깨지지 않는 법

    FFS: 디스크를 의식하는 파일 시스템

    초기 UNIX 파일 시스템은 inode와 데이터가 멀리 떨어져 있고 파일 블록이 흩어져서 성능이 2%까지 떨어졌어요. FFS는 디스크를 실린더 그룹(지금은 블록 그룹)으로 나누고, 같은 디렉터리의 파일과 그 inode를 같은 그룹에 두고, 큰 파일은 여러 그룹에 분산해요. 결과: 관련 데이터가 가까이 있어 탐색이 줄어요. ext4가 이 후손이에요.

    크래시 일관성 문제

    파일에 블록 하나를 추가하려면 (1) 데이터 비트맵, (2) inode, (3) 데이터 블록 세 곳을 써야 해요. 디스크는 한 번에 한 블록만 원자적으로 쓸 수 있으니, 중간에 전원이 나가면 불일치가 생겨요.

    • 데이터만 쓰임: 데이터는 있지만 가리키는 inode가 없어 그냥 사라짐 (괜찮음)
    • inode만 쓰임: inode가 쓰레기 데이터를 가리킴, 비트맵과 불일치 (나쁨)
    • 비트맵만 쓰임: 공간 누수
    • inode + 비트맵: 쓰레기 데이터를 읽음
    • inode + 데이터: 비트맵 불일치, 나중에 덮어써질 수 있음

    해결 1: fsck

    부팅 시 전체 디스크를 검사해 불일치를 고쳐요. 느리고(TB 디스크면 몇 시간), "inode가 쓰레기를 가리키는" 경우는 고칠 수 없어요.

    해결 2: 저널링 (Write-Ahead Logging)

    디스크를 갱신하기 전에 "무엇을 쓸 것인지"를 먼저 저널(로그)에 기록해요.

    1. 저널 쓰기: 트랜잭션 시작 블록(TxB) + 갱신할 블록들의 내용을 저널에 씀
    2. 저널 커밋: 트랜잭션 끝 블록(TxE) 씀. 이게 디스크에 도달하면 트랜잭션은 커밋된 것
    3. 체크포인트: 실제 위치에 블록들을 씀
    4. 해제: 저널 공간 재사용

    크래시 후 복구: 저널을 읽어 커밋된 트랜잭션은 재실행(redo), 커밋 안 된 건 버려요. 1단계와 2단계 사이에 쓰기 배리어(fsync)가 있어야 TxE가 먼저 쓰이는 걸 막아요. 저널 쓰기와 커밋을 합치려고 블록 체크섬을 쓰기도 해요.

    데이터 저널링 vs 메타데이터 저널링

    데이터까지 저널에 쓰면(data 모드) 모든 데이터를 두 번 써요. ext4 기본은 ordered 모드: 데이터 블록을 먼저 실제 위치에 쓰고, 그 다음 메타데이터만 저널링해요. 순서를 지키면 "inode가 쓰레기를 가리키는" 일이 없어요.

    백엔드에서는 이 저널링이 DB의 WAL/redo 로그와 완전히 같은 원리예요. InnoDB redo 로그, PostgreSQL WAL, Kafka 로그, Raft 로그 전부 "먼저 순차 로그에 쓰고 커밋, 나중에 실제 자리에 반영"이에요. 이 장을 이해하면 DB 챕터의 트랜잭션 복구, 체크포인트, innodb_log_file_size가 왜 성능에 영향을 주는지가 바로 보여요. 그리고 fsync 없는 저널은 의미가 없으니, 클라우드 디스크에서 fsync 지연이 곧 커밋 지연이에요.
    시니어 심화 본문은 WAL의 원리를 다뤘는데, 운영에서 WAL 기반 저장소가 갑자기 쓰기를 멈추는 가장 흔한 이유는 체크포인트가 로그 생성 속도를 못 따라갈 때예요.

    상황

    주문 DB가 평소에는 쓰기가 빠른데, 대량 상품 가격 변경 배치가 돌 때마다 몇 초씩 모든 쓰기가 멈췄어요. 그동안 주문도 저장되지 않았어요. CPU와 디스크 사용률은 높지 않았어요.

    깨지는 과정

    1. DB는 변경을 먼저 로그(WAL, InnoDB의 리두 로그)에 순서대로 쓰고, 실제 데이터 페이지는 메모리에서만 바꿔 둬요. 데이터 페이지를 디스크의 제자리에 반영하는 일(체크포인트, 플러시)은 나중에 해요.
    2. 로그 공간은 유한해요. 데이터 페이지가 제자리에 반영돼야 그 변경을 담은 앞쪽 로그를 재사용할 수 있어요.
    3. 배치가 짧은 시간에 아주 많은 행을 바꾸자, 로그가 쌓이는 속도가 페이지를 반영하는 속도보다 빨라졌어요.
    4. 로그 공간이 거의 다 차자, DB는 더 쓸 곳을 만들기 위해 반영을 급하게 몰아서 하고, 그동안 새 쓰기를 멈춰요. "평소엔 빠르다가 주기적으로 몇 초씩 쓰기가 멎는" 증상이에요.

    해결책

    • 로그 공간을 넉넉히 잡아요. MySQL 8.0.30부터는 innodb_redo_log_capacity로, PostgreSQL은 max_wal_size로 정해요. 공간이 크면 쓰기가 몰려도 반영을 고르게 할 시간이 생겨요. 대가는 장애 후 복구할 때 다시 적용할 로그가 많아져서 재시작이 오래 걸린다는 거예요.
    • 반영 속도를 디스크 성능에 맞춰요. InnoDB의 innodb_io_capacity와 innodb_io_capacity_max를 실제 디스크의 IOPS에 맞게 올려요. 기본값은 옛 HDD 기준이라 SSD에서는 너무 낮을 수 있어요. PostgreSQL은 checkpoint_completion_target으로 반영을 체크포인트 간격 전체에 고르게 퍼뜨려요.
    • 쓰기를 고르게 퍼뜨려요. 대량 변경 배치는 작은 묶음으로 나누고 묶음 사이에 쉬어요. 몰아서 쓰지 않으면 로그가 차오를 일이 없어요.

    WAL에는 좋은 성질도 하나 있어요. 여러 트랜잭션의 로그를 모아 fsync 한 번으로 내리는 그룹 커밋 덕분에, 동시 커밋이 많을수록 커밋 하나당 비용이 줄어요. 그래서 단일 스레드로 순차 커밋하는 벤치마크는 실제 처리량을 크게 과소평가해요. 용량을 잴 때는 실제와 비슷한 동시성으로 재요.

    운영에서 알아채는 법

    • MySQL에서는 SHOW ENGINE INNODB STATUS의 LOG 부분에서 현재 로그 위치(Log sequence number)와 마지막 체크포인트(Last checkpoint at)의 차이를 봐요. 이 차이가 로그 용량에 가까워지면 곧 멈춰요. 이 값을 지표로 남겨요.
    • PostgreSQL에서는 로그에 "checkpoints are occurring too frequently" 경고가 나오면 max_wal_size가 작다는 뜻이에요.
    • 쓰기 지연 그래프에 주기적인 봉우리가 있고 그 시각이 대량 쓰기 배치와 겹친다면 이 문제를 먼저 의심해요.
    핵심 정리
    • FFS = 관련 데이터를 같은 그룹에 → 탐색 감소
    • 여러 블록 갱신은 원자적이지 않음 → 크래시 시 불일치
    • 저널링: 로그에 먼저 쓰고 커밋 → 실제 반영. 복구는 redo
    • DB WAL과 동일한 원리
    셀프 체크
    1. 저널 쓰기와 커밋 블록 사이에 배리어가 필요한 이유는?
    2. 저널링이 데이터를 두 번 쓰는데도 빠른 이유는?
    답 보기

    1. 디스크는 쓰기 순서를 바꿀 수 있어요. TxE가 먼저 디스크에 도달하고 중간 블록이 안 쓰인 채 크래시하면, 복구 시 "커밋된 트랜잭션"으로 보고 쓰레기를 재실행해요. 배리어로 TxE 전에 모든 로그 블록이 도달했음을 보장해요.

    2. 저널은 순차 쓰기라 빠르고, 체크포인트는 나중에 모아서 배치로 해요. 여러 트랜잭션의 같은 블록 갱신을 한 번으로 합칠 수도 있어요. 랜덤 쓰기를 즉시 하는 것보다 전체 비용이 작아요.

    OSTEP의 마지막 조각 — 다음 챕터(네트워크, 분산 시스템)로 이어지는 다리

    분산 시스템의 핵심 문제: 실패

    머신이 여러 대면 일부는 항상 고장 나 있어요. 분산 시스템의 목표는 일부가 실패해도 전체가 동작하는 거예요. 그 외 성능(네트워크는 느림), 보안도 문제예요.

    통신은 신뢰할 수 없다

    패킷은 유실되고, 손상되고(체크섬으로 감지), 지연돼요. 신뢰성 있는 통신은 ACK + 타임아웃 + 재전송으로 만들어요. 그런데 ACK가 유실되면 송신자는 재전송하고 수신자는 같은 메시지를 두 번 받아요. 그래서 시퀀스 번호로 중복을 감지해요. 이게 TCP예요.

    RPC

    원격 함수를 로컬 함수처럼 호출하게 하는 추상화. 스텁이 인자를 직렬화(marshal)해서 보내고, 서버가 역직렬화해서 실행하고 결과를 돌려줘요. 문제: 어떤 전송 계층 위에 올릴까(TCP는 ACK가 이중이라 UDP + 자체 재시도가 효율적일 수 있음), 큰 인자, 오래 걸리는 호출의 타임아웃, 바이트 순서(endianness).

    NFS와 상태 없음

    Sun NFS는 서버를 stateless로 설계했어요. 서버가 클라이언트의 열린 파일을 기억하지 않고, 모든 요청이 파일 핸들 + 오프셋을 담아서 서버가 죽었다 살아나도 그냥 재시도하면 돼요. 그래서 요청이 멱등(idempotent)해야 해요. "오프셋 100에 쓰기"는 몇 번 해도 같아요. 캐시 일관성은 느슨하게(close-to-open) 해결했어요.

    백엔드에서는 "상태 없는 서버 + 멱등한 요청 + 재시도"가 NFS에서 나온 설계 원칙이고, 지금 REST API 설계와 쿠버네티스의 핵심 전제예요. "요청이 실패했는지 응답만 유실됐는지 알 수 없다"는 문제가 결제 API의 멱등성 키로 이어져요. 분산 시스템 챕터(DDIA)에서 이 문제들을 본격적으로 다뤄요.
    시니어 심화 본문의 "상태 없는 서버 + 멱등한 요청 + 재시도"를 여러 계층에 적용하면 재시도가 곱해지는 문제가 생겨요.

    상황

    게이트웨이, 주문 서비스, 재고 서비스가 각자 "실패하면 3번까지 시도"하도록 설정돼 있어요. 각 팀이 따로 정한 합리적인 설정이었어요. 재고 DB가 10초 동안 느려졌을 때, 재고 DB가 받은 요청 수가 평소의 20배를 넘었고 DB는 10초가 아니라 10분 동안 회복하지 못했어요.

    깨지는 과정

    1. 재고 DB가 느려지자 재고 서비스의 DB 호출이 타임아웃 나요. 재고 서비스는 3번 시도해요.
    2. 재고 서비스가 결국 실패를 돌려주면, 주문 서비스가 재고 서비스 호출을 3번 시도해요. 그 각각에서 재고 서비스는 또 DB를 3번 시도해요.
    3. 게이트웨이도 주문 서비스를 3번 시도해요. 사용자 요청 하나가 재고 DB에는 최대 3 × 3 × 3 = 27번의 요청이 돼요.
    4. 가장 힘든 순간에 부하가 27배가 돼요. DB는 원인이 사라진 뒤에도 쏟아지는 재시도 때문에 회복하지 못해요(분산 챕터 C장 시니어의 준안정 장애).

    타임아웃의 크기 관계도 문제를 키워요. 게이트웨이의 타임아웃이 2초인데 주문 서비스가 재고를 부르는 타임아웃이 3초라면, 게이트웨이는 이미 포기하고 재시도했는데 아래에서는 첫 번째 요청이 계속 일하고 있어요. 아무도 기다리지 않는 일이 쌓여요.

    해결책

    • 재시도는 한 계층에서만 해요. 보통 가장 바깥(클라이언트나 게이트웨이)이나 실패를 가장 잘 아는 가장 안쪽 중 하나를 골라요. 나머지 계층은 실패를 그대로 위로 올려 보내요.
    • 재시도에 예산을 둬요. 전체 요청 중 재시도 비율에 상한(예: 10%)을 두면, 장애 때도 부하 증폭이 1.1배에서 멈춰요. gRPC와 Envoy는 재시도 예산 설정을 지원해요.
    • 타임아웃은 바깥이 가장 길게, 안쪽으로 갈수록 짧게 둬요. 호출하는 쪽의 타임아웃이 호출받는 쪽의 처리 시간보다 길어야 해요. 더 좋은 방법은 요청의 남은 시간(deadline)을 아래로 전달해서, 남은 시간이 없으면 아래 계층이 일을 시작하지 않게 하는 거예요(30장 시니어).
    • 재시도할 실패만 재시도해요. 타임아웃, 연결 실패, 503은 재시도할 만하지만, 400이나 비즈니스 오류는 몇 번을 해도 같아요. "과부하라서 거절함"이라는 응답(429, 503)에는 재시도 대신 기다리라는 신호(Retry-After)를 따라요.
    • 지수 백오프와 지터를 써요. 재시도 간격을 시도마다 늘리고 무작위 지연을 섞어서, 모든 클라이언트가 같은 순간에 몰리지 않게 해요.

    운영에서 알아채는 법

    • 서비스별로 "받은 요청 중 재시도인 것의 비율"을 지표로 남겨요. 요청에 재시도 횟수 헤더를 붙이면 아래 계층에서도 셀 수 있어요.
    • 하위 시스템이 받은 요청 수를 사용자 요청 수로 나눈 증폭 비율을 봐요. 평소 1 근처인 값이 장애 때 몇 배로 뛰면 재시도가 곱해지고 있는 거예요.
    • 서비스들의 재시도와 타임아웃 설정을 한 표로 모아 두고, 새 서비스를 붙일 때 검토해요. 곱셈은 표로 봐야 보여요.
    핵심 정리
    • 분산 = 부분 실패가 일상, 통신은 신뢰 불가
    • 신뢰성 = ACK + 타임아웃 + 재전송 + 시퀀스 번호
    • stateless 서버 + 멱등 요청 → 재시도가 안전
    셀프 체크
    1. 요청을 보냈는데 응답이 없을 때, 서버가 처리했는지 알 수 있나요? 그래서 어떻게 설계해야 하나요?
    답 보기

    알 수 없어요. 요청이 유실됐을 수도, 서버가 처리하고 응답이 유실됐을 수도 있어요. 그래서 재시도해도 안전하도록 요청을 멱등하게 만들어야 해요. 자연스럽게 멱등하지 않은 작업(결제 생성)은 클라이언트가 멱등성 키를 붙이고 서버가 중복을 걸러요.

    실습 과제

    • 2부 스레드 2개로 공유 카운터를 100만 번씩 증가시켜 race condition을 재현하고, 락 / CAS / LongAdder로 각각 고쳐 성능 비교하기
    • 2부 락 두 개를 반대 순서로 잡는 데드락을 만들고 jstack(또는 gdb)으로 확인한 뒤 락 순서 고정으로 해결하기
    • 2부 strace -f -e trace=epoll_wait,read,write로 Node.js나 Nginx가 이벤트 루프를 도는 걸 관찰하기
    • 3부 파일에 write만 한 것과 write + fsync한 것의 처리량 차이를 측정하기 (1만 번 작은 쓰기)
