    운영체제

    기준 교재: OSTEP (Operating Systems: Three Easy Pieces) · 4~6주

    OSTEP은 운영체제를 가상화 · 병행성 · 영속성 세 조각으로 나눠요. OS는 CPU와 메모리를 "각 프로세스가 혼자 쓰는 것처럼" 보이게 만들고(가상화), 여러 흐름이 동시에 돌아도 안전하게 하고(병행성), 전원이 꺼져도 데이터가 남게 해요(영속성). 이 페이지는 그 장 순서를 그대로 따라가요.

    백엔드 개발자에게 특히 중요한 장은 6장(제한적 직접 실행), 19장(TLB), 21~22장(스왑), 2부 전체(병행성), 33장(이벤트 기반), 42장(저널링)이에요. 시간이 없으면 이 장들을 먼저 읽으세요.

    2장 운영체제 개요

    OS가 하는 일 세 가지와, 이 책이 왜 그 순서로 가는지

    OS는 자원 관리자

    프로그램이 실행된다는 건 CPU가 메모리에서 명령어를 가져와(fetch) 해석하고(decode) 실행하는(execute) 일을 반복하는 거예요. 그런데 프로그램은 수십 개가 동시에 돌고, CPU와 메모리는 한정돼 있어요. OS는 이 물리 자원을 나눠 주고, 서로 침범하지 못하게 보호하는 자원 관리자예요.

    세 가지 핵심 개념

    • 가상화(Virtualization): 물리 CPU 1개를 "프로세스마다 CPU가 하나씩 있는 것처럼", 물리 메모리를 "프로세스마다 독립된 큰 메모리가 있는 것처럼" 보이게 해요. 1부 내용이에요.
    • 병행성(Concurrency): 여러 실행 흐름이 같은 메모리를 건드릴 때 생기는 문제를 다뤄요. 락, 조건 변수, 세마포어. 2부 내용이에요.
    • 영속성(Persistence): 디스크와 파일 시스템. 전원이 나가도 데이터를 안전하게 남기는 방법. 3부 내용이에요.

    설계 목표

    추상화(복잡한 하드웨어를 단순한 인터페이스로), 성능(OS 자체 오버헤드 최소화), 보호와 격리, 신뢰성, 에너지 효율. 이 중 어느 것을 우선할지가 OS마다 달라요.

    백엔드에서는 우리가 쓰는 스레드풀, 커넥션 풀, 비동기 프레임워크, JVM GC는 전부 이 세 조각 위에 얹혀 있어요. "왜 스레드가 많으면 느려지나", "왜 디스크 쓰기는 순차로 해야 하나" 같은 질문의 답이 이 책에 있어요.
    시니어 심화 OS가 숨겨 준 것(스케줄링, 페이지 캐시, 쓰기 버퍼링)은 평소에는 몰라도 되지만, 꼬리 지연과 장애의 원인은 대개 그 숨겨진 층에 있어요. 그래서 자원마다 사용률·포화도·에러(USE 방법)를 따로 보는 습관이 필요해요. 사용률이 낮아도 포화(대기열)가 있으면 느려요. 컨테이너에서는 cgroup이 한도를 따로 걸기 때문에, 호스트 지표가 여유로워도 컨테이너는 CPU 스로틀링이나 OOM 상태일 수 있어요. 호스트 지표와 컨테이너 지표를 구분해서 보세요.
    핵심 정리
    • OS = 자원 관리자 + 하드웨어 추상화
    • 가상화(CPU·메모리) → 병행성 → 영속성 순서로 공부

    답 보기

    CPU 가상화: 물리 CPU를 시분할해서 각 프로세스가 CPU를 독점하는 것처럼 보이게 하는 것. 메모리 가상화: 각 프로세스에 독립된 가상 주소 공간을 주고, OS와 하드웨어가 물리 메모리로 변환해 주는 것.

    1부 가상화 — CPU

    4장 프로세스

    실행 중인 프로그램을 OS는 어떻게 표현하는가

    프로세스란

    프로세스는 실행 중인 프로그램이에요. 디스크의 프로그램 파일은 그냥 바이트 덩어리이고, OS가 그것을 메모리에 올리고 실행 상태를 만들어 줘야 프로세스가 돼요. 프로세스의 상태를 이루는 것들(machine state)은 다음과 같아요.

    • 메모리(주소 공간): 코드, 데이터, 힙, 스택
    • 레지스터: 특히 PC(다음 실행할 명령 주소), SP(스택 포인터)
    • 열린 파일 목록, 현재 디렉터리 같은 I/O 정보

    프로세스 생성 과정

    1. 프로그램 코드와 정적 데이터를 디스크에서 메모리로 로드 (현대 OS는 필요한 페이지만 lazy하게 로드)
    2. 스택 할당, main()의 argc/argv 설정
    3. 힙 할당
    4. 표준 입출력 fd(0, 1, 2) 등 초기화
    5. main()으로 점프

    프로세스 상태

    상태의미
    RunningCPU에서 실행 중
    Ready실행할 수 있지만 CPU를 기다리는 중
    BlockedI/O 등 다른 사건을 기다리느라 실행할 수 없음

    I/O를 요청하면 Running → Blocked가 되고, 그 사이 OS는 다른 Ready 프로세스를 실행해요. I/O가 끝나면 Blocked → Ready. 이 전환이 CPU를 놀리지 않는 핵심이에요.

    자료구조

    OS는 프로세스마다 PCB(Process Control Block)를 두고 레지스터 값, 상태, PID, 메모리 정보, 열린 파일을 저장해요. 컨텍스트 스위칭 때 여기에 레지스터를 저장했다가 복원해요.

    백엔드에서는 DB 쿼리를 기다리는 요청 스레드는 Blocked 상태예요. 스레드가 100개인데 CPU 사용률이 10%라면, 대부분 Blocked라는 뜻이고 스레드 수를 늘리거나 비동기 I/O로 바꿀 여지가 있다는 신호예요. ps, top의 STAT 열(R, S, D)이 이 상태예요.
    시니어 심화 리눅스의 로드 애버리지는 실행 대기(R)뿐 아니라 인터럽트 불가 대기(D, 주로 디스크 I/O)도 세요. 그래서 "로드는 높은데 CPU는 한가한" 서버는 CPU가 아니라 I/O 병목이에요.
    • vmstat 1의 r(실행 대기)과 b(블록) 열로 둘을 나눠 봐요.
    • /proc/pressure/cpu, io, memory(PSI)는 "작업이 자원을 기다리느라 멈춰 있던 시간 비율"을 직접 알려줘요. 사용률보다 체감 지연에 가까운 지표예요.
    • pidstat -w의 자발적 전환(cswch/s, I/O·락 대기)과 비자발적 전환(nvcswch/s, CPU 경쟁)을 구분하면 스레드가 왜 CPU를 놓는지 보여요.
    핵심 정리
    • 프로세스 = 주소 공간 + 레지스터 + I/O 상태
    • Running / Ready / Blocked 세 상태, I/O 대기 중엔 다른 프로세스가 CPU 사용
    셀프 체크
    1. Ready와 Blocked의 차이는 무엇인가요?
    2. 프로세스가 I/O를 요청하면 OS는 무엇을 하나요?
    답 보기

    1. Ready는 CPU만 주면 바로 실행 가능한 상태, Blocked는 I/O 완료 같은 외부 사건이 있어야 실행 가능한 상태예요.

    2. 그 프로세스를 Blocked로 바꾸고, Ready 큐에서 다른 프로세스를 골라 CPU를 줘요. I/O가 끝나면 인터럽트로 알림을 받아 Ready로 되돌려요.

    5장 프로세스 API

    fork, exec, wait — UNIX가 프로세스를 다루는 방식

    fork()

    호출한 프로세스를 거의 똑같이 복제해요. 자식은 부모의 주소 공간 복사본을 갖고, fork() 다음 줄부터 실행돼요. 부모에겐 자식 PID가, 자식에겐 0이 반환돼서 둘을 구분해요. 실제로는 전체를 복사하지 않고 copy-on-write로 페이지를 공유하다가 쓰기가 일어날 때만 복사해요.

    exec()

    현재 프로세스의 코드와 데이터를 다른 프로그램으로 덮어써요. 새 프로세스를 만들지 않아요. 그래서 쉘은 fork() → 자식에서 exec() 순서로 명령을 실행해요.

    wait()

    자식이 끝날 때까지 기다리고 종료 상태를 거둬요. 부모가 wait()를 하지 않으면 자식은 종료 후에도 PCB가 남는 좀비 프로세스가 돼요. 부모가 먼저 죽으면 자식은 init(PID 1)에 입양돼요.

    왜 fork와 exec을 나눴나

    fork와 exec 사이에 자식이 자기 환경을 바꿀 수 있어서예요. 쉘의 리다이렉션(ls > out.txt)은 fork 후 자식이 표준 출력 fd를 파일로 바꾼 뒤 exec하는 거예요. 파이프도 같은 원리예요.

    백엔드에서는 컨테이너 안에서 애플리케이션이 PID 1이 되면 입양된 좀비를 거두는 역할도 떠안아요. 그래서 tini 같은 init 프로세스를 두거나 docker run --init을 써요. Node.js의 child_process, Python의 subprocess, JVM의 ProcessBuilder가 전부 fork+exec이에요. 큰 JVM에서 자식 프로세스를 자주 띄우면 fork 비용(페이지 테이블 복사)이 눈에 띄게 커져요.
    시니어 심화 fork에는 본문에 없는 함정이 세 가지 더 있어요.
    • copy-on-write 메모리: fork 직후에는 페이지를 공유하지만, 부모가 쓰기를 계속하면 페이지가 복사돼요. Redis가 스냅샷을 뜨는 동안 쓰기가 많으면 메모리 사용량이 크게 늘어나는 이유예요. 메모리 한도를 데이터 크기에 딱 맞추면 스냅샷 중에 OOM이 나요.
    • 멀티스레드 + fork: 자식에는 fork를 호출한 스레드만 복제돼요. 다른 스레드가 잡고 있던 락은 자식에서 영원히 잠긴 채 남아요. fork 뒤에는 곧바로 exec하거나 posix_spawn을 써야 해요.
    • PID 1과 시그널: PID 1은 핸들러를 등록하지 않은 시그널을 무시해요. 앱이 SIGTERM 핸들러 없이 PID 1로 뜨면 종료 요청을 무시하다가 유예 시간이 지난 뒤 SIGKILL로 죽어요. 배포가 느리고 진행 중 요청이 끊기는 원인이에요.
    핵심 정리
    • fork = 복제, exec = 덮어쓰기, wait = 종료 회수
    • 좀비는 wait 안 한 자식, 고아는 init이 입양

    6장 제한적 직접 실행

    프로세스를 CPU에서 직접 실행하면서도 OS가 통제권을 잃지 않는 방법

    문제

    성능을 위해 프로그램을 CPU에서 직접 실행하고 싶어요. 그런데 그러면 (1) 프로그램이 멋대로 디스크에 접근하거나 다른 프로세스 메모리를 읽는 걸 어떻게 막나, (2) 프로그램이 CPU를 영원히 쓰면 OS가 어떻게 되찾나, 두 문제가 생겨요.

    문제 1: 제한된 연산 — 사용자 모드와 커널 모드

    CPU는 두 모드를 가져요. 사용자 모드에서는 I/O 같은 특권 명령을 실행할 수 없어요. 프로세스가 특권 작업이 필요하면 시스템 콜을 해요.

    1. 프로세스가 trap 명령을 실행하면 CPU가 커널 모드로 바뀌고 미리 등록된 트랩 핸들러로 점프해요.
    2. OS가 요청을 검증하고 처리해요 (예: read() → 디스크 읽기).
    3. return-from-trap으로 사용자 모드로 돌아가 다음 명령을 실행해요.

    트랩 핸들러 주소는 부팅 때 OS가 트랩 테이블에 등록해요. 프로세스는 "몇 번 시스템 콜"만 지정할 수 있고 주소는 지정할 수 없어서 안전해요.

    문제 2: 프로세스 전환 — 타이머 인터럽트

    프로세스가 실행 중이면 OS는 실행 중이 아니에요. OS가 CPU를 되찾는 방법은 두 가지예요.

    • 협조적: 프로세스가 시스템 콜이나 yield()를 호출할 때까지 기다려요. 무한 루프에 빠지면 방법이 없어요.
    • 비협조적: 타이머 인터럽트. 수 밀리초마다 하드웨어가 인터럽트를 걸고, 커널 모드로 들어가 OS가 실행돼요. 이때 스케줄러가 다른 프로세스로 바꿀 수 있어요.

    컨텍스트 스위치

    프로세스 A에서 B로 바꾸려면 (1) A의 레지스터를 A의 커널 스택/PCB에 저장하고, (2) B의 레지스터를 복원하고, (3) B의 커널 스택으로 바꾼 뒤 return-from-trap하면 B가 실행돼요. 수백 나노초~수 마이크로초가 들어요. 숨은 비용은 CPU 캐시, TLB, 분기 예측기가 비워지는 것이고, 이게 직접 비용보다 커요.

    백엔드에서는 모든 I/O(네트워크 읽기, 파일 쓰기, System.nanoTime()도 가끔)는 시스템 콜이고, 시스템 콜마다 모드 전환 비용이 있어요. 작은 쓰기를 수천 번 하는 것보다 버퍼에 모아 한 번 쓰는 게 빠른 이유예요. strace -c로 어떤 시스템 콜을 몇 번 하는지 볼 수 있어요. 또 스레드가 많아 컨텍스트 스위칭이 잦으면 vmstat의 cs 열이 치솟아요.
    시니어 심화 시스템 콜 비용은 고정값이 아니에요. CPU 취약점 완화 패치(KPTI 등) 이후로 모드 전환이 더 비싸졌고, 시스템 콜이 잦은 워크로드일수록 영향이 커요.
    • 시각 조회(clock_gettime)는 보통 vDSO 덕분에 커널에 들어가지 않고 끝나요. 그런데 가상 머신의 클록 소스가 tsc가 아니면 진짜 시스템 콜이 돼서 타임스탬프를 많이 찍는 코드가 느려져요. /sys/devices/system/clocksource/clocksource0/current_clocksource로 확인해요.
    • perf trace나 strace -T로 호출별 소요 시간을 보면 "횟수가 많은 것"과 "한 번이 느린 것"을 구분할 수 있어요. 단 strace는 대상 프로세스를 크게 느리게 하니 운영에서는 짧게만 써요.
    핵심 정리
    • 사용자/커널 모드 + 시스템 콜(trap) = 제한된 연산 해결
    • 타이머 인터럽트 = OS가 CPU를 되찾는 보장
    • 컨텍스트 스위치 비용은 레지스터 저장보다 캐시/TLB 오염이 큼
    셀프 체크
    1. 시스템 콜이 일반 함수 호출보다 비싼 이유는?
    2. 타이머 인터럽트가 없으면 어떤 문제가 생기나요?
    답 보기

    1. 사용자 모드 → 커널 모드 전환(trap), 레지스터 저장, 커널 스택 전환, 보안 검증, 그리고 돌아올 때 역순. 함수 호출은 같은 모드에서 점프만 해요.

    2. 무한 루프에 빠진 프로세스가 CPU를 영원히 점유해도 OS가 개입할 수 없어요. 재부팅밖에 방법이 없어요.

    7~8장 스케줄링

    누구에게 CPU를 줄 것인가 — FIFO에서 MLFQ까지

    평가 기준

    • 반환 시간(turnaround): 도착 → 완료까지. 배치 작업에서 중요.
    • 응답 시간(response): 도착 → 처음 실행까지. 대화형 작업에서 중요.
    • 공정성: 굶는 작업이 없는가.

    기본 정책

    정책동작문제
    FIFO온 순서대로 끝까지긴 작업 뒤의 짧은 작업이 기다림(convoy effect)
    SJF짧은 작업 먼저작업 길이를 미리 알아야 함, 긴 작업 기아
    STCFSJF + 선점 (남은 시간이 더 짧은 작업이 오면 바꿈)반환 시간 최적이지만 응답 시간 나쁨
    RR타임 슬라이스마다 돌아가며응답 시간 최고, 반환 시간 나쁨. 슬라이스가 짧으면 스위칭 비용 증가

    I/O를 하는 작업은 Blocked 동안 CPU를 다른 작업에 주는 중첩(overlap)으로 전체 효율을 높여요.

    MLFQ (Multi-Level Feedback Queue)

    작업 길이를 모르면서도 SJF처럼 동작하고 싶을 때. 우선순위가 다른 큐를 여러 개 두고, 과거 행동으로 우선순위를 조정해요.

    1. 새 작업은 최상위 큐에 넣어요 (짧은 대화형 작업이라 가정).
    2. 한 큐에서 타임 슬라이스를 다 쓰면(= CPU를 오래 쓰는 작업) 한 단계 내려요.
    3. I/O로 CPU를 일찍 놓는 작업은 우선순위를 유지해요.
    4. 주기적으로 모든 작업을 최상위로 올려요 (기아 방지, 행동 변화 반영).
    5. CPU 사용량은 슬라이스가 아니라 누적 할당량으로 세요 (슬라이스 끝나기 직전 I/O하는 꼼수 방지).

    리눅스 CFS

    실제 리눅스는 CFS(Completely Fair Scheduler)를 써요. 각 작업의 가상 실행 시간(vruntime)을 Red-Black 트리로 관리하고 가장 적게 실행된 작업을 다음에 실행해요. nice 값이 vruntime 증가 속도를 바꿔 가중치를 줘요. 6.6부터는 EEVDF로 바뀌었지만 공정 분배라는 원리는 같아요.

    백엔드에서는 쿠버네티스 CPU limit은 CFS 쿼터(cgroup)로 구현돼요. 100ms 주기에 limit만큼만 쓰고 나머지는 스로틀링돼요. 멀티스레드 JVM이 limit 0.5 CPU면 50ms 만에 쿼터를 다 쓰고 50ms 멈추는 일이 반복돼서 p99 지연이 튀어요. container_cpu_cfs_throttled_seconds_total 메트릭으로 확인해요.
    시니어 심화 스로틀링의 흔한 원인은 limit이 작아서가 아니라 런타임이 코어 수를 잘못 아는 것이에요. 런타임이 cgroup 한도 대신 호스트 코어 수를 기준으로 GC 스레드, 이벤트 루프, 공용 풀을 만들면 그 스레드들이 동시에 돌면서 쿼터를 순식간에 태워요. 쓰는 런타임과 버전이 컨테이너 한도를 인식하는지 확인하세요.
    • cgroup의 cpu.stat에 있는 nr_throttled, throttled_time이 원본 수치예요.
    • 지연에 민감한 서비스는 CPU limit을 빼고 request만 두는 선택도 있어요. 대신 노드 단위 경합을 감수해야 해요.
    • 클라우드 VM에서는 top의 st(steal)가 높으면 같은 물리 호스트의 다른 VM에 CPU를 빼앗기는 중이에요. 우리 쪽 튜닝으로는 못 고쳐요.
    핵심 정리
    • 반환 시간 vs 응답 시간은 트레이드오프 (STCF vs RR)
    • MLFQ = 과거 행동으로 우선순위 학습 + 주기적 부스트
    • 리눅스 CFS = vruntime 기반 공정 분배, 컨테이너 limit은 CFS 쿼터
    셀프 체크
    1. RR의 타임 슬라이스를 너무 짧게 하면 왜 나쁜가요?
    2. MLFQ에서 주기적으로 우선순위를 올려주는 이유는?
    답 보기

    1. 컨텍스트 스위칭 비용(캐시 오염 포함)이 실제 작업 시간 대비 커져서 전체 처리량이 떨어져요.

    2. CPU 집약 작업이 하위 큐에서 영원히 굶는 걸 막고, 대화형으로 바뀐 작업이 다시 높은 우선순위를 받을 수 있게 하기 위해서예요.

    1부 가상화 — 메모리

    13~14장 주소 공간과 메모리 API

    프로세스가 보는 메모리의 모습, 그리고 malloc/free

    주소 공간

    각 프로세스는 자기만의 가상 주소 공간을 봐요. 0번지부터 시작하는 큰 연속 메모리처럼 보이지만 실제 물리 메모리 어디에 있는지는 몰라요.

    높은 주소  ┌────────────┐
           │   stack    │  ← 아래로 자람 (지역 변수, 호출 정보)
           │     ↓      │
           │            │
           │     ↑      │
           │    heap    │  ← 위로 자람 (malloc/new)
           ├────────────┤
           │    data    │  전역/정적 변수
           ├────────────┤
낮은 주소  │    code    │  명령어
           └────────────┘

    메모리 가상화의 목표는 투명성(프로세스가 모르게), 효율성(하드웨어 지원), 보호(다른 프로세스 침범 불가)예요.

    메모리 API

    • 스택 메모리: 함수 안 지역 변수. 컴파일러가 자동으로 할당/해제. 함수가 끝나면 사라져요.
    • 힙 메모리: malloc(size)로 할당, free(ptr)로 해제. 프로그래머 책임.

    흔한 오류: 할당 안 하고 쓰기, 크기 부족(버퍼 오버플로), 초기화 안 함, 해제 안 함(메모리 누수), 해제 후 사용(dangling pointer), 두 번 해제.

    malloc은 시스템 콜이 아니라 라이브러리 함수예요. 내부적으로 brk/mmap 시스템 콜로 큰 덩어리를 받아서 잘라 써요.

    백엔드에서는 GC 언어도 힙을 써요. 다만 free를 GC가 대신 해요. "메모리 누수"는 GC 언어에서도 생겨요. 더 이상 안 쓰는 객체를 static Map이나 캐시가 계속 참조하면 GC가 회수 못 해요. 스레드 스택은 스레드마다 따로 있어서(JVM 기본 512KB~1MB 예약) 스레드 1만 개면 스택만 수 GB를 예약해요. 가상 스레드(Java 21)가 스택을 힙에 두는 이유예요.
    시니어 심화 컨테이너에서 JVM이 OOMKilled되는 가장 흔한 이유는 힙이 아니에요. 프로세스 메모리는 힙 + 메타스페이스 + 스레드 스택 + 다이렉트 버퍼 + 코드 캐시 + GC 자체 구조의 합이라, -Xmx를 컨테이너 한도와 같게 잡으면 반드시 넘어요.
    • -XX:NativeMemoryTracking=summary를 켜고 jcmd <pid> VM.native_memory summary로 영역별 사용량을 봐요.
    • 리눅스는 메모리를 오버커밋해요. malloc이 성공해도 물리 메모리는 실제로 접근할 때 잡히고, 그때 부족하면 OOM killer가 프로세스를 죽여요. 흔적은 dmesg에 남아요.
    • 스레드가 많은 네이티브 프로세스는 glibc malloc의 스레드별 아레나 때문에 RSS가 부풀 수 있어요. MALLOC_ARENA_MAX를 줄이거나 jemalloc으로 바꿔서 비교해요.
    핵심 정리
    • 주소 공간 = code / data / heap / stack, 스택과 힙이 마주보며 자람
    • 힙은 명시적 관리(malloc/free) 또는 GC, 누수는 GC 언어에도 있음
    셀프 체크
    1. 스택과 힙 메모리의 수명 차이는?
    2. GC 언어에서 메모리 누수가 생기는 예를 하나 들어보세요.
    답 보기

    1. 스택은 함수 호출 동안만 살고 반환하면 자동 해제. 힙은 명시적으로 해제하거나 GC가 회수할 때까지 살아요.

    2. 요청마다 객체를 static List에 add하고 제거하지 않는 경우, 리스너를 등록하고 해제하지 않는 경우, ThreadLocal을 비우지 않고 스레드풀 스레드가 재사용되는 경우.

    15~17장 주소 변환, 세그멘테이션, 빈 공간 관리

    가상 주소를 물리 주소로 바꾸는 첫 번째 방법들

    주소 변환의 기본 아이디어

    프로그램이 메모리 접근을 할 때마다 하드웨어(MMU)가 가상 주소를 물리 주소로 바꿔요. OS는 변환 규칙을 설정하고, 변환 자체는 하드웨어가 해서 빨라요. 이걸 하드웨어 기반 주소 변환이라고 해요.

    베이스-바운드 (동적 재배치)

    가장 단순한 방법. CPU에 base와 bounds 레지스터를 두고, 물리 주소 = 가상 주소 + base, 그리고 가상 주소 < bounds를 검사해요. 넘으면 예외(segfault). 컨텍스트 스위치 때 OS가 두 레지스터를 바꿔요.

    문제: 주소 공간 전체를 물리 메모리에 연속으로 둬야 해서, 스택과 힙 사이의 빈 공간까지 전부 차지해요(내부 단편화).

    세그멘테이션

    code, heap, stack을 각각 별도 세그먼트로 두고 세그먼트마다 base/bounds를 가져요. 가상 주소의 상위 비트로 세그먼트를 고르고 나머지를 오프셋으로 써요. 빈 공간을 할당하지 않아도 되고, 코드 세그먼트를 여러 프로세스가 공유할 수도 있어요(보호 비트).

    문제: 세그먼트 크기가 제각각이라 물리 메모리에 작은 구멍이 많이 생겨요(외부 단편화).

    빈 공간 관리

    크기가 가변인 조각을 관리하는 문제는 세그먼트 배치와 malloc 구현 둘 다에 나와요.

    • 분할(splitting)과 병합(coalescing): 큰 빈 덩어리를 잘라 주고, 해제 시 인접한 빈 덩어리와 합쳐요.
    • 헤더: 할당한 덩어리 앞에 크기를 기록해서 free(ptr)만으로 크기를 알아요.
    • 전략: best fit(가장 작은 맞는 것, 작은 조각 남음), worst fit, first fit(처음 맞는 것, 빠름), next fit.
    • 분리 리스트(segregated list): 자주 쓰는 크기별로 전용 리스트. 커널 slab 할당자, jemalloc/tcmalloc의 size class가 이 방식이에요.
    • 버디 할당자: 2의 거듭제곱 크기로 쪼개고, 해제 시 "버디"와 병합. 병합이 빨라요.
    백엔드에서는 JVM 힙은 세대별로 나눠 young은 bump pointer로 순차 할당(매우 빠름)하고, old는 compaction으로 단편화를 없애요. Redis는 jemalloc을 써요. 메모리를 많이 썼다 해제해도 RSS가 안 줄어드는 건 할당자가 OS에 바로 반환하지 않고 단편화된 조각을 들고 있기 때문이에요(mem_fragmentation_ratio).
    핵심 정리
    • MMU가 하드웨어로 변환, OS는 규칙 설정
    • 베이스-바운드 → 내부 단편화, 세그멘테이션 → 외부 단편화
    • 가변 크기 관리는 분할/병합 + 분리 리스트가 실무 표준
    셀프 체크
    1. 내부 단편화와 외부 단편화의 차이는?
    답 보기

    내부 단편화: 할당받은 덩어리 안에 안 쓰는 공간이 남는 것(베이스-바운드에서 스택-힙 사이). 외부 단편화: 할당 사이사이에 작은 빈 공간이 흩어져 총합은 충분한데 연속된 큰 공간이 없는 것(세그멘테이션, malloc).

    18장 페이징

    가변 크기 대신 고정 크기 페이지로 나누면 단편화가 사라진다

    기본 개념

    가상 주소 공간을 고정 크기 페이지(보통 4KB)로, 물리 메모리를 같은 크기 페이지 프레임으로 나눠요. 어떤 페이지든 어떤 프레임에나 들어갈 수 있어요. 그래서 외부 단편화가 없고, 빈 공간 관리가 "빈 프레임 목록"으로 단순해져요.

    페이지 테이블

    프로세스마다 "가상 페이지 번호(VPN) → 물리 프레임 번호(PFN)" 매핑을 담은 페이지 테이블이 있어요. 주소 변환은 이렇게 해요.

    가상 주소 (32비트, 4KB 페이지):
  ┌──────────── VPN (20비트) ────────────┬── offset (12비트) ──┐

1. VPN으로 페이지 테이블 조회 → PFN
2. 물리 주소 = PFN ‖ offset   (offset은 그대로)

    페이지 테이블 엔트리(PTE)에는 PFN 외에 valid 비트(매핑 여부), protection 비트(읽기/쓰기/실행), present 비트(메모리에 있는지, 스왑됐는지), dirty 비트(수정됨), accessed 비트(최근 접근) 등이 있어요.

    두 가지 문제

    • 느림: 메모리 접근 1번에 페이지 테이블 조회가 추가돼서 메모리 접근이 2번이 돼요. → 19장 TLB
    • 큼: 32비트 주소 공간, 4KB 페이지면 페이지가 220개 = 엔트리 100만 개 × 4바이트 = 4MB. 프로세스마다. 64비트는 더 심해요. → 20장 다단계 페이지 테이블
    백엔드에서는 mmap으로 파일을 메모리에 매핑하면 페이지 단위로 lazy하게 읽혀요. Kafka, RocksDB, MongoDB(WiredTiger 이전)가 이걸 써요. 또 JVM의 -XX:+UseLargePages나 Redis의 THP(Transparent Huge Pages) 경고는 페이지 크기 얘기예요. 페이지를 2MB로 키우면 TLB 효율은 좋지만 Redis처럼 fork + copy-on-write를 쓰는 프로세스는 쓰기 한 번에 2MB를 복사해서 지연이 튀어요.
    시니어 심화 mmap은 공짜가 아니에요. 페이지 폴트는 그 스레드를 예고 없이 멈추는 블로킹 I/O라서, 이벤트 루프나 지연에 민감한 스레드가 mmap 영역을 건드리면 지연을 예측할 수 없어요.
    • 폴트에는 두 종류가 있어요. 디스크를 읽지 않는 minor fault는 싸고, 디스크를 읽는 major fault는 비싸요. pidstat -r의 majflt/s가 올라가면 메모리가 모자라 페이지가 쫓겨났다 다시 읽히는 중이에요.
    • mmap한 파일의 I/O 에러는 반환값이 아니라 SIGBUS 시그널로 와요. 일반 read처럼 에러 처리를 할 수 없어요.
    • THP는 always 대신 madvise로 두는 것이 흔한 타협이에요. 요청한 프로세스만 huge page를 쓰고, 백그라운드 압축(compaction)으로 인한 지연 스파이크를 줄여요.
    핵심 정리
    • 고정 크기 페이지 → 외부 단편화 없음, 관리 단순
    • 주소 = VPN + offset, 페이지 테이블로 VPN→PFN
    • 문제: 변환 느림(TLB로 해결), 테이블 큼(다단계로 해결)

    19장 TLB — 변환 캐시

    페이징을 빠르게 만드는 하드웨어 캐시

    TLB란

    Translation Lookaside Buffer. MMU 안에 있는 작은 캐시로 최근 VPN→PFN 변환 결과를 저장해요. 주소 변환 때 먼저 TLB를 보고, 있으면(TLB hit) 페이지 테이블을 안 읽어요. 없으면(TLB miss) 페이지 테이블을 읽고 TLB에 채워요.

    보통 64~2048 엔트리 정도로 작아요. 그런데도 hit rate가 99%를 넘는 건 지역성 때문이에요.

    • 공간 지역성: 배열을 순회하면 같은 페이지 안의 주소를 연속으로 접근 → 첫 접근만 miss.
    • 시간 지역성: 최근 쓴 페이지를 곧 다시 씀.

    TLB miss 처리

    x86은 하드웨어가 페이지 테이블을 걸어서(page table walk) 채워요. MIPS 등은 OS가 트랩 핸들러에서 채워요.

    컨텍스트 스위치와 TLB

    TLB 엔트리는 특정 프로세스의 매핑이라 프로세스가 바뀌면 유효하지 않아요. 전환 때 TLB를 전부 비우거나(flush), 엔트리에 ASID(주소 공간 ID)를 붙여 구분해요. 비우면 전환 직후 miss가 폭증해요. 이게 컨텍스트 스위칭의 숨은 비용이에요.

    백엔드에서는 큰 힙을 랜덤하게 접근하는 워크로드(큰 해시맵, 인메모리 캐시)는 TLB miss가 잦아요. 2MB huge page를 쓰면 TLB 하나가 512배 넓은 범위를 커버해서 효과가 커요. 데이터 레이아웃을 순차로(배열, 컬럼 지향) 바꾸는 것도 같은 이유로 빨라져요. 이게 "캐시 친화적 코드"의 핵심이에요.
    시니어 심화 TLB 비용은 측정할 수 있어요. perf stat -e dTLB-load-misses,iTLB-load-misses -p <pid>로 miss 수를 보고 huge page 적용 전후를 비교해요.
    • TLB shootdown: 멀티스레드 프로세스가 munmap이나 mprotect로 매핑을 바꾸면 그 프로세스를 돌리는 모든 코어의 TLB를 무효화해야 해요. 코어가 많을수록 비싸서, 매핑을 자주 만들고 없애는 할당 패턴이 코어 수에 비례해 느려져요.
    • NUMA: 소켓이 여러 개인 큰 서버에서는 다른 노드의 메모리에 접근하는 것이 더 느려요. 큰 버퍼풀을 쓰는 DB는 메모리가 한 노드에 쏠리지 않게 인터리브로 띄우고, numastat으로 분포를 확인해요.
    핵심 정리
    • TLB = 주소 변환 캐시, 지역성 덕분에 hit rate 99%+
    • 컨텍스트 스위치 시 flush 또는 ASID
    • huge page = TLB 커버리지 확대

    20장 작은 페이지 테이블

    다단계 페이지 테이블로 크기 문제를 해결한다

    문제

    선형 페이지 테이블은 주소 공간 전체에 대해 엔트리를 가져요. 대부분의 프로세스는 주소 공간의 아주 일부만 쓰는데도요. 힙과 스택 사이의 거대한 빈 공간에 대한 엔트리는 전부 낭비예요.

    해결책들

    • 큰 페이지: 엔트리 수가 줄지만 내부 단편화가 커져요.
    • 페이징 + 세그멘테이션: 세그먼트마다 페이지 테이블. 세그먼트 크기만큼만 테이블을 둬요. 하지만 세그멘테이션의 단점을 다시 가져와요.
    • 다단계 페이지 테이블: 페이지 테이블 자체를 페이지 단위로 쪼개고, 쓰지 않는 조각은 할당하지 않아요. 최상위 페이지 디렉터리가 "이 조각이 존재하는가"를 가리켜요. 현대 OS의 표준이에요.

    다단계 페이지 테이블의 트레이드오프

    공간은 사용량에 비례해서 작아지지만, TLB miss 때 메모리를 여러 번 읽어야 해요. x86-64는 4단계(최근 5단계 지원)라서 TLB miss 한 번에 메모리를 4번 읽어요. 그래서 TLB가 더 중요해져요.

    역 페이지 테이블

    프로세스별이 아니라 물리 프레임마다 하나씩 "어느 프로세스의 어느 페이지인가"를 기록하는 방법. 테이블이 하나뿐이라 작지만 검색이 필요해서 해시를 써요.

    백엔드에서는 이 장은 직접 다룰 일은 적지만, "fork가 큰 프로세스에서 왜 느린가"의 답이에요. fork는 페이지 테이블 전체를 복사해야 하고, 수십 GB 힙이면 페이지 테이블만 수십 MB예요. Redis가 RDB 저장 때 fork하면 큰 인스턴스에서 수백 ms 멈추는 이유 중 하나예요.
    핵심 정리
    • 다단계 페이지 테이블 = 쓰는 부분만 할당
    • 단계가 깊을수록 TLB miss 비용 증가

    1. 다단계 페이지 테이블이 공간을 절약하는 원리와 그 대가는?
    답 보기

    원리: 페이지 테이블을 페이지 크기로 쪼개고, 가상 주소 공간에서 안 쓰는 영역의 조각은 아예 할당하지 않음. 페이지 디렉터리가 조각의 존재 여부만 가리킴. 대가: TLB miss 시 단계 수만큼 메모리 접근이 늘어남.

    21~22장 물리 메모리 크기의 극복 — 스왑

    메모리보다 큰 주소 공간을 지원하는 방법과 페이지 교체 정책

    스왑 공간과 페이지 폴트

    디스크의 일부를 스왑 공간으로 두고, 물리 메모리에 없는 페이지를 거기 보관해요. PTE의 present 비트가 0이면 메모리에 없다는 뜻이고, 접근하면 페이지 폴트가 발생해요. OS의 페이지 폴트 핸들러가 디스크에서 페이지를 읽어 프레임에 올리고, PTE를 갱신한 뒤 명령을 재실행해요. 그동안 프로세스는 Blocked예요.

    페이지 폴트는 두 가지예요.

    • Minor fault: 디스크 I/O 없이 처리. 처음 접근하는 힙 페이지 할당(zero page), 파일 캐시에 이미 있는 페이지 매핑, copy-on-write.
    • Major fault: 디스크에서 읽어야 함. 수 ms. 이게 많으면 성능이 무너져요.

    메모리가 부족할 때

    빈 프레임이 없으면 누군가를 내보내야(evict) 해요. 실제로는 워터마크를 두고 빈 프레임이 low 아래로 떨어지면 백그라운드 스레드(리눅스 kswapd)가 high까지 미리 내보내요.

    교체 정책

    정책동작비고
    OPT가장 먼 미래에 쓸 페이지 교체이론적 최적, 구현 불가, 비교 기준
    FIFO가장 먼저 들어온 것단순, 캐시 크기를 늘려도 miss가 늘 수 있음(Belady 이상)
    Random무작위최악 상황을 피함
    LRU가장 오래 안 쓴 것지역성 활용, 정확히 구현하면 비쌈
    Clockaccessed 비트로 LRU 근사실제 OS 사용. 원형으로 돌며 비트가 1이면 0으로 내리고 넘어감, 0이면 교체

    dirty 페이지는 디스크에 써야 해서 clean 페이지를 우선 내보내요. 프리페칭(다음 페이지 미리 읽기)과 클러스터링(쓰기 모아서)으로 디스크 I/O를 줄여요.

    스래싱

    프로세스들의 작업 집합(working set)이 메모리보다 크면 페이지를 올리자마자 내보내는 일이 반복돼요. CPU는 놀고 디스크만 바빠요. 해결은 프로세스 수를 줄이거나(admission control), 메모리를 늘리거나, 리눅스처럼 OOM killer로 프로세스를 죽이는 것뿐이에요.

    백엔드에서는 서버에서 스왑은 사실상 장애예요. JVM 힙이 스왑되면 GC가 디스크를 긁어서 수십 초씩 멈춰요. 보통 vm.swappiness=1로 낮추거나 스왑을 끄고, 대신 메모리 limit을 명확히 잡아 OOM으로 빨리 죽고 재시작하게 해요. DB 서버의 innodb_buffer_pool_size를 물리 메모리의 70~80%로 두는 것도 스왑을 피하면서 페이지 캐시 공간을 남기는 타협이에요. 그리고 LRU/Clock은 DB 버퍼풀, Redis maxmemory 정책에서도 똑같이 나와요.
    시니어 심화 스왑을 꺼도 스래싱은 생겨요. 메모리가 모자라면 커널은 파일 기반 페이지(실행 코드, mmap한 파일)를 버리고 필요할 때 디스크에서 다시 읽어요. "스왑은 0인데 디스크 읽기가 폭증하고 서버가 느려지다 죽는" 현상이에요.
    • 컨테이너에서는 cgroup의 memory.events에 있는 oom_kill 카운터와 종료 코드 137이 OOM의 증거예요.
    • 쿠버네티스가 축출을 판단하는 기준은 RSS가 아니라 working set이에요. container_memory_working_set_bytes를 한도와 비교해서 알람을 걸어요.
    • sar -B의 pgscand/s(직접 회수)가 올라가면 메모리를 할당하는 스레드가 직접 회수 작업을 하느라 멈추고 있다는 뜻이에요. OOM이 나기 전에 지연으로 먼저 나타나요.
    핵심 정리
    • present 비트 0 → 페이지 폴트 → 디스크에서 로드
    • 교체는 LRU 근사(Clock), dirty보다 clean 우선
    • 스래싱 = 작업 집합 > 메모리, 서버에서 스왑은 피해야

    2부 병행성

    26~27장 스레드 개요와 API

    왜 스레드가 필요하고, 왜 어려운가

    스레드란

    프로세스 안의 실행 흐름이에요. 같은 프로세스의 스레드는 주소 공간(code, data, heap)을 공유하고, 각자 PC와 레지스터, 스택을 가져요. 그래서 스레드 전환은 페이지 테이블을 바꾸지 않아 프로세스 전환보다 싸요.

    왜 쓰나: (1) 멀티코어 병렬 처리, (2) I/O 대기 중 다른 일 하기(중첩). 프로세스로도 되지만 메모리 공유가 쉬운 스레드가 편해요.

    문제: 공유 데이터

    두 스레드가 전역 counter를 100만 번씩 증가시키면 200만이 나와야 하는데 그보다 작게 나와요. counter++가 사실 세 명령이기 때문이에요.

    mov  counter, %eax    ; 읽기
add  $1, %eax         ; 더하기
mov  %eax, counter    ; 쓰기

    스레드 1이 읽은 직후(50) 타이머 인터럽트로 스레드 2가 실행돼 51을 쓰고, 다시 스레드 1이 돌아와 51을 쓰면 증가가 한 번 사라져요.

    용어

    • 경쟁 조건(race condition): 결과가 실행 타이밍에 따라 달라지는 상황
    • 임계 영역(critical section): 공유 자원에 접근하는 코드 조각
    • 상호 배제(mutual exclusion): 한 번에 한 스레드만 임계 영역에 들어가게 보장
    • 원자적(atomic): 중간에 끊기지 않고 전부 실행되거나 전혀 실행되지 않음

    스레드 API (pthread)

    pthread_create로 생성, pthread_join으로 종료 대기, pthread_mutex_lock/unlock, pthread_cond_wait/signal. Java의 Thread, synchronized, Object.wait/notify와 1:1로 대응돼요. 주의: 스레드에 넘기는 인자를 스택 변수의 주소로 주면 함수가 반환된 뒤 dangling이 돼요.

    백엔드에서는 웹 서버의 요청 하나 = 스레드 하나(톰캣 기본)예요. 요청 처리 중 공유하는 모든 것(static 필드, 싱글톤 빈의 필드, 캐시 Map)은 임계 영역이에요. 스프링 빈은 싱글톤이라 필드에 요청별 상태를 두면 바로 race condition이에요. 이게 "컨트롤러/서비스는 상태가 없어야 한다"는 규칙의 이유예요.
    시니어 심화 락을 제대로 걸어도 남는 문제가 있어요.
    • 거짓 공유(false sharing): 서로 다른 스레드가 서로 다른 변수를 갱신해도 그 변수들이 같은 캐시 라인에 있으면 코어끼리 캐시 라인을 계속 빼앗아요. 코어를 늘렸는데 처리량이 오히려 떨어지는 원인이에요. 자주 갱신하는 스레드별 카운터는 패딩으로 떨어뜨려요.
    • 가시성: 임계 영역 문제가 없어 보여도, 동기화 없이 읽으면 다른 스레드가 쓴 최신 값을 못 볼 수 있어요. 종료 플래그 하나라도 volatile이나 원자 타입으로 두어야 해요.
    • ThreadLocal + 스레드풀: 스레드가 재사용되므로 지우지 않은 값이 다음 요청으로 넘어가요. 이전 요청의 사용자 정보가 보이는 사고가 이렇게 나요. 반드시 finally에서 지우세요.
    핵심 정리
    • 스레드 = 주소 공간 공유 + 스택·레지스터 독립
    • counter++는 3명령, 중간에 끊기면 증가가 사라짐
    • 임계 영역을 상호 배제로 보호해야 함
    셀프 체크

    28장 락

    상호 배제를 하드웨어와 OS로 구현하는 방법

    락의 조건

    좋은 락은 (1) 상호 배제를 보장하고, (2) 공정해서 굶는 스레드가 없고, (3) 성능이 좋아야 해요(경쟁 없을 때 오버헤드, 경쟁 있을 때 처리량).

    잘못된 시도: 인터럽트 끄기, 플래그

    인터럽트를 끄면 싱글 코어에서는 되지만 멀티코어에서는 안 되고, 악의적 프로그램이 영원히 끌 수 있어요. 단순 플래그(while(flag); flag=1;)는 검사와 설정 사이에 끊길 수 있어서 상호 배제가 깨져요.

    하드웨어 원자 명령

    • Test-and-Set: 옛 값을 반환하면서 새 값을 쓰는 걸 원자적으로. 이걸로 스핀 락을 만들어요: while (TestAndSet(&flag, 1) == 1);
    • Compare-and-Swap (CAS): "현재 값이 expected면 new로 바꾸고 성공 반환". Test-and-Set보다 강력해서 lock-free 자료구조의 기초예요.
    • Fetch-and-Add: 값을 원자적으로 1 올리고 옛 값 반환. 이걸로 티켓 락을 만들면 공정해져요(번호표 순서).

    스핀 vs 슬립

    스핀 락은 락을 못 얻으면 CPU를 태우며 돌아요. 싱글 코어에서 락 가진 스레드가 선점되면 타임 슬라이스를 통째로 낭비해요. 대안:

    • yield(): 못 얻으면 CPU 양보. 스레드가 많으면 여전히 낭비.
    • 큐 + 슬립: 못 얻으면 대기 큐에 넣고 잠들기(park), 해제 시 하나 깨우기(unpark). 리눅스 futex가 이 방식. 경쟁 없으면 사용자 공간에서 CAS만으로 끝나고, 경쟁 있을 때만 커널로 들어가요.
    • 2단계 락: 잠깐 스핀하다가(곧 풀릴 것 같으면) 안 되면 슬립. 실제 뮤텍스 대부분이 이 방식이에요.
    백엔드에서는 Java synchronized는 경쟁 없으면 CAS로 얻는 얇은 락, 경쟁이 생기면 OS 뮤텍스로 부풀어요(lock inflation). AtomicInteger.incrementAndGet()은 CAS 루프예요. 경쟁이 심하면 CAS 실패-재시도가 반복되므로 LongAdder처럼 셀을 나눠 경쟁을 분산해요. DB의 SELECT ... FOR UPDATE도 결국 락이고, 스핀 vs 슬립 문제가 innodb_lock_wait_timeout으로 나타나요.
    시니어 심화 락 문제는 "어느 락에서 얼마나 기다리는가"를 재야 풀려요.
    • 스레드 덤프(jcmd <pid> Thread.print)를 몇 초 간격으로 여러 번 떠서, 같은 모니터 주소를 기다리는 BLOCKED 스레드가 반복해서 보이면 그 락이 병목이에요. JFR의 모니터 대기 이벤트는 대기 시간까지 알려줘요.
    • 락을 쥔 채 I/O를 하지 마세요. 임계 영역 안의 DB 호출이나 HTTP 호출 한 번이 그 락을 기다리는 모든 스레드의 지연이 돼요. 락 안에서는 메모리 연산만 하고, I/O 결과는 락 밖에서 준비해서 넣어요.
    • 락을 쥔 스레드가 스케줄러에 의해 밀려나면 대기자 전체가 그 시간만큼 멈춰요(락 컨보이). CPU 스로틀링이 걸린 컨테이너에서 락 경합이 유독 심해 보이는 이유예요.
    핵심 정리
    • 락은 하드웨어 원자 명령(TAS, CAS, FAA) 위에 세워짐
    • 스핀은 짧은 임계 영역·멀티코어에 적합, 슬립은 긴 대기에 적합
    • 실제 뮤텍스 = 잠깐 스핀 → futex로 슬립
    셀프 체크

    답 보기

    29장 락 기반 병행 자료구조

    락을 어디에, 얼마나 잘게 걸 것인가

    병행 카운터

    가장 단순한 건 카운터 하나에 락 하나. 정확하지만 코어가 늘수록 느려져요(락 경쟁). 해결은 근사 카운터: 코어마다 지역 카운터를 두고 각자 락으로 증가시키다가, 임계값 S에 도달하면 전역 카운터로 옮겨요. S가 크면 빠르지만 전역 값이 부정확해요.

    병행 연결 리스트, 큐, 해시 테이블

    • 리스트: 리스트 전체에 락 하나(단순), 또는 노드마다 락(hand-over-hand locking). 후자는 이론상 병행성이 높지만 락 비용이 커서 실제로는 더 느린 경우가 많아요.
    • 큐: head 락과 tail 락을 분리하면 enqueue와 dequeue가 동시에 가능해요(Michael & Scott 큐). 더미 노드로 둘을 분리해요.
    • 해시 테이블: 버킷마다 락. 서로 다른 버킷 접근은 병렬. 확장성이 매우 좋아요.

    교훈

    "더 많은 병행성 = 더 빠름"이 아니에요. 락을 잘게 쪼개면 락 획득/해제 비용이 늘어요. 먼저 단순하게 만들고, 측정해서 병목일 때만 정교하게 가세요. 그리고 주의: 락을 잡은 채로 return하는 경로(에러 처리)에서 락을 놓지 않는 버그가 매우 흔해요.

    백엔드에서는 Java ConcurrentHashMap이 버킷(세그먼트) 단위 락 + CAS예요. Collections.synchronizedMap은 전체 락이라 경쟁 시 훨씬 느려요. LongAdder가 근사 카운터예요. DB에서도 같은 원리예요. 테이블 락보다 행 락이, 행 락보다 낙관적 락이 병행성이 높지만 비용이 달라요. 그리고 "핫 로우"(모든 요청이 같은 행을 UPDATE)는 아무리 행 락이라도 직렬화돼요. 카운터를 샤딩하거나 Redis로 빼는 이유예요.
    핵심 정리
    • 락 하나 = 단순하지만 확장 안 됨, 잘게 쪼개면 경쟁은 줄지만 오버헤드 증가
    • 근사 카운터, 버킷별 락, head/tail 분리 큐가 대표 기법
    • 측정 없이 최적화하지 말 것

    답 보기

    30장 조건 변수

    "어떤 조건이 참이 될 때까지 기다리기"를 올바르게 하는 법

    문제

    부모 스레드가 자식이 끝나길 기다리고 싶어요. while (!done);으로 스핀하면 CPU를 낭비해요. 락만으로는 "조건을 기다린다"를 표현할 수 없어요.

    조건 변수

    조건 변수는 대기 큐예요. wait(cond, mutex)는 뮤텍스를 풀고 잠들었다가, 깨어나면 뮤텍스를 다시 잡고 반환해요. signal(cond)은 대기 중인 스레드 하나를 깨워요.

    // 기다리는 쪽
lock(m);
while (done == 0)      // if가 아니라 while!
    wait(c, m);
unlock(m);

// 알리는 쪽
lock(m);
done = 1;
signal(c);
unlock(m);

    규칙 두 가지

    1. 상태 변수(done)를 꼭 둬요. 조건 변수만 쓰면 signal이 wait보다 먼저 일어났을 때 신호가 사라져 영원히 기다려요.
    2. 항상 while로 재검사해요. 깨어났을 때 조건이 이미 다시 거짓일 수 있어요(다른 스레드가 먼저 가져감). 또 가짜 깨어남(spurious wakeup)도 있어요.

    생산자/소비자 (유한 버퍼)

    생산자는 버퍼가 꽉 차면 기다리고, 소비자는 비면 기다려요. 조건 변수를 하나만 쓰면 소비자가 소비자를 깨우는 일이 생겨 멈출 수 있어요. empty와 fill 두 개를 써서 생산자는 fill을 signal하고 empty를 wait, 소비자는 반대로 해요.

    Covering condition

    누구를 깨워야 할지 모를 때 broadcast로 전부 깨우고 각자 while로 재검사하게 해요. 불필요한 깨움이 생기지만 정확해요.

    백엔드에서는 BlockingQueue(스레드풀의 작업 큐)가 정확히 유한 버퍼 생산자/소비자예요. Java의 Object.wait()는 반드시 synchronized 안에서, while 루프로 써야 하는 이유가 이 장이에요. 커넥션 풀에서 커넥션이 반납될 때까지 기다리는 것도 조건 변수예요(HikariCP는 더 정교한 구조를 쓰지만 원리는 같아요).
    시니어 심화 대기는 반드시 끝이 있어야 해요. 타임아웃 없는 대기는 한 곳의 고갈을 시스템 전체로 퍼뜨려요.
    • 커넥션 풀에서 커넥션을 기다리는 시간에 상한이 없으면, 풀 고갈이 곧 요청 스레드 고갈이 돼요. 대기 타임아웃은 요청 전체 타임아웃보다 훨씬 짧게 잡아요.
    • 큐에서 기다린 시간도 지연이에요. 큐가 길면 꺼냈을 때 이미 클라이언트가 포기한 요청을 처리하게 돼요. 큐 길이보다 큐 대기 시간을 메트릭으로 보고, 오래 기다린 요청은 처리하지 않고 버리는 것이 전체 처리량에는 이득이에요.
    • notifyAll은 대기자를 전부 깨우지만 진행하는 것은 하나뿐이라 나머지는 깨어났다 다시 잠들어요. 대기자가 많으면 조건별로 조건 변수를 나눠서 필요한 쪽만 깨워요.
    핵심 정리
    • 조건 변수 = 조건을 기다리는 큐, wait는 락을 풀고 잠듦
    • 상태 변수 + while 재검사는 필수
    • 생산자/소비자는 조건 변수 2개
    셀프 체크

    답 보기

    31장 세마포어

    락과 조건 변수를 하나로 — Dijkstra의 세마포어

    정의

    정수 값을 가진 객체예요. sem_wait()(P)는 값을 1 줄이고, 음수면 잠들어요. sem_post()(V)는 값을 1 늘리고, 기다리는 스레드가 있으면 하나 깨워요. 초기값이 의미를 결정해요.

    용도

    • 이진 세마포어 = 락: 초기값 1. wait = lock, post = unlock.
    • 순서 맞추기: 초기값 0. 부모가 wait, 자식이 끝나면 post. 조건 변수 대용.
    • 생산자/소비자: empty(초기값 = 버퍼 크기), full(초기값 0), 그리고 버퍼 보호용 mutex. 주의: mutex를 empty/full wait 바깥에 걸면 생산자가 mutex 잡고 empty에서 잠들어 데드락이 나요. mutex는 안쪽에.
    • 카운팅: 초기값 N. 동시에 N개까지 허용. 읽기-쓰기 락, 동시 접속 제한.

    읽기-쓰기 락

    읽기는 여러 스레드가 동시에, 쓰기는 혼자. 첫 번째 읽기가 쓰기 락을 잡고 마지막 읽기가 풀어요. 단순 구현은 읽기가 계속 들어오면 쓰기가 굶어요(writer starvation). 실제로는 복잡도 대비 이득이 작은 경우가 많아요.

    식사하는 철학자

    5명이 원탁에서 양옆 포크 2개가 있어야 먹어요. 모두 왼쪽 포크를 잡으면 데드락. 해결: 한 명만 순서를 바꿔 오른쪽부터 잡게 해요(순환 대기 깨기). 32장 데드락의 예고편이에요.

    백엔드에서는 Java Semaphore(N)으로 외부 API 동시 호출 수를 제한해요(bulkhead). 커넥션 풀의 "최대 N개"가 카운팅 세마포어예요. Resilience4j Bulkhead, Go의 버퍼 채널도 같은 것이에요.
    시니어 심화 세마포어로 동시성을 제한할 때 실무에서 틀리는 지점이에요.
    • 한도는 인스턴스별이에요. 인스턴스마다 10으로 제한해도 인스턴스가 20대면 상대 시스템에는 200이 가요. 오토스케일링으로 인스턴스가 늘면 하위 시스템이 과부하에 빠져요. 전체 합계를 지켜야 하면 하위 시스템 쪽에서 제한하거나 중앙 집계가 필요해요.
    • 획득에 타임아웃이 없으면 격벽이 아니라 대기열일 뿐이에요. 시간 제한을 두고, 못 얻으면 빠르게 실패하거나 대체 응답을 줘요.
    • 예외 경로에서 반납을 빼먹으면 허가가 영구히 줄어들어요. 재시작 전까지 처리량이 조금씩 떨어지는 장애로 나타나요. 획득과 반납은 try/finally로 묶어요.
    • 읽기-쓰기 락은 읽기가 아주 짧으면 일반 락보다 느릴 수 있고, 읽기가 끊이지 않으면 쓰기가 굶어요. 측정하고 고르세요.
    핵심 정리
    • 세마포어 = 카운터 + 대기 큐, 초기값이 역할을 정함
    • 1이면 락, 0이면 순서, N이면 동시 N개 제한
    셀프 체크
    1. 외부 결제 API 동시 호출을 10개로 제한하고 싶어요. 세마포어로 어떻게?
    답 보기

    Semaphore(10)을 만들고, 호출 전 acquire(), 완료 후 finally에서 release(). 11번째 요청은 하나가 끝날 때까지 블록돼요. 무한 대기 대신 tryAcquire(timeout)으로 빠르게 실패시키는 게 보통 더 좋아요.

    32장 병행성 버그

    실제 소프트웨어의 동시성 버그는 어떤 모양인가

    비-데드락 버그 (전체의 97%)

    • 원자성 위반: "검사 후 사용"이 원자적이어야 하는데 중간에 끊김. if (p != null) use(p) 사이에 다른 스레드가 p를 null로. 해결: 락으로 묶기.
    • 순서 위반: A가 B보다 먼저 실행된다고 가정했는데 아닐 수 있음. 스레드 생성 후 초기화가 끝나기 전에 사용. 해결: 조건 변수/세마포어로 순서 강제.

    데드락

    스레드 1이 L1 잡고 L2 기다림, 스레드 2가 L2 잡고 L1 기다림. 큰 코드베이스에서 캡슐화 때문에 생겨요. Vector.addAll(other)가 this와 other를 잠그는데 두 스레드가 반대 방향으로 호출하면 데드락.

    데드락의 4조건

    1. 상호 배제: 자원을 배타적으로 점유
    2. 점유 대기: 자원을 가진 채 다른 자원을 기다림
    3. 비선점: 자원을 강제로 뺏을 수 없음
    4. 순환 대기: 대기 그래프에 사이클

    하나만 깨면 데드락이 없어요.

    예방

    깨는 조건방법
    순환 대기락 순서 고정(전역 순서 또는 주소 순). 가장 실용적.
    점유 대기모든 락을 한 번에 잡기(큰 락으로 감싸기). 병행성 저하.
    비선점trylock 실패 시 가진 것 풀고 재시도. 라이브락 가능 → 랜덤 지연.
    상호 배제락 없이 CAS 기반 자료구조. 어려움.

    그 외: 회피(스케줄러가 락을 함께 쓰는 스레드를 동시에 안 돌림, 비실용적), 탐지와 복구(주기적으로 대기 그래프 사이클 검사, DB가 쓰는 방식).

    백엔드에서는 DB 데드락이 가장 흔해요. 트랜잭션 A가 행 1 → 행 2 순으로, B가 행 2 → 행 1 순으로 UPDATE하면 발생해요. InnoDB는 탐지해서 한쪽을 롤백해요. 애플리케이션은 항상 같은 순서(PK 오름차순)로 접근하고, 데드락 에러를 재시도해요. JVM 데드락은 jstack이 "Found one Java-level deadlock"으로 알려줘요. 그리고 "검사 후 사용" 원자성 위반은 if (!exists) insert로 유니크 제약 위반이 나는 바로 그 패턴이에요.
    시니어 심화 데드락은 락 두 개 사이에서만 생기지 않아요.
    • 스레드풀 데드락: 풀에서 도는 작업이 같은 풀에 하위 작업을 넣고 결과를 기다리면, 부모 작업이 풀을 다 채운 순간 하위 작업이 돌 스레드가 없어서 영원히 멈춰요. 부모와 자식 작업은 다른 풀에 두거나 기다리지 않는 방식으로 조합해요.
    • 분산 데드락: 서비스 A가 B를 동기로 부르고 B가 다시 A를 부르면 양쪽 스레드풀이 서로를 기다리며 고갈돼요. 이 경우에는 탐지기가 없어서 타임아웃이 유일한 방어예요. 호출 그래프에 순환이 없게 설계해요.
    • 재시도는 지터 없이 하면 양쪽이 같은 타이밍에 다시 충돌하는 라이브락이 돼요.
    핵심 정리
    • 대부분은 원자성 위반·순서 위반, 데드락은 소수지만 치명적
    • 4조건 중 하나 깨기, 실무는 락 순서 고정 + 타임아웃 + 재시도
    셀프 체크
    1. 계좌 이체(A→B, B→A 동시)에서 데드락이 나는 이유와 해결책은?
    답 보기

    이체 1은 A 행 잠금 후 B 행, 이체 2는 B 후 A를 잠가 순환 대기. 해결: 두 계좌 ID를 정렬해서 항상 작은 ID부터 잠가요. 그러면 둘 다 A → B 순서라 한쪽이 기다렸다가 진행해요.

    33장 이벤트 기반 병행성

    스레드 없이 동시성을 다루는 방법 — Node.js와 Nginx의 원리

    기본 아이디어

    스레드 대신 이벤트 루프 하나가 "이벤트가 오면 처리"를 반복해요. 루프는 단일 스레드라서 락이 필요 없고, 스케줄링을 애플리케이션이 직접 통제해요.

    while (1) {
    events = getEvents();      // 준비된 것 기다리기
    for (e in events)
        processEvent(e);       // 핸들러 실행
}

    이벤트 받기: select / poll / epoll

    select()는 fd 집합을 주면 읽기/쓰기 가능한 것을 알려줘요. 호출마다 집합 전체를 커널에 복사하고 전부 검사해서 O(n)이에요. 리눅스 epoll은 관심 fd를 커널에 한 번 등록하고, 준비된 것만 받아요. 커넥션이 수만 개라도 비용이 준비된 수에만 비례해요.

    블로킹 호출 문제

    핸들러 안에서 블로킹 시스템 콜(디스크 읽기, 동기 DB 호출)을 하면 루프 전체가 멈춰요. 다른 모든 이벤트가 기다려요. 해결은 비동기 I/O: 요청만 보내고 바로 반환, 완료되면 이벤트로 받기. 리눅스 AIO, io_uring, 또는 블로킹 작업을 별도 스레드풀에 보내기(Node.js libuv가 파일 I/O에 이렇게 해요).

    상태 관리

    스레드는 스택에 상태가 자연스럽게 남지만, 이벤트 기반은 요청을 보낼 때와 결과를 받을 때가 다른 핸들러라서 상태를 수동으로 넘겨야 해요(continuation). 콜백 지옥의 원인이고, async/await가 이걸 문법으로 숨겨 줘요.

    남는 문제

    멀티코어를 쓰려면 루프를 여러 개 돌려야 하고 그러면 다시 동기화 문제가 생겨요. 페이징(페이지 폴트)은 암묵적 블로킹이라 피할 수 없어요. 라이브러리가 내부에서 블로킹하면 알기 어려워요.

    백엔드에서는 Node.js, Netty(Spring WebFlux), Nginx, Redis가 전부 이 모델이에요. 그래서 "이벤트 루프를 막지 마라"가 철칙이에요. WebFlux에서 JDBC(블로킹)를 쓰면 루프가 멈춰요. R2DBC나 별도 스케줄러(subscribeOn(boundedElastic))를 쓰는 이유예요. Redis가 단일 스레드인데 빠른 이유도 이 모델 + 모든 데이터가 메모리라 블로킹이 없어서예요. KEYS *처럼 O(n) 명령이 루프를 막으면 전체가 멈춰요.
    시니어 심화 이벤트 루프에는 스레드풀처럼 자연스러운 상한이 없어요. 스레드 모델은 스레드가 다 차면 더 못 받지만, 이벤트 루프는 요청을 계속 받아들여 진행 중인 작업과 버퍼가 메모리에 쌓여요. 동시에 처리 중인 요청 수를 명시적으로 제한해야 해요.
    • 블로킹 I/O뿐 아니라 CPU를 오래 쓰는 작업(큰 JSON 직렬화, 암호화, 나쁜 정규식)도 루프를 막아요. 결과는 같아요.
    • 루프가 막히는지는 "루프 지연"으로 재요. 타이머가 예정보다 얼마나 늦게 실행됐는지를 메트릭으로 내보내면 돼요. Reactor에는 블로킹 호출을 테스트에서 잡아 주는 도구(BlockHound)가 있어요.
    • 가상 스레드와 고루틴은 같은 epoll 기반 다중화를 런타임 안에 숨기고 코드는 동기식으로 쓰게 해 줘요. 콜백 지옥은 사라지지만 동시성 상한이 없다는 문제는 그대로 남아요.
    핵심 정리
    • 이벤트 루프 = 단일 스레드 + epoll, 락 불필요
    • 블로킹 호출 하나가 전체를 멈춤 → 비동기 I/O 또는 별도 스레드풀
    • 상태를 수동으로 전달해야 함 → async/await

    1. 스레드 기반과 이벤트 기반 서버의 장단점을 각각 두 가지씩 말해보세요.
    2. Redis에서 KEYS *가 위험한 이유는?
    답 보기

    1. 스레드: 코드가 순차적이라 쉽고 블로킹 호출이 자연스러움 / 스레드당 메모리와 컨텍스트 스위칭 비용, 락 필요. 이벤트: 커넥션당 비용이 매우 작고 락 불필요 / 블로킹 하나가 전체를 멈추고, 상태를 수동 전달해야 해 코드가 복잡.

    3부 영속성

    36장 I/O 장치

    CPU가 장치와 대화하는 방법 — 폴링, 인터럽트, DMA

    시스템 구조

    CPU와 메모리는 빠른 메모리 버스로, 그래픽은 PCIe로, 디스크와 네트워크는 더 느린 I/O 버스로 연결돼요. 빠른 장치일수록 CPU 가까이 있어요.

    장치 인터페이스

    장치는 상태(status), 명령(command), 데이터(data) 레지스터를 노출해요. OS는 상태 레지스터를 읽어 바쁜지 확인하고, 데이터와 명령을 써서 작업을 시켜요.

    폴링 vs 인터럽트

    • 폴링: 상태 레지스터를 반복해서 읽으며 끝났는지 확인. 단순하지만 CPU 낭비.
    • 인터럽트: 요청 보내고 다른 프로세스 실행. 장치가 끝나면 인터럽트를 걸고, 핸들러가 깨워요. CPU와 I/O의 중첩이 가능해요.

    인터럽트가 항상 좋은 건 아니에요. 장치가 아주 빠르면(첫 폴링에 끝나는 수준) 인터럽트 처리와 컨텍스트 스위치가 더 비싸요. 네트워크 패킷이 폭주하면 인터럽트 처리만 하다 라이브락에 빠져요. 그래서 하이브리드(잠깐 폴링 후 인터럽트), 병합(여러 인터럽트를 모아 한 번)을 써요.

    DMA

    큰 데이터를 장치로 옮길 때 CPU가 한 워드씩 복사하면 낭비예요. DMA 엔진에 "이 메모리를 이 장치로"라고 시키면 CPU 없이 복사하고 끝나면 인터럽트를 걸어요.

    장치 드라이버

    장치마다 다른 인터페이스를 OS가 추상화하려고 드라이버 계층을 둬요. 리눅스 커널 코드의 70%가 드라이버예요.

    백엔드에서는 리눅스 NAPI가 네트워크 드라이버의 하이브리드 폴링이에요. 고성능 서버에서 패킷 폭주 시 softirq가 CPU를 다 먹는 걸 top의 si 열로 봐요. sendfile, zero-copy는 "커널 버퍼 → 사용자 버퍼 → 소켓 버퍼" 복사를 DMA로 줄이는 거예요. Kafka가 디스크에서 네트워크로 빠른 이유예요.
    핵심 정리
    • 폴링은 빠른 장치, 인터럽트는 느린 장치, 실제는 하이브리드
    • DMA = CPU 없이 메모리↔장치 복사
    셀프 체크
    1. 인터럽트 방식이 오히려 느린 경우는?
    답 보기

    장치가 매우 빨라 폴링 한두 번이면 끝날 때(인터럽트 + 컨텍스트 스위치 비용이 더 큼), 그리고 인터럽트가 폭주해 처리만 하다가 실제 일을 못 하는 라이브락 상황.

    37장 & 44장 하드 디스크와 SSD

    저장 장치의 물리 특성이 DB 설계를 결정한다

    하드 디스크

    회전하는 플래터 위를 헤드가 움직여 트랙과 섹터(512B 또는 4KB)를 읽어요. I/O 시간은 세 요소의 합이에요.

    • 탐색(seek): 헤드를 트랙으로 이동. 수 ms.
    • 회전 지연: 섹터가 헤드 아래 올 때까지. 7200rpm이면 평균 약 4ms.
    • 전송: 실제 읽기. 빠름.

    그래서 랜덤 I/O는 수 ms, 순차 I/O는 100MB/s 이상이에요. 차이가 100배 이상. 디스크 스케줄러(SSTF, SCAN/엘리베이터)는 탐색을 줄이려고 요청 순서를 바꿔요. OS는 "작은 랜덤 쓰기"를 모아 "큰 순차 쓰기"로 바꾸려 노력해요.

    SSD (플래시)

    움직이는 부품이 없어 랜덤 읽기가 수십 µs예요. 하지만 플래시의 특성 때문에 복잡해요.

    • 읽기/쓰기(program)는 페이지(4KB~16KB) 단위, 지우기(erase)는 블록(수 MB) 단위.
    • 페이지는 덮어쓸 수 없고, 블록 전체를 지운 뒤에만 다시 쓸 수 있어요.
    • 블록마다 지우기 횟수 한계(수천~수만 회)가 있어요 → wear leveling 필요.

    그래서 SSD 안의 FTL(Flash Translation Layer)이 논리 주소 → 물리 페이지 매핑을 관리하면서 로그 구조로 동작해요. 새 쓰기는 항상 빈 페이지에 쓰고 매핑만 바꿔요. 옛 페이지는 무효 표시했다가 나중에 가비지 컬렉션으로 블록을 정리해요. 랜덤 쓰기가 많으면 GC가 바빠져 성능이 떨어지고(write amplification), 수명이 줄어요.

    백엔드에서는 DB가 WAL(로그)을 순차로 먼저 쓰고 데이터 페이지는 나중에 모아서 쓰는 이유가 이 장이에요. 순차 쓰기는 HDD에서도 SSD에서도 빨라요. LSM 트리(RocksDB, Cassandra)는 아예 모든 쓰기를 순차로 만들어요. 클라우드 디스크(EBS 등)는 IOPS와 처리량이 따로 제한돼서, 작은 랜덤 I/O는 IOPS 한도에 먼저 걸려요. iostat -x의 await, %util로 봐요.
    시니어 심화 디스크 성능은 평균이 아니라 분포와 한도로 봐야 해요.
    • iostat -x의 %util은 요청을 병렬로 처리하는 SSD·NVMe·네트워크 디스크에서는 포화 지표가 아니에요. 100%여도 여유가 있을 수 있어요. 대기열 길이(aqu-sz)와 지연(await)을 같이 봐요.
    • 버스트 크레딧 방식의 클라우드 디스크는 크레딧이 떨어지면 IOPS가 급락해요. 평소에는 멀쩡하다가 배치가 도는 시간에만 DB가 느려지는 패턴이에요. 크레딧 잔량을 모니터링해요.
    • SSD는 가득 찰수록 내부 정리 작업(GC) 때문에 쓰기 지연이 커져요. 여유 공간을 남기고 TRIM이 동작하는지 확인해요.
    • 인스턴스에 붙은 로컬 NVMe는 빠르지만 인스턴스가 중지되면 데이터가 사라져요. 이때 내구성은 디스크가 아니라 복제가 책임져요.
    핵심 정리
    • HDD: 탐색+회전 = 랜덤 I/O ms 단위, 순차는 100배 빠름
    • SSD: 덮어쓰기 불가, FTL이 로그 구조로 관리, 랜덤 쓰기는 GC 부담
    • 저장소는 순차 쓰기를 좋아함 → WAL, LSM

    2. DB가 WAL을 쓰는 이유를 디스크 특성으로 설명하세요.
    답 보기

    1. 페이지를 덮어쓸 수 없어서 랜덤 쓰기는 흩어진 무효 페이지를 많이 만들고, 블록 단위 지우기 전에 유효 페이지를 옮기는 GC(write amplification)가 늘어 성능과 수명이 떨어져요.

    2. 변경을 데이터 페이지에 바로 쓰면 랜덤 I/O가 돼요. 대신 변경 내용을 로그 파일 끝에 순차로 추가(append)하고 fsync하면 빠르고 안전해요. 데이터 페이지는 나중에 체크포인트 때 모아서 써요.

    39장 파일과 디렉터리

    파일 시스템 인터페이스 — open, read, write, fsync

    파일과 디렉터리

    파일은 바이트 배열이고 저수준 이름인 inode 번호를 가져요. 디렉터리는 "이름 → inode 번호" 목록을 담은 특수한 파일이에요. 경로 /a/b/c는 루트부터 디렉터리를 하나씩 따라가며 찾아요.

    파일 디스크립터

    open()은 fd(작은 정수)를 반환해요. 프로세스마다 fd 테이블이 있고, 각 항목은 시스템 전역 open file table의 엔트리(현재 오프셋, 모드, inode 참조)를 가리켜요. 0/1/2는 stdin/stdout/stderr. fork하면 fd 테이블이 복사되고 open file 엔트리는 공유돼요(오프셋 공유). dup()도 같은 엔트리를 가리키는 새 fd를 만들어요(리다이렉션 원리).

    읽기와 쓰기

    read(fd, buf, n), write(fd, buf, n)은 현재 오프셋에서 동작하고 오프셋을 옮겨요. lseek()으로 오프셋을 바꿔요(랜덤 접근). pread/pwrite는 오프셋을 명시해서 멀티스레드에서 안전해요.

    fsync — 즉시 쓰기

    write()가 반환돼도 데이터는 메모리(페이지 캐시)에만 있어요. OS는 5~30초 뒤에 모아서 디스크에 써요. 그 사이 전원이 나가면 사라져요. fsync(fd)는 그 파일의 dirty 데이터를 디스크에 쓰고 완료될 때까지 기다려요. 새 파일은 디렉터리 엔트리도 영속해야 하므로 디렉터리도 fsync해야 해요.

    그 외

    • rename()은 원자적이에요. 임시 파일에 쓰고 fsync 후 rename하면 "전부 아니면 전무" 갱신이 돼요. 에디터와 DB가 쓰는 패턴.
    • 하드 링크: 같은 inode에 이름 하나 더. inode의 참조 수가 0이 될 때 삭제. rm은 사실 unlink().
    • 심볼릭 링크: 경로를 담은 별도 파일. 대상이 없으면 dangling.
    • 퍼미션: owner/group/other × rwx. chmod.
    • 마운트: 여러 파일 시스템을 하나의 트리에 붙여요.
    백엔드에서는 "로그 파일에 write했는데 서버가 죽으니 마지막 몇 초가 사라졌다"가 fsync 문제예요. MySQL innodb_flush_log_at_trx_commit=1은 커밋마다 fsync(안전, 느림), 2는 1초마다(빠름, 1초 유실 가능)예요. Kafka의 acks와 flush 설정, Redis AOF의 appendfsync도 같은 결정이에요. 그리고 삭제한 파일이 열려 있으면 디스크가 안 비워지는 것(lsof | grep deleted)은 inode 참조 수 때문이에요.
    시니어 심화 fsync는 실패할 수 있고, 실패한 뒤가 더 위험해요. 리눅스에서는 fsync가 에러를 반환한 뒤 해당 페이지가 더 이상 "써야 할 것"으로 남지 않을 수 있어서, 다시 fsync를 호출하면 성공으로 보이는데 데이터는 디스크에 없어요. 그래서 PostgreSQL은 fsync 실패 시 재시도하지 않고 프로세스를 죽인 뒤 WAL로 복구하도록 바꿨어요. 직접 파일에 쓰는 코드라면 fsync 에러를 삼키지 마세요.
    • fd 한도는 소켓도 포함해요. /proc/<pid>/limits로 실제 적용된 값을, ls /proc/<pid>/fd | wc -l로 현재 사용량을 봐요. 사용량이 천천히 계속 늘면 닫지 않는 fd가 있는 거예요.
    • 로그 로테이션은 "rename 후 프로세스가 파일을 다시 열기"가 안전해요. 복사 후 비우는 방식(copytruncate)은 그 사이에 쓴 로그를 잃을 수 있어요.
    핵심 정리
    • 파일 = inode, 디렉터리 = 이름→inode 목록, fd → open file → inode
    • write는 캐시, fsync해야 디스크. 디렉터리도 fsync
    • rename은 원자적 → 임시파일+rename 패턴
    셀프 체크
    1. 설정 파일을 안전하게(중간에 죽어도 깨지지 않게) 갱신하는 절차는?
    2. write()가 성공을 반환했는데 데이터가 유실될 수 있는 이유는?
    답 보기

    1. 임시 파일에 전체 내용 write → 임시 파일 fsync → rename(temp, target) → 디렉터리 fsync. rename이 원자적이라 옛 파일 또는 새 파일 둘 중 하나만 보여요.

    2. write는 페이지 캐시에 복사하고 반환해요. 디스크 쓰기는 나중에 비동기로 일어나서 그 전에 전원이 나가면 사라져요. fsync로 강제해야 해요.

    40장 파일 시스템 구현

    아주 단순한 파일 시스템(vsfs)으로 보는 디스크 레이아웃

    디스크 구조

    디스크를 4KB 블록으로 나누고, 대부분은 데이터 블록, 일부는 메타데이터예요.

    ┌───┬───┬───┬────────────┬──────────────────────────────┐
│ S │ i │ d │  inode 테이블 │         데이터 블록            │
└───┴───┴───┴────────────┴──────────────────────────────┘
 S: 슈퍼블록 (FS 정보)   i/d: inode·데이터 비트맵 (빈 블록 추적)

    inode

    파일 하나의 메타데이터: 크기, 퍼미션, 시간, 그리고 데이터 블록 포인터. 포인터가 고정 개수면 큰 파일을 못 담으니 간접 포인터를 써요. 직접 포인터 12개 + 1단 간접(포인터 블록) + 2단 + 3단. 대부분 파일은 작아서 직접 포인터로 끝나고, 큰 파일만 간접 포인터를 타요. ext4는 대신 extent(연속 블록 범위)를 써서 큰 파일을 효율적으로 표현해요.

    읽기 경로 예: /foo/bar 읽기

    1. 루트 inode(번호 고정, 보통 2) 읽기 → 루트 데이터 블록에서 foo 찾기
    2. foo inode 읽기 → 데이터 블록에서 bar 찾기
    3. bar inode 읽기 → 데이터 블록 읽기

    경로가 깊을수록 I/O가 늘어요. 쓰기는 더 비싸요. 새 파일 만들기는 비트맵, inode, 디렉터리 데이터, 디렉터리 inode까지 여러 블록을 갱신해요.

    캐싱과 버퍼링

    이 I/O들은 대부분 페이지 캐시에 맞아요. 리눅스는 남는 메모리를 전부 파일 캐시로 써요(free의 buff/cache). 쓰기는 모아서(write buffering) 한 번에 하고, 같은 블록을 여러 번 쓰면 한 번만 디스크에 가요. 대가는 유실 위험, 그래서 fsync.

    백엔드에서는 DB의 데이터 파일 읽기도 페이지 캐시를 거쳐요. 그래서 MySQL은 자기 버퍼풀과 OS 캐시에 같은 데이터가 이중으로 있는 걸 피하려고 innodb_flush_method=O_DIRECT로 캐시를 우회해요. 반대로 Kafka는 자체 캐시 없이 페이지 캐시에 전적으로 의존해요. 그래서 Kafka 브로커의 JVM 힙은 작게 잡고 OS 메모리를 남겨둬요. "메모리를 다 쓴 것 같은데 실제로는 캐시"인 상황을 구분하려면 free -m의 available을 봐야 해요.
    핵심 정리
    • 슈퍼블록 + 비트맵 + inode 테이블 + 데이터 블록
    • inode = 메타데이터 + 블록 포인터(간접 포인터 또는 extent)
    • 페이지 캐시가 I/O를 흡수, 쓰기 버퍼링은 성능 vs 유실 트레이드오프
    셀프 체크
    1. Kafka는 왜 JVM 힙을 작게 잡으라고 할까요?
    답 보기

    Kafka는 메시지를 자체 메모리에 캐시하지 않고 OS 페이지 캐시에 맡겨요. 힙을 크게 잡으면 페이지 캐시 공간이 줄어 디스크 읽기가 늘어요. 또 큰 힙은 GC 일시정지가 길어요. 보통 힙 4~6GB에 나머지는 OS에 남겨요.

    41~42장 지역성(FFS)과 크래시 일관성(저널링)

    파일 시스템이 디스크를 똑똑하게 쓰는 법, 그리고 중간에 죽어도 깨지지 않는 법

    FFS: 디스크를 의식하는 파일 시스템

    초기 UNIX 파일 시스템은 inode와 데이터가 멀리 떨어져 있고 파일 블록이 흩어져서 성능이 2%까지 떨어졌어요. FFS는 디스크를 실린더 그룹(지금은 블록 그룹)으로 나누고, 같은 디렉터리의 파일과 그 inode를 같은 그룹에 두고, 큰 파일은 여러 그룹에 분산해요. 결과: 관련 데이터가 가까이 있어 탐색이 줄어요. ext4가 이 후손이에요.

    크래시 일관성 문제

    파일에 블록 하나를 추가하려면 (1) 데이터 비트맵, (2) inode, (3) 데이터 블록 세 곳을 써야 해요. 디스크는 한 번에 한 블록만 원자적으로 쓸 수 있으니, 중간에 전원이 나가면 불일치가 생겨요.

    • 데이터만 쓰임: 데이터는 있지만 가리키는 inode가 없어 그냥 사라짐 (괜찮음)
    • inode만 쓰임: inode가 쓰레기 데이터를 가리킴, 비트맵과 불일치 (나쁨)
    • 비트맵만 쓰임: 공간 누수
    • inode + 비트맵: 쓰레기 데이터를 읽음
    • inode + 데이터: 비트맵 불일치, 나중에 덮어써질 수 있음

    해결 1: fsck

    부팅 시 전체 디스크를 검사해 불일치를 고쳐요. 느리고(TB 디스크면 몇 시간), "inode가 쓰레기를 가리키는" 경우는 고칠 수 없어요.

    해결 2: 저널링 (Write-Ahead Logging)

    디스크를 갱신하기 전에 "무엇을 쓸 것인지"를 먼저 저널(로그)에 기록해요.

    1. 저널 쓰기: 트랜잭션 시작 블록(TxB) + 갱신할 블록들의 내용을 저널에 씀
    2. 저널 커밋: 트랜잭션 끝 블록(TxE) 씀. 이게 디스크에 도달하면 트랜잭션은 커밋된 것
    3. 체크포인트: 실제 위치에 블록들을 씀
    4. 해제: 저널 공간 재사용

    크래시 후 복구: 저널을 읽어 커밋된 트랜잭션은 재실행(redo), 커밋 안 된 건 버려요. 1단계와 2단계 사이에 쓰기 배리어(fsync)가 있어야 TxE가 먼저 쓰이는 걸 막아요. 저널 쓰기와 커밋을 합치려고 블록 체크섬을 쓰기도 해요.

    데이터 저널링 vs 메타데이터 저널링

    데이터까지 저널에 쓰면(data 모드) 모든 데이터를 두 번 써요. ext4 기본은 ordered 모드: 데이터 블록을 먼저 실제 위치에 쓰고, 그 다음 메타데이터만 저널링해요. 순서를 지키면 "inode가 쓰레기를 가리키는" 일이 없어요.

    백엔드에서는 이 저널링이 DB의 WAL/redo 로그와 완전히 같은 원리예요. InnoDB redo 로그, PostgreSQL WAL, Kafka 로그, Raft 로그 전부 "먼저 순차 로그에 쓰고 커밋, 나중에 실제 자리에 반영"이에요. 이 장을 이해하면 DB 챕터의 트랜잭션 복구, 체크포인트, innodb_log_file_size가 왜 성능에 영향을 주는지가 바로 보여요. 그리고 fsync 없는 저널은 의미가 없으니, 클라우드 디스크에서 fsync 지연이 곧 커밋 지연이에요.
    시니어 심화 WAL의 성능과 안전을 좌우하는 것은 세 가지예요.
    • 그룹 커밋: 여러 트랜잭션의 로그를 모아 fsync 한 번으로 내려요. 동시 커밋이 많을수록 커밋당 fsync 비용이 줄어요. 단일 스레드로 순차 커밋하는 벤치마크가 실제 처리량을 크게 과소평가하는 이유예요.
    • 체크포인트 압박: 로그 공간은 유한해요. 데이터 페이지 반영이 로그 생성 속도를 못 따라가면 로그가 가득 차서 쓰기 전체가 멈춰요. "평소엔 빠르다가 주기적으로 쓰기가 멎는" 현상이 이것이에요.
    • 찢어진 쓰기(torn write): 기본 저널링 모드는 메타데이터만 보호해요. 페이지 하나를 쓰다 전원이 나가면 반쯤 써진 페이지가 남아요. 그래서 DB는 자체 방어를 둬요(InnoDB의 doublewrite buffer, PostgreSQL의 full page write).
    그리고 fsync가 성공을 반환해도 디스크나 컨트롤러의 쓰기 캐시가 거짓말을 할 수 있어요. 내구성은 문서가 아니라 전원 차단 테스트로 확인하는 것이에요.
    핵심 정리
    • FFS = 관련 데이터를 같은 그룹에 → 탐색 감소
    • 여러 블록 갱신은 원자적이지 않음 → 크래시 시 불일치
    • 저널링: 로그에 먼저 쓰고 커밋 → 실제 반영. 복구는 redo
    • DB WAL과 동일한 원리
    셀프 체크
    1. 저널 쓰기와 커밋 블록 사이에 배리어가 필요한 이유는?
    2. 저널링이 데이터를 두 번 쓰는데도 빠른 이유는?
    답 보기

    1. 디스크는 쓰기 순서를 바꿀 수 있어요. TxE가 먼저 디스크에 도달하고 중간 블록이 안 쓰인 채 크래시하면, 복구 시 "커밋된 트랜잭션"으로 보고 쓰레기를 재실행해요. 배리어로 TxE 전에 모든 로그 블록이 도달했음을 보장해요.

    2. 저널은 순차 쓰기라 빠르고, 체크포인트는 나중에 모아서 배치로 해요. 여러 트랜잭션의 같은 블록 갱신을 한 번으로 합칠 수도 있어요. 랜덤 쓰기를 즉시 하는 것보다 전체 비용이 작아요.

    분산 시스템의 핵심 문제: 실패

    머신이 여러 대면 일부는 항상 고장 나 있어요. 분산 시스템의 목표는 일부가 실패해도 전체가 동작하는 거예요. 그 외 성능(네트워크는 느림), 보안도 문제예요.

    통신은 신뢰할 수 없다

    패킷은 유실되고, 손상되고(체크섬으로 감지), 지연돼요. 신뢰성 있는 통신은 ACK + 타임아웃 + 재전송으로 만들어요. 그런데 ACK가 유실되면 송신자는 재전송하고 수신자는 같은 메시지를 두 번 받아요. 그래서 시퀀스 번호로 중복을 감지해요. 이게 TCP예요.

    RPC

    원격 함수를 로컬 함수처럼 호출하게 하는 추상화. 스텁이 인자를 직렬화(marshal)해서 보내고, 서버가 역직렬화해서 실행하고 결과를 돌려줘요. 문제: 어떤 전송 계층 위에 올릴까(TCP는 ACK가 이중이라 UDP + 자체 재시도가 효율적일 수 있음), 큰 인자, 오래 걸리는 호출의 타임아웃, 바이트 순서(endianness).

    NFS와 상태 없음

    Sun NFS는 서버를 stateless로 설계했어요. 서버가 클라이언트의 열린 파일을 기억하지 않고, 모든 요청이 파일 핸들 + 오프셋을 담아서 서버가 죽었다 살아나도 그냥 재시도하면 돼요. 그래서 요청이 멱등(idempotent)해야 해요. "오프셋 100에 쓰기"는 몇 번 해도 같아요. 캐시 일관성은 느슨하게(close-to-open) 해결했어요.

    백엔드에서는 "상태 없는 서버 + 멱등한 요청 + 재시도"가 NFS에서 나온 설계 원칙이고, 지금 REST API 설계와 쿠버네티스의 핵심 전제예요. "요청이 실패했는지 응답만 유실됐는지 알 수 없다"는 문제가 결제 API의 멱등성 키로 이어져요. 분산 시스템 챕터(DDIA)에서 이 문제들을 본격적으로 다뤄요.
    시니어 심화 "상태 없음"은 상태를 없앤 것이 아니라 DB와 캐시로 옮긴 거예요. 병목과 장애 지점도 같이 옮겨 갔다는 뜻이에요.
    • 타임아웃은 계층 순서대로: 호출하는 쪽의 타임아웃이 호출받는 쪽의 처리 시간 한도보다 길어야 해요. 반대면 상위는 이미 포기했는데 하위는 계속 일하는 낭비가 생기고, 재시도가 그 위에 겹쳐요.
    • 재시도 증폭: 계층마다 3번씩 재시도하면 3계층에서 최악 27배의 부하가 돼요. 재시도는 한 계층에서만 하고 나머지는 실패를 그대로 올려요.
    • 재시도와 순서: 느리게 도착한 첫 요청이 재시도보다 나중에 처리되면 새 값을 옛 값으로 덮어써요. 멱등성만으로는 부족하고, 버전이나 조건부 갱신으로 순서를 지켜야 해요.
    핵심 정리
    • 분산 = 부분 실패가 일상, 통신은 신뢰 불가
    • 신뢰성 = ACK + 타임아웃 + 재전송 + 시퀀스 번호
    • stateless 서버 + 멱등 요청 → 재시도가 안전
    셀프 체크
    1. 요청을 보냈는데 응답이 없을 때, 서버가 처리했는지 알 수 있나요? 그래서 어떻게 설계해야 하나요?
    답 보기

    알 수 없어요. 요청이 유실됐을 수도, 서버가 처리하고 응답이 유실됐을 수도 있어요. 그래서 재시도해도 안전하도록 요청을 멱등하게 만들어야 해요. 자연스럽게 멱등하지 않은 작업(결제 생성)은 클라이언트가 멱등성 키를 붙이고 서버가 중복을 걸러요.
