    네트워크

    기준 교재: 성공과 실패를 결정하는 1%의 네트워크 원리 (Tsutomu Tone) + HTTP 완벽 가이드 · 3~4주

    『1%의 네트워크 원리』는 "브라우저에 URL을 입력하면 무슨 일이 일어나는가"를 브라우저 → 프로토콜 스택 → LAN → 인터넷 → 서버 측 → 웹 서버 순서로 패킷을 따라가며 설명해요. 이 페이지는 그 6장 구성을 따르고, HTTP 자체는 『HTTP 완벽 가이드』에서 필요한 장만 부록으로 붙였어요.

    백엔드 개발자에게 특히 중요한 장은 1장(DNS), 2장(TCP 전체), 5장(LB·프록시), 6장(서버 소켓), 부록 B(연결 관리), C(캐시)예요.

    성공과 실패를 결정하는 1%의 네트워크 원리 기준 교재패킷의 여정을 따라가는 구성, 입문자에게 최적

    1.1 URL 해석과 HTTP 요청 메시지

    브라우저가 가장 먼저 하는 일

    URL 분해

    https://api.example.com:443/users/42?fields=name#top
└─┬─┘   └──────┬───────┘└┬┘└───┬───┘└────┬─────┘└┬┘
스킴        호스트        포트   경로      쿼리     프래그먼트

    브라우저는 스킴으로 프로토콜을 정하고, 호스트로 어느 서버인지, 경로와 쿼리로 무엇을 요청할지 정해요. 프래그먼트는 서버로 보내지 않아요.

    HTTP 요청 메시지

    GET /users/42?fields=name HTTP/1.1      ← 요청 라인: 메서드 URI 버전
Host: api.example.com                   ← 헤더 (이름: 값)
Accept: application/json
Authorization: Bearer eyJ...
                                        ← 빈 줄
(본문: GET은 보통 없음)

    응답도 같은 구조예요: 상태 라인(HTTP/1.1 200 OK) + 헤더 + 빈 줄 + 본문. HTTP는 텍스트 기반, 상태 없음(stateless)이에요. 요청 하나하나가 독립이고, 서버는 이전 요청을 기억하지 않아요. 그래서 상태가 필요하면 쿠키나 토큰으로 매번 알려줘야 해요.

    메서드

    메서드의미안전멱등
    GET리소스 조회OO
    HEADGET과 같지만 본문 없이 헤더만OO
    POST리소스 생성, 처리 요청XX
    PUT리소스 전체 교체XO
    PATCH리소스 일부 수정X구현에 따라
    DELETE리소스 삭제XO
    OPTIONS지원 메서드 확인 (CORS preflight)OO

    안전 = 서버 상태를 바꾸지 않음. 멱등 = 여러 번 해도 한 번과 결과가 같음. 브라우저와 프록시는 이 성질을 믿고 GET을 캐시하고, 멱등한 요청만 자동 재시도해요.

    백엔드에서는 조회를 POST로 만들면 캐시와 재시도의 이점을 전부 잃어요. 반대로 상태를 바꾸는 작업을 GET으로 만들면 크롤러나 프리페치가 실행해 버려요. API 설계 시 메서드의 안전·멱등 성질을 지키는 게 HTTP 인프라(CDN, 프록시, 클라이언트 라이브러리)를 공짜로 쓰는 길이에요.
    시니어 심화 본문은 메서드의 안전·멱등 성질을 지키라고 했는데, 이것이 중요한 이유는 HTTP 인프라가 그 성질을 믿고 자동으로 재시도하거나 미리 호출하기 때문이에요.

    상황 1: POST가 실패했는데 처리됐는지 모름

    앱이 주문 생성 POST /orders를 보냈는데 응답을 받기 직전에 와이파이가 끊겼어요. 앱은 "네트워크 오류"를 보여 줬고, 사용자는 다시 눌렀어요. 서버에는 주문이 두 건 생겼어요.

    1. 요청이 서버에 도착해 처리됐는지, 도착하기 전에 끊겼는지 클라이언트는 알 수 없어요. 둘 다 "응답 없음"으로 똑같이 보여요.
    2. 그래서 HTTP 인프라는 메서드를 보고 판단해요. 예를 들어 nginx는 업스트림 서버와의 연결이 실패하면 GET, PUT, DELETE 같은 멱등 메서드는 다른 서버로 다시 보내지만, POST는 기본적으로 다시 보내지 않아요. 두 번 실행되면 결과가 달라질 수 있다고 보기 때문이에요.
    3. 결국 POST의 재시도 판단은 사용자나 앱에게 넘어오고, 그 재시도는 중복을 만들어요.

    해결: 요청마다 클라이언트가 고유한 키를 만들어 Idempotency-Key 헤더로 보내고, 서버는 같은 키의 중복 요청에 처음 결과를 그대로 돌려줘요(API 챕터 5장, 분산 챕터 B장 시니어). 앱은 재시도할 때 같은 키를 다시 써야 해요. 재시도마다 새 키를 만들면 아무 의미가 없어요.

    상황 2: GET이 상태를 바꿈

    뉴스레터 메일의 "수신 거부" 링크가 GET /unsubscribe?token=...로 바로 수신 거부를 처리했어요. 어느 날 회사 고객 수천 명이 메일을 열지도 않았는데 수신 거부가 됐어요.

    1. 기업용 메일 보안 장비는 메일 속 링크가 안전한지 확인하려고 링크를 미리 열어 봐요. 메신저의 링크 미리보기, 브라우저의 미리 가져오기도 같아요.
    2. 이 도구들은 GET이 "안전한 메서드", 즉 아무것도 바꾸지 않는다고 믿고 마음대로 호출해요.
    3. 상태를 바꾸는 GET은 사람이 아닌 도구에 의해 실행돼요.

    해결: GET 링크는 확인 화면을 보여 주고, 실제 변경은 버튼으로 보내는 POST에서 해요. 메일 수신 거부처럼 원클릭이 필요하면, 메일 클라이언트가 보내는 표준 POST 방식(List-Unsubscribe-Post 헤더)을 써요.

    운영에서 알아채는 법

    • 같은 회원이 몇 초 안에 같은 내용으로 만든 주문 건수를 세어 봐요. 0이 아니라면 POST 재시도가 중복을 만들고 있어요.
    • 상태를 바꾸는 API의 접근 로그에서 User-Agent를 봐요. 사람이 아닌 봇이나 스캐너가 호출하고 있다면 그 API는 GET이면 안 돼요.
    핵심 정리
    • URL = 스킴 + 호스트 + 포트 + 경로 + 쿼리
    • HTTP 메시지 = 시작 라인 + 헤더 + 빈 줄 + 본문, 상태 없음
    • 안전·멱등은 캐시와 재시도의 근거
    셀프 체크
    1. DELETE가 멱등인 이유는? 두 번째 DELETE는 404를 돌려주는데도?
    답 보기

    멱등은 "서버 상태"가 같다는 뜻이지 "응답"이 같다는 뜻이 아니에요. 한 번 지우든 두 번 지우든 리소스는 없는 상태로 같아요. 응답 코드가 200 → 404로 달라져도 멱등이에요.

    1.2~1.3 DNS — 이름을 IP로

    리졸버와 DNS 서버의 계층 구조

    리졸버

    브라우저가 api.example.com의 IP를 알아내려면 OS의 리졸버(getaddrinfo 같은 라이브러리 함수)를 불러요. 리졸버는 먼저 로컬 캐시와 /etc/hosts를 보고, 없으면 설정된 DNS 서버(/etc/resolv.conf, 보통 ISP나 8.8.8.8)에 UDP 53번으로 질의해요.

    DNS 서버의 계층

    전 세계 도메인을 한 서버가 다 알 수 없으니 계층적으로 위임해요.

    재귀 서버가 이 과정을 대신 하고 결과를 TTL 동안 캐시해요. 두 번째 질의부터는 바로 응답해요.

    레코드 종류

    • A / AAAA: 이름 → IPv4 / IPv6
    • CNAME: 이름 → 다른 이름 (별칭). www.example.com → example.cdn.net
    • MX: 메일 서버
    • NS: 이 도메인의 권한 서버
    • TXT: 임의 텍스트 (도메인 소유 확인, SPF)

    TTL과 전파

    DNS를 바꿔도 캐시가 만료될 때까지 옛 IP로 가요. 그래서 이전 작업 전에 TTL을 미리 낮춰요(300초 → 60초). "DNS 전파에 48시간"이라는 말은 TTL이 길거나 중간 캐시 서버가 TTL을 무시하는 경우예요.

    백엔드에서는 JVM은 DNS 결과를 자체 캐시해요. 기본은 보안 관리자 없으면 30초지만 옛 버전은 영구 캐시였어요(networkaddress.cache.ttl). 로드밸런서 IP가 바뀌었는데 옛 IP로 계속 가서 장애가 나는 전형적 사고예요. 쿠버네티스 안에서는 CoreDNS가 my-svc.my-ns.svc.cluster.local을 서비스 IP로 풀어주고, ndots:5 설정 때문에 외부 도메인(api.example.com처럼 점이 5개 미만)을 조회하면 클러스터 검색 도메인을 붙인 이름부터 차례로 물어서, 보통 3~4번 실패한 뒤에야 성공하는 지연 문제가 있어요. DNS 조회 실패나 느림은 "외부 API가 느리다"로 보여서 찾기 어려워요. dig +trace, nslookup으로 직접 확인하세요.
    시니어 심화 본문의 JVM DNS 캐시 문제와 짝을 이루는 함정이 있어요. DNS로 트래픽을 옮길 때 실제 전환 시간은 TTL이 아니라 연결의 수명이 정한다는 거예요.

    상황

    주문 DB가 장애 조치로 새 원본으로 넘어갔어요. DB 엔드포인트의 DNS는 30초 안에 새 원본을 가리켰어요. 그런데 장애 조치 20분 뒤에도 일부 API 서버가 "read-only" 에러를 내며 주문을 저장하지 못했어요.

    깨지는 과정

    1. 커넥션 풀은 이미 맺은 연결을 계속 재사용해요. 새로 연결을 맺을 때만 DNS를 조회해요.
    2. 옛 원본은 죽지 않고 읽기 전용 복제본으로 내려갔어요. 그래서 풀에 있던 연결들은 끊기지 않고 옛 서버에 그대로 붙어 있어요.
    3. 그 연결로 보낸 쓰기는 "read-only" 에러로 실패해요. 하지만 연결 자체는 살아 있으니 풀은 연결을 버리지 않고 계속 빌려줘요.
    4. HikariCP의 기본 최대 연결 수명(maxLifetime)은 30분이에요. 연결이 수명이 다해 새로 맺어질 때까지 최대 30분 동안 일부 요청이 실패해요.

    같은 일이 HTTP에서도 생겨요. 외부 API가 로드밸런서의 IP를 바꿨는데 keep-alive 연결이 옛 IP에 붙어 있으면, 옛 IP가 내려갈 때까지 그쪽으로 보내요.

    해결책

    • 최대 연결 수명을 정해요. maxLifetime이 DNS 기반 전환의 실제 상한이에요. 몇 분 안에 전환돼야 한다면 수명을 그만큼 짧게 둬요. DB의 유휴 연결 타임아웃(wait_timeout)보다도 짧아야 해요.
    • 장애 조치를 아는 드라이버를 써요. AWS의 Aurora라면 AWS Advanced JDBC Wrapper처럼 장애 조치를 감지해 연결을 새 원본으로 바로 옮겨 주는 드라이버가 있어요. 전환 시간이 수명이 아니라 몇 초로 줄어요.
    • 읽기 전용 에러를 신호로 써요. 쓰기가 "read-only" 에러로 실패하면 그 연결을 풀에서 버리게 하거나, 풀 전체를 새로 고치는 처리를 넣어요(HikariCP의 softEvictConnections()).
    • JVM의 DNS 캐시도 확인해요. 보안 관리자가 켜져 있으면 JVM은 DNS 결과를 영원히 캐시해요. networkaddress.cache.ttl을 명시적으로 짧게(예: 30초) 두세요.

    운영에서 알아채는 법

    • 장애 조치 훈련 때 "DNS가 바뀐 시각"과 "모든 서버가 새 원본에 쓰기 시작한 시각"을 함께 재요. 둘의 차이가 실제 전환 시간이에요.
    • 장애 조치 뒤 "read-only" 같은 에러가 서버별로 얼마나 오래 이어지는지 봐요. 일부 서버만 길게 이어진다면 연결 수명 문제예요.
    핵심 정리
    • 리졸버 → 재귀 서버 → 루트 → TLD → 권한 서버
    • TTL 동안 캐시, 바꾸기 전엔 TTL 낮추기
    • 애플리케이션 런타임도 캐시함(JVM) → 장애 원인

    1. DNS는 왜 UDP를 쓰나요? TCP를 쓰는 경우는?
    2. CNAME과 A 레코드의 차이는?
    답 보기

    1. 질의/응답이 작은 패킷 하나로 끝나서 TCP 연결 수립(1 RTT)이 아까워요. 응답이 512바이트(EDNS면 더 큼)를 넘거나 존 전송(AXFR)일 때 TCP를 써요. DoT/DoH는 TCP/HTTPS 위예요.

    2. A는 이름을 IP로 직접 매핑. CNAME은 이름을 다른 이름으로 매핑해서 한 번 더 조회가 필요해요. 대신 대상 IP가 바뀌어도 CNAME은 안 바꿔도 돼요(CDN, LB 도메인에 사용). 루트 도메인(apex)에는 CNAME을 못 둬요(ALIAS 레코드로 대체).

    1.4 프로토콜 스택에 송신을 의뢰한다 — 소켓

    브라우저는 직접 패킷을 보내지 않는다. OS에게 부탁한다

    프로토콜 스택

    네트워크 통신 기능은 OS 안에 있어요(TCP, IP, 드라이버). 애플리케이션은 소켓 API로 OS에 의뢰만 해요. 그래서 모든 언어의 HTTP 클라이언트는 결국 같은 시스템 콜을 불러요.

    소켓 라이브러리 호출 순서 (클라이언트)

    1. socket(): 소켓 생성. fd를 돌려받아요. OS 안에 제어 정보(상태, 상대 IP·포트, 버퍼)를 담을 공간이 생겨요.
    2. connect(fd, 서버IP, 포트): 서버와 연결. 3-way handshake가 여기서 일어나요.
    3. write(fd, 요청) / read(fd, 버퍼): 데이터 송수신. HTTP 메시지는 그냥 바이트예요.
    4. close(fd): 연결 종료. 4-way handshake.

    이 4단계가 전부예요. HTTP 라이브러리가 하는 일은 메시지를 문자열로 만들어 write하고, read한 바이트를 파싱하는 것이에요.

    포트

    IP는 머신을, 포트는 머신 안의 프로그램(소켓)을 가리켜요. 서버는 잘 알려진 포트(80, 443, 3306)로 기다리고, 클라이언트는 OS가 주는 임시 포트(ephemeral, 리눅스 기본 32768~60999)를 써요. 연결은 (출발 IP, 출발 포트, 목적 IP, 목적 포트) 4-tuple로 식별돼요.

    백엔드에서는 클라이언트 임시 포트는 약 28,000개뿐이에요. 같은 목적지(IP:포트)로 연결을 계속 새로 맺고 끊으면(keep-alive 없이) TIME_WAIT가 쌓여 포트가 고갈돼요. "Cannot assign requested address" 에러가 그거예요. 커넥션 풀을 쓰거나 net.ipv4.ip_local_port_range를 넓혀요. 또 ulimit -n이 소켓 fd 수를 제한하니 서버에서는 반드시 올려야 해요.
    시니어 심화 본문은 같은 목적지로 연결을 계속 맺으면 포트가 고갈된다고 했는데, 여기서 중요한 단어는 "같은 목적지"예요. 포트 한도는 서버 전체가 아니라 목적지 (IP, 포트) 하나당이에요.

    상황

    주문 서비스가 결제사 API를 부를 때 매번 새 HTTP 연결을 맺어요. 클라우드의 NAT 게이트웨이를 거쳐 밖으로 나가요. 세일 날 트래픽이 세 배가 되자 결제 호출의 일부가 연결 단계에서 조용히 실패했어요. 결제사 쪽에는 아무 문제가 없었어요.

    깨지는 과정

    1. TCP 연결은 (내 IP, 내 포트, 상대 IP, 상대 포트) 네 값의 조합으로 구분돼요. 상대가 다르면 같은 내 포트를 다시 쓸 수 있어요. 그래서 한도는 "목적지 하나당 쓸 수 있는 내 포트 수"예요.
    2. 리눅스가 나가는 연결에 쓰는 포트 범위는 기본 약 28,000개(32768~60999)예요. 연결을 닫은 쪽은 그 포트를 TIME_WAIT 상태로 60초 동안 붙잡아요. 같은 목적지로 초당 약 470개를 넘게 새로 맺으면 포트가 바닥나요.
    3. NAT 게이트웨이를 거치면 모든 서버의 연결이 NAT의 IP 하나로 나가요. 이제 한도는 서버 하나가 아니라 NAT 장비의 포트예요. AWS NAT 게이트웨이는 목적지 하나당 동시 연결 약 55,000개가 상한이고, 넘으면 연결이 실패해요.
    4. 애플리케이션 로그에는 "connect timed out"이나 연결 실패만 남아서, 결제사 장애로 오해하기 쉬워요.

    해결책

    • 연결을 재사용해요. HTTP 클라이언트에 커넥션 풀과 keep-alive를 켜요. 요청마다 연결을 맺지 않으면 포트도 TIME_WAIT도 거의 생기지 않아요. 클라이언트 객체를 요청마다 새로 만드는 코드가 가장 흔한 원인이에요.
    • 나가는 IP를 늘려요. NAT 게이트웨이에 IP를 여러 개 붙이거나 NAT를 여러 개 두면 한도가 그만큼 늘어요.
    • NAT를 거칠 필요가 없는 곳은 우회해요. 같은 클라우드의 서비스(S3 같은 저장소)는 VPC 엔드포인트로 연결하면 NAT를 거치지 않아요. 비용도 줄어요.
    • 커널 설정은 마지막에 봐요. 포트 범위를 넓히거나 tcp_tw_reuse를 켜는 것은 서버 자체의 한도만 늘려요. NAT의 한도에는 효과가 없어요.

    운영에서 알아채는 법

    • 서버에서 ss -s로 TIME_WAIT 연결 수를 봐요. 수만 개라면 연결을 재사용하지 않고 있어요.
    • AWS NAT 게이트웨이는 포트 할당 실패를 ErrorPortAllocation 지표로 보여줘요. 이 값에 알림을 걸어요.
    • 외부 API 호출 실패를 "연결 단계 실패"와 "응답 단계 실패"로 나눠 기록하면, 상대 장애인지 우리 쪽 한도인지 바로 구분돼요.
    핵심 정리
    • 통신은 OS가 함, 앱은 socket/connect/write/read/close만
    • 연결 식별 = 4-tuple, 클라이언트 포트는 유한
    셀프 체크
    1. 한 클라이언트가 같은 서버 포트로 동시에 여러 연결을 맺을 수 있는 이유는?
    답 보기

    연결은 4-tuple로 구분되는데 클라이언트 출발 포트가 연결마다 달라요. (10.0.0.1:50001 → 서버:443)과 (10.0.0.1:50002 → 서버:443)은 다른 연결이에요. 서버 쪽은 443 하나로 수만 개 연결을 받아요.

    2장 TCP/IP의 데이터를 전기 신호로

    2.1~2.2 소켓 작성과 접속 — 3-way handshake

    connect() 안에서 일어나는 일

    TCP 헤더

    TCP는 데이터 앞에 20바이트 이상의 헤더를 붙여요. 중요한 필드: 출발/목적 포트, 시퀀스 번호(이 세그먼트의 첫 바이트 번호), ACK 번호(다음에 받고 싶은 바이트 번호), 제어 비트(SYN, ACK, FIN, RST, PSH), 윈도우 크기(내가 받을 수 있는 양).

    3-way handshake

    왜 3번? 양쪽 모두 "내가 보낼 수 있고, 상대가 받을 수 있다"를 확인해야 해서예요. 2번이면 서버는 자기 SYN이 도착했는지 몰라요. 초기 시퀀스 번호를 랜덤으로 하는 건 옛 연결의 패킷과 섞이는 걸 막고 추측 공격을 어렵게 하려는 거예요.

    서버 쪽: backlog

    서버는 listen(fd, backlog)로 대기해요. SYN을 받은 연결(SYN 큐)과 handshake가 끝나 accept()를 기다리는 연결(accept 큐) 두 큐가 있어요. 애플리케이션이 accept를 못 따라가면 accept 큐가 넘쳐 SYN+ACK를 안 보내거나 연결을 버려요. 클라이언트는 타임아웃으로 봐요.

    SYN flood

    SYN만 보내고 ACK를 안 보내면 SYN 큐가 차요. 방어는 SYN cookie: 큐에 저장하지 않고 시퀀스 번호에 정보를 인코딩해서 ACK가 오면 복원해요.

    백엔드에서는 트래픽 급증 때 "연결은 됐는데 응답이 없다"와 "연결 자체가 안 된다"를 구분해야 해요. 후자는 accept 큐 overflow일 수 있어요. ss -ltn의 Recv-Q(현재 큐)와 Send-Q(backlog 한도), netstat -s | grep -i listen의 overflow 카운트로 확인해요. 애플리케이션이 listen()에 넘기는 값(톰캣 acceptCount, Nginx backlog)과 커널 net.core.somaxconn 중 작은 값이 적용돼요.
    시니어 심화 본문은 accept 큐가 넘치는 상황을 다뤘는데, 이때 클라이언트 쪽에서 보이는 증상에는 아주 특징적인 모양이 있어요. 연결 시간이 정확히 1초, 3초, 7초씩 늦어요.

    상황

    세일 시작 순간 API 응답 시간 그래프에 이상한 봉우리가 생겼어요. 대부분은 50ms인데, 일부 요청이 정확히 1초대, 3초대, 7초대에 몰려 있었어요. 그런데 서버 애플리케이션의 응답 시간 지표는 평소와 같았어요.

    깨지는 과정

    1. 연결 요청(SYN)이 몰리면서 커널의 accept 큐가 가득 찼어요. 애플리케이션이 연결을 꺼내 가는 속도보다 들어오는 속도가 빨랐어요.
    2. 큐가 넘치면 리눅스는 기본적으로 새 연결 요청을 조용히 버려요. 거절 응답도 보내지 않아요.
    3. 클라이언트는 응답이 없으니 SYN을 다시 보내요. 리눅스 클라이언트의 첫 재전송은 1초 뒤이고, 그 뒤로 2초, 4초로 간격이 두 배씩 늘어요.
    4. 그래서 연결이 1초, 1+2=3초, 3+4=7초 뒤에 성공하는 계단 모양이 나와요.
    5. 서버 애플리케이션은 연결을 받은 뒤부터 시간을 재니, 이 기다림은 지표에 전혀 잡히지 않아요.

    해결책

    • 큐 크기를 확인해요. accept 큐의 크기는 애플리케이션이 정한 값(톰캣은 server.tomcat.accept-count, 기본 100)과 커널의 net.core.somaxconn 중 작은 쪽이에요. 둘 다 확인해야 해요.
    • 근본 원인은 꺼내 가는 속도예요. 큐를 키우면 순간적인 몰림은 흡수하지만, 애플리케이션 스레드가 모두 바쁘면 결국 또 넘쳐요. 처리량 자체와 부하 차단을 함께 봐야 해요.
    • 클라이언트의 연결 타임아웃을 짧게 둬요. 연결 타임아웃을 1초 정도로 두고 다른 인스턴스로 재시도하면, 7초짜리 재전송을 기다리는 것보다 꼬리 지연이 훨씬 짧아요. 연결 단계의 실패는 요청이 전달되지 않은 것이 확실하니 POST도 안전하게 재시도할 수 있어요.
    • 버리지 말고 거절하게 할 수도 있어요. net.ipv4.tcp_abort_on_overflow=1이면 큐가 넘칠 때 RST를 보내서 클라이언트가 즉시 실패를 알아요. 다만 순간적인 몰림까지 바로 실패하게 되니 신중하게 써요.

    운영에서 알아채는 법

    • 응답 시간 분포(히스토그램)에서 1초, 3초 근처의 봉우리를 찾아요. 평균이나 p99만 보면 이 모양이 안 보여요.
    • 서버에서 nstat -az | grep -i listen으로 TcpExtListenOverflows와 TcpExtListenDrops를 봐요. 이 값이 오르면 큐가 넘친 거예요.
    • ss -lnt의 LISTEN 소켓 줄에서 Recv-Q(지금 큐에 있는 연결 수)가 Send-Q(큐 크기)에 가까우면 넘치기 직전이에요.
    핵심 정리
    • SYN → SYN+ACK → ACK, 1 RTT, 시퀀스 번호 교환
    • 서버 backlog = SYN 큐 + accept 큐, 넘치면 연결 실패
    셀프 체크
    1. handshake가 2-way면 안 되는 이유는?
    2. accept 큐가 꽉 차면 클라이언트는 어떤 현상을 보나요?
    답 보기

    1. 서버가 보낸 SYN+ACK가 클라이언트에 도착했는지 서버가 알 수 없어요. 양방향 모두의 도달성과 초기 번호를 확인하려면 마지막 ACK가 필요해요.

    2. 리눅스 기본은 마지막 ACK를 버려요. 클라이언트는 ESTABLISHED라고 믿고 데이터를 보내지만 응답이 없고, 재전송 후 결국 타임아웃. 서버 로그엔 아무것도 안 남아서 찾기 어려워요.

    2.3 데이터 송수신 — 신뢰성, 흐름 제어, 혼잡 제어

    TCP가 "확실히, 순서대로, 너무 빠르지 않게" 보내는 방법

    세그먼트와 MSS

    애플리케이션이 write한 데이터는 송신 버퍼에 쌓이고, TCP가 MSS(최대 세그먼트 크기, 이더넷에서 보통 1460바이트) 단위로 잘라 보내요. 작은 데이터를 바로 보낼지 모아서 보낼지는 Nagle 알고리즘이 정해요. 지연이 중요하면 TCP_NODELAY로 꺼요.

    신뢰성: 시퀀스 번호와 ACK

    모든 바이트에 번호가 있고, 수신자는 "여기까지 받았다"를 ACK 번호로 알려요. 송신자는 ACK가 일정 시간(RTO, RTT 기반으로 계산) 안에 안 오면 재전송해요. 같은 ACK가 3번 연속 오면(dup ACK) 타임아웃 전에 바로 재전송해요(fast retransmit). 순서가 바뀌어 도착한 세그먼트는 수신 버퍼에서 정렬해요.

    흐름 제어: 수신 윈도우

    수신자가 버퍼에서 데이터를 꺼내는 속도보다 빨리 보내면 넘쳐요. 그래서 수신자는 ACK마다 윈도우 크기(남은 버퍼)를 알려주고, 송신자는 ACK 없이 그만큼만 보내요. 윈도우가 0이면 멈춰요. 애플리케이션이 read()를 안 하면 윈도우가 0이 되고 송신자가 블록돼요. 이게 backpressure가 TCP 레벨에서 자연스럽게 작동하는 원리예요.

    혼잡 제어: 혼잡 윈도우

    수신자는 여유 있어도 중간 라우터가 넘칠 수 있어요. 송신자는 네트워크 상태를 추측해 혼잡 윈도우(cwnd)를 관리하고, 실제 전송량은 min(수신 윈도우, cwnd)예요.

    • Slow start: cwnd를 1 MSS에서 시작해 RTT마다 2배로 (지수 증가)
    • Congestion avoidance: 임계값(ssthresh) 넘으면 RTT마다 1 MSS씩 (선형 증가)
    • 손실 감지: 타임아웃이면 cwnd를 1로 리셋(심각), dup ACK 3번이면 절반으로(가벼움)

    리눅스 기본 알고리즘은 CUBIC(손실 기반)이고, Google의 BBR은 손실 대신 대역폭과 RTT를 측정해 결정해요. 손실이 있는 무선망에서 BBR이 훨씬 좋아요.

    지연의 원인

    1 RTT가 100ms인 대륙 간 통신에서 slow start 때문에 처음 몇 RTT는 윈도우가 작아요. 작은 파일 하나도 수백 ms가 걸려요. 그래서 연결을 재사용(keep-alive)하면 이미 커진 cwnd를 이어 쓸 수 있어 빨라요. 초기 cwnd를 10 MSS로 올린 것(RFC 6928)도 이 때문이에요.

    백엔드에서는 큰 응답(수 MB JSON, 파일 다운로드)이 느린 건 대역폭보다 RTT × 윈도우 성장 때문인 경우가 많아요. 압축(gzip, brotli)으로 바이트를 줄이는 게 효과적이에요. 그리고 수신 윈도우 0 = 상대 애플리케이션이 안 읽고 있다는 뜻이에요. 서버가 응답을 느리게 보내는 줄 알았는데 클라이언트가 처리를 못 하는 경우를 Wireshark의 "TCP ZeroWindow"로 잡아요. 스트리밍 응답에서 클라이언트가 느리면 서버 스레드가 write에서 블록되는 이유이기도 해요.
    시니어 심화 본문은 큰 응답이 느린 이유를 다뤘는데, 작은 요청에서도 패킷 하나의 유실이 200ms를 더하는 경우가 있어요. 데이터센터 안에서도요.

    상황

    주문 서비스가 같은 데이터센터의 재고 서비스를 부르는 호출은 평균 2ms예요. 그런데 p99.9가 늘 200ms 부근에 붙어 있었어요. 재고 서비스의 처리 시간 지표는 p99.9도 5ms였어요.

    깨지는 과정

    1. TCP는 보낸 데이터의 확인 응답(ACK)이 일정 시간 안에 오지 않으면 다시 보내요. 이 대기 시간이 재전송 타임아웃(RTO)이에요.
    2. RTO는 측정된 왕복 시간으로 계산하지만, 리눅스에서는 아무리 짧아도 200ms 아래로 내려가지 않아요. 왕복 시간이 0.5ms인 같은 데이터센터 안이라도 마찬가지예요.
    3. 그래서 패킷 하나가 유실되고 타임아웃으로 재전송되면, 그 요청에는 200ms가 더해져요. 2ms짜리 요청이 202ms가 돼요.
    4. 유실률이 0.1%만 돼도 1,000번에 한 번은 200ms가 붙어요. p99.9가 200ms에 붙는 이유예요.

    비슷한 모양의 다른 원인도 있어요. 요청을 작은 조각 두 번에 나눠 쓰는 코드는, 보내는 쪽의 Nagle 알고리즘(작은 패킷을 모아서 보내기)과 받는 쪽의 지연 ACK(ACK를 조금 미뤘다 보내기)가 서로를 기다리면서 40ms씩 늦어질 수 있어요. 대부분의 HTTP 클라이언트와 서버는 TCP_NODELAY로 Nagle을 꺼서 이 문제를 피해요.

    해결책

    • 유실이 어디서 나는지 찾아요. 대개 세 곳이에요. 혼잡한 스위치, 서버 NIC의 수신 버퍼(링 버퍼) 넘침, 그리고 꽉 찬 소켓 수신 버퍼예요. NIC 쪽은 ethtool -S의 drop 카운터로, 서버 쪽은 nstat의 버퍼 관련 카운터로 확인해요.
    • 꼬리 지연이 중요한 호출은 헤지 요청을 고려해요. 응답이 p95 시간을 넘으면 같은 요청을 다른 인스턴스로 한 번 더 보내고, 먼저 온 응답을 써요. 멱등한 조회에만 써야 하고, 요청량이 몇 % 늘어나는 대가가 있어요.
    • 연결을 재사용해요. 새 연결의 처음 몇 패킷은 혼잡 제어가 조심스럽고, SYN이 유실되면 1초(2.1 시니어)를 기다려요. 풀에서 데워진 연결을 쓰면 이런 비용이 줄어요.

    운영에서 알아채는 법

    • "평균은 몇 ms인데 p99.9가 200ms 근처"라는 모양이 가장 강한 신호예요.
    • ss -ti로 연결별 재전송 횟수(retrans)를 보고, nstat의 TcpRetransSegs를 지표로 남겨 서버 전체의 재전송 추세를 봐요. 재전송이 특정 랙이나 특정 서버에 몰린다면 그쪽 장비를 의심해요.
    • 호출하는 쪽과 받는 쪽의 지연 지표를 나란히 봐요. 차이가 크다면 그 사이(네트워크, 큐)에서 시간이 새고 있어요.
    핵심 정리
    • 신뢰성 = 시퀀스 번호 + ACK + 재전송
    • 흐름 제어 = 수신 윈도우(수신자 보호), 혼잡 제어 = cwnd(네트워크 보호)
    • slow start 때문에 새 연결은 느림 → keep-alive
    셀프 체크
    1. 흐름 제어와 혼잡 제어는 누구를 보호하나요?
    2. 같은 대역폭인데 RTT가 10배 길면 처리량이 어떻게 되나요?
    답 보기

    1. 흐름 제어는 수신자의 버퍼(수신자가 윈도우로 알려줌), 혼잡 제어는 중간 네트워크(송신자가 손실·지연으로 추정).

    2. 처리량 ≈ 윈도우 / RTT. 윈도우가 같으면 RTT가 10배 길 때 처리량은 1/10이에요. 그래서 장거리 통신은 윈도우를 키워야 하고(window scaling), slow start 단계도 10배 오래 걸려요.

    2.4 연결 끊기 — 4-way handshake와 TIME_WAIT

    close() 안에서 일어나는 일, 그리고 서버에 쌓이는 상태들

    4-way handshake

    TCP는 양방향이 독립적이라 각 방향을 따로 닫아요. 한쪽이 FIN을 보내도 반대 방향은 열려 있어 데이터를 계속 받을 수 있어요(half-close).

    TIME_WAIT

    먼저 닫은 쪽이 마지막 ACK 후 2MSL(리눅스 60초) 동안 유지하는 상태예요. 이유: (1) 마지막 ACK가 유실되면 상대가 FIN을 재전송하니 다시 ACK해 줘야 함, (2) 네트워크에 떠도는 옛 패킷이 같은 4-tuple의 새 연결에 섞이는 걸 막음. 정상이에요. 문제는 너무 많을 때예요. 포트와 메모리를 차지해요.

    해결: 연결을 재사용(keep-alive, 커넥션 풀)해서 close 횟수 자체를 줄여요. net.ipv4.tcp_tw_reuse=1로 클라이언트 쪽 TIME_WAIT 소켓을 재사용할 수 있어요.

    CLOSE_WAIT

    상대의 FIN을 받고 ACK는 보냈는데, 우리 애플리케이션이 close()를 안 한 상태예요. OS는 앱이 close할 때까지 기다려요. 쌓인다면 100% 우리 코드의 소켓 누수예요.

    RST

    정상 종료가 아닌 강제 리셋. 닫힌 포트로 데이터가 오거나, 애플리케이션이 데이터가 남은 소켓을 close하거나, 방화벽이 끊을 때 보내요. 받은 쪽은 "Connection reset by peer"예요.

    백엔드에서는 서버의 ss -tan | awk '{print $1}' | sort | uniq -c로 상태 분포를 봐요. TIME_WAIT가 수만 개면 짧은 연결을 너무 많이 만드는 것(HTTP 클라이언트에 keep-alive 안 씀, DB 커넥션 풀 없음), CLOSE_WAIT가 쌓이면 응답 스트림을 안 닫는 코드(HttpClient 응답 body를 소비하지 않음, try-with-resources 누락). "Connection reset"이 간헐적으로 나면 LB idle timeout과 keep-alive timeout 불일치를 의심하세요(5장).
    시니어 심화 본문은 "Connection reset"이 간헐적으로 나면 타임아웃 불일치를 의심하라고 했는데, 같은 원리로 배포할 때마다 에러가 몇 건씩 나는 이유도 설명돼요. 연결을 닫는 순서의 문제예요.

    상황

    배포는 무중단 롤링 배포인데, 배포할 때마다 502 에러와 "Connection reset"이 수십 건씩 나요. 트래픽이 많은 시간에 배포하면 수백 건이에요.

    깨지는 과정

    1. 배포 도구가 옛 서버에 종료 신호를 보내요. 서버가 바로 프로세스를 끝내요.
    2. 그 순간 처리 중이던 요청은 응답을 받지 못하고 끊겨요.
    3. 로드밸런서는 헬스 체크가 몇 번 실패한 뒤에야 이 서버가 빠졌다는 것을 알아요. 그 몇 초 동안 새 요청이 계속 죽은 서버로 가서 실패해요.
    4. 로드밸런서나 클라이언트가 이 서버와 맺어 둔 keep-alive 연결도 갑자기 끊겨요. 그 연결로 막 보내려던 요청은 "Connection reset"을 받아요.

    해결책: 닫는 순서를 지키기

    • 먼저 새 트래픽을 끊어요. 종료 신호를 받으면 준비 상태(readiness) 검사를 실패로 바꿔서, 로드밸런서가 이 서버를 대상에서 빼게 해요.
    • 그리고 기다려요. 로드밸런서나 쿠버네티스가 그 사실을 반영하는 데는 몇 초가 걸려요. 그동안에도 요청은 들어와요. 쿠버네티스에서는 preStop 훅에 몇 초의 sleep을 넣어 이 시간을 벌어요. 이 단계를 빼먹는 것이 가장 흔한 실수예요(쿠버네티스 챕터 7장).
    • 진행 중인 요청을 끝내요. 스프링 부트는 server.shutdown=graceful로 새 요청을 받지 않고 진행 중인 요청을 마칠 때까지 기다려요. 기다리는 최대 시간은 spring.lifecycle.timeout-per-shutdown-phase로 정해요.
    • keep-alive 연결은 정중하게 닫아요. 남은 연결에 오는 응답에 Connection: close를 붙여서, 클라이언트가 그 연결을 더 쓰지 않게 해요.
    • 전체 시간이 종료 유예 시간 안에 들어가게 해요. 쿠버네티스는 terminationGracePeriodSeconds(기본 30초)가 지나면 강제로 종료해요. "기다리기 + 요청 마무리"가 이보다 짧아야 해요.

    평소에도 비슷한 경쟁이 있어요. 서버가 유휴 연결을 닫는 순간 클라이언트가 그 연결로 요청을 보내면 reset이 나요. 클라이언트의 유휴 타임아웃을 서버보다 짧게 둬서, 연결을 닫는 쪽이 항상 클라이언트가 되게 하면 이 경쟁이 사라져요.

    운영에서 알아채는 법

    • 5xx 에러 그래프에 배포 시각을 겹쳐 봐요. 배포마다 짧은 봉우리가 있다면 종료 순서 문제예요.
    • 로드밸런서 로그에서 대상 서버의 연결이 끊겨 생긴 502와, 서버가 실제로 돌려준 5xx를 구분해서 세요.
    핵심 정리
    • FIN/ACK × 2, 각 방향 독립 종료
    • TIME_WAIT = 먼저 닫은 쪽, 정상, 많으면 연결 재사용으로 해결
    • CLOSE_WAIT = 우리 앱의 close 누락
    셀프 체크
    1. 서버에서 TIME_WAIT가 많다면 누가 연결을 먼저 닫고 있는 건가요? 그게 좋은가요?
    답 보기

    TIME_WAIT는 먼저 close한 쪽에 생기니, 서버가 먼저 닫고 있어요. HTTP 서버가 응답 후 연결을 닫는(Connection: close) 설정이거나 keep-alive timeout이 짧아서예요. 서버가 TIME_WAIT를 떠안으면 포트는 괜찮지만(서버 포트는 고정) 메모리와 소켓 테이블을 차지해요. 가능하면 클라이언트가 먼저 닫거나, keep-alive로 연결 수 자체를 줄이는 게 좋아요.

    2.5 IP와 이더넷 — 패킷 송신

    TCP 세그먼트가 IP 패킷이 되고 이더넷 프레임이 되어 케이블로

    IP 헤더와 캡슐화

    TCP 세그먼트 앞에 IP 헤더(출발/목적 IP, TTL, 프로토콜 번호, 체크섬)를 붙여 IP 패킷을 만들고, 그 앞에 이더넷 헤더(출발/목적 MAC)를 붙여 프레임을 만들어요. 각 계층은 아래 계층의 데이터일 뿐이에요.

    IP 주소와 서브넷

    IP 주소는 네트워크 부분 + 호스트 부분이에요. 10.0.1.5/24는 앞 24비트가 네트워크. 같은 네트워크면 직접(이더넷으로), 다르면 기본 게이트웨이(라우터)로 보내요. 이 판단을 라우팅 테이블로 해요(ip route).

    ARP: IP → MAC

    같은 LAN에서 프레임을 보내려면 상대의 MAC 주소가 필요해요. ARP로 "이 IP 가진 사람 MAC 알려줘"를 브로드캐스트하고 응답을 캐시해요. 다른 네트워크로 보낼 때는 게이트웨이의 MAC을 써요. MAC은 한 홉, IP는 끝에서 끝이에요.

    MTU와 단편화

    이더넷 프레임 최대 1500바이트(MTU). IP 패킷이 더 크면 쪼개야(fragmentation) 하는데, 비효율적이라 TCP는 처음부터 MSS = MTU − 40으로 맞춰요. 경로 중간에 MTU가 작은 구간이 있으면 Path MTU Discovery로 찾아요. VPN이나 터널링에서 MTU 문제로 "작은 요청은 되는데 큰 요청만 멈추는" 현상이 생겨요.

    UDP

    헤더 8바이트(포트, 길이, 체크섬)뿐. 연결, 순서, 재전송 없음. 그래서 빠르고 단순해요. DNS, 영상 통화(늦은 패킷은 버리는 게 나음), 게임, 그리고 QUIC(HTTP/3)가 UDP 위에 자체 신뢰성을 구현해요.

    백엔드에서는 도커 브리지 네트워크, 쿠버네티스 Pod 네트워크, VPC 서브넷과 라우팅 테이블, 보안 그룹이 전부 이 장의 개념이에요. "Pod에서 외부 DB로 연결이 안 된다"를 추적할 때 ip route, traceroute, tcpdump -i any port 3306이 기본 도구예요. 오버레이 네트워크(VXLAN)는 헤더를 더 붙여서 MTU가 1450 등으로 줄어들어요.
    시니어 심화 본문에서 오버레이 네트워크는 MTU가 줄어든다고 했는데, MTU 문제는 "작은 요청은 되는데 큰 응답만 멈추는" 아주 헷갈리는 증상으로 나타나요.

    상황

    쿠버네티스로 이전한 뒤, 주문 목록 API가 가끔 응답 없이 멈췄어요. 헬스 체크는 통과하고, 주문 상세 같은 작은 응답은 멀쩡했어요. 주문이 많은 회원의 목록처럼 응답이 큰 경우에만 멈췄어요. 외부 결제사와의 TLS 연결이 핸드셰이크 단계에서 멈추는 일도 있었어요.

    깨지는 과정

    1. MTU는 한 번에 보낼 수 있는 패킷의 최대 크기예요. 일반 이더넷은 1500바이트인데, 오버레이 네트워크(VXLAN)는 패킷을 한 번 더 감싸느라 약 50바이트를 써서 실제로는 1450바이트까지만 지나가요.
    2. 1500바이트 패킷을 받은 경로 중간의 장비는, "조각내지 말라"는 표시가 있으면 패킷을 버리고 "더 작게 보내라"는 ICMP 메시지를 보낸 쪽에 돌려줘야 해요. 보낸 쪽은 이것을 보고 크기를 줄여요(경로 MTU 탐색).
    3. 그런데 보안을 이유로 방화벽이 ICMP를 전부 막아 두면 이 메시지가 돌아오지 않아요. 보낸 쪽은 이유를 모른 채 같은 크기로 재전송하고, 패킷은 계속 사라져요.
    4. 연결 수립 패킷과 작은 요청, 작은 응답은 1450바이트보다 작아서 통과해요. 큰 응답과 인증서 체인이 담긴 TLS 핸드셰이크처럼 큰 패킷이 필요한 것만 멈춰요.

    "연결은 되고 헬스 체크도 통과하는데 특정 API만 응답이 안 온다"는 증상 때문에 애플리케이션 버그로 오해하고 시간을 많이 써요. VPN, 터널, 쿠버네티스 오버레이 네트워크에서 자주 나요.

    해결책

    • 경로가 받아 주는 최대 크기를 찾아요. ping -M do -s 1472 대상은 조각내기를 금지하고 1500바이트(1472 + 헤더 28) 패킷을 보내요. 실패하면 크기를 줄여 가며 통과하는 최대값을 찾아요.
    • 필요한 ICMP는 허용해요. "조각 필요"(ICMP type 3, code 4) 메시지는 막지 말아야 해요. ICMP를 전부 막는 것은 보안 이득보다 장애 위험이 커요.
    • MSS를 낮춰요. TCP 연결 수립 때 서로 알려 주는 최대 세그먼트 크기(MSS)를 경로 장비에서 줄이면(MSS 클램핑) 처음부터 작은 패킷으로 주고받아요.
    • 인터페이스 MTU를 맞춰요. 쿠버네티스 CNI 플러그인 설정에서 파드의 MTU를 오버레이에 맞게(예: 1450) 지정해요.
    • 리눅스의 MTU 탐색을 켜요. net.ipv4.tcp_mtu_probing=1이면 ICMP가 오지 않을 때도 커널이 크기를 줄여 보며 스스로 맞춰요.

    운영에서 알아채는 법

    • "응답 크기가 클 때만" 실패하거나 타임아웃이 난다면 MTU를 가장 먼저 의심해요. 응답 크기별로 실패율을 나눠 보면 경계가 1.4KB 근처에서 보여요.
    • 새로운 네트워크 구간(VPN, 클러스터 이전, 클라우드 간 연결)을 열 때마다 위의 ping 검사를 체크리스트에 넣어요.
    핵심 정리
    • 캡슐화: HTTP → TCP → IP → 이더넷
    • IP는 끝에서 끝, MAC은 한 홉. 라우팅 테이블로 직접/게이트웨이 결정, ARP로 MAC 찾기
    • MTU 1500, MSS 1460
    셀프 체크
    1. 패킷이 라우터를 지날 때 바뀌는 헤더와 안 바뀌는 헤더는?
    답 보기

    이더넷 헤더(MAC)는 홉마다 새로 붙여요(출발 = 라우터 MAC, 목적 = 다음 홉 MAC). IP 헤더의 출발/목적 IP는 그대로이고 TTL만 1 줄고 체크섬이 다시 계산돼요(NAT를 지나면 IP도 바뀌어요). TCP 헤더와 데이터는 그대로예요.

    3~4장 LAN과 인터넷

    3장 허브, 스위치, 라우터

    케이블을 떠난 프레임이 LAN 안에서 어떻게 전달되는가

    허브 → 스위치

    허브는 들어온 신호를 모든 포트로 그냥 복사해요(충돌 발생, 지금은 안 씀). 스위치는 프레임의 출발 MAC을 보고 "이 MAC은 이 포트"를 MAC 주소 테이블에 학습하고, 목적 MAC에 해당하는 포트로만 보내요. 모르는 MAC이면 전체에 보내요(flooding). 2계층(L2) 장비예요.

    라우터

    라우터는 IP 패킷을 봐요(L3). 이더넷 헤더를 떼고, 목적 IP를 라우팅 테이블에서 찾아(가장 긴 prefix 일치) 다음 홉과 출력 포트를 정하고, TTL을 1 줄이고, 새 이더넷 헤더를 붙여 보내요. TTL이 0이 되면 버리고 ICMP Time Exceeded를 돌려줘요(traceroute의 원리).

    라우팅 테이블

    목적 네트워크      넥스트 홉       인터페이스
10.0.1.0/24       직접 연결       eth0
10.0.2.0/24       10.0.1.254     eth0
0.0.0.0/0         10.0.1.1       eth0      ← 기본 경로

    라우터끼리는 라우팅 프로토콜(OSPF, BGP)로 경로를 교환해요. 인터넷 전체 경로는 BGP로 ISP(AS)끼리 교환해요.

    NAT

    사설 IP(10.x, 192.168.x)는 인터넷에서 못 써요. 라우터가 나가는 패킷의 출발 IP·포트를 공인 IP·새 포트로 바꾸고 변환 테이블에 기록, 돌아오는 패킷을 역변환해요. 밖에서 안으로 먼저 연결할 수 없어요(포트 포워딩 필요).

    백엔드에서는 쿠버네티스 Service(ClusterIP)는 iptables/IPVS로 하는 NAT이에요. NodePort, 클라우드 NAT Gateway, 도커의 -p 8080:80 전부 NAT. NAT 테이블은 연결 추적(conntrack)에 의존하고 크기 한계가 있어요. 트래픽 급증 시 nf_conntrack: table full, dropping packet이 나면 이거예요. 또 NAT 뒤의 유휴 연결은 일정 시간 후 테이블에서 지워져서, 오래 유휴한 DB 연결이 갑자기 끊기는 이유가 돼요(TCP keepalive로 방지).
    핵심 정리
    • 스위치 = MAC 테이블 학습(L2), 라우터 = 라우팅 테이블(L3)
    • 가장 긴 prefix 일치, 기본 경로 0.0.0.0/0, TTL
    • NAT = 주소 변환 + 연결 추적, 유휴 연결 소멸 주의
    셀프 체크
    1. 스위치와 라우터의 역할 차이를 한 문장으로.
    2. NAT 뒤에서 오래 유휴한 TCP 연결이 끊기는 이유와 대책은?
    답 보기

    1. 스위치는 같은 네트워크 안에서 MAC으로 프레임을 전달하고, 라우터는 다른 네트워크 사이에서 IP로 패킷을 전달해요.

    2. NAT 장비가 유휴 연결의 변환 엔트리를 타임아웃으로 지워서, 이후 패킷이 매핑을 못 찾고 버려지거나 RST를 받아요. 대책: TCP keepalive(SO_KEEPALIVE, 커널 tcp_keepalive_time을 타임아웃보다 짧게) 또는 애플리케이션 레벨 ping, 커넥션 풀의 유휴 검증/최대 수명 설정.

    4장 액세스 회선과 프로바이더

    인터넷은 ISP들의 연합이다 (짧게)

    인터넷의 구조

    인터넷은 하나의 네트워크가 아니라 수만 개의 AS(자율 시스템), 즉 ISP·기업·클라우드의 네트워크가 서로 연결된 집합이에요. AS끼리는 BGP로 "나는 이 IP 대역에 갈 수 있다"를 광고하고, IX(인터넷 교환점)에서 서로 직접 연결(피어링)해요.

    지연의 물리적 한계

    빛의 속도는 광섬유에서 약 200,000km/s. 서울-미국 서부 왕복 약 18,000km = 최소 90ms. 라우터 처리, 큐잉이 더해져 실제 150ms 정도예요. 이 RTT는 어떤 최적화로도 줄일 수 없어요. 줄이려면 가까이 두는 것(CDN, 리전 선택, 엣지)뿐이에요.

    경로는 비대칭일 수 있다

    가는 길과 오는 길이 다를 수 있어요. BGP는 각 AS가 자기 정책으로 경로를 고르기 때문이에요. 그래서 한쪽 방향만 느린 현상이 생겨요.

    백엔드에서는 리전 간 호출(서울 ↔ 미국 서부)은 RTT 150ms × 왕복 횟수예요(미국 동부면 RTT가 200ms 가까이 돼요). 요청 하나에 DB 왕복이 10번이면 1.5초. 리전 간 동기 호출을 피하고, 데이터를 리전 안에 두고, 꼭 필요하면 왕복 횟수를 줄여야(배치) 해요. 클라우드의 가용 영역(AZ) 간은 1~2ms, 같은 AZ는 0.1ms대예요. 이 차이가 아키텍처를 결정해요.
    핵심 정리
    • 인터넷 = AS들의 BGP 연합, 피어링
    • RTT는 물리 한계, 줄이려면 거리를 줄이거나 왕복 횟수를 줄이거나
    셀프 체크
    1. 서울의 API 서버가 미국의 DB를 쓰면 요청당 최소 지연은 어떻게 계산하나요?
    답 보기

    RTT(약 150ms) × DB 왕복 횟수. 연결 수립까지 포함하면 TCP 1 RTT + TLS 1~2 RTT가 더해져요. 커넥션 풀로 연결 비용은 없애도 쿼리당 150ms는 못 피해요. 쿼리 5번이면 750ms.

    5장 서버 측 LAN — 방화벽, 캐시, 로드밸런서

    5.1 방화벽

    패킷 필터링으로 들어오는 트래픽을 거른다

    패킷 필터링

    방화벽은 패킷의 IP, 포트, 프로토콜, 방향, TCP 플래그를 보고 통과/차단을 결정해요. 규칙 예: "외부 → 서버:443 허용, 외부 → 서버:22는 사무실 IP만, 나머지 거부". 내부에서 시작한 연결의 응답은 허용해야 하니, 상태 기반(stateful) 방화벽은 연결을 추적해서 ESTABLISHED 연결의 패킷을 자동 허용해요.

    클라우드의 방화벽

    • 보안 그룹(Security Group): 인스턴스 단위, stateful, 허용 규칙만
    • 네트워크 ACL: 서브넷 단위, stateless(응답도 명시 허용 필요), 허용/거부
    • 쿠버네티스 NetworkPolicy: Pod 단위

    방화벽이 못 막는 것

    허용된 포트(443)로 들어오는 애플리케이션 레벨 공격(SQL 인젝션, XSS)은 못 막아요. 그건 WAF(웹 애플리케이션 방화벽, L7)가 HTTP 내용을 보고 거르거나 애플리케이션이 막아야 해요.

    백엔드에서는 "연결이 안 된다"의 절반은 보안 그룹이에요. 확인 순서: (1) 서버에서 포트가 listen 중인가(ss -ltn), (2) 0.0.0.0에 바인딩됐나 127.0.0.1에만 됐나, (3) 보안 그룹/NACL이 출발 IP와 포트를 허용하나, (4) 중간에 NAT·프록시가 있나. nc -zv host port, telnet으로 각 지점에서 확인해요. 그리고 방화벽이 유휴 연결을 끊는(idle timeout) 것도 흔해요. DB 연결이 "갑자기" 죽는 또 다른 원인이에요.
    시니어 심화 본문은 연결이 안 될 때 인바운드 규칙을 확인하라고 했는데, 보안 관점에서 더 자주 비어 있는 것은 아웃바운드 통제예요.

    상황

    상품 이미지 URL을 받아 썸네일을 만드는 API에 취약점이 있었어요. 공격자가 그 서버에서 임의의 코드를 실행했고, 서버의 환경 변수에 있던 DB 접속 정보와 클라우드 키를 자기 서버로 보냈어요. 인바운드 규칙은 철저했지만 아웃바운드는 전부 열려 있었어요.

    왜 아웃바운드가 중요한가

    1. 서버가 뚫린 뒤에 공격자가 하는 일은 대부분 밖으로 나가는 연결이에요. 데이터를 공격자 서버로 보내고, 추가 도구를 내려받고, 명령을 받을 서버에 접속해요.
    2. 아웃바운드가 전부 열려 있으면, 침입 하나가 곧바로 데이터 유출로 이어져요.
    3. 반대로 아웃바운드가 막혀 있으면 공격자가 서버 안에 들어와도 할 수 있는 일이 크게 줄어요. 침입을 막는 방어선이 실패했을 때의 두 번째 방어선이에요.

    해결책

    • 기본 거부, 필요한 목적지만 허용해요. 주문 서버가 밖으로 나갈 곳은 결제사, 문자 발송사, 패키지 저장소 정도예요. 그 목록만 허용해요.
    • 도메인으로 허용하려면 프록시를 써요. 외부 API의 IP는 자주 바뀌어서 IP 목록으로 관리하기 어려워요. 그래서 아웃바운드를 전용 프록시로만 나가게 하고, 프록시에서 도메인 단위로 허용해요. 프록시 로그가 "어떤 서버가 어디로 나갔는지"의 기록이 돼요.
    • 쿠버네티스에서는 NetworkPolicy의 egress 규칙을 써요. 기본 정책을 거부로 두고 파드마다 필요한 목적지만 열어요.
    • 클라우드 메타데이터 주소를 막아요. 사용자가 준 URL을 서버가 호출하는 기능은 169.254.169.254 같은 내부 주소로 요청을 보내 클라우드 키를 훔치는 공격(SSRF, 보안 챕터 8장)에 쓰여요. 애플리케이션 검증과 함께 네트워크에서도 막아요.
    • 내부망에서는 DROP보다 REJECT를 고려해요. 패킷을 버리면(DROP) 클라이언트는 연결 타임아웃까지 기다리며 스레드를 붙잡고, 거절하면(REJECT) 즉시 실패해요. 외부에서 오는 스캔에는 DROP이 정보를 덜 주지만, 내부 서비스 사이에서는 빠른 실패가 장애 전파를 줄여요.

    대가: 새 외부 연동을 붙일 때마다 허용 목록을 바꿔야 해요. 이 절차가 너무 느리면 개발자가 우회로를 찾으니, 요청하고 반영되기까지의 시간을 짧게 유지하세요.

    운영에서 알아채는 법

    • 프록시나 방화벽의 아웃바운드 거부 로그를 모니터링해요. 평소 없던 목적지로 가려는 시도는 침입의 초기 신호일 수 있어요.
    • DNS 조회 로그도 남겨요. 데이터를 DNS 질의에 실어 내보내는 방법도 있어서, 이상하게 긴 서브도메인 조회가 많다면 의심해요.
    핵심 정리
    • 패킷 필터링: IP·포트·방향, stateful은 응답 자동 허용
    • 보안 그룹(stateful) vs NACL(stateless)
    • L7 공격은 WAF 또는 애플리케이션 책임
    셀프 체크
    1. stateful과 stateless 방화벽의 차이가 규칙 작성에 어떤 영향을 주나요?
    답 보기

    stateful은 나가는 연결만 허용하면 그 응답은 자동 허용돼요. stateless는 응답 패킷(서버 → 클라이언트 임시 포트 1024~65535)도 명시적으로 허용 규칙을 써야 해요. NACL에서 응답 포트 범위를 빼먹으면 요청은 가는데 응답이 안 와요.

    5.2 로드밸런서

    서버 한 대로 부족할 때 — 분산의 원리와 함정

    왜 필요한가

    DNS 라운드로빈으로 여러 IP를 돌려줄 수도 있지만, 죽은 서버를 빼지 못하고 캐시 때문에 즉시 반영이 안 돼요. 로드밸런서는 하나의 IP로 받아 뒤의 서버들에 나눠 주고, 헬스 체크로 죽은 서버를 자동으로 빼요.

    예AWS NLB, LVS, HAProxy(tcp 모드)AWS ALB, Nginx, Envoy, HAProxy(http 모드)

    분산 알고리즘

    라운드로빈, 가중 라운드로빈, 최소 연결(least connections), 해시(출발 IP나 URL 기준으로 같은 서버로). 응답 시간 기반도 있어요.

    헬스 체크

    LB가 주기적으로 각 서버에 요청해(TCP 연결 또는 GET /health) 실패가 N번 연속이면 뺐다가, 성공이 M번 연속이면 넣어요. 헬스 체크 엔드포인트가 DB까지 확인하면 DB 장애 때 모든 서버가 동시에 빠져 전체 장애가 돼요. 자기 자신의 생존(liveness)과 트래픽 받을 준비(readiness)를 구분하세요.

    Sticky session

    세션을 서버 메모리에 두면 같은 사용자가 같은 서버로 가야 해요. LB가 쿠키를 심어 고정해요. 부하가 쏠리고 서버가 죽으면 세션이 날아가요. 세션을 Redis 등 외부로 빼고 서버를 무상태로 만드는 게 정석이에요.

    타임아웃 불일치 (가장 흔한 사고)

    LB는 뒤 서버와의 연결을 재사용하려고 유휴 상태로 열어 둬요(idle timeout, ALB 기본 60초). 서버의 keep-alive timeout이 더 짧으면(톰캣 기본 60초, Node 기본 5초!) 서버가 먼저 닫고, LB는 모르고 그 연결로 요청을 보내 502가 나요. 규칙: 서버 keep-alive timeout > LB idle timeout.

    백엔드에서는 LB가 TLS를 종료하면 서버는 HTTP를 받아서 request.isSecure()가 false이고, 클라이언트 IP는 LB IP로 보여요. X-Forwarded-For, X-Forwarded-Proto 헤더를 읽어야 해요(Spring ForwardedHeaderFilter, Express trust proxy). XFF는 클라이언트가 위조할 수 있으니 LB가 붙인 마지막 값만 믿어야 해요. 배포 시 "connection draining"(기존 요청이 끝날 때까지 기다린 후 빼기)을 설정하지 않으면 배포마다 에러가 나요. 쿠버네티스는 readiness probe + preStop hook이 이 역할이에요.
    시니어 심화 본문은 분산 알고리즘을 소개했는데, 실제로 부하가 고르게 나뉘지 않는 가장 흔한 이유는 알고리즘보다 새로 뜬 인스턴스가 준비되지 않은 것이에요.

    상황

    트래픽이 몰리자 오토스케일링이 서버를 10대에서 15대로 늘렸어요. 그런데 늘린 직후 오히려 p99 응답 시간이 두 배로 나빠졌고, 몇 분 뒤에야 내려왔어요.

    깨지는 과정

    1. 방금 뜬 JVM 서버는 아직 JIT 컴파일이 안 돼서 코드가 느리게 실행돼요. 커넥션 풀과 로컬 캐시도 비어 있어요(JVM 챕터 2장).
    2. 준비 상태 검사는 "요청을 받을 수 있는가"만 보니 바로 통과해요. 로드밸런서는 새 서버에 곧바로 제 몫의 트래픽을 보내요.
    3. 새 서버 5대는 몇 분 동안 평소보다 몇 배 느리게 응답해요. 전체 요청의 1/3이 이 서버들로 가니 p99가 크게 나빠져요.
    4. 최소 연결 수 알고리즘이라면 더 나빠요. 새 서버는 연결이 0개라서 가장 한가해 보이고, 새 요청이 한꺼번에 몰려요.

    해결책

    • 트래픽을 조금씩 늘려 줘요. 로드밸런서의 점진적 투입(slow start) 기능은 새 대상에 처음 몇십 초 동안 트래픽을 조금씩 늘려 보내요. AWS ALB의 대상 그룹 설정이나 Envoy의 slow start 모드가 이것이에요.
    • 준비 전에 미리 데워요. 준비 상태 검사를 통과시키기 전에 주요 API를 내부에서 수백 번 호출해서 JIT 컴파일, 커넥션 풀, 캐시를 채워요. 쓰기가 일어나지 않는 조회 API로 해요.
    • 오토스케일링은 일찍 시작해요. 새 서버가 제 몫을 하기까지 몇 분이 걸리니, CPU 80%가 아니라 60%에서 늘리기 시작해요.
    • 오래 사는 연결은 수명을 둬요. WebSocket이나 gRPC처럼 한 번 맺으면 오래 쓰는 연결은, 서버를 늘려도 옛 서버에 붙어 있어서 새 서버로 퍼지지 않아요. 서버가 연결의 최대 수명(gRPC 서버의 MAX_CONNECTION_AGE)을 정해 주기적으로 다시 맺게 해야 새 서버로 퍼져요.

    운영에서 알아채는 법

    • 응답 시간을 서버별로, 그리고 서버가 뜬 지 몇 분 됐는지별로 나눠 봐요. 새 서버만 느리다면 워밍업 문제예요.
    • 스케일 아웃 이벤트 시각을 p99 그래프에 겹쳐 봐요. 늘린 직후 나빠지는 모양이 반복되면 이 패턴이에요.
    • 오래 사는 연결을 쓴다면 서버별 연결 수를 봐요. 새 서버의 연결 수가 오래도록 적다면 수명 설정이 필요해요.
    핵심 정리
    • L4 = 연결 단위·빠름, L7 = 요청 단위·똑똑함
    • 헬스 체크는 자기 생존만, 의존성 상태를 넣으면 연쇄 장애
    • 서버 keep-alive > LB idle timeout, XFF로 원래 클라이언트 정보
    셀프 체크
    1. Node.js 서버를 ALB 뒤에 뒀더니 간헐적 502가 나요. 원인과 해결은?
    2. WebSocket 서비스에 L7 LB를 쓸 때 주의점은?
    답 보기

    1. Node의 keep-alive timeout 기본 5초 < ALB idle 60초. Node가 먼저 닫은 연결로 ALB가 요청을 보내 502. server.keepAliveTimeout = 65000(ALB보다 길게), headersTimeout도 그보다 길게 설정.

    2. WebSocket은 HTTP Upgrade 후 긴 TCP 연결이라 L7 LB가 Upgrade를 지원해야 하고, idle timeout이 연결을 끊지 않도록 길게 하거나 주기적 ping을 보내야 해요. 연결이 한 서버에 고정되므로 서버 간 메시지 전달은 Redis Pub/Sub 같은 별도 채널이 필요해요.

    5.3 캐시 서버, 리버스 프록시, CDN

    서버 앞에서 요청을 대신 처리하는 것들

    프록시의 두 방향

    • 포워드 프록시: 클라이언트 쪽에 있어요. 회사 네트워크에서 외부로 나갈 때 거치는 것. 클라이언트를 숨기고, 접근 제어, 캐시.
    • 리버스 프록시: 서버 쪽에 있어요. 클라이언트는 프록시를 서버로 알아요. 서버를 숨기고, TLS 종료, 캐시, 압축, 정적 파일, 로드밸런싱. Nginx가 대표예요.

    리버스 프록시가 서버를 보호하는 방법

    느린 클라이언트(모바일)가 요청을 천천히 보내면 애플리케이션 스레드가 그만큼 묶여요. Nginx는 요청 전체를 받아서(buffering) 한 번에 앱에 넘기고, 응답도 받아서 느린 클라이언트에 천천히 보내요. 앱 스레드는 빨리 풀려요. 이벤트 루프 기반이라 수만 개 유휴 연결을 싸게 들고 있어요.

    캐시 서버

    같은 URL의 응답을 저장했다가 돌려줘요. HTTP 캐시 헤더(부록 C)를 따라요. 프록시 캐시(Varnish, Nginx cache)는 서버 바로 앞에서, CDN은 사용자 가까이에서 캐시해요.

    CDN

    전 세계 엣지 서버에 콘텐츠를 캐시해요. 사용자는 DNS(GeoDNS 또는 Anycast)로 가장 가까운 엣지에 연결돼요. 정적 파일(이미지, JS)은 물론 TTL이 짧은 API 응답도 캐시할 수 있어요. TLS 종료를 엣지에서 하면 handshake RTT가 짧아져요. 엣지에서 origin까지는 CDN이 최적화된 경로와 keep-alive 연결로 가요.

    캐시 무효화: 파일을 바꿨는데 CDN이 옛것을 주는 문제. 파일명에 해시를 넣거나(app.3f2a1.js, 영원히 캐시), purge API를 호출해요.

    백엔드에서는 앱 서버 앞에 Nginx를 두는 이유: TLS, 정적 파일, gzip, 버퍼링, 요청 크기 제한, rate limit, 그리고 앱이 재시작하는 동안 503 페이지. 쿠버네티스 Ingress 컨트롤러가 그 역할이에요. API 응답을 CDN에 캐시하려면 Cache-Control: public, max-age=60과 Vary 헤더를 정확히 써야 하고, 인증된 응답은 private로 막아야 해요. 안 그러면 A의 개인 정보가 B에게 가요.
    시니어 심화 본문은 캐시 헤더 실수가 개인정보 유출로 이어진다고 했는데, 캐시는 공격자가 일부러 오염시키거나 속일 수도 있어요.

    상황 1: 캐시 오염

    상품 페이지는 CDN에 캐시돼요. 애플리케이션은 X-Forwarded-Host 헤더를 보고 페이지 안의 이미지와 스크립트 주소를 만들어요. 어느 날 상품 페이지의 스크립트가 낯선 도메인에서 로드되고 있다는 신고가 들어왔어요.

    1. CDN은 요청의 일부(주소와 Vary에 적힌 헤더)만 캐시 키로 써요. X-Forwarded-Host는 키에 없어요.
    2. 공격자가 이 헤더에 자기 도메인을 넣어 상품 페이지를 요청해요. 애플리케이션은 공격자 도메인의 스크립트를 가리키는 페이지를 만들어요.
    3. CDN은 그 응답을 "상품 페이지"로 캐시해요. 그 뒤로 같은 주소를 요청한 모든 사용자가 공격자의 스크립트를 실행하는 페이지를 받아요.

    원칙: 캐시 키에 없는 입력은 응답에 반영하지 않아요. 프록시가 붙이는 헤더는 신뢰할 수 있는 프록시에서 덮어쓰고, 애플리케이션은 허용 목록에 있는 호스트만 받아들여요. 링크 주소는 요청 헤더가 아니라 설정값으로 만들어요.

    상황 2: 캐시 속이기

    CDN이 "확장자가 .css, .js, .png인 주소는 캐시"하도록 설정돼 있어요. 그리고 애플리케이션은 /account/profile/anything.css처럼 뒤에 붙은 경로를 무시하고 /account/profile 페이지를 돌려줘요.

    1. 공격자가 로그인한 사용자에게 /account/profile/x.css 링크를 클릭하게 만들어요.
    2. 애플리케이션은 그 사용자의 프로필 페이지를 돌려주고, CDN은 확장자만 보고 그것을 캐시해요.
    3. 공격자가 같은 주소를 요청하면 캐시된 남의 프로필 페이지를 받아요.

    원칙: 캐시 여부는 확장자가 아니라 응답의 Cache-Control로 결정하게 해요. 개인화된 응답에는 항상 Cache-Control: private이나 no-store를 붙이고, 애플리케이션은 알 수 없는 경로를 관대하게 받아 주지 말고 404로 거절해요.

    운영에서 알아채는 법

    • CDN 로그에서 같은 캐시 키에 대해 응답 크기나 해시가 갑자기 바뀐 경우를 찾아요.
    • 로그인이 필요한 경로가 CDN에서 캐시 적중(HIT)으로 응답된 기록이 있다면 즉시 조사해요. 정상이라면 0이어야 해요.
    • 주기적으로 의심스러운 헤더와 경로를 붙인 요청을 보내 응답이 바뀌는지 검사하는 보안 점검을 해요.
    핵심 정리
    • 리버스 프록시 = 서버 앞, TLS·캐시·버퍼링·보호
    • CDN = 사용자 가까운 캐시, 파일명 해시로 무효화
    • 캐시 헤더 실수는 개인정보 유출
    셀프 체크
    1. Nginx의 요청 버퍼링이 애플리케이션 서버를 어떻게 보호하나요?
    답 보기

    느린 클라이언트가 요청 본문을 몇 초에 걸쳐 보내도 Nginx가 다 받은 뒤 앱에 한 번에 넘겨요. 앱 스레드는 요청 수신에 시간을 쓰지 않아요. 응답도 Nginx가 받아 두고 천천히 보내서 앱 스레드가 즉시 다음 요청을 처리해요. Slowloris 같은 공격도 Nginx 수준에서 흡수돼요.

    6장 웹 서버에 도착하여 응답이 돌아온다

    6.1 서버의 소켓 — listen, accept, 그리고 동시 처리 모델

    서버 프로그램이 연결을 받는 구조

    서버 소켓 호출 순서

    1. socket(): 소켓 생성
    2. bind(fd, 0.0.0.0:8080): 포트 지정. 127.0.0.1에 바인딩하면 외부에서 못 들어와요.
    3. listen(fd, backlog): 접속 대기 상태로
    4. accept(fd): 연결이 오면 새 소켓(fd)을 돌려줘요. 원래 listen 소켓은 계속 대기해요.
    5. 새 fd로 read/write, 끝나면 close

    연결마다 fd가 하나씩 생겨요. 그래서 동시 연결 수 = fd 수이고 ulimit -n에 걸려요.

    동시 처리 모델

    모델동작예특징
    프로세스 per 연결accept 후 fork옛 Apache prefork격리 좋음, 무거움
    스레드 per 연결/요청스레드풀에서 하나 할당톰캣, Apache worker단순, 블로킹 I/O OK, 스레드 수 = 동시 요청 한계
    이벤트 루프epoll로 준비된 소켓만 처리Nginx, Node.js, Netty연결당 비용 작음, 블로킹 금지
    하이브리드이벤트 루프가 I/O, 워커 스레드가 처리톰캣 NIO, Jetty연결은 많이, 처리는 스레드로

    톰캣 NIO: acceptor 스레드가 accept, poller 스레드가 epoll로 데이터 도착을 감지, 데이터가 오면 워커 스레드(기본 200)에 넘겨 처리해요. 그래서 keep-alive 유휴 연결 1만 개를 들고 있어도 스레드는 200개면 돼요.

    스레드풀 크기

    워커 스레드 수는 "동시에 처리 중인 요청 수"의 상한이에요. 모두 DB를 기다리고 있으면 새 요청은 큐에서 대기해요. 요청당 DB 대기가 길면 스레드를 늘리거나, 비동기로 바꾸거나, 가상 스레드를 써요. 하지만 DB 커넥션 풀이 10개면 스레드 200개는 의미가 없어요. 병목은 늘 가장 좁은 곳이에요.

    백엔드에서는 성능 문제를 볼 때 (1) accept 큐 넘침(연결 실패), (2) 워커 스레드 고갈(연결은 되는데 응답 지연), (3) DB 커넥션 풀 고갈(스레드는 있는데 풀 대기), (4) DB 자체 느림을 구분해야 해요. 각각 ss -ltn, 스레드 덤프/활성 스레드 메트릭, HikariCP pending 메트릭, 슬로우 쿼리 로그로 봐요. 그리고 server.tomcat.threads.max, accept-count, max-connections가 각각 워커 수, backlog, poller가 들고 있을 최대 연결 수예요.
    시니어 심화 본문은 스레드풀 크기가 동시 처리 상한이라고 했는데, 풀을 키울 때 놓치기 쉬운 것은 이용률이 높아질수록 지연이 비선형으로 커진다는 사실이에요.

    상황

    주문 API는 요청 하나에 평균 50ms가 걸리고, 피크 때 초당 180건이 들어와요. 스레드 10개면 초당 200건을 처리할 수 있으니 "충분하다"고 계산했어요. 실제 피크 때 평균 응답 시간은 500ms였고, p99는 2초가 넘었어요.

    깨지는 과정

    1. 초당 180건 ÷ 처리 능력 200건이면 이용률은 90%예요. 평균으로는 감당할 수 있어요.
    2. 그런데 요청은 고르게 오지 않아요. 어떤 100ms에는 5건, 다음 100ms에는 30건이 와요. 몰린 순간에는 줄이 생겨요.
    3. 한가한 순간에는 놀고 있던 스레드가 그 줄을 빨리 해소하지만, 이용률이 높으면 한가한 순간 자체가 드물어요. 줄이 해소되기 전에 다음 몰림이 와요.
    4. 가장 단순한 대기열 모델에서 요청이 머무는 시간은 "처리 시간 ÷ (1 − 이용률)"이에요. 이용률 50%면 처리 시간의 2배, 80%면 5배, 90%면 10배예요(성능 분석 챕터 7장). 50ms가 500ms가 된 이유예요.

    이용률이 100%에 가까워질수록 지연은 끝없이 커져요. 그래서 "평균 처리 시간 × 초당 요청 수"로 딱 맞는 스레드 수를 계산하면, 평균은 맞아도 꼬리 지연에서 무너져요.

    해결책

    • 평균 부하에서 이용률 50~70%를 목표로 잡아요. 위 예라면 피크 초당 180건을 이용률 60%로 받으려면 초당 300건, 즉 스레드 15개가 필요해요. 스레드를 늘리면 커넥션 풀과 DB 용량도 같이 봐야 해요.
    • 그 이상의 부하는 빠르게 거절해요. 이용률이 90%를 넘는 구간에서는 요청을 더 받아도 모두가 느려질 뿐이에요. 대기열 길이나 동시 처리 수에 상한을 두고, 넘으면 즉시 503을 돌려주는 편이 받아들인 요청의 응답 시간을 지켜요.
    • 처리 시간의 편차를 줄여요. 대부분 10ms인데 가끔 2초짜리 요청(큰 엑셀 다운로드 같은)이 섞이면 줄이 훨씬 길어져요. 느린 요청은 별도 풀이나 별도 서버로 분리해요.

    운영에서 알아채는 법

    • 스레드 풀의 활성 스레드 수 ÷ 최대 스레드 수를 이용률 지표로 남겨요. 이용률이 70%를 넘는 시간대에 p99가 함께 오르는지 봐요.
    • 응답 시간을 "대기 시간"과 "처리 시간"으로 나눠 기록할 수 있다면, 처리 시간은 그대로인데 대기 시간만 늘 때가 바로 이 상황이에요.
    핵심 정리
    • socket → bind → listen → accept(새 fd) → read/write
    • 스레드 per 요청 vs 이벤트 루프 vs 하이브리드(톰캣 NIO)
    • 워커 스레드 = 동시 처리 상한, 병목은 가장 좁은 곳
    셀프 체크
    1. 톰캣 NIO가 스레드 200개로 유휴 연결 1만 개를 유지할 수 있는 이유는?
    답 보기

    연결과 처리를 분리했기 때문이에요. 유휴 연결은 poller 스레드 하나가 epoll로 감시만 하고, 데이터가 실제로 도착한 연결만 워커 스레드에 넘겨요. 스레드는 "요청을 처리하는 동안"만 점유돼요.

    6.2 응답이 브라우저로 돌아온다 — 전체 흐름 복습

    "URL 입력부터 화면까지"를 한 번에

    전체 흐름

    1. 브라우저: URL 파싱, HSTS 확인, 캐시 확인(있으면 끝)
    2. DNS: 리졸버 → 재귀 서버(캐시) → 루트/TLD/권한 서버 → IP
    3. TCP: socket, connect → 3-way handshake (1 RTT)
    4. TLS: ClientHello/ServerHello, 인증서 검증, 키 교환 (TLS 1.3은 1 RTT)
    5. HTTP 요청: write → 송신 버퍼 → MSS로 분할 → IP/이더넷 캡슐화 → 스위치 → 라우터들(BGP 경로) → 서버 측 LAN
    6. 서버 측: 방화벽 → CDN/LB(TLS 종료, 헬스 체크된 서버로) → 리버스 프록시 → 앱 서버(accept 큐 → poller → 워커 스레드)
    7. 애플리케이션: 라우팅, 인증, 비즈니스 로직, DB(커넥션 풀 → 쿼리 → 결과), 캐시
    8. HTTP 응답: write → 역순으로 돌아감. cwnd에 따라 여러 RTT에 걸쳐
    9. 브라우저: 응답 파싱, 캐시 저장, HTML 파싱 → 추가 리소스 요청(keep-alive 재사용, HTTP/2 멀티플렉싱) → 렌더링

    지연이 쌓이는 곳

    구간전형적 지연줄이는 법
    DNS0~100ms캐시, TTL, DNS prefetch
    TCP handshake1 RTTkeep-alive, HTTP/2, QUIC(0-RTT)
    TLS handshake1~2 RTTTLS 1.3, 세션 재개, CDN 엣지 종료
    요청 전송 + 서버 처리앱에 달림DB 왕복 줄이기, 캐시, 비동기
    응답 전송크기/RTT에 비례, slow start압축, 크기 줄이기, 연결 재사용
    백엔드에서는 "API가 느리다"를 들으면 어느 구간인지 먼저 나눠야 해요. curl -w "@format.txt"로 time_namelookup, time_connect, time_appconnect(TLS), time_starttransfer(TTFB), time_total을 구간별로 보세요. TTFB가 크면 서버, total − TTFB가 크면 응답 크기/네트워크예요. 브라우저 DevTools의 Timing 탭도 같은 구간을 보여줘요.
    시니어 심화 본문은 curl -w로 구간별 시간을 재라고 했는데, 운영에서는 서버가 재는 지연과 사용자가 겪는 지연이 다르다는 점이 더 중요해요.

    상황

    세일 때 고객센터에 "결제 페이지가 너무 느리다"는 문의가 쏟아졌어요. 그런데 API 서버의 응답 시간 대시보드는 p99 120ms로 평소와 같았어요. 팀은 "서버는 정상"이라고 판단했어요.

    깨지는 과정

    1. 서버의 응답 시간 지표는 요청이 애플리케이션 코드에 도착한 순간부터 재요.
    2. 그 전에 쓴 시간은 빠져 있어요. accept 큐에서 기다린 시간(2.1 시니어), 톰캣 스레드가 없어서 작업 큐에서 기다린 시간, 로드밸런서 안에서 기다린 시간, GC로 프로세스가 멈춰서 요청을 받지 못한 시간이에요.
    3. 과부하일수록 이 바깥 구간이 커져요. 앱 안의 처리 시간은 그대로인데, 문 앞에서 기다리는 시간이 늘어요.
    4. 그래서 대시보드는 정상인데 사용자는 느린 상황이 생겨요. 서버 지표만 믿으면 가장 심한 순간을 놓쳐요.

    부하 테스트 도구에도 비슷한 함정이 있어요. 많은 도구는 응답을 받은 뒤에 다음 요청을 보내기 때문에, 서버가 느려지면 요청을 덜 보내고, 느렸던 구간의 측정값도 적게 남아요. 이것을 coordinated omission이라고 해요. 결과적으로 부하 테스트의 p99가 실제보다 훨씬 좋게 나와요. 정해진 속도로 요청을 보내고 원래 보냈어야 할 시각부터 시간을 재는 도구(wrk2, k6의 constant-arrival-rate 실행기)를 써요.

    해결책: 여러 지점에서 재기

    • 로드밸런서의 시간과 비교해요. 로드밸런서 접근 로그에는 대상 서버의 응답 시간과 전체 처리 시간이 따로 남아요. nginx라면 $request_time과 $upstream_response_time이에요. 둘의 차이가 "앱 바깥에서 쓴 시간"이에요.
    • 앱 안에서도 대기 시간을 재요. 요청이 로드밸런서를 지난 시각을 헤더(X-Request-Start)로 붙이게 하고, 앱이 처리를 시작할 때 그 차이를 지표로 남기면 큐 대기 시간이 보여요.
    • 밖에서 재요. 외부에서 주기적으로 주요 API를 호출하는 합성 모니터링과, 실제 사용자의 브라우저나 앱에서 재는 실사용자 측정(RUM)이 최종 기준이에요. 서버 지표가 정상인데 이 값이 나쁘면 문제는 서버 바깥이나 문 앞에 있어요.
    • GC 멈춤도 지표로 남겨요. 멈춘 동안 들어온 요청은 앱 지표에 짧게 잡히지만 사용자에게는 멈춘 시간만큼 늦어요.

    운영에서 알아채는 법

    • 대시보드에 서버 응답 시간, 로드밸런서 응답 시간, 외부 측정 응답 시간을 한 그래프에 겹쳐 둬요. 셋이 벌어지는 순간이 문 앞에서 기다리는 순간이에요.
    • 고객 문의와 서버 지표가 어긋날 때는 서버 지표가 틀렸을 가능성을 먼저 의심해요.
    핵심 정리
    • DNS → TCP → TLS → HTTP → LB/프록시 → 앱 → DB → 역순
    • 연결 수립만 2~3 RTT, 재사용이 핵심
    • 지연은 구간별로 나눠서 측정
    셀프 체크
    1. "브라우저에 URL을 입력하면?"을 끊기지 않고 3분 안에 설명해보세요. 각 단계에서 장애가 나면 사용자가 보는 증상도 함께.
    답 보기

    위 9단계를 따라가세요. 증상 예: DNS 실패 → "사이트를 찾을 수 없음", TCP 실패 → "연결 거부/시간 초과", TLS 실패 → 인증서 경고, LB 뒤 서버 전멸 → 502/503, 앱 느림 → 로딩 스피너만 오래, 응답 전송 중 끊김 → 일부만 렌더링.

    부록 — HTTP 완벽 가이드 핵심

    A. 연결 관리 — HTTP/1.1, HTTP/2, HTTP/3

    HTTP 완벽 가이드 4장 + 그 이후의 발전

    HTTP/1.0 → 1.1: keep-alive

    1.0은 요청마다 TCP 연결을 새로 맺었어요(handshake + slow start 매번). 1.1은 기본이 persistent connection이에요. 한 연결로 여러 요청을 순서대로 보내요. Connection: close로 명시해야 끊어요.

    문제: 한 연결에서 요청은 직렬이에요. 앞 응답이 느리면 뒤가 기다려요(HOL blocking). 파이프라이닝(응답 안 기다리고 여러 요청 보내기)은 있지만 프록시 호환 문제로 브라우저가 안 써요. 대신 브라우저는 호스트당 6개 연결을 열어요.

    HTTP/2

    • 바이너리 프레이밍: 텍스트 대신 프레임 단위
    • 멀티플렉싱: 한 TCP 연결 안에 여러 스트림. 요청/응답이 섞여서 동시에 흘러요. HTTP 레벨 HOL blocking 해결.
    • 헤더 압축(HPACK): 반복되는 헤더(쿠키, User-Agent)를 인덱스로
    • 서버 푸시: 요청 전에 리소스 미리 보내기(실제로는 거의 안 쓰고 폐기 추세)
    • 우선순위, 흐름 제어(스트림 단위)

    남은 문제: TCP는 순서를 보장해야 해서 패킷 하나가 유실되면 모든 스트림이 재전송을 기다려요(TCP 레벨 HOL blocking). 손실률이 높은 모바일에서 HTTP/1.1 연결 6개보다 나쁠 수 있어요.

    HTTP/3 (QUIC)

    TCP 대신 UDP 위에 QUIC를 구현했어요. QUIC가 신뢰성, 혼잡 제어, TLS 1.3을 내장해요.

    • 스트림이 독립적: 한 스트림의 패킷 손실이 다른 스트림을 막지 않아요.
    • 연결 수립 1 RTT(TCP+TLS 합쳐서), 재접속은 0-RTT
    • 연결 마이그레이션: 연결을 IP/포트가 아니라 Connection ID로 식별해서 Wi-Fi ↔ LTE 전환에도 유지

    UDP를 막는 네트워크가 있어 TCP 폴백이 필요해요. 커널이 아닌 사용자 공간 구현이라 CPU를 더 써요.

    백엔드에서는 서버 간 통신(마이크로서비스)에서 HTTP/1.1 클라이언트가 커넥션 풀 없이 매번 새 연결을 맺는 게 가장 흔한 성능 낭비예요. 커넥션 풀 크기, 풀당 호스트 최대 연결, 유휴 타임아웃을 반드시 설정하세요. gRPC는 HTTP/2 위라 연결 하나로 멀티플렉싱해요. 그래서 L4 LB 뒤에서 gRPC는 한 서버에 몰려요(연결이 하나니까). L7 LB(요청 단위 분산)나 클라이언트 사이드 LB가 필요해요.
    핵심 정리
    • 1.1 = keep-alive, 직렬 → HOL blocking
    • 2 = 멀티플렉싱, 헤더 압축, 하지만 TCP HOL 남음
    • 3 = QUIC/UDP, 스트림 독립, 0-RTT, 연결 마이그레이션
    셀프 체크
    1. gRPC 서비스가 L4 LB 뒤에서 부하가 안 나뉘는 이유와 해결책은?
    답 보기

    gRPC는 HTTP/2 연결 하나에 모든 요청을 멀티플렉싱해요. L4 LB는 연결 단위로 분산하니 클라이언트 하나의 모든 요청이 한 서버로 가요. 해결: L7 LB(Envoy, ALB gRPC 모드)로 요청 단위 분산, 또는 클라이언트가 서버 목록을 알고 직접 라운드로빈(클라이언트 사이드 LB, 쿠버네티스 headless service), 또는 연결 최대 수명을 짧게 해 주기적 재연결.

    B. 캐시

    HTTP 완벽 가이드 7장 — 요청을 서버까지 보내지 않는 기술

    캐시의 두 질문

    1. 신선한가(freshness): 서버에 안 물어보고 바로 써도 되는가
    2. 재검증(revalidation): 신선하지 않을 때 "아직 그대로인가"를 싸게 확인

    신선도: Cache-Control

    지시어의미
    max-age=NN초 동안 신선. 서버에 안 물어봄
    s-maxage=N공유 캐시(CDN, 프록시)용 max-age
    no-cache저장은 하되 쓰기 전에 항상 재검증
    no-store아예 저장 금지(민감 정보)
    private브라우저만 저장, 공유 캐시 금지(개인화 응답)
    public공유 캐시 허용(인증 응답도)
    immutable신선한 동안 재검증도 안 함(해시 파일명)
    stale-while-revalidate=N만료 후 N초는 옛것을 주면서 뒤에서 갱신

    재검증: 조건부 요청

    • 서버가 ETag: "abc123"(내용 해시) 또는 Last-Modified를 응답에 넣어요.
    • 캐시가 만료되면 클라이언트가 If-None-Match: "abc123"으로 요청해요.
    • 같으면 서버는 304 Not Modified(본문 없음)로 응답, 다르면 200과 새 본문.

    본문 전송을 아끼지만 서버 왕복은 있어요. 서버는 ETag 비교를 본문 생성 전에 할 수 있어야 효과가 커요.

    Vary

    같은 URL이라도 Accept-Encoding이나 Accept-Language에 따라 응답이 다르면 Vary: Accept-Encoding으로 알려요. 캐시가 헤더 값별로 따로 저장해요. Vary: Cookie나 Vary: *는 사실상 캐시 불가예요.

    캐시 가능한 조건

    GET/HEAD, 상태 코드 200/301/404 등, no-store 아님, Authorization 헤더가 있으면 공유 캐시는 public 명시 없이는 저장 안 함.

    백엔드에서는 API 응답에 캐시 헤더를 안 쓰면 브라우저가 휴리스틱으로 캐시할 수도 있어요(Last-Modified 기반). 명시하세요. 동적 API는 Cache-Control: no-store 또는 private, no-cache, 공개 조회 API는 public, max-age=60, stale-while-revalidate=300처럼. 스프링의 ETag 필터(ShallowEtagHeaderFilter)는 본문을 만든 뒤 해시하므로 서버 부하는 안 줄고 전송량만 줄어요. 그리고 이 HTTP 캐시 모델(TTL + 재검증 + 키별 변형)은 Redis 캐시 설계에도 그대로 쓰는 사고방식이에요.
    시니어 심화 본문의 ETag와 304는 서버가 여러 대일 때 조용히 무력해지는 경우가 많아요.

    상황

    정적 파일과 상품 API에 ETag를 붙여 조건부 요청을 받게 했어요. 클라이언트는 다시 요청할 때 If-None-Match로 ETag를 보내고, 내용이 같으면 서버가 본문 없이 304를 돌려줘서 전송량을 아껴요. 그런데 몇 달 뒤 보니 304 비율이 2%였어요. 내용은 거의 바뀌지 않는데요.

    깨지는 과정

    1. 웹 서버가 정적 파일의 ETag를 파일의 수정 시각과 크기로 만들고 있었어요. 배포할 때 서버마다 파일이 복사된 시각이 조금씩 달라서, 같은 파일인데도 서버마다 ETag가 달라요.
    2. 브라우저가 서버 A에서 받은 ETag로 조건부 요청을 보내요. 로드밸런서가 그 요청을 서버 B로 보내요.
    3. 서버 B는 자기 ETag와 다르니 "다른 버전"이라고 판단하고 전체 본문을 다시 보내요.
    4. 압축도 ETag를 바꿔요. 어떤 서버 설정은 응답을 gzip으로 압축하면서 ETag를 약한 ETag(W/"...")로 바꾸거나 다른 값으로 만들어요. 압축 여부가 서버마다 다르면 또 어긋나요.

    캐시가 동작하는 것처럼 보이고 에러도 없으니 아무도 알아채지 못해요. 그냥 전송량과 서버 부하가 조금 더 클 뿐이에요.

    해결책

    • ETag는 내용의 해시로 만들어요. 파일 내용이나 응답 본문의 해시로 만들면 어느 서버에서든 같은 내용은 같은 ETag가 돼요. 스프링의 ShallowEtagHeaderFilter는 응답 본문의 해시로 ETag를 만들어요. 다만 이 필터는 응답을 다 만든 뒤에 해시를 계산하니, 전송량은 줄지만 서버의 계산은 줄지 않아요. 계산까지 줄이려면 데이터의 버전(예: 상품의 updated_at)으로 ETag를 만들고 본문을 만들기 전에 비교해요.
    • 정적 파일은 파일 이름에 해시를 넣어요. app.3f2a1c.js처럼 빌드 도구가 내용 해시를 이름에 넣으면, 내용이 바뀌면 주소가 바뀌어요. 이런 파일은 Cache-Control: max-age=31536000, immutable로 1년 캐시하고 조건부 요청 자체를 없애요. HTML만 짧게 캐시해요.
    • 롤링 배포 순서를 지켜요. 배포 중에는 새 HTML이 요청한 새 정적 파일이 아직 옛 버전인 서버로 갈 수 있어요. 그러면 404가 나요. 정적 파일을 CDN이나 저장소에 먼저 올리고, 옛 파일도 한동안 남겨 둔 뒤에 HTML을 바꿔요.

    운영에서 알아채는 법

    • 조건부 요청(If-None-Match가 있는 요청) 중 304로 응답한 비율을 지표로 남겨요. 내용이 자주 바뀌지 않는데 이 비율이 낮다면 ETag가 서버마다 다른 거예요.
    • 같은 주소를 서버 여러 대에 직접 요청해서 ETag가 같은지 비교해 보세요. 가장 빠른 확인 방법이에요.
    핵심 정리
    • max-age = 신선, no-cache = 매번 재검증, no-store = 저장 금지, private = 개인
    • ETag + If-None-Match → 304
    • Vary로 변형 구분, 인증 응답은 public 없이 공유 캐시 안 됨
    셀프 체크
    1. no-cache와 no-store의 차이는?
    2. 로그인한 사용자의 "내 주문 목록" 응답에 Cache-Control: public, max-age=300을 붙이면?
    답 보기

    1. no-cache는 저장은 하고 쓸 때마다 서버에 재검증(304면 재사용). no-store는 저장 자체를 안 해요. no-cache는 "항상 최신 확인", no-store는 "흔적 남기지 마".

    2. CDN/프록시가 이 응답을 저장하고 같은 URL을 요청한 다른 사용자에게 줘요. 개인정보 유출 사고예요. private(또는 no-store)로 해야 해요. 이런 사고가 실제로 여러 번 있었어요.

    C. 상태와 인증 — 쿠키, 세션, 토큰, CORS

    HTTP 완벽 가이드 11~12장 — 상태 없는 프로토콜에 상태를 얹는 법

    쿠키

    서버가 Set-Cookie: sid=abc; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600으로 심으면, 브라우저가 이후 같은 도메인 요청에 Cookie: sid=abc를 자동으로 붙여요.

    • HttpOnly: JS에서 접근 불가(XSS로 탈취 방지)
    • Secure: HTTPS에서만 전송
    • SameSite: 다른 사이트에서 시작된 요청에 쿠키를 보낼지. Lax(기본, 링크 이동 GET만), Strict, None(교차 사이트 허용, Secure 필수). CSRF 방어의 핵심.
    • Domain: 서브도메인 공유 여부

    세션 vs 토큰

    서버 세션JWT 같은 자기 완결 토큰
    저장서버(메모리/Redis)에 상태, 쿠키엔 ID만클라이언트가 서명된 토큰 보유, 서버는 상태 없음
    검증저장소 조회서명 검증만(저장소 불필요)
    무효화즉시(저장소에서 삭제)어려움(만료까지 유효, 블랙리스트 필요)
    확장공유 저장소 필요서버 추가 쉬움

    JWT를 쓰면서 블랙리스트를 Redis에 두면 결국 세션과 같아져요. 짧은 access 토큰 + 긴 refresh 토큰(서버 저장)이 흔한 타협이에요.

    인증 헤더

    Authorization: Bearer <token>이 API 표준. Basic은 base64(id:pw)라 HTTPS 필수. 401은 "누군지 모름"(인증 실패), 403은 "누군지 알지만 권한 없음".

    CORS

    브라우저의 동일 출처 정책: 스크립트는 다른 출처(스킴+호스트+포트)의 응답을 읽을 수 없어요. API가 다른 도메인이면 서버가 Access-Control-Allow-Origin으로 허용해야 해요. 단순하지 않은 요청(PUT, JSON 본문, 커스텀 헤더)은 브라우저가 먼저 OPTIONS preflight를 보내 Access-Control-Allow-Methods/Headers를 확인해요. 쿠키를 보내려면 Access-Control-Allow-Credentials: true와 Origin을 *가 아닌 명시로.

    CORS는 서버 보호가 아니에요. curl은 CORS를 무시해요. 브라우저 사용자를 보호하는 거예요. 서버 보호는 인증·인가예요.

    백엔드에서는 CORS 에러는 서버 로그에 안 남아요(브라우저가 응답을 막은 것). preflight OPTIONS에 인증 필터가 401을 주면 CORS 실패로 보여요. OPTIONS는 인증 전에 통과시키세요. Access-Control-Allow-Origin: * + credentials는 브라우저가 거부해요. 그리고 SameSite=Lax 기본값 때문에 다른 도메인의 프론트에서 쿠키 인증이 안 되는 건 설계 문제이지 버그가 아니에요. 같은 사이트(서브도메인)로 두거나 토큰 방식을 쓰세요.
    시니어 심화 본문은 세션과 토큰을 비교했는데, 토큰 방식을 택했다면 가장 자주 틀리는 곳은 JWT 검증이에요.

    상황

    API 서버는 로그인할 때 JWT를 발급하고, 요청마다 서명을 검증해요. 보안 점검에서 두 가지가 지적됐어요. 하나는 특정 모양의 토큰이 서명 없이도 통과한다는 것, 다른 하나는 서명 키가 3년째 바뀌지 않았고 바꿀 방법도 없다는 것이었어요.

    깨지는 과정 1: 토큰이 고른 알고리즘을 믿기

    1. JWT의 헤더에는 서명 알고리즘(alg)이 적혀 있어요. 일부 라이브러리와 직접 짠 검증 코드는 이 값을 보고 검증 방식을 골라요.
    2. 공격자가 alg를 none으로 바꾸고 서명을 비운 토큰을 보내면, "서명 없음"으로 검증해서 통과시키는 구현이 있었어요.
    3. 또 서버가 RS256(비대칭: 개인키로 서명, 공개키로 검증)을 쓰는데 공격자가 alg를 HS256(대칭: 같은 키로 서명과 검증)으로 바꾸면, 서버가 공개키를 대칭키로 써서 검증하는 구현이 있어요. 공개키는 말 그대로 공개돼 있으니, 공격자가 그것으로 서명한 토큰이 통과해요.

    해결: 서버가 허용하는 알고리즘을 직접 고정하고, 토큰이 말하는 알고리즘은 무시해요. 라이브러리에 허용 알고리즘 목록을 명시적으로 넘기고, none은 절대 허용하지 않아요. 만료(exp), 발급자(iss), 대상(aud)도 함께 검증해요.

    깨지는 과정 2: 키를 바꿀 수 없음

    1. 서명 키가 하나뿐이고 설정에 박혀 있어요. 키를 바꾸는 순간 이미 발급된 모든 토큰이 검증에 실패해서 전체 사용자가 로그아웃돼요.
    2. 그래서 아무도 키를 바꾸지 못하고, 키가 유출돼도 대응할 수 없는 상태가 돼요.

    해결: 키마다 ID(kid)를 붙이고, 검증하는 쪽은 여러 키를 동시에 받아들이게 해요. 공개키 목록은 JWKS 형식으로 제공해요. 교체는 세 단계예요. 새 키를 검증 목록에 추가하고, 발급을 새 키로 바꾸고, 옛 키로 발급된 토큰이 모두 만료된 뒤 옛 키를 목록에서 빼요. 사용자는 아무것도 느끼지 못해요.

    토큰 수명과 폐기

    • 액세스 토큰은 짧게(5~15분) 둬요. JWT는 서버가 상태를 갖지 않아서 발급한 토큰을 중간에 무효로 만들기 어려워요. 수명이 짧으면 유출돼도 피해 시간이 짧아요.
    • 리프레시 토큰은 쓸 때마다 새로 발급해요(순환). 그리고 이미 쓴 리프레시 토큰이 다시 오면 탈취로 보고, 그 사용자의 리프레시 토큰을 모두 폐기해요. 정상 사용자와 공격자 중 누가 먼저 썼든 둘 중 하나는 옛 토큰을 쓰게 되니 탈취가 드러나요.
    • 즉시 폐기가 필요하면 목록을 둬요. 비밀번호 변경, 계정 정지 때는 토큰 ID(jti)나 "이 시각 이전 발급 토큰 무효"를 Redis에 두고 검증할 때 확인해요. 상태를 조금 갖는 대가로 즉시성을 얻어요.

    운영에서 알아채는 법

    • 서명 검증 실패를 사유별(서명 불일치, 만료, 알 수 없는 kid, 허용되지 않은 알고리즘)로 나눠 지표로 남겨요. 허용되지 않은 알고리즘 시도가 보이면 공격 시도예요.
    • 리프레시 토큰 재사용 감지 건수를 따로 세어요. 0이 아니라면 실제 탈취가 일어나고 있을 수 있어요.
    • 키 교체를 1년에 한 번 이상 실제로 해 보세요. 한 번도 안 해 본 교체 절차는 사고 때 동작하지 않아요.
    핵심 정리
    • 쿠키 = 브라우저 자동 첨부, HttpOnly/Secure/SameSite 필수
    • 세션 = 서버 상태·즉시 무효화, 토큰 = 무상태·무효화 어려움
    • CORS = 브라우저 정책, preflight는 인증 전 통과
    셀프 체크
    1. CSRF 공격이 무엇이고 SameSite 쿠키가 어떻게 막나요?
    2. JWT로 "로그아웃 즉시 무효화"를 하려면?
    답 보기

    1. 악성 사이트가 사용자의 브라우저로 우리 사이트에 요청(폼 POST 등)을 보내면 브라우저가 쿠키를 자동 첨부해 인증된 요청이 돼요. SameSite=Lax/Strict는 다른 사이트에서 시작된 요청에 쿠키를 안 붙여서 막아요. 추가로 CSRF 토큰, Origin 헤더 검사.

    2. 토큰 ID(jti)를 서버 블랙리스트(Redis, 만료까지 TTL)에 넣고 매 요청 확인. 또는 access 토큰을 매우 짧게(5분) 하고 refresh 토큰만 서버에서 관리해 폐기. 전자는 사실상 세션 방식으로 회귀예요.

    D. HTTPS와 TLS

    HTTP 완벽 가이드 14장 — 암호화, 인증서, handshake

    TLS가 주는 것

    • 기밀성: 중간에서 못 읽음(대칭키 암호화)
    • 무결성: 중간에서 못 바꿈(MAC/AEAD)
    • 인증: 상대가 진짜 그 서버인지(인증서)

    대칭키 + 비대칭키

    대칭키(AES)는 빠르지만 키를 미리 공유해야 해요. 비대칭키(RSA, ECDHE)는 공개키로 암호화하면 개인키로만 풀 수 있지만 느려요. TLS는 비대칭(정확히는 ECDHE 키 교환)으로 세션 키를 합의하고, 데이터는 대칭키로 암호화해요. ECDHE는 매 연결마다 임시 키를 써서 서버 개인키가 나중에 유출돼도 과거 트래픽을 못 풀어요(forward secrecy).

    인증서와 CA

    인증서 = "이 공개키는 example.com 것" + CA의 서명. 브라우저는 내장된 루트 CA 목록으로 서명 체인을 검증해요: 서버 인증서 → 중간 CA → 루트 CA. 서버는 중간 인증서까지 함께 보내야 해요. 빠뜨리면 일부 클라이언트(특히 Java, 오래된 안드로이드)에서만 실패해요. 도메인 일치(SAN), 유효 기간, 폐기 여부(OCSP)도 확인해요. Let's Encrypt로 무료 자동 발급이 표준이 됐어요.

    TLS 1.3 handshake

    Client                                   Server
  │ ── ClientHello (지원 암호, 키 교환용 공개값) ──→ │
  │ ←─ ServerHello (선택 암호, 키 교환용 공개값)      │
  │    + 인증서 + 서명 + Finished ─────────────── │
  │ ── Finished ────────────────────────────────→ │   ← 여기서부터 암호화 데이터
  1 RTT (TLS 1.2는 2 RTT)

    세션 재개(session ticket)로 재접속 시 0-RTT 데이터도 가능해요(재전송 공격 위험이 있어 멱등 요청만).

    SNI와 TLS 종료

    한 IP에 여러 도메인을 호스팅하면 서버는 어떤 인증서를 줄지 알아야 해요. ClientHello에 SNI(서버 이름)가 평문으로 들어가요. LB/CDN이 TLS를 종료하면 그 뒤는 평문 HTTP예요(내부망 신뢰). 끝까지 암호화하려면 재암호화(re-encrypt)하거나 mTLS(서비스 메시)를 써요.

    백엔드에서는 "javax.net.ssl.SSLHandshakeException: unable to find valid certification path"는 JVM 트러스트스토어에 그 CA가 없거나 서버가 중간 인증서를 안 보낸 거예요. openssl s_client -connect host:443 -servername host로 체인을 확인하세요. 내부 서비스 간 mTLS는 클라이언트도 인증서를 내는 거예요. 인증서 만료는 가장 흔한 "예고된 장애"예요. 만료 30일 전 알람을 걸고 자동 갱신하세요. TLS handshake는 CPU를 꽤 쓰니, 서버 간 통신에서 연결을 재사용하지 않으면 handshake 비용이 요청 처리 비용을 넘기도 해요.
    시니어 심화 본문은 인증서 만료를 "예고된 장애"라고 했는데, 만료보다 더 자주 사고를 내는 것은 인증서를 바꿨는데 반영되지 않거나, 바꾼 인증서가 일부 클라이언트에서만 실패하는 경우예요.

    상황 1: 갱신했는데 만료 장애

    인증서는 자동 갱신으로 만료 30일 전에 새 파일로 바뀌어 있었어요. 파일의 만료일을 보는 알람도 조용했어요. 그런데 원래 만료일 자정에 API가 전부 인증서 오류를 냈어요.

    1. 서버 프로세스는 시작할 때 인증서 파일을 읽어 메모리에 들고 있어요.
    2. 파일은 새것으로 바뀌었지만, 서버가 재시작되지 않아서 메모리에는 옛 인증서가 그대로예요.
    3. 알람은 디스크의 파일을 보고 있었으니 "아직 60일 남음"이라고 판단했어요. 실제로 클라이언트에게 보내지는 인증서는 오늘 만료였어요.

    해결: 서버가 재시작 없이 인증서를 다시 읽는지 확인해요(nginx는 reload, 일부 서버는 자동 감지). 안 된다면 갱신 직후 reload나 재시작을 자동화해요. 그리고 만료 알람은 파일이 아니라 실제로 접속해서 받은 인증서의 만료일로 걸어요. Prometheus의 blackbox exporter가 주는 probe_ssl_earliest_cert_expiry 같은 지표예요.

    상황 2: 브라우저는 되는데 일부 클라이언트만 실패

    인증서를 새 업체 것으로 바꿨어요. 브라우저에서는 문제가 없었는데, 다른 회사의 서버가 우리 API를 부를 때와 일부 구형 안드로이드 앱에서 "unable to find valid certification path" 같은 오류가 났어요.

    1. 인증서는 루트 인증 기관부터 중간 인증서를 거쳐 우리 인증서까지 이어지는 사슬로 검증돼요. 서버는 중간 인증서까지 함께 보내야 해요.
    2. 새 설정에서 중간 인증서가 빠져 있었어요.
    3. 브라우저는 빠진 중간 인증서를 스스로 내려받거나 캐시해 둔 것을 써서 통과시켜요. 그래서 브라우저로 확인하면 멀쩡해요.
    4. 자바 클라이언트, curl, 구형 모바일 OS는 그렇게 하지 않아서 실패해요.

    해결: 인증서 파일에 중간 인증서까지 포함한 전체 사슬(fullchain)을 설정해요. 바꾼 뒤에는 브라우저가 아니라 openssl s_client -connect 호스트:443 -showcerts로 서버가 실제로 보내는 사슬을 확인해요.

    상황 3: 인증서 고정

    모바일 앱이 보안 강화를 위해 서버 인증서의 공개키를 앱에 고정(pinning)해 두면, 서버 인증서의 키를 바꾸는 순간 업데이트하지 않은 옛 앱이 전부 접속하지 못해요. 앱 업데이트는 강제할 수 없으니 몇 달 동안 일부 사용자가 앱을 못 써요. 고정한다면 예비 키를 함께 넣어 두고, 키 교체 계획을 앱 배포 일정과 함께 세워요. 고정 대상은 우리 인증서보다 수명이 긴 중간 인증서의 키로 하는 방법도 있어요.

    운영에서 알아채는 법

    • 외부에서 실제 접속해 만료일과 사슬을 검사하는 모니터링을 모든 공개 도메인에 걸어요.
    • 인증서를 바꾼 직후에는 TLS 핸드셰이크 실패 수를 클라이언트 종류(User-Agent)별로 나눠 봐요. 특정 클라이언트만 실패한다면 사슬이나 지원 알고리즘 문제예요.
    핵심 정리
    • 비대칭으로 키 합의, 대칭으로 데이터. ECDHE = forward secrecy
    • 인증서 체인: 서버 → 중간 → 루트, 중간 인증서 누락 주의
    • TLS 1.3 = 1 RTT, SNI 평문, 종료 지점 이후는 평문

    답 보기

    1. 목적 IP와 포트, SNI(도메인 이름, ECH 미적용 시), 패킷 크기와 타이밍, DNS 질의(DoH 미적용 시). URL 경로, 헤더, 본문은 못 봐요.

    2. ECDHE를 쓴 TLS 1.3(1.2에서도 ECDHE 스위트)이면 못 해요. 세션 키는 매 연결 임시 키로 만들어졌고 개인키는 서명에만 쓰였어요. RSA 키 교환(TLS 1.2 이하, 지금은 비권장)이면 가능해요.

    패킷을 직접 보면 책의 모든 문장이 구체화돼요.

    • 1장 dig +trace api.example.com으로 루트 → TLD → 권한 서버를 따라가고, dig의 TTL 값이 두 번째 조회에서 줄어드는 것 확인하기
    • 2장 Wireshark(또는 tcpdump -i any port 80 -w cap.pcap)로 curl http://example.com을 캡처해 SYN/SYN+ACK/ACK, 데이터, FIN 흐름과 시퀀스 번호 읽기
    • 2장 ss -tan state time-wait | wc -l, ss -tan state close-wait로 서버의 소켓 상태 분포 보기. keep-alive 없이 curl을 100번 돌린 뒤 TIME_WAIT 변화 관찰

    • 5장 Nginx를 리버스 프록시로 앞에 두고 proxy_read_timeout, keepalive 설정을 바꿔가며 백엔드 keep-alive timeout과의 불일치로 502를 재현하기

    • 부록 curl -v로 ETag를 받아 If-None-Match로 다시 요청해 304 받기. openssl s_client로 인증서 체인 출력해 보기
