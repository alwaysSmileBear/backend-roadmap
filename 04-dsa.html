    이 챕터의 목표는 코딩 테스트가 아니에요. "이 자료구조를 왜 썼는지, 복잡도가 어떻게 되는지"를 설명할 수 있는 것이에요. 그래서 각 장의 마지막에는 그 구조가 DB·Redis·JVM·분산 시스템 어디에 숨어 있는지를 연결해요. 구성은 『Hello Coding 알고리즘』의 순서(복잡도 → 배열/리스트 → 정렬 → 해시 → 그래프 → 그리디/DP)를 따르되, 백엔드에 중요한 트리와 실무 구조를 보강했어요.

    하루 한 문제씩 풀면서 각 장을 읽으면 가장 효과가 좋아요. 문제는 그 장의 자료구조를 쓰는 걸로 고르세요.

    1장 시간복잡도와 공간복잡도

    "얼마나 빠른가"가 아니라 "입력이 커지면 얼마나 느려지는가"

    Big-O

    입력 크기 n에 대해 연산 횟수가 어떤 함수로 증가하는지를 나타내요. 상수와 낮은 차수 항은 버려요. 3n² + 100n + 5 = O(n²).

    복잡도이름예n=10⁶일 때 대략
    O(1)상수배열 인덱스, 해시 조회1
    O(log n)로그이진 탐색, B-Tree 탐색20
    O(n)선형리스트 순회, 풀스캔10⁶
    O(n log n)선형 로그비교 정렬2×10⁷
    O(n²)이차이중 루프, 버블 정렬10¹² (불가)
    O(2ⁿ)지수부분집합 전부n=40이면 이미 10¹²

    경험 규칙: 1초에 약 10⁸ 연산. n=10⁵면 O(n²)은 10¹⁰이라 불가, O(n log n)은 OK.

    최악·평균·상환

    • 최악: 보통 Big-O가 말하는 것. 해시는 최악 O(n)(모두 충돌)이지만 평균 O(1).
    • 상환(amortized): 가끔 비싼 연산이 있어도 전체 평균. 동적 배열의 append는 가끔 O(n) 복사가 있지만 상환 O(1).

    공간복잡도

    추가로 쓰는 메모리. 재귀는 호출 깊이만큼 스택을 써요. 깊이 10만이면 스택 오버플로. 반복으로 바꾸거나 명시적 스택.

    실무에서 숨은 O(n²)

    • 루프 안에서 list.contains(), list.remove(obj), indexOf()
    • 루프 안에서 문자열 += (매번 새 문자열 복사) → StringBuilder
    • 루프 안에서 DB 쿼리 (N+1) — 복잡도에 네트워크 RTT가 곱해져 최악
    • 정렬된 리스트에 하나씩 삽입하면서 매번 정렬
    백엔드에서는 "개발 환경에서는 빠른데 운영에서 느리다"의 대부분은 복잡도 문제예요. 데이터 100건에서는 O(n²)도 1만 번이지만 10만 건에서는 100억 번이에요. 코드 리뷰에서 "이 루프 안에 뭐가 있지?"를 습관적으로 보세요. 그리고 상수도 중요해요. 같은 O(1)이어도 해시 조회(수십 ns)와 Redis 조회(수백 µs)와 DB 조회(수 ms)는 10⁴배 차이예요.
    시니어 심화 본문은 데이터가 늘면 O(n²)이 터진다고 했는데, 복잡도에는 데이터의 크기뿐 아니라 데이터의 모양도 영향을 줘요. 평균 복잡도는 입력이 무작위일 때의 이야기이고, 최악의 입력은 공격자가 고를 수 있어요.

    상황

    상품 리뷰 API가 리뷰 제목을 "단어와 공백만 허용"하는 정규식 ^(\w+\s?)*$로 검사해요. 평소 제목은 20자 안팎이라 검사는 1ms도 걸리지 않아요. 어느 날 누군가 aaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!(a 30개 뒤에 느낌표)를 제목으로 보냈고, 그 요청 하나가 CPU 코어 하나를 몇 초 동안 100%로 묶었어요.

    깨지는 과정

    1. 자바를 포함한 대부분의 정규식 엔진은 백트래킹 방식이에요. 패턴을 맞춰 보다가 실패하면 직전 선택으로 돌아가 다른 방법을 시도해요.
    2. (\w+\s?)*는 "aaaa"를 묶는 방법이 여러 가지예요. "aaaa" 한 덩어리, "aaa"+"a", "aa"+"aa", "a"+"a"+"aa" 같은 식으로, 글자가 n개면 2의 n-1제곱 가지예요.
    3. 문자열 끝의 느낌표 때문에 결국 매칭은 실패해요. 엔진은 실패를 확정하기 전에 모든 묶는 방법을 다 시도해요.
    4. 글자가 하나 늘 때마다 시간이 두 배가 돼요. 30글자면 수억 번을 시도해요. 같은 요청을 수십 개 보내면 톰캣 요청 스레드가 전부 묶여 서비스가 멈춰요. 이것을 ReDoS(정규식 서비스 거부)라고 불러요.

    정규식만의 문제가 아니에요. 같은 모양의 공격이 여러 곳에 있어요. 수만 단계로 중첩된 JSON은 재귀로 내려가는 파서의 스택을 넘치게 해요(StackOverflowError). 같은 버킷으로 가도록 만든 키 수천 개는 해시 맵을 O(n)으로 만들어요(3장). 1MB짜리 gzip 본문이 풀면 수 GB가 되는 압축 폭탄도 있어요. 공통점은 입력이 작아 보여도 처리 비용은 입력의 모양이 결정한다는 거예요.

    해결책

    • 입구에서 크기와 깊이에 상한을 둬요. 본문 크기(예: 1MB), 문자열 길이(리뷰 제목 100자), 배열 길이, JSON 중첩 깊이를 요청이 비즈니스 로직에 닿기 전에 제한해요. Jackson은 2.15부터 StreamReadConstraints로 중첩 깊이와 문자열 길이에 기본 상한을 둬요. 최악의 입력이 들어올 자리 자체를 없애는 방법이라 가장 효과가 커요.
    • 길이 검사를 정규식보다 먼저 해요. 100자로 잘린 입력이면 나쁜 패턴이어도 피해가 제한돼요.
    • 중첩된 반복을 피해요. (a+)+, (\w+\s?)*처럼 반복 안에 반복이 있으면 위험 신호예요. 위 예는 ^\w+(\s\w+)*$처럼 묶는 방법이 하나뿐이 되게 고칠 수 있어요.
    • 사용자 입력을 패턴으로 쓰지 않아요. 검색어를 그대로 Pattern.compile()에 넣으면 공격자가 패턴까지 골라요. 문자 그대로 찾을 거라면 Pattern.quote()로 감싸요.
    • 입력을 통제할 수 없다면 백트래킹 없는 엔진을 써요. RE2(자바는 re2j)는 입력 길이에 비례하는 시간을 보장해요. 대신 역참조 같은 일부 기능이 없어요.
    • 압축을 풀 때도 풀린 크기에 상한을 둬요.

    대가: 상한을 너무 낮게 잡으면 정상 사용자가 거절돼요. 실제 데이터의 최댓값(예: 가장 긴 리뷰 제목)을 확인하고 넉넉하게 잡으세요.

    운영에서 알아채는 법

    • 트래픽은 평소와 같은데 CPU만 튀고, 느린 요청이 특정 API의 일부 요청에 몰려 있다면 의심해요.
    • 그 순간 스레드 덤프를 몇 초 간격으로 여러 번 떠서 같은 스레드가 계속 java.util.regex.Pattern 안에 있으면 거의 확실해요.
    • 느린 요청 로그에 입력 길이를 같이 남겨 두면 원인 입력을 바로 찾을 수 있어요.
    • 정규식을 추가할 때는 "매칭에 실패하는 50자 입력"으로 실행 시간을 재는 테스트를 같이 넣어요.
    핵심 정리
    • Big-O = 증가율, 상수 무시. 1초 ≈ 10⁸ 연산
    • 루프 안의 O(n) 연산 = O(n²). 루프 안의 I/O는 더 나쁨
    셀프 체크
    1. 두 리스트 A, B(각 n개)의 교집합을 구하는 가장 단순한 방법과 개선한 방법의 복잡도는?
    답 보기

    단순: A의 각 원소에 대해 B를 순회 → O(n²). 개선: B를 HashSet으로 만들고(O(n)) A를 순회하며 contains(O(1)) → O(n). 또는 둘 다 정렬 후 투 포인터 → O(n log n).

    2장 배열, 연결 리스트, 스택, 큐

    가장 기본적인 선형 구조와 그 트레이드오프

    배열 vs 연결 리스트

    연산배열(동적 배열)연결 리스트
    인덱스 접근O(1)O(n)
    끝에 추가상환 O(1)O(1) (tail 포인터)
    중간 삽입/삭제O(n) (뒤로 밀기)O(1) (위치를 알 때) + 찾기 O(n)
    메모리연속, 캐시 친화적흩어짐, 포인터 오버헤드

    현대 CPU에서는 배열이 거의 항상 이겨요. 연속 메모리라 캐시와 TLB(OS 챕터 19장)에 유리해요. 연결 리스트의 "O(1) 삽입"은 삽입 위치까지 가는 O(n)이 숨어 있어요. Java LinkedList를 쓸 이유는 거의 없고 ArrayList나 ArrayDeque를 쓰세요.

    동적 배열의 리사이징

    꽉 차면 2배(Java는 1.5배) 크기의 새 배열에 복사. 복사는 O(n)이지만 드물어서 상환 O(1). 크기를 미리 알면 new ArrayList<>(capacity)로 복사를 피해요.

    스택과 큐

    • 스택(LIFO): 함수 호출, 괄호 검사, 되돌리기(undo), DFS. 배열로 구현.
    • 큐(FIFO): 작업 대기열, BFS, 버퍼. 원형 배열(ring buffer)이나 연결 리스트. Java는 ArrayDeque.
    • 덱: 양쪽 삽입·삭제. 슬라이딩 윈도우 최댓값.
    • 우선순위 큐: 가장 작은(큰) 것 먼저. 힙으로 구현(5장).

    링 버퍼

    고정 크기 배열을 원형으로 쓰는 큐. head/tail 인덱스만 움직여서 할당이 없어요. 로그 버퍼, 네트워크 소켓 버퍼, Disruptor(LMAX), Kafka 프로듀서 배치가 이 구조예요. 꽉 차면 "덮어쓰기" 또는 "블록" 정책을 정해야 해요.

    백엔드에서는 스레드풀의 작업 큐가 LinkedBlockingQueue(무제한)인지 ArrayBlockingQueue(유한)인지가 장애 양상을 결정해요. 무제한이면 요청이 쌓여 메모리 OOM, 유한이면 넘칠 때 거부 정책(RejectedExecutionHandler)이 실행돼요. 유한 + 빠른 거부가 보통 더 건강해요(backpressure). Kafka 컨슈머의 폴링, Redis의 LPUSH/BRPOP 큐도 같은 FIFO예요.
    시니어 심화 본문은 유한 큐가 더 건강하다고 했는데, 자바의 ThreadPoolExecutor는 큐와 스레드 수가 직관과 다르게 맞물려서 많이 틀려요.

    상황

    주문이 완료되면 알림 발송을 스레드 풀에 넘겨요. 설정은 코어 스레드 10, 최대 스레드 50, 큐는 크기 제한이 없는 LinkedBlockingQueue예요. 세일 때 알림이 몰리면 스레드가 50개까지 늘어날 거라고 기대했어요.

    깨지는 과정

    1. 스레드 10개가 모두 바빠지면 새 작업은 스레드를 더 만들지 않고 큐로 가요.
    2. 큐가 가득 차야 최대 스레드 수까지 늘리는데, 크기 제한이 없는 큐는 차지 않아요. 그래서 스레드는 영원히 10개예요. 최대 50이라는 설정은 한 번도 쓰이지 않아요.
    3. 세일 때 들어오는 알림이 처리량보다 많으면 큐가 계속 길어져요. 알림이 몇 분씩 늦게 나가요.
    4. 큐에 쌓인 작업 객체가 결국 힙 메모리를 다 쓰고 OutOfMemoryError가 나요. 같은 JVM에서 돌던 주문 API까지 같이 죽어요. 부가 기능인 알림 때문에 핵심인 주문이 멈춰요.

    Executors.newFixedThreadPool()과 newSingleThreadExecutor()도 내부적으로 크기 제한 없는 큐를 써요. 편한 팩토리 메서드에 이 함정이 그대로 숨어 있어요.

    해결책

    • 큐에 상한을 둬요. 크기는 "얼마나 기다려도 되는가 × 처리량"으로 정해요. 스레드 10개가 작업 하나에 50ms를 쓰면 초당 200건을 처리해요. 알림이 1초까지 늦어도 된다면 큐는 200이면 충분해요. 이보다 크게 잡아도 처리량은 그대로이고 늦어지는 시간만 길어져요.
    • 큐가 찼을 때의 거부 정책을 골라요. 기본 제공 정책은 네 가지이고 대가가 각자 달라요.
      • AbortPolicy(기본값): 예외를 던져요. 호출한 쪽이 실패를 알고 직접 대처할 수 있어요.
      • CallerRunsPolicy: 작업을 넘긴 스레드가 직접 실행해요. 넘기는 속도가 자연스럽게 느려져서 백프레셔(받는 쪽이 보내는 쪽의 속도를 늦추는 것)가 돼요. 대신 넘긴 스레드가 톰캣 요청 스레드라면 그만큼 API 응답이 느려져요.
      • DiscardPolicy: 조용히 버려요. 조회수 집계처럼 일부를 잃어도 되는 작업에만 써요.
      • DiscardOldestPolicy: 큐에서 가장 오래된 작업을 버려요. 배송 기사의 위치 갱신처럼 최신 값만 의미 있을 때 맞아요.
    • 잃으면 안 되는 작업은 실패를 기록해요. 주문 알림은 AbortPolicy를 쓰고, 예외가 나면 알림 요청을 DB 테이블에 저장해 두었다가 배치로 다시 보내요.
    • 용도별로 풀을 나눠요. 알림, 외부 결제 호출, 이미지 처리가 한 풀을 같이 쓰면, 하나가 느려질 때 나머지가 같이 밀려요. 풀을 나누면 피해가 한 기능에서 멈춰요(벌크헤드).

    운영에서 알아채는 법

    • Micrometer의 ExecutorServiceMetrics로 풀을 감싸면 큐 길이, 실행 중인 스레드 수, 완료 작업 수가 지표로 나와요. 거부 횟수는 거부 정책 안에서 카운터를 올려 직접 남겨요.
    • 큐 길이가 계속 늘면 처리량이 유입량보다 적다는 뜻이에요.
    • 실행 중인 스레드 수가 코어 값에 붙어 있고 최대 값에 한 번도 닿지 않는다면 바로 이 함정이에요.
    핵심 정리
    • 배열이 캐시 친화적이라 대부분 이김. LinkedList는 거의 안 씀
    • 동적 배열 리사이징은 상환 O(1), 용량 미리 지정
    • 스택 = DFS/호출, 큐 = BFS/작업, 링 버퍼 = 고정 크기 무할당 큐
    셀프 체크
    1. ArrayList 중간 삭제가 O(n)인데도 LinkedList보다 빠른 경우가 많은 이유는?
    답 보기

    ArrayList의 O(n)은 연속 메모리를 한 블록 옮기는 System.arraycopy라 매우 빠르고 캐시에 유리해요. LinkedList는 삭제 위치까지 포인터를 따라가며 O(n)만큼 캐시 미스를 내고, 노드마다 객체 할당과 GC 부담이 있어요. 수만 개 이하에선 ArrayList가 거의 항상 빨라요.

    2부 해시

    3장 해시 테이블

    O(1) 조회의 원리, 충돌, 리사이징, 그리고 해시 함수의 품질

    원리

    키를 해시 함수로 정수로 바꾸고, 버킷 배열 크기로 나눈 나머지를 인덱스로 써요. 좋은 해시 함수는 키를 버킷에 고르게 흩뿌려요. 평균 O(1) 조회·삽입·삭제.

    충돌 해결

    • 체이닝: 버킷마다 연결 리스트. 충돌하면 리스트에 추가. Java HashMap이 이 방식이고, 한 버킷이 8개를 넘으면 Red-Black 트리로 바꿔 최악 O(log n)을 보장해요(해시 충돌 DoS 방어).
    • 오픈 어드레싱: 충돌하면 다음 빈 칸을 찾아 넣음(선형 탐사, 이차 탐사, 더블 해싱). 포인터가 없어 캐시 친화적. Python dict, Go map, Rust HashMap. 삭제가 까다로워요(tombstone).

    로드 팩터와 리사이징

    원소 수 / 버킷 수 = 로드 팩터. 높으면 충돌이 늘어요. Java는 0.75를 넘으면 버킷을 2배로 늘리고 전부 재배치(rehash)해요. O(n)이지만 드물어서 상환 O(1). 크기를 알면 초기 용량을 지정하세요. 대량 삽입 중 리사이징이 반복되면 눈에 띄게 느려요.

    해시 함수의 조건

    • 같은 키 → 같은 해시 (결정적). equals가 같으면 hashCode도 같아야 함. Java에서 equals만 오버라이드하면 HashMap이 깨져요.
    • 고르게 분포. 나쁜 해시(예: 문자열 길이)는 전부 한 버킷에 → O(n).
    • 빠름. 암호학적 해시(SHA-256)는 해시 테이블엔 과해요.

    순서

    해시 테이블은 순서가 없어요. 삽입 순서가 필요하면 LinkedHashMap(해시 + 이중 연결 리스트), 정렬 순서가 필요하면 TreeMap(Red-Black 트리, O(log n)).

    백엔드에서는 JPA 엔티티를 HashSet에 넣을 때 equals/hashCode를 PK 기준으로 오버라이드하는데, PK가 저장 전엔 null이라 해시가 바뀌어 Set에서 사라지는 버그가 있어요. 또 HashMap은 스레드 안전하지 않아서 멀티스레드에서 리사이징 중 접근하면 무한 루프(Java 7) 또는 데이터 유실이 나요. 공유하면 ConcurrentHashMap. 그리고 DB의 해시 조인, 해시 인덱스, Redis의 Hash 타입, 세션 저장소 전부 이 구조예요.
    시니어 심화 본문의 해시 테이블은 평균 O(1)이지만, 그 평균에는 "키가 버킷에 고르게 흩어진다"는 전제가 있어요. 공격자가 그 전제를 깨뜨릴 수 있어요.

    상황

    상품 목록 API가 필터 조건을 쿼리 파라미터로 받아요. 서버는 파라미터를 해시 맵에 담아 처리해요. 어느 날 파라미터가 10만 개 붙은 요청 몇 개가 들어오자 API 서버 CPU가 몇 분 동안 100%가 됐어요.

    깨지는 과정

    1. 해시 맵은 키의 해시값으로 버킷을 골라요. 키가 고르게 흩어지면 버킷마다 원소가 한두 개라서 삽입과 조회가 O(1)이에요.
    2. 자바의 String.hashCode()는 공식이 명세로 공개돼 있고 실행마다 바뀌는 무작위 값(시드)이 없어요. 그래서 같은 해시값을 가진 문자열을 미리 계산할 수 있어요. 예를 들어 "Aa"와 "BB"는 해시값이 같아요(2112).
    3. 같은 해시값을 가진 조각을 이어 붙여도 해시값이 같아요. "AaAa", "AaBB", "BBAa", "BBBB"는 모두 같은 버킷으로 가요. 조각을 k번 이어 붙이면 충돌하는 키가 2의 k제곱 개 생겨요.
    4. 이런 키 10만 개가 한 버킷에 모이면, 키 하나를 넣을 때마다 버킷의 모든 키와 비교해요. 전체 비용이 O(n²), 약 50억 번의 비교가 돼서 요청 하나가 CPU를 수십 초 묶어요.

    2011년에 이 방법으로 자바, PHP, 파이썬, 루비의 웹 프레임워크가 한꺼번에 취약하다는 것이 발표됐어요. 웹 서버는 요청 파라미터를 자동으로 해시 맵에 넣기 때문에, 애플리케이션 코드가 아무것도 하지 않아도 공격이 성립했어요.

    해결책

    • 런타임의 대책을 알아 둬요. 파이썬, 루비, Go 같은 언어는 문자열 해시에 프로세스마다 다른 무작위 시드를 섞어요. 공격자가 충돌하는 키를 미리 계산할 수 없어요. 자바는 hashCode()가 명세라 바꿀 수 없어서 다른 길을 택했어요. 자바 8의 HashMap은 한 버킷의 원소가 8개를 넘으면(테이블 크기가 64 이상일 때) 그 버킷을 연결 리스트에서 균형 트리로 바꿔요. 최악이 O(n)에서 O(log n)으로 줄어요.
    • 입구에서 개수를 제한해요. 톰캣의 maxParameterCount로 요청 파라미터 수를, 본문 크기 제한으로 JSON 객체의 키 수를 묶어요. 기본값은 버전마다 다르니 사용하는 버전에서 확인하세요. 필터 조건이 수십 개를 넘을 일이 없다면 그보다 조금 넉넉한 값으로 낮춰요.
    • 외부 입력을 키로 쓰는 자체 맵과 캐시에도 상한을 둬요. 사용자가 보낸 값으로 키를 만드는 로컬 캐시는 크기 제한이 없으면 충돌 공격과 메모리 고갈에 같이 노출돼요.

    대가: 트리로 바뀐 버킷은 연결 리스트보다 메모리를 많이 써요. 그래서 원소가 적을 때는 리스트를 유지하고 임계값을 넘을 때만 바꿔요.

    운영에서 알아채는 법

    • 요청 수는 평소와 같은데 CPU가 튀고, 느린 요청의 파라미터 수나 본문 크기가 비정상적으로 크다면 의심해요.
    • 스레드 덤프에서 HashMap.putVal이나 TreeNode 관련 프레임이 반복해서 보이면 거의 확실해요.
    • 접근 로그에 파라미터 개수와 본문 크기를 남겨 두면 분포에서 튀는 요청이 바로 보여요.
    핵심 정리
    • 해시 함수 → 버킷, 충돌은 체이닝 또는 오픈 어드레싱
    • 로드 팩터 초과 시 리사이징(O(n)), 초기 용량 지정
    • equals ↔ hashCode 계약, 멀티스레드는 ConcurrentHashMap
    셀프 체크
    1. 해시 테이블의 최악 복잡도가 O(n)인 상황과 Java HashMap이 이를 완화하는 방법은?
    답 보기

    모든 키가 같은 버킷에 떨어질 때(나쁜 해시 함수, 또는 공격자가 해시 충돌 키를 의도적으로 보내는 HashDoS). Java 8+는 한 버킷의 체인이 8개를 넘으면 Red-Black 트리로 변환해 최악을 O(log n)으로 낮춰요. 추가로 문자열 해시에 랜덤 시드를 쓰는 언어도 있어요(Python, Ruby).

    4장 분산 해싱 — Consistent Hashing과 Bloom Filter

    해시를 여러 서버에 걸쳐 쓰는 법, 그리고 확률적 자료구조

    문제: hash(key) % N

    캐시 서버 N대에 키를 분배할 때 hash(key) % N을 쓰면, 서버가 4 → 5대가 되는 순간 거의 모든 키의 담당 서버가 바뀌어요. 캐시가 통째로 미스 나서 DB가 죽어요.

    Consistent Hashing

    서버와 키를 모두 같은 해시 공간(0 ~ 2³²을 원형 링으로)에 배치해요. 키는 링에서 시계 방향으로 처음 만나는 서버가 담당해요. 서버를 추가하면 그 서버와 바로 앞 서버 사이의 키만 이동(평균 1/N). 제거해도 그 서버의 키만 다음 서버로.

    문제: 서버가 적으면 링에서 구간이 불균등해요. 해결은 가상 노드: 서버 하나를 링에 100~200개 점으로 배치해 구간을 고르게 해요. 서버 성능에 따라 가상 노드 수를 다르게 해 가중치도 줄 수 있어요.

    쓰는 곳: Memcached 클라이언트, DynamoDB, Cassandra, Redis Cluster(슬롯 16384개로 변형), CDN, 로드밸런서의 세션 어피니티.

    Bloom Filter

    "이 원소가 집합에 있는가?"를 아주 적은 메모리로 답하는 확률적 구조. 비트 배열 m개와 해시 함수 k개.

    • 추가: 키를 k개 해시로 돌려 나온 k개 위치의 비트를 1로.
    • 질의: k개 위치가 모두 1이면 "아마 있음", 하나라도 0이면 "확실히 없음".

    거짓 음성은 없고 거짓 양성만 있어요. 1% 오류율에 원소당 약 10비트. 1억 개를 120MB로. 삭제는 못 해요(Counting Bloom Filter는 가능).

    쓰는 곳: LSM 트리(RocksDB, Cassandra)에서 "이 SSTable에 키가 없다"를 디스크 안 읽고 판단, 캐시 관통 방지(없는 키 요청을 DB 전에 차단), 크롤러의 방문 URL, 추천에서 이미 본 항목 제외.

    HyperLogLog

    유니크 개수(cardinality)를 약 12KB로 0.8% 오차로 세는 구조. Redis PFADD/PFCOUNT. "일간 순 방문자"를 Set으로 세면 수백 MB, HLL이면 12KB.

    백엔드에서는 Redis Cluster는 키를 CRC16 % 16384 슬롯으로 나누고 슬롯을 노드에 배정해요. 노드 추가 시 슬롯 단위로 이동(resharding). 가상 노드의 변형이에요. 캐시 관통(cache penetration) 방어에 Bloom filter를 Redis 앞에 두면(BF.ADD/BF.EXISTS, RedisBloom) 존재하지 않는 ID 공격이 DB까지 안 가요. 다만 "아마 있음"은 확인이 필요하니 캐시 → DB 순서는 유지해요.
    핵심 정리
    • % N은 서버 변경 시 전체 재배치, consistent hashing은 1/N만 이동
    • 가상 노드로 균등화. Redis Cluster 슬롯이 변형
    • Bloom filter = 거짓 양성만, 적은 메모리. HLL = 카디널리티 근사
    셀프 체크
    1. Bloom filter가 "있다"고 했는데 실제로 없을 수 있어요. 그래도 캐시 관통 방어에 유용한 이유는?
    답 보기

    목적은 "없는 키"를 DB 전에 걸러내는 거예요. "확실히 없음"은 100% 정확하니 그 요청은 즉시 거절해요. "아마 있음"(1% 거짓 양성)은 평소처럼 캐시 → DB로 가요. 즉 없는 키 요청의 99%를 DB 접근 없이 막고, 있는 키는 한 번도 잘못 거절하지 않아요.

    3부 트리

    5장 이진 탐색 트리, 균형 트리, 힙

    정렬을 유지하면서 O(log n)에 넣고 빼고 찾기

    이진 탐색 트리 (BST)

    왼쪽 서브트리 < 노드 < 오른쪽 서브트리. 탐색·삽입·삭제가 높이에 비례. 랜덤 삽입이면 높이 ≈ log n이지만, 정렬된 순서로 넣으면 한쪽으로 치우쳐 높이 n(연결 리스트가 됨). 중위 순회하면 정렬된 순서가 나와요.

    균형 트리

    • AVL: 좌우 높이 차 ≤ 1 엄격 유지. 탐색이 빠르고 삽입·삭제 시 회전이 많음.
    • Red-Black Tree: 느슨한 균형(가장 긴 경로 ≤ 가장 짧은 경로 × 2). 회전이 적어 삽입·삭제가 빠름. Java TreeMap/TreeSet, 리눅스 CFS 스케줄러, HashMap 버킷 트리화, epoll 내부.
    • B-Tree / B+Tree: 노드 하나에 키 수백 개, 높이 3~4. 디스크·페이지 기반 저장소용. DB 챕터 8장에서 자세히. 메모리에서도 캐시 라인 활용 때문에 B-Tree 변형이 Red-Black보다 빠른 경우가 많아요(Rust BTreeMap).

    힙

    부모 ≤ 자식(최소 힙)인 완전 이진 트리. 배열로 구현(i의 자식은 2i+1, 2i+2). 최솟값은 루트 O(1), 삽입은 끝에 넣고 위로 올리기(sift-up) O(log n), 삭제는 루트를 빼고 마지막을 루트로 올려 아래로 내리기(sift-down) O(log n). BST와 달리 정렬된 순회는 못 해요. 오직 최소(최대)만.

    쓰는 곳: 우선순위 큐, 다익스트라, 타이머(가장 빠른 만료 시각), 작업 스케줄러, "상위 K개"(크기 K 최소 힙 유지 → O(n log K)), 여러 정렬된 스트림 병합(K-way merge, LSM 컴팩션).

    트라이 (Trie)

    문자열을 글자 단위 경로로 저장. 접두사 검색 O(문자열 길이). 자동완성, IP 라우팅 테이블(최장 접두사 일치), 사전. 메모리를 많이 써서 압축 트라이(radix tree)를 써요. Nginx 라우팅, Go httprouter가 radix tree.

    스킵 리스트

    정렬된 연결 리스트 위에 "급행" 층을 확률적으로 쌓은 구조. 위층에서 크게 건너뛰다 내려와서 O(log n). 균형 트리와 성능은 비슷한데 구현이 훨씬 단순하고 락 없는 동시성 구현이 쉬워요. Redis Sorted Set, Java ConcurrentSkipListMap, LevelDB/RocksDB 메모리 테이블(memtable).

    백엔드에서는 "최근 N분 안에 만료되는 것" 같은 타이머는 힙(PriorityQueue, ScheduledThreadPoolExecutor 내부)이고, Netty는 더 싼 타이밍 휠을 써요. 랭킹은 Redis Sorted Set(ZADD/ZRANGE, 스킵 리스트)이 O(log n)이라 DB ORDER BY score보다 훨씬 빨라요. 라우터가 URL 경로를 매칭하는 것도 트라이예요. 정렬된 범위 조회가 필요한 메모리 구조는 TreeMap(subMap, ceilingKey)이에요.
    시니어 심화 본문은 타이머에 힙을 쓴다고 했는데, 힙에는 운영에서 문제가 되는 약점이 하나 있어요. 중간의 임의 원소를 지우기가 어렵다는 거예요.

    상황

    결제사 API를 호출할 때마다 "3초 뒤 타임아웃 처리" 작업을 ScheduledThreadPoolExecutor에 등록해요. 응답이 오면 그 작업을 cancel()로 취소해요. 호출의 99%는 100ms 안에 끝나요. 그런데 세일 기간에 API 서버의 메모리가 점점 차오르고 GC가 잦아졌어요.

    깨지는 과정

    1. 스케줄러 내부의 큐는 실행 시각 순서로 정렬된 최소 힙이에요. 가장 빨리 실행할 작업을 꺼내는 것은 O(log n)으로 빨라요.
    2. 문제는 취소예요. 기본 설정에서는 취소된 작업을 힙에서 빼지 않고 "취소됨" 표시만 해요. 그 작업은 원래 실행 시각인 3초 뒤에 꺼내질 때 비로소 버려져요.
    3. 초당 2만 건을 호출하면 힙에는 항상 6만 개(2만 × 3초)의 죽은 작업이 있어요. 타임아웃을 30초로 늘리면 60만 개예요.
    4. 작업마다 람다가 요청 객체와 응답 버퍼를 붙잡고 있어서, 그 메모리도 실행 시각까지 GC가 회수하지 못해요. old 영역이 커지고 GC 시간이 늘어요.
    5. 힙이 클수록 삽입도 조금씩 느려지고, 스케줄러 큐는 락 하나로 보호되기 때문에 등록하는 스레드들이 서로 기다려요.

    해결책

    • 취소 즉시 제거하게 설정해요. setRemoveOnCancelPolicy(true)를 켜면 취소할 때 힙에서 바로 빠져요. 스케줄러의 힙은 작업마다 자기 위치(인덱스)를 기억하고 있어서 제거가 O(log n)이에요.
    • 타이머가 아주 많고 대부분 취소된다면 타이밍 휠을 써요. 시간 칸이 원형으로 이어진 배열이에요. 칸 하나를 100ms로 정하면, "3초 뒤" 작업은 지금 칸에서 30칸 뒤에 넣어요. 바늘이 100ms마다 한 칸씩 이동하며 그 칸의 작업을 실행해요. 칸 수보다 먼 시간은 "몇 바퀴 뒤"를 같이 기록해요. 등록과 취소가 둘 다 O(1)이에요. Netty의 HashedWheelTimer가 이 구조이고, Kafka도 요청 타임아웃 관리에 계층형 타이밍 휠을 써요.
    • 직접 타이머를 걸 필요가 없는지 먼저 봐요. HTTP 클라이언트의 연결, 읽기, 전체 요청 타임아웃 설정을 쓰면 스케줄러에 등록할 일 자체가 없어요.

    대가: 타이밍 휠은 정밀도가 칸 크기로 떨어져요. 3초 타임아웃이 3.0초가 아니라 3.0~3.1초 사이에 실행돼요. 타임아웃 용도에는 충분하지만 정확한 시각이 중요한 작업에는 맞지 않아요.

    운영에서 알아채는 법

    • 스케줄러의 getQueue().size()를 지표로 남겨요. 이 값이 "초당 등록 수 × 실제 평균 처리 시간"보다 훨씬 크면 취소된 작업이 쌓이고 있는 거예요.
    • 힙 덤프에서 ScheduledFutureTask 객체가 수십만 개 보이면 같은 원인이에요.
    핵심 정리
    • BST는 치우침 문제 → Red-Black(메모리), B-Tree(디스크)
    • 힙 = 최소/최대만 O(1), 삽입·삭제 O(log n), 배열 구현
    • 트라이 = 접두사, 스킵 리스트 = 단순한 정렬 구조(Redis ZSET)
    셀프 체크
    1. 1억 개 로그 중 응답 시간 상위 100개를 메모리 적게 쓰면서 구하는 방법은?
    2. Redis가 Sorted Set에 Red-Black 트리 대신 스킵 리스트를 쓴 이유는?
    답 보기

    1. 크기 100의 최소 힙을 유지해요. 각 로그를 보며 힙 크기가 100 미만이면 넣고, 아니면 힙의 최솟값(100개 중 가장 작은 것)보다 크면 최솟값을 빼고 넣어요. O(n log 100), 메모리 100개. 전체 정렬(O(n log n), 메모리 n)보다 훨씬 효율적이에요.

    2. Redis 작성자의 설명: 구현이 단순하고, 범위 조회(ZRANGE)를 위한 연결 리스트 순회가 자연스럽고, 메모리 사용을 조절할 수 있어요(층 확률). 성능은 균형 트리와 동급이에요.

    4부 그래프

    6장 그래프 — 표현, BFS/DFS, 최단 경로, 위상 정렬

    관계를 다루는 구조. 의존성, 네트워크, 추천, 소셜

    표현

    • 인접 리스트: 노드마다 이웃 목록. 메모리 O(V+E). 희소 그래프(대부분)에 적합. Map<Node, List<Node>>.
    • 인접 행렬: V×V 배열. 간선 존재 확인 O(1). 밀집 그래프나 V가 작을 때.

    BFS (너비 우선)

    큐를 써서 가까운 노드부터. 시작점에서 각 노드까지 최단 거리(간선 수 기준)를 구해요. O(V+E). 방문 체크 필수(사이클). 쓰는 곳: 최단 경로(가중치 없음), 소셜 "n촌" 관계, 크롤러, 레벨 순회.

    DFS (깊이 우선)

    스택(또는 재귀)으로 한 방향 끝까지. O(V+E). 쓰는 곳: 사이클 탐지, 연결 요소, 경로 존재 여부, 위상 정렬, 백트래킹. 재귀 깊이 주의(명시적 스택으로).

    위상 정렬

    방향 비순환 그래프(DAG)에서 "A가 B보다 먼저"를 만족하는 순서. 진입 차수가 0인 노드부터 큐로(Kahn), 또는 DFS 종료 순서의 역. 사이클이 있으면 불가능 → 순환 의존성 탐지. 쓰는 곳: 빌드 순서, 패키지 설치, 스프링 빈 초기화 순서, 워크플로/DAG 스케줄러(Airflow), 마이그레이션 순서.

    다익스트라 (가중치 최단 경로)

    시작점에서 거리가 가장 짧은 미방문 노드를 우선순위 큐(힙)로 꺼내 이웃 거리를 갱신. O((V+E) log V). 음수 가중치 불가(벨만-포드). 쓰는 곳: 지도, 네트워크 라우팅(OSPF가 다익스트라), 비용 최소 경로.

    유니온 파인드 (Disjoint Set)

    "같은 집합인가?"와 "합치기"를 거의 O(1)(역 아커만 함수)에. 경로 압축 + 랭크. 쓰는 곳: 연결 요소 동적 관리, 크루스칼 MST, 중복 계정 병합, 네트워크 연결 여부.

    백엔드에서는 스프링이 빈 의존성 그래프에서 순환 참조를 탐지하는 것, 마이크로서비스 호출 그래프에서 분산 트레이싱이 경로를 재구성하는 것, 권한 상속(역할 → 역할), 조직도, 카테고리 트리, 추천의 "함께 구매" 그래프, DB의 외래키 의존성 순서로 테이블 삭제하기 전부 그래프 문제예요. 깊은 트리를 재귀 쿼리로 가져오는 건 WITH RECURSIVE(MySQL 8.0)가 BFS를 DB에서 해주는 거예요.
    시니어 심화 본문은 깊은 트리를 WITH RECURSIVE로 가져온다고 했는데, 그래프를 DB에 저장할 때는 저장 방식이 조회 성능을 결정해요. 카테고리 트리를 예로 들어 볼게요.

    상황

    카테고리는 "전자제품 > 컴퓨터 > 노트북 > 게이밍 노트북"처럼 4~5단계 트리예요. 상품 목록 페이지는 열릴 때마다 "이 카테고리와 모든 하위 카테고리의 상품"을 조회해요. 카테고리 이동은 한 달에 몇 번 관리자가 하는 정도예요.

    세 가지 저장 방식

    • 인접 리스트: 행마다 부모 ID만 둬요(categories(id, parent_id)). 쓰기가 가장 단순해서 이동은 parent_id 한 행만 고치면 돼요. 대신 "모든 하위"를 구하려면 재귀 쿼리로 깊이만큼 조인을 반복해야 해요. 깊이가 5 정도면 충분히 빨라요.
    • 경로 열거: 행마다 루트부터의 경로를 문자열로 저장해요(path = '/1/7/42/'). 하위 전체는 WHERE path LIKE '/1/7/%'로 찾아요. 접두사로 시작하는 LIKE는 인덱스 범위 검색이 되니까 빨라요. 대신 카테고리를 옮기면 하위 전체의 경로 문자열을 고쳐야 하고, 경로 길이에 상한이 생겨요.
    • 클로저 테이블: 모든 조상과 후손의 쌍을 별도 테이블에 저장해요(category_closure(ancestor, descendant, depth)). 하위 전체가 조인 한 번이고, "두 단계 아래까지만" 같은 조건도 depth로 쉽게 걸어요. 대신 노드를 추가할 때 조상 수만큼 행을 넣고, 옮길 때는 서브트리와 옛 조상 사이의 행을 지우고 새 조상과의 행을 넣어야 해요. 행 수는 대략 "노드 수 × 평균 깊이"예요.

    고르는 기준

    읽기와 쓰기의 비율, 그리고 트리의 크기로 골라요. 카테고리가 수천 개 정도라면 사실 가장 빠른 방법은 트리 전체를 애플리케이션 메모리에 캐시하고 메모리에서 하위를 구하는 거예요. 저장은 인접 리스트로 단순하게 하고, 변경할 때만 캐시를 다시 만들면 돼요. 트리가 커서 메모리에 올릴 수 없고 읽기가 압도적으로 많다면 경로 열거나 클로저 테이블이 맞아요. 이동이 잦은 트리(조직도처럼)라면 인접 리스트가 유리해요.

    순환이라는 함정

    어떤 방식이든 데이터 오류로 순환이 생길 수 있어요. 관리자가 실수로 "컴퓨터"의 부모를 그 하위인 "노트북"으로 바꾸면, 컴퓨터 > 노트북 > 컴퓨터 > …가 끝없이 이어져요. 방문 표시 없는 탐색은 끝나지 않고, UNION ALL로 쓴 재귀 쿼리는 무한히 행을 만들어요.

    • 저장할 때 막아요. 부모를 바꾸기 전에 새 부모가 내 하위인지 검사해요. 하위라면 거부해요.
    • 조회할 때도 상한을 둬요. 재귀 쿼리에 depth < 20 같은 조건을 넣어요. PostgreSQL 14부터는 CYCLE 절로 순환을 감지할 수 있고, MySQL 8은 재귀 횟수가 cte_max_recursion_depth(기본 1000)를 넘으면 에러로 멈춰요.

    운영에서 알아채는 법

    • 카테고리 페이지의 쿼리 시간을 지표로 남겨요. 트리가 커지면서 서서히 느려지는 것을 미리 볼 수 있어요.
    • 재귀 깊이 초과 에러가 로그에 보이면 순환을 먼저 의심해요.
    • 순환과 고아 노드(부모가 지워진 노드)를 찾는 검사 쿼리를 하루 한 번 배치로 돌려요.
    핵심 정리
    • 인접 리스트가 기본. BFS = 큐·최단 거리, DFS = 스택·사이클·경로
    • 위상 정렬 = DAG의 순서, 사이클이면 불가
    • 다익스트라 = 힙으로 가중치 최단 경로
    셀프 체크
    1. 마이크로서비스 배포 순서를 의존성에 따라 정하고, 순환 의존을 탐지하려면?
    답 보기

    서비스를 노드, "A가 B를 호출"을 A→B 간선으로 그래프를 만들고 위상 정렬. Kahn 알고리즘으로 진입 차수 0인 것부터 꺼내 큐에 넣고, 끝났는데 처리 안 된 노드가 남으면 그 노드들이 사이클이에요. 배포 순서는 위상 순서의 역(의존당하는 것 먼저).

    5부 알고리즘 기법

    7장 정렬과 탐색

    비교 정렬의 하한은 O(n log n)이에요. 더 빠르려면 비교를 안 해야 해요(기수 정렬). 안정 정렬은 같은 키의 원래 순서를 유지해요. "이름순 정렬 후 부서순 정렬"이 부서 안에서 이름순을 유지하려면 안정 정렬이어야 해요.

    외부 정렬

    메모리보다 큰 데이터: 메모리 크기만큼 잘라 정렬해 파일로 쓰고(run), 그 파일들을 K-way 병합(힙). DB의 filesort(DB 챕터 9장)가 정확히 이거예요. sort_buffer_size가 run 크기.

    이진 탐색

    정렬된 배열에서 O(log n). 구현이 쉬워 보이지만 off-by-one이 많아요. 변형이 중요해요.

    • lower_bound: x 이상인 첫 위치. upper_bound: x 초과인 첫 위치. 둘의 차가 x의 개수.
    • 답을 이진 탐색(parametric search): "조건을 만족하는 최소 값"을 찾을 때 값의 범위를 이진 탐색. "서버 N대로 처리 가능한가?"가 단조이면 최소 N을 log번 확인으로.

    DB B-Tree의 페이지 안에서 키를 찾는 것, 타임스탬프 정렬 로그에서 시간 범위 찾기, 버전 배열에서 "이 커밋이 포함된 첫 버전"(git bisect)이 이진 탐색이에요.

    투 포인터, 슬라이딩 윈도우

    정렬된 두 배열의 병합·교집합, 연속 구간의 합/최대 등을 O(n)에. "최근 1분 요청 수"를 큐로 유지하는 슬라이딩 윈도우 rate limiter가 이 기법이에요.

    백엔드에서는 Java Collections.sort(객체)는 팀소트(안정), Arrays.sort(int[])는 듀얼 피벗 퀵소트(불안정). 정렬 키가 같은 항목의 순서가 중요하면 compareTo에 두 번째 키를 넣어 명시하세요. "DB에서 정렬 vs 애플리케이션에서 정렬": DB가 인덱스로 할 수 있으면 DB, 아니면 데이터가 작을 때 애플리케이션. 수십만 건을 가져와 정렬하는 건 네트워크와 메모리 낭비예요.
    시니어 심화 본문은 정렬 키가 같을 때의 순서를 명시하라고 했는데, 비교 함수에는 더 위험한 실수가 있어요. 비교 함수가 규칙을 어기면 정렬이 예외를 던져요. 그것도 특정 데이터에서만요.

    상황

    정산 화면에서 주문을 생성 시각 순으로 정렬해요. 생성 시각은 밀리초 단위 long이고, 비교 함수는 (a, b) -> (int) (a.getCreatedAt() - b.getCreatedAt())로 썼어요. 테스트와 일주일치 조회는 멀쩡했는데, 운영에서 "최근 3개월" 조회를 하면 가끔 500 에러가 났어요.

    깨지는 과정

    1. 두 시각의 차이를 int로 바꾸면, 차이가 약 24.8일(2의 31제곱 밀리초)을 넘을 때 값이 잘려 부호가 엉뚱하게 나와요. 한 달 전 주문이 오늘 주문보다 "나중"이라고 판정될 수 있어요.
    2. 그러면 "A가 B보다 앞이고 B가 C보다 앞인데, C가 A보다 앞"인 모순이 생겨요. 비교 함수가 지켜야 하는 규칙(추이성)이 깨진 거예요.
    3. 자바의 객체 정렬(팀소트)은 정렬 도중 이 모순을 발견하면 IllegalArgumentException: Comparison method violates its general contract!를 던져요.
    4. 원소가 32개 미만이면 팀소트는 다른 경로로 정렬해서 예외 없이 조용히 틀린 순서를 돌려줘요. 그래서 작은 테스트 데이터로는 통과하고, 운영 데이터 수천 건과 한 달 넘는 기간이 겹칠 때만 터져요. 재현이 가장 어려운 종류의 버그예요.

    같은 규칙 위반은 다른 모양으로도 생겨요. NaN이 섞인 double을 <, >로 비교하면 NaN은 무엇과도 "같다"고 판정돼서 추이성이 깨져요. 정렬하는 동안 다른 스레드가 비교 대상 값을 바꿔도 마찬가지예요.

    해결책

    • 뺄셈 대신 비교 메서드를 써요. Long.compare(a, b), 또는 Comparator.comparingLong(Order::getCreatedAt).thenComparing(Order::getId)처럼 조립해요. 뒤에 붙인 ID 비교는 시각이 같은 주문의 순서도 고정해 줘요.
    • 실수는 Double.compare로 비교해요. NaN을 항상 가장 큰 값으로 일관되게 취급해요.
    • null은 규칙을 정해요. Comparator.nullsLast(...)로 감싸서 null의 위치를 명시해요.
    • 정렬 중에는 값이 바뀌지 않게 해요. 공유 컬렉션을 정렬한다면 복사본을 만들어 정렬해요.
    • 같은 넘침이 이진 탐색에도 있어요. 중간값을 (lo + hi) / 2로 구하면 인덱스가 클 때 넘쳐요. lo + (hi - lo) / 2로 써요. JDK의 Arrays.binarySearch에도 2006년까지 이 버그가 있었어요(컴퓨터 구조 챕터 1장).

    테스트와 운영에서 알아채는 법

    • 비교 함수 테스트에 극단값을 넣어요. Long.MIN_VALUE, Long.MAX_VALUE, 음수, null, NaN, 같은 값을 섞은 1만 건을 정렬하고, 결과가 실제로 정렬돼 있는지 인접한 원소끼리 검사해요. jqwik 같은 속성 기반 테스트 도구로 무작위 입력을 자동으로 만들 수도 있어요.
    • 로그에서 "Comparison method violates"를 검색하는 알림을 걸어 둬요. 이 메시지는 원인이 거의 항상 비교 함수예요.
    • 특정 조회 조건(긴 기간, 큰 페이지)에서만 500이 난다면 데이터 크기에 따라 경로가 달라지는 코드를 의심해요.
    핵심 정리
    • 비교 정렬 하한 n log n, 실무는 팀소트(안정)·퀵소트
    • 외부 정렬 = run + K-way 병합 = DB filesort
    • 이진 탐색은 lower/upper bound와 "답 찾기" 변형이 핵심
    셀프 체크
    1. 정렬된 타임스탬프 배열에서 [t1, t2] 구간의 이벤트 수를 O(log n)에 구하려면?
    답 보기

    upper_bound(t2) - lower_bound(t1). lower_bound(t1)은 t1 이상인 첫 인덱스, upper_bound(t2)는 t2 초과인 첫 인덱스. 둘 다 이진 탐색 O(log n).

    8장 재귀, 분할 정복, 동적 계획법, 그리디

    문제를 작게 쪼개는 네 가지 사고방식

    재귀

    함수가 자기를 호출. 기저 조건(멈추는 조건)과 재귀 조건(문제를 작게). 트리·그래프 순회, 디렉터리 탐색, JSON 파싱, 조합 생성에 자연스러워요. 깊이가 깊으면(1만 이상) 스택 오버플로 → 반복 + 명시적 스택.

    분할 정복

    문제를 독립된 부분 문제로 나눠 각각 풀고 합침. 병합 정렬, 퀵 정렬, 이진 탐색, 큰 수 곱셈(카라츠바). 부분 문제가 겹치지 않을 때. MapReduce가 분할 정복의 분산 버전이에요(분산 시스템 챕터 10장).

    동적 계획법 (DP)

    부분 문제가 겹칠 때 결과를 저장(메모이제이션)해 다시 안 풀기. 피보나치를 순진하게 재귀하면 O(2ⁿ), 저장하면 O(n). 조건: (1) 최적 부분 구조(큰 문제의 최적해가 작은 문제의 최적해로 구성), (2) 중복 부분 문제.

    • Top-down: 재귀 + 캐시(Map/배열). 직관적.
    • Bottom-up: 작은 것부터 표를 채움. 스택 안 씀, 빠름.

    대표 문제: 배낭 문제, 최장 공통 부분 수열(LCS, diff 알고리즘), 편집 거리(오타 교정, 유사도), 경로 수, 동전 거스름돈. 핵심은 상태를 정의하는 것: "dp[i][j] = i번째까지 고려하고 용량 j일 때 최대 가치".

    그리디

    매 단계 지금 가장 좋아 보이는 선택. 빠르지만 항상 최적은 아님. 최적이 보장되는 경우: 활동 선택(가장 빨리 끝나는 것부터), 허프만 코딩, 다익스트라, 크루스칼/프림(MST), 동전이 배수 관계일 때 거스름돈. 보장 안 되는 경우는 DP나 탐색. 증명이 어려우면 "반례가 있나?"를 먼저 찾으세요.

    백트래킹

    모든 경우를 DFS로 탐색하되 가망 없는 가지를 일찍 자름(가지치기). N-Queen, 스도쿠, 조합 최적화. 지수 시간이지만 가지치기로 실용적.

    백엔드에서는 DP는 직접 쓸 일이 드물지만 "메모이제이션"은 매일 써요. 캐시가 곧 메모이제이션이에요(같은 입력 → 저장된 출력). 비싼 계산 결과를 @Cacheable로 저장하는 것, 재귀적 권한 계산 결과를 요청 범위에서 캐시하는 것. 그리디는 "지금 가장 여유 있는 서버에 보내기"(least connections), "가장 빨리 끝날 작업부터"(SJF 스케줄링) 같은 휴리스틱으로 자주 쓰고, 전역 최적이 아님을 인지하면 돼요. 편집 거리는 검색 오타 교정, LCS는 텍스트 diff·버전 비교에 들어가요.
    시니어 심화 본문은 메모이제이션이 곧 캐시라고 했는데, 메모이제이션을 서비스의 캐시로 키우는 순간 문제의 본질이 바뀌어요. 계산이 아니라 무효화가 어려워져요.

    상황

    상품 상세 화면의 "내 최종 가격"은 계산이 무거워서 @Cacheable(key = "#memberId + ':' + #productId")로 1시간 캐시했어요. 순수한 함수(같은 입력이면 항상 같은 출력)라면 이것으로 충분해요. 그런데 이 계산은 회원 ID와 상품 ID만으로 결과가 정해지지 않아요.

    깨지는 과정

    계산 결과가 실제로 의존하는 입력은 상품 가격, 회원 등급, 보유 쿠폰, 진행 중인 행사, 그리고 현재 시각(행사 기간 안인지)이에요. 키에는 그중 둘만 들어 있어요.

    1. 오전 9시에 회원의 최종 가격을 계산해 캐시에 넣어요.
    2. 9시 10분에 회원이 VIP로 승급해요. 캐시는 그대로라서 50분 동안 VIP 할인이 빠진 가격이 보여요. 고객 문의가 들어와요.
    3. 10시에 타임 세일이 끝나요. 9시 30분에 계산된 캐시에는 세일 가격이 남아 있어요. 세일이 끝난 뒤에도 30분 동안 할인 가격이 보여요.
    4. 결제 금액도 이 캐시를 읽는다면, 화면 문제가 아니라 실제 손실이 돼요.

    해결책

    방법은 두 방향이에요. 의존하는 입력이 바뀌면 키가 자동으로 달라지게 하거나, 입력이 바뀔 때 캐시를 지우는 경로를 만들어요.

    • 입력의 버전을 키에 넣어요. 회원 등급이 바뀔 때마다 오르는 "회원 버전"과 가격 정책이 바뀔 때마다 오르는 "정책 버전"을 키에 포함해요(price:{member}:{product}:{memberVer}:{policyVer}). 입력이 바뀌면 새 키를 쓰니까 지우는 코드가 필요 없고, 옛 키는 TTL로 사라져요. 대신 조회할 때마다 버전을 읽는 비용이 들어요.
    • 변경 이벤트로 지워요. 등급이 바뀌면 그 회원의 가격 캐시를 모두 지워요. 이때 키를 패턴으로 찾으면 안 돼요(Redis의 KEYS는 서버를 멈춰요). 회원별로 해시 하나에 상품별 필드로 저장해 두면 해시 하나를 지우는 것으로 끝나요.
    • 시각에 의존하는 입력은 TTL로 다뤄요. TTL을 "1시간"과 "행사 종료까지 남은 시간" 중 짧은 쪽으로 정해요. 행사가 끝나는 순간 캐시도 끝나요.
    • 표시용 계산과 결제용 계산을 분리해요. 캐시는 화면 표시에만 쓰고, 결제 시점에는 항상 캐시 없이 다시 계산해요. 위의 방법이 다 실패해도 돈은 틀리지 않게 하는, 가장 중요한 안전장치예요.

    대가: 키에 입력을 많이 넣을수록 같은 키가 다시 쓰일 확률(적중률)이 떨어져요. 그래서 시각처럼 계속 바뀌는 입력에 강하게 의존하는 계산은 애초에 캐시 대상이 아닐 수도 있어요.

    운영에서 알아채는 법

    • 결제할 때 다시 계산한 가격과 화면에 보여 준 가격이 다른 건수를 지표로 남겨요. 캐시가 얼마나 틀리는지를 직접 재는 지표예요.
    • "보이는 가격과 결제 가격이 다르다"는 고객 문의가 특정 시각(행사 종료, 등급 변경 배치 직후)에 몰린다면 무효화 경로가 빠진 입력이 있다는 신호예요.
    핵심 정리
    • 분할 정복 = 독립 부분 문제, DP = 겹치는 부분 문제 + 저장
    • DP 핵심 = 상태 정의. 캐시 = 메모이제이션
    • 그리디 = 빠르지만 최적 보장은 증명 필요, 반례부터
    셀프 체크
    1. 분할 정복과 DP의 차이를 한 문장으로.
    2. 동전 {1, 3, 4}로 6원을 거슬러 줄 때 그리디가 실패하는 이유는?
    답 보기

    1. 둘 다 문제를 쪼개지만, 분할 정복은 부분 문제가 독립이라 각각 풀고, DP는 부분 문제가 겹쳐서 결과를 저장해 재사용해요.

    2. 그리디는 4 → 1 → 1로 3개. 최적은 3 + 3으로 2개. 동전이 배수 관계가 아니면 "지금 가장 큰 동전"이 전역 최적을 보장하지 않아요. DP로 dp[금액] = min(dp[금액 − 동전] + 1).

    6부 실무 자료구조

    9장 캐시 교체와 레이트 리미터

    LRU/LFU 구현, 토큰 버킷, 슬라이딩 윈도우 — 직접 구현해 볼 가치가 있는 것들

    LRU 캐시

    가장 오래 안 쓴 것을 버림. HashMap + 이중 연결 리스트로 get/put 모두 O(1).

    • HashMap: 키 → 리스트 노드. 바로 찾기.
    • 이중 연결 리스트: 사용 순서. get/put하면 노드를 맨 앞으로 옮기고(O(1), 양쪽 포인터 있으니까), 꽉 차면 맨 뒤를 제거.

    Java: new LinkedHashMap<>(cap, 0.75f, true) + removeEldestEntry 오버라이드. 정확한 LRU는 접근마다 리스트 갱신이 필요해서 동시성이 높으면 락 경합이 커요. 그래서 Redis는 샘플링 근사 LRU(OS 챕터 22장 Clock과 같은 이유), Caffeine은 Window TinyLFU를 써요.

    LFU

    가장 적게 쓴 것을 버림. 빈도별 리스트 + HashMap으로 O(1) 구현 가능. 오래된 인기 항목이 안 빠지는 문제(cache pollution)가 있어 시간 감쇠를 넣어요. Redis allkeys-lfu는 로그 카운터 + 감쇠.

    레이트 리미터

    알고리즘동작특징
    고정 윈도우1분 단위로 카운트단순. 경계에서 2배 허용(59초에 100, 61초에 100)
    슬라이딩 로그요청 타임스탬프를 전부 저장, 최근 1분 것만 세기정확, 메모리 큼
    슬라이딩 윈도우 카운터이전 윈도우 카운트 × 겹친 비율 + 현재 카운트근사, 메모리 작음. 실무 표준
    토큰 버킷초당 r개 토큰 보충, 최대 b개. 요청마다 토큰 1개 소비순간 burst(b개) 허용, 평균 r/초. AWS API, Nginx limit_req(burst)
    리키 버킷큐에 넣고 일정 속도로 처리출력이 균일. burst 흡수가 아니라 평탄화

    토큰 버킷 구현: 마지막 보충 시각과 토큰 수만 저장. 요청 시 tokens = min(b, tokens + (now − last) × r)로 지연 계산. 저장 공간 O(1). 분산 환경이면 Redis에 Lua 스크립트로 원자적 실행.

    타이밍 휠

    타이머가 수십만 개일 때 힙(O(log n))도 부담. 시계처럼 슬롯 배열을 돌며 각 슬롯의 리스트를 처리. 삽입·삭제 O(1). Netty, Kafka(지연 작업), 커널 타이머.

    백엔드에서는 로컬 캐시는 Caffeine(기본 선택), 분산 캐시는 Redis. 레이트 리밋은 게이트웨이(Nginx, Spring Cloud Gateway, Envoy)에서 토큰 버킷으로, 사용자별이면 Redis + Lua. 직접 구현할 일이 있다면 LRU와 토큰 버킷은 각각 30줄 안에 나오니 한 번은 손으로 짜 보세요. 면접 단골이기도 해요.
    시니어 심화 본문은 사용자별 레이트 리밋을 Redis + Lua로 한다고 했는데, 여러 서버가 한도를 나눠 지키는 방식에는 정확성과 비용 사이의 선택이 있어요.

    상황

    공개 상품 API에 회원당 분당 600회 제한을 걸어요. API 서버는 10대이고, 피크 때 초당 10만 요청이 들어와요. 어느 서버로 요청이 가든 한 회원의 합계가 600을 넘지 않아야 해요.

    네 가지 방식

    • 요청마다 Redis에서 세기: INCR과 EXPIRE를 Lua 스크립트로 묶어 원자적으로 실행해요. 가장 정확해요. 대신 모든 요청에 Redis 왕복(보통 0.5~1ms)이 하나씩 붙고, 피크 때 Redis가 초당 10만 건을 받아야 해요. 그리고 Redis가 멈추면 레이트 리밋도 같이 멈춰요.
    • 서버마다 나눠 갖기: 서버마다 "600 ÷ 10 = 60"을 따로 지켜요. Redis 왕복이 없어요. 하지만 로드밸런서가 연결 단위로 나누면(keep-alive 연결은 한 서버에 붙어 있어요) 한 회원의 요청이 대부분 한 서버로 가서, 그 회원은 60에서 막혀요. 서버 수가 바뀔 때마다 몫도 다시 계산해야 해요.
    • 토큰을 묶음으로 받아 오기: 서버가 Redis에서 토큰을 20개씩 받아 와서(DECRBY 20) 로컬에서 하나씩 써요. 왕복이 1/20로 줄어요. 토큰은 공용 풀에서만 나오니 한도를 넘지는 않아요. 다만 서버들이 받아 놓고 아직 안 쓴 토큰만큼 다른 서버에서 조금 일찍 막힐 수 있어요.
    • 로컬에서 세고 주기적으로 합치기: 서버마다 로컬에서 세다가 1초마다 Redis에 합계를 보내고 전체 합계를 받아 와요. Redis 부하가 가장 적지만, 1초 사이에는 한도를 넘을 수 있어요. 남용 감지처럼 대략 맞으면 되는 곳에 맞아요.

    Redis가 응답하지 않을 때

    어떤 방식이든 Redis에 의존한다면 Redis 장애 때 어떻게 할지를 미리 정해야 해요. 정하지 않으면 레이트 리밋이 서비스 전체 장애의 원인이 돼요.

    • 통과(fail-open)와 차단(fail-closed) 중에 골라요. 목적이 남용 방지라면 잠깐 막지 못해도 큰일이 아니니 통과시켜요. 목적이 하위 시스템(DB, 외부 결제사) 보호라면 차단해요.
    • Redis 호출에 짧은 타임아웃을 둬요. 클라이언트 기본 타임아웃이 몇 초라면, Redis가 느려지는 순간 모든 API가 몇 초씩 느려져요. 레이트 리밋 확인은 50ms 정도면 충분해요.
    • 연속으로 실패하면 로컬 모드로 내려가요. 서킷 브레이커로 Redis 실패를 감지하면 "서버마다 나눠 갖기" 방식으로 잠시 바꿔요. 부정확하지만 아예 제한이 없는 것보다 나아요.

    운영에서 알아채는 법

    • 회원별 거절(429) 비율을 지표로 남겨요. 정상 사용 패턴인데 거절이 많은 회원이 있다면 한도가 서버별로 쪼개져 있는지 확인해요.
    • 레이트 리밋 확인에 걸리는 시간(Redis 왕복 포함)을 API 응답 시간과 따로 봐요.
    • 로컬 모드로 내려간 횟수와 시간을 남겨요. 자주 내려간다면 Redis 쪽 용량을 먼저 봐야 해요.
    핵심 정리
    • LRU = HashMap + 이중 연결 리스트, O(1). 실무는 근사 LRU/TinyLFU
    • 토큰 버킷 = burst 허용 + 평균 제한, O(1) 저장. 슬라이딩 윈도우 카운터 = 경계 문제 완화
    셀프 체크
    1. LRU에서 이중 연결 리스트가 단일 연결 리스트면 안 되는 이유는?
    2. 고정 윈도우의 경계 문제를 설명하고 토큰 버킷이 어떻게 다른지.
    답 보기

    1. 중간 노드를 맨 앞으로 옮기려면 그 노드의 이전 노드의 next를 바꿔야 해요. 단일 연결이면 이전 노드를 찾으려고 처음부터 순회(O(n)). 이중 연결이면 prev 포인터로 O(1).

    2. 분당 100 제한에서 0:59에 100개, 1:01에 100개면 2초 안에 200개가 통과해요. 토큰 버킷은 시간에 비례해 토큰이 차고(초당 1.67개) 버킷 용량(예: 100)만큼만 burst를 허용해서, 100개를 쓰면 다시 쌓일 때까지 기다려야 해요. 경계가 없어요.

    백엔드에서는 새 시스템을 만날 때 "내부 자료구조가 뭐지?"를 물어보면 성능 특성이 보여요. Kafka가 왜 순차 읽기만 빠른지(로그), Redis ZSET이 왜 O(log n)인지(스킵 리스트), Elasticsearch가 왜 쓰기 직후 검색이 안 되는지(세그먼트 refresh), Cassandra가 왜 쓰기는 빠른데 읽기 증폭이 있는지(LSM). 자료구조를 알면 문서의 "제한 사항"이 왜 있는지 납득이 돼요.

    • Redis 타입마다 내부 구조가 복잡도를 결정
    • "내부 자료구조가 뭐지?"가 시스템 이해의 출발점
    셀프 체크
    1. B+Tree 기반 DB와 LSM 기반 DB의 읽기·쓰기 특성 차이를 자료구조로 설명하세요.
    답 보기

    B+Tree는 제자리 갱신이라 쓰기가 랜덤 I/O(페이지 찾아서 수정), 읽기는 높이만큼(3~4번)으로 안정적. LSM은 쓰기를 메모리(memtable)에 모아 정렬된 파일(SSTable)로 순차 쓰기라 쓰기 처리량이 높지만, 읽기는 여러 SSTable을 확인해야 해서 읽기 증폭이 있고 Bloom filter로 완화. 백그라운드 컴팩션이 CPU·I/O를 써요. 쓰기 위주(로그, 시계열)는 LSM, 읽기 위주(OLTP)는 B+Tree.
