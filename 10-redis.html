    Redis

    기준 자료: Redis 공식 문서 + 개발자를 위한 레디스 · 2~3주

    Redis는 "빠른 캐시"로만 쓰이다가 장애가 난 뒤에야 내부를 들여다보게 되는 시스템이에요. 이 챕터는 왜 빠른지, 무엇을 하면 느려지는지, 데이터가 언제 사라질 수 있는지를 구조에서부터 정리해요.

    캐시 전략(cache-aside, 스탬피드 등)은 분산 시스템 챕터 부록에서 다뤘어요. 여기서는 Redis 자체에 집중해요. 시간이 없으면 1장(단일 스레드), 3장(만료와 메모리), 7장(분산 락과 원자성)을 먼저 읽으세요.

    Redis 공식 문서 기준 자료redis.io/docs · 명령마다 시간 복잡도가 적혀 있음
    개발자를 위한 레디스 입문운영 관점까지 한국어로
    1부 실행 모델과 자료형

    1장 단일 스레드 모델과 명령 복잡도

    빠른 이유와 느려지는 이유가 같은 곳에 있다

    명령은 한 번에 하나씩

    Redis는 명령 실행을 스레드 하나로 해요. 이벤트 루프가 여러 연결에서 온 명령을 차례로 꺼내 실행하고 응답해요. 데이터가 전부 메모리에 있어서 명령 하나가 마이크로초 단위로 끝나고, 락이 필요 없어서 단순하고 빨라요.

    최근 버전은 네트워크 읽기·쓰기에 여러 스레드를 쓸 수 있지만 명령 실행은 여전히 직렬이에요.

    결과: 모든 명령이 원자적

    명령 하나가 실행되는 도중에 다른 명령이 끼어들지 못해요. INCR가 락 없이 안전한 이유예요.

    대가: 느린 명령 하나가 전체를 멈춘다

    명령 하나가 100ms 걸리면 그동안 다른 모든 클라이언트가 기다려요. 그래서 명령의 시간 복잡도가 중요해요.

    위험한 명령이유대안
    KEYS *전체 키 순회, O(N)SCAN으로 조금씩
    SMEMBERS, HGETALL, LRANGE 0 -1큰 컬렉션 전체 반환SSCAN, HSCAN, 범위 제한
    DEL (큰 키)원소 수만큼 메모리 해제UNLINK(백그라운드 해제)
    FLUSHALL전체 삭제ASYNC 옵션, 운영에서는 금지

    왕복이 진짜 비용

    명령 실행은 마이크로초지만 네트워크 왕복은 그보다 수백 배 길어요. 명령 100개를 하나씩 보내면 왕복 100번이에요. 파이프라인으로 묶어 보내면 왕복 한 번이에요.

    백엔드에서는 "Redis가 느려졌다"의 대부분은 Redis가 아니라 누군가 보낸 느린 명령이에요. SLOWLOG GET으로 오래 걸린 명령을 확인하세요. 운영 환경에서는 KEYS, FLUSHALL 같은 명령을 설정으로 막거나 이름을 바꿔 두는 것이 사고를 줄여요.
    시니어 심화
    • 지연의 원인은 명령만이 아니에요. 스냅샷을 위한 fork, 디스크 동기화, 많은 키의 동시 만료, 큰 키의 삭제도 이벤트 루프를 멈춰요. LATENCY DOCTOR와 지연 모니터가 원인별 기록을 보여줘요.
    • 큰 키(big key)는 느린 명령, 느린 삭제, 클러스터 이동 지연의 공통 원인이에요. 주기적으로 찾아서 쪼개요. 원소 수백만 개짜리 해시 하나보다 키 여러 개가 나아요.
    • 코어가 여러 개여도 Redis 프로세스 하나는 코어 하나만 써요. 처리량을 늘리는 방법은 인스턴스를 늘려 데이터를 나누는 것(클러스터)이에요.
    핵심 정리
    • 명령 실행은 단일 스레드 → 모든 명령이 원자적, 락 불필요
    • 느린 명령 하나가 전체를 막음. O(N) 명령과 큰 키 주의
    • 왕복을 줄이는 것이 최적화의 중심(파이프라인)
    셀프 체크
    1. 운영 중인 Redis에서 KEYS user:* 를 실행하면 어떤 일이 일어나나요?
    답 보기

    KEYS는 전체 키 공간을 한 번에 순회하는 O(N) 명령이에요. 키가 수백만 개면 수백 밀리초에서 수 초가 걸리고, 명령 실행이 단일 스레드이므로 그동안 다른 모든 클라이언트의 명령이 대기해요. 서비스 전체가 그 시간만큼 멈추고 타임아웃이 연쇄적으로 발생해요. 같은 일을 SCAN으로 하면 커서를 따라 조금씩 나눠 순회하므로 사이사이에 다른 명령이 실행돼요.

    2장 자료형과 활용 패턴

    문제에 맞는 자료형을 고르면 코드가 사라진다

    자료형과 대표 용도

    자료형핵심 연산쓰는 곳
    StringGET/SET, INCR, SET NX EX캐시, 카운터, 락, 플래그
    HashHGET/HSET, HINCRBY객체의 필드별 저장, 필드 단위 갱신
    ListLPUSH/RPOP, BRPOP단순 큐, 최근 N개
    SetSADD, SISMEMBER, 교집합·합집합중복 제거, 태그, 포함 여부
    Sorted SetZADD, ZRANGE, ZRANGEBYSCORE랭킹, 시간순 인덱스, 지연 큐
    StreamXADD, XREADGROUP, XACK소비자 그룹이 있는 메시지 로그
    HyperLogLogPFADD, PFCOUNT고유 방문자 수 근사
    BitmapSETBIT, BITCOUNT일별 출석, 플래그 대량 저장

    패턴 몇 가지

    • 랭킹: ZADD board 점수 사용자, 상위 10명은 ZREVRANGE board 0 9, 내 순위는 ZREVRANK. 전부 O(log N).
    • 레이트 리밋: INCR 후 첫 증가일 때만 EXPIRE. 두 명령 사이가 끊기면 만료 없는 키가 남으니 Lua로 묶거나 SET NX EX로 시작해요.
    • 최근 본 항목: LPUSH 후 LTRIM 0 99로 길이 고정.
    • 지연 큐: 실행 시각을 점수로 Sorted Set에 넣고, 현재 시각 이하인 것을 꺼내요.

    Pub/Sub과 Stream의 차이

    Pub/Sub은 보내는 순간 구독 중인 클라이언트에게만 전달하고 저장하지 않아요. 구독자가 잠깐 끊기면 그 사이 메시지는 사라져요. Stream은 로그로 저장하고 소비자 그룹이 어디까지 처리했는지 기억해요.

    백엔드에서는 객체를 JSON 문자열로 String에 넣을지 Hash로 넣을지는 접근 패턴으로 정해요. 항상 통째로 읽고 쓰면 String이 단순해요. 필드 하나만 자주 바꾸거나 읽으면 Hash가 맞아요. String에 넣고 필드 하나를 바꾸려고 읽기-수정-쓰기를 하면 동시 갱신에서 값이 덮어써져요.
    시니어 심화
    • List를 큐로 쓸 때의 유실: 워커가 꺼낸 뒤 처리 중에 죽으면 메시지가 사라져요. 꺼내면서 처리 중 목록으로 옮기는 방식(LMOVE)이나 확인 응답이 있는 Stream을 써요. 신뢰성이 중요한 큐라면 전용 메시지 브로커가 맞아요.
    • 작은 컬렉션은 압축 인코딩으로 저장돼요. 원소 수나 값 크기가 임계값을 넘으면 일반 구조로 바뀌면서 메모리 사용량이 몇 배로 뛰어요. 작은 해시 여러 개로 나눠 담는 것이 메모리 절약 기법으로 쓰이는 이유예요.
    • 키 이름에 규칙을 두세요(서비스:엔티티:ID). 규칙이 없으면 어떤 키가 누구 것인지, 지워도 되는지 아무도 모르게 돼요.
    핵심 정리
    • 자료형마다 연산과 복잡도가 다름. 용도에 맞게 선택
    • Sorted Set = 랭킹·시간 인덱스·지연 큐
    • Pub/Sub은 저장 안 함, Stream은 저장 + 소비 위치 추적
    셀프 체크
    1. 실시간 랭킹을 DB의 ORDER BY 대신 Sorted Set으로 구현하면 좋은 이유를 설명하세요.
    답 보기

    Sorted Set은 점수 순서로 정렬된 구조를 항상 유지해요. 점수 갱신, 상위 N명 조회, 특정 사용자의 순위 조회가 모두 O(log N)이에요. DB에서는 점수가 바뀔 때마다 인덱스를 갱신해야 하고, 특정 사용자의 순위를 구하려면 그보다 점수가 높은 행을 세어야 해서 데이터가 많을수록 느려져요. 점수가 자주 바뀌고 순위 조회가 많은 워크로드에 Sorted Set이 잘 맞아요.

    3장 만료와 메모리 관리

    메모리가 찼을 때 무슨 일이 일어나는가

    만료는 두 방식으로 처리된다

    • 수동(lazy): 키에 접근할 때 만료됐는지 확인하고, 만료됐으면 그때 지워요.
    • 능동(active): 주기적으로 만료 시간이 있는 키 중 일부를 무작위로 뽑아 만료된 것을 지워요.

    그래서 만료된 키가 즉시 메모리에서 사라지지 않아요. 접근하지 않는 만료 키는 능동 삭제가 닿을 때까지 메모리를 차지해요.

    메모리 한도와 제거 정책

    maxmemory에 도달하면 maxmemory-policy에 따라 동작해요.

    정책동작
    noeviction지우지 않고 쓰기 명령에 에러 반환
    allkeys-lru모든 키 중 오래 안 쓴 것부터 제거
    allkeys-lfu모든 키 중 덜 자주 쓴 것부터 제거
    volatile-lru / volatile-ttl만료 시간이 있는 키 중에서만 제거

    Redis의 LRU는 근사예요. 전체를 정렬하지 않고 몇 개를 뽑아 그중 가장 오래된 것을 지워요.

    용도에 따라 정책이 다르다

    • 캐시: 지워져도 다시 채울 수 있으니 allkeys-lru나 allkeys-lfu.
    • 사라지면 안 되는 데이터(세션, 락, 큐): 제거 정책에 맡기면 안 돼요. noeviction으로 두고 용량을 관리해요.

    둘을 한 인스턴스에 섞으면 어느 정책도 맞지 않아요. 캐시용과 저장용 인스턴스를 분리하세요.

    백엔드에서는 모든 캐시 키에 TTL을 주세요. TTL 없는 키는 아무도 지우지 않는 한 영원히 남아서, 메모리가 서서히 차다가 어느 날 제거가 시작되거나 쓰기가 거부돼요. 그리고 많은 키에 같은 TTL을 주면 같은 순간에 한꺼번에 만료돼요. TTL에 무작위 값을 조금 더해 흩어 놓으세요.
    시니어 심화
    • 메모리 사용량과 OS가 보는 사용량은 달라요. 할당과 해제를 반복하면 단편화로 실제 점유(RSS)가 데이터 크기보다 커져요. INFO memory의 단편화 비율을 보고, 높으면 능동 조각 모음 설정을 검토해요.
    • maxmemory는 프로세스 전체 한도가 아니에요. 복제 버퍼, 클라이언트 출력 버퍼, 스냅샷 중의 복사본은 그 밖이에요. 컨테이너 한도는 maxmemory보다 넉넉하게 잡아야 OOM으로 죽지 않아요.
    • 느린 클라이언트의 출력 버퍼: 응답을 제때 읽지 않는 클라이언트(느린 구독자, 큰 결과를 요청한 클라이언트)가 있으면 서버 쪽에 응답이 쌓여요. 버퍼 한도 설정이 이런 클라이언트를 끊어 줘요.
    핵심 정리
    • 만료 키는 즉시 지워지지 않음(접근 시 + 주기적 샘플링)
    • maxmemory 도달 시 정책에 따라 제거 또는 쓰기 거부
    • 캐시용과 저장용 인스턴스 분리. 모든 캐시 키에 TTL + 지터
    셀프 체크
    1. 세션과 캐시를 같은 Redis 인스턴스에 두고 allkeys-lru를 쓰면 어떤 문제가 생기나요?
    답 보기

    메모리가 한도에 닿으면 Redis는 캐시와 세션을 구분하지 않고 오래 안 쓴 키부터 지워요. 캐시 데이터가 늘어나 메모리를 채우면 활동이 뜸했던 사용자의 세션이 지워져서 그 사용자들이 갑자기 로그아웃돼요. 그렇다고 noeviction으로 바꾸면 캐시가 메모리를 채웠을 때 세션 쓰기까지 거부돼요. 지워져도 되는 데이터와 안 되는 데이터는 요구하는 정책이 반대이므로 인스턴스를 나눠야 해요.

    2부 내구성과 가용성

    4장 영속화 — RDB와 AOF

    재시작하면 데이터가 얼마나 남는가

    RDB: 시점 스냅샷

    특정 시점의 전체 데이터를 파일 하나로 저장해요. 자식 프로세스를 fork해서 그 프로세스가 디스크에 쓰고, 부모는 계속 명령을 처리해요. 메모리는 copy-on-write로 공유돼요.

    • 파일이 작고 복구가 빨라요. 백업에 적합해요.
    • 마지막 스냅샷 이후의 변경은 전부 유실돼요.

    AOF: 쓰기 명령 로그

    데이터를 바꾸는 명령을 파일 끝에 계속 덧붙여요. 재시작하면 로그를 처음부터 다시 실행해 복구해요. 디스크 동기화 시점이 유실 범위를 정해요.

    appendfsync동기화최대 유실
    always명령마다거의 없음. 가장 느림
    everysec1초마다약 1초
    noOS에 맡김수십 초 가능

    로그는 계속 커지므로 주기적으로 재작성해요. 현재 데이터를 만드는 최소한의 명령으로 줄이는 작업이고, 이것도 fork를 써요.

    함께 쓰기

    두 방식을 같이 켜면 재시작 때 AOF를 우선 사용해요. 스냅샷을 앞부분에 두고 그 뒤의 변경만 명령 로그로 붙이는 혼합 형식이 복구 속도와 유실 범위를 함께 잡아요.

    백엔드에서는 순수 캐시라면 영속화를 꺼도 돼요. 재시작하면 비어 있지만 다시 채우면 되고, fork와 디스크 쓰기로 인한 지연이 없어져요. 반대로 세션, 큐, 카운터처럼 사라지면 곤란한 데이터를 넣었다면 지금 설정에서 최대 몇 초의 데이터를 잃는지를 팀이 알고 있어야 해요.
    시니어 심화
    • fork의 비용: 데이터가 클수록 페이지 테이블 복사에 시간이 걸리고 그동안 Redis가 멈춰요. 스냅샷 중에 쓰기가 많으면 수정된 페이지가 복사돼 메모리 사용량이 크게 늘어요. 메모리 한도를 데이터 크기에 딱 맞추면 스냅샷 중에 OOM이 나요.
    • 디스크가 느리면 명령도 느려져요. everysec에서도 이전 동기화가 끝나지 않았으면 쓰기가 기다려요. 스냅샷과 AOF 재작성이 겹치면 디스크 I/O가 경합해요.
    • 복제본에서만 영속화하고 주 서버는 끄는 구성에서, 주 서버가 빈 채로 재시작하면 복제본이 그 빈 상태를 복제해 데이터 전체가 사라져요. 자동 재시작과 이 구성을 같이 쓰면 안 돼요.
    핵심 정리
    • RDB = 스냅샷(빠른 복구, 마지막 스냅샷 이후 유실)
    • AOF = 명령 로그(appendfsync가 유실 범위 결정)
    • 캐시는 꺼도 됨. 저장용이면 유실 범위를 숫자로 알고 있을 것
    셀프 체크
    1. appendfsync everysec 설정에서 "커밋된 데이터는 안전하다"고 말할 수 없는 이유는 무엇인가요?
    답 보기

    Redis는 명령을 실행하고 클라이언트에게 성공을 응답한 뒤, 최대 1초 후에야 그 내용을 디스크에 동기화해요. 응답과 동기화 사이에 서버가 죽으면 클라이언트는 성공으로 알고 있는 쓰기가 사라져요. 관계형 DB의 커밋처럼 "성공 응답 = 디스크에 기록됨"이 아니에요. 그 보장이 필요하면 always로 두어야 하는데 처리량이 크게 떨어지므로, 그런 데이터는 Redis가 아닌 저장소에 두는 것이 보통이에요.

    5장 복제와 Sentinel

    비동기 복제가 만드는 유실 구간

    복제의 동작

    1. 복제본이 연결하면 주 서버가 스냅샷을 만들어 보낸다(전체 동기화).
    2. 그 뒤로는 주 서버가 실행한 쓰기 명령을 계속 흘려보낸다.
    3. 잠깐 끊겼다 다시 붙으면, 주 서버가 최근 명령을 담아 둔 버퍼(백로그)에서 빠진 부분만 보낸다(부분 동기화). 버퍼를 벗어났으면 다시 전체 동기화.

    복제는 비동기

    주 서버는 복제본의 확인을 기다리지 않고 클라이언트에게 응답해요. 주 서버가 죽으면 아직 복제본에 도달하지 않은 쓰기는 사라져요. WAIT 명령으로 복제본 몇 대가 받을 때까지 기다릴 수 있지만, 강한 일관성을 보장하는 것은 아니에요.

    Sentinel: 자동 장애 조치

    별도의 Sentinel 프로세스 여러 개가 주 서버를 감시해요.

    • Sentinel 하나가 응답 없음을 감지하고, 정족수 이상이 동의하면 장애로 판정해요.
    • 복제본 하나를 주 서버로 승격하고 나머지를 새 주 서버에 붙여요.
    • 클라이언트는 Sentinel에게 현재 주 서버 주소를 물어 연결해요.

    Sentinel은 과반수 합의가 가능하도록 최소 3대를 서로 다른 장애 영역에 둬요.

    스플릿 브레인

    네트워크가 갈려 옛 주 서버가 일부 클라이언트와 함께 고립되면, 반대편에서는 새 주 서버가 뽑혀요. 고립된 쪽 클라이언트가 옛 주 서버에 쓴 데이터는 네트워크가 복구될 때 옛 주 서버가 복제본으로 강등되면서 전부 버려져요.

    min-replicas-to-write를 설정하면 연결된 복제본이 일정 수 미만일 때 주 서버가 쓰기를 거부해서 유실 구간을 줄여요.

    백엔드에서는 복제본에서 읽으면 방금 쓴 값이 안 보일 수 있어요. 그리고 만료 처리는 주 서버가 주도하므로 복제본의 동작이 미묘하게 달라요. 클라이언트 라이브러리가 장애 조치 후 새 주 서버로 자동 전환하는지, 전환에 얼마나 걸리는지는 실제로 주 서버를 죽여 보고 확인하세요. 설정만 봐서는 알 수 없어요.
    핵심 정리
    • 전체 동기화 → 명령 스트림. 재연결 시 백로그 안이면 부분 동기화
    • 비동기 복제라 장애 조치 시 최근 쓰기 유실 가능
    • Sentinel 3대 이상. 스플릿 브레인의 쓰기는 버려짐
    셀프 체크
    1. Redis 주 서버가 죽고 Sentinel이 복제본을 승격했습니다. 클라이언트가 성공 응답을 받은 쓰기가 사라질 수 있는 이유를 설명하세요.
    답 보기

    Redis 복제는 비동기라서 주 서버는 명령을 실행하고 복제본에 전달되기를 기다리지 않은 채 클라이언트에게 성공을 응답해요. 주 서버가 그 직후에 죽으면 그 명령은 복제본에 도달하지 못했을 수 있어요. 승격된 복제본은 그 쓰기를 모르는 상태에서 새 주 서버가 되고, 옛 주 서버가 돌아와도 새 주 서버의 데이터로 덮어쓰므로 그 쓰기는 복구되지 않아요.

    6장 Redis Cluster

    데이터를 여러 노드에 나눈다

    해시 슬롯

    키 공간을 16384개의 슬롯으로 나누고, 각 슬롯을 주 서버 중 하나에 배정해요. 키의 슬롯은 키 이름의 CRC16 값을 16384로 나눈 나머지예요. 노드를 추가하면 슬롯 일부를 새 노드로 옮겨요.

    클라이언트가 라우팅한다

    중간 프록시가 없어요. 클라이언트가 슬롯-노드 대응표를 갖고 직접 맞는 노드로 보내요. 잘못 보내면 노드가 리다이렉트로 알려줘요.

    • MOVED: 그 슬롯은 이제 저 노드 것. 대응표를 갱신해요.
    • ASK: 그 슬롯이 옮겨지는 중. 이번 한 번만 저 노드로.

    여러 키 명령의 제약

    여러 키를 다루는 명령(MGET, 트랜잭션, Lua 스크립트)은 모든 키가 같은 슬롯에 있어야 해요. 서로 다른 노드에 걸친 원자적 연산은 지원하지 않아요.

    해시 태그: 키 이름에 중괄호가 있으면 그 안의 부분만으로 슬롯을 계산해요. {user:42}:profile과 {user:42}:cart는 같은 슬롯에 놓여요.

    장애 조치

    노드들이 서로 상태를 주고받다가(가십), 주 서버 과반수가 어떤 주 서버를 장애로 판정하면 그 복제본 중 하나가 승격돼요. 복제는 여기서도 비동기라 유실 구간이 있어요. 과반수의 주 서버와 연결이 끊긴 쪽은 쓰기를 멈춰요.

    운영에서 만나는 문제

    • 핫 키: 한 키에 요청이 몰리면 그 키가 있는 노드만 바빠요. 클러스터를 늘려도 풀리지 않아요.
    • 큰 키의 이동: 슬롯을 옮길 때 키 하나는 통째로 옮겨져요. 큰 키는 그동안 양쪽 노드를 멈춰요.
    • 해시 태그 남용: 많은 키를 같은 태그로 묶으면 한 슬롯에 쏠려요.
    백엔드에서는 단일 인스턴스에서 클러스터로 옮기면 여러 키를 한 번에 다루던 코드가 깨져요. CROSSSLOT 에러가 그거예요. 파이프라인도 라이브러리가 노드별로 나눠 보내 주는지 확인해야 해요. 처음부터 "함께 원자적으로 다뤄야 하는 키"가 무엇인지 정해서 해시 태그로 묶어 설계하세요.
    핵심 정리
    • 16384 슬롯을 노드에 배정. 클라이언트가 직접 라우팅(MOVED/ASK)
    • 여러 키 연산은 같은 슬롯 안에서만. 해시 태그로 묶음
    • 핫 키와 큰 키는 클러스터로 해결되지 않음
    셀프 체크
    1. Redis Cluster에서 MGET user:1 user:2 user:3 이 실패하는 이유와 해결 방법을 말해보세요.
    답 보기

    세 키의 슬롯이 서로 다르면 서로 다른 노드에 있을 수 있고, 클러스터는 여러 슬롯에 걸친 명령을 하나의 명령으로 처리하지 않아서 CROSSSLOT 에러를 내요. 해결은 두 가지예요. 키를 슬롯별로 나눠 각 노드에 따로 요청하고 결과를 합치거나(대부분의 클러스터 지원 클라이언트가 해 줌), 함께 다뤄야 하는 키들에 같은 해시 태그를 넣어 같은 슬롯에 놓이게 해요. 후자는 원자성이 필요할 때 쓰지만 태그 하나에 키가 쏠리지 않게 주의해야 해요.

    3부 원자성

    7장 트랜잭션, Lua, 분산 락

    여러 명령을 하나처럼 실행한다

    문제: 명령 사이에 다른 클라이언트가 끼어든다

    명령 하나는 원자적이지만, "읽고 → 판단하고 → 쓰는" 여러 명령 사이에는 다른 클라이언트의 명령이 실행될 수 있어요.

    MULTI / EXEC

    MULTI 뒤의 명령들을 모아 두었다가 EXEC에서 끼어듦 없이 한꺼번에 실행해요. 관계형 DB의 트랜잭션과 다른 점이 있어요.

    • 롤백이 없어요. 중간 명령이 실패해도 나머지는 실행돼요.
    • 모아 둔 명령들은 앞 명령의 결과를 볼 수 없어요. 읽은 값으로 분기할 수 없어요.

    WATCH로 키를 감시해 두면, EXEC 전에 그 키가 바뀌었을 때 트랜잭션이 취소돼요. 낙관적 락이고 실패하면 재시도해요.

    Lua 스크립트

    스크립트 전체가 하나의 명령처럼 실행돼요. 안에서 값을 읽고 조건에 따라 쓸 수 있어요. "확인 후 실행"이 필요한 대부분의 경우에 맞는 도구예요. 단, 스크립트가 도는 동안 다른 모든 명령이 멈추니 짧아야 해요.

    분산 락

    SET lock:order:42 고유값 NX PX 30000
    • NX: 없을 때만 설정 → 한 클라이언트만 성공.
    • PX: 만료 시간 → 락을 쥔 클라이언트가 죽어도 풀림.
    • 고유값: 해제할 때 "내가 건 락인지" 확인하려고 넣어요.

    해제는 "값이 내 것이면 삭제"를 Lua로 원자적으로 해요. 확인 없이 DEL하면, 내 락이 만료된 뒤 다른 클라이언트가 건 락을 지워 버려요.

    백엔드에서는 락의 만료 시간보다 작업이 오래 걸리면 락이 풀린 줄 모르고 두 클라이언트가 동시에 작업해요. GC 멈춤이나 네트워크 지연으로 누구에게나 생길 수 있어요. 그래서 Redis 락은 효율을 위한 락(같은 작업을 두 번 하지 않기)으로는 충분하지만, 정확성을 위한 락(두 번 하면 데이터가 깨짐)으로는 부족해요. 후자는 DB의 조건부 갱신이나 유니크 제약으로 최종 방어하세요.
    시니어 심화
    • 장애 조치와 락: 락을 주 서버에 걸었는데 복제 전에 주 서버가 죽으면, 승격된 복제본에는 그 락이 없어요. 다른 클라이언트가 같은 락을 얻어요. 여러 독립 인스턴스의 과반수에 락을 거는 알고리즘(Redlock)이 이를 보완하려 하지만, 시계와 프로세스 멈춤에 대한 가정 때문에 안전성에 대한 반론이 있어요.
    • 펜싱 토큰: 락을 얻을 때마다 증가하는 번호를 받고, 보호 대상 자원이 "이전에 본 번호보다 작은 요청"을 거부하게 하면 만료된 락을 쥔 클라이언트의 쓰기를 막을 수 있어요. 자원 쪽의 협조가 필요해요.
    • 스크립트는 클러스터에서 한 슬롯의 키만 다룰 수 있고, 다루는 키를 모두 인자로 선언해야 해요.
    핵심 정리
    • MULTI/EXEC = 끼어듦 없는 일괄 실행, 롤백 없음. WATCH로 낙관적 락
    • Lua = 읽고 판단하고 쓰기를 원자적으로. 짧게
    • 락 = SET NX PX + 고유값, 해제는 확인 후 삭제. 정확성은 DB에서 최종 방어
    셀프 체크
    1. 분산 락을 해제할 때 그냥 DEL을 하면 왜 위험한가요?
    답 보기

    락에는 만료 시간이 있어요. 클라이언트 A의 작업이 만료 시간보다 오래 걸리면 락이 자동으로 풀리고, 클라이언트 B가 같은 락을 얻어요. 그 뒤에 A가 작업을 마치고 DEL을 하면 A가 지우는 것은 자기 락이 아니라 B의 락이에요. 그러면 C가 락을 얻어 B와 동시에 작업하게 돼요. 그래서 락을 걸 때 자기만 아는 고유값을 넣고, 해제할 때 값이 그 고유값과 같은 경우에만 지우는 것을 Lua 스크립트로 원자적으로 해야 해요.

    실습

    실습 과제

    로컬 Redis 하나로 대부분 재현할 수 있어요.

    • 1장 키 100만 개를 넣고 KEYS *와 SCAN을 실행하며 다른 클라이언트의 지연을 측정. SLOWLOG 확인
    • 1장 명령 1만 개를 하나씩 보낼 때와 파이프라인으로 보낼 때의 시간 비교
    • 2장 Sorted Set으로 랭킹 구현(점수 갱신, 상위 10명, 내 순위). List 큐에서 워커를 강제 종료해 메시지 유실 재현
    • 3장 maxmemory를 작게 잡고 정책별로 한도 도달 시 동작 비교. TTL 없는 키가 섞였을 때의 차이 관찰
    • 4장 appendfsync 설정별로 쓰기 중 프로세스를 강제 종료하고 유실된 건수 세기
    • 5장 주 서버 1 + 복제본 2 + Sentinel 3을 띄우고, 쓰기 부하 중 주 서버를 죽여 유실 건수와 전환 시간 측정
    • 7장 락 해제를 DEL로 구현한 버전에서 만료 후 남의 락을 지우는 상황 재현. Lua 해제로 고치기
