    Redis

    기준 자료: Redis 공식 문서 + 개발자를 위한 레디스 · 2~3주

    Redis는 "빠른 캐시"로 쓰이다가 장애가 난 뒤에야 내부를 들여다보게 되는 경우가 많아요. 이 챕터는 왜 빠른지, 무엇을 하면 느려지는지, 데이터가 언제 사라질 수 있는지를 구조에서부터 봐요.

    예시는 쇼핑몰이에요. 상품 정보 캐시, 로그인 세션, 인기 상품 랭킹, 재고 차감용 락을 Redis에 둔 상황을 따라가요. 캐시 전략(cache-aside, 스탬피드)은 분산 시스템 챕터 부록에서 다뤘으니 여기서는 Redis 자체에 집중해요. 시간이 없으면 1장(단일 스레드), 3장(만료와 메모리), 7장(분산 락)을 먼저 읽으세요.

    Redis 공식 문서 기준 자료redis.io/docs · 명령마다 시간 복잡도가 적혀 있음
    개발자를 위한 레디스 입문운영 관점까지 한국어로
    1부 실행 모델과 자료형

    1장 단일 스레드 모델과 명령 복잡도

    빠른 이유와 갑자기 느려지는 이유가 같은 곳에 있다

    문제: 모든 요청이 2초씩 멈췄다

    평소 1ms 안에 응답하던 Redis가 어느 순간 모든 클라이언트에게 2초씩 늦게 응답했어요. CPU도 메모리도 여유가 있었고, 몇 초 뒤에는 저절로 정상으로 돌아왔어요. 그 순간 운영자 한 명이 "키가 몇 개나 있나 보려고" 관리 도구에서 KEYS *를 실행했어요. 명령 하나가 어떻게 서비스 전체를 멈출 수 있을까요?

    명령은 한 번에 하나씩 실행된다

    Redis는 명령 실행을 스레드 하나로 해요. 여러 연결에서 들어온 명령을 이벤트 루프(운영체제 챕터 33장)가 차례로 꺼내 하나씩 실행하고 응답해요. 최근 버전은 네트워크 읽기와 쓰기에 여러 스레드를 쓸 수 있지만, 명령 실행 자체는 여전히 하나씩이에요.

    이 구조가 Redis를 빠르게 만들어요. 데이터가 전부 메모리에 있어서 명령 하나가 마이크로초 단위로 끝나고, 여러 스레드가 같은 데이터를 건드리지 않으니 락이 필요 없어요. 덤으로 모든 명령이 원자적이에요. 재고 수량을 줄이는 DECR가 실행되는 동안 다른 명령이 끼어들 수 없어서, 여러 서버가 동시에 호출해도 값이 틀리지 않아요.

    대가: 느린 명령 하나가 전부를 세운다

    같은 이유로, 명령 하나가 2초 걸리면 그 2초 동안 다른 모든 클라이언트가 기다려요. KEYS *는 저장된 키 전체를 한 번에 훑는 명령이라 키가 수백만 개면 몇 초가 걸려요. 그동안 상품 조회도, 세션 확인도, 재고 차감도 전부 줄을 서요.

    그래서 Redis에서는 명령의 시간 복잡도를 알고 써야 해요. 공식 문서에 명령마다 적혀 있어요.

    위험한 명령이유대안
    KEYS *전체 키를 한 번에 순회SCAN으로 조금씩 나눠 순회
    HGETALL, SMEMBERS, LRANGE 0 -1큰 컬렉션 전체를 한 번에 반환HSCAN, SSCAN, 범위 제한
    큰 키의 DEL원소 수만큼 메모리 해제UNLINK(백그라운드에서 해제)

    진짜 비용은 왕복이다

    명령 실행은 마이크로초지만, 애플리케이션 서버와 Redis 사이의 네트워크 왕복은 그보다 수백 배 길어요. 장바구니 상품 100개의 가격을 하나씩 GET하면 왕복이 100번이에요. 명령을 모아서 한 번에 보내는 파이프라인이나, 여러 키를 한 번에 읽는 MGET을 쓰면 왕복 한 번이 돼요.

    백엔드에서는 "Redis가 느려졌다"의 대부분은 Redis가 아니라 누군가 보낸 느린 명령이에요. SLOWLOG GET으로 오래 걸린 명령을 먼저 확인하세요. 운영 환경에서는 KEYS, FLUSHALL 같은 명령을 설정으로 막거나 이름을 바꿔 두면 사고가 줄어요. 애플리케이션 코드에서는 반복문 안의 Redis 호출을 찾아 파이프라인이나 다중 키 명령으로 바꾸는 것이 가장 효과가 커요.
    시니어 심화 느린 명령 다음으로 흔한 원인이 큰 키예요. 인기 상품의 리뷰 ID를 Set 하나에 계속 넣다 보면 원소가 수백만 개인 키 하나가 생겨요. 이 키에 SMEMBERS를 하면 응답 하나가 수십 MB가 되고, 실행 시간과 네트워크 전송 시간 동안 다른 요청이 밀려요. 만료되거나 삭제될 때는 메모리 해제에 시간이 걸려 또 멈춰요. 클러스터에서 이 키를 다른 노드로 옮길 때도 키 하나는 통째로 옮겨지므로 그동안 양쪽 노드가 바빠요.

    큰 키는 쓰는 코드만 봐서는 찾기 어려워요. 크기가 데이터에 따라 자라기 때문이에요. 주기적으로 키 크기를 샘플링하는 도구(redis-cli --bigkeys, MEMORY USAGE)로 찾고, 상품별·월별처럼 범위를 나눈 여러 키로 쪼개요. 처음부터 "이 키의 원소 수에 상한이 있는가"를 설계 리뷰에서 묻는 것이 가장 싸요.

    핵심 정리
    • 명령 실행은 스레드 하나 → 모든 명령이 원자적, 락 불필요
    • 느린 명령 하나가 전체를 막음. O(N) 명령과 큰 키 주의
    • 실행보다 왕복이 비쌈. 파이프라인과 다중 키 명령으로 줄임
    셀프 체크
    1. 운영 중인 Redis에서 KEYS user:* 를 실행하면 어떤 일이 일어나나요?
    답 보기

    KEYS는 저장된 키 전체를 한 번에 훑는 명령이에요. 키가 수백만 개면 수백 밀리초에서 수 초가 걸리고, 명령 실행이 스레드 하나로 이뤄지므로 그동안 다른 모든 클라이언트의 명령이 기다려요. 서비스 전체가 그 시간만큼 멈추고 애플리케이션 쪽에서는 타임아웃이 연달아 나요. 같은 일을 SCAN으로 하면 커서를 따라 조금씩 나눠 훑으므로 사이사이에 다른 명령이 실행돼요.

    2장 자료형과 활용 패턴

    문제에 맞는 자료형을 고르면 코드가 사라진다

    문제: 인기 상품 랭킹을 실시간으로

    메인 화면에 "지금 가장 많이 팔리는 상품 10개"를 보여주려고 해요. 처음에는 DB에서 ORDER BY sales DESC LIMIT 10을 했는데, 주문이 들어올 때마다 판매량이 바뀌고 메인 화면 조회는 초당 수천 번이라 DB가 버티지 못했어요. 결과를 1분간 캐시하니 이번에는 "방금 산 상품이 랭킹에 안 보인다"는 문의가 와요.

    Redis는 값의 모양을 안다

    Redis를 "키에 문자열을 넣는 저장소"로만 쓰면 이 문제를 못 풀어요. Redis는 값으로 리스트, 집합, 정렬된 집합 같은 자료구조를 저장하고, 그 자료구조에 맞는 연산을 서버 안에서 실행해요. 데이터를 꺼내 애플리케이션에서 가공하지 않아도 돼요.

    랭킹에는 Sorted Set이 맞아요. 원소마다 점수를 붙여 두면 Redis가 항상 점수 순서로 정렬된 상태를 유지해요.

    주문이 들어오면 ZINCRBY ranking 1 상품42로 점수를 올리고, 메인 화면은 ZREVRANGE ranking 0 9 WITHSCORES로 상위 10개를 가져와요. 특정 상품의 순위는 ZREVRANK예요. 셋 다 원소 수가 늘어도 로그 시간에 끝나서, 상품이 수십만 개여도 빨라요. 캐시가 아니라 원본처럼 항상 최신이니 "방금 산 상품이 안 보이는" 문제도 없어요.

    자주 쓰는 자료형

    자료형핵심 연산쇼핑몰에서 쓰는 곳
    StringGET/SET, INCR, SET NX EX상품 정보 캐시, 조회수, 락
    HashHGET/HSET, HINCRBY장바구니(상품 ID → 수량)
    ListLPUSH, LTRIM, BRPOP최근 본 상품 20개
    SetSADD, SISMEMBER쿠폰을 이미 받은 사용자
    Sorted SetZADD, ZRANGE, ZRANGEBYSCORE랭킹, 시간순 인덱스, 예약 작업
    StreamXADD, XREADGROUP, XACK처리 확인이 필요한 작업 큐
    HyperLogLogPFADD, PFCOUNT상품별 순 방문자 수(근사)

    장바구니를 JSON 문자열 하나로 넣으면 수량 하나를 바꿀 때마다 전체를 읽고 고치고 다시 써야 해요. 두 요청이 동시에 하면 한쪽의 변경이 사라져요. Hash로 넣으면 HINCRBY cart:7 상품42 1 한 번으로 그 필드만 원자적으로 바뀌어요.

    Pub/Sub과 Stream은 다르다

    둘 다 메시지를 주고받는 기능이지만 성격이 반대예요. Pub/Sub은 보내는 순간 구독 중인 클라이언트에게만 전달하고 저장하지 않아요. 구독자가 잠깐 끊겨 있었다면 그 사이 메시지는 사라져요. Stream은 메시지를 로그로 저장하고, 소비자 그룹이 어디까지 처리했는지와 처리 확인을 받지 못한 메시지를 기억해요. 놓치면 안 되는 작업에는 Stream이에요.

    백엔드에서는 값을 String에 통째로 넣을지 Hash로 나눌지는 접근 패턴으로 정해요. 항상 통째로 읽고 쓰면 String이 단순해요. 일부 필드만 자주 바꾸거나 읽으면 Hash예요. 그리고 키 이름에 규칙을 두세요(서비스:엔티티:ID, 예: shop:cart:7). 규칙이 없으면 어떤 키가 누구 것인지, 지워도 되는지 아무도 모르게 돼요.
    시니어 심화 List를 작업 큐로 쓰는 코드는 흔하지만, 본문의 Pub/Sub과 비슷한 구멍이 있어요. 워커가 BRPOP으로 작업을 꺼내는 순간 그 작업은 Redis에서 사라져요. 워커가 처리 도중 죽으면 작업은 어디에도 남지 않아요. 주문 확인 메일 발송 같은 작업이 조용히 사라지는 거예요.

    보완하는 방법은 꺼내는 동시에 "처리 중" 목록으로 옮기는 거예요(LMOVE). 처리가 끝나면 처리 중 목록에서 지우고, 별도 감시 작업이 처리 중 목록에 오래 남은 작업을 원래 큐로 되돌려요. 그런데 이것은 Stream의 소비자 그룹이 기본으로 해 주는 일이에요. Stream은 꺼낸 메시지를 확인(XACK) 전까지 대기 목록에 두고, 오래 확인되지 않은 메시지를 다른 소비자가 가져가게(XAUTOCLAIM) 할 수 있어요. 새로 만든다면 List보다 Stream이 낫고, 유실과 재처리의 보장이 업무상 중요하다면 Kafka 같은 전용 브로커를 검토하세요.

    핵심 정리
    • Redis는 자료구조를 저장하고 그 연산을 서버에서 실행
    • Sorted Set = 랭킹, 시간순 인덱스. 점수 갱신과 조회가 로그 시간
    • Pub/Sub은 저장 안 함, Stream은 저장하고 처리 확인을 추적
    셀프 체크
    1. 장바구니를 JSON 문자열 하나로 저장했을 때와 Hash로 저장했을 때, 두 요청이 동시에 수량을 바꾸면 각각 어떻게 되나요?
    답 보기

    JSON 문자열이면 각 요청이 전체를 읽고, 애플리케이션에서 수량을 고치고, 전체를 다시 써요. 두 요청이 같은 옛 값을 읽고 각자 고쳐 쓰면 나중에 쓴 쪽이 앞의 변경을 덮어써서 하나가 사라져요. Hash로 저장하면 상품별 수량이 필드 하나라서 HINCRBY 같은 명령으로 그 필드만 Redis 안에서 원자적으로 바꿔요. 명령 실행이 하나씩 이뤄지므로 두 요청의 변경이 모두 반영돼요.

    3장 만료와 메모리 관리

    메모리가 가득 찼을 때 무엇이 지워지는가

    문제: 사용자들이 갑자기 로그아웃됐다

    상품 정보 캐시와 로그인 세션을 같은 Redis에 두고 있었어요. 대규모 할인 행사 날, 상품 캐시가 평소보다 훨씬 많이 쌓였고, 그 무렵부터 "갑자기 로그인이 풀린다"는 문의가 쏟아졌어요. 세션의 만료 시간은 아직 한참 남아 있었어요. 세션은 왜 사라졌을까요?

    만료된 키는 언제 지워지나

    먼저 만료부터 봐요. 키에 만료 시간(TTL)을 주면 그 시간이 지난 뒤 사라져요. 그런데 Redis는 만료 시각에 맞춰 키를 하나씩 지우지 않아요. 두 가지 방식을 섞어요.

    하나는 접근할 때 확인하는 방식이에요. 누군가 그 키를 읽으려 할 때 만료됐으면 그때 지우고 없다고 답해요. 다른 하나는 주기적으로 일부를 뽑아 확인하는 방식이에요. 만료 시간이 있는 키 중 몇 개를 무작위로 골라 만료된 것을 지워요. 그래서 만료됐지만 아무도 읽지 않는 키는 한동안 메모리에 남아 있을 수 있어요.

    메모리 한도에 닿으면

    Redis가 쓸 메모리 상한은 maxmemory로 정하고, 상한에 닿았을 때 무엇을 할지는 maxmemory-policy가 정해요.

    정책동작
    noeviction아무것도 지우지 않고 쓰기 명령에 에러를 돌려줌
    allkeys-lru모든 키 중 가장 오래 안 쓴 것부터 지움
    allkeys-lfu모든 키 중 덜 자주 쓴 것부터 지움
    volatile-lru, volatile-ttl만료 시간이 있는 키 중에서만 골라 지움

    이제 로그아웃의 원인이 보여요. 정책이 allkeys-lru였다면, 행사로 상품 캐시가 메모리를 채우는 순간 Redis는 캐시와 세션을 구분하지 않고 오래 안 쓴 키부터 지워요. 잠시 장바구니를 보며 머뭇거리던 사용자의 세션이 상품 캐시보다 "오래 안 쓴 키"였던 거예요. 만료 시간과는 상관없어요.

    캐시와 저장은 정책이 반대다

    캐시는 지워져도 원본에서 다시 채우면 되니 메모리가 차면 지우는 정책이 맞아요. 세션, 락, 작업 큐처럼 사라지면 안 되는 데이터는 지우면 안 되니 noeviction이 맞고, 대신 용량을 관리해야 해요. 둘을 한 인스턴스에 두면 어느 정책을 골라도 한쪽이 틀려요. 캐시용 Redis와 저장용 Redis를 분리하는 것이 답이에요.

    백엔드에서는 모든 캐시 키에 TTL을 주세요. TTL이 없는 키는 아무도 지우지 않는 한 영원히 남아, 메모리가 서서히 차다가 어느 날 제거가 시작되거나 쓰기가 거부돼요. 그리고 상품 캐시를 한꺼번에 채우면서 똑같은 TTL을 주면 같은 순간에 한꺼번에 만료돼 원본 DB로 요청이 몰려요. TTL에 몇 초에서 몇 분의 무작위 값을 더해 흩어 놓으세요.
    시니어 심화 maxmemory를 컨테이너 메모리 한도와 같게 잡으면 Redis가 OOM으로 죽어요. maxmemory가 세는 것은 데이터 영역이고, 그 밖에서 쓰는 메모리가 있기 때문이에요.

    가장 큰 것은 클라이언트 출력 버퍼예요. 응답을 제때 읽어 가지 않는 클라이언트가 있으면 보낼 응답이 서버에 쌓여요. 큰 결과를 요청해 놓고 천천히 읽는 클라이언트, 메시지를 따라가지 못하는 Pub/Sub 구독자가 흔한 원인이에요. 복제본으로 보낼 데이터를 담는 복제 버퍼, 메모리 단편화도 있어요. 그리고 다음 장의 스냅샷 저장 중에는 쓰기가 많을수록 메모리 사용량이 더 늘어요. 그래서 컨테이너 한도는 maxmemory보다 넉넉하게 잡고, 클라이언트 종류별 출력 버퍼 한도(client-output-buffer-limit)를 설정해 문제 있는 클라이언트를 끊어내요. INFO memory의 실제 점유량(RSS)과 데이터 사용량의 차이를 모니터링하면 이런 바깥 메모리가 보여요.

    핵심 정리
    • 만료 키는 접근할 때와 주기적 샘플링으로 지워짐. 즉시 사라지지 않음
    • maxmemory에 닿으면 정책에 따라 지우거나 쓰기를 거부
    • 캐시(지워도 됨)와 저장(지우면 안 됨)은 인스턴스를 분리
    셀프 체크
    1. 세션과 캐시를 같은 Redis에 두고 allkeys-lru를 쓰면 어떤 문제가 생기나요?
    답 보기

    메모리가 한도에 닿으면 Redis는 캐시와 세션을 구분하지 않고 오래 안 쓴 키부터 지워요. 캐시가 늘어 메모리를 채우면 활동이 뜸했던 사용자의 세션이 만료 시간과 상관없이 지워져서 그 사용자들이 갑자기 로그아웃돼요. 그렇다고 noeviction으로 바꾸면 캐시가 메모리를 채웠을 때 세션 쓰기까지 거부돼요. 지워져도 되는 데이터와 지우면 안 되는 데이터는 맞는 정책이 반대이므로 인스턴스를 나눠야 해요.

    4장 영속화 — RDB와 AOF

    재시작하면 데이터가 얼마나 남아 있는가

    문제: 재시작 후 장바구니가 비었다

    Redis 서버를 패치하려고 재시작했더니 사용자들의 장바구니가 몇 분 전 상태로 돌아가 있었어요. 메모리에만 있던 데이터가 사라진 거예요. Redis는 메모리 저장소지만 디스크에 저장하는 방법도 있어요. 두 가지이고, 둘은 잃는 범위가 달라요.

    RDB: 특정 시점의 사진

    RDB는 특정 시점의 전체 데이터를 파일 하나로 저장해요. "5분마다, 그사이 변경이 100건 이상이면"처럼 조건을 정해 두면 그때마다 저장해요. 저장하는 동안에도 Redis가 명령을 계속 처리할 수 있도록 자식 프로세스를 하나 복제(fork)해서 그 프로세스가 파일을 써요.

    파일이 작고 다시 읽어 들이는 것이 빨라서 백업에 좋아요. 대신 마지막 저장 이후의 변경은 전부 잃어요. 5분마다 저장했다면 최대 5분 치가 사라져요. 위 장바구니 사고가 이 경우예요.

    AOF: 변경 명령의 기록

    AOF는 데이터를 바꾸는 명령을 실행할 때마다 파일 끝에 덧붙여요. 재시작하면 이 기록을 처음부터 다시 실행해서 데이터를 복원해요. 잃는 범위는 이 기록을 언제 디스크에 확실히 내려쓰느냐(appendfsync)가 정해요.

    appendfsync디스크 동기화최대 유실
    always명령마다거의 없음. 쓰기가 크게 느려짐
    everysec1초마다약 1초
    no운영체제에 맡김수십 초까지 가능

    기록은 계속 길어지므로 주기적으로 다시 쓰기를 해요. 같은 키를 백 번 바꿨다면 마지막 값을 만드는 명령 하나로 줄이는 작업이에요. 실무에서는 두 방식을 함께 써서, 파일 앞부분은 스냅샷으로 두고 그 뒤의 변경만 명령으로 붙이는 형식이 흔해요. 복원이 빠르고 잃는 범위는 작아요.

    "성공"의 의미가 DB와 다르다

    everysec에서도 Redis는 명령을 실행하자마자 클라이언트에게 성공을 응답하고, 디스크 동기화는 최대 1초 뒤에 해요. 그 사이에 서버가 죽으면 성공 응답을 받은 쓰기가 사라져요. 관계형 DB의 커밋처럼 "성공 응답 = 디스크에 기록됨"이 아니에요.

    백엔드에서는 순수 캐시라면 영속화를 꺼도 돼요. 재시작하면 비어 있지만 다시 채우면 되고, 저장 작업으로 인한 지연이 사라져요. 반대로 장바구니, 세션, 카운터처럼 사라지면 곤란한 데이터를 넣었다면, 지금 설정에서 최대 몇 초의 데이터를 잃는지를 팀 전체가 알고 있어야 해요. 그 범위를 받아들일 수 없는 데이터라면 Redis가 아니라 DB가 원본이어야 해요.
    시니어 심화 RDB 저장과 AOF 다시 쓰기는 둘 다 fork를 써요. 이 fork가 운영에서 두 가지 문제를 만들어요.

    첫째는 멈춤이에요. fork는 부모 프로세스의 메모리 주소 대응표(페이지 테이블)를 복사해야 하는데, Redis가 수십 GB를 쓰고 있으면 이 복사에만 수십에서 수백 밀리초가 걸리고 그동안 Redis가 멈춰요. INFO stats의 latest_fork_usec로 측정할 수 있어요. 둘째는 메모리 급증이에요. fork 직후 부모와 자식은 메모리를 공유하다가, 부모가 어떤 메모리 페이지를 고치는 순간 그 페이지만 복사해요(copy-on-write). 저장하는 동안 쓰기가 많으면 복사되는 페이지가 늘어 메모리 사용량이 최대 두 배 가까이 갈 수 있어요. 운영체제의 큰 페이지 기능(THP)이 켜져 있으면 작은 쓰기 하나에도 2MB가 복사되어 더 심해져요. 그래서 큰 인스턴스는 쓰기가 적은 시간에 저장하거나, 복제본에서만 저장하거나, 메모리 여유를 넉넉히 둬요.

    핵심 정리
    • RDB = 시점 스냅샷. 빠른 복원, 마지막 저장 이후 유실
    • AOF = 변경 명령 기록. appendfsync가 유실 범위를 결정
    • 성공 응답이 곧 디스크 기록은 아님. 잃으면 안 되는 데이터의 원본은 DB
    셀프 체크
    1. appendfsync everysec 설정에서 "성공 응답을 받은 데이터는 안전하다"고 말할 수 없는 이유는 무엇인가요?
    답 보기

    Redis는 명령을 실행하고 곧바로 클라이언트에게 성공을 응답한 뒤, 최대 1초 후에야 그 내용을 디스크에 동기화해요. 응답과 동기화 사이에 서버가 죽으면 클라이언트는 성공으로 알고 있는 쓰기가 사라져요. 관계형 DB의 커밋처럼 응답 시점에 디스크 기록이 끝나 있는 것이 아니에요. 그 보장이 필요하면 always로 두어야 하는데 쓰기 성능이 크게 떨어지므로, 그런 데이터는 보통 Redis가 아닌 DB에 둬요.

    2부 가용성

    5장 복제와 Sentinel

    장애 조치가 끝났는데 방금 쓴 데이터가 없다

    문제: 주 서버가 죽었을 때

    Redis 서버 한 대가 죽으면 세션과 장바구니를 전부 못 쓰게 돼요. 그래서 복제본을 두고, 주 서버가 죽으면 복제본을 새 주 서버로 올려요. 그런데 이렇게 넘어간 뒤에 "결제 직전에 담은 상품이 장바구니에서 사라졌다"는 문의가 와요. 넘어가는 과정에서 무엇을 잃었을까요?

    복제는 비동기다

    복제본이 처음 연결되면 주 서버가 스냅샷을 만들어 통째로 보내요. 그 뒤로는 주 서버가 실행한 쓰기 명령을 계속 흘려보내고, 복제본이 같은 명령을 실행해 따라가요. 잠깐 끊겼다 다시 붙으면 주 서버가 최근 명령을 모아 둔 버퍼에서 빠진 부분만 보내고, 버퍼 범위를 벗어났으면 다시 통째로 보내요.

    핵심은 주 서버가 복제본의 확인을 기다리지 않고 클라이언트에게 성공을 응답한다는 점이에요. 장바구니에 상품을 담는 명령이 주 서버에서 실행되고 성공 응답이 나간 직후, 복제본으로 전달되기 전에 주 서버가 죽으면 그 명령은 어디에도 없어요.

    Sentinel: 자동으로 주 서버를 바꾼다

    Sentinel은 주 서버를 감시하는 별도의 프로세스예요. 여러 대를 띄워 두고, 한 Sentinel이 주 서버의 응답이 없다고 판단하면 다른 Sentinel들에게 물어요. 미리 정한 수(정족수) 이상이 동의하면 장애로 확정하고, 복제본 하나를 새 주 서버로 올린 뒤 나머지 복제본을 새 주 서버에 붙여요. 애플리케이션은 Sentinel에게 "지금 주 서버가 누구냐"고 물어서 연결해요.

    Sentinel은 과반수 판단이 가능하도록 최소 3대를 서로 다른 장애 영역에 둬요. 2대면 하나가 죽었을 때 과반수를 만들 수 없어요.

    스플릿 브레인: 양쪽에서 쓰기가 일어난다

    더 나쁜 경우도 있어요. 네트워크가 갈라져서 옛 주 서버가 일부 애플리케이션 서버와 함께 고립됐다고 해 봐요. 반대편의 Sentinel들은 주 서버가 죽었다고 보고 새 주 서버를 뽑아요. 그동안 고립된 쪽의 애플리케이션은 옛 주 서버에 계속 써요. 네트워크가 복구되면 옛 주 서버는 복제본으로 내려가면서 새 주 서버의 데이터로 덮어써지고, 고립된 동안 받은 쓰기는 전부 버려져요.

    min-replicas-to-write와 min-replicas-max-lag를 설정하면, 연결된 복제본이 정해진 수보다 적을 때 주 서버가 쓰기를 거부해요. 고립된 주 서버는 복제본과 연결이 끊겼으니 금방 쓰기를 멈추고, 버려질 쓰기의 양이 줄어요. WAIT 명령으로 복제본 몇 대가 받을 때까지 기다릴 수도 있지만, 이것도 장애 조치 때의 유실을 완전히 막지는 못해요.

    백엔드에서는 복제본에서 읽으면 방금 쓴 값이 아직 안 보일 수 있어요. 세션처럼 쓴 직후 읽는 데이터는 주 서버에서 읽으세요. 그리고 클라이언트 라이브러리가 장애 조치 후 새 주 서버로 자동으로 넘어가는지, 넘어가는 데 몇 초가 걸리는지는 실제로 주 서버를 죽여 봐야 알 수 있어요. 설정만 보고 판단하지 마세요.
    핵심 정리
    • 복제는 비동기. 주 서버는 복제를 기다리지 않고 응답
    • Sentinel 3대 이상이 정족수로 장애를 판정하고 복제본을 승격
    • 스플릿 브레인 동안의 쓰기는 버려짐. min-replicas 설정으로 줄임
    셀프 체크
    1. Redis 주 서버가 죽고 Sentinel이 복제본을 승격했습니다. 성공 응답을 받은 쓰기가 사라질 수 있는 이유를 설명하세요.
    답 보기

    Redis 복제는 비동기라서 주 서버는 명령을 실행하고 복제본에 전달되기를 기다리지 않은 채 성공을 응답해요. 그 직후 주 서버가 죽으면 그 명령은 복제본에 도착하지 못했을 수 있어요. 승격된 복제본은 그 쓰기를 모르는 상태로 새 주 서버가 되고, 옛 주 서버가 돌아와도 새 주 서버의 데이터로 덮어써지므로 그 쓰기는 되살아나지 않아요.

    6장 Redis Cluster

    데이터를 여러 서버에 나누면 무엇이 안 되는가

    문제: 서버 한 대로는 부족하다

    사용자가 늘어 세션과 장바구니가 서버 한 대의 메모리를 넘었어요. 1장에서 본 것처럼 명령 실행은 스레드 하나라서, 코어가 많은 서버로 바꿔도 처리량은 크게 늘지 않아요. 데이터를 여러 서버에 나눠야 해요.

    해시 슬롯

    Redis Cluster는 키 공간을 16,384개의 슬롯으로 나누고, 슬롯 묶음을 각 주 서버에 배정해요. 어떤 키가 어느 슬롯에 들어갈지는 키 이름으로 계산한 해시 값을 16,384로 나눈 나머지예요. 서버를 추가하면 기존 서버들의 슬롯 일부를 새 서버로 옮겨요. 키 하나하나가 아니라 슬롯 단위로 옮기니 관리가 단순해요.

    클라이언트가 길을 찾는다

    중간에 라우팅 서버가 없어요. 클라이언트 라이브러리가 "어느 슬롯이 어느 서버에 있는지" 표를 갖고 직접 맞는 서버로 보내요. 표가 낡아서 잘못 보내면 서버가 알려줘요. MOVED는 "그 슬롯은 이제 저 서버 것"이라는 뜻이라 클라이언트가 표를 갱신하고, ASK는 "지금 옮기는 중이니 이번 한 번만 저 서버로"라는 뜻이에요.

    여러 키를 한 번에 다루기 어렵다

    나누는 대가가 여기 있어요. 여러 키를 함께 다루는 명령(MGET, MULTI 트랜잭션, Lua 스크립트)은 모든 키가 같은 슬롯에 있어야 해요. 서로 다른 서버에 걸친 원자적 연산은 지원하지 않아요. 단일 서버에서 잘 돌던 "장바구니와 쿠폰 사용 여부를 함께 확인하는 스크립트"가 클러스터에서는 CROSSSLOT 에러를 내요.

    이때 쓰는 것이 해시 태그예요. 키 이름에 중괄호가 있으면 중괄호 안의 부분만으로 슬롯을 계산해요. {user:42}:cart와 {user:42}:coupon은 같은 슬롯에 들어가서 함께 다룰 수 있어요.

    클러스터로 풀리지 않는 것

    요청이 키 하나에 몰리면(핫 키) 그 키가 있는 서버만 바빠요. 서버를 아무리 늘려도 키 하나는 한 서버에 있으니 풀리지 않아요. 행사 상품의 재고 키가 대표적이에요. 원소가 아주 많은 큰 키도 마찬가지로 한 서버의 부담이고, 슬롯을 옮길 때 통째로 옮겨져 양쪽 서버를 붙잡아요. 해시 태그를 남용해 많은 키를 같은 태그로 묶으면 한 슬롯에 쏠리는 문제도 생겨요. 장애 조치는 각 주 서버의 복제본이 승격되는 방식이고, 여기서도 복제는 비동기라 5장의 유실 구간이 그대로 있어요.

    백엔드에서는 단일 서버에서 클러스터로 옮기면 여러 키를 한 번에 다루던 코드가 깨져요. 옮기기 전에 다중 키 명령, 트랜잭션, 스크립트를 전부 찾아서, 함께 다뤄야 하는 키들에 같은 해시 태그를 넣으세요. 파이프라인도 클라이언트 라이브러리가 서버별로 나눠 보내 주는지 확인해야 해요. 처음부터 클러스터를 염두에 두고 "원자적으로 함께 다뤄야 하는 키"를 설계 단계에서 정해 두는 것이 가장 싸요.
    핵심 정리
    • 16,384 슬롯을 서버에 배정. 클라이언트가 직접 라우팅(MOVED, ASK)
    • 여러 키 연산은 같은 슬롯 안에서만. 해시 태그로 묶음
    • 핫 키와 큰 키는 서버를 늘려도 해결되지 않음
    셀프 체크
    1. Redis Cluster에서 MGET user:1 user:2 user:3 이 실패하는 이유와 해결 방법을 말해보세요.
    답 보기

    세 키는 해시 값이 달라 서로 다른 슬롯, 따라서 서로 다른 서버에 있을 수 있어요. 클러스터는 여러 슬롯에 걸친 명령을 하나로 처리하지 않아 CROSSSLOT 에러를 내요. 해결은 두 가지예요. 키를 서버별로 나눠 각각 요청하고 결과를 합치거나(클러스터를 지원하는 클라이언트 라이브러리가 대신 해 주기도 해요), 함께 다뤄야 하는 키들에 같은 해시 태그를 넣어 같은 슬롯에 두는 거예요. 원자성이 필요할 때는 후자를 쓰되, 태그 하나에 키가 쏠리지 않게 주의해요.

    3부 원자성

    7장 트랜잭션, Lua, 분산 락

    여러 명령을 하나처럼 실행하고, 서버끼리 순서를 정한다

    문제: 쿠폰이 한도보다 많이 발급됐다

    선착순 쿠폰 100장을 발급하는 기능을 만들었어요. 코드는 이래요. 발급 수를 읽고(GET), 100 미만이면 발급하고 수를 올려요(INCR). 그런데 행사가 끝나고 보니 107장이 나갔어요. 1장에서 Redis의 모든 명령은 원자적이라고 했는데 왜 이런 일이 생겼을까요?

    명령 하나는 원자적이지만, 명령 사이는 아니다

    원자적인 것은 명령 하나예요. GET과 INCR 사이에는 다른 클라이언트의 명령이 끼어들 수 있어요. 서버 여러 대가 동시에 99를 읽으면 전부 "아직 한도 안"이라고 판단하고 각자 발급해요. 데이터베이스 챕터에서 본 "확인 후 실행" 경쟁과 같은 문제예요.

    방법 1: 판단을 명령 하나에 담는다

    가장 단순한 해결은 읽고 판단하는 순서를 뒤집는 거예요. 먼저 INCR로 올리고, 그 결과값이 100 이하면 발급하고, 넘으면 발급하지 않아요. INCR은 원자적이라 서버 백 대가 동시에 호출해도 1부터 차례로 다른 값을 받아요. 101번째부터는 결과가 100을 넘으니 발급되지 않아요.

    방법 2: Lua 스크립트

    판단이 더 복잡하면(이 사용자가 이미 받았는지도 확인해야 한다면) Lua 스크립트를 써요. 스크립트 전체가 명령 하나처럼 실행돼서, 그 안에서 읽고, 판단하고, 쓰는 동안 아무것도 끼어들지 못해요. 대신 스크립트가 도는 동안 다른 모든 명령이 멈추니 짧아야 해요.

    MULTI/EXEC 트랜잭션도 있지만 성격이 달라요. 명령을 모아 두었다가 끼어듦 없이 한꺼번에 실행할 뿐, 앞 명령의 결과를 보고 분기할 수 없고 중간 명령이 실패해도 롤백하지 않아요. 확인 후 실행에는 Lua가 맞아요.

    분산 락: Redis 밖의 작업에 순서 정하기

    재고 차감처럼 Redis 밖(DB, 외부 API)에서 일어나는 작업을 서버 한 대만 하게 하려면 락이 필요해요.

    SET lock:stock:42 서버A-고유값 NX PX 30000

    NX는 키가 없을 때만 설정하라는 뜻이라 한 서버만 성공해요. PX 30000은 30초 뒤 자동으로 풀리게 해서, 락을 쥔 서버가 죽어도 영원히 잠기지 않아요. 값에 넣는 고유값은 풀 때 필요해요.

    위 그림처럼 서버 A의 작업이 GC 멈춤 때문에 30초를 넘기면 락이 저절로 풀리고 서버 B가 락을 얻어요. 그 뒤 A가 깨어나 DEL을 하면, 지워지는 것은 자기 락이 아니라 B의 락이에요. 그러면 서버 C도 락을 얻어 B와 동시에 작업해요. 그래서 풀 때는 "값이 내 고유값과 같을 때만 지운다"를 Lua로 원자적으로 해야 해요.

    백엔드에서는 이 그림의 문제는 해제를 고쳐도 남아요. A가 깨어나 해제는 안전하게 하더라도, A와 B가 잠시 동시에 재고를 차감하는 구간은 이미 지나갔어요. 그래서 Redis 락은 같은 작업을 두 번 하지 않게 하는 효율용으로는 충분하지만, 두 번 하면 데이터가 깨지는 정확성용으로는 부족해요. 재고 같은 데이터는 DB의 조건부 갱신(UPDATE ... WHERE stock >= 1)이나 유니크 제약으로 최종 방어하세요.
    시니어 심화 락이 만료된 뒤 깨어난 서버의 쓰기를 막는 방법이 펜싱 토큰이에요. 락을 얻을 때마다 계속 증가하는 번호를 함께 받아요. A가 33번, 그 뒤에 B가 34번을 받았다고 해 봐요. 재고를 저장하는 쪽(DB)은 마지막으로 받은 번호를 기억해 두고, 그보다 작은 번호를 가진 요청은 거부해요. B가 34번으로 먼저 쓰고 나면, 늦게 깨어난 A의 33번 요청은 거부돼요.

    이 방식은 저장하는 쪽의 협조가 필요해요. DB라면 행에 버전 컬럼을 두고 "버전이 내 토큰보다 작을 때만 갱신"하는 조건부 UPDATE로 구현해요. 사실 이 조건부 갱신만으로도 동시 수정을 막을 수 있어서, 결국 정확성은 락이 아니라 DB가 지키는 구조가 돼요. 여러 독립된 Redis에 과반수로 락을 거는 방법(Redlock)도 있지만, 시계와 프로세스 멈춤에 대한 가정 때문에 정확성을 보장하지 못한다는 반론이 있어요. 분산 시스템 챕터 8장의 "프로세스는 언제든 멈춘다"가 바로 이 문제예요.

    핵심 정리
    • 명령 하나는 원자적이지만 명령 사이에는 끼어들 수 있음
    • 판단을 명령 하나에(INCR 결과로 판단) 또는 Lua 스크립트로. MULTI는 롤백 없음
    • 락 = SET NX PX + 고유값, 해제는 확인 후 삭제. 정확성은 DB에서 최종 방어
    셀프 체크
    1. 분산 락을 해제할 때 그냥 DEL을 하면 왜 위험한가요?
    답 보기

    락에는 만료 시간이 있어서, 서버 A의 작업이 그보다 오래 걸리면 락이 자동으로 풀리고 서버 B가 같은 락을 얻어요. 그 뒤 A가 작업을 마치고 DEL을 하면 A가 지우는 것은 자기 락이 아니라 B의 락이에요. 그러면 서버 C가 락을 얻어 B와 동시에 작업하게 돼요. 그래서 락을 걸 때 자기만 아는 고유값을 넣고, 해제할 때 값이 그 고유값과 같을 때만 지우는 것을 Lua 스크립트로 원자적으로 해야 해요.

    실습

    실습 과제

    로컬 Redis 하나로 대부분 재현할 수 있어요.

    • 1장 키 100만 개를 넣고 KEYS *와 SCAN을 실행하며 다른 클라이언트의 응답 시간 측정. SLOWLOG GET 확인
    • 1장 장바구니 상품 100개 가격을 하나씩 GET할 때와 파이프라인, MGET으로 가져올 때의 시간 비교
    • 2장 Sorted Set으로 인기 상품 랭킹 구현(점수 증가, 상위 10개, 내 순위). List 큐에서 워커를 강제 종료해 작업 유실 재현
    • 3장 maxmemory를 작게 잡고 세션과 캐시를 섞어 넣은 뒤 정책별로 무엇이 지워지는지 확인
    • 4장 appendfsync 설정별로 쓰기 도중 프로세스를 강제 종료하고 유실 건수 세기
    • 5장 주 서버 1 + 복제본 2 + Sentinel 3을 띄우고 쓰기 도중 주 서버를 죽여 유실 건수와 전환 시간 측정
    • 7장 GET 후 INCR로 만든 선착순 쿠폰에 동시 요청을 보내 초과 발급 재현. INCR 결과로 판단하도록 고치기. DEL 해제 락에서 남의 락을 지우는 상황 재현 후 Lua 해제로 고치기
