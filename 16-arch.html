    컴퓨터 구조

    기준 교재: 컴퓨터 시스템(CS:APP, Computer Systems: A Programmer's Perspective) · 4~6주

    운영체제와 자료구조 챕터에서 "캐시 친화적", "문맥 전환 비용", "원자적 명령" 같은 말이 설명 없이 나왔어요. 이 챕터는 그 아래층이에요. 프로그램이 하드웨어에서 실제로 어떻게 실행되는지를 프로그래머 관점에서 봐요.

    회로 설계가 아니라 "이것을 알면 코드를 다르게 짜게 되는" 내용만 골랐어요. 시간이 없으면 1장(수의 표현)과 4장(캐시)을 먼저 읽으세요. 버그와 성능에 가장 직접 닿아요.

    컴퓨터 시스템 (CS:APP) 기준 교재2~3장, 5~7장, 12장이 이 챕터의 범위
    혼자 공부하는 컴퓨터 구조+운영체제 입문CS:APP이 부담스러울 때 먼저
    1부 표현

    1장 정보의 표현 — 정수와 부동소수점

    숫자는 수학의 수가 아니다

    정수: 유한한 비트

    32비트 부호 있는 정수는 약 −21억에서 +21억까지만 표현해요. 넘으면 에러가 나지 않고 조용히 반대쪽 끝으로 넘어가요(오버플로).

    int a = 2_000_000_000;
      int b = a + a;          // -294967296. 예외 없음

    음수는 2의 보수로 표현해요. 최상위 비트가 음의 가중치를 가져요. 덕분에 덧셈과 뺄셈을 같은 회로로 하지만, 음수 쪽 범위가 하나 더 넓어서 가장 작은 값의 절댓값은 표현할 수 없어요.

    자주 만나는 오버플로

    • 두 수의 중간값 (low + high) / 2.
    • 밀리초 단위 시간 계산(days * 24 * 60 * 60 * 1000이 int 범위를 넘음).
    • 비교 함수에서 a - b의 부호로 대소 판단.
    • 자동 증가 ID가 32비트 한계에 도달.

    부동소수점: 근삿값

    IEEE 754는 수를 부호 × 가수 × 2의 지수로 표현해요. 2진 분수라서 10진수 0.1을 정확히 표현할 수 없어요.

    0.1 + 0.2 == 0.3        // false
      0.1 + 0.2               // 0.30000000000000004
    • double의 유효 자릿수는 10진수로 약 15~16자리예요. 그보다 큰 정수는 정확히 담지 못해요(2의 53제곱 초과).
    • 크기가 많이 다른 수를 더하면 작은 쪽이 사라져요. 그래서 더하는 순서에 따라 결과가 달라요.
    • 특수한 값이 있어요. 무한대, 그리고 NaN(자기 자신과도 같지 않음).

    바이트 순서

    여러 바이트로 된 수를 메모리에 놓는 순서가 CPU마다 달라요. 낮은 바이트를 먼저 두는 방식(리틀 엔디언, x86과 ARM의 일반적 설정)과 높은 바이트를 먼저 두는 방식(빅 엔디언, 네트워크 프로토콜의 표준)이 있어요.

    백엔드에서는 돈을 double로 계산하지 마세요. 오차가 쌓여 합계가 1원씩 어긋나요. 정수 최소 단위(원, 센트)로 저장하거나 BigDecimal(DB는 DECIMAL)을 써요. JSON의 숫자는 많은 구현에서 double로 읽혀서, 64비트 정수 ID를 숫자로 보내면 자바스크립트 클라이언트에서 끝자리가 바뀌어요. 큰 ID는 문자열로 내보내세요.
    시니어 심화
    • 오버플로를 검사하는 연산을 쓰세요. 자바의 Math.addExact, Math.multiplyExact, Math.toIntExact는 넘치면 예외를 던져요. 금액, 수량, 크기 계산처럼 틀리면 안 되는 곳은 조용한 오버플로보다 예외가 나아요. 외부 입력으로 버퍼 크기를 계산하는 코드의 오버플로는 보안 취약점으로 이어져요.
    • 부동소수점 비교는 등호 대신 허용 오차로 해요. 그리고 병렬로 합산하면 더하는 순서가 달라져 실행마다 결과의 끝자리가 달라질 수 있어요. 재현성이 필요한 집계는 순서를 고정하거나 정확한 타입을 써요.
    • NaN은 정렬과 집계를 망가뜨려요. 어떤 비교도 거짓이라 비교 기반 로직이 예상과 다르게 동작해요. 외부에서 들어온 실수는 유한한 값인지 검증해요.
    핵심 정리
    • 정수는 범위가 유한, 넘으면 조용히 순환
    • 부동소수점은 근삿값. 0.1을 정확히 표현 못 함
    • 돈은 정수 최소 단위나 십진 타입. 큰 정수 ID는 JSON에서 문자열로
    셀프 체크
    1. JSON으로 64비트 정수 ID 9007199254740993을 보냈는데 브라우저에서 9007199254740992로 보입니다. 이유는 무엇인가요?
    답 보기

    자바스크립트의 숫자는 64비트 부동소수점이에요. 부동소수점은 가수 부분이 53비트라서 2의 53제곱(9007199254740992)까지만 모든 정수를 정확히 표현해요. 그보다 큰 정수는 표현 가능한 가장 가까운 값으로 반올림돼요. 서버가 보낸 값은 정확했지만 클라이언트가 숫자로 파싱하는 순간 정밀도를 잃은 거예요. 64비트 ID는 JSON에서 문자열로 내보내야 해요.

    2장 프로그램의 기계 수준 표현

    함수 호출은 스택 위에서 일어난다

    소스에서 실행까지

    컴파일러는 소스를 CPU가 이해하는 기계어 명령으로 바꿔요. 명령 하나는 아주 단순해요. 레지스터 사이의 연산, 메모리에서 읽기와 쓰기, 조건에 따른 점프 정도예요.

    • 레지스터: CPU 안의 아주 빠른 저장 공간. 수십 개뿐이에요.
    • 프로그램 카운터: 다음에 실행할 명령의 주소.
    • 스택 포인터: 스택의 현재 꼭대기.

    if와 for는 기계어에 없어요. 전부 "비교하고, 결과에 따라 다른 주소로 점프"로 바뀌어요.

    호출 스택

    함수를 호출할 때마다 스택에 프레임이 하나 쌓여요.

    • 돌아갈 주소(호출이 끝나면 어디로 복귀할지).
    • 지역 변수.
    • 레지스터에 다 못 담은 인자와 저장해 둘 레지스터 값.

    함수가 끝나면 프레임이 사라지고 호출한 곳으로 돌아가요. 그래서 지역 변수는 함수가 끝나면 없어져요.

    스택의 한계

    스택 크기는 고정돼 있어요. 재귀가 너무 깊으면 스택을 다 써서 스택 오버플로가 나요. 꼬리 재귀를 반복문으로 바꿔 주는 최적화가 없는 언어(자바 등)에서는 깊이를 보장할 수 없는 재귀를 반복문과 명시적 스택으로 바꿔야 해요.

    스택과 힙

    스택힙
    할당·해제포인터 이동뿐. 매우 빠름빈 공간을 찾아야 함. 해제나 GC 필요
    수명함수가 끝나면 사라짐명시적 해제나 GC 전까지
    크기작고 고정크고 가변
    공유스레드마다 따로스레드 간 공유
    백엔드에서는 스택 트레이스는 호출 스택의 프레임을 아래에서 위로 읽은 거예요. 예외를 만들 때 이 스택을 훑어 기록하는 비용이 커서, 정상 흐름 제어에 예외를 쓰면 느려요. 깊은 프레임워크 호출(프록시, 필터, AOP)은 프레임을 수백 개씩 쌓으니, 그 위에서 깊은 재귀를 하면 생각보다 빨리 스택이 바닥나요.
    시니어 심화
    • 버퍼 오버플로 공격의 원리가 여기 있어요. 스택의 지역 배열에 길이 검사 없이 쓰면 그 옆에 저장된 복귀 주소를 덮어쓸 수 있고, 함수가 끝날 때 공격자가 정한 주소로 점프해요. 메모리 안전 언어는 경계 검사로 막지만, 네이티브 라이브러리를 호출하는 순간 다시 노출돼요. 스택 보호 값, 주소 무작위화, 실행 불가 스택이 방어 계층이에요.
    • 인라이닝은 호출을 없애 프레임 생성 비용을 지우고 더 큰 범위의 최적화를 가능하게 해요. 작은 메서드로 잘게 나눈 코드가 느리지 않은 이유예요. 다만 프로파일에서는 인라이닝된 함수가 호출자에 합쳐져 보여요.
    • 탈출 분석으로 컴파일러가 객체를 힙 대신 스택이나 레지스터에 둘 수 있어요. 메서드 밖으로 나가지 않는 임시 객체는 할당 비용이 없을 수 있어요.
    핵심 정리
    • 제어 구조는 비교 + 점프로 번역됨
    • 호출마다 스택 프레임(복귀 주소, 지역 변수). 깊은 재귀는 스택 오버플로
    • 스택 = 빠르고 짧은 수명, 힙 = 유연하고 관리 비용
    셀프 체크
    1. 깊이를 알 수 없는 트리를 재귀로 순회하는 코드가 운영에서 StackOverflowError를 냈습니다. 원인과 해결 방법을 말해보세요.
    답 보기

    재귀 호출은 한 번마다 스택에 프레임을 쌓아요. 스레드의 스택 크기는 고정돼 있어서 재귀 깊이가 그 한도를 넘으면 스택이 넘쳐요. 테스트 데이터는 얕았지만 운영 데이터 중에 아주 깊거나 순환하는 구조가 있었던 거예요. 해결은 재귀를 반복문으로 바꾸고, 방문할 노드를 힙에 있는 명시적 스택이나 큐에 담는 거예요. 힙은 훨씬 크기 때문에 깊이 제한에서 벗어나요. 순환 가능성이 있으면 방문한 노드를 기록해 다시 들어가지 않게 하고, 깊이 상한도 둬요.

    2부 실행

    3장 파이프라인과 분기 예측

    CPU는 명령을 순서대로 하나씩 실행하지 않는다

    파이프라인

    명령 하나의 실행은 여러 단계(가져오기, 해석, 실행, 메모리 접근, 결과 기록)로 나뉘어요. CPU는 한 명령이 끝나기를 기다리지 않고, 앞 명령이 다음 단계로 넘어가면 바로 다음 명령을 시작해요. 여러 명령이 서로 다른 단계에서 동시에 진행돼요.

    슈퍼스칼라와 비순차 실행

    현대 CPU는 한 사이클에 여러 명령을 동시에 시작하고, 서로 의존하지 않는 명령은 순서를 바꿔 준비된 것부터 실행해요. 결과는 원래 순서대로 확정해서 프로그램에게는 순서대로 실행된 것처럼 보여요.

    그래서 성능을 정하는 것은 명령의 개수가 아니라 명령 사이의 의존 관계예요. 앞의 결과가 있어야 다음을 시작할 수 있는 긴 사슬은 병렬로 못 풀어요.

    분기 예측

    조건 분기를 만나면 조건이 계산되기 전에는 다음에 어느 쪽 명령을 가져올지 알 수 없어요. 기다리면 파이프라인이 비어요. 그래서 CPU는 과거 이력으로 방향을 예측해서 미리 실행해요(투기적 실행).

    • 예측이 맞으면 손실이 없어요.
    • 틀리면 미리 실행한 것을 전부 버리고 올바른 쪽에서 다시 시작해요. 명령 십수 개 분량의 시간을 잃어요.

    규칙적인 분기(루프 조건, 거의 항상 같은 쪽으로 가는 검사)는 거의 다 맞혀요. 데이터에 따라 무작위로 갈리는 분기가 문제예요.

    // 값이 무작위면 절반은 예측 실패
      for (int v : data) if (v >= 128) sum += v;

      // 같은 데이터를 정렬한 뒤에는 분기가 규칙적이라 훨씬 빠름

    SIMD

    명령 하나로 여러 데이터에 같은 연산을 동시에 적용해요. 배열 전체에 같은 계산을 하는 코드를 컴파일러가 자동으로 이런 명령으로 바꾸기도 해요(자동 벡터화). 데이터가 연속된 배열에 있고 루프 안에 복잡한 분기가 없어야 가능해요.

    백엔드에서는 일반적인 백엔드 코드에서 분기 예측을 의식하고 짤 일은 드물어요. I/O가 훨씬 커요. 이 지식이 쓰이는 곳은 대량의 데이터를 메모리에서 처리하는 코드(집계, 필터, 직렬화, 압축)와, 분석용 DB가 왜 컬럼 단위로 묶어 처리하는지를 이해할 때예요. 그리고 마이크로 벤치마크의 결과가 입력 데이터의 패턴에 따라 몇 배씩 달라지는 이유이기도 해요.
    핵심 정리
    • 파이프라인 + 비순차 실행: 성능은 명령 사이의 의존 관계가 결정
    • 분기 예측 실패는 비쌈. 무작위로 갈리는 분기가 문제
    • SIMD: 연속된 배열 + 단순한 루프일 때 여러 값을 한 번에
    셀프 체크
    1. 같은 배열에 같은 조건문을 적용하는데, 배열을 정렬한 뒤에 훨씬 빨라졌습니다. 이유를 설명하세요.
    답 보기

    CPU는 조건 분기의 결과를 기다리지 않고 과거 이력으로 방향을 예측해 다음 명령을 미리 실행해요. 무작위로 섞인 데이터에서는 조건의 참과 거짓이 불규칙하게 나와 예측이 절반쯤 틀리고, 틀릴 때마다 미리 실행한 작업을 버리고 다시 시작하는 비용을 내요. 정렬된 데이터에서는 조건이 한동안 계속 거짓이다가 어느 지점부터 계속 참이 되므로 예측이 거의 다 맞아요. 실행하는 명령의 수는 같지만 예측 실패로 버리는 시간이 사라져서 빨라져요.

    4장 메모리 계층과 캐시

    메모리 접근은 균일하게 빠르지 않다

    계층 구조

    빠른 저장 장치는 비싸고 작아요. 그래서 여러 층으로 쌓아요.

    층대략적인 접근 시간크기
    레지스터1 사이클 미만수십 개
    L1 캐시약 1ns수십 KB
    L2 캐시수 ns수백 KB ~ 수 MB
    L3 캐시수십 ns수 MB ~ 수십 MB(코어 간 공유)
    메인 메모리약 100nsGB 단위
    SSD수십~수백 μsTB 단위

    L1에 있는 데이터와 메모리에서 가져와야 하는 데이터는 백 배쯤 차이 나요.

    지역성

    캐시가 효과를 내는 이유는 프로그램이 메모리를 고르게 쓰지 않기 때문이에요.

    • 시간 지역성: 방금 쓴 것을 곧 다시 쓴다.
    • 공간 지역성: 방금 쓴 것의 근처를 곧 쓴다.

    캐시 라인

    캐시는 바이트 하나가 아니라 64바이트 덩어리(캐시 라인) 단위로 가져와요. 배열의 한 원소를 읽으면 옆의 원소들도 같이 캐시에 올라와요. 그리고 순차 접근 패턴을 감지하면 CPU가 다음 라인을 미리 가져와요(프리페치).

    코드에 미치는 영향

    • 배열 순회는 빠르고 포인터 추적은 느려요. 연결 리스트나 트리는 노드마다 메모리의 다른 곳으로 뛰어서 매번 캐시 미스가 날 수 있어요.
    • 2차원 배열은 저장된 순서대로 순회해요. 행 우선으로 저장된 배열을 열 우선으로 돌면 매 접근이 다른 캐시 라인이에요.
    • 객체의 배열(참조의 배열)보다 값의 배열이 훨씬 캐시 친화적이에요.
    • 자주 함께 쓰는 필드는 가까이, 자주 쓰는 데이터와 드물게 쓰는 데이터는 분리해요.
    백엔드에서는 이것이 자료구조 챕터에서 "대부분의 경우 ArrayList가 LinkedList를 이긴다"고 한 이유예요. 중간 삽입이 O(n)이어도 연속 메모리를 미는 것이 포인터를 따라가는 것보다 빨라요. 분석용 DB가 컬럼 단위로 저장하는 것, B-Tree가 한 노드에 키를 많이 담는 것, 해시 맵 구현이 연결 리스트 대신 열린 주소법을 쓰는 것도 전부 같은 이유예요.
    시니어 심화
    • 거짓 공유: 서로 다른 스레드가 서로 다른 변수를 고쳐도 그 변수들이 같은 캐시 라인에 있으면, 한쪽이 쓸 때마다 다른 코어의 그 라인이 무효가 돼요. 논리적으로는 공유가 없는데 하드웨어 수준에서 경합해요. 스레드별 카운터 배열에서 전형적으로 나타나고, 패딩으로 라인을 떨어뜨려 풀어요.
    • 측정하세요. perf stat으로 캐시 미스 수와 명령당 사이클 수를 볼 수 있어요. 명령 수는 같은데 사이클이 많다면 메모리 접근을 기다리고 있는 거예요.
    • 큰 힙과 무작위 접근의 조합은 캐시뿐 아니라 주소 변환 캐시(TLB)도 놓쳐요. 수십 GB의 해시 맵을 무작위로 조회하는 워크로드에서 큰 페이지가 효과를 내는 이유예요.
    핵심 정리
    • 캐시와 메모리의 접근 시간 차이는 백 배 수준
    • 캐시 라인(64바이트) 단위로 가져오고 순차 접근은 미리 가져옴
    • 연속된 배열 순회가 빠르고 포인터 추적이 느린 이유
    셀프 체크
    1. 복잡도가 같은 O(n) 순회인데 배열이 연결 리스트보다 훨씬 빠른 이유를 메모리 계층으로 설명하세요.
    답 보기

    배열의 원소는 메모리에 연속해 있어요. 한 원소를 읽으면 같은 캐시 라인에 있는 이웃 원소들이 함께 캐시에 올라오고, CPU가 순차 접근을 감지해 다음 라인도 미리 가져와요. 그래서 대부분의 접근이 캐시에서 끝나요. 연결 리스트의 노드는 각각 따로 할당돼 메모리 여기저기에 흩어져 있고, 다음 노드의 위치는 현재 노드를 읽어야 알 수 있어서 미리 가져올 수도 없어요. 노드마다 캐시 미스가 나면 접근 한 번이 백 배쯤 느린 메모리 접근이 돼요. 접근 횟수는 같아도 한 번의 비용이 크게 달라요.

    5장 링킹과 로딩

    여러 파일이 하나의 실행 가능한 프로그램이 되기까지

    컴파일 단위와 심볼

    소스 파일은 각각 따로 컴파일돼 목적 파일이 돼요. 목적 파일에는 기계어와 함께, 자기가 정의한 함수·변수의 이름(심볼)과 다른 곳에 있다고 가정하고 쓴 심볼의 목록이 있어요. 다른 파일의 함수를 호출하는 자리에는 아직 주소가 비어 있어요.

    링커가 하는 일

    • 심볼 해석: 참조된 이름마다 정의를 찾아 연결해요. 못 찾으면 "정의되지 않은 참조", 둘 이상이면 "중복 정의" 에러예요.
    • 재배치: 모든 코드와 데이터의 최종 주소를 정하고, 비워 둔 주소 자리를 채워요.

    정적 링킹과 동적 링킹

    정적동적
    시점빌드할 때 라이브러리 코드를 실행 파일에 복사실행할 때 공유 라이브러리를 찾아 연결
    실행 파일크고 자기 완결적작고 외부 라이브러리에 의존
    라이브러리 갱신다시 빌드해야 반영라이브러리 파일만 교체하면 반영
    위험보안 패치가 늦게 반영실행 환경에 맞는 버전이 없으면 실행 실패

    동적 링킹에서 공유 라이브러리의 코드는 여러 프로세스가 물리 메모리를 공유해요. 그리고 함수의 실제 주소는 처음 호출될 때 찾아서 채워 넣어요(지연 바인딩).

    로딩

    실행 파일을 실행하면 OS가 파일의 각 구역(코드, 초기화된 데이터 등)을 프로세스의 가상 주소 공간에 매핑해요. 전부 읽어 들이는 것이 아니라, 실제로 접근하는 페이지만 그때 디스크에서 읽어요.

    주소 공간 배치 무작위화

    실행할 때마다 스택, 힙, 라이브러리의 위치를 무작위로 바꿔요. 공격자가 특정 코드의 주소를 미리 알 수 없게 해요. 이를 위해 코드는 어느 주소에 놓여도 동작하도록(위치 독립 코드) 컴파일돼요.

    백엔드에서는 컨테이너 이미지에서 "로컬에서는 되는데 이미지에서는 not found"가 나는 흔한 원인이 동적 링킹이에요. 빌드한 환경과 실행 환경의 C 라이브러리가 다르면(glibc 기반에서 빌드해 musl 기반 이미지에서 실행) 실행 파일이 필요한 라이브러리를 찾지 못해요. ldd로 의존하는 공유 라이브러리를 확인하고, 최소 이미지에 넣을 바이너리는 정적으로 링크해요. 네이티브 확장이 있는 패키지도 같은 문제를 겪어요.
    핵심 정리
    • 컴파일은 파일별, 링커가 심볼을 해석하고 주소를 확정
    • 정적 = 자기 완결, 동적 = 실행 환경의 라이브러리에 의존
    • 로딩은 필요한 페이지만. 주소 무작위화가 공격을 어렵게 함
    셀프 체크
    1. 빌드 서버에서 만든 실행 파일이 최소 컨테이너 이미지에서 "no such file or directory"로 실패합니다. 파일은 분명히 있습니다. 왜인가요?
    답 보기

    에러가 가리키는 것은 실행 파일 자체가 아니라 그 실행 파일이 필요로 하는 것일 가능성이 커요. 동적으로 링크된 실행 파일은 시작할 때 동적 로더와 공유 라이브러리를 찾는데, 최소 이미지에는 그것들이 없거나 다른 종류의 C 라이브러리가 들어 있어요. 로더를 찾지 못하면 실행 파일이 없는 것과 같은 에러가 나요. 의존하는 공유 라이브러리 목록을 확인해서 이미지에 넣거나, 실행 파일을 정적으로 링크해 외부 의존을 없애거나, 빌드 환경과 실행 환경의 기반 이미지를 맞춰야 해요.

    6장 멀티코어와 메모리 순서

    락과 원자 변수가 하드웨어에서 뜻하는 것

    코어마다 캐시가 있다

    각 코어는 자기 L1·L2 캐시를 가져요. 같은 메모리 위치의 사본이 여러 코어의 캐시에 동시에 있을 수 있어요. 한 코어가 그 값을 고치면 다른 코어의 사본은 낡은 것이 돼요.

    캐시 일관성 프로토콜

    코어들은 캐시 라인의 상태(나만 갖고 있고 고쳤음, 나만 갖고 있음, 여럿이 공유 중, 무효)를 서로 주고받으며 맞춰요. 한 코어가 공유 중인 라인에 쓰려면 먼저 다른 코어들의 사본을 무효화해야 해요.

    그래서 여러 코어가 같은 캐시 라인에 번갈아 쓰면 그 라인이 코어 사이를 계속 오가요. 락이 없어도 느려져요. 공유 카운터 하나를 여러 스레드가 올리는 코드가 코어를 늘려도 빨라지지 않는 이유예요.

    원자적 명령

    count++는 읽기, 더하기, 쓰기 세 단계라서 두 코어가 동시에 하면 하나가 사라져요. CPU는 이 세 단계를 다른 코어가 끼어들 수 없게 실행하는 명령을 제공해요.

    • 비교 후 교환(CAS): "이 위치의 값이 A이면 B로 바꾸고, 아니면 실패". 락 없는 자료구조와 원자 변수의 기반이에요.
    • 이 명령들은 해당 캐시 라인을 독점한 채 실행돼요. 일반 명령보다 비싸고, 경쟁이 심하면 라인을 차지하려는 다툼이 생겨요.

    쓰기 버퍼와 메모리 순서

    코어는 쓰기를 곧바로 캐시에 반영하지 않고 쓰기 버퍼에 잠깐 뒀다가 내보내요. 그래서 한 코어가 쓴 값이 다른 코어에 바로 보이지 않고, 서로 다른 위치에 대한 쓰기와 읽기의 순서가 다른 코어에게는 뒤바뀌어 보일 수 있어요.

    허용되는 재배열의 범위는 CPU 구조마다 달라요. x86은 비교적 엄격하고 ARM은 더 느슨해요. x86에서 문제없이 돌던 동시성 버그가 ARM 서버로 옮기면 드러나는 이유예요.

    메모리 장벽

    "여기까지의 쓰기가 다른 코어에 보이게 하고, 이 지점을 넘어 순서를 바꾸지 마라"는 명령이에요. 언어의 volatile, 원자 변수, 락이 내부적으로 이것을 넣어요. 프로그래머는 장벽을 직접 쓰지 않고, 언어의 메모리 모델이 정한 규칙(자바의 happens-before)을 따르면 돼요.

    백엔드에서는 실용적인 결론은 세 가지예요. 첫째, 동기화 없이 공유 변수를 읽고 쓰는 코드는 "테스트에서 문제없었다"로 안전하다고 할 수 없어요. 하드웨어와 컴파일러가 바뀌면 깨져요. 둘째, 여러 스레드가 자주 갱신하는 카운터는 원자 변수 하나보다 스레드별로 나눠 세고 읽을 때 합치는 구조(LongAdder)가 빨라요. 셋째, 가장 싼 동기화는 공유하지 않는 것이에요. 불변 객체, 스레드별 데이터, 메시지 전달.
    핵심 정리
    • 코어별 캐시 → 같은 라인에 여러 코어가 쓰면 라인이 오가며 느려짐
    • CAS 같은 원자적 명령이 락과 원자 변수의 바탕
    • 쓰기는 다른 코어에 바로 보이지 않음. 보장은 언어의 메모리 모델로
    셀프 체크
    1. 스레드 16개가 AtomicLong 하나를 계속 증가시키는 코드가 스레드 1개일 때보다 전체 처리량이 낮습니다. 이유는 무엇인가요?
    답 보기

    그 변수가 있는 캐시 라인은 한 번에 한 코어만 쓸 수 있어요. 코어 하나가 증가시키려면 그 라인을 독점해야 하고, 그러면 다른 코어들의 사본이 무효가 돼요. 16개 코어가 번갈아 쓰면 라인이 코어 사이를 끊임없이 옮겨 다니고, 각 코어는 라인을 가져오기를 기다리는 데 대부분의 시간을 써요. 또 비교 후 교환이 다른 코어의 갱신 때문에 실패해 재시도하는 일도 늘어요. 스레드 하나일 때는 라인이 한 코어의 캐시에 머물러 이런 비용이 없어요. 스레드별로 따로 세고 읽을 때 합치는 구조로 바꾸면 라인을 다투지 않아요.

    실습

    실습 과제

    작은 프로그램으로 직접 재 보면 숫자가 기억에 남아요.

    • 1장 정수 오버플로가 나는 중간값 계산과 시간 계산을 재현. 0.1을 열 번 더한 값과 1.0 비교. 금액을 double과 십진 타입으로 각각 합산해 차이 확인
    • 2장 재귀 깊이를 늘려 가며 스택 오버플로가 나는 지점을 찾고, 스레드 스택 크기 설정을 바꿔 다시 측정. 반복문으로 바꾸기
    • 3장 무작위 배열과 정렬된 배열에 같은 조건부 합산을 돌려 시간 비교
    • 4장 큰 2차원 배열을 행 우선과 열 우선으로 순회해 시간 비교. 같은 원소 수의 배열과 연결 리스트 순회 비교
    • 4장 인접한 두 카운터를 두 스레드가 각각 증가시키는 코드로 거짓 공유 재현. 패딩을 넣어 비교
    • 5장 실행 파일의 공유 라이브러리 의존성을 확인하고, 그 라이브러리가 없는 최소 이미지에서 실행해 실패 재현. 정적 링크로 해결
    • 6장 스레드 수를 늘려 가며 원자 변수 하나를 증가시키는 처리량과 스레드별 카운터의 처리량 비교
