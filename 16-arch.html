    컴퓨터 구조

    기준 교재: 컴퓨터 시스템(CS:APP, Computer Systems: A Programmer's Perspective) · 4~6주

    운영체제와 자료구조 챕터에서 "캐시 친화적", "문맥 전환 비용", "원자적 명령" 같은 말이 설명 없이 나왔어요. 이 챕터는 그 아래층이에요. 프로그램이 하드웨어에서 실제로 어떻게 실행되는지를 프로그래머의 눈으로 봐요.

    회로 설계가 아니라 "알면 코드를 다르게 짜게 되는" 내용만 골랐어요. 예시는 쇼핑몰 백엔드에서 실제로 만나는 버그와 성능 문제예요. 시간이 없으면 1장(수의 표현)과 4장(캐시)을 먼저 읽으세요. 버그와 성능에 가장 직접 닿아요.

    컴퓨터 시스템 (CS:APP) 기준 교재2~3장, 5~7장, 12장이 이 챕터의 범위
    혼자 공부하는 컴퓨터 구조+운영체제 입문CS:APP이 부담스러울 때 먼저
    1부 표현

    1장 정보의 표현 — 정수와 부동소수점

    컴퓨터의 숫자는 수학의 숫자가 아니다

    문제: 정산 합계가 1원 틀리고, 주문 번호 끝자리가 바뀐다

    두 가지 버그가 같은 주에 들어왔어요. 하나는 판매자 정산 합계가 상품별 금액을 더한 값과 1원씩 다르다는 것이었어요. 금액을 double로 계산하고 있었어요. 다른 하나는 웹 화면에 표시된 주문 번호가 DB의 번호와 끝자리가 다르다는 것이었어요. 서버는 맞는 번호를 보냈는데요. 둘 다 숫자를 컴퓨터가 어떻게 표현하는지에서 나온 문제예요.

    정수: 범위를 넘으면 조용히 돌아간다

    32비트 정수(int)는 약 −21억에서 +21억까지만 담아요. 범위를 넘으면 에러가 나지 않고 반대쪽 끝으로 넘어가요(오버플로).

    int a = 2_000_000_000;
      int b = a + a;          // -294967296. 예외 없음

    음수는 2의 보수로 표현해요. 가장 높은 비트가 음의 값을 갖는 방식이라 덧셈과 뺄셈을 같은 회로로 할 수 있어요. 대신 음수 쪽이 하나 더 넓어서, 가장 작은 값은 부호를 뒤집을 수 없어요. 실무에서 자주 만나는 오버플로는 이래요. 두 수의 중간값 (low + high) / 2, 밀리초 계산(30 * 24 * 60 * 60 * 1000은 int 범위를 넘어요), 비교 함수에서 a - b의 부호로 크기 판단, 그리고 자동 증가 ID가 21억에 닿는 날이에요.

    부동소수점: 근삿값이다

    double은 수를 "부호 × 가수 × 2의 지수"로 표현해요(IEEE 754). 2진 분수라서 10진수 0.1을 정확히 표현할 수 없어요. 1/3을 10진 소수로 정확히 못 쓰는 것과 같아요.

    0.1 + 0.2 == 0.3        // false
      0.1 + 0.2               // 0.30000000000000004

    정산 버그가 이것이었어요. 상품 금액을 double로 수천 번 더하면 작은 오차가 쌓여 반올림 결과가 1원 달라져요. 그리고 크기가 많이 다른 수를 더하면 작은 쪽이 사라지기 때문에, 더하는 순서에 따라 결과가 달라지기도 해요.

    큰 정수도 double에서는 깨진다

    double의 가수는 53비트라서, 2의 53제곱(약 9천조)보다 큰 정수는 정확히 담지 못하고 가까운 값으로 반올림돼요. 자바스크립트의 숫자는 전부 double이에요. 서버가 JSON에 64비트 주문 번호 9007199254740993을 숫자로 보내면, 브라우저가 읽는 순간 9007199254740992가 돼요. 주문 번호 버그가 이것이었어요.

    백엔드에서는 돈을 double로 계산하지 마세요. 정수 최소 단위(원, 센트)를 long으로 쓰거나 BigDecimal을 쓰고, DB는 DECIMAL로 저장해요. JSON으로 내보내는 64비트 ID는 숫자가 아니라 문자열로 보내세요. 그리고 날짜·시간 계산은 직접 곱셈하지 말고 Duration, Instant 같은 시간 타입을 쓰면 오버플로와 단위 실수를 함께 피할 수 있어요.
    시니어 심화 조용한 오버플로가 가장 위험한 곳은 틀려도 아무도 모르는 계산이에요. 수량 × 단가가 int 범위를 넘어 음수가 되면, 할인 계산이 음수를 받아 고객에게 돈을 주는 주문이 될 수 있어요. 외부 입력으로 버퍼 크기나 배열 크기를 계산하는 코드에서 오버플로가 나면 보안 취약점으로 이어져요.

    그래서 틀리면 안 되는 계산에는 넘치면 예외를 던지는 연산을 써요. 자바의 Math.addExact, Math.multiplyExact, Math.toIntExact예요. 조용히 틀린 값보다 시끄러운 예외가 나아요. 부동소수점을 써야 하는 계산(통계, 추천 점수)에서는 같음 비교 대신 허용 오차로 비교하고, 병렬로 합산하면 더하는 순서가 실행마다 달라져 끝자리가 바뀔 수 있다는 것을 알아 두세요. 재현성이 필요하면 순서를 고정해요. 마지막으로 NaN은 자기 자신과도 같지 않아서 정렬과 집계를 망가뜨려요. 외부에서 들어온 실수는 유한한 값인지 먼저 확인하세요.

    핵심 정리
    • 정수는 범위가 유한. 넘으면 조용히 반대쪽으로
    • 부동소수점은 근삿값. 0.1을 정확히 표현 못 하고, 2의 53제곱보다 큰 정수도 깨짐
    • 돈은 정수 최소 단위나 십진 타입. 64비트 ID는 JSON에서 문자열로
    셀프 체크
    1. JSON으로 64비트 정수 ID 9007199254740993을 보냈는데 브라우저에서 9007199254740992로 보입니다. 이유는 무엇인가요?
    답 보기

    자바스크립트의 숫자는 64비트 부동소수점이에요. 부동소수점은 가수 부분이 53비트라서 2의 53제곱(9007199254740992)까지만 모든 정수를 정확히 표현해요. 그보다 큰 정수는 표현할 수 있는 가장 가까운 값으로 반올림돼요. 서버가 보낸 값은 정확했지만 클라이언트가 숫자로 읽는 순간 정밀도를 잃은 거예요. 64비트 ID는 JSON에서 문자열로 내보내야 해요.

    2장 프로그램의 기계 수준 표현

    함수 호출은 스택 위에서 일어난다

    문제: 카테고리 트리를 읽다 서버가 죽었다

    상품 카테고리를 트리로 보여주는 API가 있어요. 카테고리마다 하위 카테고리를 재귀로 불러와요. 테스트 데이터는 깊이가 3이라 문제가 없었는데, 운영에서 한 판매자가 실수로 깊이 5,000짜리 카테고리 사슬을 만들자 이 API가 StackOverflowError로 죽었어요. 메모리는 충분했는데 왜 넘쳤을까요?

    기계어는 아주 단순하다

    컴파일러(자바라면 JIT, 1장)는 코드를 CPU가 실행하는 기계어 명령으로 바꿔요. 명령 하나는 아주 단순해요. CPU 안의 작은 저장 공간인 레지스터 사이의 계산, 메모리에서 읽기와 쓰기, 조건에 따라 다른 주소로 점프하기 정도예요. if와 for는 기계어에 없어요. 전부 "비교하고, 결과에 따라 다른 주소로 점프"로 바뀌어요. CPU는 다음에 실행할 명령의 주소(프로그램 카운터)와 스택의 현재 꼭대기(스택 포인터)를 레지스터에 들고 있어요.

    함수를 부를 때마다 스택에 한 칸

    함수를 호출할 때마다 스택에 프레임이 하나 쌓여요. 프레임에는 함수가 끝나면 돌아갈 주소, 지역 변수, 레지스터에 다 못 담은 인자와 잠시 저장해 둘 값이 들어가요. 함수가 끝나면 프레임이 사라지고 호출한 곳으로 돌아가요. 지역 변수가 함수가 끝나면 사라지는 이유예요.

    스택의 크기는 스레드마다 고정돼 있어요(자바는 보통 1MB 안팎). 재귀 호출 한 번마다 프레임이 하나씩 쌓이니, 깊이 5,000의 재귀는 프레임 5,000개예요. 프레임 하나가 수백 바이트면 스택을 다 써요. 힙에 메모리가 아무리 남아 있어도 스택은 따로라서 상관없어요.

    해결: 반복문과 명시적 스택

    깊이를 보장할 수 없는 데이터를 재귀로 처리하지 마세요. 재귀를 반복문으로 바꾸고, 방문할 카테고리를 힙에 있는 자료구조(ArrayDeque)에 넣었다 꺼내요. 힙은 스택보다 훨씬 커서 깊이 제한에서 벗어나요. 그리고 판매자 실수로 순환(A의 하위가 B, B의 하위가 A)이 생기면 반복문도 끝나지 않으니, 방문한 카테고리를 기록하고 깊이 상한을 둬요.

    스택과 힙

    스택힙
    할당·해제스택 포인터를 움직이기만 함. 매우 빠름빈 자리를 찾아야 하고, 해제나 GC가 필요
    수명함수가 끝나면 사라짐해제되거나 GC될 때까지
    크기작고 고정크고 늘어남
    공유스레드마다 따로모든 스레드가 공유
    백엔드에서는 스택 트레이스는 이 프레임들을 위에서 아래로 적은 거예요. 예외 객체를 만들 때 이 스택을 훑어 기록하는 비용이 커서, 정상적인 흐름 제어에 예외를 쓰면 느려요. 그리고 스프링의 프록시, 필터, AOP는 요청 하나에 프레임을 수백 개씩 쌓아요. 그 위에서 재귀를 하면 생각보다 빨리 스택이 바닥나요.
    시니어 심화 스택의 구조를 알면 버퍼 오버플로 공격이 왜 가능한지 보여요. C 같은 언어에서 스택의 지역 배열에 길이 검사 없이 쓰면, 배열 옆에 저장된 복귀 주소를 덮어쓸 수 있어요. 함수가 끝나면 CPU는 그 주소로 점프하니, 공격자가 정한 코드가 실행돼요. 자바 같은 메모리 안전 언어는 배열 경계를 검사해서 막지만, 네이티브 라이브러리(이미지 처리, 압축)를 호출하는 순간 다시 노출돼요. 그래서 운영체제와 컴파일러는 겹겹의 방어를 둬요. 복귀 주소 앞에 확인값을 두어 덮어쓰였는지 검사하고, 실행할 때마다 메모리 배치를 무작위로 바꾸고(5장), 스택 영역에서는 코드를 실행하지 못하게 해요.

    성능 쪽에서는 인라이닝이 프레임 비용을 없애요. JIT가 작은 메서드의 호출을 호출한 자리에 펼쳐 넣으면 프레임이 생기지 않고, 더 넓은 범위의 최적화가 가능해져요. 작은 메서드로 잘게 나눈 코드가 느리지 않은 이유예요. 메서드 밖으로 나가지 않는 객체는 JIT가 힙 대신 스택이나 레지스터에 두기도 해요(탈출 분석). 그래서 짧게 쓰고 버리는 임시 객체는 할당 비용이 거의 없을 수 있어요.

    핵심 정리
    • 제어 구조는 비교 + 점프로 번역됨
    • 호출마다 스택 프레임. 스택 크기는 스레드마다 고정 → 깊은 재귀는 넘침
    • 깊이를 보장할 수 없으면 반복문 + 힙의 자료구조로. 순환과 깊이 상한도
    셀프 체크
    1. 깊이를 알 수 없는 트리를 재귀로 순회하는 코드가 운영에서 StackOverflowError를 냈습니다. 원인과 해결 방법을 말해보세요.
    답 보기

    재귀 호출은 한 번마다 스택에 프레임을 쌓아요. 스레드의 스택 크기는 고정돼 있어서 재귀 깊이가 그 한도를 넘으면 스택이 넘쳐요. 테스트 데이터는 얕았지만 운영 데이터 중에 아주 깊거나 순환하는 구조가 있었던 거예요. 해결은 재귀를 반복문으로 바꾸고, 방문할 노드를 힙에 있는 명시적 스택이나 큐에 담는 거예요. 힙은 훨씬 커서 깊이 제한에서 벗어나요. 순환 가능성이 있으면 방문한 노드를 기록해 다시 들어가지 않게 하고 깊이 상한도 둬요.

    2부 실행

    3장 파이프라인과 분기 예측

    CPU는 명령을 하나씩 순서대로 실행하지 않는다

    문제: 정렬했더니 필터가 빨라졌다

    추천 서비스에서 상품 점수 배열 1,000만 개 중 기준 점수 이상인 것만 합산하는 코드가 있어요. 우연히 배열을 먼저 정렬해 두었더니 같은 반복문이 몇 배 빨라졌어요. 실행하는 명령의 개수는 똑같은데요. 이유를 알려면 CPU가 명령을 실행하는 방식을 봐야 해요.

    파이프라인: 여러 명령을 겹쳐서 실행한다

    명령 하나의 실행은 여러 단계로 나뉘어요. 명령을 가져오고, 해석하고, 계산하고, 메모리에 접근하고, 결과를 기록해요. CPU는 한 명령이 다섯 단계를 다 끝내길 기다리지 않고, 앞 명령이 다음 단계로 넘어가면 바로 다음 명령의 첫 단계를 시작해요. 세탁기가 돌아가는 동안 다음 빨래를 넣는 것과 같아요.

    현대 CPU는 여기서 더 나아가 한 사이클에 여러 명령을 동시에 시작하고, 서로 기다릴 필요가 없는 명령은 순서를 바꿔 준비된 것부터 실행해요. 결과는 원래 순서대로 확정해서 프로그램에게는 순서대로 실행된 것처럼 보여요. 그래서 성능을 정하는 것은 명령의 개수가 아니라 명령 사이의 의존 관계예요. 앞의 결과가 있어야 다음을 시작할 수 있는 긴 사슬은 겹쳐 실행할 수 없어요.

    분기 예측: 결과를 기다리지 않고 미리 간다

    조건 분기(if)가 파이프라인의 골칫거리예요. 조건을 계산하기 전에는 다음에 어느 쪽 명령을 가져올지 알 수 없는데, 기다리면 파이프라인이 텅 비어요. 그래서 CPU는 과거의 기록을 보고 어느 쪽으로 갈지 예측해서 미리 실행해요. 예측이 맞으면 손해가 없어요. 틀리면 미리 실행한 것을 전부 버리고 올바른 쪽에서 다시 시작해요. 명령 십수 개를 실행할 시간을 잃어요.

    규칙적인 분기(반복문의 조건, 거의 항상 같은 쪽으로 가는 검사)는 거의 다 맞혀요. 문제는 데이터에 따라 무작위로 갈리는 분기예요. 섞여 있는 점수 배열에서 if (score >= 기준)은 참과 거짓이 불규칙해서 절반 가까이 틀려요. 정렬된 배열에서는 한동안 계속 거짓이다가 어느 지점부터 계속 참이라 거의 다 맞혀요. 명령 수는 같지만 버리는 시간이 사라져서 빨라진 거예요.

    SIMD: 명령 하나로 여러 값

    명령 하나로 여러 데이터에 같은 계산을 동시에 하는 기능도 있어요. 배열 전체에 같은 계산을 하는 반복문을 컴파일러가 자동으로 이런 명령으로 바꾸기도 해요(자동 벡터화). 데이터가 연속된 배열에 있고 반복문 안에 복잡한 분기가 없어야 가능해요.

    백엔드에서는 일반적인 백엔드 코드에서 분기 예측을 의식하며 짤 일은 드물어요. 네트워크와 DB의 대기 시간이 훨씬 커요. 이 지식이 쓰이는 곳은 대량의 데이터를 메모리에서 처리하는 코드(집계, 필터, 직렬화, 압축)이고, 분석용 DB가 왜 데이터를 컬럼 단위로 묶어 한꺼번에 처리하는지 이해할 때예요. 그리고 마이크로 벤치마크의 결과가 입력 데이터의 패턴에 따라 몇 배씩 달라지는 이유이기도 해요(성능 분석 챕터 8장).
    핵심 정리
    • 파이프라인 + 순서 바꿔 실행: 성능은 명령 사이의 의존 관계가 결정
    • 분기 예측이 틀리면 미리 실행한 것을 버림. 무작위로 갈리는 분기가 비쌈
    • SIMD: 연속된 배열 + 단순한 반복문일 때 여러 값을 한 번에
    셀프 체크
    1. 같은 배열에 같은 조건문을 적용하는데, 배열을 정렬한 뒤에 훨씬 빨라졌습니다. 이유를 설명하세요.
    답 보기

    CPU는 조건 분기의 결과를 기다리지 않고 과거 기록으로 방향을 예측해 다음 명령을 미리 실행해요. 무작위로 섞인 데이터에서는 조건의 참과 거짓이 불규칙하게 나와 예측이 절반 가까이 틀리고, 틀릴 때마다 미리 실행한 작업을 버리고 다시 시작하는 비용을 내요. 정렬된 데이터에서는 조건이 한동안 계속 거짓이다가 어느 지점부터 계속 참이 되므로 예측이 거의 다 맞아요. 실행하는 명령의 수는 같지만 예측 실패로 버리는 시간이 사라져서 빨라져요.

    4장 메모리 계층과 캐시

    메모리 접근은 똑같이 빠르지 않다

    문제: 같은 O(n)인데 열 배 느리다

    장바구니 상품 목록을 처리하는 코드에서 LinkedList를 ArrayList로 바꿨더니 순회가 열 배 가까이 빨라졌어요. 둘 다 처음부터 끝까지 한 번씩 보는 O(n)이고, 원소 수도 같은데요. 자료구조 챕터에서 "대부분의 경우 배열이 이긴다"고 한 이유가 여기 있어요.

    메모리는 여러 층이다

    빠른 저장 장치는 비싸고 작아요. 그래서 컴퓨터는 메모리를 여러 층으로 쌓아요.

    CPU 바로 옆의 L1 캐시에 있는 데이터와 메인 메모리에서 가져와야 하는 데이터는 접근 시간이 백 배쯤 차이 나요. CPU는 계산을 기다리기보다 메모리를 기다리는 시간이 훨씬 많아요. 그래서 데이터가 캐시에 있느냐가 성능을 크게 좌우해요.

    캐시가 통하는 이유: 지역성

    캐시가 효과를 내는 것은 프로그램이 메모리를 고르게 쓰지 않기 때문이에요. 방금 쓴 것을 곧 다시 쓰고(시간 지역성), 방금 쓴 것의 근처를 곧 써요(공간 지역성). 그리고 캐시는 바이트 하나가 아니라 64바이트 덩어리(캐시 라인)로 가져와요. 배열의 원소 하나를 읽으면 그 옆의 원소들도 함께 캐시에 올라와요. 게다가 CPU는 순서대로 읽는 패턴을 알아채면 다음 덩어리를 미리 가져와요(프리페치).

    배열과 연결 리스트

    이제 위 문제의 답이 나와요. ArrayList는 원소 참조가 메모리에 연속으로 놓여 있어요. 하나를 읽으면 옆의 것들이 같은 캐시 라인에 함께 올라오고, CPU가 순서대로 읽는 것을 알아채 다음 라인도 미리 가져와요. 대부분의 접근이 캐시에서 끝나요. LinkedList의 노드는 각각 따로 만들어져 힙 여기저기에 흩어져 있고, 다음 노드의 위치는 지금 노드를 읽어야 알 수 있어서 미리 가져올 수도 없어요. 노드마다 메인 메모리까지 가는 거예요. 접근 횟수는 같아도 한 번의 비용이 다른 거예요.

    코드에 미치는 영향

    연결 리스트나 트리처럼 포인터를 따라가는 구조보다 배열이 캐시에 유리해요. 2차원 배열은 저장된 순서(행 우선)대로 돌아요. 반대로 돌면 매번 다른 캐시 라인이에요. 객체를 담은 배열(참조의 배열)보다 값 자체를 담은 배열(int[])이 훨씬 유리해요. 그리고 자주 함께 쓰는 필드는 가까이, 자주 쓰는 데이터와 드물게 쓰는 데이터는 떼어 두면 캐시에 쓸모 있는 데이터가 더 많이 담겨요.

    백엔드에서는 이것이 B-Tree가 노드 하나에 키를 수백 개 담는 이유이고(데이터베이스 챕터 8장), 분석용 DB가 컬럼 단위로 저장하는 이유이고, 해시 맵 구현이 연결 리스트 대신 배열 안에서 빈자리를 찾는 방식을 쓰는 이유예요. 모두 "한 번 가져온 캐시 라인을 최대한 쓰자"는 같은 생각이에요. 백엔드 코드에서는 큰 목록을 처리할 때 LinkedList를 쓰지 않는 것, 숫자 목록은 박싱된 List<Long> 대신 long[]을 쓰는 것으로 대부분 충분해요.
    시니어 심화 캐시 라인 단위로 움직인다는 사실은 멀티스레드 코드에서 함정이 돼요. 거짓 공유예요. 서로 다른 두 스레드가 서로 다른 변수를 고치는데, 두 변수가 우연히 같은 64바이트 캐시 라인에 있다고 해 봐요. 한 코어가 자기 변수를 쓰면 다른 코어의 그 캐시 라인 전체가 무효가 되고, 다른 코어는 자기 변수를 쓰려고 그 라인을 다시 가져와야 해요. 코드상으로는 공유하는 것이 없는데 하드웨어 수준에서 계속 다퉈요. 스레드별 카운터를 배열에 나란히 둔 코드에서 전형적으로 나타나고, 스레드를 늘렸는데 오히려 느려지는 증상으로 보여요. 변수 사이에 빈 공간(패딩)을 넣어 다른 캐시 라인으로 떨어뜨리면 풀려요(자바의 @Contended, LongAdder가 내부적으로 이렇게 해요).

    캐시 문제는 측정할 수 있어요. perf stat으로 캐시 미스 수와 "명령 하나에 걸린 사이클 수"를 보면, 명령 수는 같은데 사이클이 많을 때 메모리를 기다리고 있다는 것이 드러나요. 그리고 수십 GB의 해시 맵을 무작위로 조회하는 워크로드는 캐시뿐 아니라 주소 변환 캐시(TLB, 운영체제 챕터 19장)도 놓쳐서, 큰 페이지를 쓰면 효과가 커요.

    핵심 정리
    • 캐시와 메인 메모리의 접근 시간은 백 배쯤 차이
    • 캐시 라인(64바이트) 단위로 가져오고, 순서대로 읽으면 미리 가져옴
    • 연속된 배열 순회가 빠르고 포인터 따라가기가 느린 이유
    셀프 체크
    1. 복잡도가 같은 O(n) 순회인데 배열이 연결 리스트보다 훨씬 빠른 이유를 메모리 계층으로 설명하세요.
    답 보기

    배열의 원소는 메모리에 연속으로 있어요. 한 원소를 읽으면 같은 캐시 라인에 있는 이웃 원소들이 함께 캐시에 올라오고, CPU가 순서대로 읽는 것을 알아채 다음 라인도 미리 가져와요. 그래서 대부분의 접근이 캐시에서 끝나요. 연결 리스트의 노드는 각각 따로 만들어져 메모리 여기저기에 흩어져 있고, 다음 노드의 위치는 지금 노드를 읽어야 알 수 있어서 미리 가져올 수도 없어요. 노드마다 캐시 미스가 나면 한 번의 접근이 백 배쯤 느린 메인 메모리 접근이 돼요. 접근 횟수는 같아도 한 번의 비용이 크게 달라요.

    5장 링킹과 로딩

    빌드 서버에서는 돌던 실행 파일이 컨테이너에서 "없다"고 한다

    문제: 파일은 분명히 있는데 "no such file or directory"

    이미지 리사이즈를 하는 작은 Go 프로그램을 빌드 서버에서 만들고, 아주 작은 기반 이미지(Alpine)의 컨테이너에 복사해 실행했어요. 그랬더니 exec: no such file or directory가 났어요. ls로 보면 파일은 분명히 그 자리에 있고 실행 권한도 있어요. 무엇이 없다는 걸까요?

    파일마다 따로 컴파일하고, 링커가 잇는다

    소스 파일은 각각 따로 컴파일되어 목적 파일이 돼요. 목적 파일에는 기계어와 함께, 그 파일이 정의한 함수·변수의 이름(심볼)과, 다른 곳에 있다고 가정하고 쓴 심볼의 목록이 들어 있어요. 다른 파일이나 라이브러리의 함수를 부르는 자리에는 아직 주소가 비어 있어요.

    링커는 두 가지 일을 해요. 참조된 이름마다 정의를 찾아 연결하고(못 찾으면 "정의되지 않은 참조", 둘 이상이면 "중복 정의" 에러예요), 모든 코드와 데이터의 최종 주소를 정해서 비워 둔 자리를 채워요.

    정적 링킹과 동적 링킹

    라이브러리를 연결하는 시점이 두 가지예요. 정적 링킹은 빌드할 때 라이브러리 코드를 실행 파일 안에 복사해요. 실행 파일이 크지만 혼자서 돌아요. 라이브러리에 보안 패치가 나오면 다시 빌드해야 해요. 동적 링킹은 실행할 때 운영체제의 동적 로더가 필요한 공유 라이브러리(.so)를 찾아 연결해요. 실행 파일이 작고, 여러 프로세스가 같은 라이브러리의 메모리를 나눠 쓰고, 라이브러리 파일만 바꾸면 패치가 반영돼요. 대신 실행 환경에 맞는 라이브러리가 있어야 해요.

    위 문제가 이것이었어요. 빌드 서버(Ubuntu)는 C 표준 라이브러리로 glibc를 쓰고, 실행 파일은 glibc의 동적 로더를 찾도록 동적 링크돼 있었어요. Alpine 이미지에는 glibc 대신 musl이라는 다른 C 라이브러리가 있어서, 그 로더 파일 자체가 없었어요. 커널은 실행 파일이 가리키는 로더를 못 찾았고, 그 실패를 "파일이 없다"로 보고한 거예요. 없는 것은 실행 파일이 아니라 로더였어요.

    로딩

    실행 파일을 실행하면 운영체제가 파일의 각 구역(코드, 초기화된 데이터)을 프로세스의 가상 주소 공간에 연결만 해 둬요. 전부 읽어 들이지 않고, 실제로 접근하는 페이지만 그때 디스크에서 읽어요(운영체제 챕터 18장). 그리고 실행할 때마다 스택, 힙, 라이브러리의 위치를 무작위로 바꿔서, 공격자가 특정 코드의 주소를 미리 알 수 없게 해요(주소 공간 배치 무작위화). 이를 위해 코드는 어느 주소에 놓여도 동작하도록 컴파일돼요.

    백엔드에서는 컨테이너 이미지에서 "로컬에서는 되는데 이미지에서는 안 된다"의 흔한 원인이 이 문제예요. ldd 실행파일로 어떤 공유 라이브러리에 의존하는지 확인하고, 최소 이미지에 넣을 바이너리는 정적으로 링크하거나(Go는 CGO_ENABLED=0), 빌드 이미지와 실행 이미지의 기반(glibc 계열인지 musl 계열인지)을 맞추세요. 네이티브 확장이 들어 있는 라이브러리(이미지 처리, 암호화)도 같은 문제를 겪어요.
    핵심 정리
    • 파일마다 따로 컴파일, 링커가 심볼을 연결하고 주소를 확정
    • 정적 = 혼자 돌아감, 동적 = 실행 환경의 로더와 라이브러리에 의존
    • 로더가 없으면 "파일 없음"으로 실패. 로딩은 필요한 페이지만, 주소는 무작위
    셀프 체크
    1. 빌드 서버에서 만든 실행 파일이 최소 컨테이너 이미지에서 "no such file or directory"로 실패합니다. 파일은 분명히 있습니다. 왜인가요?
    답 보기

    에러가 가리키는 것은 실행 파일 자체가 아니라 그 실행 파일이 필요로 하는 것일 가능성이 커요. 동적으로 링크된 실행 파일은 시작할 때 동적 로더와 공유 라이브러리를 찾는데, 최소 이미지에는 그것들이 없거나 다른 종류의 C 라이브러리가 들어 있어요. 로더를 찾지 못하면 실행 파일이 없는 것과 같은 에러가 나요. 의존하는 공유 라이브러리 목록을 확인해서 이미지에 넣거나, 실행 파일을 정적으로 링크해 외부 의존을 없애거나, 빌드 환경과 실행 환경의 기반 이미지를 맞춰야 해요.

    6장 멀티코어와 메모리 순서

    락과 원자 변수가 하드웨어에서 뜻하는 것

    문제: 스레드를 늘렸더니 카운터가 느려졌다

    주문 API 서버에서 "초당 주문 수"를 세는 통계 카운터를 AtomicLong 하나로 만들었어요. 코어 16개 서버에서 요청 처리 스레드가 전부 이 카운터를 올렸더니, 카운터 갱신 하나가 단일 스레드일 때보다 수십 배 느려졌고 전체 처리량도 떨어졌어요. 락도 안 쓰는데 왜 느려질까요?

    코어마다 캐시가 있다

    코어는 각자 L1, L2 캐시를 가져요(4장). 그래서 같은 메모리 위치의 사본이 여러 코어의 캐시에 동시에 있을 수 있어요. 한 코어가 그 값을 고치면 다른 코어의 사본은 낡은 것이 돼요. 코어들은 캐시 일관성 프로토콜로 이것을 맞춰요. 캐시 라인마다 "나만 갖고 있고 고쳤음", "나만 갖고 있음", "여럿이 공유 중", "무효" 같은 상태를 두고 서로 알려요. 한 코어가 공유 중인 라인에 쓰려면 먼저 다른 코어들의 사본을 무효로 만들어야 해요.

    여러 코어가 같은 캐시 라인에 번갈아 쓰면, 그 라인이 코어 사이를 계속 오가요. 코어 하나가 쓰려면 라인을 가져와 독점해야 하고, 그 순간 다른 코어들의 사본은 무효가 되고, 다음 코어가 쓰려면 다시 가져와야 해요. 위 문제의 카운터가 이것이에요. 16개 코어가 한 캐시 라인을 두고 줄을 서서, 대부분의 시간을 라인이 오기를 기다리는 데 썼어요. 락이 없어도 사실상 직렬로 실행된 거예요.

    원자적 명령

    count++는 읽기, 더하기, 쓰기 세 단계라 두 코어가 동시에 하면 하나가 사라져요. CPU는 이것을 다른 코어가 끼어들 수 없게 한 번에 하는 명령을 줘요. 대표적인 것이 비교 후 교환(CAS)이에요. "이 위치의 값이 A이면 B로 바꾸고, 아니면 실패"를 한 번에 해요. 원자 변수와 락이 전부 이 위에 만들어져요. 이 명령은 해당 캐시 라인을 독점한 채 실행돼서 일반 명령보다 비싸고, 경쟁이 심하면 라인을 차지하려는 다툼과 실패 후 재시도가 겹쳐요.

    해결은 같은 라인을 다투지 않게 하는 거예요. 스레드마다 따로 세고, 값이 필요할 때 합쳐요. LongAdder가 이렇게 해요. 통계 카운터를 LongAdder로 바꾸자 처리량이 원래대로 돌아왔어요.

    쓴 값이 바로 보이지 않는다

    코어는 쓰기를 곧바로 캐시에 반영하지 않고 쓰기 버퍼에 잠깐 뒀다가 내보내요. 그래서 한 코어가 쓴 값이 다른 코어에 바로 보이지 않고, 서로 다른 위치에 대한 읽기와 쓰기의 순서가 다른 코어에게는 뒤바뀌어 보일 수 있어요. 허용되는 뒤바뀜의 범위는 CPU마다 달라요. x86은 비교적 엄격하고 ARM은 더 느슨해요. 그래서 x86 서버에서 문제없던 동시성 버그가 ARM 서버(클라우드의 Graviton 등)로 옮기면 드러나요.

    "여기까지의 쓰기를 다른 코어에 보이게 하고, 이 지점을 넘어 순서를 바꾸지 마라"는 명령이 메모리 장벽이에요. 언어의 volatile, 원자 변수, 락이 내부적으로 이것을 넣어요. 프로그래머가 장벽을 직접 쓸 일은 없고, 언어의 메모리 모델이 정한 규칙(자바의 happens-before, JVM 챕터 6장)을 따르면 돼요.

    백엔드에서는 실무에서의 결론은 세 가지예요. 첫째, 동기화 없이 공유 변수를 읽고 쓰는 코드는 "테스트에서 문제없었다"로 안전하다고 할 수 없어요. 하드웨어와 JIT가 바뀌면 깨져요. 둘째, 여러 스레드가 자주 올리는 카운터는 원자 변수 하나보다 LongAdder가 빨라요. 셋째, 가장 싼 동기화는 공유하지 않는 것이에요. 불변 객체, 스레드별 데이터, 메시지로 넘기기를 먼저 생각하세요.
    핵심 정리
    • 코어마다 캐시 → 같은 라인에 여러 코어가 쓰면 라인이 오가며 사실상 직렬
    • CAS 같은 원자적 명령이 락과 원자 변수의 바탕. 경쟁하면 비쌈 → 나눠서 세기
    • 쓰기는 다른 코어에 바로 보이지 않음. 뒤바뀜 범위는 CPU마다 다름 → 언어의 메모리 모델로
    셀프 체크
    1. 스레드 16개가 AtomicLong 하나를 계속 증가시키는 코드가 스레드 1개일 때보다 전체 처리량이 낮습니다. 이유는 무엇인가요?
    답 보기

    그 변수가 있는 캐시 라인은 한 번에 한 코어만 쓸 수 있어요. 코어 하나가 증가시키려면 그 라인을 독점해야 하고, 그러면 다른 코어들의 사본이 무효가 돼요. 16개 코어가 번갈아 쓰면 라인이 코어 사이를 끊임없이 오가고, 각 코어는 라인을 가져오기를 기다리는 데 대부분의 시간을 써요. 비교 후 교환이 다른 코어의 갱신 때문에 실패해 재시도하는 일도 늘어요. 스레드 하나일 때는 라인이 한 코어의 캐시에 머물러 이런 비용이 없어요. 스레드별로 따로 세고 읽을 때 합치는 구조(LongAdder)로 바꾸면 라인을 다투지 않아요.

    실습

    실습 과제

    작은 프로그램으로 직접 재 보면 숫자가 기억에 남아요.

    • 1장 int 오버플로가 나는 중간값 계산과 밀리초 계산 재현. 금액 1만 건을 double과 BigDecimal로 합산해 차이 확인. 2의 53제곱 + 1을 JSON 숫자로 브라우저에 보내 보기
    • 2장 재귀 깊이를 늘려 가며 StackOverflowError가 나는 지점을 찾고, 스택 크기 옵션(-Xss)을 바꿔 다시 측정. 반복문 + ArrayDeque로 바꾸기
    • 3장 무작위 배열과 정렬된 배열에 같은 조건부 합산을 돌려 시간 비교
    • 4장 원소 100만 개의 ArrayList와 LinkedList 순회 시간 비교. 큰 2차원 배열을 행 우선과 열 우선으로 순회해 비교
    • 5장 동적 링크된 실행 파일을 Alpine 이미지에서 실행해 "no such file or directory" 재현. ldd로 원인 확인 후 정적 링크로 해결
    • 6장 스레드 수를 1, 2, 4, 8, 16으로 늘려 가며 AtomicLong 하나와 LongAdder의 처리량 비교. 인접한 두 카운터로 거짓 공유 재현
