    데이터베이스

    기준 교재: Real MySQL 8.0 (백은빈·이성욱) 1권·2권 · 6~8주 · 가장 중요한 챕터

    『Real MySQL 8.0』은 MySQL 내부 구조부터 쿼리 튜닝, 복제까지 실무 관점으로 다루는 국내 표준 교재예요. 이 페이지는 1권의 4장(아키텍처) → 5장(트랜잭션과 잠금) → 8장(인덱스) → 9장(옵티마이저) → 10장(실행 계획) → 11장(쿼리 최적화) → 13장(파티션), 2권의 15장(데이터 타입) → 16장(복제) 순서를 따라요. 교재에 없는 관계형 모델링 기초는 0장으로 앞에 붙였어요.

    PostgreSQL을 쓰더라도 B-Tree, MVCC, 격리 수준, 실행 계획의 원리는 같아요. 다른 부분은 각 장에 표시했어요.

    0장 정규화와 키 설계

    테이블을 어떻게 나누고 무엇을 키로 삼을까

    정규화의 목적

    같은 사실이 두 곳에 있으면 한 곳만 수정되는 갱신 이상이 생겨요. 정규화는 중복을 제거해서 사실 하나가 한 곳에만 있게 만드는 과정이에요.

    • 1NF: 모든 컬럼이 원자값. "태그: a,b,c" 같은 콤마 리스트 금지, 반복 컬럼(phone1, phone2) 금지.
    • 2NF: 복합키의 일부에만 종속된 컬럼 분리. (주문ID, 상품ID) → 상품명은 상품ID에만 종속 → 상품 테이블로.
    • 3NF: 키가 아닌 컬럼이 다른 비키 컬럼을 결정하면 분리. 회원(우편번호 → 시도)에서 시도는 우편번호 테이블로.
    • BCNF: 모든 결정자가 후보키. 실무에선 3NF까지 가면 대부분 충분.

    반정규화

    조회 성능을 위해 의도적으로 중복을 두는 것. 게시글의 댓글 수 컬럼, 주문의 상품명 스냅샷(상품명이 바뀌어도 당시 이름 유지가 목적이면 중복이 아니라 정당한 설계). 원칙: 정규화 먼저, 측정된 병목이 있을 때만, 갱신 경로를 한 곳으로.

    외래키

    참조 무결성을 DB가 보장해요. 대가: 쓰기마다 부모 확인(락), 삭제 순서 제약, 샤딩 불가. 대규모 서비스는 FK를 빼고 애플리케이션에서 관리하기도 하지만, 그만큼 고아 데이터 위험을 떠안는 거예요. 기본은 두고, 측정된 이유가 있을 때 빼세요.

    백엔드에서는 JPA 엔티티를 먼저 그리고 테이블을 자동 생성하면 정규화가 안 된 스키마가 나오기 쉬워요. 테이블을 먼저 설계하세요. 그리고 "상태"를 문자열 컬럼으로 두면 오타가 데이터가 돼요. ENUM이나 코드 테이블, 또는 CHECK 제약을 쓰세요.
    시니어 심화 정규화와 제약은 운영 비용과 맞바꾸는 결정이에요.
    • 외래키의 비용: 자식 행을 넣을 때마다 부모 행을 확인하면서 잠금을 잡아서, 부모 행 갱신과 경합하고 데드락의 재료가 돼요. 일부 온라인 스키마 변경 도구는 외래키가 있는 테이블을 지원하지 않거나 제약이 있고, 샤딩하면 샤드 사이에는 외래키를 걸 수 없어요. 그래서 큰 서비스는 외래키 없이 애플리케이션 검증과 정합성 검사 배치로 가기도 해요. 어느 쪽이든 의식적인 선택이어야 해요.
    • 반정규화한 값은 어긋나요. 갱신 경로를 하나로 모으는 것에 더해, 원본과 복사본을 주기적으로 대조하는 쿼리를 돌려 어긋남을 찾아내야 해요.
    • 소프트 삭제(deleted_at)는 모든 조회에 조건을 강요하고, 유니크 제약을 깨뜨리고(삭제된 행과 중복), 인덱스를 키워요. 정말 복구가 필요한지, 별도 이력 테이블로 옮기는 편이 낫지 않은지 먼저 따져요.
    핵심 정리
    • 정규화 = 사실 하나가 한 곳에, 3NF까지가 실무 기준
    • 반정규화는 측정 후, 갱신 경로를 한 곳으로
    • PK는 작고 순차적인 대리키, 자연키 지양

    1권 4장 아키텍처

    4.1 MySQL 엔진 아키텍처

    MySQL 엔진과 스토리지 엔진의 분리, 쿼리가 실행되는 경로

    두 층 구조

    • MySQL 엔진: 커넥션 핸들러, SQL 파서, 전처리기, 옵티마이저, 쿼리 실행기. "무엇을 어떻게 읽을지" 결정.
    • 스토리지 엔진: 실제로 디스크에서 데이터를 읽고 써요. InnoDB가 기본이고 사실상 유일한 선택이에요(MyISAM은 트랜잭션·행 락 없음). 테이블마다 다른 엔진 가능.

    MySQL 엔진이 스토리지 엔진에 "이 인덱스로 이 범위를 읽어 줘"라고 핸들러 API로 요청해요. 옵티마이저는 스토리지 엔진이 제공하는 통계를 보고 계획을 세워요.

    스레드 구조

    MySQL은 프로세스 하나에 스레드 여러 개예요. 클라이언트 연결마다 포그라운드 스레드(커넥션 스레드) 하나가 쿼리를 처리하고, 백그라운드 스레드들이 로그 쓰기, 버퍼풀 플러시, 체인지 버퍼 머지, 퍼지(undo 정리)를 해요. 연결이 1000개면 스레드 1000개예요. 그래서 max_connections를 무작정 올리면 OS 챕터에서 본 스레드 과다 문제가 생겨요.

    쿼리 실행 구조

    1. 파서: SQL을 토큰으로 나눠 트리로. 문법 오류 여기서.
    2. 전처리기: 테이블·컬럼 존재 확인, 권한 확인.
    3. 옵티마이저: 실행 계획 수립. (9장)
    4. 실행 엔진: 계획대로 핸들러 호출.
    5. 핸들러(스토리지 엔진): 데이터 읽기/쓰기.

    쿼리 캐시는 사라졌다

    8.0에서 쿼리 캐시가 제거됐어요. 테이블 변경 시 전체 무효화되고 락 경합이 심해서 득보다 실이 컸어요. 캐시는 애플리케이션(Redis)에서 하세요.

    스레드풀, 메모리

    엔터프라이즈판/Percona는 스레드풀로 커넥션 스레드 수를 제한해요. 메모리는 글로벌(버퍼풀, 리두 로그 버퍼 — 하나)과 세션(정렬 버퍼, 조인 버퍼 — 커넥션마다) 영역이 있어요. 세션 메모리는 커넥션 수만큼 곱해지니 sort_buffer_size를 크게 잡으면 OOM이에요.

    백엔드에서는 애플리케이션 서버 N대 × 커넥션 풀 M개 = DB 스레드 N×M. 서버를 늘릴 때 DB 커넥션 수도 같이 늘어난다는 걸 잊으면 Too many connections예요. 서버가 늘어날수록 풀 크기를 줄이거나 ProxySQL 같은 중간 풀을 둬요.
    시니어 심화 커넥션 수와 실행 중인 쿼리 수는 다른 지표예요. Threads_connected는 연결 수, Threads_running은 지금 실제로 일하는 스레드 수예요. 장애 때 봐야 하는 것은 후자예요. 동시에 실행 중인 쿼리가 코어 수를 크게 넘으면 경합 때문에 전체 처리량이 오히려 떨어져요. max_connections를 올리는 것은 이 문제를 키울 뿐이에요.
    • 재연결 폭주: DB가 재시작하거나 장애 조치가 끝난 직후, 모든 애플리케이션이 동시에 풀을 다시 채우려 들어요. 연결 수립(인증, TLS)은 비싸서 이것만으로 DB가 다시 넘어질 수 있어요. 풀 초기화에 지터를 두고 최소 유휴 연결 수를 과하게 잡지 마세요.
    • 풀의 최대 연결 수명은 서버의 wait_timeout보다 짧아야 해요. 반대면 서버가 먼저 끊은 연결을 앱이 꺼내 쓰다가 에러가 나요.
    • 커넥션을 다중화하는 프록시는 세션 상태(세션 변수, 임시 테이블, 네임드 락)를 쓰는 연결을 공유하지 못하고 고정해 버려요. 이런 기능을 많이 쓰면 프록시의 효과가 사라져요.
    핵심 정리
    • MySQL 엔진(파서·옵티마이저) + 스토리지 엔진(InnoDB)
    • 커넥션 = 스레드, 세션 메모리는 커넥션 수만큼
    • 파서 → 전처리 → 옵티마이저 → 실행 → 핸들러

    4.2 InnoDB 스토리지 엔진 아키텍처

    버퍼풀, 리두·언두 로그, MVCC — InnoDB가 빠르고 안전한 이유

    클러스터링 인덱스

    InnoDB 테이블은 PK 순서로 물리적으로 정렬 저장돼요. PK 조회는 가장 빠르고, 세컨더리 인덱스는 PK 값을 들고 있어요(8장에서 자세히). PK가 없으면 유니크 인덱스, 그것도 없으면 숨은 6바이트 row id를 써요. PK를 꼭 두세요.

    버퍼풀

    디스크의 데이터·인덱스 페이지(16KB)를 메모리에 캐시하는 공간이에요. InnoDB 성능의 핵심. innodb_buffer_pool_size는 전용 서버에서 물리 메모리의 50~80%.

    • LRU 리스트: OS의 페이지 교체와 같은 문제. 풀스캔이 캐시를 쓸어버리는 걸 막으려고 new/old 두 영역(midpoint insertion)으로 나눠요. 새 페이지는 old에 들어가고, 일정 시간 안에 다시 접근되면 new로 올라가요.
    • 플러시 리스트: 변경된(dirty) 페이지 목록. 백그라운드가 주기적으로 디스크에 써요(체크포인트).
    • 더블 라이트 버퍼: 16KB 페이지를 쓰다 중간에 죽으면 반만 쓰인 페이지(torn page)가 돼요. 먼저 별도 영역에 순차로 쓰고 실제 위치에 써서, 복구 시 온전한 복사본을 써요.

    리두 로그 (WAL)

    OS 챕터 42장 저널링 그대로예요. 변경은 버퍼풀에서 하고, "무엇을 바꿨는지"를 리두 로그에 순차로 먼저 써요. 커밋 = 리두 로그 디스크 기록. 데이터 페이지는 나중에 체크포인트 때 써요. 크래시 후 복구는 리두 로그를 재실행(redo).

    innodb_flush_log_at_trx_commit: 1 = 커밋마다 fsync(안전, ACID의 D), 2 = 커밋마다 OS 버퍼에 쓰고 1초마다 fsync(MySQL 크래시엔 안전, OS 크래시엔 1초 유실), 0 = 1초마다(가장 빠름, 1초 유실). 리두 로그 파일이 작으면 체크포인트가 잦아 성능이 떨어져요.

    언두 로그

    변경 전 값을 저장해요. 두 가지 용도: (1) 롤백, (2) MVCC(다른 트랜잭션이 옛 버전을 읽을 때). 오래 열린 트랜잭션이 있으면 그 시점 이후의 언두를 지울 수 없어서(퍼지 불가) 언두 공간이 커지고 느려져요. 트랜잭션은 짧게.

    MVCC

    행을 UPDATE하면 버퍼풀의 행은 새 값, 언두 로그에는 옛 값이 남아요. 다른 트랜잭션이 그 행을 읽으면 자기 격리 수준과 시작 시점에 따라 버퍼풀 값 또는 언두의 옛 값을 봐요. 그래서 읽기는 쓰기를 기다리지 않고, 쓰기도 읽기를 기다리지 않아요. 잠금 없는 일관된 읽기(consistent non-locking read). 5장에서 격리 수준과 연결돼요.

    그 외

    • 체인지 버퍼: 세컨더리 인덱스 페이지가 버퍼풀에 없을 때 변경을 임시 저장했다가 나중에 페이지가 읽힐 때 머지. 랜덤 I/O를 줄여요. 유니크 인덱스엔 못 써요(중복 확인 필요).
    • 어댑티브 해시 인덱스: 자주 접근하는 B-Tree 페이지를 해시로 바로 가게. 자동.
    • 자동 데드락 감지: 대기 그래프 사이클을 찾아 언두 양이 적은 쪽을 롤백. (5장)
    백엔드에서는 버퍼풀 히트율(SHOW ENGINE INNODB STATUS의 Buffer pool hit rate)이 99% 아래면 메모리 부족이에요. "DB가 느려졌다"의 첫 확인 항목. 장시간 트랜잭션(배치 작업에서 수십만 건을 한 트랜잭션으로)은 언두를 폭증시키고 다른 쿼리까지 느리게 해요. 배치는 1000건씩 끊어서 커밋하세요. 그리고 innodb_flush_log_at_trx_commit=1 + 느린 디스크 = 커밋마다 fsync 대기 = 쓰기 처리량 한계. 클라우드에서는 디스크 IOPS 티어가 곧 TPS 상한이에요.
    시니어 심화 언두가 쌓이는지는 숫자로 볼 수 있어요. SHOW ENGINE INNODB STATUS의 History list length가 계속 늘면 퍼지가 밀리고 있는 거예요. 원인 트랜잭션은 information_schema.INNODB_TRX에서 trx_started가 오래된 것을 찾으면 돼요. 쓰기를 하지 않는 트랜잭션도 원인이 돼요. 자동 커밋을 끈 세션이 SELECT 한 번 하고 방치되면 그 시점의 스냅샷을 위해 언두가 계속 보존돼요.
    • 콜드 스타트: 재시작 직후에는 버퍼풀이 비어 있어 모든 읽기가 디스크로 가요. 종료 시 버퍼풀 목록을 저장하고 시작 시 다시 읽어 들이는 설정(innodb_buffer_pool_dump_at_shutdown, innodb_buffer_pool_load_at_startup)이 켜져 있는지 확인하고, 장애 조치 대상 서버도 미리 데워 둬요.
    • 플러시가 밀리면 멈춰요. 더티 페이지를 내려쓰는 속도가 변경 속도를 못 따라가면 리두 로그 공간이 바닥나고 쓰기가 일시 정지돼요. innodb_io_capacity가 실제 디스크 성능에 비해 너무 낮게 잡혀 있지 않은지 확인하세요.
    핵심 정리
    • 버퍼풀 = 페이지 캐시(LRU old/new), 히트율이 성능
    • 리두 로그 = WAL, 커밋 = 로그 fsync. 언두 로그 = 롤백 + MVCC
    • MVCC = 읽기와 쓰기가 서로 안 막음, 긴 트랜잭션은 언두 폭증
    셀프 체크
    1. 커밋했는데 데이터 파일에는 아직 안 써졌어요. 지금 서버가 죽으면 데이터는 안전한가요?
    2. 풀스캔 한 번이 버퍼풀을 망치지 않는 이유는?
    답 보기

    1. innodb_flush_log_at_trx_commit=1이면 안전해요. 커밋 시 리두 로그가 fsync됐고, 재시작 시 리두 로그를 재실행해 데이터 페이지를 복원해요. 데이터 파일은 체크포인트 때 써지면 돼요.

    2. LRU를 old/new로 나누고 새로 읽힌 페이지는 old 영역에 넣어요. 풀스캔으로 한 번만 읽힌 페이지는 old에서 밀려나고, 자주 쓰는 new 영역의 페이지는 살아남아요.

    1권 5장 트랜잭션과 잠금

    5.1 트랜잭션

    ACID와 "트랜잭션을 짧게"의 진짜 의미

    ACID

    • Atomicity: 전부 반영 또는 전부 취소. 언두 로그로 롤백.
    • Consistency: 제약 조건(PK, FK, UNIQUE, CHECK)이 트랜잭션 전후로 유지. 애플리케이션 불변식은 애플리케이션 책임.
    • Isolation: 동시 트랜잭션이 서로 안 보이게. 격리 수준으로 정도 조절(5.4).
    • Durability: 커밋되면 영구. 리두 로그 fsync.

    트랜잭션이 없으면

    MyISAM에서 3건 INSERT 중 2번째가 실패하면 1건은 남아요. InnoDB는 전부 롤백돼요. 이게 "부분 실패를 신경 쓰지 않아도 된다"는 거예요.

    트랜잭션 범위 최소화

    책의 핵심 메시지. 다음을 트랜잭션 밖으로 빼세요.

    • 입력 검증, 외부 API 호출(메일, 결제 PG, 파일 업로드), 메시지 발행
    • 트랜잭션과 무관한 조회

    이유: 트랜잭션이 열려 있는 동안 (1) 잡은 락이 유지되고, (2) 언두가 쌓이고, (3) 커넥션을 점유해요. 외부 API가 3초 걸리면 그동안 락과 커넥션이 묶여요. 외부 API가 타임아웃되면 DB 커넥션 풀이 고갈돼요.

    백엔드에서는 @Transactional 메서드 안에서 외부 HTTP 호출을 하는 게 가장 흔한 실수예요. 서비스 메서드 전체에 붙이지 말고 DB 작업만 묶은 작은 메서드에 붙이거나, TransactionTemplate으로 범위를 명시하세요. 또 @Transactional(readOnly = true)는 InnoDB에 읽기 전용임을 알려 일부 최적화(트랜잭션 ID 미할당)가 되고, 복제 환경에서 replica로 라우팅하는 기준이 돼요.
    시니어 심화 스프링에서 트랜잭션은 곧 커넥션 점유예요.
    • 트랜잭션이 시작되면 커넥션을 풀에서 가져와 끝날 때까지 쥐고 있어요. 트랜잭션 안의 느린 작업은 락만 길게 잡는 것이 아니라 풀도 고갈시켜요.
    • spring.jpa.open-in-view가 켜져 있으면(기본값) 영속성 컨텍스트가 응답을 다 쓸 때까지 살아 있고, 그동안 커넥션도 반납되지 않을 수 있어요. API 서버에서는 끄고 필요한 데이터를 서비스 계층에서 다 읽어 두세요.
    • 기본 롤백 규칙은 런타임 예외에만 적용돼요. 체크 예외를 던지면 커밋돼요. 의도와 다르면 rollbackFor를 명시해요.
    • 이벤트 발행, 캐시 삭제, 알림 같은 부수 효과는 커밋 후에 실행해야 해요. 커밋 전에 내보내면 받는 쪽이 아직 보이지 않는 데이터를 조회하거나, 롤백된 변경을 알리게 돼요.
    핵심 정리
    • A = 언두, D = 리두, I = 격리 수준, C = 제약 조건
    • 트랜잭션 안에는 DB 작업만. 외부 호출·검증은 밖으로
    셀프 체크
    1. 주문 생성 → 결제 PG 호출 → 주문 상태 갱신을 한 트랜잭션에 넣으면 생기는 문제 세 가지는?
    답 보기

    (1) PG 호출 동안(수 초) 주문 행 락과 DB 커넥션 점유 → 풀 고갈. (2) PG 성공 후 상태 갱신이 실패해 롤백되면 결제는 됐는데 주문이 없음(외부 부수효과는 롤백 안 됨). (3) PG 타임아웃 시 결제됐는지 알 수 없는데 트랜잭션은 롤백 → 불일치. 해결: 주문 생성 커밋 → PG 호출 → 별도 트랜잭션으로 상태 갱신, 실패 시 보상/재조회.

    5.2 MySQL 엔진의 잠금

    스토리지 엔진 위에서 걸리는 락들 — 글로벌, 테이블, 네임드, 메타데이터

    글로벌 락

    FLUSH TABLES WITH READ LOCK. 서버 전체를 읽기 전용으로. 백업용이지만 모든 쓰기가 멈춰요. 8.0은 백업 락(LOCK INSTANCE FOR BACKUP)으로 DDL만 막고 DML은 허용해요.

    테이블 락

    LOCK TABLES로 명시적으로, 또는 MyISAM은 DML마다 암묵적으로. InnoDB는 행 락이 있어 DML에선 안 걸리고 DDL에서만 걸려요.

    네임드 락

    GET_LOCK('name', timeout) / RELEASE_LOCK('name'). 테이블이나 행이 아니라 임의의 문자열에 락을 걸어요. 여러 서버에서 같은 배치가 동시에 돌지 않게 하는 분산 락으로 써요. 세션이 끊기면 자동 해제돼요.

    메타데이터 락 (MDL)

    테이블 구조를 바꾸는 동안(ALTER, RENAME) 걸리는 락이에요. 그런데 DML도 실행 중엔 MDL(shared)을 잡아요. 트랜잭션이 열려 있으면 끝날 때까지 유지돼요. 그래서 긴 트랜잭션이 하나 있으면 ALTER가 그걸 기다리고, ALTER 뒤에 온 모든 쿼리가 ALTER를 기다려 전체가 멈춰요. 운영 중 DDL의 가장 큰 위험이에요.

    백엔드에서는 운영 중 ALTER TABLE 전에 SHOW PROCESSLIST로 긴 트랜잭션이 없는지 확인하고, lock_wait_timeout을 짧게 설정해서 MDL을 못 잡으면 빨리 실패하게 하세요. pt-online-schema-change, gh-ost는 새 테이블을 만들어 복사하고 마지막에 rename해서 MDL 점유 시간을 최소화해요. 네임드 락은 스프링 배치 중복 실행 방지, 쿠폰 발급 같은 임계 구역에 간단히 쓸 수 있어요. 단 세션 단위라 커넥션 풀에서 같은 커넥션으로 락/해제를 해야 해요.
    핵심 정리
    • InnoDB DML은 행 락, DDL은 테이블·메타데이터 락
    • MDL: 긴 트랜잭션 + ALTER = 전체 멈춤
    • 네임드 락 = 문자열 기반 분산 락
    셀프 체크
    1. 작은 테이블에 컬럼 하나 추가하는 ALTER가 전체 서비스를 멈추게 한 시나리오를 설명하세요.
    답 보기

    어떤 세션이 그 테이블을 SELECT한 트랜잭션을 커밋하지 않고 열어둠(MDL shared 유지) → ALTER가 MDL exclusive를 기다림 → ALTER 뒤에 들어온 모든 SELECT/DML이 MDL 큐에서 ALTER 뒤로 줄 섬 → 테이블 접근이 전부 멈춤. 해결: 긴 트랜잭션 kill, 또는 ALTER를 kill.

    5.3 InnoDB 스토리지 엔진 잠금

    레코드 락, 갭 락, 넥스트 키 락 — 그리고 "인덱스와 잠금"

    InnoDB는 인덱스 레코드를 잠근다

    가장 중요한 문장이에요. InnoDB의 락은 행이 아니라 인덱스의 레코드에 걸려요. 그래서 어떤 인덱스로 찾았느냐가 잠기는 범위를 결정해요.

    락의 종류

    • 레코드 락: 인덱스 레코드 하나. WHERE id = 5 FOR UPDATE(id가 PK/유니크).
    • 갭 락: 레코드 사이의 간격. 그 범위에 새 레코드가 INSERT되는 걸 막아요. 레코드 자체는 안 잠가요.
    • 넥스트 키 락: 레코드 락 + 그 앞 갭 락. REPEATABLE READ에서 범위 검색 시 기본. phantom read 방지가 목적.
    • 자동 증가 락: AUTO_INCREMENT 값을 뽑을 때 아주 짧게. innodb_autoinc_lock_mode=2(8.0 기본)면 거의 경합 없음.
    • 삽입 의도 락: INSERT 전에 갭에 거는 특수 락. 같은 갭에 다른 위치로 INSERT하는 건 서로 안 막아요.

    인덱스와 잠금 — 핵심 예제

    -- employees 테이블: first_name에만 인덱스, last_name엔 없음
-- first_name='Georgi'인 행 253건, 그중 last_name='Klassen'은 1건

UPDATE employees SET hire_date = NOW()
WHERE first_name = 'Georgi' AND last_name = 'Klassen';

    결과: 253건 전부 잠겨요. InnoDB는 first_name 인덱스로 253건을 읽으면서 전부 잠그고, 그중 last_name 조건으로 1건만 갱신해요. 인덱스가 아예 없으면 테이블 전체를 잠가요. 그래서 UPDATE/DELETE의 WHERE 조건에는 반드시 적절한 인덱스가 필요해요. 이게 "UPDATE 하나가 서비스 전체를 멈추는" 원리예요.

    잠금 확인

    SHOW PROCESSLIST;                                   -- 어떤 쿼리가 대기 중인지
SELECT * FROM performance_schema.data_locks;        -- 어떤 락을 잡고 있는지
SELECT * FROM performance_schema.data_lock_waits;   -- 누가 누구를 기다리는지
KILL <id>;                                          -- 문제 세션 종료

    데드락

    InnoDB는 대기 그래프를 보고 자동 감지해 언두 레코드가 적은 트랜잭션을 롤백해요(ER_LOCK_DEADLOCK). 애플리케이션은 이 에러를 재시도해야 해요. SHOW ENGINE INNODB STATUS의 LATEST DETECTED DEADLOCK에서 원인 쿼리를 볼 수 있어요. 예방은 OS 챕터 32장: 접근 순서 고정.

    백엔드에서는 SELECT ... FOR UPDATE를 범위 조건으로 쓰면 넥스트 키 락이 걸려 그 범위 INSERT가 전부 막혀요. 가능하면 PK로 특정 행만. 그리고 innodb_lock_wait_timeout(기본 50초!)을 애플리케이션 타임아웃에 맞게 줄이세요. 안 그러면 락 대기 중인 스레드가 50초씩 묶여요. JPA의 @Lock(PESSIMISTIC_WRITE)이 FOR UPDATE, @Version이 낙관적 락이에요. 충돌이 드물면 낙관적 락 + 재시도가 처리량이 높고, 잦으면 비관적 락이 재시도 폭풍을 막아요.
    시니어 심화 잠금을 피하거나 줄이는 실전 기법이에요.
    • 작업 큐에는 SKIP LOCKED: SELECT ... FOR UPDATE SKIP LOCKED는 다른 워커가 잠근 행을 건너뛰어요. 여러 워커가 같은 테이블에서 작업을 가져갈 때 서로 막지 않아요. NOWAIT는 기다리지 않고 즉시 실패해요.
    • 락 대기 타임아웃은 문장만 되돌려요. 기본 설정에서는 타임아웃이 난 그 문장만 롤백되고 트랜잭션은 열린 채로 남아요. 애플리케이션이 명시적으로 롤백하지 않으면 앞서 잡은 락을 그대로 쥐고 있어요.
    • 갭 락을 줄이려면 READ COMMITTED: 격리 수준을 낮추면 일반 조회·갱신의 갭 락이 대부분 사라져 데드락과 INSERT 대기가 줄어요(외래키·유니크 검사는 예외). 쓰기 경합이 심한 서비스가 RC를 고르는 이유예요.
    • 동시 INSERT 데드락: 같은 유니크 키를 세 세션이 동시에 넣다가 먼저 넣은 세션이 롤백하면, 기다리던 두 세션이 중복 검사용 공유 락을 나눠 가진 뒤 서로 배타 락을 요구하며 데드락이 나요. "INSERT만 했는데 데드락"의 정체예요. 재시도로 처리해요.
    핵심 정리
    • 락은 인덱스 레코드에. 인덱스 없는 UPDATE = 테이블 전체 잠금
    • 갭 락·넥스트 키 락이 범위 INSERT를 막음
    • 데드락은 자동 롤백 → 재시도 필수, 순서 고정으로 예방
    셀프 체크
    1. 위 예제에서 253건이 아니라 1건만 잠그게 하려면?
    2. 재고 차감의 세 가지 동시성 제어 방법과 선택 기준은?
    답 보기

    1. (first_name, last_name) 복합 인덱스를 만들면 인덱스에서 1건만 찾아 1건만 잠가요.

    2. (a) 원자적 UPDATE(SET qty = qty - 1 WHERE id = ? AND qty >= 1, 영향 행 0이면 실패): 가장 단순·빠름, 복잡한 검증 불가. (b) 비관적 락(FOR UPDATE 후 검증·갱신): 확실, 대기 발생, 충돌 잦을 때. (c) 낙관적 락(version 비교): 락 없음, 충돌 시 재시도, 충돌 드물 때. 핫 상품은 (a) 또는 Redis 원자 연산.

    5.4 트랜잭션 격리 수준

    READ UNCOMMITTED부터 SERIALIZABLE까지, 그리고 InnoDB의 REPEATABLE READ

    이상 현상

    • Dirty read: 커밋 안 된 변경을 읽음. 롤백되면 없는 값을 본 것.
    • Non-repeatable read: 같은 행을 두 번 읽었는데 사이에 다른 트랜잭션이 커밋해 값이 다름.
    • Phantom read: 같은 조건을 두 번 읽었는데 사이에 INSERT되어 행이 늘어남.

    격리 수준

    수준DirtyNon-repeatablePhantom동작
    READ UNCOMMITTEDOOO버퍼풀 값을 그냥 읽음. 쓰지 마세요.
    READ COMMITTED-OO쿼리마다 새 스냅샷. 커밋된 최신을 봄. Oracle, PostgreSQL 기본.
    REPEATABLE READ--InnoDB는 거의 -트랜잭션 첫 읽기 시점 스냅샷 유지. InnoDB 기본.
    SERIALIZABLE---읽기에도 공유 락. 동시성 최저.

    InnoDB REPEATABLE READ의 동작

    트랜잭션은 번호를 받아요. 일반 SELECT는 자기 번호보다 작은(먼저 시작해 커밋된) 트랜잭션의 변경만 봐요. 더 큰 번호가 바꾼 행은 언두 로그에서 옛 버전을 찾아 읽어요. 그래서 트랜잭션 안에서 같은 SELECT는 항상 같은 결과예요.

    Phantom: 일반 SELECT는 스냅샷이라 새 행이 안 보여요. SELECT ... FOR UPDATE는 스냅샷이 아니라 현재 데이터를 잠금 읽기하는데, 넥스트 키 락으로 범위에 INSERT를 막아 phantom을 방지해요. 단, 일반 SELECT와 잠금 읽기를 섞으면 결과가 달라 보일 수 있어요.

    READ COMMITTED를 쓰는 경우

    갭 락이 거의 안 걸려 INSERT 경합이 적고, 긴 트랜잭션의 언두 부담도 적어요. 대신 같은 트랜잭션 안에서 값이 바뀔 수 있어요. PostgreSQL 사용자는 이게 기본이라 익숙해요. MySQL에서 바꾸려면 바이너리 로그 포맷이 ROW여야 해요(16장).

    백엔드에서는 "재고 확인 후 차감"에서 SELECT로 10개 확인 → UPDATE 하는 사이 다른 트랜잭션이 차감하면? REPEATABLE READ라도 SELECT는 스냅샷일 뿐 락이 아니라서 막지 못해요. 확인-갱신은 FOR UPDATE로 잠금 읽기하거나 원자적 UPDATE로 해야 해요. 격리 수준은 "읽기의 일관성"이지 "쓰기 경쟁 방지"가 아니에요. 그리고 JPA 영속성 컨텍스트(1차 캐시)는 DB 격리 수준과 별개로 같은 엔티티를 반복 읽기처럼 보이게 해요. 둘을 혼동하지 마세요.
    시니어 심화 REPEATABLE READ에서 헷갈리는 동작 두 가지예요.
    • 스냅샷은 BEGIN이 아니라 첫 읽기에서 만들어져요. 트랜잭션을 열어 두고 한참 뒤에 첫 SELECT를 하면 그 시점의 데이터를 봐요. 시작 시점으로 고정하려면 START TRANSACTION WITH CONSISTENT SNAPSHOT을 써요.
    • 읽기와 쓰기가 보는 세계가 달라요. 일반 SELECT는 스냅샷을 보지만 UPDATE, DELETE, 잠금 읽기는 최신 커밋 데이터를 대상으로 해요. 그래서 SELECT에는 안 보이던 행이 UPDATE에는 걸리고, 그 뒤로는 내가 고친 행이라 SELECT에도 보여요. 같은 트랜잭션 안에서 결과 건수가 달라지는 이유예요.
    긴 읽기 전용 작업(리포트, 내보내기)을 RR로 오래 열어 두면 언두가 계속 쌓여요. 이런 작업은 세션 단위로 격리 수준을 낮추거나 복제본에서 돌려요.
    핵심 정리
    • RC = 쿼리마다 스냅샷, RR = 트랜잭션당 스냅샷(InnoDB 기본)
    • 스냅샷 읽기는 락이 아님. 확인-갱신은 FOR UPDATE나 원자적 UPDATE
    • InnoDB RR은 넥스트 키 락으로 phantom 대부분 방지
    셀프 체크
    1. REPEATABLE READ에서 두 세션이 같은 행을 UPDATE하면 두 번째는 무엇을 기준으로 갱신하나요?
    답 보기

    UPDATE는 스냅샷이 아니라 현재 커밋된 최신 값을 잠금 읽기해서 갱신해요. 첫 세션이 커밋할 때까지 기다렸다가 그 결과 위에 갱신해요. 그래서 SET qty = qty - 1은 안전하고, SELECT로 읽은 값을 애플리케이션에서 계산해 SET qty = 9로 쓰면 lost update가 나요.

    1권 8장 인덱스

    8.1~8.2 디스크 읽기 방식과 인덱스란

    랜덤 I/O vs 순차 I/O, 그리고 인덱스가 빠른 이유와 느린 이유

    랜덤 I/O와 순차 I/O

    OS 챕터 37장. 디스크 I/O 비용은 횟수가 결정해요. 3개 페이지를 순차로 읽으면 1번 I/O, 흩어져 있으면 3번. SSD도 랜덤이 느려요. 쿼리 튜닝 = 랜덤 I/O 횟수 줄이기.

    인덱스란

    책의 색인. 컬럼 값과 그 값을 가진 행의 위치(InnoDB는 PK)를 정렬해서 따로 저장한 것. 정렬돼 있으니 찾기는 빠르고(이진 탐색 가능), INSERT/UPDATE/DELETE마다 정렬을 유지해야 하니 쓰기는 느려져요. 인덱스는 "읽기 속도를 위해 쓰기 속도를 희생하는 것"이에요.

    인덱스 종류

    • B-Tree: 범위, 정렬, 접두사 모두 가능. 기본.
    • Hash: 등호 비교만, 매우 빠름. InnoDB는 어댑티브 해시만(메모리 엔진에서 명시 가능).
    • 전문 검색(Fulltext), 공간(R-Tree), 함수 기반, 멀티 밸류(JSON 배열): 8.5

    유니크 인덱스는 중복 확인 때문에 쓰기 시 체인지 버퍼를 못 써요. 그래도 유일성이 필요하면 꼭 두세요. 애플리케이션 검사는 경쟁 조건에 뚫려요.

    백엔드에서는 "인덱스를 많이 걸수록 좋다"는 착각이 가장 흔해요. 인덱스 5개면 INSERT마다 B-Tree 5개 + 클러스터링 인덱스를 갱신해요. 쓰기 위주 테이블(로그, 이벤트)은 인덱스를 최소로. 그리고 인덱스마다 버퍼풀 공간을 차지하니, 안 쓰는 인덱스는 메모리 낭비예요. sys.schema_unused_indexes로 찾아 지우세요.
    시니어 심화 인덱스는 추가보다 삭제와 변경이 조심스러워요.
    • 지우기 전에 숨겨 보세요. 8.0의 invisible index는 인덱스를 유지하되 옵티마이저만 못 보게 해요. 숨긴 뒤 문제가 없으면 지우고, 느려지면 즉시 되돌려요. 큰 인덱스를 지웠다가 다시 만드는 데 걸리는 시간을 피할 수 있어요.
    • 복제본에서도 같은 시간이 걸려요. 원본에서 온라인으로 끝난 인덱스 생성이 복제본에서는 그 시간만큼 복제 지연으로 나타날 수 있어요. 복제본 읽기에 의존하는 서비스라면 작업 시간대를 골라야 해요.
    • 유니크 인덱스는 쓰기가 더 비싸요. 일반 세컨더리 인덱스의 변경은 모아 뒀다가 나중에 반영할 수 있지만, 유니크 인덱스는 중복 확인을 위해 매번 해당 페이지를 읽어야 해요.
    • 선택도가 낮은 컬럼(상태, 성별)의 인덱스는 보통 쓸모없지만, 값이 한쪽으로 쏠려 있을 때는 달라요. "미처리 1%"만 찾는 쿼리에는 효과가 커요.
    핵심 정리
    • I/O 비용 = 횟수, 튜닝 = 랜덤 I/O 줄이기
    • 인덱스 = 정렬된 복사본. 읽기 빠름, 쓰기 느림, 메모리 차지
    셀프 체크
    1. 인덱스를 추가하면 느려지는 작업과 그 이유는?
    답 보기

    INSERT, DELETE, 그리고 인덱스 컬럼을 바꾸는 UPDATE. 각 인덱스 B-Tree에서 정렬 위치를 찾아 삽입/삭제해야 하고, 페이지가 꽉 차면 분할도 일어나요. 또 버퍼풀 메모리를 나눠 써서 데이터 페이지 히트율이 떨어질 수 있어요.

    8.3 B-Tree 인덱스

    구조, 키 추가·삭제·검색, 그리고 인덱스를 못 쓰는 조건들

    구조

    InnoDB는 B+Tree. 키는 리프에만 있고, 브랜치는 길잡이예요. 페이지(16KB)마다 키가 수백 개 들어가서 수천만 건도 높이 3~4예요. 리프가 연결돼 있어 범위 검색은 첫 위치만 찾고 옆으로 읽어요(순차 I/O).

    세컨더리 인덱스의 리프에는 PK 값이 있어요. 그래서 세컨더리 인덱스로 찾은 뒤 나머지 컬럼이 필요하면 PK로 클러스터링 인덱스를 다시 찾아요. 이게 비용이에요(8.8 클러스터링 인덱스, 10장 Using index).

    키 추가·삭제·변경

    • 추가: 위치 찾아 삽입. 페이지가 꽉 차면 분할(비용 큼). 세컨더리 인덱스는 체인지 버퍼로 지연 가능.
    • 삭제: 삭제 마크만. 공간은 나중에 재활용.
    • 변경: 삭제 + 추가.

    테이블의 인덱스가 3개면 INSERT 비용은 대략 1(데이터) + 1.5 × 3(인덱스)로 책은 설명해요.

    검색: 인덱스를 쓸 수 있는 조건

    B-Tree는 왼쪽 값(접두사)부터 찾아요. 전화번호부에서 "성"을 모르면 "이름"으로 못 찾는 것과 같아요.

    조건인덱스 사용
    col = ?, col IN (...), col BETWEEN, col > ?O
    col LIKE 'abc%'O (접두사)
    col LIKE '%abc'X (왼쪽이 불확정)
    col <> ?, col NOT IN거의 X (대부분 행이 해당)
    WHERE DATE(created_at) = ?, WHERE col + 1 = ?X (컬럼을 변형하면 못 씀)
    WHERE varchar_col = 123X (타입 불일치 → 컬럼이 변환됨)
    WHERE col IS NULLO (InnoDB는 NULL도 인덱싱)

    인덱스 스캔 방식

    • 레인지 스캔: 시작점 찾고 필요한 만큼 순서대로. 가장 좋음. type: range, ref, const
    • 풀 스캔: 인덱스 전체를 처음부터 끝까지. 조건 컬럼이 인덱스에 있지만 접두사가 아닐 때. 테이블보다는 작아서 풀 테이블 스캔보다 나음. type: index
    • 루스 스캔: 중간중간 건너뛰며. GROUP BY, MIN/MAX 최적화.
    • 스킵 스캔(8.0): 선행 컬럼 조건 없이 후행 컬럼으로. 선행 컬럼의 유니크 값이 적을 때만.

    다중 컬럼 인덱스와 컬럼 순서

    INDEX (a, b, c)는 a로 정렬, a 같으면 b, b 같으면 c. 쓸 수 있는 조건: a / a,b / a,b,c. b만, c만, b,c는 접두사가 아니라 못 써요(스킵 스캔 제외). 범위 조건 뒤의 컬럼은 범위를 좁히지 못해요. WHERE a = 1 AND b > 10 AND c = 5는 (a, b)까지만 탐색 범위, c는 읽으면서 필터. 그래서 등호 컬럼을 앞에, 범위 컬럼을 뒤에.

    정렬 방향

    8.0부터 INDEX (a ASC, b DESC)처럼 컬럼별 방향 지정 가능. ORDER BY a, b DESC를 인덱스만으로 처리하려면 필요해요. 역순 스캔은 정순보다 약간 느려요(페이지 잠금 방향 때문).

    백엔드에서는 가장 흔한 "인덱스 있는데 안 탐" 원인: (1) LIKE '%검색어%' → 전문 검색이나 검색 엔진으로, (2) DATE(created_at) = '2024-01-01' → created_at >= '2024-01-01' AND created_at < '2024-01-02'로, (3) 문자열 컬럼에 숫자 비교 → 타입 맞추기, (4) 복합 인덱스 순서가 쿼리 패턴과 안 맞음 → 등호 컬럼 먼저. JPA에서는 생성되는 SQL을 로그로 보고 EXPLAIN하세요. 보이지 않는 SQL이 느린 SQL이에요.
    시니어 심화 인덱스가 있어도 옵티마이저가 고르지 않거나 어느 날 다른 것을 고를 수 있어요.
    • 계획 뒤집힘: 실행 계획은 통계에 의존하고 통계는 표본 추정이에요. 데이터 분포가 변하거나 통계가 다시 계산되면 배포 없이도 계획이 바뀌어 갑자기 느려져요. 핵심 쿼리는 실행 계획을 주기적으로 확인하고, 급할 때는 ANALYZE TABLE이나 인덱스 힌트로 고정해요.
    • 등호 → 정렬 → 범위: 복합 인덱스에 정렬 컬럼이 낄 때는 등호 컬럼 다음에 정렬 컬럼, 마지막에 범위 컬럼을 두면 정렬 작업 없이 인덱스 순서대로 읽을 수 있어요. 범위를 앞에 두면 정렬이 따로 필요해져요.
    • 긴 문자열의 접두사 인덱스(col(20))는 크기를 줄여 주지만 커버링과 정렬에는 쓸 수 없어요.
    • 함수 기반 인덱스(8.0)로 표현식 결과에 인덱스를 걸 수 있어요. 컬럼을 변형하는 조건을 쿼리에서 고칠 수 없을 때의 대안이에요.
    핵심 정리
    • B+Tree: 리프에 키+PK, 리프 연결, 높이 3~4
    • 왼쪽 접두사 규칙. 컬럼 변형·타입 불일치·%abc는 못 씀
    • 복합 인덱스: 등호 먼저, 범위 뒤. 범위 뒤 컬럼은 필터만
    셀프 체크
    1. INDEX (status, created_at)에서 WHERE status IN ('A','B') AND created_at > ?와 WHERE created_at > ? AND status = 'A'는 각각 인덱스를 어떻게 쓰나요?
    2. 왜 WHERE phone = 01012345678(숫자)은 varchar 컬럼 인덱스를 못 쓰나요?
    답 보기

    1. 둘 다 같은 인덱스를 써요. WHERE 절 순서는 무관하고 옵티마이저가 인덱스 순서대로 재배치해요. status가 등호(IN은 등호 여러 개)라 (status, created_at) 둘 다 탐색 범위에 쓰여요. 만약 인덱스가 (created_at, status)였다면 created_at 범위 뒤의 status는 필터로만 쓰여 효율이 떨어져요.

    2. MySQL은 문자열과 숫자 비교 시 문자열을 숫자로 변환해요. 컬럼 쪽이 변환되니 인덱스의 정렬 순서를 쓸 수 없어 풀스캔. '01012345678'로 문자열 리터럴을 써야 해요.

    8.8 클러스터링 인덱스

    InnoDB 테이블은 PK 순서로 저장된다 — 이것이 모든 것을 바꾼다

    클러스터링이란

    InnoDB에서 테이블 = PK B+Tree예요. 리프 페이지에 행 데이터 전체가 PK 순으로 정렬돼 있어요. 그래서 "클러스터링 인덱스 = 테이블"이고, PK 조회는 인덱스를 찾으면 바로 데이터예요.

    세컨더리 인덱스는 PK를 들고 있다

    세컨더리 인덱스 리프에는 (인덱스 컬럼 값, PK 값)이 있어요. 행의 물리 위치가 아니에요. 이유: 페이지 분할로 행이 이동해도 세컨더리 인덱스를 안 고쳐도 되니까. 대가: 세컨더리 인덱스로 조회 → PK 얻음 → 클러스터링 인덱스 다시 탐색(2번 탐색). 그리고 PK가 크면 모든 세컨더리 인덱스가 커져요.

    PK 선택이 중요한 이유

    • 순차 PK(AUTO_INCREMENT): 새 행은 항상 마지막 페이지에 → 페이지 분할 적고, 최근 페이지만 버퍼풀에 있으면 됨.
    • 랜덤 PK(UUID v4): 새 행이 B-Tree 아무 곳에 → 페이지 분할 잦음, 모든 페이지가 쓰기 대상이라 버퍼풀 효율 저하, 단편화. 또 36바이트 문자열이면 세컨더리 인덱스마다 36바이트 추가.
    • PK 변경: 행이 물리적으로 이동(삭제 + 삽입). 세컨더리 인덱스도 전부 갱신. PK는 바뀌지 않는 값으로.

    클러스터링의 장단점

    장점단점
    PK 조회 매우 빠름세컨더리 인덱스 조회는 2번 탐색
    PK 범위 조회 = 순차 I/OPK가 크면 모든 인덱스가 커짐
    세컨더리 인덱스가 PK를 포함 → 커버링 효과INSERT 성능이 PK 순서에 좌우

    PostgreSQL은 다르게 동작해요. 힙 테이블에 행이 삽입 순으로 쌓이고 모든 인덱스(PK 포함)가 물리 위치(TID)를 가리켜요. 그래서 UUID PK의 삽입 비용 차이가 MySQL보다 작아요. 대신 행이 갱신되면 모든 인덱스를 갱신해야 해요(HOT 최적화 제외).

    백엔드에서는 UUID를 외부 식별자로 쓰고 싶다면 (1) 내부 PK는 BIGINT AUTO_INCREMENT, UUID는 별도 유니크 컬럼으로, 또는 (2) UUID v7/ULID를 BINARY(16)으로 저장(시간순 + 16바이트). JPA의 @GeneratedValue(strategy = UUID)는 v4라 위험해요. 그리고 "자주 같이 읽는 데이터를 PK 순서로 가깝게 두기"가 설계 포인트예요. 사용자의 주문을 자주 조회한다면 주문 PK를 (user_id, order_id) 복합으로 하면 한 사용자의 주문이 물리적으로 붙어 있어요.
    시니어 심화 PK 설계는 나중에 바꾸기가 가장 어려운 결정이에요.
    • 삭제해도 공간은 돌아오지 않아요. 대량 DELETE 뒤에도 테이블 파일 크기는 그대로이고, 빈 공간이 페이지마다 흩어져 남아요. 공간을 되찾으려면 테이블을 다시 만들어야 하는데(ALTER TABLE ... ENGINE=InnoDB), 큰 테이블에서는 I/O 부담과 복제 지연이 커요. 주기적으로 지울 데이터라면 처음부터 파티션으로 설계하는 편이 나아요.
    • AUTO_INCREMENT는 연속이 아니에요. 롤백된 INSERT가 쓴 번호는 돌아오지 않고, 벌크 INSERT에서는 번호가 섞여요. "번호가 비면 안 된다"는 요구(전표 번호 등)를 PK에 얹지 마세요. 별도 채번이 필요해요.
    • 순차 ID를 밖에 노출하면 전체 건수와 증가 속도를 추정할 수 있고, 번호를 하나씩 바꿔 가며 남의 데이터를 조회하는 공격이 쉬워져요. 외부에 내보내는 식별자는 따로 두고 권한 검사는 항상 서버에서 해요.
    핵심 정리
    • InnoDB 테이블 = PK B+Tree, 세컨더리 인덱스 리프 = (키, PK)
    • PK는 작고 순차적이고 불변으로. UUID v4 PK는 분할·단편화·크기 문제
    • PostgreSQL은 힙 + TID라 다름

    답 보기

    클러스터링 인덱스는 PK 순서를 유지하려고 페이지 분할 시 행을 옮겨요. 물리 주소를 저장했다면 행이 옮겨질 때마다 모든 세컨더리 인덱스의 해당 엔트리를 갱신해야 해요. PK를 저장하면 행이 어디로 가든 PK로 다시 찾을 수 있어 세컨더리 인덱스는 그대로예요.

    1권 9장 옵티마이저와 힌트

    9.1~9.2 쿼리 실행 절차와 기본 데이터 처리

    풀 테이블 스캔, ORDER BY(filesort), GROUP BY, DISTINCT, 임시 테이블

    옵티마이저의 일

    같은 결과를 내는 실행 방법은 여러 개예요(어느 인덱스, 어느 테이블부터 조인, 정렬을 인덱스로 할지 따로 할지). 옵티마이저는 통계(테이블 행 수, 인덱스 카디널리티, 페이지 수)로 각 방법의 비용을 추정해 가장 싼 것을 골라요. 통계가 틀리면 계획이 틀려요. ANALYZE TABLE로 갱신하고, 8.0의 히스토그램(ANALYZE TABLE ... UPDATE HISTOGRAM)은 값 분포 편향까지 반영해요.

    풀 테이블 스캔

    옵티마이저가 선택하는 경우: 테이블이 아주 작음(페이지 1개), 조건에 맞는 인덱스 없음, 인덱스로 읽을 행이 전체의 20~25% 이상(인덱스 랜덤 I/O보다 순차 풀스캔이 쌈). InnoDB는 풀스캔 시 리드 어헤드로 페이지를 미리 읽어요.

    ORDER BY — 정렬 처리

    세 가지 방식, 성능 순:

    1. 인덱스 사용: ORDER BY 컬럼이 인덱스 순서와 같으면 읽은 순서가 곧 정렬. 추가 비용 없음. Extra에 아무 표시 없음.
    2. 조인에서 드라이빙 테이블만 정렬: 첫 테이블을 정렬 후 조인. Extra: Using filesort.
    3. 임시 테이블 정렬: 조인 결과를 임시 테이블에 넣고 정렬. Extra: Using temporary; Using filesort. 가장 느림.

    filesort는 "파일 정렬"이 아니라 "인덱스 없이 정렬"이에요. sort_buffer_size 안에서 메모리 정렬, 넘치면 디스크에 쪼개 쓰고 병합(실제 파일). 정렬 대상이 크면 느려요. 정렬 대상 레코드를 줄이려면 WHERE로 먼저 거르고, 컬럼 수도 줄이세요(SELECT *는 정렬 버퍼를 낭비).

    LIMIT과 정렬: ORDER BY x LIMIT 10은 전체를 정렬한 뒤 10개 자르는 게 아니라 우선순위 큐로 상위 10개만 유지해요. 그래도 전체를 읽기는 해요. 인덱스로 정렬하면 10개만 읽고 끝나요.

    GROUP BY

    • 인덱스 사용(타이트 스캔): GROUP BY 컬럼이 인덱스 순이면 읽으면서 그룹핑. 추가 비용 없음.
    • 루스 인덱스 스캔: 인덱스의 유니크 값마다 건너뛰며. Extra: Using index for group-by.
    • 임시 테이블: 인덱스 못 쓰면. Extra: Using temporary. 8.0부터 GROUP BY가 암묵적 정렬을 안 해요(정렬 필요하면 ORDER BY 명시).

    DISTINCT

    SELECT DISTINCT a, b는 (a, b) 조합의 유일. COUNT(DISTINCT a)는 임시 테이블로 중복 제거. 조인 후 DISTINCT는 조인 결과 전체를 임시 테이블에 넣어야 해서 비싸요. 세미 조인(EXISTS)으로 바꿀 수 있는지 보세요.

    내부 임시 테이블

    메모리(TempTable 엔진, temptable_max_ram)에 만들다가 넘치면 디스크로. 필요한 경우: ORDER BY와 GROUP BY 컬럼이 다름, 조인 결과를 정렬/그룹핑, DISTINCT + ORDER BY, UNION(ALL 제외), 파생 테이블. Extra: Using temporary.

    백엔드에서는 페이징 쿼리 ORDER BY created_at DESC LIMIT 20 OFFSET 100000은 100,020건을 읽고 버려요. 뒤 페이지로 갈수록 느려져요. 커서(키셋) 페이징: WHERE created_at < :last AND id < :lastId ORDER BY created_at DESC, id DESC LIMIT 20으로 인덱스 범위 스캔만 하게 하세요. 또 Extra에 Using temporary; Using filesort가 같이 뜨면 거의 항상 튜닝 대상이에요.
    시니어 심화 정렬과 임시 테이블의 메모리는 세션 단위예요. sort_buffer_size, tmp_table_size를 전역으로 키우면 커넥션 수만큼 곱해져서 메모리가 터져요. 꼭 필요한 쿼리에서만 세션 변수로 올려요. 디스크로 넘어간 임시 테이블 수(Created_tmp_disk_tables)가 늘어나는지가 감시 지표예요.
    • 커서 페이징의 함정: 정렬 키가 유일하지 않으면 경계에서 행이 빠지거나 중복돼요. (created_at, id)처럼 유일해지는 조합으로 정렬하고, 조건도 두 컬럼을 함께 비교해요. 그 조건이 인덱스 범위 스캔으로 풀리는지 EXPLAIN으로 확인하세요.
    • 전체 건수가 더 비싸요. 목록은 20건만 읽지만 "총 N건"은 조건에 맞는 전부를 세야 해요. 큰 목록에서는 건수를 없애거나("더 보기"), 근사치나 별도 집계 값을 써요.
    • 옵티마이저가 왜 그 계획을 골랐는지는 optimizer_trace로 볼 수 있어요. 후보 계획별 비용 추정이 나와요.
    핵심 정리
    • 옵티마이저 = 통계 기반 비용 추정. 통계 갱신 중요
    • 정렬·그룹핑은 인덱스 순서로 처리되는 게 최선, 아니면 filesort/임시 테이블
    • OFFSET 페이징은 뒤로 갈수록 느림 → 커서 페이징

    답 보기

    9.3 고급 최적화 — 조인과 서브쿼리

    네스티드 루프, 해시 조인, 세미 조인, ICP, MRR

    네스티드 루프 조인

    MySQL의 기본. 드라이빙(첫) 테이블을 읽고, 각 행마다 드리븐(둘째) 테이블을 조인 조건으로 찾아요. 드리븐 테이블의 조인 컬럼에 인덱스가 필수예요. 없으면 드라이빙 행 수 × 드리븐 풀스캔. 옵티마이저는 보통 행 수가 적은 쪽을 드라이빙으로 골라요(인덱스가 한쪽에만 있으면 없는 쪽이 드라이빙).

    블록 네스티드 루프: 드리븐에 인덱스가 없을 때 드라이빙 행들을 조인 버퍼에 모아 드리븐을 한 번만 스캔. Extra: Using join buffer. 8.0.18+는 대신 해시 조인을 써요(동등 조인에서 인덱스 없을 때 훨씬 빠름).

    조인 순서와 OUTER JOIN

    INNER JOIN은 옵티마이저가 순서를 바꿀 수 있지만, LEFT JOIN은 왼쪽이 드라이빙으로 고정돼요. 불필요한 LEFT JOIN은 INNER로 바꾸면 최적화 여지가 커져요. 또 LEFT JOIN b ... WHERE b.col = ?는 사실상 INNER JOIN이에요(b가 NULL이면 걸러지니까).

    서브쿼리 최적화

    • 세미 조인: WHERE id IN (SELECT ...), EXISTS를 조인처럼 처리. 8.0은 Table Pull-out, Duplicate Weed-out, First Match, Loose Scan, Materialization 중 선택. 옛 버전처럼 "IN 서브쿼리는 느리다"는 이제 대부분 아니에요.
    • 안티 세미 조인: NOT IN, NOT EXISTS. 8.0.17+ 최적화. 단 NOT IN은 서브쿼리에 NULL이 하나라도 있으면 결과가 전부 빈 집합이에요(SQL 3값 논리). NOT EXISTS가 안전.
    • 파생 테이블(FROM 절 서브쿼리): 8.0은 외부 쿼리에 병합(merge)하거나 임시 테이블화. 병합되면 인덱스를 쓸 수 있어요.

    ICP (Index Condition Pushdown)

    인덱스에 있는 컬럼의 조건은 스토리지 엔진이 인덱스 단계에서 걸러서 불필요한 테이블 읽기를 줄여요. INDEX (last_name, first_name)에 WHERE last_name = 'A' AND first_name LIKE '%b'면, 옛날엔 last_name으로 찾은 행을 전부 테이블에서 읽고 first_name을 검사했지만, ICP는 인덱스에서 first_name 조건까지 확인하고 통과한 것만 테이블을 읽어요. Extra: Using index condition.

    MRR과 BKA

    MRR(Multi-Range Read): 세컨더리 인덱스로 얻은 PK들을 정렬해서 클러스터링 인덱스를 순차로 읽어요. 랜덤 I/O → 순차 I/O. BKA(Batched Key Access): 조인에서 MRR을 활용. 기본은 꺼져 있고 효과는 상황에 따라.

    옵티마이저 힌트

    SELECT /*+ INDEX(t idx_name) */, JOIN_ORDER, NO_ICP 등. 통계가 잘못됐거나 옵티마이저가 명백히 틀릴 때만. 힌트는 데이터 분포가 바뀌면 독이 돼요. 인덱스 힌트(USE INDEX, FORCE INDEX)보다 옵티마이저 힌트가 유연해요.

    백엔드에서는 JPA의 N+1이 바로 "애플리케이션 레벨 네스티드 루프 조인"이에요. 주문 100건 조회 후 각 주문의 사용자를 100번 쿼리. DB 조인(fetch join)이나 IN 절 배치 로딩(default_batch_fetch_size)으로 바꾸면 100번 왕복이 1~2번이 돼요. 네트워크 RTT를 생각하면 DB 안의 네스티드 루프보다 수백 배 느려요. 그리고 NOT IN + NULL 함정은 실무에서 "결과가 갑자기 0건"으로 나타나요.
    핵심 정리
    • 네스티드 루프: 드리븐 조인 컬럼 인덱스 필수. 없으면 해시 조인
    • IN/EXISTS는 세미 조인으로 최적화됨. NOT IN + NULL 주의
    • ICP = 인덱스 단계에서 필터, MRR = PK 정렬 후 순차 읽기
    셀프 체크
    1. A(1만 건) JOIN B(100만 건), 조인 컬럼 인덱스는 B에만. 어느 쪽이 드라이빙이 되고 왜?
    답 보기

    A가 드라이빙. A를 풀스캔(1만 건)하며 각 행에 대해 B를 인덱스로 찾아요(1만 번 인덱스 탐색). 반대로 B가 드라이빙이면 100만 번 A를 찾아야 하는데 A엔 인덱스가 없어 매번 풀스캔이에요. 옵티마이저는 인덱스가 없는 쪽을 드라이빙으로 선호해요.

    • performance_schema.events_statements_summary_by_digest(또는 sys.statement_analysis)는 쿼리 형태별 총 소요 시간, 실행 횟수, 읽은 행 수 대비 반환 행 수를 줘요. 총 시간 순으로 정렬한 것이 튜닝 우선순위예요.
    • EXPLAIN은 그 서버의 통계로 계획을 세워요. 데이터가 적은 스테이징의 계획은 운영과 달라요. 운영 복제본에서 확인하세요.
    • 지금 돌고 있는 느린 쿼리의 계획은 EXPLAIN FOR CONNECTION <id>로 볼 수 있어요.
    • 조회 쿼리에는 실행 시간 상한(max_execution_time)을 걸어 두세요. 계획이 뒤집힌 쿼리 하나가 커넥션을 전부 붙잡는 것을 막아요.

    • EXPLAIN ANALYZE로 추정과 실측 비교

    11.1~11.4 SELECT 작성 시 주의사항

    인덱스를 살리는 WHERE, 날짜·문자열·NULL 비교, 페이징

    인덱스 컬럼을 변형하지 마라

    -- X: 컬럼에 함수 → 인덱스 불가
WHERE DATE(created_at) = '2024-01-15'
WHERE YEAR(created_at) = 2024
WHERE LOWER(email) = 'a@b.com'
WHERE salary * 12 >= 50000000

-- O: 리터럴 쪽을 변형
WHERE created_at >= '2024-01-15' AND created_at < '2024-01-16'
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'
WHERE email = 'a@b.com'       -- 콜레이션이 ci면 대소문자 무관
WHERE salary >= 50000000 / 12

    정말 함수가 필요하면 함수 기반 인덱스(8.0)나 생성 컬럼에 인덱스.

    타입과 콜레이션

    • 문자열 컬럼 vs 숫자 리터럴 → 컬럼이 변환돼 인덱스 불가(8장).
    • 조인 컬럼의 타입·문자셋·콜레이션이 다르면 변환이 필요해 인덱스 불가. 테이블 간 FK 컬럼은 반드시 같은 정의로.
    • 날짜: DATETIME 컬럼에 문자열 '2024-01-15'는 자동 변환되어 OK. 반대로 문자열 컬럼에 날짜 함수는 X.

    NULL

    NULL = NULL은 NULL(거짓도 참도 아님). col = NULL은 아무것도 안 나와요. IS NULL로. NOT IN (서브쿼리)에 NULL이 섞이면 전체 결과가 빈 집합(9장). 집계 함수는 NULL을 무시하지만 COUNT(*)는 행 수. COUNT(col)은 NULL 아닌 수.

    LIMIT과 페이징

    • LIMIT n OFFSET m은 m+n건 읽고 m건 버림. 큰 OFFSET은 느림.
    • 커서 페이징: 마지막 본 값을 조건으로. WHERE (created_at, id) < (:last_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20. 인덱스 (created_at, id) 필요. 정렬 키는 유일해야(동점 처리 위해 id 추가).
    • COUNT(*) 전체 건수: InnoDB는 MVCC 때문에 전체를 세요. 큰 테이블에선 느림. 근사치(information_schema.TABLES.TABLE_ROWS)나 카운터 테이블, 또는 "다음 페이지 있음"만 보여주기.

    SELECT *

    필요한 컬럼만. 커버링 인덱스 가능성이 생기고, 정렬 버퍼·네트워크·메모리가 줄어요. TEXT/BLOB 컬럼이 있으면 특히.

    그 외

    • OR 조건은 각각 인덱스가 있으면 index_merge, 없으면 풀스캔. UNION ALL로 나누는 게 나을 때도.
    • LIKE '%x%'는 전문 검색(FULLTEXT) 또는 Elasticsearch.
    • 조인 조건과 필터 조건을 ON과 WHERE에 적절히. OUTER JOIN에서 WHERE에 드리븐 조건을 쓰면 INNER로 바뀜.
    백엔드에서는 QueryDSL/JPQL이 만드는 SQL도 결국 이 규칙을 따라요. 특히 ORM이 생성하는 WHERE DATE(...), 타입 변환, 불필요한 LEFT JOIN을 로그로 확인하세요. 커서 페이징은 "무한 스크롤"의 표준이고, 관리자 화면의 "N페이지로 이동"은 OFFSET이 필요하지만 그 화면은 트래픽이 적으니 허용해요. 용도에 맞게.
    시니어 심화 쿼리 하나는 옳아도 규모에서 달라지는 것들이에요.
    • COUNT(*)는 InnoDB에서 실제로 세요. MVCC 때문에 트랜잭션마다 보이는 행 수가 달라서 "전체 행 수"를 저장해 두지 않아요. 큰 테이블의 건수는 별도 집계 테이블이나 근사치로 해결해요.
    • 큰 IN 목록: 값이 수천 개인 IN 절은 계획 수립 비용이 커지고, 값 개수가 일정 수준을 넘으면 옵티마이저가 정밀 추정 대신 통계 추정으로 바꿔서 계획이 불안정해져요. 적당한 크기로 나눠 실행하거나 임시 테이블에 넣고 조인해요.
    • OR 조건: 서로 다른 컬럼의 OR는 인덱스 하나로 풀리지 않아요. 인덱스 병합에 기대기보다 UNION ALL로 나누는 편이 계획이 안정적이에요.
    • 존재 여부만 필요하면 COUNT가 아니라 LIMIT 1이나 EXISTS로 첫 행에서 멈추게 해요.
    핵심 정리
    • 컬럼 변형 금지, 리터럴을 변형. 타입·콜레이션 일치
    • NULL은 IS NULL, NOT IN + NULL 주의
    • OFFSET → 커서 페이징, SELECT * → 필요한 컬럼

    11.5~11.7 INSERT, UPDATE, DELETE, 스키마 조작

    쓰기 쿼리의 성능과 안전, 그리고 운영 중 DDL

    INSERT

    • 다중 행 INSERT: INSERT INTO t VALUES (...), (...), (...). 한 건씩 1000번보다 1000건 한 번이 수십 배 빠름(왕복, 파싱, 로그 fsync 절약). JDBC rewriteBatchedStatements=true가 이걸 만들어요.
    • PK 순서: 8장. AUTO_INCREMENT면 자동으로 순차. 벌크 로드 시엔 PK 순으로 정렬해서 넣기.
    • INSERT ... ON DUPLICATE KEY UPDATE: upsert. 유니크 키 충돌 시 갱신. INSERT IGNORE는 충돌 무시(경고만). 경쟁 조건 없이 "없으면 넣고 있으면 갱신"을 원자적으로.
    • INSERT ... SELECT: 소스 테이블에 공유 락(RR에서) → 큰 테이블이면 주의. RC나 바이너리 로그 ROW 포맷이면 완화.

    UPDATE / DELETE

    • WHERE에 인덱스: 5장. 없으면 테이블 전체 잠금.
    • 대량 변경은 나눠서: 100만 건 DELETE 한 번 = 100만 행 락 + 거대한 언두 + 복제 지연. DELETE ... LIMIT 1000을 반복, 사이에 짧은 sleep.
    • UPDATE ... ORDER BY ... LIMIT: 순서대로 일부만. 배치 처리에.
    • 조인 UPDATE/DELETE: UPDATE a JOIN b ON ... SET a.x = b.y. 다른 테이블 기준 갱신.
    • 자기 테이블 서브쿼리: DELETE FROM t WHERE id IN (SELECT id FROM t ...)는 MySQL이 금지. 파생 테이블로 한 번 감싸거나 조인으로.

    스키마 조작 (DDL)

    8.0 온라인 DDL: 많은 ALTER가 DML을 막지 않고 진행돼요. 알고리즘:

    • INSTANT: 메타데이터만 변경, 즉시. 컬럼 끝에 추가(8.0.12+), 기본값 변경 등.
    • INPLACE: 테이블 재구성 없이(또는 있어도 DML 허용). 인덱스 추가/삭제 등. 중간에 DML 로그를 쌓았다가 마지막에 적용.
    • COPY: 새 테이블에 복사. DML 차단. 컬럼 타입 변경 등.

    ALTER TABLE ... ALGORITHM=INSTANT, LOCK=NONE으로 명시하면 안 되는 경우 에러로 알려줘서 안전해요. 그리고 5.2장 MDL 문제는 어떤 알고리즘이든 시작·끝에 잠깐 필요하니 긴 트랜잭션 확인은 필수.

    큰 테이블의 COPY DDL은 pt-online-schema-change나 gh-ost로: 새 테이블 생성 → 트리거/binlog로 변경 추적하며 복사 → 원자적 RENAME.

    백엔드에서는 JPA saveAll()은 기본적으로 한 건씩 INSERT예요. hibernate.jdbc.batch_size + rewriteBatchedStatements=true + ID 생성 전략이 IDENTITY가 아니어야(IDENTITY는 즉시 INSERT 필요) 배치가 돼요. 마이그레이션 도구(Flyway)로 DDL을 배포하면서 ALGORITHM=INSTANT를 명시하는 습관을 들이세요. "컬럼 추가는 안전, 타입 변경·NOT NULL 추가·인덱스 추가는 크기 확인" 정도의 규칙을 팀에 두세요.
    시니어 심화 스키마 변경과 대량 변경은 한 번에 하지 않고 나눠요.
    • 확장 → 이행 → 축소: 롤링 배포 중에는 옛 코드와 새 코드가 같은 스키마를 써요. 컬럼 이름 변경이나 NOT NULL 추가를 한 번에 하면 둘 중 하나가 깨져요. 새 컬럼 추가(확장) → 양쪽에 쓰기와 기존 데이터 채우기(이행) → 옛 컬럼 제거(축소)를 서로 다른 배포로 나눠요.
    • 청크는 PK 범위로: DELETE ... LIMIT 1000을 반복하면 매번 앞에서부터 다시 찾느라 갈수록 느려져요. PK 범위를 잘라서 지우고, 청크 사이에 복제 지연을 확인하며 속도를 조절해요.
    • INSTANT에도 한도가 있어요. 즉시 추가·삭제한 컬럼 변경이 일정 횟수 쌓이면 다음 변경에서 테이블 재구성이 필요해져요. "컬럼 추가는 항상 즉시"라고 가정하지 말고 큰 테이블은 사전에 알고리즘을 명시해서 확인해요.
    • DDL은 운영과 같은 크기의 데이터로 소요 시간을 재 본 뒤에 실행해요.
    핵심 정리
    • INSERT는 다중 행으로, PK 순으로, upsert는 ON DUPLICATE KEY UPDATE
    • 대량 UPDATE/DELETE는 LIMIT으로 쪼개서
    • DDL은 INSTANT/INPLACE 명시, 긴 트랜잭션 확인, 큰 테이블은 online schema change 도구

    1. 3년 지난 로그 5천만 건을 운영 중 삭제해야 해요. 방법은?
    답 보기

    (1) 인덱스가 있는 컬럼(created_at 또는 PK 범위) 조건으로 DELETE ... LIMIT 5000을 반복, 사이에 100ms sleep, 복제 지연 모니터링하며. (2) 더 좋은 건 처음부터 날짜 파티션을 두고 ALTER TABLE ... DROP PARTITION(13장)으로 즉시 삭제. (3) 남길 데이터가 적으면 새 테이블에 복사 후 RENAME 교체. 한 번에 DELETE하면 수십 분 락 + 언두 폭증 + 복제 지연.

    1권 13장 파티션

    13장 파티션

    하나의 테이블을 여러 물리 조각으로 — 언제 도움이 되고 언제 독인가

    개념

    논리적으로 하나의 테이블을 같은 서버 안에서 여러 물리 테이블(파티션)로 나눠요. 샤딩(여러 서버)과 달라요. 각 파티션은 자기 B-Tree를 가져요.

    종류

    • RANGE: 값 범위. PARTITION BY RANGE (YEAR(created_at)). 로그·이력 테이블의 표준. 오래된 파티션을 DROP PARTITION으로 즉시 삭제.
    • LIST: 값 목록. 지역 코드별 등.
    • HASH / KEY: 해시로 균등 분산. 특정 파티션만 읽는 효과는 PK 조회에서만.

    제약

    • 파티션 키는 PK와 모든 유니크 키에 포함돼야 해요. (파티션 간 유일성 검사를 못 하니까) → PK가 (id, created_at)이 되고, id만으로 유니크를 보장 못 해요.
    • 외래키 불가.
    • 파티션 키 조건이 없는 쿼리는 모든 파티션을 각각 탐색(파티션 프루닝 실패). 파티션이 100개면 인덱스 탐색 100번. 오히려 느려요.
    • 파티션마다 인덱스가 따로라 ORDER BY LIMIT도 각 파티션에서 읽어 병합.

    언제 쓰나

    (1) 시간 기준으로 오래된 데이터를 통째로 지우는 테이블(로그, 이벤트, 알림), (2) 대부분의 쿼리가 파티션 키(날짜)를 조건으로 갖는 테이블. 이 둘이 아니면 대개 인덱스 설계가 답이에요. "테이블이 크니까 파티션"은 틀린 이유예요. B-Tree는 크기에 로그 비례라 1억 건도 높이 4예요.

    백엔드에서는 파티션 테이블의 PK가 복합키가 되면서 JPA 매핑(@IdClass)이 번거로워지고, "id로 조회"가 모든 파티션을 뒤지게 돼요. 시간 기반 삭제가 목적이라면 애플리케이션 조회 패턴에 항상 날짜 조건을 넣을 수 있는지 먼저 확인하세요. 안 되면 파티션 대신 월별 테이블 + 배치 DROP, 또는 아카이빙 배치가 현실적일 수 있어요.
    핵심 정리
    • 파티션 = 같은 서버 안 물리 분할, DROP PARTITION이 최대 장점
    • 파티션 키가 PK·유니크에 포함, 조건에 없으면 전 파티션 탐색
    • 시간 기반 삭제 + 쿼리에 날짜 조건이 있을 때만
    셀프 체크
    1. 파티션이 쿼리를 오히려 느리게 하는 경우는?
    답 보기

    WHERE에 파티션 키가 없을 때. 옵티마이저가 어느 파티션인지 몰라 모든 파티션의 인덱스를 각각 탐색하고 결과를 병합해요. 파티션 수만큼 I/O가 늘어요. 또 유니크 제약이 파티션 키를 포함해야 해서 설계가 꼬이고, 파티션별 인덱스가 메모리를 더 써요.

    2권 15장 데이터 타입

    15장 데이터 타입

    문자열, 숫자, 날짜, JSON — 타입 선택이 저장 공간과 인덱스와 버그를 결정한다

    문자열: CHAR vs VARCHAR

    CHAR(10)은 항상 10문자 공간(utf8mb4면 40바이트 예약), VARCHAR는 실제 길이 + 길이 바이트(1~2). 길이가 거의 고정이고 자주 바뀌면 CHAR(변경 시 페이지 내 이동 없음), 아니면 VARCHAR. VARCHAR(255)와 VARCHAR(20)은 저장은 같지만 메모리 정렬·임시 테이블에서는 선언 길이만큼 할당해요. 필요한 만큼만 선언하세요. TEXT는 별도 페이지(off-page)에 저장될 수 있어 조회 비용이 커요.

    문자셋과 콜레이션

    8.0 기본 utf8mb4(이모지 포함 4바이트). utf8(=utf8mb3)은 3바이트까지라 이모지 저장 시 에러. 콜레이션은 비교·정렬 규칙: utf8mb4_0900_ai_ci(악센트·대소문자 무시, 기본), utf8mb4_bin(바이트 비교). 조인·비교하는 컬럼은 콜레이션이 같아야 인덱스를 써요. 대소문자 구분이 필요한 값(토큰, base64)은 bin.

    숫자

    • 정수: TINYINT(1B) ~ BIGINT(8B). ID는 BIGINT(INT는 21억에서 끝남 — 실제 사고 많음).
    • DECIMAL: 정확한 소수. 돈은 반드시 DECIMAL. FLOAT/DOUBLE은 근사값이라 0.1 + 0.2 ≠ 0.3.
    • BOOLEAN = TINYINT(1).

    날짜와 시간

    • DATETIME: 8바이트(8.0은 5+소수), 타임존 없이 입력 그대로 저장. 1000~9999년.
    • TIMESTAMP: 4바이트, UTC로 저장하고 세션 타임존으로 변환해서 보여줌. 2038년 1월까지. 타임존 변환이 자동이라 편하지만 커넥션 타임존 설정에 따라 값이 달라 보여서 혼란의 원인.
    • 권장: 서버와 커넥션 타임존을 UTC로 통일하고 DATETIME에 UTC 저장, 표시 시 애플리케이션에서 변환. JDBC serverTimezone/connectionTimeZone 확인.
    • DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP로 created_at/updated_at 자동화.

    ENUM, SET

    ENUM은 내부적으로 정수 저장이라 작고 빠르지만, 값 추가 시 ALTER(끝에 추가는 INSTANT). 정렬이 문자열이 아니라 정의 순서. 코드 테이블이나 애플리케이션 enum + VARCHAR/TINYINT가 더 유연해요.

    JSON

    바이너리로 저장, 경로 접근(->>) 가능. 유연하지만 (1) 인덱스는 생성 컬럼이나 멀티 밸류 인덱스를 통해서만, (2) 부분 갱신이 제한적, (3) 스키마가 코드에만 있어 관리 어려움. 정말 스키마가 가변적인 부가 속성에만. 자주 조건으로 쓰는 값은 컬럼으로 빼세요.

    백엔드에서는 타임존 버그는 (1) MySQL 서버 타임존, (2) JDBC 커넥션 타임존, (3) JVM 기본 타임존, (4) 애플리케이션 변환 네 곳이 어긋나서 생겨요. 전부 UTC로 고정하고 SELECT NOW(), @@session.time_zone로 확인하세요. INT ID 고갈은 "어느 날 갑자기 INSERT 실패"로 나타나는 시한폭탄이에요. 지금 확인하세요.
    시니어 심화 타입은 한 번 정하면 바꾸는 비용이 커요.
    • VARCHAR 길이를 늘릴 때: 길이를 저장하는 바이트 수가 바뀌는 경계(255바이트)를 넘기면 즉시 변경이 안 되고 테이블을 다시 만들어요. utf8mb4에서는 글자 수 63과 64 사이가 그 경계예요.
    • 콜레이션은 버전마다 기본값이 달라요. 5.7에서 만든 테이블과 8.0에서 만든 테이블은 기본 콜레이션이 달라서, 둘을 조인하면 인덱스를 못 쓰거나 에러가 나요. 후행 공백을 비교에 포함하는지도 콜레이션에 따라 달라요. 업그레이드 때 명시적으로 통일하세요.
    • TIMESTAMP와 DATETIME의 차이: TIMESTAMP는 세션 타임존에 따라 변환해서 저장·조회하고 DATETIME은 넣은 값 그대로예요. 섞어 쓰면 타임존 설정이 바뀔 때 한쪽만 값이 달라져 보여요.
    • JSON 안의 값으로 조회해야 한다면 생성 컬럼(generated column)으로 꺼내 인덱스를 걸어요. 자주 쓰는 조건이면 처음부터 일반 컬럼으로 두는 것이 맞아요.
    핵심 정리
    • VARCHAR는 필요한 길이만, utf8mb4, 비교 컬럼은 콜레이션 통일
    • ID는 BIGINT, 돈은 DECIMAL
    • DATETIME + UTC 통일, TIMESTAMP는 2038 한계
    • JSON은 부가 속성만, 조건 컬럼은 분리
    셀프 체크
    1. DATETIME과 TIMESTAMP의 차이와 선택 기준은?
    답 보기

    TIMESTAMP는 UTC로 저장하고 세션 타임존으로 자동 변환, 4바이트, 2038년까지. DATETIME은 변환 없이 그대로 저장, 더 넓은 범위. 세션 타임존이 제각각이면 TIMESTAMP 값이 다르게 보여 혼란이 생겨요. 권장은 모든 레이어 UTC 통일 + DATETIME. 2038 문제도 피해요.

    2권 16장 복제

    16.1~16.3 복제 아키텍처와 타입

    바이너리 로그, I/O·SQL 스레드, 바이너리 로그 위치 vs GTID

    왜 복제하나

    (1) 스케일 아웃: 읽기를 replica로 분산, (2) 백업: replica에서 백업해 source 부담 없이, (3) 분석 쿼리 격리, (4) 고가용성: source 장애 시 replica 승격.

    아키텍처

    1. Source가 변경을 바이너리 로그에 기록 (커밋 시, 리두 로그와 2단계 커밋으로 일관성 유지)
    2. Replica의 I/O 스레드가 Source에 접속해 바이너리 로그를 받아 릴레이 로그에 저장
    3. Replica의 SQL(applier) 스레드가 릴레이 로그를 읽어 실행

    8.0은 applier를 여러 스레드로(replica_parallel_workers, LOGICAL_CLOCK) 병렬 적용해 지연을 줄여요.

    복제 타입: 위치 기반 vs GTID

    • 바이너리 로그 위치 기반: "파일 binlog.000123의 위치 4567부터". 서버마다 파일명·위치가 달라서 replica를 다른 source로 옮기거나 장애 조치 시 위치 계산이 복잡.
    • GTID(Global Transaction ID): 트랜잭션마다 server_uuid:번호. 모든 서버에서 같은 트랜잭션은 같은 ID. "이 GTID까지 적용했다"로 어느 서버에 붙여도 자동으로 이어져요. 8.0 표준, 장애 조치 자동화의 전제.
    백엔드에서는 RDS/Aurora의 read replica, Aurora의 reader 엔드포인트가 이 구조예요(Aurora는 스토리지 공유라 지연이 훨씬 짧지만 원리는 같아요). 애플리케이션은 쓰기 DataSource와 읽기 DataSource를 나누고, @Transactional(readOnly=true)로 라우팅하는 게 흔한 구현이에요(AbstractRoutingDataSource 또는 JDBC ReplicationDriver).
    시니어 심화 복제본은 읽기 확장 수단이기 전에 장애 대비 용량이에요.
    • 읽기 분산의 연쇄 장애: 복제본 하나가 죽으면 그 읽기가 남은 서버로 몰려요. 평소에 복제본들이 꽉 차게 일하고 있었다면 남은 서버도 연달아 넘어가요. 한 대가 빠져도 버티는 여유를 두고 운영해요.
    • 승격 대상은 원본과 같은 사양이어야 해요. 비용을 아끼려고 복제본을 작게 두면 장애 조치 직후 쓰기 부하를 못 받아요.
    • 장애 조치 뒤의 애플리케이션: 풀에 남은 옛 연결, 런타임의 DNS 캐시 때문에 앱이 강등된 서버에 계속 쓰려고 해요. 읽기 전용 에러를 받으면 풀을 비우고 다시 연결하게 만들고, 실제로 장애 조치를 일으켜 보는 훈련으로 확인해요.
    • 백업과 무거운 분석 쿼리는 서비스 트래픽을 받지 않는 전용 복제본에서 돌려요.
    핵심 정리
    • binlog → I/O 스레드 → 릴레이 로그 → applier 스레드
    • GTID = 전역 트랜잭션 ID, 장애 조치와 토폴로지 변경의 표준
    셀프 체크
    1. GTID가 위치 기반보다 장애 조치에 유리한 이유는?
    답 보기

    source가 죽어 replica A를 승격하고 replica B를 A에 붙일 때, 위치 기반은 B가 옛 source의 어느 위치까지 받았는지를 A의 binlog 위치로 환산해야 해요(파일명·오프셋이 다름). GTID는 B가 "여기까지 적용"한 GTID 집합을 A에 알려주면 A가 그 다음부터 보내줘요. 자동이고 중복·누락이 없어요.

    16.4~16.7 복제 포맷, 동기 방식, 토폴로지, 지연

    STATEMENT vs ROW, 비동기 vs 반동기, 그리고 복제 지연을 다루는 법

    바이너리 로그 포맷

    포맷기록 내용장점단점
    STATEMENT실행한 SQL 문로그 작음비결정적 함수(NOW(), UUID(), LIMIT 없는 ORDER BY)가 replica에서 다른 결과. RC 격리 수준 사용 불가
    ROW변경된 행의 전후 값정확, 안전, RC 사용 가능. 8.0 기본대량 UPDATE 시 로그 거대(100만 행 = 100만 이벤트)
    MIXED기본 STATEMENT, 위험하면 ROW절충판단 기준 복잡

    ROW 포맷은 CDC(Change Data Capture, Debezium 등)의 기반이에요. binlog를 읽어 Kafka로 보내면 DB 변경 이벤트 스트림이 돼요. 분산 시스템 챕터 11장.

    동기 방식

    • 비동기(기본): Source는 replica가 받았는지 안 기다려요. 빠르지만 Source가 죽으면 마지막 트랜잭션들이 replica에 없을 수 있음(데이터 유실).
    • 반동기(semi-sync): 최소 1대 replica가 릴레이 로그에 받았다(적용은 아님)고 응답해야 커밋 완료. 유실 방지, 지연 약간 증가. 타임아웃되면 비동기로 자동 전환.
    • 그룹 복제 / InnoDB Cluster: Paxos 기반 합의로 과반수 동의 후 커밋. 자동 장애 조치. 분산 시스템 챕터 9장의 합의가 여기 쓰여요.

    토폴로지

    단일 source → 다중 replica(표준). 체인(source → replica → replica, 중간 replica는 log_replica_updates). 듀얼 source(양방향, 충돌 위험 커서 비권장). 다중 source → 단일 replica(집계용).

    복제 지연

    Source 커밋 → replica 적용 사이의 시간. SHOW REPLICA STATUS의 Seconds_Behind_Source(부정확할 수 있음, heartbeat 테이블로 측정 권장). 원인: 대량 쓰기(단일 트랜잭션에 100만 행), applier 단일 스레드 병목, replica 하드웨어 열세, replica에서 무거운 읽기 쿼리, 인덱스 없는 UPDATE(ROW 포맷에서 행마다 풀스캔!).

    애플리케이션 대응:

    • read-your-writes: 쓰기 직후 읽기는 source로. 같은 요청/세션 안에서, 또는 쓴 뒤 N초 동안.
    • 중요한 읽기(결제 확인, 재고)는 항상 source.
    • 지연 임계값을 넘으면 replica를 읽기 풀에서 자동 제외(ProxySQL, 애플리케이션 헬스체크).
    • 대량 쓰기는 쪼개서(11장).
    백엔드에서는 "글을 썼는데 목록에 없어요"가 복제 지연의 전형적 증상이에요. 트랜잭션 안에서 읽기가 source로 가는지, 커밋 직후 다음 요청의 조회가 replica로 가는지 확인하세요. 그리고 ROW 포맷 + PK 없는 테이블 = replica에서 행 하나 찾으려 풀스캔 = 지연 폭발. 모든 테이블에 PK를 두는 또 하나의 이유예요.
    핵심 정리
    • ROW 포맷이 표준, CDC의 기반
    • 비동기는 유실 가능, 반동기는 수신 보장, 그룹 복제는 합의
    • 복제 지연: read-your-writes는 source로, 대량 쓰기는 분할, PK 필수
    셀프 체크
    1. 반동기 복제에서 "받았다"와 "적용했다"의 차이가 왜 중요한가요?
    2. 복제 지연을 줄이기 위해 애플리케이션이 할 수 있는 일 세 가지는?
    답 보기

    1. 반동기는 replica가 릴레이 로그에 기록했다는 확인만 받아요. 아직 적용 전이라 그 replica를 읽어도 최신이 아닐 수 있어요. 유실 방지(내구성)는 보장하지만 읽기 일관성은 보장하지 않아요. 둘을 혼동하면 "반동기인데 왜 옛 데이터가 보이지?"가 돼요.

    2. (1) 대량 UPDATE/DELETE를 작은 배치로 나누기, (2) 모든 테이블에 PK 두기(ROW 적용 효율), (3) replica에서 무거운 분석 쿼리 돌리지 않기(별도 replica로 격리). 추가로 트랜잭션을 짧게.
