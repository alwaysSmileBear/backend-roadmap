    성능 분석

    기준 교재: 시스템 성능 분석(Systems Performance, Brendan Gregg) · 3~4주

    앞의 챕터들은 장마다 진단 명령어를 하나씩 소개했어요. 이 챕터는 그것들을 하나의 절차로 묶어요. 느리다는 신고를 받았을 때 어디서부터 보고, 무엇을 재고, 어떻게 원인을 좁히는지예요.

    성능 작업에서 가장 흔한 실패는 도구를 모르는 것이 아니라 방법 없이 추측하는 것이에요. 1~2장의 방법론과 지연 분포를 먼저 읽고, 나머지는 필요할 때 찾아보세요.

    1부 방법론

    1장 용어와 방법론

    무엇을 재는지 정하고, 순서대로 본다

    기본 용어

    • 지연(latency): 요청 하나가 걸린 시간. 기다린 시간 + 처리한 시간.
    • 처리량(throughput): 단위 시간당 처리한 요청 수.
    • 사용률(utilization): 자원이 바빴던 시간의 비율.
    • 포화(saturation): 자원이 감당하지 못해 대기열에 쌓인 양.

    사용률이 100%가 아니어도 포화는 생겨요. 순간적으로 몰리면 평균 사용률 60%인 자원에서도 대기가 발생해요.

    하지 말아야 할 방법

    • 가로등 방식: 아는 도구, 익숙한 지표만 본다. 문제가 거기 없으면 못 찾아요.
    • 무작위 변경: 설정을 하나씩 바꿔 보며 나아지길 기대한다. 나아져도 이유를 모르고, 여러 개를 바꿔서 무엇이 효과였는지도 몰라요.
    • 남 탓: "네트워크 문제 같아요", "DB가 느린 것 같아요". 근거 없이 넘기는 것.

    USE 방법 (자원 관점)

    모든 자원(CPU, 메모리, 디스크, 네트워크, 그리고 풀·락 같은 소프트웨어 자원)에 대해 세 가지를 확인해요.

    • Utilization: 얼마나 바쁜가
    • Saturation: 대기가 쌓였는가
    • Errors: 에러가 있는가

    빠짐없이 훑는 것이 목적이에요. 에러부터 보면 빨라요. 해석이 쉽고 원인을 바로 가리키는 경우가 많아요.

    RED 방법 (서비스 관점)

    서비스마다 세 가지를 봐요. Rate(초당 요청 수), Errors(실패한 요청 수), Duration(걸린 시간의 분포). RED로 "어느 서비스가 이상한가"를 찾고, USE로 "그 서비스의 어느 자원이 병목인가"를 찾아요.

    백엔드에서는 커넥션 풀, 스레드풀, 세마포어도 자원이에요. USE를 그대로 적용하세요. 풀의 사용률은 사용 중인 수 / 최대 수, 포화는 대기 중인 요청 수와 대기 시간, 에러는 획득 타임아웃이에요. OS 지표가 전부 한가한데 느리다면 대부분 이런 소프트웨어 자원이 포화된 거예요.
    시니어 심화
    • 문제 정의부터 하세요. "느리다"를 받으면 무엇이, 언제부터, 누구에게, 얼마나 느린지와 그 무렵 무엇이 바뀌었는지를 먼저 물어요. 이 질문만으로 절반은 풀려요.
    • 지표가 없는 자원이 맹점이에요. USE 표를 만들어 각 칸을 어떤 지표로 채울지 적어 보면, 측정하지 않고 있던 자원이 드러나요. 그 칸을 채우는 것이 다음 장애를 줄이는 일이에요.
    • 변경은 한 번에 하나, 그리고 전후를 같은 조건에서 재요. 효과가 없으면 되돌려요. 효과 없는 변경이 쌓이면 시스템을 아무도 설명할 수 없게 돼요.
    핵심 정리
    • 사용률 ≠ 포화. 대기열이 지연을 만듦
    • USE = 자원별 사용률·포화·에러, RED = 서비스별 요청률·에러·소요 시간
    • 추측과 무작위 변경 대신 빠짐없이 훑는 절차
    셀프 체크
    1. CPU 사용률이 50%인데 요청 지연이 커졌습니다. 사용률만으로 CPU 문제가 아니라고 결론 내릴 수 없는 이유는 무엇인가요?
    답 보기

    사용률은 일정 구간의 평균이라 그 안의 순간적인 몰림을 숨겨요. 1초 중 절반은 모든 코어가 꽉 차고 절반은 놀아도 평균은 50%예요. 꽉 찬 순간에는 실행 대기열에 스레드가 쌓여서 지연이 생겨요. 컨테이너라면 CPU 한도에 걸려 스로틀링되는 경우도 사용률은 낮게 보여요. 그래서 사용률과 함께 포화 지표(실행 대기열 길이, 스로틀링 시간)를 봐야 해요.

    2장 지연 분포와 백분위

    평균은 아무도 겪지 않는 숫자다

    평균이 숨기는 것

    요청 99개가 10ms, 1개가 2초면 평균은 약 30ms예요. 대시보드는 건강해 보이지만 100명 중 1명은 2초를 기다렸어요. 지연 분포는 한쪽으로 긴 꼬리를 가져서 평균과 중앙값이 대표값 구실을 못 해요.

    백분위

    • p50: 절반의 요청이 이보다 빨랐다(중앙값).
    • p99: 99%가 이보다 빨랐다. 100번 중 가장 느린 1번.
    • p99.9: 1000번 중 가장 느린 1번.

    꼬리가 중요한 이유

    • 사용자는 요청을 여러 번 보내요. 한 화면이 API 20개를 부르면, 각 호출이 p99보다 빠를 확률 0.99를 20번 곱해 약 82%예요. 사용자 5명 중 1명은 그 화면에서 p99 지연을 겪어요.
    • 서비스가 여러 하위 서비스를 병렬로 부르면 가장 느린 응답을 기다려요. 하위 서비스의 꼬리가 상위 서비스의 평균이 돼요.
    • 꼬리 지연을 겪는 요청은 대개 데이터가 많은 사용자, 즉 가장 중요한 고객이에요.

    분포를 직접 본다

    백분위 몇 개보다 히스토그램이나 히트맵이 더 많은 것을 알려줘요. 봉우리가 둘이면 서로 다른 두 경로가 섞여 있는 거예요(캐시 적중과 미스, 빠른 쿼리와 느린 쿼리). 평균을 줄이려 하지 말고 느린 봉우리가 무엇인지 찾아요.

    백엔드에서는 메트릭 라이브러리가 백분위를 어떻게 계산하는지 확인하세요. 인스턴스 안에서 계산한 p99를 여러 인스턴스에 걸쳐 평균 내면 의미 없는 숫자가 돼요. 히스토그램 버킷으로 내보내고 수집 시스템에서 합친 뒤 백분위를 계산해야 해요. 그리고 지연은 성공과 실패를 나눠서 재요. 빠르게 실패하는 에러가 섞이면 지연이 좋아진 것처럼 보여요.
    시니어 심화
    • 측정이 꼬리를 놓치는 경우: 부하 생성기가 응답을 받은 뒤에야 다음 요청을 보내면, 서버가 멈춘 동안 보냈어야 할 요청이 아예 측정에서 빠져요. 멈춤이 길수록 기록된 지연은 실제보다 좋게 나와요. 정해진 시각에 보냈어야 할 요청을 기준으로 지연을 재는 도구를 써요.
    • 꼬리를 줄이는 기법: 일정 시간 안에 응답이 없으면 다른 복제본에 같은 요청을 한 번 더 보내고 먼저 온 것을 쓰는 방식(헤지 요청)이 있어요. 부하가 조금 늘지만 p99가 크게 줄어요. 멱등한 읽기에만 써요.
    • 최댓값도 기록하세요. p99.9까지 정상인데 최댓값이 수십 초라면 타임아웃에 걸린 요청이 있는 거예요.
    핵심 정리
    • 지연은 긴 꼬리 분포. 평균이 아니라 백분위로
    • 호출이 많을수록, 병렬 팬아웃이 클수록 꼬리가 사용자 경험을 지배
    • 백분위는 평균 낼 수 없음. 히스토그램을 합쳐서 계산
    셀프 체크
    1. 서비스 A가 요청마다 하위 서비스 10개를 병렬로 호출하고 전부 기다립니다. 각 하위 서비스의 p99가 100ms일 때 A의 지연에 대해 무엇을 말할 수 있나요?
    답 보기

    하위 호출 10개가 전부 100ms 안에 끝날 확률은 0.99를 10번 곱한 약 90%예요. 즉 A의 요청 10개 중 1개는 적어도 하나의 하위 호출이 100ms를 넘겨요. 하위 서비스에서 100번에 1번 일어나는 일이 A에서는 10번에 1번 일어나는 거예요. 팬아웃이 클수록 하위 서비스의 꼬리 지연이 상위 서비스의 일상적인 지연이 되므로, 하위 서비스는 p99보다 더 높은 백분위를 관리해야 해요.

    2부 관찰

    3장 리눅스 서버 첫 점검

    서버에 들어가서 처음 1분 동안 볼 것

    순서대로 훑는다

    명령보는 것이상 신호
    uptime로드 애버리지 1·5·15분코어 수보다 크고, 1분 값이 15분 값보다 크면 악화 중
    dmesg -T | tail커널 메시지OOM kill, 디스크·네트워크 에러
    vmstat 1실행 대기, 메모리, 스왑, CPU 분해r이 코어 수 초과, si/so가 0이 아님
    mpstat -P ALL 1코어별 CPU한 코어만 100%(단일 스레드 병목)
    pidstat 1프로세스별 CPU예상 밖의 프로세스
    iostat -xz 1디스크별 지연과 대기열await와 대기열 길이 증가
    free -m메모리available이 바닥
    sar -n DEV 1네트워크 처리량인터페이스 한도에 근접
    sar -n TCP,ETCP 1연결 수, 재전송재전송 증가
    top전체 요약위에서 놓친 것 확인

    CPU 시간의 분해

    • us(사용자): 애플리케이션 코드. 높으면 프로파일러로.
    • sy(시스템): 커널. 높으면 시스템 콜이나 네트워크 처리가 많은 것.
    • wa(I/O 대기): CPU는 놀지만 I/O를 기다리는 작업이 있음.
    • st(steal): 가상화 환경에서 다른 VM에 빼앗긴 시간.

    메모리 읽는 법

    free의 free 열이 작다고 메모리 부족이 아니에요. 리눅스는 남는 메모리를 파일 캐시로 써요. 필요하면 비워 줄 수 있는 양까지 포함한 available을 보세요.

    백엔드에서는 컨테이너 안에서 이 명령들을 실행하면 대부분 호스트 전체의 값이 보여요. 컨테이너의 실제 한도와 사용량은 cgroup 파일(cpu.stat, memory.current, memory.events)이나 오케스트레이터의 메트릭에서 봐야 해요. 호스트에 CPU가 남아도 컨테이너는 한도에 걸려 스로틀링 중일 수 있어요.
    시니어 심화
    • 짧게 사는 프로세스는 주기적으로 샘플링하는 도구에 잡히지 않아요. 초당 수백 번 떴다 죽는 프로세스가 CPU를 다 써도 top에는 안 보여요. 프로세스 생성을 추적하는 도구로 확인해요.
    • 1초 평균도 평균이에요. 수십 밀리초짜리 멈춤은 1초 간격 지표에 묻혀요. 꼬리 지연의 원인을 찾을 때는 이벤트 단위로 추적하는 도구(perf, eBPF 기반 도구)가 필요해요.
    • 점검 순서를 스크립트로 만들어 장애 때 한 번에 수집하세요. 장애 중에 명령어를 기억해 내며 하나씩 치는 것은 느리고, 나중에 비교할 기록도 남지 않아요.
    핵심 정리
    • 에러 → 포화 → 사용률 순으로 정해진 목록을 훑음
    • CPU는 us/sy/wa/st로 분해해서 읽음
    • 컨테이너 안에서는 cgroup 지표가 진짜 값
    셀프 체크
    1. vmstat에서 r 값이 코어 수보다 훨씬 큰데 us+sy는 30%입니다. 어떤 상황을 의심할 수 있나요?
    답 보기

    실행하려는 스레드는 많은데 CPU는 다 쓰이지 않고 있다는 모순된 상태예요. 컨테이너의 CPU 한도에 걸려 스로틀링 중이면, 스레드는 실행 대기 상태로 쌓이지만 한도 때문에 CPU를 더 못 써서 사용률이 낮게 나와요. 호스트 전체 기준 지표를 컨테이너 안에서 보고 있어서 다른 컨테이너의 대기열이 섞여 보이는 경우도 있어요. cgroup의 스로틀링 통계를 확인해요.

    4장 프로파일링과 플레임 그래프

    CPU 시간이 코드의 어디에서 쓰이는가

    샘플링 프로파일러

    초당 수십~수백 번, 실행 중인 스레드의 호출 스택을 기록해요. 어떤 함수가 샘플에 많이 잡혔다면 그 함수에서 시간을 많이 썼다는 뜻이에요. 모든 호출을 기록하는 방식보다 부하가 훨씬 적어서 운영 환경에서도 쓸 수 있어요.

    플레임 그래프 읽는 법

    • 세로: 호출 스택. 아래가 호출한 쪽, 위가 호출된 쪽.
    • 가로: 그 함수가 샘플에 잡힌 비율. 시간 순서가 아니에요. 이름순으로 정렬돼요.
    • 폭이 넓은 것이 시간을 많이 쓴 것.
    • 맨 위가 평평하게 넓은 곳이 실제로 CPU를 태우는 함수예요. 그 아래는 거기까지 오는 경로예요.

    프로파일의 종류

    종류답하는 질문
    CPUCPU를 쓰는 동안 어디에 있었나
    벽시계(wall-clock)기다리는 시간을 포함해 어디에 있었나
    할당어느 코드가 메모리를 많이 할당하나
    락어느 락에서 얼마나 기다렸나

    응답이 느린데 CPU 프로파일이 깨끗하면, 그 요청은 CPU를 쓰지 않고 기다리고 있는 거예요. 벽시계나 락 프로파일로 바꿔야 해요.

    비교하기

    배포 전후, 정상 인스턴스와 느린 인스턴스의 프로파일을 겹쳐 차이만 보면(차분 플레임 그래프) 무엇이 달라졌는지 바로 드러나요.

    백엔드에서는 프로파일에서 자주 보이는 범인은 비즈니스 로직이 아니에요. JSON 직렬화, 로깅(문자열 조립, 예외 스택 생성), 정규식, 리플렉션, 그리고 루프 안의 불필요한 객체 생성이에요. 로그 레벨이 꺼져 있어도 인자를 만드는 비용은 나가니, 비싼 로그 인자는 지연 평가로 넘기세요.
    시니어 심화
    • 프로파일은 "가장 느린 것"이 아니라 "총합이 큰 것"을 보여줘요. 한 번에 1ms지만 요청마다 500번 불리는 함수가 맨 위에 나와요. 해결은 그 함수를 빠르게 하는 것이 아니라 덜 부르는 것일 때가 많아요.
    • 인라이닝된 함수는 프로파일에서 호출자에 합쳐져 보여요. 이름이 안 보인다고 실행되지 않은 것이 아니에요.
    • 운영에서 낮은 비율로 항상 프로파일을 수집해 두면(연속 프로파일링) 회귀를 배포 단위로 추적할 수 있어요. 성능 문제의 대부분은 어느 날 갑자기가 아니라 여러 배포에 걸쳐 조금씩 나빠진 거예요.
    핵심 정리
    • 샘플링 = 주기적으로 스택 기록. 부하가 낮아 운영에서도 가능
    • 플레임 그래프: 폭 = 비율, 가로축은 시간이 아님. 맨 위 넓은 곳이 범인
    • CPU가 깨끗한데 느리면 벽시계·락 프로파일로
    셀프 체크
    1. 플레임 그래프에서 어떤 함수의 폭이 전체의 40%입니다. 이 함수 자체가 느리다고 결론 내릴 수 있나요?
    답 보기

    아니요. 폭은 그 함수와 그 함수가 호출한 모든 것을 합친 시간이에요. 그 함수 바로 위에 다른 함수들이 폭을 대부분 채우고 있다면 시간은 그 위쪽 함수들에서 쓰인 거예요. 그 함수 자체가 쓴 시간은 위에 아무것도 없이 평평하게 드러난 부분만이에요. 또 폭이 넓은 이유가 한 번의 실행이 느려서인지 아주 많이 호출돼서인지도 그래프만으로는 구분되지 않아요.

    5장 계측 설계

    문제가 났을 때 답할 수 있도록 미리 심어 둔다

    무엇을 계측하나

    외부로 나가거나 들어오는 모든 경계에 같은 세 가지를 심어요. 호출 수, 실패 수, 소요 시간 분포.

    • 들어오는 요청(엔드포인트별)
    • DB 쿼리, 캐시 호출, 외부 API 호출, 메시지 발행·소비
    • 풀과 큐: 사용 중인 수, 대기 수, 대기 시간

    메트릭 종류

    • 카운터: 늘어나기만 하는 누적값(요청 수, 에러 수). 조회할 때 변화율로 바꿔 봐요.
    • 게이지: 현재 값(큐 길이, 사용 중인 커넥션 수). 수집 시점의 값만 남아요.
    • 히스토그램: 값을 구간별로 센 분포(지연, 크기).

    레이블 설계

    메트릭에 레이블(엔드포인트, 상태 코드, 호출 대상)을 붙이면 나눠 볼 수 있어요. 그런데 레이블 값의 조합 하나하나가 별도의 시계열이 돼요. 값의 종류가 한정된 것만 레이블로 써요. 사용자 ID, 주문 ID, 전체 URL 경로를 넣으면 시계열이 끝없이 늘어요.

    세 신호의 역할

    • 메트릭: 무엇이 얼마나 이상한지 알려줌. 싸고 오래 보관 가능.
    • 트레이스: 한 요청이 어느 구간에서 시간을 썼는지 알려줌.
    • 로그: 그 순간 정확히 무슨 일이 있었는지 알려줌.

    셋을 같은 ID로 연결해야 메트릭에서 이상을 보고 → 해당 트레이스를 찾고 → 그 요청의 로그를 읽는 흐름이 돼요.

    백엔드에서는 게이지는 수집 주기 사이의 변화를 놓쳐요. 15초마다 큐 길이를 읽으면 그 사이에 찼다가 비워진 것은 안 보여요. 포화를 보려면 길이 게이지와 함께 대기 시간 히스토그램을 남기세요. 그리고 URL 경로를 레이블로 쓸 때는 /orders/1042가 아니라 /orders/{id} 같은 경로 템플릿으로 넣어요.
    시니어 심화
    • 히스토그램 버킷 경계가 정밀도예요. 목표가 300ms인데 버킷이 100ms 다음 500ms라면 목표 달성 여부를 알 수 없어요. 목표값 주변에 경계를 촘촘히 둬요.
    • 알람은 원인이 아니라 증상에 걸어요. "CPU 80%"는 사용자에게 문제가 없어도 울리고, 사용자가 겪는 문제 중 CPU와 무관한 것은 놓쳐요. 에러율과 지연 같은 사용자가 겪는 증상에 알람을 걸고, 자원 지표는 원인을 찾을 때 봐요.
    • 계측 자체의 비용을 재세요. 요청마다 수십 개의 스팬과 로그 줄을 만들면 그것이 지연과 비용의 큰 부분이 돼요. 트레이스는 샘플링하고, 뜨거운 경로의 로그는 줄여요.
    핵심 정리
    • 모든 경계에 호출 수·실패 수·소요 시간 분포
    • 레이블은 값의 종류가 한정된 것만
    • 메트릭 → 트레이스 → 로그를 같은 ID로 연결
    셀프 체크
    1. 커넥션 풀의 "사용 중인 커넥션 수" 게이지만으로는 풀 고갈을 놓칠 수 있는 이유를 설명하세요.
    답 보기

    게이지는 수집하는 순간의 값만 남겨요. 풀이 수집 주기 사이에 잠깐 가득 찼다가 풀리면 기록에는 여유 있는 값만 남아요. 그 짧은 순간에 커넥션을 기다린 요청들은 지연을 겪었지만 지표에는 흔적이 없어요. 커넥션을 얻기까지 기다린 시간을 히스토그램으로 남기면, 요청마다 기록되므로 순간적인 고갈도 대기 시간 분포의 꼬리로 드러나요.

    3부 실험

    6장 부하 테스트 설계

    무엇을 알고 싶은지가 테스트의 모양을 정한다

    테스트의 종류

    종류방법알고 싶은 것
    부하예상 최대 트래픽을 일정 시간 유지목표를 만족하는가
    스트레스한계를 넘을 때까지 계속 증가어디서, 어떻게 무너지는가
    스파이크갑자기 몇 배로 올렸다 내림급증을 견디고 회복하는가
    지속(soak)보통 부하를 몇 시간~며칠누수, 서서히 나빠지는 것

    부하 모델

    • 닫힌 모델: 가상 사용자 N명이 "요청 → 응답 대기 → 다음 요청"을 반복해요. 서버가 느려지면 요청도 덜 보내요.
    • 열린 모델: 초당 N개씩 정해진 속도로 보내요. 서버가 느려져도 계속 와요.

    인터넷 서비스의 실제 트래픽은 열린 모델에 가까워요. 사용자는 서버 사정을 봐주지 않아요. 닫힌 모델로만 테스트하면 과부하 상황을 재현하지 못해요.

    현실과 맞추기

    • 데이터 크기: 빈 DB에서의 쿼리는 운영과 실행 계획이 달라요.
    • 요청 분포: 같은 ID만 반복 조회하면 전부 캐시에 맞아요. 실제 접근 분포(소수가 인기 있고 긴 꼬리가 있는)를 흉내 내요.
    • 요청 구성: 읽기와 쓰기의 비율, 무거운 엔드포인트의 비중.
    • 워밍업: 시작 직후의 구간은 결과에서 빼요.

    결과 읽기

    부하를 단계적으로 올리며 처리량과 지연을 함께 그려요. 처리량이 더 늘지 않고 지연만 오르기 시작하는 지점이 한계예요. 그 지점에서 무엇이 포화됐는지를 USE로 찾는 것이 테스트의 진짜 결과예요.

    백엔드에서는 부하 생성기가 병목이 되는 경우가 많아요. 생성기 서버의 CPU가 꽉 차면 서버가 느린 것처럼 보여요. 생성기의 자원 지표도 같이 보고, 필요하면 여러 대로 나눠요. 외부 API(결제, 메시지 발송)는 실제로 호출되지 않게 가짜 응답으로 바꾸되, 그 가짜가 실제와 비슷한 지연을 갖게 하세요. 즉시 응답하는 가짜는 스레드와 커넥션 점유 시간을 비현실적으로 짧게 만들어요.
    시니어 심화
    • 한계 너머의 동작이 더 중요해요. 한계를 넘었을 때 처리량이 유지되며 초과분만 거절되는지, 아니면 처리량 자체가 무너지는지를 확인하세요. 후자라면 부하 차단이 없는 거예요.
    • 회복을 확인하세요. 부하를 정상으로 되돌린 뒤 지연이 원래대로 돌아오는 데 걸리는 시간을 재요. 밀린 큐와 재시도 때문에 돌아오지 않는 시스템이 있어요.
    • 운영 트래픽 재생이 가장 현실적인 분포를 줘요. 기록한 요청을 다시 보내거나 실제 트래픽의 복사본을 새 버전에 흘려요. 쓰기 요청의 부작용과 개인정보 처리는 미리 정리해야 해요.
    핵심 정리
    • 부하·스트레스·스파이크·지속 테스트는 답하는 질문이 다름
    • 열린 모델(도착률 고정)이 실제 트래픽에 가까움
    • 데이터 크기와 접근 분포를 운영과 맞춤. 한계에서 무엇이 포화됐는지가 결과
    셀프 체크
    1. 가상 사용자 100명으로 테스트했더니 서버가 느려져도 에러 없이 버텼습니다. 이 결과로 "과부하에 안전하다"고 할 수 없는 이유는 무엇인가요?
    답 보기

    가상 사용자 방식은 응답을 받아야 다음 요청을 보내므로, 서버가 느려지면 들어오는 요청도 같이 줄어요. 서버가 스스로 부하를 조절하는 셈이라 진짜 과부하 상태에 도달하지 않아요. 실제로는 서버가 느려져도 새 사용자가 같은 속도로 계속 도착하고, 기다리다 지친 사용자가 재시도까지 해서 부하가 오히려 늘어요. 초당 도착률을 고정한 방식으로 처리 능력을 넘는 부하를 줘 봐야 과부하 동작을 알 수 있어요.

    7장 큐잉 이론과 용량 계획

    왜 80%에서 갑자기 느려지는가

    대기는 사용률에 비선형

    요청이 불규칙하게 도착하고 처리 시간도 들쭉날쭉하면, 평균적으로는 감당할 수 있어도 순간순간 대기가 생겨요. 서버가 하나인 가장 단순한 모델에서 평균 체류 시간은 다음과 같아요.

    체류 시간 = 처리 시간 / (1 - 사용률)

      사용률 50% → 처리 시간의 2배
      사용률 80% → 5배
      사용률 90% → 10배
      사용률 95% → 20배

    사용률이 100%에 가까워질수록 지연은 무한대로 가요. "아직 20% 남았다"가 아니라 "이미 무릎을 지났다"예요.

    변동성이 대기를 만든다

    도착 간격이나 처리 시간의 변동이 클수록 같은 사용률에서 대기가 길어요. 평균 처리 시간이 같아도, 가끔 아주 오래 걸리는 요청이 섞이면 그 뒤의 요청이 전부 밀려요. 느린 요청을 따로 분리하는 것(별도 풀, 별도 큐)이 전체 지연을 줄이는 이유예요.

    서버가 여러 대일 때

    같은 총 처리 능력이라면 큐 하나를 여러 서버가 나눠 처리하는 쪽이 서버마다 큐를 따로 두는 쪽보다 대기가 짧아요. 따로 두면 한 서버에는 줄이 있는데 옆 서버는 노는 상황이 생겨요.

    용량 계획

    1. 부하를 대표하는 지표를 정한다(초당 요청 수, 동시 사용자 수).
    2. 그 지표와 자원 사용량의 관계를 측정한다.
    3. 부하의 성장을 예측한다(추세 + 예정된 이벤트).
    4. 목표 사용률을 정하고 필요한 자원을 계산한다.

    목표 사용률은 100%가 아니에요. 지연 목표를 지키는 사용률, 그리고 일부가 죽어도 남은 것이 그 사용률을 넘지 않는 수준이에요.

    확장성의 한계

    서버를 두 배로 늘려도 처리량이 두 배가 되지 않아요. 직렬로 처리해야 하는 부분(공유 락, 단일 DB)이 상한을 정하고, 노드끼리 조율하는 비용은 노드가 늘수록 커져서 어느 지점부터는 늘릴수록 처리량이 줄어요.

    백엔드에서는 오토스케일링은 용량 계획을 대신하지 못해요. 새 인스턴스가 뜨고 준비되기까지 몇 분이 걸리고, 그동안은 기존 인스턴스가 버텨야 해요. 그리고 애플리케이션 서버를 늘리면 DB 커넥션 수도 같이 늘어요. 가장 늘리기 어려운 자원(보통 DB)이 전체의 상한이라는 것을 알고, 스케일 아웃의 최대치를 거기에 맞춰 정하세요.
    핵심 정리
    • 체류 시간 ∝ 1/(1−사용률). 80%를 넘으면 급격히 악화
    • 변동성이 대기를 키움. 느린 요청을 분리
    • 목표 사용률은 장애 시 남은 용량 기준. 직렬 구간이 확장의 상한
    셀프 체크
    1. 같은 처리 능력의 서버 4대가 있을 때, 서버별 큐 4개보다 공유 큐 1개가 나은 이유를 설명하세요.
    답 보기

    서버마다 큐를 따로 두면 요청이 어느 큐에 들어갔느냐에 따라 운이 갈려요. 한 서버가 오래 걸리는 요청을 처리하는 동안 그 큐의 요청들은 기다리는데, 옆 서버는 큐가 비어 놀고 있을 수 있어요. 공유 큐에서는 어느 서버든 비는 즉시 다음 요청을 가져가므로, 노는 서버가 있는 한 기다리는 요청이 없어요. 같은 자원으로 대기 시간이 줄고, 특히 처리 시간의 변동이 클수록 차이가 커져요.

    8장 벤치마크의 함정

    숫자는 쉽게 나오고, 맞는 숫자는 어렵다

    잘못 재는 방법들

    • 다른 것을 잼: 디스크 성능을 재려 했는데 전부 파일 캐시에서 읽혔다. DB 성능을 재려 했는데 클라이언트가 병목이었다.
    • 워밍업 없이 잼: 캐시가 비어 있고 JIT가 돌기 전의 숫자.
    • 너무 짧게 잼: 주기적으로 일어나는 일(GC, 체크포인트, 컴팩션)이 한 번도 포함되지 않음.
    • 한 번만 잼: 실행마다 편차가 있는데 그 크기를 모름. 5% 개선이 편차보다 작으면 개선이 아니에요.
    • 최적화가 지워 버림: 결과를 쓰지 않는 계산은 컴파일러가 없앨 수 있어요.
    • 평균만 보고함: 분포와 꼬리를 숨김.

    능동적으로 검증한다

    벤치마크를 돌리는 동안 시스템을 관찰해요. 지금 무엇이 한계를 정하고 있는지 USE로 확인하고, 그것이 재려던 대상이 맞는지 봐요. 숫자만 받아 적는 것은 벤치마크가 아니에요.

    환경의 잡음

    • 클라우드 인스턴스는 이웃과 자원을 나눠요. 같은 종류의 인스턴스도 시간에 따라, 인스턴스에 따라 달라요.
    • CPU 주파수 조절, 버스트 크레딧, 다른 프로세스.
    • 비교하려면 같은 기계에서 번갈아 여러 번 돌려요.

    남의 벤치마크 읽기

    제품 비교 벤치마크는 대개 만든 쪽이 유리한 워크로드와 설정으로 재요. 확인할 것: 워크로드가 우리와 닮았는가, 양쪽 다 제대로 튜닝했는가, 내구성 설정이 같은가(한쪽만 디스크 동기화를 끄지 않았는가), 꼬리 지연을 공개했는가.

    백엔드에서는 코드 수준의 미세 최적화를 할 때는 먼저 그것이 전체에서 얼마를 차지하는지 프로파일로 확인하세요. 전체의 2%인 함수를 두 배 빠르게 해도 1%예요. 그리고 개선을 주장하려면 운영과 비슷한 부하에서 전후를 같은 방법으로 여러 번 재고, 편차와 함께 제시해요.
    핵심 정리
    • 재려던 것을 재고 있는지 실행 중에 확인
    • 워밍업, 충분한 길이, 반복 실행, 편차 보고
    • 남의 벤치마크는 워크로드·튜닝·내구성 설정을 먼저 확인
    셀프 체크
    1. 두 DB의 쓰기 성능 비교에서 한쪽이 10배 빠르게 나왔습니다. 결과를 믿기 전에 무엇을 확인해야 하나요?
    답 보기

    가장 먼저 내구성 설정이 같은지 봐요. 한쪽은 커밋마다 디스크에 동기화하고 다른 쪽은 메모리에만 쓰고 응답했다면 서로 다른 것을 잰 거예요. 그다음으로 복제 설정과 일관성 수준이 같은지, 양쪽 모두 권장 설정으로 튜닝했는지, 데이터 크기가 메모리보다 큰지(작으면 디스크를 전혀 재지 않은 것), 워크로드의 읽기·쓰기 비율과 키 분포가 우리와 닮았는지, 측정 시간이 컴팩션이나 체크포인트 같은 주기적 작업을 포함할 만큼 길었는지를 확인해요.

    4부 개선

    9장 성능 개선의 순서

    가장 싼 것부터, 측정된 것만

    암달의 법칙

    전체 시간 중 일부만 빨라지면 전체 개선은 그 부분의 비중에 묶여요. 전체의 20%를 차지하는 부분을 아무리 빠르게 해도 전체는 최대 25% 빨라질 뿐이에요. 가장 큰 덩어리부터 줄여야 하고, 그러려면 덩어리의 크기를 먼저 재야 해요.

    개선의 위계

    위쪽일수록 효과가 크고 싸요.

    1. 하지 않는다: 필요 없는 작업을 없앤다. 안 쓰는 필드 조회, 중복 호출, 쓸모없는 로그.
    2. 덜 한다: 한 번 한 것을 다시 쓴다(캐시), 묶어서 한다(배치), 필요한 만큼만 한다(페이징, 지연 로딩).
    3. 나중에 한다: 응답에 필요 없는 일은 비동기로 넘긴다.
    4. 동시에 한다: 서로 독립적인 호출을 병렬로.
    5. 더 빠르게 한다: 알고리즘, 자료구조, 쿼리 계획.
    6. 자원을 더 쓴다: 서버를 늘리거나 키운다.

    백엔드에서 가장 흔한 원인

    • 왕복 횟수: 루프 안의 쿼리, 루프 안의 원격 호출. 한 번의 왕복은 빠르지만 수백 번이면 느려요.
    • 인덱스 없는 쿼리, 필요 이상의 행·컬럼 조회.
    • 직렬로 부르는 독립적인 외부 호출.
    • 풀 고갈: 느린 작업이 커넥션이나 스레드를 오래 쥠.
    • 큰 응답: 페이징 없는 목록, 압축 안 한 본문.

    작업 절차

    1. 목표를 숫자로 정한다. 목표가 없으면 끝이 없어요.
    2. 현재 값을 잰다(기준선).
    3. 가장 큰 덩어리를 찾는다(트레이스, 프로파일).
    4. 가설을 세우고 하나만 바꾼다.
    5. 같은 방법으로 다시 잰다. 효과가 없으면 되돌린다.
    6. 목표에 도달하면 멈춘다.
    백엔드에서는 느린 API를 받으면 분산 트레이스 하나를 먼저 여세요. 대부분 "같은 쿼리가 200번" 또는 "외부 호출 5개가 직렬"처럼 구조가 바로 보여요. 그 단계에서 해결되는 문제가 프로파일러까지 가야 하는 문제보다 훨씬 많아요. 캐시는 마지막에 꺼내세요. 캐시는 느린 쿼리를 없애지 않고 숨기며, 무효화라는 새 문제를 가져와요.
    시니어 심화
    • 성능 예산: 엔드포인트의 지연 목표를 구간별로 나눠 배정해요(DB 얼마, 외부 호출 얼마, 직렬화 얼마). 예산이 있으면 새 기능이 어디를 초과시켰는지 바로 보이고, 설계 단계에서 "이 호출을 추가할 여유가 있는가"를 물을 수 있어요.
    • 회귀는 배포 파이프라인에서 잡아요. 주요 경로의 지연과 쿼리 수를 자동으로 재서 기준에서 벗어나면 알려요. 요청당 쿼리 수 같은 결정적인 지표가 지연보다 잡음이 적어 자동 검사에 좋아요.
    • 처리량과 지연은 다른 최적화예요. 배치로 묶으면 처리량은 오르지만 개별 요청은 묶일 때까지 기다려요. 어느 쪽이 목표인지 먼저 정해요.
    핵심 정리
    • 암달의 법칙: 가장 큰 덩어리부터. 크기는 재서 안다
    • 하지 않기 → 덜 하기 → 나중에 → 동시에 → 빠르게 → 자원 추가
    • 목표 → 기준선 → 가설 하나 → 재측정. 캐시는 마지막
    셀프 체크
    1. 응답 시간 1초인 API에서 DB가 700ms, 직렬화가 100ms, 나머지가 200ms입니다. 직렬화를 10배 빠르게 하는 것과 DB 시간을 절반으로 줄이는 것 중 무엇이 효과가 큰가요?
    답 보기

    직렬화를 10배 빠르게 하면 100ms가 10ms가 되어 전체는 910ms, 9% 개선이에요. DB 시간을 절반으로 줄이면 700ms가 350ms가 되어 전체는 650ms, 35% 개선이에요. 개선 폭은 그 부분을 얼마나 빠르게 했느냐보다 그 부분이 전체에서 차지하는 비중에 좌우돼요. 그래서 구간별 시간을 먼저 재고 가장 큰 구간부터 손대야 해요.

    실습

    실습 과제

    일부러 느린 서비스를 만들고 원인을 절차대로 찾아보세요.

    • 1장 내 서비스의 자원 목록(OS 자원 + 풀·큐·락)을 적고, 각각의 사용률·포화·에러를 어떤 지표로 볼지 표로 채우기. 빈 칸 찾기
    • 2장 요청의 1%가 2초 걸리는 엔드포인트를 만들고 평균, p50, p99, 히스토그램을 비교. 20번 호출하는 클라이언트의 체감 지연 측정
    • 3장 CPU 포화, 메모리 부족, 디스크 I/O 포화를 각각 인위적으로 만들고 점검 목록의 어느 명령에서 드러나는지 기록
    • 4장 루프 안에서 정규식을 매번 컴파일하는 코드를 프로파일링하고 플레임 그래프에서 찾기. 고친 뒤 차분 그래프로 비교
    • 5장 커넥션 풀 크기를 2로 줄이고 부하를 줘서, 사용 중 게이지와 대기 시간 히스토그램이 각각 무엇을 보여주는지 비교
    • 6~7장 닫힌 모델과 열린 모델로 같은 서비스를 테스트. 열린 모델에서 도착률을 올리며 사용률 대비 지연 곡선 그리기
    • 9장 N+1 쿼리가 있는 API를 트레이스로 찾아 고치고, 요청당 쿼리 수를 검사하는 테스트 추가
