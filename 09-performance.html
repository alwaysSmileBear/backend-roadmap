    성능 분석

    기준 교재: 시스템 성능 분석(Systems Performance, Brendan Gregg) · 3~4주

    앞의 챕터들은 장마다 진단 명령어를 하나씩 소개했어요. 이 챕터는 그것들을 하나의 절차로 묶어요. "느리다"는 신고를 받았을 때 어디서부터 보고, 무엇을 재고, 어떻게 원인을 좁히는지예요.

    예시는 한 사건을 따라가요. 쇼핑몰의 주문 API가 느려졌다는 신고가 들어왔고, 그 원인을 찾아 고치기까지예요. 성능 작업에서 가장 흔한 실패는 도구를 모르는 것이 아니라 방법 없이 추측하는 것이에요. 1~2장의 방법론과 지연 분포를 먼저 읽으세요.

    1장 용어와 방법론

    추측하지 않고, 정해진 순서로 훑는다

    문제: "주문이 느려요"

    고객센터에서 "주문 버튼을 누르면 한참 걸린다"는 문의가 늘었다고 연락이 왔어요. 팀원 한 명은 "DB 같은데요", 다른 한 명은 "어제 배포 때문 아닐까요"라고 해요. 어디서부터 봐야 할까요?

    하지 말아야 할 방법

    흔한 실패가 세 가지 있어요. 자기가 아는 도구와 익숙한 지표만 보는 것(아는 곳에 원인이 없으면 못 찾아요), 설정을 하나씩 바꿔 보며 나아지길 기다리는 것(나아져도 이유를 모르고, 여러 개를 바꿔서 무엇이 효과였는지도 몰라요), 근거 없이 다른 팀의 문제라고 넘기는 것이에요. 셋 다 방법 없이 추측하는 거예요.

    먼저 용어를 맞춘다

    지연은 요청 하나가 걸린 시간이에요. 기다린 시간과 처리한 시간의 합이에요. 처리량은 단위 시간에 처리한 요청 수예요. 사용률은 자원이 바빴던 시간의 비율이고, 포화는 자원이 감당하지 못해 대기열에 쌓인 양이에요. 사용률이 100%가 아니어도 포화는 생겨요. 요청이 순간적으로 몰리면 평균 사용률 60%인 자원에서도 줄이 생겨요.

    두 방법을 이어 쓴다

    먼저 RED 방법으로 어느 서비스가 이상한지 찾아요. 서비스마다 초당 요청 수(Rate), 실패한 요청 수(Errors), 걸린 시간의 분포(Duration)를 봐요. 주문 API의 시간 분포가 나빠졌고, 주문 API가 부르는 재고 서비스는 정상이라면 범위가 주문 API로 좁혀져요.

    그다음 USE 방법으로 그 서비스의 어느 자원이 병목인지 찾아요. 모든 자원에 대해 사용률(Utilization), 포화(Saturation), 에러(Errors)를 차례로 확인해요. 자원은 CPU, 메모리, 디스크, 네트워크만이 아니에요. 커넥션 풀, 스레드풀, 락 같은 소프트웨어 자원도 포함해요. 핵심은 빠짐없이 훑는 거예요. 에러부터 보면 빨라요. 해석이 쉽고 원인을 바로 가리키는 경우가 많아요.

    이 사건에서는 주문 API 서버의 CPU, 메모리, 네트워크는 전부 한가했어요. 그런데 DB 커넥션 풀의 사용률이 100%였고, 커넥션을 기다리는 요청이 수십 개 쌓여 있었어요(포화). 범위가 "왜 커넥션이 반납되지 않는가"로 좁혀졌어요.

    백엔드에서는 커넥션 풀, 스레드풀, 세마포어에도 USE를 그대로 적용하세요. 풀의 사용률은 사용 중인 수 ÷ 최대 수, 포화는 기다리는 요청 수와 기다린 시간, 에러는 획득 타임아웃이에요. 운영체제 지표가 전부 한가한데 느리다면 대부분 이런 소프트웨어 자원이 포화된 거예요. 그래서 이 지표들은 처음부터 내보내 둬야 해요.
    시니어 심화 방법론보다 먼저 해야 하는 일이 문제를 정의하는 것이에요. "주문이 느려요"를 받으면 바로 지표를 열지 말고 다섯 가지를 먼저 물어요. 무엇이 느린가(주문 생성인가 주문 조회인가), 얼마나 느린가(평소 대비 몇 배인가), 누구에게 느린가(전체인가 특정 지역, 특정 회원인가), 언제부터인가, 그 무렵 무엇이 바뀌었는가(배포, 설정, 트래픽, 데이터).

    이 질문만으로 절반은 풀려요. "어제 오후 3시부터, VIP 회원만, 주문 조회가 느리다"면 VIP 회원은 주문 이력이 많다는 사실과 연결되고, 범위가 거의 정해져요. 그리고 USE 표를 실제로 만들어 보세요. 자원마다 세 칸을 어떤 지표로 채울지 적다 보면 측정하지 않고 있던 자원이 드러나요. "스레드풀 대기 시간"이나 "락 대기 시간" 칸이 비어 있다면, 다음 장애 때 그곳이 원인이어도 찾을 방법이 없어요. 빈 칸을 채우는 것이 다음 장애를 줄이는 일이에요.

    핵심 정리
    • 사용률 ≠ 포화. 대기열이 지연을 만듦
    • RED로 어느 서비스, USE로 어느 자원. 소프트웨어 자원도 자원
    • 추측과 무작위 변경 대신 정해진 순서로 빠짐없이
    셀프 체크
    1. CPU 사용률이 50%인데 요청 지연이 커졌습니다. 사용률만 보고 CPU 문제가 아니라고 결론 내릴 수 없는 이유는 무엇인가요?
    답 보기

    사용률은 일정 구간의 평균이라 그 안의 순간적인 몰림을 숨겨요. 1초 중 절반은 모든 코어가 꽉 차고 절반은 놀아도 평균은 50%예요. 꽉 찬 순간에는 실행을 기다리는 스레드가 쌓여 지연이 생겨요. 컨테이너라면 CPU 한도에 걸려 스로틀링되는 동안에도 사용률은 낮게 보일 수 있어요. 그래서 사용률과 함께 포화 지표(실행 대기열 길이, 스로틀링 시간)를 봐야 해요.

    2장 지연 분포와 백분위

    평균은 아무도 겪지 않는 숫자다

    문제: 대시보드는 정상인데 고객은 느리다고 한다

    주문 API의 평균 응답 시간은 45ms로 평소와 비슷했어요. 그런데 고객 문의는 계속 늘었어요. 대시보드가 틀린 걸까요, 고객이 틀린 걸까요?

    평균이 숨기는 것

    요청 99개가 10ms, 1개가 3초 걸리면 평균은 약 40ms예요. 대시보드는 건강해 보이지만 100명 중 1명은 3초를 기다렸어요. 응답 시간은 대부분 빠르고 일부가 아주 느린, 한쪽으로 긴 꼬리를 가진 분포라서 평균이 대표값 구실을 못 해요.

    그래서 백분위를 봐요. p50은 절반의 요청이 이보다 빨랐다는 값(중앙값), p99는 99%가 이보다 빨랐다는 값, 즉 100번 중 가장 느린 1번이에요.

    꼬리가 생각보다 자주 보인다

    "100번에 1번이면 드문 일 아닌가" 싶지만, 사용자는 요청을 한 번만 보내지 않아요. 주문 화면 하나가 API를 20번 부르면, 20번 모두 p99보다 빠를 확률은 0.99를 20번 곱한 약 82%예요. 사용자 다섯 명 중 한 명은 그 화면에서 p99 지연을 겪어요. 그리고 꼬리 지연을 겪는 요청은 대개 주문 이력이 많은, 즉 가장 많이 사는 고객의 요청이에요.

    분포를 직접 본다

    백분위 몇 개보다 히스토그램(응답 시간 구간마다 요청이 몇 개였는지)이 더 많은 것을 알려줘요.

    이 사건의 히스토그램에는 봉우리가 두 개 있었어요. 대부분의 요청은 10ms 근처에 모여 있고, 일부가 300ms 근처에 따로 모여 있었어요. 봉우리가 둘이라는 것은 서로 다른 두 경로가 섞여 있다는 뜻이에요. 확인해 보니 상품 정보가 캐시에 있으면 빠른 경로, 캐시에 없으면 DB를 거치는 느린 경로였어요. 평균을 줄이려 애쓸 것이 아니라 느린 봉우리가 왜 커졌는지를 찾으면 돼요.

    백엔드에서는 응답 시간은 성공과 실패를 나눠서 재세요. 에러가 빠르게 반환되면 전체 응답 시간이 좋아진 것처럼 보여요. DB가 죽어서 모든 요청이 5ms 만에 에러로 끝나면 대시보드의 응답 시간은 역대 최고가 돼요. 그리고 응답 시간 대시보드에는 평균 대신 p50, p99, 최댓값을 함께 두세요.
    시니어 심화 백분위를 잘못 계산하는 흔한 실수가 백분위의 평균이에요. 주문 API 서버 10대가 각자 계산한 p99를 평균 내면 전체의 p99가 되지 않아요. 한 대만 느려서 그 서버의 p99가 2초이고 나머지가 100ms라면, 평균은 약 290ms로 보이지만 실제 전체 p99는 그보다 훨씬 나빠요.

    그래서 각 서버는 백분위를 계산하지 말고 히스토그램의 구간별 개수를 내보내고, 수집 시스템이 구간별로 합친 뒤에 백분위를 계산해야 해요. 이때 정밀도는 구간 경계가 정해요. 목표가 300ms인데 구간이 100ms 다음 500ms라면 300ms를 지켰는지 알 수 없어요. 목표값 주변에 경계를 촘촘하게 두세요. 마지막으로 꼬리를 줄이는 기법도 있어요. 일정 시간 안에 응답이 없으면 다른 서버에 같은 요청을 한 번 더 보내고 먼저 온 응답을 쓰는 방식(헤지 요청)이에요. 부하는 조금 늘지만 p99가 크게 줄어요. 여러 번 보내도 안전한 조회 요청에만 써요.

    핵심 정리
    • 응답 시간은 긴 꼬리 분포. 평균이 아니라 백분위로
    • 요청이 많을수록 꼬리를 겪는 사용자가 늘어남
    • 히스토그램의 봉우리가 둘이면 경로가 둘. 백분위는 평균 낼 수 없음
    셀프 체크
    1. 서비스 A가 요청마다 하위 서비스 10개를 동시에 호출하고 전부 기다립니다. 각 하위 서비스의 p99가 100ms일 때 A의 지연에 대해 무엇을 말할 수 있나요?
    답 보기

    하위 호출 10개가 모두 100ms 안에 끝날 확률은 0.99를 10번 곱한 약 90%예요. 즉 A의 요청 10개 중 1개는 적어도 하나의 하위 호출이 100ms를 넘겨요. 하위 서비스에서 100번에 1번 일어나는 일이 A에서는 10번에 1번 일어나는 거예요. 동시에 부르는 하위 서비스가 많을수록 그들의 꼬리 지연이 상위 서비스의 평범한 지연이 되므로, 하위 서비스는 p99보다 더 높은 백분위를 관리해야 해요.

    2부 관찰

    3장 리눅스 서버 첫 점검

    서버에 들어가서 처음 1분 동안 볼 것

    문제: 서버에 들어왔는데 무엇부터 칠지 모르겠다

    주문 API 서버 한 대만 유독 느리다는 것을 찾았어요. 그 서버에 접속했는데, 습관처럼 top만 열고 한참 들여다보다 시간이 흘러요. top은 많은 것을 보여주지만 원인을 가리켜 주지는 않아요.

    정해진 순서로 훑는다

    1장의 USE를 서버 자원에 적용한 점검 순서가 있어요. 각 명령은 몇 초면 끝나고, 순서대로 보면 1분 안에 대부분의 자원 문제가 드러나요.

    uptime의 로드 애버리지는 1분, 5분, 15분 평균이에요. 1분 값이 15분 값보다 크면 상황이 나빠지는 중이에요. dmesg의 커널 메시지에는 OOM으로 죽은 프로세스, 디스크나 네트워크 하드웨어 에러가 남아요. 여기서 답이 나오는 경우가 생각보다 많아요. vmstat 1은 1초마다 실행 대기 중인 프로세스 수(r), 스왑 입출력(si, so), CPU 시간의 분해를 보여줘요. r이 코어 수보다 계속 크면 CPU 포화예요. mpstat -P ALL 1로 코어별로 보면 한 코어만 100%인 경우(단일 스레드 병목)가 드러나요. iostat -xz 1은 디스크별 대기 시간과 대기열 길이, sar -n DEV 1과 sar -n TCP,ETCP 1은 네트워크 처리량과 TCP 재전송을 보여줘요.

    CPU 시간을 나눠서 읽는다

    CPU 사용률은 하나의 숫자가 아니에요. us(사용자)가 높으면 애플리케이션 코드가 CPU를 쓰는 것이니 프로파일러로 가요(4장). sy(시스템)가 높으면 커널이 바쁜 것이니 시스템 호출이나 네트워크 처리가 많은 거예요. wa(I/O 대기)는 CPU는 놀고 있지만 디스크를 기다리는 작업이 있다는 뜻이고, st(steal)는 가상 머신에서 같은 물리 서버의 다른 가상 머신에게 CPU를 빼앗긴 시간이에요. st가 높으면 우리 코드로는 고칠 수 없어요.

    메모리는 available을 본다

    free의 free 값이 작다고 메모리가 부족한 것이 아니에요. 리눅스는 남는 메모리를 파일 캐시로 써서 free는 항상 작게 보여요. 필요하면 비워 줄 수 있는 캐시까지 포함한 available을 보세요.

    이 사건에서는 vmstat의 st가 30% 가까이 나왔어요. 그 서버만 이웃 가상 머신에게 CPU를 빼앗기고 있었던 거예요. 인스턴스를 교체해서 해결했어요.

    백엔드에서는 컨테이너 안에서 이 명령들을 실행하면 대부분 호스트 전체의 값이 보여요. 컨테이너의 실제 한도와 사용량은 cgroup 파일(cpu.stat의 스로틀링 횟수, memory.current, memory.events의 OOM 횟수)이나 쿠버네티스 메트릭에서 봐야 해요. 호스트에 CPU가 남아도 컨테이너는 한도에 걸려 스로틀링 중일 수 있어요.
    시니어 심화 이 점검표에는 두 가지 사각지대가 있어요. 첫째는 짧게 사는 프로세스예요. 위 명령들은 몇 초마다 그 순간의 모습을 보는 방식이라, 0.1초 만에 떴다 사라지는 프로세스는 거의 잡히지 않아요. 헬스 체크 스크립트가 초당 수백 번 외부 명령을 실행하며 CPU를 다 쓰고 있어도 top에는 아무것도 안 보이고 CPU 사용률만 높아요. 프로세스 생성을 추적하는 도구(execsnoop 같은 eBPF 도구)로 찾아요.

    둘째는 1초 안의 일이에요. 1초 간격 지표도 결국 1초 평균이라, 50ms짜리 멈춤 여러 번은 평균에 묻혀요. 꼬리 지연의 원인을 찾을 때는 이벤트 하나하나를 기록하는 도구(perf, eBPF 기반 도구)가 필요해요. 그리고 점검 순서를 스크립트로 만들어 장애 때 한 번에 수집하세요. 장애 중에 명령어를 기억해 내며 하나씩 치는 것은 느리고, 나중에 정상 때와 비교할 기록도 남지 않아요.

    핵심 정리
    • 에러 → 포화 → 사용률 순으로 정해진 목록을 훑음
    • CPU는 us/sy/wa/st로 나눠 읽음. 메모리는 available
    • 컨테이너 안에서는 cgroup 지표가 실제 값
    셀프 체크
    1. vmstat에서 r 값이 코어 수보다 훨씬 큰데 us+sy는 30%입니다. 어떤 상황을 의심할 수 있나요?
    답 보기

    실행하려는 스레드는 많은데 CPU는 다 쓰이지 않는 모순된 상태예요. 컨테이너의 CPU 한도에 걸려 스로틀링 중이면, 스레드는 실행 대기로 쌓이지만 한도 때문에 CPU를 더 못 써서 사용률이 낮게 나와요. 가상 머신에서 steal 시간이 높은 경우도 비슷하게 보여요. 또는 컨테이너 안에서 호스트 전체 기준의 지표를 보고 있어서 다른 컨테이너의 대기열이 섞여 보이는 것일 수도 있어요. cgroup의 스로틀링 통계와 st 값을 확인해요.

    4장 프로파일링과 플레임 그래프

    CPU 시간이 코드의 어디에서 쓰이는가

    문제: CPU가 높은데 어느 코드인지 모른다

    배포 후 주문 API 서버의 CPU 사용률이 30%에서 70%로 올랐어요. 3장의 점검에서 us(애플리케이션 코드)가 높다는 것까지 확인했어요. 이번 배포에는 수십 개의 변경이 들어 있어요. 어느 코드가 CPU를 쓰는지 어떻게 찾을까요?

    샘플링 프로파일러

    프로파일러는 초당 수십에서 수백 번, 실행 중인 스레드가 지금 어떤 함수 호출 경로 위에 있는지(호출 스택)를 기록해요. 어떤 함수가 기록에 많이 잡혔다면 그 함수에서 시간을 많이 썼다는 뜻이에요. 모든 호출을 기록하는 대신 표본만 뜨기 때문에 부하가 작아서 운영 서버에서도 쓸 수 있어요.

    플레임 그래프 읽는 법

    수천 개의 호출 스택 기록을 한 그림으로 합친 것이 플레임 그래프예요.

    세로는 호출 경로예요. 아래가 호출한 쪽, 위가 호출된 쪽이에요. 가로 폭은 그 함수가 기록에 잡힌 비율이에요. 가로축은 시간 순서가 아니에요. 이름순으로 정렬돼 있을 뿐이에요. 폭이 넓을수록 시간을 많이 쓴 것이고, 특히 맨 위에 평평하게 넓게 드러난 부분이 실제로 CPU를 태우는 함수예요. 그 아래는 거기까지 오는 길이에요.

    이 사건의 그래프에서는 할인 계산 함수 위에 Pattern.compile이 넓게 드러나 있었어요. 새로 추가된 쿠폰 코드 검증이 요청마다 정규식을 새로 컴파일하고 있었던 거예요. 정규식을 한 번만 컴파일해 상수로 두니 CPU가 원래대로 돌아왔어요.

    CPU가 깨끗한데 느리면

    CPU 프로파일은 CPU를 쓰는 동안만 기록해요. 요청이 DB 응답이나 락을 기다리는 시간은 나오지 않아요. 응답은 느린데 CPU 프로파일에 특별한 것이 없다면, 그 요청은 기다리고 있는 거예요. 기다리는 시간까지 포함하는 벽시계 프로파일, 락 대기를 보여주는 락 프로파일로 바꿔야 해요. 메모리 할당이 많은 코드를 찾는 할당 프로파일도 있어요. GC가 잦을 때 써요.

    백엔드에서는 프로파일에서 자주 나오는 범인은 업무 로직이 아니에요. JSON 직렬화, 로깅(로그 레벨이 꺼져 있어도 인자로 넘길 문자열을 미리 조립하는 비용, 예외 스택 생성), 정규식 컴파일, 리플렉션, 그리고 반복문 안에서 매번 새로 만드는 객체예요. 비싼 로그 인자는 log.debug("{}", obj)처럼 자리 표시자로 넘겨 실제로 출력할 때만 문자열을 만들게 하세요.
    시니어 심화 프로파일은 "가장 느린 함수"가 아니라 "총합이 큰 함수"를 보여줘요. 한 번에 0.5ms밖에 안 걸리지만 요청마다 400번 불리는 함수가 맨 위에 나와요. 이때 답은 그 함수를 빠르게 하는 것이 아니라 덜 부르는 것인 경우가 많아요. 할인 계산을 주문 항목마다 반복하는 대신 한 번 계산해서 재사용하는 식이에요.

    그리고 성능 문제의 대부분은 어느 날 갑자기가 아니라 여러 배포에 걸쳐 조금씩 나빠진 거예요. 배포마다 2%씩 느려지면 아무도 알아채지 못하다가 반년 뒤에 두 배가 돼요. 운영에서 낮은 비율로 프로파일을 항상 수집해 두면(연속 프로파일링), 배포 전후의 그래프를 겹쳐 차이만 보여주는 차분 플레임 그래프로 어느 배포의 어느 함수가 늘었는지 바로 찾을 수 있어요. 문제가 재현되기를 기다리지 않아도 돼요.

    핵심 정리
    • 샘플링 = 주기적으로 호출 스택 기록. 부하가 작아 운영에서도 가능
    • 플레임 그래프: 폭 = 비율, 가로축은 시간이 아님. 맨 위 넓은 곳이 범인
    • CPU가 깨끗한데 느리면 벽시계·락 프로파일로
    셀프 체크
    1. 플레임 그래프에서 어떤 함수의 폭이 전체의 40%입니다. 이 함수 자체가 느리다고 결론 내릴 수 있나요?
    답 보기

    아니요. 폭은 그 함수와 그 함수가 호출한 모든 것을 합친 시간이에요. 그 함수 바로 위에 다른 함수들이 폭을 대부분 채우고 있다면 시간은 위쪽 함수들에서 쓰인 거예요. 그 함수 자체가 쓴 시간은 위에 아무것도 없이 드러난 부분뿐이에요. 또 폭이 넓은 이유가 한 번의 실행이 느려서인지, 아주 많이 불려서인지도 그래프만으로는 구분되지 않아요.

    5장 계측 설계

    문제가 났을 때 답할 수 있도록 미리 심어 둔다

    문제: 장애 때 필요한 지표가 없었다

    1장의 사건에서 DB 커넥션 풀이 포화된 것까지는 찾았어요. 그런데 "커넥션을 얻기까지 얼마나 기다렸는지", "어느 API가 커넥션을 오래 쥐고 있었는지"를 보려 하니 그런 지표가 없었어요. 장애가 끝난 뒤에 계측을 추가해 봐야 지나간 장애는 다시 볼 수 없어요.

    무엇을 계측하나

    규칙은 단순해요. 서비스 경계를 넘는 모든 곳에 같은 세 가지를 심어요. 호출 수, 실패 수, 걸린 시간의 분포예요. 들어오는 요청(엔드포인트별), 나가는 호출(DB 쿼리, 캐시, 외부 API, 메시지 발행과 소비), 그리고 풀과 큐(사용 중인 수, 기다리는 수, 기다린 시간)예요. 2장에서 본 것처럼 시간은 평균이 아니라 히스토그램으로 남겨요.

    게이지의 함정

    메트릭에는 늘어나기만 하는 누적값(카운터), 지금 값(게이지), 값의 분포(히스토그램)가 있어요. 게이지는 수집하는 순간의 값만 남겨요. 15초마다 "사용 중인 커넥션 수"를 읽으면, 그 사이에 꽉 찼다가 풀린 것은 기록에 남지 않아요. 그 순간에 기다린 요청들은 지연을 겪었는데 지표에는 흔적이 없어요. 그래서 포화를 보려면 게이지와 함께 커넥션을 얻기까지 기다린 시간의 히스토그램을 남겨야 해요. 요청마다 기록되니 짧은 고갈도 꼬리로 드러나요.

    레이블은 종류가 한정된 값만

    메트릭에 레이블(엔드포인트, 상태 코드, 호출 대상)을 붙이면 나눠서 볼 수 있어요. 그런데 레이블 값의 조합 하나하나가 별도의 시계열이 돼요. 회원 ID나 주문 번호를 레이블로 넣으면 시계열이 끝없이 늘어 모니터링 시스템이 먼저 죽어요. URL도 /orders/1042가 아니라 /orders/{id}처럼 경로 틀로 넣어요.

    세 신호를 같은 ID로 잇는다

    메트릭은 무엇이 얼마나 이상한지 알려줘요. 싸고 오래 보관할 수 있어요. 트레이스는 요청 하나가 어느 구간에서 시간을 썼는지 보여줘요. 로그는 그 순간 정확히 무슨 일이 있었는지 알려줘요. 셋이 같은 요청 ID(트레이스 ID)로 이어져 있어야 "p99가 튀었다 → 그 시각의 느린 트레이스를 연다 → 그 요청의 로그를 읽는다"로 몇 분 안에 원인에 닿아요.

    백엔드에서는 스프링 부트라면 Micrometer가 HTTP 요청, HikariCP 커넥션 풀(대기 시간 포함), JVM 지표를 기본으로 내보내요. 히스토그램은 설정으로 켜야 하는 경우가 많으니 확인하세요. 트레이스는 OpenTelemetry로 수집하고, 로그 패턴에 트레이스 ID를 넣어 두면 셋이 이어져요.
    시니어 심화 알람은 원인이 아니라 증상에 거세요. "CPU 80% 초과" 알람은 사용자에게 아무 문제가 없을 때도 울리고(배치가 돌 때), 사용자가 겪는 문제 중 CPU와 무관한 것(커넥션 풀 고갈, 외부 API 지연)은 놓쳐요. 알람이 자주 헛울리면 사람들은 알람을 무시하게 되고, 진짜 장애 때도 무시해요.

    사용자가 겪는 것, 즉 에러율과 응답 시간에 알람을 걸고, 자원 지표는 원인을 찾을 때 봐요. 더 나아가 목표(SLO, 예: "30일 동안 요청의 99.9%가 300ms 안에 성공")를 정하고, 그 목표를 얼마나 빠르게 갉아먹고 있는지(오류 예산 소진 속도)에 알람을 걸면, 잠깐의 튐에는 울리지 않고 지속적인 악화에는 빨리 울려요. 그리고 계측 자체의 비용도 재세요. 요청마다 스팬 수십 개와 로그 수십 줄을 남기면 그것이 지연과 저장 비용의 큰 부분이 돼요. 트레이스는 에러와 느린 요청을 우선 남기는 방식으로 샘플링해요.

    핵심 정리
    • 모든 경계에 호출 수·실패 수·시간 분포. 풀과 큐는 대기 시간까지
    • 게이지는 순간만 봄. 포화는 대기 시간 히스토그램으로. 레이블은 종류가 한정된 값만
    • 메트릭 → 트레이스 → 로그를 같은 ID로 연결
    셀프 체크
    1. 커넥션 풀의 "사용 중인 커넥션 수" 게이지만으로는 풀 고갈을 놓칠 수 있는 이유를 설명하세요.
    답 보기

    게이지는 수집하는 순간의 값만 남겨요. 풀이 수집 주기 사이에 잠깐 가득 찼다가 풀리면 기록에는 여유 있는 값만 남아요. 그 짧은 순간에 커넥션을 기다린 요청들은 지연을 겪었지만 지표에는 흔적이 없어요. 커넥션을 얻기까지 기다린 시간을 히스토그램으로 남기면, 요청마다 기록되므로 순간적인 고갈도 대기 시간 분포의 꼬리로 드러나요.

    3부 실험

    6장 부하 테스트 설계

    테스트 방식이 답할 수 있는 질문을 정한다

    문제: 부하 테스트를 통과했는데 행사 날 무너졌다

    할인 행사 전에 부하 테스트를 했어요. 가상 사용자 500명이 주문을 반복하게 했더니 응답이 조금 느려지긴 했지만 에러 없이 버텼어요. 그런데 행사 당일 실제 트래픽은 그보다 적었는데도 서버가 무너졌어요. 테스트가 무엇을 놓쳤을까요?

    두 가지 부하 모델

    닫힌 모델은 가상 사용자 N명이 "요청 → 응답 기다림 → 다음 요청"을 반복하는 방식이에요. 서버가 느려지면 응답이 늦게 오니 다음 요청도 늦게 보내요. 서버가 느려질수록 부하가 저절로 줄어요. 위 테스트가 이 방식이었어요. 서버가 스스로 부하를 조절한 셈이라 진짜 과부하 상태에 가지 않았어요.

    열린 모델은 서버 상태와 무관하게 초당 N개씩 정해진 속도로 보내는 방식이에요. 실제 인터넷 트래픽은 이쪽에 가까워요. 서버가 느려도 새 고객은 같은 속도로 계속 들어오고, 기다리다 지친 고객은 새로고침을 눌러 요청을 더 보내요.

    무엇을 알고 싶은지에 따라 모양이 다르다

    테스트방법답하는 질문
    부하예상 최대 트래픽을 일정 시간 유지목표를 지키는가
    스트레스한계를 넘을 때까지 계속 올림어디서, 어떻게 무너지는가
    스파이크갑자기 몇 배로 올렸다가 내림급증을 견디고 회복하는가
    지속보통 부하를 몇 시간에서 며칠누수나 서서히 나빠지는 것이 있는가

    현실과 맞춘다

    데이터 크기를 맞춰요. 상품 100개짜리 테스트 DB에서 빠른 쿼리가 상품 300만 개에서는 실행 계획이 달라요. 요청 분포도 맞춰요. 같은 상품만 반복 조회하면 전부 캐시에 맞아서 DB는 쉬고 있어요. 실제처럼 일부 인기 상품에 몰리고 나머지는 드문드문 조회되게 해요. 시작 직후의 워밍업 구간은 결과에서 빼요.

    결과는 숫자가 아니라 병목이다

    도착률을 단계적으로 올리면서 처리량과 응답 시간을 함께 그리면, 처리량이 더 늘지 않고 응답 시간만 오르기 시작하는 지점이 보여요. 그 지점에서 무엇이 포화됐는지를 1장의 USE로 찾는 것이 부하 테스트의 진짜 결과예요. "초당 800건까지 버팀"이 아니라 "초당 800건에서 DB 커넥션 풀이 포화됨"이 결과예요.

    백엔드에서는 부하 생성기 자체가 병목이 되는 경우가 많아요. 생성기 서버의 CPU가 꽉 차면 서버가 느린 것처럼 보여요. 생성기의 자원 지표도 같이 보고, 필요하면 여러 대로 나눠요. 결제처럼 실제로 호출하면 안 되는 외부 API는 가짜 서버로 바꾸되, 가짜도 실제와 비슷한 응답 시간을 갖게 하세요. 즉시 응답하는 가짜는 스레드와 커넥션을 쥐는 시간을 비현실적으로 짧게 만들어서 결과를 좋게 왜곡해요.
    시니어 심화 스트레스 테스트에서 진짜 봐야 하는 것은 한계 너머의 모습이에요. 두 가지를 확인하세요.

    첫째, 한계를 넘었을 때 처리량이 유지되는가예요. 건강한 시스템은 한계를 넘는 부분만 빠르게 거절하고, 처리할 수 있는 만큼은 계속 처리해요. 건강하지 않은 시스템은 처리량 자체가 무너져요. 큐에 쌓인 요청들이 메모리를 채우고, 클라이언트가 이미 포기한 요청을 뒤늦게 처리하느라 정작 새 요청을 못 받아요. 둘째, 부하를 정상으로 되돌렸을 때 회복하는가예요. 밀린 큐, 계속되는 재시도, 비어 버린 캐시 때문에 부하가 줄어도 원래 상태로 돌아오지 않는 시스템이 있어요(준안정 장애). 부하를 내린 뒤 응답 시간이 정상으로 돌아오기까지 걸리는 시간을 재고, 돌아오지 않는다면 부하 차단과 재시도 제한이 빠진 거예요.

    핵심 정리
    • 닫힌 모델은 서버가 느려지면 부하도 줄어 과부하를 재현 못 함. 열린 모델(도착률 고정)로
    • 부하·스트레스·스파이크·지속 테스트는 답하는 질문이 다름
    • 데이터 크기와 요청 분포를 운영과 맞춤. 한계 지점에서 무엇이 포화됐는지가 결과
    셀프 체크
    1. 가상 사용자 100명으로 테스트했더니 서버가 느려져도 에러 없이 버텼습니다. 이 결과로 "과부하에 안전하다"고 할 수 없는 이유는 무엇인가요?
    답 보기

    가상 사용자 방식은 응답을 받아야 다음 요청을 보내므로, 서버가 느려지면 들어오는 요청도 같이 줄어요. 서버가 스스로 부하를 조절하는 셈이라 진짜 과부하 상태에 도달하지 않아요. 실제로는 서버가 느려져도 새 사용자가 같은 속도로 계속 도착하고, 기다리다 지친 사용자가 재시도까지 해서 부하가 오히려 늘어요. 초당 도착률을 고정한 방식으로 처리 능력을 넘는 부하를 줘 봐야 과부하 때의 동작을 알 수 있어요.

    7장 큐잉 이론과 용량 계획

    왜 사용률 80%에서 갑자기 느려지는가

    문제: 20%나 남았는데 느리다

    주문 API 서버의 CPU 사용률이 80%였어요. 아직 20% 여유가 있다고 생각했는데, 응답 시간은 평소의 다섯 배였어요. 사용률과 응답 시간은 왜 비례하지 않을까요?

    대기는 사용률에 비례하지 않는다

    요청이 고르게 일정한 간격으로 온다면 사용률 99%까지도 기다림이 없어요. 하지만 실제 요청은 불규칙하게 와요. 평균적으로는 감당할 수 있어도 어떤 순간에는 몰려서 줄이 생겨요. 서버가 하나인 가장 단순한 모델에서 요청이 머무는 평균 시간은 이렇게 돼요.

    머무는 시간 = 처리 시간 ÷ (1 - 사용률)

      사용률 50% → 처리 시간의 2배
      사용률 80% → 5배
      사용률 90% → 10배
      사용률 95% → 20배

    사용률이 100%에 다가갈수록 머무는 시간은 끝없이 커져요. 80%에서는 "20% 남았다"가 아니라 "이미 곡선의 무릎을 지났다"예요. 위 문제의 다섯 배가 정확히 이 숫자예요.

    변동이 클수록 줄이 길다

    같은 평균 처리 시간이라도, 가끔 아주 오래 걸리는 요청이 섞이면 줄이 훨씬 길어져요. 대부분 10ms인데 가끔 2초짜리 주문 이력 조회가 끼면, 그 뒤의 요청들이 전부 2초를 기다려요. 그래서 느린 요청을 따로 떼어 처리하는 것(별도 스레드풀, 별도 큐)이 전체 응답 시간을 줄여요.

    줄은 하나로 서는 것이 낫다

    같은 처리 능력이라면, 서버마다 따로 줄을 세우는 것보다 줄 하나를 여러 서버가 나눠 처리하는 쪽이 기다림이 짧아요. 따로 줄을 세우면 한 서버에는 줄이 있는데 옆 서버는 노는 상황이 생기기 때문이에요. 마트 계산대의 줄이 하나로 바뀌는 것과 같은 이유예요.

    용량 계획

    먼저 부하를 대표하는 지표(초당 주문 수)를 정하고, 그 지표와 자원 사용량의 관계를 측정해요. 그다음 부하가 얼마나 늘지 예측하고(추세와 예정된 행사), 목표 사용률을 정해 필요한 자원을 계산해요. 목표 사용률은 위 곡선에서 응답 시간 목표를 지키는 지점이면서, 서버 일부가 죽어도 남은 서버가 그 사용률을 넘지 않는 수준이어야 해요. 가용 영역 세 곳에 나눠 두었다면 두 곳만으로 최대 부하를 받을 수 있어야 해요.

    서버를 늘려도 끝이 있다

    서버를 두 배로 늘려도 처리량이 두 배가 되지 않아요. 모두가 거쳐야 하는 부분(DB 하나, 공유 락 하나)이 상한을 정하고, 서버끼리 맞춰야 하는 비용은 서버가 늘수록 커져서, 어느 지점부터는 늘릴수록 오히려 처리량이 줄어요.

    백엔드에서는 오토스케일링은 용량 계획을 대신하지 못해요. 새 인스턴스가 뜨고 워밍업을 마치기까지 몇 분이 걸리고, 그동안은 기존 인스턴스가 버텨야 해요. 그리고 애플리케이션 서버를 늘리면 DB 커넥션 수도 같이 늘어요. 가장 늘리기 어려운 자원(대개 DB)이 전체의 상한이라는 것을 알고, 서버를 몇 대까지 늘릴 수 있는지를 거기서 거꾸로 계산하세요.
    핵심 정리
    • 머무는 시간 ∝ 1/(1−사용률). 80%를 넘으면 급격히 악화
    • 변동이 대기를 키움. 느린 요청을 분리. 줄은 하나로
    • 목표 사용률은 장애 때 남은 용량 기준. 모두가 거치는 부분이 확장의 상한
    셀프 체크
    1. 같은 처리 능력의 서버 4대가 있을 때, 서버별 줄 4개보다 공유 줄 1개가 나은 이유를 설명하세요.
    답 보기

    서버마다 줄을 따로 두면 요청이 어느 줄에 섰느냐에 따라 운이 갈려요. 한 서버가 오래 걸리는 요청을 처리하는 동안 그 줄의 요청들은 기다리는데, 옆 서버는 줄이 비어 놀고 있을 수 있어요. 공유 줄에서는 어느 서버든 비는 즉시 다음 요청을 가져가므로, 노는 서버가 있는 한 기다리는 요청이 없어요. 같은 자원으로 기다리는 시간이 줄고, 처리 시간의 변동이 클수록 차이가 커져요.

    8장 벤치마크의 함정

    숫자는 쉽게 나오고, 맞는 숫자는 어렵다

    문제: 새 JSON 라이브러리가 3배 빠르다는데

    팀원이 JSON 라이브러리를 바꾸자고 제안하면서 벤치마크 결과를 가져왔어요. 반복문으로 주문 객체를 백만 번 직렬화했더니 새 라이브러리가 세 배 빠르다는 거예요. 바꿨더니 운영 서버의 응답 시간은 거의 그대로였어요. 무엇이 틀렸을까요?

    잘못 재는 방법들

    다른 것을 쟀을 수 있어요. 반복문에서 같은 객체를 백만 번 직렬화하면 그 객체는 캐시에 머물러 있고, JIT는 결과를 쓰지 않는 계산을 지워 버릴 수도 있어요. 디스크 성능을 재려 했는데 전부 파일 캐시에서 읽히는 경우, DB를 재려 했는데 부하 생성기가 병목인 경우도 같은 실수예요.

    워밍업 없이 쟀을 수 있어요. 처음 몇 초는 인터프리터로 돌고 캐시가 비어 있어요. 너무 짧게 쟀을 수 있어요. 주기적으로 일어나는 일(GC, DB 체크포인트, 컴팩션)이 한 번도 포함되지 않아요. 한 번만 쟀을 수 있어요. 실행마다 결과가 5% 흔들리는데 개선이 5%라면 개선인지 알 수 없어요. 그리고 평균만 보고했다면 꼬리 지연이 가려져요.

    그리고 가장 근본적인 이유가 있었어요. 4장의 플레임 그래프로 보면 직렬화는 주문 API 전체 시간의 4%였어요. 4%를 세 배 빠르게 해도 전체는 3% 남짓 빨라질 뿐이에요(9장).

    측정하는 동안 관찰한다

    벤치마크를 돌리는 동안 시스템을 관찰하세요. 지금 무엇이 한계를 정하고 있는지 1장의 USE로 확인하고, 그것이 재려던 대상이 맞는지 봐요. CPU가 100%가 아닌데 처리량이 멈췄다면 어딘가 다른 곳(락, 네트워크, 생성기)이 한계예요. 숫자만 받아 적는 것은 벤치마크가 아니에요.

    환경의 잡음

    클라우드 인스턴스는 이웃과 자원을 나눠 써서 같은 종류의 인스턴스도 시간과 장소에 따라 성능이 달라요. CPU 클록 조절, 디스크의 버스트 크레딧도 결과를 흔들어요. 두 버전을 비교한다면 같은 기계에서 번갈아 여러 번 돌려요.

    남의 벤치마크 읽기

    제품 비교 벤치마크는 대개 만든 쪽이 유리한 조건으로 재요. 워크로드가 우리와 닮았는지, 양쪽 모두 제대로 튜닝했는지, 내구성 설정이 같은지(한쪽만 디스크 동기화를 끄지 않았는지), 꼬리 지연을 공개했는지를 먼저 확인하세요.

    백엔드에서는 코드 수준의 미세한 최적화를 하기 전에 그 코드가 전체에서 몇 퍼센트인지 프로파일로 먼저 확인하세요. 그리고 개선을 주장하려면 운영과 비슷한 부하에서 전후를 같은 방법으로 여러 번 재고, 흔들림의 폭과 함께 보여주세요. 자바 코드의 마이크로 벤치마크는 워밍업과 최적화 제거 문제를 처리해 주는 JMH로 하세요.
    핵심 정리
    • 재려던 것을 재고 있는지 실행 중에 확인(USE)
    • 워밍업, 충분한 길이, 반복 실행, 흔들림 폭 보고. 전체 대비 비중 먼저
    • 남의 벤치마크는 워크로드·튜닝·내구성 설정을 먼저 확인
    셀프 체크
    1. 두 DB의 쓰기 성능 비교에서 한쪽이 10배 빠르게 나왔습니다. 결과를 믿기 전에 무엇을 확인해야 하나요?
    답 보기

    가장 먼저 내구성 설정이 같은지 봐요. 한쪽은 커밋마다 디스크에 동기화하고 다른 쪽은 메모리에만 쓰고 응답했다면 서로 다른 것을 잰 거예요. 그다음 복제와 일관성 설정이 같은지, 양쪽 모두 권장 설정으로 튜닝했는지, 데이터 크기가 메모리보다 커서 디스크를 실제로 썼는지, 읽기·쓰기 비율과 키 분포가 우리 워크로드와 닮았는지, 측정 시간이 체크포인트나 컴팩션 같은 주기적 작업을 포함할 만큼 길었는지를 확인해요.

    4부 개선

    9장 성능 개선의 순서

    가장 싼 것부터, 측정된 것만

    문제: 무엇부터 고칠까

    1장의 사건으로 돌아가요. DB 커넥션 풀이 포화된 원인을 트레이스로 보니, 주문 생성 API 하나가 요청마다 쿼리를 120번 보내고 있었어요. 주문 항목마다 상품, 재고, 할인 정보를 따로 조회하는 코드였어요. 고칠 방법은 여러 가지가 떠올라요. 커넥션 풀을 키운다, DB 서버를 키운다, 결과를 캐시한다, 쿼리를 합친다. 무엇부터 해야 할까요?

    큰 덩어리부터

    전체 시간 중 일부만 빨라지면 전체 개선은 그 부분의 비중에 묶여요(암달의 법칙). 전체의 20%를 차지하는 부분을 아무리 빠르게 해도 전체는 최대 25% 빨라질 뿐이에요. 그러니 가장 큰 덩어리부터 줄여야 하고, 덩어리의 크기는 재야 알아요. 이 사건에서는 주문 생성 시간의 85%가 쿼리 120번의 왕복이었어요.

    개선의 위계

    위에 있을수록 효과가 크고 비용이 적어요. 가장 좋은 것은 하지 않는 것이에요. 쓰지 않는 필드를 조회하는 쿼리, 중복 호출, 쓸모없는 로그를 없애요. 다음은 덜 하는 것이에요. 120번의 쿼리를 상품 ID 목록으로 한 번에 조회하는 3번의 쿼리로 합치는 것이 여기예요. 왕복이 40분의 1로 줄어요. 그다음은 응답에 필요 없는 일(주문 확인 메일)을 나중에 비동기로 하는 것, 서로 독립적인 호출을 동시에 하는 것, 알고리즘이나 쿼리 계획으로 더 빠르게 하는 것이에요. 자원을 더 쓰는 것(서버 증설, 풀 확대)은 마지막이에요. 커넥션 풀을 키웠다면 DB에 더 많은 동시 쿼리가 몰려 DB까지 느려졌을 거예요.

    백엔드에서 가장 흔한 원인

    경험상 순서가 있어요. 반복문 안의 쿼리나 원격 호출(왕복 횟수), 인덱스를 못 타는 쿼리와 필요 이상의 행·컬럼 조회, 서로 독립적인데 하나씩 차례로 부르는 외부 호출, 느린 작업이 커넥션이나 스레드를 오래 쥐어 생기는 풀 고갈, 페이징 없는 목록이나 압축하지 않은 큰 응답이에요.

    작업 절차

    목표를 숫자로 정해요(주문 생성 p99 300ms 이하). 목표가 없으면 끝나지 않아요. 지금 값을 재고(기준선), 가장 큰 덩어리를 찾고(트레이스, 프로파일), 가설을 세워 하나만 바꾸고, 같은 방법으로 다시 재요. 효과가 없으면 되돌려요. 목표에 닿으면 멈춰요.

    백엔드에서는 느린 API를 받으면 프로파일러보다 분산 트레이스 하나를 먼저 여세요. 대부분 "같은 쿼리가 200번" 또는 "외부 호출 5개가 차례로"처럼 구조가 바로 보여요. 그 단계에서 풀리는 문제가 프로파일러까지 가야 하는 문제보다 훨씬 많아요. 캐시는 마지막에 꺼내세요. 캐시는 느린 쿼리를 없애지 않고 숨기며, 무효화라는 새 문제를 가져와요.
    시니어 심화 한 번 고친 성능은 그대로 두면 다시 나빠져요. 다음 기능을 추가하면서 누군가 반복문 안에 쿼리를 또 넣기 때문이에요. 그래서 고친 뒤에는 회귀를 막는 장치를 둬요.

    응답 시간은 환경에 따라 흔들려서 자동 검사의 기준으로 쓰기 어려워요. 대신 요청당 쿼리 수처럼 결정적인 지표를 테스트로 고정하세요. "주문 생성 API는 쿼리 5번 이하"를 통합 테스트로 확인하면, 누군가 N+1을 다시 만들었을 때 배포 전에 실패해요. 더 나아가 엔드포인트마다 성능 예산을 정해 두는 방법도 있어요. 응답 시간 목표를 구간별로 나눠 배정하는 거예요(DB 100ms, 외부 호출 120ms, 나머지 80ms). 예산이 있으면 새 기능이 어느 구간을 넘겼는지 바로 보이고, 설계 단계에서 "이 외부 호출을 하나 더 넣을 여유가 있는가"를 물을 수 있어요. 처리량과 응답 시간은 다른 최적화라는 점도 기억하세요. 묶어서 처리하면 처리량은 오르지만 개별 요청은 묶일 때까지 기다려요.

    핵심 정리
    • 암달의 법칙: 비중이 큰 덩어리부터. 비중은 재야 앎
    • 하지 않기 → 덜 하기 → 나중에 → 동시에 → 빠르게 → 자원 추가
    • 목표 → 기준선 → 하나만 변경 → 재측정. 쿼리 수 같은 결정적 지표로 회귀 방지
    셀프 체크
    1. 응답 시간 1초인 API에서 DB가 700ms, 직렬화가 100ms, 나머지가 200ms입니다. 직렬화를 10배 빠르게 하는 것과 DB 시간을 절반으로 줄이는 것 중 무엇이 효과가 큰가요?
    답 보기

    직렬화를 10배 빠르게 하면 100ms가 10ms가 되어 전체는 910ms, 9% 개선이에요. DB 시간을 절반으로 줄이면 700ms가 350ms가 되어 전체는 650ms, 35% 개선이에요. 개선 폭은 그 부분을 얼마나 빠르게 했느냐보다 그 부분이 전체에서 차지하는 비중에 좌우돼요. 그래서 구간별 시간을 먼저 재고 가장 큰 구간부터 손대야 해요.

    실습

    실습 과제

    일부러 느린 서비스를 만들고 원인을 절차대로 찾아보세요.

    • 1장 내 서비스의 자원 목록(운영체제 자원 + 풀·큐·락)을 적고, 각각의 사용률·포화·에러를 어떤 지표로 볼지 표로 채우기. 빈 칸 찾기
    • 2장 요청의 1%가 2초 걸리는 엔드포인트를 만들고 평균, p50, p99, 히스토그램 비교. 20번 호출하는 화면의 체감 지연 측정
    • 3장 CPU 포화, 메모리 부족, 디스크 I/O 포화를 각각 인위적으로 만들고 점검 목록의 어느 명령에서 드러나는지 기록
    • 4장 반복문 안에서 정규식을 매번 컴파일하는 코드를 프로파일링해 플레임 그래프에서 찾기. 고친 뒤 차분 그래프로 비교
    • 5장 커넥션 풀 크기를 2로 줄이고 부하를 줘서, 사용 중 게이지와 대기 시간 히스토그램이 각각 무엇을 보여주는지 비교
    • 6~7장 닫힌 모델과 열린 모델로 같은 서비스를 테스트. 열린 모델로 도착률을 올리며 사용률 대비 응답 시간 곡선 그리기
    • 9장 N+1 쿼리가 있는 API를 트레이스로 찾아 고치고, 요청당 쿼리 수를 확인하는 테스트 추가
