오브젝트 + 클린 아키텍처 · 상시 병행

진행률 0%

    소프트웨어 설계

    기준 교재: 오브젝트 (조영호) + 클린 아키텍처 (Robert C. Martin) · 상시 병행

    『오브젝트』는 15장에 걸쳐 객체지향 설계의 핵심은 "책임을 어디에 둘 것인가"라는 하나의 질문을 파고들어요. 영화 예매 예제가 책 전체를 관통해요. 이 페이지는 그 15장을 주제별로 묶어 1부로, 『클린 아키텍처』의 설계 원칙(SOLID)·컴포넌트 원칙·아키텍처 경계를 2부로 정리했어요. 마지막 부록은 테스트예요.

    앞 챕터들이 "시스템이 어떻게 동작하는가"였다면 이 챕터는 "코드를 어떻게 바꾸기 쉽게 만드는가"예요. 이론은 짧고 실천이 길어요. 각 장을 읽고 지금 작업 중인 코드에서 해당 냄새를 하나씩 찾아보세요.

    오브젝트 기준 교재조영호 · 3·4·5·8·9장이 핵심. 코드를 직접 따라 치면서
    클린 아키텍처Robert C. Martin · 3부(설계 원칙), 5부(아키텍처)
    객체지향의 사실과 오해 입문오브젝트가 무겁게 느껴지면 먼저
    리팩터링 2판 실천Martin Fowler · 냄새 카탈로그와 기법
    1부 오브젝트 — 역할, 책임, 협력

    1~2장 객체, 설계, 그리고 객체지향 프로그래밍

    티켓 판매소 예제와 영화 예매 예제 — 절차적 코드가 왜 변경에 약한가

    설계란

    "코드를 배치하는 것". 좋은 설계는 오늘 요구사항을 만족하면서 내일의 변경을 수용하는 것. 변경이 어려운 이유는 의존성 때문이에요. A가 B의 내부를 알면 B를 바꿀 때 A도 바뀌어요.

    티켓 판매 예제의 문제

    Theater.enter(audience)가 관람객의 가방을 열어 초대장을 확인하고 돈을 꺼내 판매원의 매표소에 넣어요. 문제: (1) 관람객·판매원이 수동적이고 Theater가 모든 걸 함, (2) Theater가 Bag, TicketOffice 내부까지 알아 결합도 높음, (3) 가방 구조가 바뀌면 Theater가 바뀜. 해결: "관람객이 스스로 티켓을 사고, 판매원이 스스로 판다"로 책임을 옮김. 자율적인 객체. Theater는 ticketSeller.sellTo(audience)만 호출. 캡슐화 ↑ 결합도 ↓.

    트레이드오프: Audience의 자율성을 높이려 Bag을 바꾸다 TicketSeller가 Bag에 의존하게 되는 등, 모든 변경에는 득과 실이 있어요. 설계는 트레이드오프의 산물.

    영화 예매 예제로 본 객체지향

    Movie(영화), Screening(상영), DiscountPolicy(할인 정책: 금액/비율), DiscountCondition(할인 조건: 순번/기간), Reservation(예매). 핵심 설계:

    // Movie는 어떤 할인 정책인지 모름. DiscountPolicy 추상에만 의존
public class Movie {
    private DiscountPolicy discountPolicy;
    public Money calculateMovieFee(Screening screening) {
        return fee.minus(discountPolicy.calculateDiscountAmount(screening));
    }
}
// 할인 정책 추가 = 새 클래스 추가. Movie는 안 바뀜
    • 협력: 객체들이 메시지를 주고받으며 기능을 완성. Screening → Movie → DiscountPolicy → DiscountCondition.
    • 추상화: Movie는 "할인 정책"이라는 추상에 의존. 구체(AmountDiscountPolicy)는 실행 시점에 결정 → 컴파일 의존성 ≠ 런타임 의존성. 유연함의 대가는 "코드만 보고 실행 흐름을 알기 어려움".
    • 상속과 다형성: 같은 메시지에 다른 응답. 메서드 결정이 런타임에(동적 바인딩).
    • 상속 vs 합성: 상속은 부모 내부에 결합, 컴파일 시점 고정. 합성은 인터페이스로 결합, 런타임 교체 가능. 합성 우선.
    백엔드에서는 Service 클래스가 Entity의 getter로 데이터를 꺼내 모든 계산을 하는 코드가 Theater 예제 그대로예요(트랜잭션 스크립트). 엔티티는 수동적 데이터 가방. 그래서 할인 규칙이 바뀌면 Service가 바뀌고, 같은 규칙이 다른 Service에 중복돼요. "이 계산은 누가 알아야 하나?"를 물어 그 데이터를 가진 객체에게 메서드로 옮기세요. 그게 1부 전체의 연습이에요.
    시니어 심화 본문은 데이터를 가진 객체에게 계산을 옮기라고 했는데, 모든 코드를 그렇게 설계할 필요는 없어요. 오히려 어디에 설계 노력을 쓸지 고르는 것이 더 중요한 판단이에요.

    상황

    백오피스의 모든 기능을 같은 방식으로 만들었어요. 공지사항 등록에도 엔티티, 값 객체, 도메인 서비스, 리포지터리 인터페이스와 구현체가 있어요. 공지에 필드 하나를 추가하는 데 파일 일곱 개를 고쳐야 해요. 반면 정작 복잡한 할인 계산은 서비스 클래스 하나에 2,000줄짜리 if 문으로 남아 있어요.

    왜 이렇게 되나

    설계 노력이 규칙의 복잡도와 상관없이 모든 곳에 똑같이 들어갔어요. 규칙이 거의 없는 곳에 들인 구조는 비용만 남기고, 규칙이 복잡한 곳은 "일단 돌아가게" 만든 뒤로 아무도 손대지 못해요.

    어디에 어떤 방식을 쓸까

    • 트랜잭션 스크립트가 맞는 곳: 입력을 검증하고 테이블에 저장하고 조회하는 것이 전부인 기능이에요. 공지사항, 배너, 코드 테이블, 관리자 설정 같은 곳이에요. 서비스 메서드 하나가 절차대로 처리하는 코드가 가장 싸고 읽기 쉬워요.
    • 객체에 책임을 나누는 것이 맞는 곳: 상태가 바뀌는 규칙이 있는 곳(주문은 결제 전, 결제 완료, 배송 중, 배송 완료로 바뀌고, 단계마다 취소 가능 조건이 달라요), 계산 규칙이 조합되는 곳(쿠폰, 등급 할인, 행사 할인의 중첩), 그리고 그 규칙이 자주 바뀌는 곳이에요.
    • 지금 손봐야 한다는 신호: 같은 if 조건이 여러 서비스에 복사돼 있거나, 메서드가 수백 줄이거나, 버그 수정이 특정 파일에 몰려 있어요.

    느낌이 아니라 기록으로 찾기

    버전 관리 기록에서 자주 바뀌는 파일을 뽑아 볼 수 있어요.

    git log --since=1.year --name-only --format= | sort | uniq -c | sort -rn | head -20

    자주 바뀌는 파일 중에서 크고 복잡한 파일이 핫스팟이에요. 설계를 손볼 우선순위가 가장 높은 곳이에요. 그리고 같은 커밋에 자주 함께 등장하는 파일 쌍을 보면, 서로 다른 패키지에 있는데 항상 같이 바뀌는 코드가 드러나요. 경계가 잘못 그어졌다는 신호예요(도메인 주도 설계 챕터 1장). code-maat 같은 도구가 이 분석을 자동으로 해 줘요.

    핫스팟 상위 몇 개만 리팩터링하고 나머지는 단순하게 둬요. 1년 동안 두 번 바뀐 파일은 아무리 지저분해도 고칠 이유가 약해요.

    대가: 한 코드베이스에 두 스타일이 공존해요. "이 패키지는 스크립트 방식, 이 패키지는 도메인 모델"이라는 규칙을 문서로 남겨 두지 않으면 리뷰 때마다 같은 논쟁이 반복돼요.

    운영에서 알아채는 법

    • 기능 하나를 바꾸는 PR에서 수정된 파일 수를 봐요. 단순한 기능인데 파일 수가 많다면 과한 구조예요.
    • 분기마다 핫스팟 목록을 다시 뽑아서, 지난 분기에 손본 곳이 목록에서 내려갔는지 확인해요.
    핵심 정리
    • 설계 = 변경을 위한 코드 배치. 의존성이 변경 비용
    • 자율적 객체: 자기 데이터는 자기가 처리(캡슐화)
    • 추상에 의존 → 구체는 런타임에 조립. 합성 > 상속
    셀프 체크
    1. "컴파일 시점 의존성과 런타임 의존성이 다르다"가 유연한 설계의 조건인 이유와 대가는?
    답 보기

    코드는 추상(DiscountPolicy)에만 의존하고 실제 객체(AmountDiscountPolicy)는 실행 시 주입되니, 새 구현을 추가해도 기존 코드가 안 바뀌어요(확장 가능). 대가: 코드만 봐서는 어떤 객체가 실제로 협력하는지 알 수 없어 디버깅과 이해가 어려워요. 설정·조립 코드(DI 컨테이너)를 봐야 해요.

    3장 역할, 책임, 협력

    객체지향의 본질은 클래스가 아니라 협력하는 객체들의 책임

    협력

    객체는 혼자 못 해요. 요청(메시지)을 보내고 응답을 받으며 협력해요. 메시지를 받은 객체는 자율적으로 처리 방법(메서드)을 정해요. 협력이 객체의 행동을 결정하고, 행동이 상태를 결정해요. 객체가 먼저가 아니라 협력이 먼저.

    책임

    협력에 참여하기 위해 객체가 수행하는 행동. 두 종류: 하는 것(계산, 다른 객체의 행동 시작, 제어·조정)과 아는 것(자기 정보, 관련 객체, 계산한 것). 책임 할당의 기본: 정보 전문가(Information Expert) — 그 책임을 수행하는 데 필요한 정보를 가장 잘 아는 객체에게. 영화 요금 계산은 요금을 아는 Movie에게, 할인 여부는 조건을 아는 DiscountCondition에게.

    책임 주도 설계(RDD): 시스템 책임 파악 → 작은 책임으로 분할 → 수행할 객체(역할)에 할당 → 혼자 못 하면 도움 줄 객체 찾아 할당 → 협력 완성. 데이터가 아니라 책임에서 시작.

    역할

    협력 안에서 책임의 집합. 같은 역할을 여러 객체가 수행할 수 있으면(AmountDiscountPolicy, PercentDiscountPolicy 둘 다 "할인 정책" 역할) 협력을 추상화해 하나로 설명할 수 있어요. 역할 = 추상 클래스/인터페이스. 역할이 필요한지는 "대체 가능한 객체가 둘 이상인가"로. 하나뿐이면 역할을 미리 만들지 마세요(불필요한 추상화).

    백엔드에서는 새 기능을 설계할 때 "테이블부터" 또는 "클래스 다이어그램부터" 그리지 말고 "무슨 요청이 들어오고 누가 답해야 하나"부터. 유스케이스를 시퀀스로 그리면 메시지가 보이고, 메시지를 받을 객체가 정해지고, 그 객체가 알아야 할 것(상태)이 정해져요. 그다음 테이블. 그리고 PaymentGateway 인터페이스에 구현이 하나뿐이고 바뀔 계획이 없으면 인터페이스는 아직 필요 없어요. 테스트 더블이 필요할 때 만들어도 늦지 않아요.
    시니어 심화 본문은 "무슨 요청이 들어오고 누가 답해야 하나"부터 시작하라고 했는데, 이 원칙은 클래스 사이뿐 아니라 서비스 사이의 경계에도 그대로 적용돼요.

    상황

    주문 서비스가 할인율을 정하려고 회원 서비스에서 회원 정보를 통째로 받아 와요(가입일, 누적 구매액, 최근 6개월 주문 수). 그리고 "이 회원이 VIP인가"를 직접 계산해요. 쿠폰 서비스에도 같은 계산이 복사돼 있어요. 본문의 Theater 예제와 같은 모양이에요.

    깨지는 과정

    1. VIP 기준이 "누적 100만 원"에서 "누적 150만 원이면서 최근 3개월 안에 구매"로 바뀌어요. 규칙의 주인은 회원팀인데, 고쳐야 할 코드는 주문 서비스와 쿠폰 서비스에 있어요.
    2. 두 팀의 배포 시점이 하루 어긋나요. 그날 하루 같은 회원이 주문에서는 VIP, 쿠폰에서는 일반 회원으로 판정돼서 고객 문의가 쏟아져요.
    3. 회원 서비스가 응답 필드 이름을 바꾸자 두 서비스가 동시에 깨져요. 그 뒤로 세 서비스는 항상 함께 배포해요.

    서비스는 셋으로 나뉘었지만 하나를 바꿀 때마다 셋을 함께 배포해야 해요. 이것을 분산된 모놀리스라고 불러요. 모놀리스의 결합은 그대로이고, 네트워크 호출과 배포 조율 비용만 더해진 상태예요.

    해결책

    • 판단은 데이터를 가진 서비스가 해요. 회원 서비스가 "이 회원의 등급은?"에 답하는 API를 제공하고, 주문 서비스는 결과인 "VIP"만 받아요. 등급 규칙은 회원 서비스 한 곳에만 있어요.
    • 더 나아가 이벤트로 알려요. 등급이 바뀌면 회원 서비스가 "회원 등급 변경" 이벤트를 발행하고, 주문과 쿠폰 서비스는 등급을 로컬에 저장해 둬요. 주문할 때 회원 서비스를 부를 필요가 없어서 가용성 곱셈에서도 빠져요(분산 챕터 1장).
    • 응답에는 필요한 것만 담아요. 내부 필드를 통째로 내보내면 받는 쪽이 그 필드에 의존하기 시작해요. 노출한 필드는 바꿀 수 없는 약속이 돼요.
    • 서비스를 나누기 전에 메시지를 그려요. 주요 유스케이스마다 "누가 누구에게 무엇을 묻는가"를 화살표로 그려요. 데이터를 받아 와서 직접 계산하는 화살표가 많은 곳이 경계가 잘못된 곳이에요.

    대가: 회원 서비스의 API가 늘어나고, 이벤트로 받은 등급은 몇 초 늦을 수 있어요. 할인율 표시에는 문제가 없지만, 등급이 바뀐 직후의 주문이 옛 등급으로 계산될 수 있다는 점은 정책으로 정해 둬야 해요.

    운영에서 알아채는 법

    • 배포 기록에서 "항상 같은 날 함께 배포되는 서비스 쌍"을 찾아요. 그 쌍이 경계가 잘못된 후보예요.
    • 한 팀의 기능 변경 하나가 여러 저장소의 PR로 나뉘는 횟수를 세어 봐요.
    • 다른 서비스의 응답 형식 변경 때문에 난 장애를 따로 분류해 두면 결합이 어디에 있는지 보여요.
    핵심 정리
    • 협력 → 책임 → 객체 순. 데이터가 아니라 책임에서 시작
    • 정보 전문가에게 책임 할당
    • 역할 = 대체 가능한 객체들의 추상. 둘 이상일 때만
    셀프 체크
    1. "주문 총액 계산"은 OrderService, Order, OrderLine 중 누가 책임져야 하고 왜?
    답 보기

    정보 전문가: 총액에 필요한 정보(라인 목록, 각 라인의 가격×수량)를 가진 Order가 totalAmount()를, 각 라인 금액은 OrderLine이 amount()를. OrderService는 Order에게 메시지만 보내요. Service가 getter로 꺼내 계산하면 Order 구조가 바뀔 때 Service가 바뀌고, 같은 계산이 여러 Service에 중복돼요.

    4~5장 설계 품질과 책임 할당 (GRASP)

    데이터 중심 설계가 왜 나쁜가, 그리고 책임을 할당하는 패턴들

    데이터 중심 설계의 문제

    "Movie에는 무엇이 있어야 하나?"(데이터)에서 시작하면 getter/setter가 생기고, 모든 로직이 외부(Service)로 가요. 결과:

    • 캡슐화 위반: 내부 구조(필드)가 getter로 노출. 구조 변경 = 사용처 전부 변경.
    • 높은 결합도: 여러 객체가 Movie 내부에 의존.
    • 낮은 응집도: Service 하나가 여러 이유로 변경(할인 규칙, 예매 규칙, 요금 규칙).

    좋은 설계의 척도: 캡슐화(변하는 것을 숨김), 응집도(한 모듈은 한 이유로 변경), 결합도(의존하는 모듈이 변경될 때 함께 변경되는 정도). 세 가지가 서로 연결돼 있어요. "getter 하나 추가"가 캡슐화 위반의 시작이에요.

    GRASP 패턴 (책임 할당의 원칙)

    패턴질문답
    Information Expert누가 책임져야 하나?필요한 정보를 가진 객체
    Creator누가 생성해야 하나?그 객체를 포함·집합·기록하거나 초기화 데이터를 가진 객체. Screening이 Reservation을 생성
    Low Coupling여러 후보 중 선택은?결합도를 덜 높이는 쪽
    High Cohesion여러 후보 중 선택은?응집도를 유지하는 쪽
    Polymorphism타입에 따라 행동이 다르면?if/switch 대신 각 타입이 책임. 할인 조건 종류별 클래스
    Protected Variations변경이 예상되는 곳은?안정된 인터페이스로 감싸 변경을 격리
    Pure Fabrication도메인 객체에 안 맞는 책임은?인위적 객체(Repository, Service) 만들기

    변경의 이유로 응집도 보기

    DiscountCondition이 순번 조건과 기간 조건을 type 필드로 구분해 if로 분기하면, 두 조건 중 하나만 바뀌어도 클래스가 바뀌고 안 쓰는 필드가 생겨요(순번 조건엔 기간 필드가 null). 징후: 인스턴스 변수가 초기화되는 시점이 다름, 메서드들이 서로 다른 인스턴스 변수 그룹을 씀. 해결: 타입별로 클래스 분리(SequenceCondition, PeriodCondition) + 공통 인터페이스 → 다형성.

    리팩터링 순서

    책은 긴 메서드를 작은 메서드로 쪼개고(이름이 의도를 드러냄), 객체를 자율적으로 만드는(로직을 데이터 쪽으로) 과정을 보여줘요. 먼저 동작하는 코드를 만들고, 책임을 옮기며 개선. 처음부터 완벽한 설계는 없어요.

    백엔드에서는 "한 Service가 500줄"은 응집도 문제예요. 메서드들을 "어떤 필드/리포지토리를 쓰는가"로 묶어보면 2~3개 클래스로 나뉘어요. 엔티티에 type 컬럼 + switch는 Polymorphism 적용 대상(JPA 상속 매핑 또는 타입별 정책 객체). Creator 패턴은 "Order가 OrderLine을 만든다"처럼 애그리거트 루트가 하위를 생성하는 DDD 규칙과 같아요.
    시니어 심화 본문은 GRASP로 책임을 할당했는데, 책임 할당이 트랜잭션과 만나면 한 가지를 더 정해야 해요. 어떤 객체들이 항상 함께 맞아야 하는가예요.

    상황

    주문 엔티티에 주문 항목, 결제, 배송, 배송 이력, 리뷰가 모두 JPA 연관관계로 연결돼 있어요. "다 주문과 관련 있으니까" 한 덩어리로 만들었어요. 그런데 배송 추적 시스템이 배송 이력을 추가할 때마다, 같은 시각 주소를 바꾸던 고객의 요청이 낙관적 락 충돌로 실패해요.

    깨지는 과정

    1. 배송 이력을 추가하는 코드가 주문을 통해 이력을 넣으면서 주문의 버전(@Version)이 올라가요.
    2. 같은 시각 고객이 주소를 바꾸려고 주문을 수정해요. 읽을 때의 버전과 지금 버전이 달라서 충돌이 나요.
    3. 배송 이력과 배송 주소는 서로 아무 관계가 없는데, 같은 묶음에 있다는 이유만으로 서로를 실패시켜요.
    4. 게다가 주문을 조회할 때마다 리뷰와 배송 이력까지 따라 로딩되거나, 지연 로딩으로 쿼리가 수십 개 나가요.

    반대로 너무 잘게 나눠도 문제예요. 주문 항목을 주문과 별개로 두고 항목만 따로 지울 수 있게 하면, 주문의 총액과 항목 금액의 합이 어긋나요.

    묶는 기준: 불변식

    불변식은 언제나 참이어야 하는 규칙이에요. "주문 총액은 항목 금액의 합이다", "주문 하나의 항목은 50개 이하다", "결제가 끝난 주문의 항목은 바꿀 수 없다" 같은 것이에요. 이 규칙을 지키려면 함께 바뀌어야 하는 객체들을 하나의 묶음, 즉 애그리거트로 둬요. 위 예에서는 주문과 주문 항목이 한 애그리거트예요. 리뷰는 주문과 같이 바뀔 이유가 없으니 별도 애그리거트, 배송 이력은 배송 애그리거트에 둬요. 묶는 기준은 "관련 있는가"가 아니라 "함께 바뀌어야 규칙이 지켜지는가"예요.

    애그리거트를 다루는 규칙

    • 바깥에서는 대표 객체(루트)를 통해서만 바꿔요. 항목 삭제는 order.removeItem(itemId)로만 하고, 그 메서드 안에서 상태 검사와 총액 재계산을 해요. 주문 항목만 따로 다루는 리포지터리는 만들지 않아요.
    • 애그리거트 사이는 ID로 가리켜요. 리뷰는 Order 객체가 아니라 orderId 값만 가져요. JPA 연관관계를 걸지 않으면 로딩 경계가 분명해지고, 실수로 다른 애그리거트를 고치는 일이 없어요.
    • 한 트랜잭션에서는 애그리거트 하나만 고쳐요. 주문 완료와 재고 차감이 둘 다 필요하면, 주문을 완료하면서 이벤트를 발행하고 재고는 그 이벤트를 받아 별도 트랜잭션에서 차감해요. 두 애그리거트 사이의 일관성은 조금 뒤에 맞춰요(도메인 주도 설계 챕터 2장).
    • 작게 유지해요. 대부분의 애그리거트는 루트 하나와 값 객체 몇 개로 충분해요.

    대가: 애그리거트 사이의 즉시 일관성을 포기해요. 재고 차감 이벤트가 실패하면 주문을 취소하는 보상 처리가 필요하고, 화면에는 "처리 중" 같은 중간 상태가 생겨요.

    운영에서 알아채는 법

    • 낙관적 락 충돌을 기능별로 기록해요. 서로 다른 기능 사이의 충돌이 많다면 애그리거트가 너무 커요.
    • API 하나가 실행하는 쿼리 수를 봐요(Hibernate 통계). 조회 하나에 쿼리가 수십 개라면 연관관계로 묶인 범위가 너무 넓어요.
    • 코드 리뷰에서 "이 트랜잭션은 애그리거트를 몇 개 고치나"를 확인 항목으로 둬요.
    핵심 정리
    • 데이터 중심 = getter/setter + 외부 로직 = 캡슐화 위반·결합↑·응집↓
    • GRASP: 정보 전문가, 창조자, 낮은 결합, 높은 응집, 다형성, 변경 보호
    • 응집도 징후: 변수 초기화 시점 다름, 메서드별 변수 그룹 다름 → 분리
    셀프 체크
    1. 클래스 하나가 낮은 응집도를 가지고 있다는 코드상의 징후 두 가지는?
    답 보기

    (1) 인스턴스 변수들이 서로 다른 시점·조건에서 초기화됨(일부는 항상 null). (2) 메서드들이 서로 겹치지 않는 변수 집합을 사용함(메서드 A는 x,y만, B는 z,w만). 둘 다 "사실은 두 클래스"라는 뜻이에요. 추가로 "이 클래스가 바뀌는 이유를 두 개 이상 말할 수 있다".

    6~7장 메시지와 인터페이스, 객체 분해

    좋은 인터페이스의 조건 — 디미터, 묻지 말고 시켜라, 의도를 드러내는 이름, 명령-쿼리 분리

    인터페이스 설계 원칙

    • 디미터 법칙: "낯선 자에게 말하지 마라". 메서드 안에서는 this, 인자, 필드, 지역 생성 객체의 메서드만 호출. a.getB().getC().doSomething()(기차 충돌)은 A가 B·C의 구조를 다 아는 것. B가 바뀌면 깨져요. 단, 값 객체나 빌더/스트림 체이닝은 예외.
    • 묻지 말고 시켜라(Tell, Don't Ask): 상태를 물어 밖에서 판단하지 말고 객체에게 시켜라. if (order.getStatus() == PAID) order.setStatus(SHIPPED) → order.ship(). 판단 로직이 데이터와 함께 있게.
    • 의도를 드러내는 인터페이스: 어떻게가 아니라 무엇을. isSatisfiedBySequence() → isSatisfiedBy(). 구현이 달라도 같은 이름이면 다형성 가능.
    • 명령-쿼리 분리(CQS): 상태를 바꾸는 메서드(명령)는 값을 반환하지 않고, 값을 반환하는 메서드(쿼리)는 상태를 바꾸지 않는다. 쿼리는 몇 번 불러도 안전(참조 투명성), 명령은 부수효과를 명확히. isSatisfied()가 내부 상태를 바꾸면 디버깅 지옥.

    객체 분해 vs 기능 분해

    7장. 절차적 분해(하향식 기능 분해)는 메인 함수를 단계로 쪼개요. 문제: 데이터가 전역이 되어 모든 함수가 결합, 요구사항 변경 시 메인부터 재구성, 비즈니스 로직이 인터페이스(입출력)에 결합. 추상 데이터 타입(ADT)은 데이터 + 연산을 묶지만 타입 분기(if type)가 남고, 객체(클래스)는 타입마다 클래스를 두어 분기를 다형성으로. 새 타입 추가 = 새 클래스(OCP). 단, 새 연산 추가가 잦으면 ADT가 유리할 수도(표현식 문제). 변경 축을 보고 선택.

    백엔드에서는 Controller가 user.getProfile().getAddress().getZipCode()를 하면 Profile·Address 구조 변경이 Controller까지 퍼져요. user.zipCode()로. JPA 엔티티에 setStatus가 public이면 어디서든 상태를 멋대로 바꿔요. cancel(), ship() 같은 의도 있는 메서드만 열고 setter는 닫으세요. Repository의 findAndUpdate처럼 조회하면서 상태를 바꾸는 메서드는 CQS 위반이라 호출자가 두 번 부르면 사고예요.
    시니어 심화 본문의 디미터 법칙과 Tell, Don't Ask는 좋은 원칙이지만, 조회 화면 앞에서는 자주 무리가 생겨요. 화면은 여러 객체의 데이터를 한꺼번에 묻는 일이니까요.

    상황

    판매자 대시보드의 주문 표에는 주문 번호, 회원 이름, 상품 이미지, 배송 상태, 정산 예정일이 한 줄에 나와요. 처음에는 Order 엔티티에 getMemberName(), getThumbnailUrl(), getSettlementDate()를 하나씩 추가했어요.

    깨지는 과정

    1. 주문 엔티티가 회원, 상품, 배송, 정산을 알게 돼요. 도메인 객체가 화면의 요구로 커져요.
    2. 주문 100건을 엔티티로 읽으면 연관 객체 넷이 지연 로딩되면서 쿼리가 1 + 100 × 4 = 401개 나가요(N+1 문제).
    3. fetch join으로 한 번에 가져오려 하면, 컬렉션 두 개 이상을 동시에 fetch join할 수 없거나(MultipleBagFetchException), 컬렉션 fetch join과 페이징을 함께 쓰면 전체를 메모리로 가져와 자르는 경고가 나와요.
    4. 화면에 컬럼이 하나 추가될 때마다 도메인 엔티티를 고치고, 도메인 테스트가 깨져요.

    해결책: 읽는 쪽을 분리

    • 상태를 바꾸는 명령은 도메인 객체에게 시켜요. order.cancel()처럼 규칙이 있는 변경은 지금처럼 엔티티가 맡아요.
    • 화면을 위한 조회는 전용 쿼리로 DTO를 바로 만들어요. JPQL의 생성자 표현식, QueryDSL의 Projections, jOOQ, MyBatis 무엇이든 좋아요. 필요한 컬럼만 조인 한 번으로 가져와요. 401개였던 쿼리가 1~2개가 돼요.
    • 패키지를 나눠요. order.command와 order.query처럼 나누고, 조회 쪽은 도메인 엔티티를 import하지 않게 해요. 화면이 바뀌어도 도메인 코드는 그대로예요.
    • 필요해질 때만 한 단계씩 나아가요. 같은 DB에서 코드만 나누는 것이 첫 단계예요. 조회가 무거우면 이벤트로 채우는 조회 전용 테이블을 만들고, 여러 서비스의 데이터를 합쳐야 하면 별도 저장소로 가요(도메인 주도 설계 챕터 6장 CQRS).
    • 디미터 법칙의 적용 범위를 알아 둬요. 이 법칙은 동작을 가진 객체에 적용해요. 구조를 드러내는 것이 목적인 DTO와 값 객체는 dto.getAddress().getCity()처럼 따라가도 괜찮아요.

    대가: 같은 데이터에 모델이 두 개 생겨요. 위험한 것은 "취소 가능 여부"처럼 도메인 규칙이 필요한 표시를 조회 쪽에서 다시 구현하는 거예요. 그런 규칙은 도메인 쪽 정책 클래스를 조회 쪽에서도 호출하거나, 결과를 컬럼으로 저장해 두고 읽어요.

    운영에서 알아채는 법

    • 요청 하나당 실행된 SQL 수를 지표로 남겨요(datasource-proxy, p6spy, Hibernate 통계). 목록 API에서 수십 개가 나온다면 N+1이에요.
    • 도메인 엔티티를 고친 PR의 이유가 "화면 요구"인 경우가 잦다면 조회를 분리할 때예요.

    • 의도를 드러내는 이름, 명령/쿼리 분리
    • 타입 추가가 잦으면 다형성(클래스), 연산 추가가 잦으면 ADT

    8~9장 의존성 관리와 유연한 설계

    의존성의 종류, 의존성 역전, 생성과 사용의 분리, 의존성 주입

    의존성이란

    A가 B를 알아야 동작하면 A는 B에 의존. B가 바뀌면 A도 바뀔 수 있어요. 종류: 클래스 의존(컴파일), 객체 의존(런타임). 전이적 의존(A→B→C면 A→C). 의존성은 없앨 수 없고, 관리하는 것. 목표: 변경이 잦은 것에 의존하지 않기 = 구체가 아닌 추상에 의존.

    바람직한 의존성

    • 컨텍스트 독립성: Movie가 "금액 할인 정책"을 알면 그 맥락에만 묶임. "할인 정책"만 알면 어디서든 재사용.
    • 의존성 역전(DIP): 상위(정책, Movie)가 하위(구현, AmountDiscountPolicy)에 의존하지 말고, 둘 다 추상(DiscountPolicy)에 의존. 추상의 소유권은 상위 모듈에. 인터페이스는 그것을 사용하는 쪽의 패키지에 둬요.
    • 명시적 의존성: 생성자나 메서드 인자로 받아 밖에서 보이게. 메서드 안에서 new하면 숨은 의존성이라 교체·테스트 불가.
    • new는 해롭다: new AmountDiscountPolicy(...)를 Movie 안에서 하면 구체 클래스와 생성자 인자까지 알아야 해요. 생성은 밖에서(조립 코드, 팩토리, DI 컨테이너), Movie는 사용만. 생성과 사용의 분리.

    유연한 설계의 도구

    • OCP: 확장에 열리고 수정에 닫힘. 새 할인 정책 = 새 클래스, Movie 수정 없음. 추상화 + 의존성 역전으로 달성.
    • 의존성 주입(DI): 생성자 주입(필수 의존성, 불변, 권장), setter 주입(선택적), 메서드 인자 주입(일시적). 서비스 로케이터(객체가 스스로 찾아옴)는 의존성을 숨겨 비권장.
    • 팩토리: 생성 책임만 가진 객체. 생성 로직이 복잡하거나 조건부일 때.
    • 조합 가능한 행동: 작은 객체들을 조립해 큰 행동. "어떻게"가 아니라 "무엇을"을 선언하는 코드. new Movie("아바타", new AmountDiscountPolicy(800, new SequenceCondition(1), new PeriodCondition(...)))는 읽기만 해도 정책이 보여요.

    과도한 유연성

    유연성은 복잡성을 낳아요. 변경이 실제로 예상되는 곳에만. "나중에 필요할지도"로 추상화하면 코드만 늘어요(YAGNI). 책은 "유연성은 설계의 목적이 아니라 변경을 위한 수단"이라고 해요.

    백엔드에서는 스프링 DI가 이 장 그대로예요. @Autowired 필드 주입은 숨은 의존성(테스트에서 주입 어려움, 순환 의존 감지 안 됨)이라 생성자 주입(@RequiredArgsConstructor)을. 인터페이스를 infrastructure 패키지에 두고 domain이 그걸 import하면 DIP 위반이에요. OrderRepository 인터페이스는 domain에, JpaOrderRepository는 infrastructure에. 그리고 "구현체가 하나뿐인 인터페이스를 모든 Service에"는 과도한 유연성의 전형이에요. 외부 시스템 경계(결제, 메일, 저장소)에만 두세요.
    시니어 심화 본문은 DIP의 위치(인터페이스는 domain에)를 다뤘는데, 인터페이스를 domain에 두었는데도 역전이 형식뿐인 경우가 많아요. 인터페이스의 시그니처에 기술이 새어 나오기 때문이에요.

    상황

    OrderRepository 인터페이스를 domain 패키지에 두었어요. 그런데 메서드가 Page<Order> findByStatus(OrderStatus status, Pageable pageable)와 List<Order> findAll(Specification<Order> spec)이에요. 일부 조회를 외부 검색 서비스로 옮기려고 하자, 인터페이스부터 다시 짜야 했어요.

    깨지는 과정

    1. Page와 Pageable은 스프링 데이터의 타입이고, Specification은 JPA Criteria API 위에 만든 스프링 데이터 JPA의 타입이에요. 파일 위치만 domain일 뿐 domain은 스프링 데이터와 JPA에 묶여 있어요.
    2. Specification을 만드는 서비스 코드는 JPA Criteria를 알아야 해요. 도메인 규칙과 쿼리 기술이 같은 곳에 섞여요.
    3. 검색 서비스로 구현을 바꾸려 하면 Specification을 해석할 방법이 없어요. 인터페이스를 바꾸고, 그 인터페이스를 쓰는 모든 서비스를 고쳐야 해요. 의존성을 역전시킨 목적(구현을 바꿔도 domain은 그대로)이 달성되지 않았어요.
    4. domain만 단위 테스트하려 해도 스프링 데이터 라이브러리가 클래스패스에 있어야 해요.

    해결책

    • 인터페이스는 도메인의 언어로 써요. findPendingOlderThan(Duration age)처럼 "무엇을 원하는가"를 이름으로 드러내고, 기술 타입 대신 자체 타입이나 기본 타입을 써요. 페이징이 필요하면 단순한 자체 record를 만들어요.
    • 화면용 조회는 리포지터리에서 빼요. 페이징, 정렬, 동적 필터가 필요한 것은 대부분 화면용 조회예요. 조회 전용 코드로 옮기면(6장 시니어) 도메인 리포지터리에는 ID로 찾기와 저장 정도만 남아서 기술이 새어 나올 자리가 줄어요.
    • 구현체는 인프라 패키지에 둬요. JpaOrderRepository가 domain의 인터페이스를 구현하고, 내부에서 스프링 데이터 인터페이스를 써요. 스프링 데이터 타입은 이 클래스 밖으로 나가지 않아요.
    • 규칙을 사람 대신 빌드가 지키게 해요. ArchUnit 테스트로 domain 패키지가 프레임워크를 참조하면 실패하게 만들어요. 
      noClasses().that().resideInAPackage("..domain..")
    .should().dependOnClassesThat()
    .resideInAnyPackage("org.springframework..", "jakarta.persistence..")
      더 강하게 하려면 Gradle 멀티 모듈로 domain 모듈을 분리하고 의존성에 스프링을 넣지 않아요. 잘못된 import는 아예 컴파일되지 않아요.
    • 타협하는 경우 규칙을 명시해요. 엔티티에 @Entity 같은 JPA 애너테이션은 허용하되 스프링 데이터 타입은 금지하는 식으로 정하는 팀이 많아요. 실용적인 선택이에요. 다만 그 경계를 ArchUnit 규칙에 그대로 적어 두세요.

    대가: domain을 완전히 분리하면 도메인 객체와 JPA 엔티티 사이의 변환 코드가 생겨요. 저장 기술을 바꿀 가능성이 낮다면 위의 타협안이 더 싸요.

    알아채는 법

    • domain 패키지의 import 문에서 org.springframework와 jakarta.persistence를 검색해 보세요. 결과 수가 곧 역전이 깨진 정도예요.
    • ArchUnit 테스트를 CI에 넣으면 새로 새어 나오는 의존성이 PR 단계에서 잡혀요.
    핵심 정리
    • 의존성은 관리 대상. 추상에 의존, 추상은 사용하는 쪽이 소유(DIP)
    • new는 밖으로(생성과 사용 분리), 생성자 주입으로 명시
    • OCP = 추상 + 역전. 유연성은 필요한 곳에만
    셀프 체크
    1. "의존성 역전"에서 무엇이 역전되나요? 역전 전후를 패키지 구조로 설명하세요.
    답 보기

    전통적: 상위 정책(domain.OrderService)이 하위 구현(infra.MySqlOrderDao)을 import. 변경이 잦은 인프라가 바뀌면 도메인이 영향받음. 역전 후: 도메인이 domain.OrderRepository 인터페이스를 정의·소유하고, infra.JpaOrderRepository가 그걸 implements하며 domain을 import. 의존 방향이 infra → domain으로 역전. 추상(인터페이스)의 소유권이 하위에서 상위로 옮겨간 게 핵심이에요.

    10~11장 상속과 코드 재사용, 합성과 유연한 설계

    상속이 왜 위험한가(취약한 기반 클래스), 합성과 믹스인으로 대체하기

    상속의 문제

    • 취약한 기반 클래스: 부모 내부 구현에 자식이 결합. 부모를 바꾸면 자식이 예상치 못하게 깨져요. InstrumentedHashSet extends HashSet에서 addAll이 내부적으로 add를 호출해 카운트가 2배로. 부모의 "구현"을 알아야 안전하게 상속할 수 있다면 캡슐화 실패.
    • 불필요한 인터페이스 상속: Stack extends Vector라 중간 삽입이 가능해져 스택 규칙이 깨짐. Properties extends Hashtable이라 문자열 아닌 값이 들어감.
    • 메서드 오버라이딩 오작용, 부모 변경 시 자식 변경, 다중 상속 불가(다이아몬드).
    • 책의 예: 전화 요금(일반/심야) × 세금 정책을 상속으로 조합하면 클래스 폭발(2×N). 중복 코드가 클래스마다.

    상속이 적절한 경우: is-a가 성립하고 부모를 추상화(추상 클래스, 템플릿 메서드)해 자식이 구현 세부가 아닌 추상 메서드에만 의존할 때. 구현 재사용이 목적이면 상속 금지.

    합성

    다른 객체를 필드로 갖고 인터페이스를 통해 사용. 내부 구현에 결합 안 됨, 런타임 교체 가능, 조합 폭발 없음. 전화 요금 × 세금 = RatePolicy 객체 + TaxPolicy 객체를 조합(데코레이터처럼 감싸기). 클래스 수가 덧셈(2+N)으로.

    // 상속: NightlyDiscountPhoneWithTax extends NightlyDiscountPhone ... 폭발
// 합성: Phone(ratePolicy) 에서 ratePolicy = new TaxablePolicy(new NightlyDiscountPolicy(...))
phone = new Phone(new RateDiscountablePolicy(amount, new TaxablePolicy(rate, new RegularPolicy(...))));

    객체 합성이 클래스 상속보다 좋은 이유: 변경을 런타임으로 미루고, 조합을 선언적으로 표현하고, 각 정책이 독립적으로 테스트돼요.

    믹스인

    특정 기능 조각을 여러 클래스에 섞어 넣는 기법. 스칼라 trait, Ruby module, Kotlin/Java 8+의 default 메서드로 흉내. 상속 계층과 무관하게 행동 조합. 쌓을 수 있는 변경(stackable modification).

    백엔드에서는 BaseService, AbstractController에 공통 로직을 넣고 모두 상속하는 패턴이 취약한 기반 클래스예요. 부모를 손대면 모든 자식이 영향받고, 자식마다 필요 없는 메서드를 물려받아요. 공통 로직은 별도 컴포넌트(합성)나 AOP·필터·인터셉터로. JPA 엔티티 상속(@Inheritance)도 신중하게 — 조인 전략은 쿼리가 복잡해지고, 단일 테이블은 null 컬럼이 늘어요. 자주 바뀌는 분류는 상속보다 정책 객체 + 타입 컬럼.
    시니어 심화 본문은 공통 로직을 상속 대신 합성이나 AOP로 빼라고 했는데, 합성으로 감싼 기능들은 감싸는 순서가 의미를 바꿔요. 스프링에서 자주 사고가 나는 지점이에요.

    상황

    상품 재고 차감에 낙관적 락(@Version)을 걸었어요. 두 주문이 동시에 같은 재고를 고치면 한쪽이 충돌하니까, 충돌하면 다시 시도하려고 한 메서드에 두 애너테이션을 붙였어요.

    @Retryable(retryFor = OptimisticLockingFailureException.class)
@Transactional
public void decrease(Long productId, int qty) { ... }

    그런데 인기 상품 세일 때 재시도는 한 번도 성공하지 않았고, 충돌 에러가 그대로 사용자에게 나갔어요.

    깨지는 과정

    두 애너테이션은 둘 다 프록시가 메서드를 바깥에서 감싸는 방식으로 동작해요. 어느 쪽이 바깥인지에 따라 결과가 완전히 달라지는데, 코드만 봐서는 순서가 보이지 않아요.

    재시도가 트랜잭션 안쪽에 있으면 세 가지가 동시에 틀어져요.

    1. 충돌이 재시도 밖에서 터져요. 낙관적 락 충돌은 보통 커밋하면서 UPDATE를 보낼 때 발견돼요. 커밋은 바깥의 트랜잭션 프록시가 하니까, 안쪽의 재시도는 예외를 보지도 못해요.
    2. 다시 읽어도 옛 값이에요. 메서드 안에서 직접 flush()해서 충돌을 안쪽에서 일으켜도, 같은 트랜잭션 안에서는 JPA가 처음 읽은 엔티티를 1차 캐시(영속성 컨텍스트)에서 그대로 돌려줘요. 버전이 옛 값이라 몇 번을 시도해도 같은 충돌이 나요.
    3. 트랜잭션은 이미 롤백 전용이에요. JPA 예외가 한 번 나면 그 트랜잭션은 롤백 전용으로 표시돼요. 재시도가 성공해도 커밋할 수 없어요.

    해결책

    • 재시도와 트랜잭션을 서로 다른 빈으로 나눠요. 재시도를 담당하는 StockFacade가 @Transactional이 붙은 StockService를 호출하게 해요. 시도할 때마다 새 트랜잭션과 새 영속성 컨텍스트가 열리고, 순서도 코드에 그대로 드러나요. 애너테이션의 @Order로 프록시 순서를 맞추는 방법도 있지만, 눈에 보이지 않는 설정에 기대게 돼요.
    • 같은 클래스 안에서 자기 메서드를 부르면 안 돼요. this.decrease()는 프록시를 거치지 않아서 애너테이션이 아예 동작하지 않아요. 반드시 다른 빈을 거쳐야 해요.
    • 재시도 횟수와 간격을 정해요. 3회 정도로 제한하고, 지수 백오프(시도마다 대기 시간을 두 배로)에 무작위 지연(지터)을 섞어요. 동시에 충돌한 요청들이 똑같은 간격으로 다시 시도하면 또 충돌하기 때문이에요.
    • 충돌이 잦은 곳은 방식을 바꿔요. 인기 상품처럼 같은 행에 요청이 몰리면 재시도가 계속 실패해요. 그런 곳은 낙관적 락 대신 원자적 UPDATE(SET stock = stock - ? WHERE stock >= ?)나 비관적 락이 나아요.

    재시도, 트랜잭션, 캐시, 서킷 브레이커, 권한 검사는 전부 같은 구조라서 같은 문제가 생겨요. 예를 들어 캐시가 권한 검사보다 바깥이면 다른 사용자의 결과가 캐시에서 나갈 수 있어요. 여러 애너테이션을 겹칠 때는 "바깥부터 어떤 순서로 감싸져야 하는가"를 먼저 정하세요.

    운영에서 알아채는 법

    • RetryListener로 재시도 횟수를 지표로 남겨요.
    • 재시도 지표가 0인데 충돌 에러는 나고 있다면 재시도가 예외를 못 보고 있는 거예요.
    • 재시도가 항상 최대 횟수까지 가서 실패한다면 같은 트랜잭션 안에서 재시도하고 있다는 신호예요.
    • 배포 전에 스레드 10개로 동시에 재고를 차감하는 테스트를 돌리고, 마지막 재고 숫자가 정확히 맞는지 확인해요.
    핵심 정리
    • 상속 = 부모 구현에 결합, 클래스 폭발, 취약한 기반 클래스
    • 합성 = 인터페이스 결합, 런타임 조합, 조합 수 덧셈
    • 상속은 is-a + 추상화된 부모에만. 구현 재사용은 합성
    셀프 체크
    1. 취약한 기반 클래스 문제를 실제 자바 표준 라이브러리 예로 설명하세요.
    답 보기

    HashSet을 상속해 add와 addAll을 오버라이드하고 추가 횟수를 세면, HashSet.addAll이 내부적으로 add를 호출하기 때문에 3개를 addAll하면 카운트가 6이 돼요. 이걸 알려면 HashSet 소스를 봐야 하고, JDK 버전이 바뀌어 내부 구현이 바뀌면 동작이 또 바뀌어요. 합성(HashSet을 필드로 두고 위임)하면 내부 구현과 무관해요(Effective Java 아이템 18).

    12~13장 다형성, 서브클래싱과 서브타이핑

    동적 메서드 탐색의 원리, 그리고 "올바른 상속"의 조건 — 리스코프 치환 원칙

    다형성의 종류

    오버로딩(같은 이름 다른 인자), 강제(타입 변환), 매개변수(제네릭), 포함(서브타입) — 보통 말하는 다형성. 같은 메시지에 수신 객체 타입에 따라 다른 메서드 실행.

    동적 메서드 탐색

    메시지를 받으면 (1) 객체의 클래스에서 메서드를 찾고, (2) 없으면 부모 클래스로 올라가며(상속 계층), (3) 끝까지 없으면 예외. self(this) 전송: 부모 메서드 안에서 this.foo()를 호출하면 탐색이 실제 객체의 클래스부터 다시 시작해 자식의 오버라이드가 실행돼요(템플릿 메서드의 원리, 그리고 취약한 기반 클래스의 원인). super 전송: 부모부터 탐색. 상속은 메서드 탐색 경로를 공유하는 것.

    서브클래싱 vs 서브타이핑

    • 서브클래싱(구현 상속): 코드 재사용 목적. 부모와 자식이 행위 호환 안 될 수 있음.
    • 서브타이핑(인터페이스 상속): 부모 대신 자식을 써도 동작이 같음(행동 호환성). 이게 "올바른" 상속.

    행동 호환성은 클라이언트 관점에서 판단해요. "펭귄은 새다"는 분류상 맞지만 클라이언트가 fly()를 기대하면 호환 안 돼요. 해결: 클라이언트 기대에 맞게 계층 재구성(Bird → FlyingBird, Penguin은 Bird만), 또는 클라이언트 기대를 바꾸기.

    리스코프 치환 원칙 (LSP)

    "S가 T의 서브타입이면 T 객체를 S 객체로 바꿔도 프로그램이 올바르게 동작해야 한다". 계약(contract)으로 표현: 자식은 부모의 사전조건을 강화하면 안 되고(더 까다롭게 받으면 안 됨), 사후조건을 약화하면 안 되고(덜 보장하면 안 됨), 불변식을 유지해야 해요. 고전 예: Square extends Rectangle에서 setWidth가 높이까지 바꾸면 "너비만 바꾼다"는 사후조건 위반.

    LSP 위반 징후: 자식에서 부모 메서드를 빈 구현이나 예외로 덮어씀(throw UnsupportedOperationException), 클라이언트가 instanceof로 분기, 부모 테스트가 자식에서 실패.

    백엔드에서는 ReadOnlyRepository extends CrudRepository에서 save를 예외로 막으면 LSP 위반이에요. 클라이언트가 Repository를 받아 save하면 터져요. 반대로 인터페이스를 분리(ISP)해 ReadRepository와 WriteRepository를 따로. 결제 수단별 PaymentMethod 구현이 "일부는 환불 불가"라면 refund()를 인터페이스에 넣지 말고 Refundable을 분리. 그리고 this.method()가 자식에서 오버라이드되어 트랜잭션 프록시를 안 타는 문제(self-invocation)는 동적 메서드 탐색 + 프록시 이해가 필요한 스프링 단골 함정이에요.
    핵심 정리
    • 동적 탐색: 객체 클래스 → 부모. self 전송은 실제 객체부터 재탐색
    • 서브타이핑 = 행동 호환, 클라이언트 관점. 서브클래싱은 재사용일 뿐
    • LSP = 사전조건 강화 금지, 사후조건 약화 금지. 위반 징후: 예외로 덮어쓰기, instanceof
    셀프 체크

    14~15장 일관성 있는 협력, 디자인 패턴과 프레임워크

    유사한 기능은 유사한 방식으로 — 변경을 캡슐화하는 설계와 패턴의 위치

    일관성 있는 협력

    비슷한 요구사항(핸드폰 요금: 고정/시간대/요일/구간별)을 각기 다른 구조로 구현하면 코드를 읽을 때마다 새로 이해해야 해요. 일관성 있는 설계: 변하는 개념을 변하지 않는 개념으로부터 분리하고, 변하는 개념을 캡슐화해요. 요금 계산의 공통 흐름(통화 목록 순회 → 각 통화 요금 → 합산)은 추상 클래스에, 통화별 요금 계산(변하는 부분)은 자식 또는 정책 객체에. 그러면 새 요금제를 추가할 때 "어떤 클래스를 어떻게"가 자명해요.

    협력 패턴이 생기면 개념적 무결성이 생겨요. 새 요구사항에 기존 협력 패턴을 먼저 적용해 보고, 안 맞으면 패턴 자체를 개선. 지속적 리팩터링.

    디자인 패턴

    패턴은 "반복되는 설계 문제와 해결책에 붙인 이름". 소통 도구이자 설계 어휘. 패턴의 핵심은 특정 클래스 구조가 아니라 어떤 변경을 캡슐화하는가예요.

    패턴캡슐화하는 변경백엔드 예
    Strategy알고리즘/정책할인 정책, 결제 수단, 정렬 기준
    Template Method알고리즘의 일부 단계JdbcTemplate, AbstractController
    Decorator부가 기능의 조합스트림 래핑, 캐시/로깅/재시도 감싸기
    Composite개별과 집합의 동일 취급할인 조건 AND/OR 트리, 메뉴/카테고리
    Observer이벤트 수신자Spring ApplicationEvent, 도메인 이벤트
    Factory / Builder생성 방법복잡한 DTO, 테스트 픽스처
    State상태별 행동주문 상태 머신(PENDING → PAID → SHIPPED)
    Adapter / Facade외부 인터페이스외부 API 클라이언트 래핑, 레거시 모듈 경계

    패턴을 목적으로 쓰지 마세요. "Strategy를 적용하자"가 아니라 "알고리즘이 바뀔 것 같으니 분리하자 → 그게 Strategy". 변경 축이 없으면 패턴은 복잡성만 더해요.

    프레임워크와 제어 역전

    라이브러리는 내가 호출, 프레임워크는 나를 호출(제어 역전, "할리우드 원칙: 우리가 연락할게요"). 프레임워크가 흐름을 소유하고 내 코드는 확장 지점(hook)에 끼워 넣어요. 템플릿 메서드와 DI가 그 메커니즘. 스프링은 빈 생명주기·트랜잭션·요청 처리 흐름을 소유하고, 나는 Controller/Service를 등록만 해요. 그래서 "프레임워크 안에서 내 코드가 언제 어떻게 불리는가"를 모르면 트랜잭션 전파, 프록시, 이벤트 순서 같은 문제를 못 풀어요.

    백엔드에서는 주문 상태를 if (status == PAID) ... else if (status == SHIPPED)로 여러 메서드에 흩어 놓으면 상태가 추가될 때 전부 고쳐요. State 패턴이나 최소한 상태 전이 표(Map)로 한 곳에. 할인 조건 조합(순번 AND 기간, 또는 둘 중 하나)은 Composite. 외부 결제 API 응답 구조가 우리 도메인에 새어 들어오면 Adapter로 경계에서 변환. 그리고 스프링 @EventListener + @TransactionalEventListener는 Observer인데 "커밋 후"에 실행되는지 여부가 Outbox 필요성(분산 챕터 부록)과 직결돼요.
    핵심 정리
    • 변하는 것과 변하지 않는 것 분리 → 일관된 협력 패턴
    • 패턴 = 변경의 캡슐화에 붙인 이름. 변경 축이 있을 때만
    • 프레임워크 = 제어 역전. 내 코드가 언제 불리는지 알아야 함
    셀프 체크
    1. "디자인 패턴을 적용했는데 코드가 더 복잡해졌다"는 상황이 생기는 이유는?
    답 보기

    패턴은 특정 변경을 쉽게 하는 대가로 간접 계층(인터페이스, 추가 클래스)을 더해요. 그 변경이 실제로 일어나지 않으면 비용만 남아요. 예: 구현이 하나뿐이고 바뀔 계획 없는 Strategy, 상태가 2개뿐인 State. "어떤 변경을 위해?"에 답할 수 없으면 적용하지 말고, 변경이 두 번째 나타날 때 리팩터링으로 도입하세요.

    2부 클린 아키텍처 — 원칙과 경계

    설계 원칙 SOLID

    클린 아키텍처 3부 — 1부에서 본 것을 다섯 원칙으로 정리

    SRP 단일 책임 원칙

    "모듈은 하나의 액터에 대해서만 책임져야 한다". "한 가지 일"이 아니에요. Employee에 calculatePay()(회계팀), reportHours()(인사팀), save()(DBA)가 있으면 세 액터의 변경 요구가 한 클래스에서 충돌해요. 회계팀 요청으로 공통 메서드를 바꿨더니 인사팀 리포트가 깨짐. 해결: 액터별로 클래스 분리, 필요하면 Facade로 묶기. 변경 이유 = 액터.

    OCP 개방-폐쇄 원칙

    확장에 열리고 수정에 닫힘. 새 기능 = 새 코드, 기존 코드 수정 최소. 방법: 변경되는 부분을 추상화 뒤로. 컴포넌트 수준에서는 의존 방향을 "보호하고 싶은 쪽(고수준 정책)으로". 상위 수준은 하위 수준의 변경에서 보호받아야 해요. 재무 보고서 예: 보고서 계산(정책)은 화면/프린터 출력(세부)이 바뀌어도 안 바뀜.

    LSP 리스코프 치환

    1부 13장. 아키텍처 수준에서는 "인터페이스 사용자들이 구현체를 구분해야 하는 순간" LSP 위반. 택시 호출 예: 업체별로 REST 파라미터 이름이 다르면 디스패처에 if (company == "Acme")가 생겨요. 설정 테이블로 격리.

    ISP 인터페이스 분리

    사용하지 않는 것에 의존하지 마라. 큰 인터페이스를 쓰면 안 쓰는 메서드의 변경에도 재컴파일·재배포. 클라이언트별로 작은 인터페이스. 아키텍처 수준: 필요 없는 기능을 가진 프레임워크/모듈에 의존하면 그것의 변경에 끌려가요.

    DIP 의존성 역전

    1부 8장. 변동성 큰 구체 클래스를 참조·상속·오버라이드하지 마라. 추상 인터페이스만 참조. 구체 객체 생성은 main 컴포넌트(또는 DI 컨테이너)에 몰아넣고, 나머지는 추상만 알게. 추상 팩토리로 생성도 역전. 제어 흐름과 소스 의존성이 반대 방향 = 역전.

    백엔드에서는 SRP의 "액터" 기준이 실용적이에요. UserService에 가입(마케팅팀), 권한(보안팀), 정산(재무팀) 로직이 섞였다면 요청 주체별로 쪼개세요. ISP는 "Repository 인터페이스에 메서드 50개"를 유스케이스별 작은 포트로. DIP는 패키지 의존 규칙으로 강제(ArchUnit 테스트: domain은 infrastructure를 import 금지). 원칙을 코드 리뷰 어휘로 쓰면 "이 PR은 OCP 위반이에요(기존 switch에 case 추가)" 식으로 논의가 빨라져요.
    시니어 심화 본문은 SOLID를 코드 리뷰의 어휘로 쓰라고 했는데, 원칙을 과하게 적용하면 원칙이 막으려던 문제를 다시 만들어요. 가장 흔한 것이 중복을 없애려다 결합을 만드는 경우예요.

    상황

    주문 확인 메일과 배송 시작 메일의 코드가 80% 같아서 sendOrderMail(type, order) 하나로 합쳤어요. 처음에는 깔끔했어요.

    깨지는 과정

    1. 마케팅팀이 주문 메일에만 추천 상품을 넣어 달라고 해요. if (type == ORDER)가 하나 생겨요.
    2. 물류팀이 배송 메일에만 택배사와 송장 번호를 넣어 달라고 해요. if (type == SHIPPING)이 생겨요.
    3. 법무팀이 주문 메일에 환불 규정 문구를 넣어 달라고 하고, 배송 메일은 해외 배송일 때만 다른 문구가 필요해요. 분기 안에 분기가 생겨요.
    4. 6개월 뒤 메서드에는 플래그 다섯 개와 분기 여덟 개가 있어요. 주문 메일을 고치다가 배송 메일이 깨지는 장애가 나요. 테스트는 공통 메서드 하나에 대해서만 있어서 그 조합을 확인하지 못했어요.

    왜 이렇게 되나: 우연한 중복과 진짜 중복

    진짜 중복은 같은 지식이 두 곳에 있는 거예요. 배송비 계산 공식이 두 곳에 있다면, 공식이 바뀔 때 두 곳이 반드시 같이 바뀌어야 해요. 이런 중복은 반드시 하나로 합쳐야 해요. 우연한 중복은 지금 이 순간 모양만 같은 거예요. 두 메일은 우연히 비슷했을 뿐, 바뀌는 이유가 달라요. 하나는 마케팅팀이, 하나는 물류팀이 바꿔요. SRP가 말하는 "액터"(변경을 요청하는 사람)가 다른 코드를 합친 거예요.

    해결책

    • 합치기 전에 물어요. "이 둘은 같은 이유로, 같은 사람의 요청으로 바뀌는가?" 아니라면 모양이 같아도 따로 둬요.
    • 세 번째를 기다려요. 두 번째 비슷한 코드가 나오면 일단 복사하고 차이를 관찰해요. 세 번째가 나오면 무엇이 진짜 공통이고 무엇이 변하는지 보이기 시작해요. 잘못된 추상화보다 중복이 싸요.
    • 이미 플래그가 쌓였다면 먼저 되돌려요. 공통 메서드를 호출하는 곳마다 그 내용을 복사해 넣고(인라인), 각 호출에서 쓰지 않는 분기를 지워요. 그러면 각 메일 코드가 단순해져요. 그 뒤에 진짜 공통인 부분만 다시 뽑아요.
    • 공통화는 "방법" 수준에서 해요. 메일 발송, 템플릿 렌더링, 재시도 같은 메커니즘은 공통으로 두고, 메일에 무엇을 쓸지는 각 메일이 정해요.

    같은 문제가 더 큰 규모에서도 생겨요. 여러 서비스가 쓰는 공통 라이브러리에 비즈니스 로직을 넣으면, 라이브러리를 고칠 때마다 모든 서비스를 함께 배포해야 해요. 공통 라이브러리에는 기술적인 코드만 넣으세요.

    알아채는 법

    • type이나 boolean 파라미터로 분기하는 메서드가 커지고 있다면 우연한 중복을 합친 신호예요.
    • 한 기능을 고친 PR이 관련 없는 기능의 테스트를 깨뜨리는 일이 반복되면, 그 둘을 묶고 있는 공통 코드를 찾아보세요.
    • 공통 메서드의 호출자마다 서로 다른 플래그 조합을 넘기고 있다면, 이미 각자 다른 메서드가 돼야 할 때예요.
    핵심 정리
    • SRP = 액터당 하나, OCP = 추상으로 보호, LSP = 치환 가능
    • ISP = 쓰는 것만 의존, DIP = 추상에 의존·생성은 main으로

    답 보기

    "한 가지 일"은 주관적이에요(주문 처리는 한 가지? 결제·재고·배송?). "변경을 요구하는 사람/조직이 하나"로 정의하면 판단이 객관적이 돼요. 서로 다른 팀이 같은 클래스를 다른 이유로 바꾸면 충돌·회귀가 나니, 그 경계로 나누면 돼요. 조직 구조가 코드 구조를 결정한다는 콘웨이 법칙과도 연결돼요.

    컴포넌트 원칙

    클린 아키텍처 4부 — 클래스를 어떻게 묶고, 묶음 사이 의존은 어떻게

    컴포넌트란

    배포 단위(jar, gem, DLL, 마이크로서비스). 독립적으로 배포·개발 가능해야 해요.

    응집도 (무엇을 함께 묶나)

    • REP 재사용/릴리스 등가: 재사용 단위 = 릴리스 단위. 함께 버전 관리되고 릴리스 노트가 있는 것끼리.
    • CCP 공통 폐쇄: 같은 이유로 같은 시점에 변경되는 클래스를 같은 컴포넌트에. SRP의 컴포넌트 버전. 변경이 한 컴포넌트에 국한되면 재배포 범위가 작아요.
    • CRP 공통 재사용: 함께 재사용되지 않는 것을 같은 컴포넌트에 두지 마라. ISP의 컴포넌트 버전. 안 쓰는 클래스 때문에 재배포하지 않게.

    세 원칙은 긴장 관계예요. REP·CCP는 크게 묶고, CRP는 작게 나눠요. 프로젝트 초기는 CCP(개발 편의), 성숙하면 REP·CRP(재사용)로 무게가 옮겨가요.

    결합도 (컴포넌트 사이 의존)

    • ADP 의존성 비순환: 컴포넌트 의존 그래프에 사이클이 없어야(DAG). 사이클이 있으면 하나를 바꿀 때 전부 함께 릴리스해야 하고, 빌드 순서가 없고, 테스트가 어려워요. 끊는 법: DIP(인터페이스 추출) 또는 둘이 공유하는 새 컴포넌트 추출.
    • SDP 안정된 의존: 더 안정된 쪽으로 의존. 안정성 = 바꾸기 어려움 = 많은 컴포넌트가 의존함(들어오는 의존 많음, 나가는 의존 적음). 변경이 잦아야 할 컴포넌트가 안정된 컴포넌트에 의존되면 안 돼요. 지표 I = 나가는 / (들어오는 + 나가는). I가 작은 쪽으로 의존.
    • SAP 안정된 추상화: 안정된 컴포넌트는 추상적이어야(변경 없이 확장 가능), 불안정한 컴포넌트는 구체적이어야. 지표 A = 추상 클래스 비율. I와 A의 합이 1 근처(주계열)가 이상적. (0,0) = 고통 지대(안정+구체, DB 스키마·유틸), (1,1) = 쓸모없는 지대(불안정+추상).
    백엔드에서는 멀티 모듈 프로젝트(Gradle)에서 domain ← application ← infrastructure/api 방향이 SDP·SAP예요. domain은 가장 안정되고(모두가 의존) 추상적(인터페이스, 순수 로직), infrastructure는 불안정(자주 바뀜)하고 구체적. common/util 모듈에 뭐든 넣으면 고통 지대(모두가 의존하는데 자주 바뀜)가 돼요. 마이크로서비스에서 A ↔ B 상호 호출은 ADP 위반이고, 보통 이벤트나 공통 서비스 추출로 끊어요. 모듈 의존 사이클은 Gradle이 막아주고, 패키지 사이클은 ArchUnit으로.
    핵심 정리
    • 묶기: REP(릴리스 단위), CCP(같이 변경), CRP(같이 사용). 초기엔 CCP
    • 의존: ADP(사이클 금지), SDP(안정된 쪽으로), SAP(안정=추상)
    • common/util은 고통 지대 주의

    1. 두 모듈이 서로 의존(사이클)할 때 끊는 두 가지 방법은?
    답 보기

    (1) DIP: B가 A를 쓰는 부분을 인터페이스로 추출해 A 쪽(또는 별도)에 두고 B는 그걸 구현. 의존 방향이 한쪽으로. (2) 둘이 공유하는 것을 새 모듈 C로 추출해 A→C, B→C로. 어느 쪽이든 결과는 DAG여야 하고, 이후 사이클이 다시 생기지 않게 빌드/테스트로 강제.

    아키텍처 — 경계, 정책과 수준, 클린 아키텍처

    클린 아키텍처 5부 — 결정을 미루는 구조, 그리고 네 개의 동심원

    아키텍처의 목적

    "시스템을 쉽게 개발·배포·운영·유지보수하게 하는 것". 핵심 수단은 선택사항(세부사항)을 열어 두는 것: DB, 웹 프레임워크, 메시징, UI를 가능한 늦게 결정하고 바꿀 수 있게. 좋은 아키텍트는 결정을 최대한 미뤄요. 결정이 미뤄질수록 더 많은 정보로 결정하고, 실험이 쉬워요.

    독립성

    유스케이스(시스템의 의도가 구조에서 보여야 — 소리치는 아키텍처), 운영(확장 방식을 바꿀 수 있게), 개발(팀별 독립), 배포(독립 배포). 계층(UI/업무규칙/DB)과 유스케이스로 분리하되, 분리 방식은 소스 수준(모놀리스 안 모듈) → 배포 수준(jar 분리) → 서비스 수준(마이크로서비스)으로 필요에 따라. 처음부터 서비스로 자르면 비싸요. 경계는 그어 두되 물리적 분리는 미뤄요.

    경계 긋기

    경계는 변경 이유가 다른 것들 사이에. 업무 규칙 ↔ DB, 업무 규칙 ↔ UI, 업무 규칙 ↔ 외부 서비스. 경계를 가로지르는 호출은 인터페이스를 통해, 의존 방향은 항상 저수준(세부) → 고수준(정책). 플러그인 아키텍처: 업무 규칙이 중심, DB와 UI는 플러그인. FitNesse 사례: DB 결정을 끝까지 미루다 결국 필요 없었음.

    정책과 수준

    수준 = 입력·출력에서 얼마나 먼가. 암호화 프로그램: 문자 읽기·쓰기(저수준) ← 암호화 알고리즘(고수준). 의존은 저수준 → 고수준으로. 고수준 정책은 저수준 세부를 몰라야 변경에서 보호돼요.

    업무 규칙

    • 엔티티: 핵심 업무 규칙 + 데이터. 시스템이 없어도 존재하는 규칙(이자 계산). 어떤 DB·UI에도 독립.
    • 유스케이스: 애플리케이션 특화 업무 규칙. 입력·출력·처리 단계. 엔티티를 조작. UI 방식은 모름(웹인지 콘솔인지).
    • 요청·응답 모델: 유스케이스 입출력은 단순 데이터 구조. 엔티티나 웹 요청 객체를 그대로 쓰면 결합.

    클린 아키텍처 (동심원)

    경계를 가로지를 때 제어 흐름(Controller → UseCase → Presenter)과 소스 의존(모두 안쪽으로)이 다르면 DIP(출력 포트 인터페이스를 유스케이스가 소유, Presenter가 구현). 헥사고날(포트와 어댑터), 어니언, DCI 등은 같은 아이디어의 변형이에요.

    험블 객체, 서비스

    테스트하기 어려운 것(UI, DB 드라이버)과 쉬운 것(로직)을 분리. Presenter는 로직, View는 멍청하게(험블). 서비스(마이크로)는 아키텍처가 아니라 배포 단위. 서비스로 나눴다고 결합이 사라지지 않아요(공유 데이터, API 계약). 서비스 안에도 경계가 필요.

    세부사항

    DB는 세부사항(데이터 모델은 중요하지만 저장 기술은 아님), 웹도 세부사항(입출력 장치의 하나), 프레임워크는 세부사항(프레임워크와 결혼하지 마라 — 프레임워크는 우리에게 헌신하지 않음. 업무 규칙에 @Entity, @Autowired를 넣는 순간 결합). 가능하면 프레임워크를 바깥 원에 가두고 업무 규칙은 순수하게. 현실에서는 완전 분리의 비용이 크니 어디까지 분리할지 의식적으로 결정.

    백엔드에서는 스프링 프로젝트의 현실적 적용: domain(엔티티·값 객체·도메인 서비스·리포지토리 인터페이스, 스프링 의존 최소), application(유스케이스/서비스, @Transactional), adapter.in.web(Controller, DTO), adapter.out.persistence(JPA 엔티티·리포지토리 구현). JPA 엔티티를 도메인 모델로 겸할지는 트레이드오프예요. 분리하면 매핑 코드가 늘고, 안 하면 JPA 제약(기본 생성자, 프록시, 양방향)이 도메인을 오염해요. 작은 서비스는 겸하고, 핵심 도메인은 분리하는 절충이 흔해요. 중요한 건 "Controller가 Repository를 직접 호출" 같은 원 건너뛰기와 "domain이 web·jpa를 import" 같은 방향 위반을 막는 것. ArchUnit으로 테스트하세요.
    핵심 정리
    • 아키텍처 = 세부 결정을 미루는 구조. DB·웹·프레임워크는 세부
    • 경계는 변경 이유가 다른 곳에, 의존은 항상 안쪽(정책)으로
    • 엔티티(핵심 규칙) → 유스케이스 → 어댑터 → 프레임워크. 헥사고날은 변형
    • 분리 수준(소스/배포/서비스)은 필요에 따라 올림
    셀프 체크
    1. "의존성 규칙"을 한 문장으로 말하고, 스프링 프로젝트에서 위반하는 전형적 예 두 가지를 드세요.
    2. 유스케이스 계층이 Controller의 Request DTO를 그대로 받으면 안 되는 이유는?
    답 보기

    1. 소스 코드 의존성은 항상 안쪽(고수준 정책)을 향해야 하고, 안쪽 원은 바깥 원의 어떤 것도 알면 안 된다. 위반 예: (a) 도메인 엔티티가 HttpServletRequest나 web DTO를 import, (b) 도메인 서비스가 JpaRepository 구체 타입이나 @Query를 직접 의존, (c) Controller가 Repository를 직접 호출해 유스케이스 원을 건너뜀.

    2. Request DTO는 웹(바깥 원)의 형식이에요. 유스케이스가 그걸 받으면 안쪽이 바깥에 의존해요. 웹 필드가 바뀌면(JSON 이름, 검증 애너테이션) 유스케이스가 바뀌고, 같은 유스케이스를 배치나 메시지 소비자에서 호출할 때 웹 DTO를 억지로 만들어야 해요. 유스케이스는 자기 입력 모델(Command)을 정의하고 Controller가 변환해요.

    부록 — 테스트

    테스트 — 종류, 더블, 테스트하기 쉬운 설계

    설계의 품질은 테스트 작성의 쉬움으로 드러난다

    테스트 피라미드

    종류범위속도비중도구
    단위클래스·함수, 외부 I/O 없음ms많이JUnit, 순수 객체
    통합DB·메시징·외부 연동 포함초중간Testcontainers, @DataJpaTest, WireMock
    E2E / 인수배포된 시스템 전체, 사용자 시나리오분핵심 흐름만REST Assured, Playwright

    단위 테스트가 많아야 하는 이유: 빠르고, 실패 원인이 명확하고, 설계 피드백을 줘요. 단위 테스트를 쓰기 어렵다면 설계 문제예요(의존성이 숨어 있거나, 책임이 섞여 있거나).

    테스트 더블

    • Dummy: 인자를 채우기만, 사용 안 됨.
    • Stub: 정해진 값을 반환. "findById(1)이 이 사용자를 돌려줌". 상태 검증용.
    • Spy: 실제 동작 + 호출 기록.
    • Mock: 기대한 호출이 일어났는지 행위 검증. "sendEmail이 이 인자로 한 번 호출됐는가".
    • Fake: 실제로 동작하는 단순 구현. 인메모리 Map 리포지토리. 가장 읽기 쉽고 리팩터링에 강해요.

    Mock 과용의 문제: 행위 검증은 "어떻게 호출했나"(구현)를 고정해요. 리팩터링으로 호출 순서·횟수가 바뀌면 동작이 같아도 테스트가 깨져요. 테스트가 안전망이 아니라 족쇄가 돼요. Mock은 경계의 외부 효과(메일 발송, 결제 API 호출)에만. 저장소는 Fake, 계산은 실제 객체.

    테스트하기 쉬운 설계

    • 순수 함수·순수 객체: 같은 입력 → 같은 출력, 부수효과 없음. 핵심 로직을 여기로 몰면 테스트가 가장 쉬워요. 1부의 "책임을 데이터 가진 객체로"가 바로 이것.
    • 의존성 주입: 생성자로 받으면 테스트에서 Fake를 넣을 수 있어요. 메서드 안 new, static 호출, 싱글톤은 교체 불가.
    • 시간·난수·환경 주입: LocalDateTime.now() 대신 Clock, Random 대신 주입된 공급자. "자정 넘어가면 깨지는 테스트"가 사라져요.
    • 부수효과를 바깥으로: 판단(순수)과 실행(I/O)을 분리. "어떤 메일을 보낼지 결정"(테스트 쉬움)과 "메일 보내기"(Mock 하나).
    • 험블 객체: 테스트 어려운 것(UI, 프레임워크 접점)을 얇게.

    좋은 테스트의 조건

    FIRST: Fast, Independent(순서 무관), Repeatable(환경 무관), Self-validating(자동 판정), Timely. 그리고 테스트 이름이 요구사항을 설명해야 해요(할인_조건을_만족하면_금액을_차감한다). Given-When-Then 구조. 테스트 하나에 검증 하나(개념적으로). 테스트 코드도 리팩터링 대상 — 중복은 픽스처·빌더로.

    백엔드에서는 @SpringBootTest로 모든 테스트를 돌리면 느려서 안 돌리게 돼요. 도메인 로직은 스프링 없이 순수 JUnit, 리포지토리는 @DataJpaTest + Testcontainers(H2는 MySQL과 달라서 운영에서만 터지는 쿼리가 생겨요), 외부 API는 WireMock, 전체는 핵심 시나리오 몇 개만 @SpringBootTest. 테스트가 when(repo.findById(1)).thenReturn(...)로 30줄이면 Fake 리포지토리를 만드세요. 그리고 "테스트 커버리지 80%"보다 "핵심 업무 규칙이 테스트로 문서화됐는가"가 기준이에요.
    시니어 심화 본문은 좋은 테스트의 조건을 다뤘는데, 테스트 스위트를 오래 운영하면 가장 큰 적은 가끔 실패하는 테스트예요. 하나만 있어도 팀 전체가 테스트 실패를 무시하게 만들어요.

    상황

    CI의 테스트 2,000개 중 다섯 개가 가끔 실패해요. 실패하면 "재실행" 버튼을 누르는 게 관행이 됐어요. 어느 날 진짜 버그 때문에 실패한 테스트도 재실행했고, 우연히 통과해서 배포됐어요. 그 버그가 운영 장애가 됐어요.

    깨지는 과정

    각자 1% 확률로 실패하는 테스트가 다섯 개면, 빌드가 이유 없이 실패할 확률은 약 5%예요. 스무 번에 한 번은 빨간불이 거짓말이에요. 사람들은 빨간불을 보면 "또 그거겠지" 하고 재실행하도록 훈련돼요. 테스트가 존재하는 이유, 즉 실패가 곧 버그라는 신호가 사라져요.

    흔한 원인과 해결

    • 실제 현재 시각: LocalDate.now()를 직접 부르는 코드는 자정 근처, 월말, 그리고 CI 서버의 시간대(대개 UTC)에서 실패해요. Clock을 주입받게 하고 테스트에서는 Clock.fixed(...)로 고정해요.
    • 공유 상태와 실행 순서: 테스트 A가 DB에 남긴 데이터 때문에 "주문 개수"를 세는 테스트 B가 실패해요. 병렬 실행이나 순서 변경 때만 드러나요. 테스트마다 자기 데이터를 만들고, 다른 테스트와 겹치지 않는 ID를 써요. @Transactional 롤백은 편하지만, 다른 스레드에서 커밋되는 비동기 코드는 롤백되지 않는다는 점을 주의해요. 테스트 실행 순서를 무작위로 돌려 보면 숨은 의존이 미리 드러나요.
    • 비동기 결과를 sleep으로 기다리기: Thread.sleep(1000)은 CI가 느린 날 실패하고, 빠른 날은 시간만 버려요. Awaitility의 await().atMost(5, SECONDS).until(...)처럼 조건이 만족되는 즉시 진행하는 방식으로 바꿔요.
    • 외부 의존: 실제 외부 API나 여러 사람이 같이 쓰는 개발 DB에 붙는 테스트는 남의 상태 때문에 실패해요. 외부 API는 WireMock으로, DB는 Testcontainers로 테스트마다 격리된 인스턴스를 띄워요.
    • 기타: HashMap의 순회 순서를 가정한 단언, 고정 포트를 쓰다 포트가 겹치는 테스트도 자주 나와요.

    팀의 운영 규칙

    • 발견하면 바로 격리해요. 메인 빌드에서 빼서 따로 돌리고(@Tag("flaky")), 담당자와 기한을 정해요. 격리 목록이 계속 늘어나면 안 돼요.
    • 자동 재시도는 신호를 숨겨요. 실패 시 자동 재실행을 켰다면, 재실행으로 통과한 테스트도 반드시 기록해서 목록으로 봐요.
    • 실행 시간에도 예산을 둬요. PR 검증이 10분을 넘기면 사람들이 로컬에서 돌리지 않고 올리기 시작해요. 스프링 테스트에서는 @MockBean을 테스트 클래스마다 다르게 쓰면 스프링 컨텍스트가 매번 새로 만들어져서 느려지는 경우가 많아요. 느린 테스트 상위 목록을 정기적으로 확인하세요.

    알아채는 법

    • CI에서 테스트별 결과 이력을 모아요. 같은 커밋에서 성공과 실패가 모두 나온 테스트는 가끔 실패하는 테스트로 확정이에요. JUnit XML 결과를 모아 집계하거나, 빌드 분석 도구의 flaky 감지 기능을 써요.
    • "재실행" 버튼이 눌린 횟수를 주 단위로 보면 팀이 테스트를 얼마나 믿는지 보여요.
    핵심 정리
    • 단위 많이, 통합 적당히, E2E 핵심만. 단위 테스트 어려움 = 설계 문제
    • Fake > Stub > Mock. Mock은 외부 효과 경계에만
    • 순수 로직 + 의존성·시간 주입 + 부수효과 분리 = 테스트 쉬운 설계
    셀프 체크
    1. Mock이 많은 테스트가 리팩터링을 방해하는 구체적 상황을 들어보세요.
    2. OrderService.place()가 재고 확인 → 주문 저장 → 메일 발송을 한다면 어떤 더블을 어디에 쓰나요?
    답 보기

    1. 테스트가 verify(repo).findById(1); verify(repo).save(any())를 검증하는데, 리팩터링으로 findById를 findWithItemsById로 바꾸거나 save를 한 번 덜 호출하게 했어요. 동작(주문이 저장됨)은 같은데 테스트가 깨져요. 결과(저장된 주문의 상태)를 검증했다면 안 깨졌을 거예요.

    2. 재고·주문 저장소: 인메모리 Fake(실제 저장·조회 동작, 테스트 후 상태 검증 가능). 메일 발송: Mock 또는 기록하는 Spy("이 주문에 대해 한 번 호출"). 재고 확인·주문 생성 로직 자체는 실제 도메인 객체. 시간은 고정 Clock 주입.
