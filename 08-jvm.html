    JVM과 자바 동시성

    기준 교재: 자바 병렬 프로그래밍(JCIP) + 자바 최적화(Optimizing Java) · 4~6주

    앞의 챕터들의 예시는 대부분 자바와 스프링이었어요. 이 챕터는 그 코드가 실제로 돌아가는 런타임을 봐요. 바이트코드가 어떻게 실행되는지, 객체가 어디에 놓이고 언제 치워지는지, 여러 스레드가 같은 메모리를 볼 때 무엇이 보장되는지예요.

    예시는 쇼핑몰의 주문 API 서버(스프링 부트)예요. 배포 직후 느린 이유, 메모리가 새는 이유, 동시 요청에서 값이 틀어지는 이유를 따라가요. 운영체제 챕터의 2부(병행성)를 먼저 읽고 오세요. 다른 언어를 주로 쓴다면 개념은 그대로 두고 그 런타임의 구현으로 바꿔 읽으면 돼요.

    1장 JVM 구조와 클래스 로딩

    로컬에서는 되는데 운영에서 NoSuchMethodError가 난다

    문제: 컴파일은 됐는데 실행 중에 메서드가 없다

    주문 API 서버에 새 기능을 배포했더니 특정 요청에서 NoSuchMethodError가 났어요. 로컬에서는 잘 돌았고, 컴파일 에러도 없었어요. 컴파일러가 확인한 메서드가 실행할 때는 왜 없을까요? 답을 찾으려면 자바 코드가 실행되기까지의 과정을 알아야 해요.

    소스에서 실행까지

    컴파일러(javac)는 소스를 특정 CPU가 아니라 JVM을 위한 명령어인 바이트코드로 바꿔 .class 파일에 담아요. 실행할 때는 클래스 로더가 필요한 클래스 파일을 찾아 메모리에 올리고, 실행 엔진이 바이트코드를 실행해요. 처음에는 한 줄씩 해석하는 인터프리터로 돌고, 자주 실행되는 부분은 JIT 컴파일러가 기계어로 바꿔요(2장). 그리고 쓰이지 않는 객체는 가비지 컬렉터가 치워요(4장).

    중요한 점은 컴파일할 때 본 클래스와 실행할 때 올라오는 클래스가 다를 수 있다는 거예요. 컴파일러는 빌드 도구가 준 라이브러리를 보고 확인하지만, 실행할 때 클래스 로더는 그 순간의 클래스패스에서 클래스를 찾아요.

    클래스는 처음 쓰일 때 준비된다

    클래스 로딩은 세 단계예요. 파일을 읽어 올리는 로딩, 바이트코드를 검증하고 다른 클래스에 대한 참조를 연결하는 링킹, 정적 필드에 값을 넣고 정적 초기화 블록을 실행하는 초기화예요. 초기화는 프로그램이 시작할 때가 아니라 그 클래스가 처음 실제로 쓰일 때 일어나요.

    부모에게 먼저 묻는다

    클래스 로더는 계층을 이뤄요. 클래스를 찾으라는 요청을 받으면 먼저 부모 로더에게 넘기고, 부모가 못 찾을 때만 자기가 찾아요(부모 위임). 그래서 애플리케이션이 java.lang.String을 다른 것으로 바꿔치기할 수 없어요. 그리고 JVM에게 클래스의 정체는 이름과 그 클래스를 올린 로더의 조합이에요. 이름이 같아도 다른 로더가 올리면 다른 클래스예요.

    다시 문제로

    이제 NoSuchMethodError의 원인이 보여요. 우리 코드는 JSON 라이브러리 2.15 버전의 새 메서드를 쓰도록 컴파일됐어요. 그런데 다른 의존성이 같은 라이브러리의 2.12 버전을 끌고 왔고, 실행 시 클래스패스에서 2.12가 먼저 잡혔어요. 클래스 이름은 같으니 로딩은 성공했지만, 그 버전에는 새 메서드가 없었던 거예요.

    백엔드에서는 ClassNotFoundException은 이름으로 클래스를 찾았는데 없을 때, NoClassDefFoundError는 컴파일할 때는 있었는데 실행할 때 없거나 초기화에 실패했을 때, NoSuchMethodError는 거의 항상 의존성 버전 충돌이에요. 빌드 도구로 의존성 트리를 출력(./gradlew dependencies)해서 같은 라이브러리의 버전이 여러 개 있는지 확인하고, 실제 배포 산출물(jar 안의 라이브러리 목록, 컨테이너 이미지)도 확인하세요. 로컬과 운영의 차이는 대개 거기서 나와요.
    시니어 심화 "처음 쓰일 때 초기화된다"는 성질이 운영에서 뜻밖의 멈춤을 만들어요. 클래스 초기화는 락을 잡고 실행되고, 한 번 실패하면 되돌릴 수 없어요.

    상황

    할인 정책 클래스의 정적 초기화 블록이 원격 설정 서버에서 할인 규칙을 읽어 와요. 배포 직후 1~2분 동안 주문 API가 몇 초씩 멈췄어요. 그리고 한 번은 설정 서버가 잠깐 응답하지 않은 날 배포했는데, 그 서버는 재시작할 때까지 모든 주문이 실패했어요.

    깨지는 과정

    1. 모두가 한 스레드를 기다려요. 배포 직후 첫 주문 요청 200개가 동시에 들어와요. 할인 정책 클래스를 처음 쓰는 순간이라, 한 스레드만 초기화를 실행하고 나머지 199개는 그 초기화가 끝날 때까지 기다려요. 원격 호출이 2초 걸리면 199개 요청이 모두 2초씩 늦어요.
    2. 실패하면 영원히 실패해요. 정적 초기화 중에 예외가 나면 첫 호출은 ExceptionInInitializerError를 받아요. 그 뒤로 그 클래스를 쓰는 모든 호출은 NoClassDefFoundError: Could not initialize class를 받아요. JVM은 초기화를 다시 시도하지 않아요. 설정 서버가 몇 초 뒤 살아나도 소용없고, 재시작해야만 풀려요.
    3. 서로를 기다리면 데드락이에요. 클래스 A의 정적 초기화가 클래스 B를 쓰고, B의 정적 초기화가 A를 쓴다고 해 봐요. 스레드 1이 A의 초기화를, 스레드 2가 B의 초기화를 동시에 시작하면 서로의 초기화가 끝나기를 영원히 기다려요.

    해결책

    • 정적 초기화에는 I/O를 넣지 않아요. 원격 호출, 파일 읽기, DB 조회는 정적 블록에서 하지 않아요.
    • 무거운 준비는 애플리케이션 시작 단계에서 명시적으로 해요. 스프링 빈의 초기화 메서드나 ApplicationRunner에서 하고, 실패하면 애플리케이션 시작 자체를 실패시켜요. 준비 상태 검사를 통과하기 전이라 트래픽이 들어오지 않고, 배포 도구가 실패를 바로 알아요.
    • 실패해도 회복할 수 있게 해요. 원격 설정은 실패하면 마지막으로 성공한 값이나 기본값을 쓰고, 주기적으로 다시 시도하는 구조로 만들어요. 정적 초기화와 달리 다음 시도에서 회복할 수 있어요.
    • 정적 필드 사이의 순환 의존을 없애요. 클래스끼리 서로의 정적 값을 참조하지 않게 해요.

    운영에서 알아채는 법

    • 로그에서 "Could not initialize class"를 검색하는 알림을 걸어요. 이 에러를 보면 원래 원인은 그보다 앞에 딱 한 번 찍힌 ExceptionInInitializerError에 있어요.
    • 배포 직후 몇 분 동안의 p99를 따로 봐요. 매 배포마다 튀면 초기화나 워밍업 문제예요.
    • 멈춘 서버의 스레드 덤프에서 여러 스레드가 같은 클래스의 초기화를 기다리고 있다면 이 문제예요. 최근 JDK는 스레드 덤프에 클래스 초기화를 기다리는 중이라고 표시해 줘요.
    핵심 정리
    • 소스 → 바이트코드 → 클래스 로더 → 인터프리터 + JIT
    • 컴파일 때와 실행 때의 클래스패스는 다를 수 있음. 버전 충돌은 NoSuchMethodError로
    • 클래스는 처음 쓰일 때 초기화. 부모 위임, 정체는 이름 + 로더
    셀프 체크
    1. NoSuchMethodError가 운영에서만 발생했습니다. 가장 먼저 의심할 것은 무엇인가요?
    답 보기

    의존성 버전 충돌이에요. 컴파일할 때 본 라이브러리 버전에는 그 메서드가 있었는데, 실행 시 클래스패스에서 먼저 잡힌 버전에는 없는 거예요. 서로 다른 라이브러리가 같은 의존성의 다른 버전을 끌고 오거나, 운영 환경(컨테이너 이미지, 서버의 공용 라이브러리)에 다른 버전이 있을 때 생겨요. 실제 배포 산출물의 의존성 트리와 포함된 jar 목록을 확인해요.

    2장 JIT 컴파일과 워밍업

    배포 직후 몇 분 동안만 느린 이유

    문제: 배포할 때마다 p99가 튄다

    주문 API 서버는 평소 p99 응답 시간이 80ms인데, 배포 직후 2~3분 동안은 400ms까지 올라가요. 코드도 데이터도 같은데 왜 시작 직후에만 느릴까요?

    JVM은 전부를 미리 컴파일하지 않는다

    JVM은 시작할 때 모든 코드를 기계어로 바꾸지 않아요. 처음에는 바이트코드를 한 줄씩 해석하는 인터프리터로 실행하면서, 메서드마다 몇 번 호출됐는지와 반복문이 몇 번 돌았는지를 세요. 자주 실행되는 부분만 골라서 컴파일해요. 실행되지도 않을 코드를 컴파일하는 비용을 아끼려는 거예요.

    컴파일도 두 단계예요. 먼저 빠르게 컴파일하는 C1 컴파일러가 적당히 최적화한 기계어를 만들고, 그 코드가 실행되면서 정보를 더 모아요. 정말 많이 실행되는 부분은 느리지만 강하게 최적화하는 C2 컴파일러가 다시 컴파일해요.

    실행 정보에 기댄 최적화

    C2가 빠른 이유는 실제로 실행된 모습을 보고 최적화하기 때문이에요. 짧은 메서드의 호출을 호출한 자리에 펼쳐 넣고(인라이닝), 메서드 밖으로 나가지 않는 객체는 힙에 만들지 않고(탈출 분석), 인터페이스 호출인데 실제로는 구현체 하나만 온다면 그 구현체를 직접 불러요.

    이 최적화들은 "지금까지는 이랬다"는 가정 위에 있어요. 새 구현체가 로드되거나 한 번도 안 타던 분기를 타면 가정이 깨지고, JVM은 컴파일된 코드를 버리고 인터프리터로 돌아갔다가 다시 컴파일해요. 이것을 역최적화라고 해요.

    워밍업

    이제 배포 직후가 느린 이유가 보여요. 시작 직후에는 대부분의 코드가 인터프리터로 돌고 있고, 동시에 컴파일 스레드가 CPU를 쓰면서 열심히 컴파일하고 있어요. 요청 처리와 컴파일이 CPU를 나눠 쓰는 거예요. 자주 쓰는 경로가 C2로 컴파일될 때까지의 이 구간을 워밍업이라고 해요. 커넥션 풀이 채워지고 캐시가 차는 시간도 여기에 더해져요.

    백엔드에서는 새 인스턴스에 바로 정상 트래픽을 주지 마세요. 준비 상태 검사를 통과하기 전에 주요 API를 몇백 번 호출해 미리 데우거나, 로드밸런서의 점진적 투입(새 인스턴스에 조금씩 늘려 가며 트래픽을 주는 기능)을 쓰세요. CPU limit이 작은 컨테이너는 컴파일 스레드와 요청 처리가 적은 CPU를 다퉈서 워밍업이 훨씬 길어져요.
    핵심 정리
    • 자주 실행되는 코드만 컴파일. 인터프리터 → C1 → C2
    • 최적화는 실행 정보에 기댄 가정. 깨지면 역최적화
    • 시작 직후가 가장 느림(워밍업). 미리 데우거나 점진적으로 투입
    셀프 체크
    1. 마이크로 벤치마크에서 반복문을 몇 번 돌려 시간을 재는 방식이 왜 부정확한가요?
    답 보기

    처음 반복은 인터프리터로 실행되고 도중에 컴파일이 일어나 속도가 바뀌어요. 또 JIT는 결과를 쓰지 않는 계산을 통째로 지우거나 상수로 바꿀 수 있어서, 재려던 코드가 실제로는 실행되지 않을 수도 있어요. 측정 반복문 자체가 실제 서비스와 다른 모양으로 최적화되기도 해요. 그래서 워밍업 반복, 결과 소비, 별도 프로세스 실행을 처리해 주는 전용 도구(JMH)를 써야 해요.

    3장 메모리 영역과 객체

    힙은 4GB로 잡았는데 컨테이너는 왜 5GB 한도에서 죽었나

    문제: 힙보다 훨씬 많이 쓴다

    주문 API 서버의 힙을 -Xmx4g로 잡고 컨테이너 메모리 한도를 5GB로 줬어요. 1GB나 여유가 있으니 괜찮을 줄 알았는데, 트래픽이 몰리자 컨테이너가 OOMKilled로 죽었어요. 힙 사용량은 3GB였어요. 나머지는 어디서 쓴 걸까요?

    JVM 프로세스의 메모리는 힙만이 아니다

    힙은 모든 객체와 배열이 놓이는 곳이고 모든 스레드가 함께 써요. -Xmx가 정하는 것은 이 영역뿐이에요. 그 밖에도 영역이 여럿 있어요.

    스택은 스레드마다 하나씩 있어요. 메서드를 호출할 때마다 지역 변수와 중간 계산값을 담은 칸(프레임)이 쌓여요. 원시 타입 지역 변수는 값이 스택에 그대로 있고, 객체는 힙에 있으며 스택에는 그 위치(참조)만 있어요. 스레드 하나의 스택은 보통 1MB 안팎을 예약하므로, 스레드가 500개면 스택만 수백 MB예요.

    메타스페이스는 로딩된 클래스의 정보를, 코드 캐시는 JIT가 만든 기계어를 담아요. 네트워크 라이브러리(Netty 등)가 힙 밖에 직접 잡는 다이렉트 버퍼도 있고, GC가 쓰는 자료구조도 메모리를 차지해요. 이것들을 다 더하면 힙보다 1~2GB 많아지는 것이 흔해요.

    객체는 생각보다 크다

    객체는 필드만 차지하지 않아요. 모든 객체 앞에는 헤더(64비트 JVM에서 보통 12바이트)가 붙고, 전체 크기는 8바이트 단위로 맞춰져요. 그래서 4바이트 정수를 담은 Integer 객체 하나가 16바이트예요. List<Integer>에 백만 개를 담으면 값은 4MB인데 실제로는 객체와 참조를 합쳐 20MB 가까이 써요.

    OutOfMemoryError는 종류를 봐야 한다

    에러 메시지 뒤에 붙는 설명이 원인을 알려줘요. Java heap space는 힙이 꽉 찬 것으로 누수이거나 그냥 작게 잡은 거예요. Metaspace는 클래스를 너무 많이 올린 것(동적 클래스 생성, 클래스 로더 누수), Direct buffer memory는 힙 밖 버퍼의 한도 초과, unable to create native thread는 운영체제가 스레드를 더 만들어 주지 못한 거예요. 그리고 컨테이너의 OOMKilled는 JVM의 에러가 아니라 운영체제가 프로세스 전체 메모리를 보고 죽인 거예요.

    백엔드에서는 컨테이너에서는 힙을 고정 값 대신 메모리 한도의 비율(-XX:MaxRAMPercentage=70 정도)로 잡고, 나머지를 힙 밖 영역에 남기세요. 그리고 -XX:+HeapDumpOnOutOfMemoryError는 항상 켜 두세요. 죽는 순간의 힙이 누수를 찾는 가장 좋은 증거예요. GC가 있는 언어에도 누수는 있어요. 만료 없는 정적 Map 캐시, 지우지 않은 ThreadLocal, 해제하지 않은 리스너처럼 참조가 남아 있으면 GC는 치우지 못해요.
    시니어 심화 힙 덤프를 열면 "무엇이 많은가"부터 보게 되는데, 누수를 찾을 때는 "누가 붙잡고 있는가"가 중요해요.

    상황

    주문 API 서버의 힙이 일주일에 걸쳐 조금씩 차다가 결국 OutOfMemoryError로 죽어요. 힙 덤프를 열었더니 byte[]가 45%, String이 20%였어요. 이 숫자만으로는 어디를 고쳐야 할지 알 수 없었어요.

    왜 "무엇이 많은가"로는 안 되나

    1. byte[]와 String은 거의 모든 객체가 안에 품고 있어요. 그것이 많다는 것은 "무언가가 많다"는 뜻일 뿐이에요.
    2. 누수의 원인은 그 작은 객체들을 수백만 개 거느리고 있는 하나의 객체예요. 그 객체는 자기 크기가 작아서 크기 순 목록에서는 보이지 않아요.
    3. 그래서 "이 객체가 사라지면 함께 회수될 크기"와 "이 객체를 누가 붙잡고 있는가"를 봐야 해요.

    해결책: 덤프를 얻고 읽는 법

    • 덤프를 확보해요. -XX:+HeapDumpOnOutOfMemoryError와 -XX:HeapDumpPath를 항상 켜 두면 죽는 순간의 덤프가 남아요. 운영 중에 직접 뜨려면 jcmd <pid> GC.heap_dump를 쓰는데, 힙 크기에 비례해 수 초에서 수십 초 동안 애플리케이션이 멈춰요. 트래픽을 뺀 서버에서 떠요. 덤프에는 개인정보가 그대로 들어 있으니 보관과 공유에 주의해요.
    • 회수될 크기(retained size)로 정렬해요. Eclipse MAT의 지배자 트리(dominator tree)는 각 객체가 사라지면 함께 회수될 크기를 보여 줘요. 수많은 작은 객체를 거느린 정적 캐시 하나가 맨 위로 올라와요.
    • GC 루트까지의 경로를 따라가요. 그 객체에서 "Path to GC Roots"를 열면 "정적 필드 OrderCache.instance, 그 안의 HashMap, 엔트리 수백만 개"처럼 붙잡고 있는 사슬이 보여요. 이 사슬이 고쳐야 할 코드를 알려줘요.
    • 두 시점을 비교해요. 몇 시간 간격으로 덤프 두 개를 떠서 클래스별 개수를 비교하면, 계속 늘어나는 클래스가 바로 보여요.

    흔한 범인은 정해져 있어요. 크기 상한 없는 정적 캐시(위 예는 캐시 키에 요청마다 다른 타임스탬프가 들어가서 같은 키가 재사용되지 않았어요. Caffeine의 maximumSize로 상한을 둬요), 등록만 하고 해제하지 않은 리스너, 정리하지 않은 ThreadLocal(OS 챕터 26장 시니어), equals와 hashCode가 잘못돼서 같은 키가 계속 새로 들어가는 맵이에요.

    힙은 멀쩡한데 프로세스 메모리가 계속 는다면 힙 밖이에요. -XX:NativeMemoryTracking=summary를 켜고 jcmd <pid> VM.native_memory summary를 시간 간격을 두고 비교하면 어느 영역이 자라는지 보여요(OS 챕터 13장 시니어).

    운영에서 알아채는 법

    • GC가 끝난 직후의 늙은 세대 사용량, 즉 "살아 있는 데이터 크기"(Micrometer의 jvm.gc.live.data.size)를 지표로 봐요. 이 바닥값이 며칠에 걸쳐 계속 오르면 누수예요. 힙 사용량 자체는 GC 때문에 오르내려서 추세가 잘 안 보여요.
    • OOM이 나기 전에 바닥값이 힙의 70%를 넘으면 알림을 보내서, 죽기 전에 덤프를 뜰 시간을 벌어요.
    핵심 정리
    • 힙(객체) · 스택(스레드별) · 메타스페이스 · 코드 캐시 · 힙 밖 버퍼
    • 프로세스 메모리 = 힙 + 그 밖. 컨테이너 한도는 넉넉히, 힙은 비율로
    • OOM은 종류를 구분. 힙 덤프 옵션은 항상 켜 둠
    셀프 체크
    1. GC가 있는 언어에서도 메모리 누수가 생기는 이유를 설명하세요.
    답 보기

    GC는 어디에서도 도달할 수 없는 객체만 회수해요. 프로그램이 더 이상 쓰지 않는 객체라도 어딘가에서 참조가 이어져 있으면 GC가 보기에는 살아 있는 객체예요. 만료 없이 계속 쌓이는 정적 맵, 스레드풀 스레드에 남은 ThreadLocal 값, 해제하지 않은 리스너가 그런 참조예요. 그래서 누수를 찾는 일은 "쓰지 않는데 붙잡혀 있는 참조 경로"를 찾는 일이에요.

    4장 가비지 컬렉션의 원리

    무엇이 쓰레기이고, 왜 어떤 객체는 비싸게 치워지는가

    문제: 1분마다 응답이 300ms씩 튄다

    주문 API 서버의 응답 시간 그래프에 1분 간격으로 뾰족한 튐이 있어요. GC 로그를 보니 그 시각마다 GC가 수백 밀리초 동안 애플리케이션을 멈췄어요. GC는 무엇을 하길래 멈추고, 왜 어떤 때는 짧고 어떤 때는 길까요?

    쓰레기는 도달할 수 없는 것

    GC는 "이 객체를 아직 쓰는가"를 직접 알 수 없어요. 대신 확실히 살아 있는 출발점들, 즉 GC 루트(실행 중인 스레드의 스택에 있는 지역 변수, 정적 필드 등)에서 참조를 따라가며 닿는 객체를 전부 표시해요. 닿지 않은 객체가 쓰레기예요.

    참조 개수를 세는 방식이 아니라서, 위 그림의 D와 E처럼 서로를 가리키지만 밖에서 닿을 수 없는 묶음도 쓰레기로 회수돼요.

    치우는 방법

    표시가 끝나면 치워야 해요. 쓰레기 자리를 비우기만 하면 빈 공간이 여기저기 흩어져서, 큰 객체를 놓을 연속된 공간이 없어져요(단편화). 살아 있는 객체를 한쪽으로 모으면 단편화는 없지만 객체를 옮기는 비용이 들어요. 또 하나의 방법은 살아 있는 객체만 다른 영역으로 복사하고 원래 영역을 통째로 비우는 거예요. 복사 방식의 비용은 살아 있는 객체 수에만 비례해요. 쓰레기가 아무리 많아도 건드리지 않으니까요.

    대부분의 객체는 금방 죽는다

    주문 API 요청 하나를 처리하면서 만든 DTO, 문자열, 리스트는 응답이 나가는 순간 전부 쓰레기가 돼요. 이처럼 대부분의 객체는 만들어진 직후에 죽는다는 관찰을 세대 가설이라고 해요. 그래서 힙을 둘로 나눠요.

    새 객체는 젊은 세대에 만들어져요. 여기는 자주, 복사 방식으로 수집해요. 대부분이 이미 죽어 있어서 복사할 것이 적으니 빨라요. 여러 번의 수집에서 살아남은 객체는 늙은 세대로 옮겨지고, 여기는 덜 자주 수집해요.

    멈춤

    객체를 옮기거나 참조 관계를 정확히 훑으려면 그동안 애플리케이션이 참조를 바꾸면 안 되니, 애플리케이션 스레드를 잠깐 멈추는 구간이 있어요(stop-the-world). 위 문제의 튐이 이 멈춤이에요. 젊은 세대 수집의 멈춤은 보통 짧고, 늙은 세대를 정리하는 수집은 길어요. GC 기술의 역사는 이 멈춤을 줄이는 방향이에요(5장).

    백엔드에서는 요청마다 만들어지는 임시 객체는 젊은 세대에서 싸게 사라지니 걱정하지 않아도 돼요. 비싼 것은 중간쯤 사는 객체예요. 수 초에서 수 분 사는 객체, 예를 들어 잠깐 캐시에 있다가 밀려나는 항목이나 큰 배치 작업의 중간 결과는 늙은 세대로 옮겨진 뒤에 죽어서 비싼 수집을 일으켜요. 캐시는 아주 오래 살거나(크기 고정) 아주 짧게 살게 설계하세요.
    시니어 심화 GC 설정을 바꾸기 전에 먼저 볼 숫자가 할당률, 즉 애플리케이션이 초당 몇 바이트를 새로 만드는가예요. 젊은 세대 수집이 얼마나 자주 일어나는지는 거의 이 숫자가 정해요.

    상황

    주문 API의 젊은 세대 GC가 초당 3번, 한 번에 30ms씩 일어나서 p99를 끌어올렸어요. 팀은 힙을 키울지, GC를 ZGC로 바꿀지 고민했어요.

    깨지는 과정

    1. 할당률을 재 보니 초당 1.5GB였어요. 젊은 세대가 500MB라면 0.33초마다 가득 차서 수집해요.
    2. 힙을 키우면 수집 간격은 늘지만 할당률은 그대로라서, 문제를 미룰 뿐이에요. GC를 바꾸면 멈춤은 줄지만 GC가 쓰는 CPU는 줄지 않아요.
    3. 할당 프로파일을 떠 보니 범인은 세 군데였어요. 디버그 로그가 꺼져 있는데도 log.debug("order=" + order)가 문자열을 먼저 조립하고 있었고, 요청마다 new ObjectMapper()를 만들고 있었고, 큰 응답을 String으로 만든 뒤 다시 byte[]로 바꾸고 있었어요.
    4. 세 곳을 고치자 할당률이 3분의 1로 줄었고, GC 빈도도 그만큼 줄었어요. GC 설정은 하나도 바꾸지 않았어요.

    해결책

    • 할당 프로파일로 범인을 찾아요. JFR의 할당 샘플 이벤트(jdk.ObjectAllocationSample)나 async-profiler의 할당 모드(-e alloc)는 어느 코드가 많이 만드는지 플레임 그래프로 보여줘요.
    • 흔한 범인부터 고쳐요. 로그는 log.debug("order={}", order)처럼 파라미터 방식으로 쓰면 레벨이 꺼져 있을 때 문자열을 만들지 않아요. ObjectMapper처럼 만들기 비싸고 스레드 안전한 객체는 하나만 만들어 재사용해요. 큰 응답은 문자열을 거치지 않고 스트림으로 바로 써요.
    • 조기 승격과 누수를 구분해요. 젊은 세대가 너무 작으면 아직 쓰는 중인 임시 객체까지 살아남아 늙은 세대로 넘어가요(조기 승격). 그러면 늙은 세대가 빠르게 차서 누수처럼 보여요. GC 로그에서 늙은 세대를 수집한 뒤의 바닥값이 계속 오르면 누수, 톱니처럼 오르내리면 조기 승격이에요.
    • G1에서는 젊은 세대 크기를 고정하지 않아요. -Xmn으로 고정하면 G1이 멈춤 목표에 맞춰 크기를 자동 조정하지 못해요. 목표 멈춤 시간(-XX:MaxGCPauseMillis)을 조정하는 편이 나아요.

    운영에서 알아채는 법

    • 할당률(Micrometer의 jvm.gc.memory.allocated의 초당 증가량)을 지표로 남겨요. 배포 전후로 할당률이 크게 오르면 그 배포가 GC 부담을 만든 거예요.
    • 승격률(jvm.gc.memory.promoted)이 할당률에 비해 높으면 조기 승격을 의심해요.
    • GC 튜닝 논의가 나오면 먼저 할당률과 할당 프로파일부터 봐요.
    핵심 정리
    • GC 루트에서 닿지 않는 객체가 쓰레기. 순환 참조도 회수됨
    • 세대 가설: 대부분 금방 죽음 → 젊은 세대를 복사 방식으로 자주, 싸게
    • 멈춤이 꼬리 지연. 중간쯤 사는 객체가 가장 비쌈
    셀프 체크
    1. 젊은 세대 수집이 빠른 이유를 복사 방식과 세대 가설로 설명하세요.
    답 보기

    복사 방식의 비용은 살아 있는 객체를 옮기는 데서 나오므로 살아 있는 객체 수에 비례하고, 죽은 객체는 건드리지도 않아요. 세대 가설에 따르면 젊은 세대의 객체는 대부분 이미 죽어 있어요. 그래서 수집할 때 옮겨야 하는 객체가 아주 적고, 영역이 얼마나 크든 쓰레기가 얼마나 많든 비용에 거의 영향을 주지 않아요.

    처리량, 멈춤 시간, 메모리 중 무엇을 내줄 것인가

    문제: 정산 배치와 주문 API에 같은 설정을 썼다

    매일 밤 도는 정산 배치와 주문 API 서버에 같은 GC 설정을 쓰고 있었어요. 배치는 총 소요 시간이 중요하고 중간에 1초 멈춰도 아무도 모르지만, 주문 API는 200ms만 멈춰도 결제 타임아웃이 나요. 같은 설정이 둘 다에게 맞을 수 있을까요?

    셋 중 둘

    GC에는 세 가지 목표가 있어요. 처리량(전체 시간 중 GC에 쓰는 비율이 낮음), 멈춤 시간(한 번의 멈춤이 짧음), 메모리(힙이 작음)예요. 셋을 동시에 최고로 만들 수는 없고, 수집기는 무엇을 우선하느냐로 갈려요.

    수집기우선하는 것방식
    Parallel처리량애플리케이션을 멈춘 채 여러 스레드로 한꺼번에 수집. 멈춤은 길지만 총 GC 시간은 적음
    G1균형힙을 같은 크기의 구역으로 나누고 쓰레기가 많은 구역부터 수집. 목표 멈춤 시간에 맞춰 한 번의 작업량을 조절. 현재 기본값
    ZGC, Shenandoah멈춤 시간표시와 객체 이동을 애플리케이션과 동시에 진행. 멈춤이 힙 크기와 거의 무관하게 아주 짧음

    정산 배치에는 Parallel이, 주문 API에는 G1이나 ZGC가 맞아요.

    동시 수집의 대가

    멈추지 않고 수집하려면, 애플리케이션이 도는 동안 바뀌는 참조를 수집기가 따라가야 해요. 그래서 참조를 읽거나 쓸 때마다 끼어드는 작은 코드(배리어)를 실행해요. 이 배리어가 평소 실행을 조금씩 느리게 하고, 수집 스레드도 애플리케이션과 CPU를 나눠 써요. 수집이 진행되는 동안 새로 만들어지는 객체를 받을 여유 공간도 더 필요해요. 짧은 멈춤을 처리량과 메모리로 사는 거예요.

    튜닝하는 순서

    먼저 GC 로그를 켜요(-Xlog:gc*). 로그 없이 옵션을 바꾸는 것은 추측이에요. 다음으로 목표를 숫자로 정해요. "p99 멈춤 100ms 이하"처럼요. 그다음 힙 크기를 봐요. 대부분의 문제는 힙이 작거나 할당이 너무 많은 거예요. 수집기 선택은 그 뒤이고, 세부 옵션은 마지막이에요. 세부 옵션부터 만지면 이유를 모르는 설정만 쌓여요.

    백엔드에서는 GC 로그에서 볼 것은 세 가지예요. 멈춤 시간의 분포, 수집 직후 늙은 세대에 남은 양의 추세(계속 오르면 누수), 그리고 전체 수집(Full GC)이 일어나는지예요. G1에서 Full GC가 보이면 동시 수집이 할당 속도를 따라가지 못한 것이니 힙을 키우거나 할당을 줄여야 해요. 힙을 키우면 수집 빈도는 줄지만 한 번에 처리할 양이 늘 수 있다는 점도 같이 봐요.
    핵심 정리
    • 처리량 · 멈춤 시간 · 메모리는 동시에 최고가 될 수 없음
    • Parallel(처리량, 배치) · G1(균형, 기본) · ZGC·Shenandoah(짧은 멈춤)
    • 로그 → 목표 → 힙 크기 → 수집기 → 세부 옵션 순서
    셀프 체크
    1. 멈춤이 짧은 동시 수집기가 있는데도 모든 서비스가 그것을 쓰지 않는 이유는 무엇인가요?
    답 보기

    멈춤을 줄이는 대가가 있기 때문이에요. 동시 수집기는 애플리케이션이 도는 동안 수집 스레드가 CPU를 같이 쓰고, 참조를 읽고 쓸 때마다 배리어 코드가 실행돼서 평소 처리량이 낮아져요. 수집 중에 만들어지는 객체를 받아낼 여유 힙도 더 필요해요. 응답 시간 꼬리가 중요한 서비스에는 이득이지만, 배치처럼 총 처리 시간이 중요하고 멈춤을 아무도 느끼지 않는 작업에는 손해예요.

    3부 동시성

    6장 자바 메모리 모델

    한 스레드가 쓴 값을 다른 스레드가 언제 보는가

    문제: 종료 플래그를 바꿨는데 루프가 안 멈춘다

    주문 API 서버에 백그라운드로 재고를 동기화하는 스레드가 있어요. 서버를 내릴 때 메인 스레드가 running = false로 바꾸면 루프가 끝나도록 짰어요.

    private boolean running = true;

      // 동기화 스레드
      while (running) { syncStock(); }

      // 종료할 때 메인 스레드
      running = false;

    그런데 가끔 이 루프가 영원히 멈추지 않아서 서버 종료가 끝나지 않았어요. 분명히 false로 바꿨는데요.

    쓴 값이 바로 보인다는 보장이 없다

    이유는 두 층에 있어요. 하드웨어 쪽을 보면, CPU 코어마다 캐시가 있고 값은 한동안 그 코어의 캐시에만 있을 수 있어요. 컴파일러 쪽을 보면, JIT는 "이 루프 안에서 running을 바꾸는 코드가 없다"고 보고 값을 한 번만 읽어 루프 밖으로 빼낼 수 있어요. 그러면 루프는 while (true)와 같아져요.

    둘 다 단일 스레드에서는 결과가 같으니 허용되는 최적화예요. 문제는 다른 스레드가 끼어들 때예요. 동기화 없이는 한 스레드의 쓰기를 다른 스레드가 언제 보는지 아무 보장이 없어요.

    세 가지 성질

    여러 스레드가 메모리를 공유할 때는 세 가지를 따로 생각해야 해요. 원자성은 연산이 중간 상태 없이 한 번에 일어나는가예요. count++는 읽기, 더하기, 쓰기 세 단계라 원자적이지 않아요. 가시성은 한 스레드의 쓰기가 다른 스레드에 보이는가예요. 위의 문제예요. 순서는 코드에 쓴 순서대로 다른 스레드에게 보이는가예요. 컴파일러와 CPU는 단일 스레드에서 결과가 같으면 명령 순서를 바꾸고, 다른 스레드는 그 바뀐 순서를 볼 수 있어요.

    happens-before

    자바 메모리 모델은 "A가 B보다 먼저 일어났다고 보장되는 관계"를 규칙으로 정해요. 이 관계가 있을 때만 A의 쓰기가 B에게 보여요. 대표적인 규칙은 이래요. 락을 푼 것은 그 뒤에 같은 락을 잡은 것보다 먼저예요. volatile 필드에 쓴 것은 그 뒤의 읽기보다 먼저예요. 스레드를 시작한 것은 그 스레드 안의 모든 동작보다 먼저예요. 생성자가 끝나면 final 필드의 값은 다른 스레드에게 보여요.

    그래서 위 문제의 해결은 running을 volatile로 선언하는 거예요. 쓰기가 다른 스레드에 보이고, 컴파일러도 읽기를 루프 밖으로 빼지 않아요. 단 volatile은 원자성은 보장하지 않아요. volatile int count에 여러 스레드가 count++를 하면 여전히 값을 잃어요. 한 번 쓰고 읽는 플래그 같은 값에만 맞아요.

    백엔드에서는 불변 객체가 가장 싼 동기화예요. 모든 필드가 final이고 생성 후 바뀌지 않으면 락 없이 어떤 스레드와도 안전하게 나눠 쓸 수 있어요. 할인 정책 설정, 상품 가격표 같은 값을 불변 객체로 만들고, 바꿔야 하면 새 객체를 만들어 참조만 교체하세요. 그 참조는 volatile이나 AtomicReference로 둬요.
    시니어 심화 가시성 문제의 변형 중 찾기 가장 어려운 것이 안전하지 않은 공개예요. 객체를 다 만들기 전에 다른 스레드가 볼 수 있게 되면, 그 스레드는 반쯤 만들어진 객체를 볼 수 있어요.

    상황

    할인 설정을 처음 쓸 때 한 번만 만드는 지연 초기화 코드가 몇 년째 문제없이 돌았어요. 비용을 줄이려고 서버를 x86에서 ARM 인스턴스로 옮긴 뒤, 하루에 몇 번씩 설정 객체의 필드가 null이라는 NullPointerException이 나기 시작했어요. 재현은 되지 않았어요.

    private static DiscountConfig config;   // volatile 없음
static DiscountConfig get() {
    if (config == null) {
        synchronized (Lock.class) {
            if (config == null) config = new DiscountConfig(load());
        }
    }
    return config;
}

    깨지는 과정

    1. 객체를 만드는 과정은 "메모리 할당, 생성자 실행(필드 채우기), 필드에 참조 대입"이에요.
    2. 컴파일러나 CPU는 결과가 같아 보이면 순서를 바꿀 수 있어요. 참조 대입이 생성자의 필드 쓰기보다 먼저 다른 코어에 보일 수 있어요.
    3. 다른 스레드는 바깥쪽 if에서 null이 아닌 참조를 보고 락 없이 바로 써요. 그런데 그 객체의 필드는 아직 그 스레드에 보이지 않아서 null이에요.
    4. x86은 메모리 순서를 비교적 엄격하게 지켜서 이 버그가 거의 드러나지 않았어요. ARM은 순서를 더 자유롭게 바꿔서 숨어 있던 버그가 나타났어요. 자바 메모리 모델이 보장하지 않는 동작에 기대고 있었던 거예요.

    생성자 안에서 this를 리스너로 등록하거나 스레드를 시작하는 것도 같은 문제예요. 생성자가 끝나기 전에 다른 스레드가 그 객체를 보게 돼요.

    해결책

    • 필드를 volatile로 해요. volatile 쓰기 이전의 모든 쓰기는 그 값을 읽은 스레드에 보이도록 보장돼요(happens-before). 이중 검사 락은 volatile이 있어야만 올바르게 동작해요.
    • 더 간단한 방법을 써요. 지연 초기화는 홀더 클래스 방식(private static class Holder { static final DiscountConfig INSTANCE = ...; })을 쓰면 클래스 초기화의 락과 가시성 보장을 그대로 얻어요. 싱글톤이라면 enum도 돼요.
    • 불변 객체와 final 필드를 써요. 자바는 생성자가 끝난 객체의 final 필드는 다른 스레드에 올바르게 보인다고 보장해요. 공유되는 설정 객체는 모든 필드를 final로 만드는 것이 가장 안전해요.
    • 생성자에서 this를 내보내지 않아요. 리스너 등록이나 스레드 시작은 객체를 다 만든 뒤 팩토리 메서드에서 해요.

    테스트와 알아채는 법

    • 이런 버그는 일반 테스트로 거의 잡히지 않아요. 동시성 코드는 "테스트를 통과했다"가 아니라 "happens-before 관계가 있는가"를 읽어서 판단해요. 꼭 확인하고 싶다면 OpenJDK의 jcstress 같은 동시성 스트레스 도구를 써요.
    • SpotBugs는 volatile 없는 이중 검사 락 패턴을 경고해요. CI에 넣어 두세요.
    • CPU 아키텍처나 JDK를 바꾼 뒤 재현되지 않는 NPE나 "있을 수 없는 값"이 나타나면 이 종류의 버그를 의심해요.
    핵심 정리
    • 동기화 없이는 다른 스레드의 쓰기가 보인다는 보장이 없음(캐시, 컴파일러 최적화)
    • 원자성 · 가시성 · 순서를 따로 생각. happens-before가 있어야 보임
    • volatile = 가시성 O, 원자성 X. 불변 객체가 가장 단순한 해법
    셀프 체크
    1. volatile int counter에 여러 스레드가 counter++를 하면 왜 값이 맞지 않나요?
    답 보기

    volatile은 각각의 읽기와 쓰기가 다른 스레드에 보이게 할 뿐, 읽기-더하기-쓰기 세 단계를 하나로 묶어 주지 않아요. 두 스레드가 같은 값을 읽고 각자 1을 더해 쓰면 증가 하나가 사라져요. 세 단계를 원자적으로 해야 하므로 AtomicInteger의 incrementAndGet이나 락을 써야 해요.

    7장 락, 원자 변수, 동시성 컬렉션

    스레드 안전한 컬렉션을 썼는데도 중복이 생긴다

    문제: 쿠폰 정책 객체가 두 번 만들어졌다

    주문 API 서버가 쿠폰 정책을 처음 쓸 때 DB에서 읽어 만들고, 이후에는 ConcurrentHashMap에 캐시해 둬요.

    if (!cache.containsKey(couponId)) {
          cache.put(couponId, loadPolicy(couponId));   // DB 조회
      }
      return cache.get(couponId);

    스레드 안전한 맵을 썼는데, 행사 시작 순간 같은 쿠폰의 정책을 DB에서 수십 번 읽은 로그가 남았어요.

    호출 하나는 안전하지만, 호출 사이는 아니다

    ConcurrentHashMap의 containsKey와 put은 각각은 스레드 안전해요. 하지만 둘 사이에 다른 스레드가 끼어들 수 있어요. 스레드 여러 개가 동시에 "없음"을 확인하고 각자 DB에서 읽어 넣었어요.

    "확인하고 넣기"를 하나의 원자 연산으로 해야 해요. computeIfAbsent(couponId, id -> loadPolicy(id))는 키마다 생성 함수를 한 번만 실행하고, 그동안 같은 키를 요청한 다른 스레드는 기다렸다가 결과를 받아요. 다만 생성 함수 안에서 같은 맵을 다시 수정하면 안 돼요.

    락: synchronized와 ReentrantLock

    여러 단계의 작업을 묶어 한 스레드만 하게 하려면 락을 써요. 자바의 모든 객체는 락을 하나씩 갖고 있고, synchronized 블록은 들어갈 때 잡고 나올 때(예외로 나와도) 풀어요. 이미 잡은 락을 같은 스레드가 다시 잡을 수 있어요. 규칙은 하나예요. 같은 상태를 건드리는 모든 코드가 같은 락을 써야 해요. 쓰기만 잠그고 읽기를 안 잠그면 6장의 가시성 문제가 그대로 남아요.

    ReentrantLock은 synchronized로 안 되는 것이 필요할 때 써요. 정해진 시간만 기다리고 포기하기(tryLock), 기다리는 중에 인터럽트 받기, 조건 변수 여러 개. 대신 finally에서 직접 풀어야 해요.

    원자 변수: 락 없이 갱신

    AtomicInteger, AtomicLong은 락 없이 원자적으로 값을 바꿔요. 바탕은 CPU의 비교 후 교환(CAS) 명령이에요. "값이 내가 읽은 그대로면 새 값으로 바꾸고, 아니면 실패"를 한 번에 해요. 실패하면 다시 읽어서 재시도해요. 경쟁이 적으면 락보다 빠르고 스레드가 잠들지 않아요. 경쟁이 심하면 재시도가 반복돼요. 초당 주문 수를 세는 통계 카운터처럼 많은 스레드가 자주 올리는 값은 LongAdder가 나아요. 스레드별로 나눠 세고 읽을 때 합쳐서 경쟁을 피해요.

    동시성 컬렉션 고르기

    공유하는 맵은 ConcurrentHashMap이 기본이에요. 읽기가 압도적으로 많고 쓰기가 아주 드문 목록(이벤트 리스너 목록)은 쓸 때마다 배열을 통째로 복사하는 CopyOnWriteArrayList가 맞아요. 작업을 넘겨주는 생산자-소비자 구조에는 비면 꺼내는 쪽이, 차면 넣는 쪽이 기다리는 BlockingQueue를 써요.

    백엔드에서는 스프링의 빈은 기본이 싱글톤이라 모든 요청 스레드가 같은 객체를 써요. 서비스 빈의 필드에 요청별 데이터(현재 사용자, 계산 중인 금액)를 두면 다른 요청과 섞여요. 빈은 상태 없이 두고, 꼭 필요한 공유 상태(로컬 캐시, 카운터)만 위의 도구로 감싸세요. SimpleDateFormat처럼 스레드 안전하지 않은 객체를 정적 필드로 공유하는 것도 같은 실수예요. DateTimeFormatter는 불변이라 안전해요.
    시니어 심화 락을 쓸 때 가장 큰 사고는 락을 쥔 채로 남의 코드를 부르는 것이에요. 리스너 호출, 콜백, 오버라이드될 수 있는 메서드, 그리고 외부 I/O가 그래요.

    상황

    상품 가격표 객체는 가격을 바꿀 때 락을 잡고, 같은 락 안에서 "가격 변경 리스너"들을 불러요. 처음에는 리스너가 로컬 캐시를 비우는 것뿐이었어요. 몇 달 뒤 다른 팀이 "가격이 바뀌면 찜한 회원에게 알림"을 리스너로 추가했어요. 알림 서버가 느려진 날, 가격과 상관없어 보이는 상품 조회까지 모두 멈췄어요.

    깨지는 과정

    1. 새 리스너는 알림 서버에 HTTP 호출을 했어요. 이 호출은 가격표의 락 안에서 실행돼요.
    2. 알림 서버가 3초씩 걸리자, 그동안 가격을 읽으려는 모든 요청 스레드가 같은 락 앞에서 기다렸어요. 상품 조회도 가격을 읽으니 같이 멈췄어요.
    3. 락을 쥐고 부른 코드는 내가 만든 것이 아니라 나중에 누군가 추가한 것이에요. 락을 만든 사람은 그 안에서 무슨 일이 일어날지 통제할 수 없어요.
    4. 리스너가 다른 락을 잡으면 더 나빠요. 그 락을 쥔 다른 스레드가 가격표 락을 기다리면 데드락이에요.

    해결책

    • 락 안에서는 메모리만 다뤄요. 락 안에서 가격을 바꾸고, 바뀐 내용을 지역 변수에 담아 락을 푼 뒤에 리스너를 불러요. 리스너 목록은 CopyOnWriteArrayList로 두면 순회하는 동안 락이 필요 없어요.
    • 느린 리스너는 비동기로 넘겨요. 알림처럼 외부 호출이 있는 처리는 이벤트로 발행하고 별도 스레드나 메시지 큐에서 처리해요. 가격 변경 자체는 리스너의 속도와 무관해져요.
    • 락의 범위는 함께 맞아야 하는 값들의 범위예요. 최저가와 최고가 두 값이 항상 "최저가 ≤ 최고가"를 지켜야 한다면, 각각을 AtomicLong으로 만들어도 소용없어요. 두 값을 따로 바꾸는 사이에 다른 스레드가 어긋난 조합을 볼 수 있어요. 하나의 락으로 묶거나, 둘을 하나의 불변 객체로 합쳐 AtomicReference로 참조를 통째로 바꿔요.
    • 읽기가 압도적으로 많으면 불변 스냅샷을 써요. 가격표 전체를 불변 객체로 만들고, 바꿀 때는 새 객체를 만들어 참조만 바꾸면 읽기는 락이 전혀 필요 없어요.

    운영에서 알아채는 법

    • JFR의 락 대기 이벤트(jdk.JavaMonitorEnter)로 어느 락에서 얼마나 기다렸는지 봐요. 대기 시간이 긴 락을 쥔 스레드의 스택에서 락 안에서 무엇을 하는지 확인해요.
    • 코드 리뷰에서 synchronized 블록이나 lock()과 unlock() 사이에 인터페이스 호출, 콜백, I/O가 있는지를 확인 항목으로 둬요.
    핵심 정리
    • 스레드 안전한 컬렉션도 여러 호출의 조합은 안전하지 않음. 원자 메서드 사용
    • 같은 상태에는 같은 락. 기능이 더 필요하면 ReentrantLock
    • 원자 변수 = CAS 재시도. 경쟁 심한 카운터는 LongAdder
    셀프 체크
    1. ConcurrentHashMap을 쓰는데도 "없으면 넣기" 코드에서 중복 생성이 발생했습니다. 원인과 해결을 말해보세요.
    답 보기

    조회와 삽입이 각각은 스레드 안전하지만 둘 사이에 다른 스레드가 끼어들 수 있어요. 두 스레드가 동시에 "없음"을 확인하고 각자 값을 만들어 넣으면 중복 생성이 돼요. 확인과 삽입을 하나의 원자 연산으로 해 주는 computeIfAbsent를 써야 해요. 이 메서드는 키마다 생성 함수를 한 번만 실행하고, 같은 키를 요청한 다른 스레드는 결과를 기다려요. 다만 생성 함수 안에서 같은 맵을 다시 수정하면 안 돼요.

    8장 스레드풀, CompletableFuture, 가상 스레드

    최대 스레드를 50으로 잡았는데 10개만 일한다

    문제: 스레드가 늘지 않는다

    주문 API 서버에서 주문이 들어오면 재고, 쿠폰, 포인트 서비스를 호출하는 작업을 별도 스레드풀에 넘겨요. 풀은 코어 스레드 10개, 최대 50개, 큐는 LinkedBlockingQueue(크기 제한 없음)로 만들었어요. 그런데 부하가 몰려도 스레드가 10개를 넘지 않았고, 응답이 점점 느려지다 메모리가 바닥났어요.

    왜 풀을 쓰나

    스레드는 만드는 비용이 있고 각자 스택 메모리를 차지해요. 요청마다 새 스레드를 만들면 부하가 몰릴 때 스레드가 끝없이 늘어 서버가 죽어요. 스레드풀은 스레드를 재사용하고, 무엇보다 동시에 도는 작업 수에 상한을 둬요.

    ThreadPoolExecutor의 순서

    작업이 들어오면 스레드풀은 이 순서로 판단해요. 실행 중인 스레드가 코어 수보다 적으면 새 스레드를 만들어요. 코어가 다 찼으면 큐에 넣어요. 큐까지 가득 차면 그제서야 최대 수까지 스레드를 더 만들어요. 그것도 다 찼으면 거부 정책을 실행해요.

    위 문제의 원인이 여기 있어요. 큐에 크기 제한이 없으니 큐는 절대 가득 차지 않고, 최대 스레드 설정은 영영 쓰이지 않아요. 작업은 스레드 10개 앞에 끝없이 쌓이고, 쌓인 작업이 메모리를 채웠어요. 큐에 상한을 두고, 큐가 찼을 때 무엇을 할지(거부 정책)를 정해야 최대 스레드 설정이 의미를 가져요. Executors.newFixedThreadPool 같은 편의 메서드는 크기 제한 없는 큐를 쓰므로 운영 코드에서는 직접 만들어요.

    풀 크기

    CPU를 계속 쓰는 작업이면 코어 수 정도가 맞아요. 더 많으면 문맥 전환만 늘어요. 다른 서비스 응답을 기다리는 시간이 대부분인 작업이면 더 많이 둬요. 대략 코어 수 × (1 + 기다리는 시간 / 계산하는 시간)이에요. 하지만 실제 상한은 호출받는 쪽이 감당할 수 있는 동시 요청 수예요. 재고 서비스가 동시에 20개만 처리할 수 있다면 우리 스레드를 100개로 늘려도 재고 서비스만 넘어져요.

    CompletableFuture: 기다리는 동안 다른 일

    재고, 쿠폰, 포인트 조회는 서로 독립적이니 순서대로 부를 필요가 없어요. CompletableFuture로 동시에 시작하고 셋이 다 끝나면 합쳐요.

    var stock  = supplyAsync(() -> stockClient.check(items), ioPool);
      var coupon = supplyAsync(() -> couponClient.validate(code), ioPool);
      stock.thenCombine(coupon, OrderCheck::new)
           .orTimeout(2, TimeUnit.SECONDS);

    실행기(ioPool)를 지정하지 않으면 공용 풀(ForkJoinPool.commonPool)에서 돌아요. 이 풀은 크기가 작고 프로세스 전체가 같이 쓰기 때문에, 여기서 다른 서비스 응답을 기다리면 병렬 스트림 같은 다른 작업까지 같이 멈춰요.

    가상 스레드

    자바 21의 가상 스레드는 JVM이 관리하는 가벼운 스레드예요. 다른 서비스 응답을 기다리는 블로킹 호출을 만나면 운영체제 스레드를 붙잡지 않고 내려와서, 적은 수의 운영체제 스레드 위에서 수만 개가 돌 수 있어요. 요청마다 스레드 하나를 쓰는 단순한 코드 그대로 높은 동시성을 얻어요.

    백엔드에서는 스레드풀의 스레드에는 이름을 붙이세요. 스레드 덤프에 pool-3-thread-7만 보이면 무슨 풀인지 알 수 없어요. 그리고 서버를 내릴 때는 새 작업을 받지 않게 한 뒤(shutdown) 진행 중인 작업이 끝나길 정해진 시간만큼 기다리고 닫아요. 그냥 프로세스를 끝내면 처리 중이던 주문 확인 작업이 사라져요.
    시니어 심화 가상 스레드로 바꾸면 스레드풀과 반대 방향의 문제가 생겨요. 가상 스레드는 만드는 비용이 싸서 풀로 묶지 않고 작업마다 새로 만들어요. 그러면 스레드 수가 더 이상 동시성의 상한이 아니에요.

    상황

    주문 서비스를 가상 스레드로 바꾸고 톰캣의 스레드 수 제한이 사실상 사라졌어요. 평소에는 처리량이 늘어 좋았는데, 세일 시작 순간 재고 서비스가 과부하로 넘어지고 DB 커넥션 획득 타임아웃이 쏟아졌어요. 예전 스레드풀 200개 시절에는 없던 일이었어요.

    깨지는 과정

    1. 예전에는 톰캣 스레드풀 크기 200이 "동시에 처리하는 요청은 200개까지"라는 상한 역할을 덤으로 하고 있었어요. 하위 시스템은 많아야 200개의 동시 호출만 받았어요.
    2. 가상 스레드에서는 요청마다 새 스레드를 만드니, 세일 순간 동시 요청 수만 개가 그대로 처리 단계로 들어와요.
    3. 수만 개가 동시에 재고 서비스를 부르고, 동시에 DB 커넥션을 요청해요. 커넥션 풀(50개) 앞에 수만 개가 줄을 서고, 대기 시간이 타임아웃을 넘어요.
    4. 스레드풀이 해 주던 보호가 사라졌고, 상한이 하위 시스템 쪽으로 옮겨 간 거예요(OS 챕터 33장 시니어).

    해결책

    • 하위 호출 앞에 동시 호출 수를 명시적으로 제한해요. 세마포어로 "재고 서비스 호출은 동시에 50개까지"처럼 정하고, 획득에 짧은 타임아웃을 둬서 못 얻으면 빠르게 실패해요.
    • 입구에서도 상한을 둬요. 진행 중인 요청 수에 상한을 두고 넘으면 503으로 거절해요. 가상 스레드는 싸지만 요청마다 붙는 메모리와 하위 자원은 싸지 않아요.
    • 고정(pinning)을 조심해요. JDK 21~23에서는 가상 스레드가 synchronized 블록 안에서 블로킹 I/O를 하면 실행 중인 플랫폼 스레드에 고정돼서, 소수의 플랫폼 스레드가 금방 바닥나요. JDK 24에서 이 제약이 대부분 풀렸어요. 그 전 버전이라면 I/O를 감싸는 락은 ReentrantLock으로 바꿔요.
    • 스레드 로컬 캐시를 다시 봐요. 스레드마다 무거운 객체(포매터, 버퍼)를 캐시하던 코드는, 스레드가 수만 개가 되면 캐시도 수만 개가 돼서 메모리 문제가 돼요.
    • CPU 작업에는 이득이 없어요. 가상 스레드는 기다리는 시간이 많은 작업을 싸게 할 뿐, 계산을 빠르게 하지 않아요. 이미지 처리 같은 CPU 작업은 코어 수에 맞춘 일반 스레드풀에 둬요.

    운영에서 알아채는 법

    • 진행 중인 요청 수와 하위 호출별 동시 호출 수를 지표로 남겨요. 스레드 수로 저절로 보이던 값이 이제는 직접 재지 않으면 안 보여요.
    • JFR의 jdk.VirtualThreadPinned 이벤트가 고정이 일어난 위치와 시간을 알려줘요.
    • 커넥션 풀의 대기 스레드 수가 풀 크기의 몇십 배로 튄다면 상한 없는 동시성이 하위로 몰리고 있는 거예요.
    핵심 정리
    • 스레드풀 = 재사용 + 동시성 상한. 코어 → 큐 → 최대 → 거부 순서
    • 큐 크기와 거부 정책을 직접 지정. 공용 풀에서 블로킹 금지
    • 가상 스레드 = 블로킹이 싼 스레드. 하위 시스템 보호는 세마포어로
    셀프 체크
    1. 코어 10, 최대 50, 크기 제한 없는 큐로 만든 스레드풀에서 부하가 몰려도 스레드가 10개를 넘지 않았습니다. 왜인가요?
    답 보기

    스레드풀은 코어 스레드가 다 차면 작업을 큐에 넣고, 큐가 가득 찼을 때만 최대 수까지 스레드를 늘려요. 큐에 크기 제한이 없으면 가득 차는 일이 없으니 최대 설정은 쓰이지 않고, 작업은 큐에 끝없이 쌓여요. 결과는 응답 지연 증가와 메모리 고갈이에요. 큐에 상한을 두고 거부 정책을 정해야 최대 설정이 의미를 가져요.

    9장 진단 도구

    응답이 멈췄을 때 재시작하기 전에 할 일

    문제: 서버가 응답하지 않는데 CPU는 한가하다

    새벽에 알람이 울렸어요. 주문 API 서버가 요청을 받기는 하는데 응답을 안 해요. CPU 사용률은 5%, 메모리도 여유가 있어요. 급한 마음에 재시작하면 일단 살아나겠지만, 원인은 영영 모르게 되고 같은 일이 또 일어나요. 재시작하기 전에 무엇을 남겨야 할까요?

    스레드 덤프: 지금 모두가 무엇을 하고 있나

    스레드 덤프는 모든 스레드가 지금 실행 중인 위치(호출 스택)와 상태를 찍은 사진이에요. jcmd <pid> Thread.print로 떠요. 상태는 이렇게 읽어요.

    상태뜻
    RUNNABLE실행 중이거나 소켓 읽기 같은 I/O를 기다리는 중
    BLOCKEDsynchronized 락을 기다리는 중. 누가 쥐고 있는지도 나옴
    WAITING / TIMED_WAITING조건이나 시간을 기다리는 중. 일이 없는 풀의 스레드는 정상적으로 이 상태

    CPU가 한가한데 응답이 없다는 것은 스레드들이 무언가를 기다리고 있다는 뜻이에요. 그런데 덤프를 한 번만 뜨면 "마침 그 순간 기다리던 것"인지 "계속 막혀 있는 것"인지 구분이 안 돼요. 그래서 몇 초 간격으로 서너 번 떠서 비교해요.

    위 그림에서 요청 스레드들은 세 번 모두 같은 락(0x7a3f)을 기다리고, 그 락은 스케줄러 스레드가 쥐고 있어요. 스케줄러 스레드는 세 번 모두 외부 API의 응답을 읽는 중이에요. 락을 쥔 채로 타임아웃 없는 외부 호출을 하고 있었던 거예요. 7장 시니어 심화의 "락을 쥔 채로 남의 코드를 부르지 마라"가 실제 장애로 나타난 모습이에요.

    다른 도구들

    힙 덤프는 힙에 있는 모든 객체의 사진이에요(jcmd <pid> GC.heap_dump). 메모리가 계속 늘 때 누가 붙잡고 있는지 찾는 데 써요. 뜨는 동안 애플리케이션이 멈추고 파일이 힙만큼 크니, 운영에서는 트래픽을 뺀 인스턴스에서 떠요. GC 로그는 비용이 거의 없으니 항상 켜 둬요. JFR(Java Flight Recorder)은 JVM에 내장된 기록기로, GC, 락 대기, 할당, I/O를 낮은 부하로 계속 기록해요. 다른 도구와 달리 "문제가 났던 그때"를 나중에 돌려 볼 수 있어요.

    증상별 출발점

    CPU가 높으면 스레드별 CPU 사용량을 보고 그 스레드의 스택을 봐요. 응답이 멈췄으면 스레드 덤프를 여러 번 떠요. 주기적으로 느려지면 GC 로그의 멈춤 시간을 봐요. 메모리가 계속 늘면 GC 직후 늙은 세대 사용량의 추세를 보고 힙 덤프를 떠요.

    백엔드에서는 장애가 나면 재시작하기 전에 스레드 덤프부터 떠요. 재시작하면 증거가 사라져요. 덤프 수집을 스크립트로 만들어 두고, 쿠버네티스라면 컨테이너 종료 직전 훅에서 자동으로 남기게 할 수도 있어요. 스프링 부트 액추에이터는 스레드 덤프와 힙 덤프 엔드포인트를 제공하지만, 인증 없이 열어 두면 메모리 안의 비밀번호와 토큰이 그대로 유출돼요.
    시니어 심화 CPU를 많이 쓰는 원인을 찾을 때 쓰는 프로파일러에도 함정이 있어요. 그리고 CPU 프로파일은 기다리는 시간을 보여주지 않아요.

    상황 1: 프로파일러가 엉뚱한 곳을 가리킴

    정산 서버의 CPU가 100%라서 프로파일러를 붙였어요. 맨 위에 나온 것은 아주 가벼운 getter 메서드였어요. 그 메서드를 아무리 봐도 CPU를 쓸 이유가 없었어요.

    1. 전통적인 자바 프로파일러는 스레드가 안전하게 멈출 수 있는 지점(safepoint)에 왔을 때만 스택을 기록해요.
    2. JIT 컴파일러는 성능을 위해 반복문 안 같은 곳에서 그 지점을 빼 버리기도 해요.
    3. 그러면 실제로 CPU를 태우는 반복문에서는 샘플이 기록되지 않고, 반복문이 끝난 바로 다음 지점(엉뚱한 getter)에서 기록돼요. 범인이 엉뚱한 곳으로 찍혀요.

    해결: 이 편향이 없는 프로파일러를 써요. async-profiler는 운영체제의 타이머 신호로 아무 지점에서나 스택을 기록하고, JFR도 safepoint와 무관하게 샘플을 모아요.

    상황 2: 느린데 CPU 프로파일에는 아무것도 없음

    주문 API가 느려졌는데 CPU는 20%로 한가했어요. CPU 프로파일에는 평소와 같은 모양만 나왔어요.

    1. CPU 프로파일은 "CPU에서 실행 중인 스레드"만 샘플링해요.
    2. 응답이 느린 이유가 락 대기, DB 커넥션 대기, 외부 API 대기라면, 그 스레드들은 CPU에서 실행 중이 아니라서 프로파일에 나오지 않아요.
    3. "느린데 CPU는 한가하다"면 CPU 프로파일은 답을 줄 수 없어요.

    해결: CPU 시간과 실제 경과 시간을 구분해요. async-profiler의 벽시계 모드(-e wall)는 기다리는 스레드까지 포함해서 "시간이 어디서 흘렀는가"를 보여줘요. 락 대기 프로파일(-e lock)이나 JFR의 락, I/O 이벤트도 같은 질문에 답해요.

    항상 켜 두는 프로파일링

    장애가 끝난 뒤에 프로파일러를 붙이면 이미 늦어요. 운영에서 낮은 비율로 프로파일을 항상 수집해 두면(연속 프로파일링: Pyroscope, 클라우드 APM의 프로파일러, JFR 상시 기록), 문제가 재현되기를 기다리지 않고 장애 시각의 프로파일을 바로 열어 볼 수 있어요. 배포 전후를 비교하는 데도 써요(성능 분석 챕터 4장 시니어). 오버헤드는 보통 몇 % 안쪽이에요.

    운영에서 알아채는 법

    • 프로파일 결과가 상식과 맞지 않는다면(가벼운 메서드가 맨 위), 프로파일러의 편향부터 의심해요.
    • "느린데 CPU는 한가함"과 "느리고 CPU도 높음"을 먼저 나누고, 그에 맞는 프로파일 모드를 골라요.
    핵심 정리
    • 스레드 덤프는 몇 초 간격으로 여러 번. 같은 자리에 계속 있는 스레드를 찾음
    • GC 로그와 JFR은 운영에서 항상 켜 둠
    • 재시작 전에 증거 수집. 진단 엔드포인트는 보호

    CPU가 한가하다는 것은 스레드들이 무언가를 기다리고 있다는 뜻이에요. 스레드 덤프를 몇 초 간격으로 여러 번 떠서 요청 처리 스레드들이 어디에 멈춰 있는지 봐요. 같은 락을 기다리며 BLOCKED라면 그 락을 쥔 스레드가 무엇을 하는지 따라가요. 커넥션 풀에서 커넥션을 기다린다면 풀 고갈이므로 커넥션을 쥔 스레드들을 봐요. 소켓 읽기에서 멈춰 있다면 하위 시스템이 응답하지 않는 것이니 타임아웃 설정과 상대 시스템을 확인해요.

    실습 과제

    문제를 직접 만들고 도구로 찾아보는 것이 가장 빨라요.

    • 1장 같은 라이브러리의 두 버전을 의존성에 넣어 NoSuchMethodError를 재현하고 의존성 트리에서 원인 찾기
    • 2장 새로 띄운 서버에 같은 요청을 반복해 보내며 처음 1,000건과 그 뒤 1,000건의 응답 시간 분포 비교
    • 3장 만료 없는 정적 Map에 계속 넣는 누수를 만들고, OOM 때 남은 힙 덤프에서 붙잡고 있는 참조 경로 찾기
    • 4~5장 같은 부하를 Parallel, G1, ZGC로 돌려 GC 로그의 멈춤 시간 분포와 처리량 비교
    • 6장 volatile 없는 종료 플래그로 끝나지 않는 루프 재현. volatile을 붙이면 끝나는지 확인
    • 7장 containsKey + put으로 만든 캐시에 동시 요청을 보내 중복 생성 재현. computeIfAbsent로 고치기
    • 8장 크기 제한 없는 큐 풀과 유한 큐 + 거부 정책 풀에 처리 속도보다 빠르게 작업을 넣고 스레드 수, 메모리, 지연 비교
    • 9장 락을 쥔 채 느린 외부 호출을 하는 코드를 만들고 스레드 덤프 세 번으로 원인 찾기
