    JVM과 자바 동시성

    기준 교재: 자바 병렬 프로그래밍(JCIP) + 자바 최적화(Optimizing Java) · 4~6주

    앞선 챕터의 예시는 대부분 자바와 스프링이었어요. 이 챕터는 그 코드가 실제로 돌아가는 런타임을 다뤄요. 바이트코드가 어떻게 실행되는지, 객체가 어디에 놓이고 언제 치워지는지, 여러 스레드가 같은 메모리를 볼 때 무엇이 보장되는지예요.

    운영체제 챕터의 2부(병행성)를 먼저 읽고 오세요. 시간이 없으면 3~4장(메모리와 GC), 6~8장(동시성)이 우선이에요. 다른 언어를 주로 쓴다면 개념은 그대로 두고 그 런타임의 구현으로 바꿔 읽으면 돼요.

    1부 실행

    1장 JVM 구조와 클래스 로딩

    .class 파일이 실행 가능한 코드가 되기까지

    실행 흐름

    1. 컴파일러(javac)가 소스를 바이트코드로 바꾼다. 특정 CPU가 아니라 가상 머신을 위한 명령어예요.
    2. 클래스 로더가 필요한 클래스를 찾아 메모리에 올린다.
    3. 실행 엔진이 바이트코드를 실행한다. 처음에는 인터프리터로, 자주 실행되는 부분은 JIT 컴파일러가 기계어로 바꿔요.
    4. 가비지 컬렉터가 더 이상 쓰이지 않는 객체를 회수한다.

    클래스 로딩 세 단계

    • 로딩: 클래스 파일을 읽어 메모리에 올린다.
    • 링킹: 바이트코드를 검증하고, 정적 필드의 공간을 잡고, 다른 클래스에 대한 참조를 연결한다.
    • 초기화: 정적 초기화 블록과 정적 필드 초기화를 실행한다. 클래스가 처음 실제로 사용될 때 일어나요.

    부모 위임 모델

    클래스 로더는 계층을 이뤄요. 클래스를 요청받으면 먼저 부모에게 넘기고, 부모가 못 찾을 때만 자기가 찾아요. 그래서 애플리케이션이 java.lang.String을 다른 것으로 바꿔치기할 수 없어요.

    클래스의 정체는 이름 + 그 클래스를 올린 로더예요. 같은 이름의 클래스를 서로 다른 로더가 올리면 JVM에게는 다른 클래스예요.

    백엔드에서는 ClassNotFoundException은 이름으로 클래스를 찾으려 했는데 없을 때, NoClassDefFoundError는 컴파일 때는 있었는데 실행 때 없거나 초기화에 실패했을 때 나요. NoSuchMethodError는 거의 항상 의존성 버전 충돌이에요. 같은 라이브러리의 두 버전이 클래스패스에 있고 예상과 다른 쪽이 먼저 잡힌 거예요. 의존성 트리를 출력해서 확인하세요.
    시니어 심화
    • 정적 초기화는 락을 잡고 실행돼요. 클래스 초기화가 느리거나(정적 블록에서 I/O) 두 클래스가 서로를 초기화 중에 참조하면, 첫 요청들이 멈추거나 데드락이 나요. 스레드 덤프에 초기화 대기로 보여요.
    • 클래스 로더 누수: 애플리케이션을 다시 올리는 환경에서 옛 로더가 올린 클래스의 객체를 누군가(스레드 로컬, 정적 캐시, 등록된 드라이버) 계속 쥐고 있으면 옛 클래스 전체가 회수되지 않아요. 메타스페이스가 조금씩 차오르는 원인이에요.
    • 시작 시간이 중요한 환경에서는 클래스 로딩과 초기화가 시작 시간의 큰 부분이에요. 클래스 데이터 공유(CDS)나 미리 컴파일된 이미지로 줄일 수 있어요.
    핵심 정리
    • 소스 → 바이트코드 → 클래스 로딩 → 인터프리터 + JIT
    • 로딩 · 링킹 · 초기화. 초기화는 첫 사용 시점
    • 클래스의 정체 = 이름 + 로더. 버전 충돌은 NoSuchMethodError로 나타남
    셀프 체크
    1. NoSuchMethodError가 운영에서만 발생했습니다. 가장 먼저 의심할 것은 무엇인가요?
    답 보기

    의존성 버전 충돌이에요. 컴파일할 때 본 라이브러리 버전에는 그 메서드가 있었는데, 실행 시 클래스패스에서 먼저 잡힌 버전에는 없는 거예요. 서로 다른 라이브러리가 같은 의존성의 다른 버전을 끌고 오거나, 운영 환경(컨테이너 이미지, 서버 공용 라이브러리)에 다른 버전이 있을 때 생겨요. 실제 배포 산출물의 의존성 트리와 포함된 jar 목록을 확인해요.

    2장 JIT 컴파일과 워밍업

    같은 코드가 처음엔 느리고 나중엔 빠른 이유

    계층형 컴파일

    JVM은 모든 코드를 미리 기계어로 바꾸지 않아요. 인터프리터로 실행하면서 호출 횟수와 반복 횟수를 세고, 자주 실행되는 부분만 컴파일해요. 먼저 빠르게 컴파일하는 컴파일러(C1)가 대충 최적화한 코드를 만들고 실행 정보를 계속 모으다가, 정말 뜨거운 코드는 느리지만 강하게 최적화하는 컴파일러(C2)가 다시 컴파일해요.

    실행 정보를 쓰는 최적화

    • 인라이닝: 메서드 호출을 호출한 자리에 펼쳐 넣는다. 다른 최적화의 출발점이에요.
    • 탈출 분석: 객체가 메서드 밖으로 나가지 않으면 힙에 할당하지 않고 필드를 지역 변수처럼 다룬다.
    • 가상 호출 최적화: 인터페이스 호출인데 실제로는 구현체 하나만 온다면 그 구현체로 직접 호출한다.

    역최적화

    위 최적화는 "지금까지는 이랬다"는 가정 위에 서 있어요. 가정이 깨지면(새 구현체가 로드됨, 한 번도 안 타던 분기를 탐) 컴파일된 코드를 버리고 인터프리터로 돌아갔다가 다시 컴파일해요.

    워밍업

    그래서 JVM 프로세스는 시작 직후가 가장 느려요. 인터프리터로 돌고 있고 컴파일 스레드가 CPU를 쓰고 있어요.

    백엔드에서는 배포 직후 첫 몇 분의 응답 시간이 튀는 것이 워밍업이에요. 새 인스턴스에 바로 정상 트래픽을 주지 말고 준비 상태가 되기 전에 주요 경로를 미리 호출하거나, LB의 점진적 투입을 써요. CPU limit이 작은 컨테이너는 컴파일 스레드와 요청 처리가 CPU를 다퉈서 워밍업이 더 길어져요.
    핵심 정리
    • 인터프리터 → C1 → C2. 뜨거운 코드만 컴파일
    • 인라이닝·탈출 분석 등은 실행 정보에 기반한 가정
    • 가정이 깨지면 역최적화. 시작 직후가 가장 느림(워밍업)
    셀프 체크
    1. 마이크로 벤치마크에서 루프를 몇 번 돌려 시간을 재는 방식이 왜 부정확한가요?
    답 보기

    처음 반복은 인터프리터로 실행되고, 도중에 컴파일이 일어나 속도가 바뀌어요. 또 JIT는 결과를 쓰지 않는 계산을 통째로 지우거나 상수로 바꿔 버릴 수 있어서, 재려던 코드가 실제로는 실행되지 않을 수도 있어요. 측정 루프 자체가 실제 서비스와 다른 형태로 컴파일되기도 해요. 그래서 워밍업 반복, 결과 소비, 분리된 프로세스 실행을 처리해 주는 전용 도구(JMH)를 써야 해요.

    2부 메모리

    3장 메모리 영역과 객체

    객체는 어디에 놓이고 얼마나 차지하는가

    런타임 메모리 영역

    영역담는 것공유
    힙모든 객체와 배열모든 스레드
    스택메서드 호출마다의 프레임(지역 변수, 중간 계산값)스레드마다 하나
    메타스페이스클래스 메타데이터모든 스레드, 힙 밖
    코드 캐시JIT가 만든 기계어모든 스레드, 힙 밖
    다이렉트 메모리힙 밖에 직접 잡은 버퍼(NIO)힙 밖

    지역 변수 중 원시 타입은 스택에 값이 그대로 있고, 객체는 힙에 있으며 스택에는 그 참조만 있어요.

    객체의 크기

    객체는 필드만 차지하지 않아요. 모든 객체 앞에 헤더가 붙어요(64비트 JVM에서 보통 12바이트). 그리고 전체 크기는 8바이트 단위로 맞춰져요. 그래서 Integer 하나가 16바이트이고, 값 4바이트를 담으려고 4배를 써요.

    힙 설정

    • -Xms, -Xmx: 힙의 시작 크기와 최대 크기.
    • 컨테이너에서는 메모리 한도의 비율로 정하는 -XX:MaxRAMPercentage가 편해요.

    OutOfMemoryError의 종류

    • Java heap space: 힙이 꽉 참. 누수이거나 그냥 작게 잡은 것.
    • Metaspace: 클래스를 너무 많이 올림(동적 생성, 로더 누수).
    • Direct buffer memory: 힙 밖 버퍼 한도 초과.
    • unable to create native thread: OS가 스레드를 더 못 만듦.
    백엔드에서는 누수의 흔한 원인은 끝없이 자라는 컬렉션이에요. 만료 없는 정적 Map 캐시, 지우지 않는 ThreadLocal, 해제하지 않은 리스너 등록. "GC가 있으니 누수가 없다"가 아니라 "참조가 남아 있으면 GC는 못 치운다"예요. -XX:+HeapDumpOnOutOfMemoryError는 항상 켜 두세요. 죽는 순간의 힙이 가장 좋은 증거예요.
    시니어 심화
    • 힙 덤프 분석은 "무엇이 많은가"보다 "누가 붙잡고 있는가"를 봐요. 객체가 차지한 자체 크기가 아니라 그 객체가 사라지면 함께 회수될 크기(retained size)로 정렬하고, GC 루트까지의 참조 경로를 따라가요.
    • 압축 참조: 힙이 약 32GB 이하면 참조를 4바이트로 줄여 써요. 그 경계를 넘기면 모든 참조가 8바이트가 되어, 힙을 조금 늘렸는데 실제 담을 수 있는 객체 수는 오히려 줄어들 수 있어요.
    • 메모리가 새는데 힙은 정상이면 힙 밖을 봐요. 다이렉트 버퍼, 스레드 스택, 네이티브 라이브러리의 할당이에요. 네이티브 메모리 추적 기능으로 영역별 추이를 비교해요.
    핵심 정리
    • 힙(객체) · 스택(프레임, 스레드별) · 메타스페이스(클래스) · 힙 밖 영역
    • 객체에는 헤더가 붙음. 박싱 타입은 값보다 훨씬 큼
    • OOM은 종류를 구분. 힙 덤프 옵션은 항상 켜 둠
    셀프 체크
    1. GC가 있는 언어에서도 메모리 누수가 생기는 이유를 설명하세요.
    답 보기

    GC는 어디에서도 도달할 수 없는 객체만 회수해요. 프로그램이 더 이상 쓰지 않는 객체라도 어딘가에서 참조가 이어져 있으면 GC가 보기에는 살아 있는 객체예요. 만료 없이 계속 쌓이는 정적 맵, 스레드풀 스레드에 남은 스레드 로컬 값, 해제하지 않은 리스너가 그런 참조예요. 그래서 누수를 찾는다는 것은 "쓰지 않는데 붙잡혀 있는 참조 경로"를 찾는 일이에요.

    4장 가비지 컬렉션의 원리

    무엇이 쓰레기이고 어떻게 치우는가

    도달 가능성

    GC는 "쓰이지 않는 객체"를 직접 알 수 없어요. 대신 GC 루트(실행 중인 스레드의 스택, 정적 필드 등)에서 참조를 따라가며 닿는 객체를 전부 표시하고, 닿지 않은 것을 쓰레기로 봐요. 참조 횟수를 세는 방식이 아니라서 서로를 참조하는 순환 구조도 문제없이 회수돼요.

    기본 알고리즘

    • 표시 후 쓸기(mark-sweep): 살아 있는 것을 표시하고 나머지를 비운다. 빈 공간이 흩어져서 단편화가 생겨요.
    • 표시 후 압축(mark-compact): 살아 있는 것을 한쪽으로 모은다. 단편화가 없지만 객체를 옮기는 비용이 들어요.
    • 복사(copying): 살아 있는 것만 다른 영역으로 옮긴다. 비용이 살아 있는 객체 수에 비례해요. 대부분이 쓰레기면 아주 빨라요.

    세대 가설

    대부분의 객체는 만들어진 직후에 죽어요. 요청 하나를 처리하며 만든 객체는 응답이 나가면 쓰레기예요. 그래서 힙을 나눠요.

    • 젊은 세대: 새 객체가 만들어지는 곳. 자주, 빠르게 수집해요(복사 방식). 대부분 죽어 있으니 옮길 것이 적어요.
    • 늙은 세대: 젊은 세대 수집에서 여러 번 살아남은 객체가 옮겨 가는 곳. 덜 자주 수집해요.

    멈춤(stop-the-world)

    객체를 옮기거나 참조 그래프를 정확히 훑으려면 애플리케이션 스레드를 멈춰야 하는 구간이 있어요. 이 멈춤이 응답 시간의 꼬리가 돼요. GC 설계의 역사는 이 멈춤을 줄이는 방향이에요.

    백엔드에서는 요청마다 만들어지는 임시 객체는 젊은 세대에서 싸게 사라져요. 문제는 중간 수명 객체예요. 수 초에서 수 분 사는 객체(세션 스코프 데이터, 큰 배치의 중간 결과, 캐시에 잠깐 있다 나가는 항목)는 늙은 세대로 넘어간 뒤 죽어서 비싼 수집을 일으켜요. 캐시는 아주 오래 살거나 아주 짧게 살게 설계하세요.
    시니어 심화
    • 할당률이 핵심 지표예요. 초당 얼마나 많은 바이트를 할당하는지가 젊은 세대 수집 빈도를 정해요. 할당 프로파일러로 어느 코드가 많이 만드는지 찾으면 GC 설정을 건드리지 않고도 개선돼요.
    • 조기 승격: 젊은 세대가 작으면 아직 쓰는 중인 임시 객체가 살아남아 늙은 세대로 넘어가요. 늙은 세대가 빠르게 차는 것이 누수가 아니라 이 문제일 수 있어요.
    • 멈춤 시간에는 GC 작업 외의 시간도 들어가요. 모든 스레드가 멈출 수 있는 지점에 도달하기를 기다리는 시간이 있어요. 한 스레드가 그 지점에 늦게 도달하면 나머지가 전부 기다려요.
    핵심 정리
    • GC 루트에서 닿지 않는 객체가 쓰레기
    • 세대 가설: 대부분 금방 죽음 → 젊은 세대를 자주, 싸게
    • 멈춤 시간이 꼬리 지연. 중간 수명 객체가 가장 비쌈
    셀프 체크
    1. 젊은 세대 수집이 빠른 이유를 복사 알고리즘과 세대 가설로 설명하세요.
    답 보기

    복사 방식의 비용은 살아 있는 객체를 옮기는 데서 나오므로 살아 있는 객체 수에 비례하고, 죽은 객체는 건드리지도 않아요. 세대 가설에 따르면 젊은 세대의 객체는 대부분 이미 죽어 있어요. 그래서 수집할 때 옮겨야 하는 객체가 아주 적고, 영역이 얼마나 큰지나 쓰레기가 얼마나 많은지는 비용에 거의 영향을 주지 않아요.

    5장 GC 수집기와 튜닝

    처리량, 멈춤 시간, 메모리 중 둘을 고른다

    세 가지 목표는 동시에 못 가진다

    처리량(GC에 쓰는 CPU 비율이 낮음), 멈춤 시간(한 번의 멈춤이 짧음), 메모리 사용량(힙이 작음). 수집기는 이 중 무엇을 우선하느냐로 갈려요.

    주요 수집기

    수집기우선하는 것특징
    Parallel처리량멈춘 채로 여러 스레드가 수집. 멈춤은 길지만 총 GC 시간은 적음. 배치에 적합
    G1균형힙을 같은 크기의 리전으로 나누고, 쓰레기가 많은 리전부터 수집. 목표 멈춤 시간을 주면 거기에 맞춰 작업량을 조절. 기본 수집기
    ZGC, Shenandoah멈춤 시간표시와 객체 이동을 애플리케이션과 동시에 수행. 멈춤이 힙 크기와 거의 무관하게 짧음. 대신 CPU와 메모리를 더 씀

    동시 수집의 원리

    애플리케이션이 도는 동안 참조 그래프가 계속 바뀌어요. 동시 수집기는 참조를 읽거나 쓸 때 끼어드는 작은 코드(배리어)로 변화를 추적해요. 이 배리어가 평상시 실행을 조금 느리게 해요. 멈춤 시간을 처리량과 맞바꾼 거예요.

    튜닝 순서

    1. GC 로그를 켠다. 로그 없이 옵션을 바꾸는 것은 추측이에요.
    2. 목표를 숫자로 정한다(p99 멈춤 얼마 이하, GC 시간 비율 얼마 이하).
    3. 힙 크기부터 본다. 대부분의 문제는 힙이 너무 작거나 할당이 너무 많은 거예요.
    4. 수집기를 고른다. 세부 옵션은 마지막이에요.
    백엔드에서는 GC 로그에서 볼 것은 세 가지예요. 멈춤 시간의 분포, 수집 후에도 남는 늙은 세대 사용량의 추세(계속 오르면 누수), 그리고 전체 수집(Full GC)의 발생 여부예요. G1에서 Full GC가 보이면 동시 수집이 할당을 못 따라간 것이니 힙을 키우거나 할당을 줄여야 해요. 힙을 키우면 수집 빈도는 줄지만 한 번에 처리할 양이 늘 수 있다는 점도 같이 보세요.
    핵심 정리
    • 처리량 · 멈춤 시간 · 메모리는 트레이드오프
    • Parallel(처리량), G1(균형, 기본), ZGC·Shenandoah(짧은 멈춤)
    • 로그 → 목표 → 힙 크기 → 수집기 → 세부 옵션 순
    셀프 체크
    1. 멈춤이 짧은 동시 수집기가 있는데도 모든 서비스가 그것을 쓰지 않는 이유는 무엇인가요?
    답 보기

    멈춤을 줄이는 대가가 있기 때문이에요. 동시 수집기는 애플리케이션이 도는 동안 수집 스레드가 CPU를 같이 쓰고, 참조 접근마다 배리어 코드가 실행돼서 평상시 처리량이 낮아져요. 수집이 진행되는 동안의 할당을 받아낼 여유 힙도 더 필요해요. 응답 시간 꼬리가 중요한 서비스에는 이득이지만, 배치처럼 총 처리 시간이 중요하고 멈춤을 아무도 느끼지 않는 작업에는 손해예요.

    3부 동시성

    6장 자바 메모리 모델

    한 스레드가 쓴 값을 다른 스레드가 언제 볼 수 있는가

    문제: 쓴 값이 안 보일 수 있다

    boolean running = true;
      // 스레드 A
      while (running) { work(); }
      // 스레드 B
      running = false;      // A가 영원히 못 볼 수 있음

    CPU는 값을 코어별 캐시와 레지스터에 두고, 컴파일러는 "이 루프 안에서 아무도 안 바꾼다"고 보고 읽기를 루프 밖으로 빼낼 수 있어요. 동기화가 없으면 B가 쓴 값을 A가 본다는 보장이 없어요.

    세 가지 성질

    • 원자성: 연산이 중간 상태 없이 한 번에 일어난다. count++는 읽기·더하기·쓰기 세 단계라 원자적이지 않아요.
    • 가시성: 한 스레드의 쓰기를 다른 스레드가 볼 수 있다.
    • 순서: 컴파일러와 CPU는 단일 스레드에서 결과가 같으면 명령 순서를 바꿔요. 다른 스레드에서는 그 바뀐 순서가 보여요.

    happens-before

    자바 메모리 모델은 "A가 B보다 먼저 일어났다고 보장되는 경우"를 규칙으로 정해요. 이 관계가 있을 때만 A의 쓰기가 B에게 보여요.

    • 락을 푸는 것 → 같은 락을 그 뒤에 잡는 것
    • volatile 필드에 쓰기 → 그 뒤의 읽기
    • 스레드를 시작하는 것 → 그 스레드 안의 모든 동작
    • final 필드: 생성자가 끝나면 다른 스레드에게 초기화된 값이 보임

    volatile이 하는 것과 못 하는 것

    volatile은 가시성과 순서를 보장하지만 원자성은 보장하지 않아요. volatile int count; count++는 여전히 값을 잃어요. 플래그처럼 한 번에 쓰고 읽는 값에만 맞아요.

    백엔드에서는 불변 객체가 가장 싼 동기화예요. 모든 필드가 final이고 생성 후 바뀌지 않으면 락 없이 어떤 스레드와도 공유할 수 있어요. 설정 객체, 값 객체, DTO를 불변으로 만들고, 바꿔야 하면 새 객체를 만들어 참조만 교체해요(참조는 volatile이나 AtomicReference로).
    시니어 심화
    • 안전하지 않은 공개: 객체를 생성자가 끝나기 전에 다른 스레드에 노출하면(생성자 안에서 자신을 리스너로 등록, 스레드 시작) 반쯤 만들어진 객체가 보여요. final 필드의 보장도 이 경우 깨져요.
    • 이중 검사 락은 인스턴스 필드가 volatile이 아니면 깨져요. 참조가 먼저 대입되고 생성자가 나중에 실행되는 순서로 바뀔 수 있어서, 다른 스레드가 초기화되지 않은 객체를 받아요. 지연 초기화는 홀더 클래스 관용구나 enum으로 해요.
    • 데이터 경쟁은 테스트로 잡기 어려워요. 특정 하드웨어와 JIT 상태에서만 드러나요. "테스트를 통과했다"는 근거가 되지 못하고, 코드를 읽어 happens-before 관계가 있는지로 판단해야 해요.
    핵심 정리
    • 동기화 없이는 다른 스레드의 쓰기가 보인다는 보장이 없음
    • happens-before가 있어야 가시성 보장(락, volatile, final, 스레드 시작)
    • volatile = 가시성 O, 원자성 X. 불변 객체가 가장 단순한 해법
    셀프 체크
    1. volatile int counter에 여러 스레드가 counter++를 하면 왜 값이 맞지 않나요?
    답 보기

    volatile은 각각의 읽기와 쓰기가 다른 스레드에 보이게 할 뿐, 읽기-더하기-쓰기 세 단계를 하나로 묶어 주지 않아요. 두 스레드가 같은 값을 읽고 각자 1을 더해 쓰면 증가 하나가 사라져요. 복합 연산의 원자성이 필요하므로 AtomicInteger의 incrementAndGet이나 락을 써야 해요.

    7장 락, 원자 변수, 동시성 컬렉션

    java.util.concurrent의 도구와 고르는 기준

    synchronized

    모든 객체는 모니터 락을 가져요. synchronized 블록에 들어갈 때 잡고 나올 때(예외로 나와도) 풀어요. 같은 스레드가 이미 가진 락을 다시 잡을 수 있어요(재진입).

    규칙: 같은 상태를 건드리는 모든 코드가 같은 락을 써야 해요. 쓰기만 잠그고 읽기는 안 잠그면 소용없어요.

    ReentrantLock

    synchronized로 안 되는 것이 필요할 때 써요. 시간 제한 획득(tryLock), 대기 중 인터럽트, 조건 변수 여러 개, 공정성 옵션. 대신 finally에서 직접 풀어야 해요.

    원자 변수와 CAS

    AtomicInteger, AtomicReference는 락 없이 원자적 갱신을 해요. 바탕은 CAS(compare-and-swap)예요. "값이 내가 읽은 그대로면 새 값으로 바꾸고, 아니면 실패"를 CPU 명령 하나로 실행하고, 실패하면 다시 읽어서 재시도해요.

    • 경쟁이 적으면 락보다 빠르고 스레드가 잠들지 않아요.
    • 경쟁이 심하면 재시도가 반복돼요. 통계용 카운터는 LongAdder가 나아요.

    동시성 컬렉션

    컬렉션특징쓰는 곳
    ConcurrentHashMap버킷 단위 잠금, 읽기는 잠금 없음공유 맵의 기본
    CopyOnWriteArrayList쓸 때마다 배열 전체 복사, 읽기는 잠금 없음읽기가 압도적이고 쓰기가 드문 목록(리스너)
    BlockingQueue 계열비면 꺼내는 쪽이, 차면 넣는 쪽이 대기생산자-소비자, 스레드풀 작업 큐

    컬렉션이 스레드 안전해도 여러 호출을 묶은 동작은 안전하지 않아요. if (!map.containsKey(k)) map.put(k, v)는 경쟁 조건이에요. putIfAbsent, computeIfAbsent 같은 원자 메서드를 써요.

    백엔드에서는 스프링의 싱글톤 빈은 모든 요청 스레드가 공유해요. 빈의 필드에 요청별 데이터를 두면 스레드 안전 문제가 생겨요. 빈은 상태 없이 두고, 꼭 필요한 공유 상태(로컬 캐시, 카운터)는 위의 동시성 도구로 감싸요. SimpleDateFormat처럼 스레드 안전하지 않은 객체를 정적 필드로 공유하는 것도 같은 실수예요.
    시니어 심화
    • 락의 범위는 불변식의 범위예요. 두 변수가 함께 맞아야 한다면(하한과 상한, 목록과 그 크기) 각각이 원자 변수여도 소용없어요. 둘을 하나의 락으로 묶거나 하나의 불변 객체로 합쳐 참조를 통째로 교체해요.
    • 외부 코드를 락 안에서 호출하지 마세요. 콜백, 리스너, 오버라이드 가능한 메서드를 락을 쥔 채 부르면 그 코드가 다른 락을 잡거나 오래 걸릴 수 있어요. 데드락과 긴 대기의 대표 원인이에요.
    • ABA 문제: CAS는 값이 A였다가 B가 됐다가 다시 A가 된 것을 구분하지 못해요. 참조를 재사용하는 자료구조에서 문제가 되고, 버전 번호를 함께 비교하는 AtomicStampedReference로 풀어요.
    핵심 정리
    • 같은 상태에는 같은 락. synchronized가 기본, 기능이 더 필요하면 ReentrantLock
    • 원자 변수 = CAS 재시도. 경쟁 심한 카운터는 LongAdder
    • 동시성 컬렉션도 복합 동작은 원자 메서드로
    셀프 체크
    1. ConcurrentHashMap을 쓰는데도 "없으면 넣기" 코드에서 중복 생성이 발생했습니다. 원인과 해결을 말해보세요.
    답 보기

    조회와 삽입이 각각은 스레드 안전하지만 둘 사이에 다른 스레드가 끼어들 수 있어요. 두 스레드가 동시에 "없음"을 확인하고 각자 값을 만들어 넣으면 중복 생성이 돼요. 확인과 삽입을 하나의 원자 연산으로 해 주는 computeIfAbsent를 써야 해요. 이 메서드는 키별로 생성 함수를 한 번만 실행해요. 다만 그 함수 안에서 같은 맵을 다시 수정하면 안 돼요.

    8장 스레드풀, CompletableFuture, 가상 스레드

    작업과 스레드를 분리한다

    왜 풀인가

    스레드는 만드는 비용이 있고 각자 스택 메모리를 가져요. 요청마다 새로 만들면 부하가 몰릴 때 스레드가 무한히 늘어 서버가 죽어요. 풀은 스레드를 재사용하고 동시에 도는 작업 수에 상한을 둬요.

    ThreadPoolExecutor의 동작 순서

    1. 실행 중인 스레드가 코어 크기보다 적으면 새 스레드를 만든다.
    2. 코어가 찼으면 큐에 넣는다.
    3. 큐도 찼으면 최대 크기까지 스레드를 더 만든다.
    4. 그것도 찼으면 거부 정책을 실행한다.

    큐가 차야 스레드가 늘어난다는 점이 직관과 달라요. Executors의 편의 메서드는 큐나 스레드 수가 무제한인 풀을 만들기 때문에, 운영 코드에서는 큐 크기와 거부 정책을 직접 정해서 만들어요.

    풀 크기

    • CPU 작업: 코어 수 근처. 더 많아도 문맥 전환만 늘어요.
    • I/O 작업: 대기 시간이 길수록 더 많이. 대략 코어 수 × (1 + 대기 시간 / 계산 시간). 실제로는 하위 시스템이 받아낼 수 있는 동시 요청 수가 상한이에요.

    CompletableFuture

    비동기 작업의 결과를 나타내고, 끝나면 이어서 할 일을 연결할 수 있어요.

    CompletableFuture.supplyAsync(() -> loadUser(id), pool)
          .thenCombine(supplyAsync(() -> loadOrders(id), pool), Profile::new)
          .orTimeout(2, TimeUnit.SECONDS)
          .exceptionally(e -> Profile.empty());

    실행기를 지정하지 않으면 공용 풀(ForkJoinPool.commonPool)에서 돌아요. 이 풀은 크기가 작고 프로세스 전체가 공유해요.

    가상 스레드

    JVM이 관리하는 가벼운 스레드예요. 블로킹 호출을 만나면 OS 스레드를 붙잡지 않고 내려와서, 적은 수의 OS 스레드 위에서 아주 많은 가상 스레드가 돌아요. 요청마다 스레드 하나를 쓰는 단순한 코드 그대로 높은 동시성을 얻어요.

    백엔드에서는 공용 풀에서 블로킹 I/O를 하면 병렬 스트림과 다른 비동기 작업이 전부 같이 멈춰요. I/O용 실행기를 따로 만들어 명시적으로 넘기세요. 그리고 풀의 스레드에는 이름을 붙여요. 스레드 덤프에서 pool-3-thread-7만 보이면 무슨 풀인지 알 수 없어요. 종료할 때는 새 작업을 막고 진행 중인 작업을 기다린 뒤 닫아요.
    시니어 심화
    • 거부는 설계의 일부예요. 큐가 찼을 때 무엇을 할지(호출자가 직접 실행해 속도를 늦춤, 즉시 실패, 가장 오래된 것 버림)를 정하지 않으면 과부하에서의 동작이 우연에 맡겨져요.
    • 가상 스레드는 풀로 묶지 않아요. 만드는 비용이 싸니 작업마다 새로 만들어요. 그러면 스레드 수가 더 이상 동시성 상한이 아니므로, DB나 외부 API로의 동시 호출 수는 세마포어로 따로 제한해야 해요.
    • 가상 스레드는 CPU 작업을 빠르게 하지 않아요. 이득은 블로킹 대기가 많은 워크로드에서만 나와요. 스레드 로컬에 무거운 객체를 캐시하던 코드는 스레드 수가 폭증하면서 메모리 문제가 돼요.
    • 문맥 전파: 트레이스 ID, 보안 컨텍스트 같은 스레드 로컬 값은 다른 스레드로 넘어가지 않아요. 비동기 경계마다 전파하는 장치가 있는지 확인하세요.
    핵심 정리
    • 풀 = 스레드 재사용 + 동시성 상한. 코어 → 큐 → 최대 → 거부 순
    • 큐 크기와 거부 정책을 직접 지정. 공용 풀에서 블로킹 금지
    • 가상 스레드 = 블로킹이 싼 스레드. 동시성 제한은 세마포어로
    셀프 체크
    1. 코어 10, 최대 50, 무제한 큐로 만든 스레드풀에서 부하가 몰려도 스레드가 10개를 넘지 않았습니다. 왜인가요?
    답 보기

    스레드풀은 코어 스레드가 다 차면 작업을 큐에 넣고, 큐가 가득 찼을 때만 최대 크기까지 스레드를 늘려요. 큐가 무제한이면 가득 차는 일이 없으니 최대 크기 설정은 쓰이지 않고, 작업은 큐에 끝없이 쌓여요. 결과는 응답 지연 증가와 메모리 고갈이에요. 큐에 상한을 두고 거부 정책을 정해야 최대 크기가 의미를 가져요.

    4부 진단

    9장 진단 도구

    추측하지 않고 본다

    스레드 덤프

    모든 스레드가 지금 무엇을 하고 있는지의 스냅샷이에요. jcmd <pid> Thread.print 또는 jstack으로 떠요.

    • RUNNABLE: 실행 중이거나 I/O 대기(소켓 읽기는 RUNNABLE로 보여요).
    • BLOCKED: 모니터 락을 기다림. 누가 그 락을 쥐고 있는지도 나와요.
    • WAITING / TIMED_WAITING: 조건이나 시간을 기다림. 빈 풀의 스레드는 정상적으로 이 상태예요.

    한 번만 떠서는 알 수 없어요. 몇 초 간격으로 서너 번 떠서, 계속 같은 자리에 있는 스레드를 찾아요.

    힙 덤프

    힙에 있는 모든 객체의 스냅샷이에요. jcmd <pid> GC.heap_dump로 뜨고 분석 도구(Eclipse MAT 등)로 열어요. 뜨는 동안 애플리케이션이 멈추고 파일이 힙만큼 커요. 운영에서는 트래픽을 뺀 인스턴스에서 떠요.

    GC 로그

    -Xlog:gc*로 켜요. 비용이 거의 없으니 운영에서도 항상 켜 둬요.

    JFR (Java Flight Recorder)

    JVM에 내장된 이벤트 기록기예요. GC, 락 대기, 할당, I/O, 메서드 샘플을 낮은 부하로 계속 기록해요. 문제가 난 뒤에 "그때 무슨 일이 있었나"를 볼 수 있다는 점이 다른 도구와 달라요.

    증상별 출발점

    증상먼저 볼 것
    CPU가 높다스레드별 CPU 사용량 → 그 스레드의 스택
    응답이 멈췄다스레드 덤프 여러 번(BLOCKED, 풀 고갈)
    주기적으로 느리다GC 로그의 멈춤 시간
    메모리가 계속 는다GC 후 늙은 세대 추세 → 힙 덤프
    백엔드에서는 장애가 나면 재시작하기 전에 스레드 덤프부터 떠요. 재시작하면 증거가 사라져요. 덤프 수집을 스크립트로 만들어 두고, 쿠버네티스라면 종료 전 훅에서 자동으로 남기게 할 수 있어요. 스프링 부트의 액추에이터는 스레드 덤프와 힙 덤프 엔드포인트를 제공하지만, 인증 없이 열어 두면 메모리 안의 비밀이 그대로 유출돼요.
    시니어 심화
    • 샘플링 프로파일러의 편향: 전통적인 프로파일러는 스레드가 안전하게 멈출 수 있는 지점에서만 샘플을 떠서 실제 뜨거운 코드를 잘못 짚어요. 이 편향이 없는 방식의 프로파일러(async-profiler, JFR)를 써요.
    • 벽시계 시간과 CPU 시간을 구분하세요. CPU 프로파일에는 기다리는 시간이 안 나와요. 응답은 느린데 CPU는 한가하면 락 대기나 I/O 대기를 보여주는 벽시계 프로파일이 필요해요.
    • 연속 프로파일링: 낮은 비율로 항상 기록해 두면, 배포 전후를 비교하거나 지나간 장애 시점을 되돌려 볼 수 있어요. 문제가 재현되기를 기다릴 필요가 없어져요.
    핵심 정리
    • 스레드 덤프는 여러 번 떠서 비교. BLOCKED와 풀 고갈을 찾음
    • GC 로그와 JFR은 운영에서 항상 켜 둠
    • 재시작 전에 증거 수집. 진단 엔드포인트는 보호
    셀프 체크
    1. 서버가 응답하지 않는데 CPU 사용률은 낮습니다. 무엇을 어떤 순서로 확인하나요?
    답 보기

    CPU가 한가하다는 것은 스레드들이 무언가를 기다리고 있다는 뜻이에요. 스레드 덤프를 몇 초 간격으로 여러 번 떠서 요청 처리 스레드들이 어디에 멈춰 있는지 봐요. 같은 락을 기다리며 BLOCKED라면 그 락을 쥔 스레드가 무엇을 하는지 따라가고, 커넥션 풀에서 커넥션을 기다린다면 풀 고갈이므로 커넥션을 쥔 스레드들을 봐요. 소켓 읽기에서 멈춰 있다면 하위 시스템이 응답하지 않는 것이니 타임아웃 설정과 상대 시스템을 확인해요.

    실습

    실습 과제

    직접 문제를 만들고 도구로 찾아보는 것이 가장 빨라요.

    • 1장 같은 라이브러리의 두 버전을 의존성에 넣어 NoSuchMethodError를 재현하고 의존성 트리에서 원인을 찾기
    • 3장 만료 없는 정적 Map에 계속 넣는 누수를 만들고, OOM 시 자동 생성된 힙 덤프에서 붙잡고 있는 참조 경로 찾기
    • 4~5장 같은 부하를 Parallel, G1, ZGC로 각각 돌려 GC 로그의 멈춤 시간 분포와 처리량 비교
    • 6장 volatile 없는 종료 플래그로 끝나지 않는 루프 재현. volatile을 붙이면 끝나는지 확인
    • 7장 스레드 8개로 int, volatile int, AtomicInteger, LongAdder 카운터를 각각 증가시켜 정확도와 속도 비교
    • 8장 무제한 큐 풀과 유한 큐 + 거부 정책 풀에 처리 속도보다 빠르게 작업을 넣고 메모리와 지연의 변화 관찰
    • 9장 두 락을 반대 순서로 잡는 데드락을 만들고 스레드 덤프에서 찾기. JFR로 60초 기록 후 락 대기 이벤트 확인
